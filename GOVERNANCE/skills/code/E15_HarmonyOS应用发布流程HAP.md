# E15 · HarmonyOS 应用发布流程：HAP 打包、AGC 上架、审核流程、版本管理

> 适用项目：harmony-app（铃语，鸿蒙适老化股票异动播报）。Stage 模型，compatibleSdkVersion 20 / targetSdk 26，纯 ArkTS、零三方依赖。本文自包含，可独立阅读，是发版操作的作业指导书。

## 1. 发布总览

铃语的发布链路：本地/CI 构建 → 签名 → 手工或 AGC 云端出包 → AGC 创建版本并提交审核 → 审核通过上架分发 → 线上观察与版本管理。三个前置事实决定流程形态：

1. **签名是硬前提**：无正确签名的 HAP 无法安装调试，更无法上架；发布证书、Profile 必须在 AGC 申请，与包名绑定；
2. **Push 依赖 AGC 侧配置**：`PushService.ets` 当前是占位封装，AGC 未开通推送前，端侧只有 `AlertPoller` 5 秒前台轮询兜底，**这不阻塞上架**——上架的判定标准是"功能如实、主流程可用"，轮询兜底正是为此设计的；
3. **FEED_URL 未正式落地**：服务未连通时首屏显示带"示例"字样的演示卡（首屏永不空白约束）。上架前必须在商店截图与版本说明里如实写明演示态，审核对"截图与实际不符"零容忍，如实标注反而安全。

## 2. HAP 打包

### 2.1 发布版构建

用 DevEco Studio 或命令行出 release 包（命令行形态）：

```
hvigorw assembleHap --mode module -p product=default -p buildMode=release
```

产物在 `build/default/outputs/default/` 下。App Pack（.app）用于上架，HAP 用于本地安装调试。铃语单模块无特性包，形态简单。

### 2.2 签名

发布签名材料四件套：发布证书（.cer）、发布 Profile（.p7b）、私钥（.p12）、密钥口令。在 AGC"证书、APP ID 与 Profile"页申请，与包名（如 `com.lingyu.alerts`，示意）一一绑定。配置进 `build-profile.json5` 的 signingConfigs，或用 DevEco 的 Structure 签名向导。三条纪律：

- 私钥与口令只存在构建机安全位置或 CI 密钥管理里，**绝不进仓库**（对应 E14 红线：不泄露任何 Token/密钥）；
- 调试证书与发布证书严格分离，发布包绝不用调试签名；
- Profile 有有效期，过期前在 AGC 续期，避免发版当日卡壳。

### 2.3 打包前检查表

- [ ] `module.json5` 的 versionCode/versionName 已递增（见第 5 节规则）；
- [ ] targetSdk 26 / compatibleSdkVersion 20 与目标上架市场要求一致；
- [ ] 权限清单复核：仅 INTERNET + 通知，各带 reason（E14 检查表同源）；
- [ ] 全仓 grep 无 token、无 `http://`、无上游名词；
- [ ] release 日志已收敛（debug 级关闭）；
- [ ] 演示卡文案与"示例"角标在断网态实测可见；
- [ ] 图标、启动图（适老化高对比）已更新且无占位图残留。

## 3. AGC 上架

### 3.1 账号与资产准备

AppGallery Connect（developer.huawei.com/consumer/cn/agcp）上完成：开发者账号实名（个人或企业，企业需对公验证）、创建应用（填包名、选择默认语言、分类建议"财经资讯"类目）、完善应用资产。

应用资产清单（适老化项单独列出，都是过审关键）：

| 资产 | 要求 |
| --- | --- |
| 应用图标 | 高对比、无小字 |
| 截图 | 3~5 张，须为真机实拍：卡片流大字界面、播报详情、演示态 |
| 应用描述 | 如实写"股票异动播报工具，不构成投资建议" |
| 隐私政策 URL | 明确列出：收集什么（无个人资料，仅设备级偏好）、为何收集、如何存储 |
| 版本说明 | 写明当前数据源状态（演示/灰度）与 Push 未开通时的轮询兜底 |
| 备案信息 | 按上架目标市场要求提供 ICP 备案等合规材料 |

### 3.2 提交包与发布方式

在"版本管理"创建版本，上传 App Pack，选择发布范围：

- **申请全网发布**：审核通过后全量上架；
- **分阶段发布（如有灰度选项）**：先小比例放量，观察崩溃率与老人反馈再放量——铃语建议首版走灰度，适老化产品的可用性问题在真人手里才暴露得出来。

上架即分发，注意红线：不涉对外公开收费（应用本身免费、无内购、无付费墙），商店定价设为免费，不申请付费类目。

### 3.3 内容合规自查

提交前对照三条红线自查一遍（这是"信号松绑但禁三条"约束在发布环节的落点）：

1. 应用描述、截图、版本说明中**不出现承诺收益/保本表述**（"稳赚""保收""必涨"零出现）；
2. **无催促性指令**（"马上买入""抓紧进场"零出现；卡片流文案由云侧红线词表 + 端侧 E11 `isSpokenSafe` 双层把关，商店素材同标准）；
3. **不涉对外公开/收费**：应用内容免费面向个人使用，描述中不引导付费群、收费服务。

财经资讯类应用审核还会看是否展示免责声明：在"关于"页与首次启动页放一句"本应用信息仅供参考，不构成投资建议"，这句话是过审刚需。

## 4. 审核流程

### 4.1 流程与时长

提交后进入华为审核队列，一般形态：自动检测（包完整性、签名、权限、API 兼容性）→ 人工审核（功能、内容、截图一致性、隐私政策）→ 出结果。常规一至数个工作日，以 AGC 后台实际状态为准。状态流转：草稿 → 待审核 → 审核中 → 已发布 / 被驳回。

### 4.2 常见驳回点与预防

| 驳回点 | 铃语的风险位 | 预防 |
| --- | --- | --- |
| 截图与实际不符 | 截图用了真实数据、线上却是演示态 | 截图与版本说明如实标注演示态 |
| 功能不完整 | Push 未开通、FEED_URL 未落地 | 轮询兜底 + 演示卡保证主流程可用；描述不夸大 |
| 隐私政策缺失/不符 | 未列全数据用途 | 按 3.1 清单逐项核对 |
| 权限与功能不匹配 | 多申权限 | E14 权限盘点表为唯一依据 |
| 崩溃/白屏 | 断网首启 | "首屏永不空白"已内建，发版前断网真机走查 |
| 违规话术 | 财经类收益承诺 | 三条红线自查（3.3） |

被驳回后按驳回意见整改，重新提交；同一版本号可复用，versionCode 不必因驳回而跳增。

### 4.3 发版前真机走查（30 分钟清单）

断网冷启动（演示卡出现、无白屏无崩溃）→ 联网冷启动（真实卡片流加载）→ 深链拉起（带 alertId 的 want 定位到卡片，E12 场景）→ 点播 TTS（AudioPlayer 出声、连点不叠音）→ 前后台切换（轮询停启正确、无异常耗电）→ 大字号下布局不溢出不截断 → 系统返回键行为符合 E12 双击退出约定。

## 5. 版本管理

### 5.1 号码规则

- `versionCode`：正整数，每次发布递增 1（AGC 要求新版本高于历史最大值）；建议直接用单调递增计数，不编码日期，简单即正确；
- `versionName`：`主.次.修` 三段（如 1.2.0）。主版本号改变留给架构级变化（如 Push 通道整体切换），次版本号新功能（如深链定位上线），修订号修 bug 与文案调整；
- 约定：versionCode 与 git tag 一一对应（`v1.2.0`），tag 打在发布提交上，可追溯每个线上包对应的源码。

### 5.2 发布节奏

- 固定节奏优于堆叠发布：小步快跑，每次包只含一个主题的变更，出问题回滚定位快；
- 每次发版在 GOVERNANCE 目录追加发版记录：版本号、日期、主要内容、已知问题、对应 tag；
- 驳回修复走修订号递增，不走新次版本。

### 5.3 升级与回滚

- AGC 支持版本管理里查看各版本状态与指标；新版本上架后老用户按市场策略更新；
- 灰度期间发现重大问题：立即在 AGC 停止该版本分发（下架该版本），修复后提更高 versionCode 的修复版——**不能复用号码回退**，这是商店侧的硬规则；
- 端侧要为"跨版本升级"留余地：本地存储结构变化需迁移（读旧结构 → 写新结构 → 删旧键），迁移失败不丢主流程，最坏退演示卡重载。

### 5.4 与架构演进对齐

两个已知的未来变更已排入版本路线：AGC 配置完成后，`PushService.ets` 从占位封装切到华为 Push Kit REST（对应一次次版本号），FEED_URL 切到 X 服务器正式源（契约 AlertFeed 不变，端侧零改动或仅配置变更）。每次这类切换都按"先灰度、再放量、发版记录写明切换项"执行，保证老人端无感升级。

### 5.5 隐私政策的内容要点

隐私政策不是走过场的法务文本，审核会对照实际行为核验。铃语的隐私政策必须如实覆盖四块：一是收集清单——端侧不收集姓名手机号等个人身份信息，仅在本机存储播报偏好与已播历史，清楚写明"这些数据不上传服务器"；二是数据用途——偏好仅用于调节播报体验，历史仅用于去重标记；三是存储与删除——数据存于设备本地，卸载应用即彻底删除，用户可在设置页手动清空；四是第三方组件声明——本项目零三方依赖、无广告、无统计埋点 SDK，这句话要明确写出，反而是加分项。政策文本与端侧实际行为必须逐条对得上：写"不上传"就必须在代码层面核实没有上传路径，任何一处不符都可能成为驳回甚至下架的理由。

### 5.6 发版记录模板

每次发版在 GOVERNANCE 目录按统一模板追加记录，字段固定：版本号与 versionCode、发版日期、对应 git tag、本版主要内容（按"新增/修复/文案"三分类列出）、已知问题与处置计划、灰度比例与放量结果、审核结果（通过日期或驳回原因摘要）、冷启动实测耗时。模板的价值在于半年后回看时，任何一个版本的"是什么、为什么、结果如何"都不需要考古。驳回记录尤其要留：同类驳回原因出现第二次就是流程漏洞，要么检查表缺项，要么检查表有项没执行。

## 6. 落地清单

- [ ] 签名四件套就位，私钥不进仓库，调试/发布签名分离；
- [ ] 打包前检查表全绿才出包；
- [ ] AGC 资产（截图如实、隐私政策、免责声明、免费声明）齐备；
- [ ] 三条红线 + 免责声明自查通过；
- [ ] 30 分钟真机走查通过；
- [ ] versionCode 递增、tag 对应、发版记录入 GOVERNANCE；
- [ ] 首版灰度，问题版本走更高 versionCode 修复；
- [ ] 隐私政策四要点与端侧行为逐条核对一致；
- [ ] 发版记录按模板入档，驳回原因留痕。
