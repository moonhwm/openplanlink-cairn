# A35 安全审查——本地数据存储安全、网络请求安全、敏感信息处理

> 项目：harmony-app（鸿蒙适老化股票异动播报应用「铃语」），纯 ArkTS + 云函数，零三方依赖。
> 本篇自包含：所有结论引用仓库文件与行号或本次实跑命令。最高红线：不泄露任何 Token/密钥；错误与攻击场景下不得向老人展示催促性或诱导性内容。

## 一、审查方法与威胁模型

方法：通读 `entry/src/main/ets/` 全部 8 个文件与 `module.json5`、`build-profile.json5`、`entry/obfuscation-rules.txt`、`entry/oh-package.json5`；实跑 `grep -rni "token\s*=\s*['\"]|apikey|api_key|secret" entry/src/main/ets/`，输出 `NO HARDCODED SECRETS FOUND`。共享上下文所述 Tushare token 失效（40101）降级东财 API 发生在服务端，端侧不持有任何数据源凭证，与红线一致。

威胁模型（适老化场景四类攻击者画像）：**诈骗分子**——最危险，目标是借应用形貌向老人注入诱导内容（伪造异动、收益暗示）；**好奇邻居/家属**——物理接触设备，翻看本地数据；**中间人**——劫持网络链路替换响应；**恶意应用**——同机其他应用，尝试拉起本应用或读取其数据。后文发现按此四类画像评估实际可达性。

## 二、本地数据存储安全

### 2.1 存储内容与敏感度盘点

本地持久化唯一入口为 Preferences，文件名 `stockpulse_settings`（`SettingsService.ets:9`），键名清单见 10-21 行。逐键评级：

| 键 | 内容 | 敏感度 | 判定 |
|---|---|---|---|
| watchlist | 自选股代码 | 低（可推断投资偏好，属个人信息） | 需隐私声明覆盖 |
| broadcast / font_level / elderly_mode / theme / auto_theme / dnd_* | 界面偏好 | 无 | 合规 |
| feed_url | 数据源地址 | 低 | 见 2.2 注入面 |
| read_alerts | 已读异动 ID，上限 200（399-402 行） | 低 | 合规 |
| play_history | 播报历史：headline/时间戳，上限 50（433-439 行） | 中（等于「何时看过什么股票异动」的行为画像） | 需隐私声明覆盖 |

沙箱评估：鸿蒙 Preferences 落于应用沙箱目录，同机恶意应用无法直接读取（系统级隔离，「好奇邻居」画像需拿到解锁设备才能看，属于设备物理占有场景，不在应用层防线内）。结论：**当前不存储任何凭证、Token、口令**，弱个人数据集中在自选股与播报历史两类，量级小且有上限截断，可接受；发布前隐私政策必须显式声明这两项的收集、本地留存属性与 50/200 条上限，否则属告知不充分。

### 2.2 feed_url 注入面（发现 P1-A）

设置页向用户开放数据源编辑（`Settings.ets:506-536` TextInput + 524-530 保存），`SettingsService.setFeedUrl`（363-373 行）**未做任何协议或域名校验**即落盘，`AlertPoller.fetchLatest` 每轮轮询直接采用（`AlertPoller.ets:38-45`）。双重风险：老人误触输入失效地址（可用性故障）；被诈骗分子诱导填入攻击者控制的 http 地址（`Settings.ets:532` 的提示文案「本机联调可填局域网 IP」反而给了话术模板），此后 feed 内容完全受攻击者支配——伪造异动一旦含「即将大涨」类文案，直接触碰「不承诺收益/保本」红线，且受害端是防备最弱的适老用户。

整改（保住局域网联调用途，收紧其余）：

```typescript
// SettingsService.setFeedUrl 入口校验
static isFeedUrlAllowed(url: string): boolean {
  if (url.startsWith('https://')) { return true; }
  // 仅放行局域网 http（联调刚需），公网 http 一律拒绝
  return /^http:\/\/(192\.168\.|10\.|172\.(1[6-9]|2\d|3[01])\.)/.test(url);
}
// 保存前：非法则提示「地址要以 https:// 开头」并不落盘
```

### 2.3 未来凭证存储规范（前瞻）

一旦引入需鉴权的数据源或用户账号，禁止写入 Preferences，必须改用关键资产存储（Asset Store Kit，`@kit.AssetAssetKit` 系列）或 HUKS 密钥管理，属性级加密落盘。本条登记为硬性规范，防止后续迭代图省事回退。

## 三、网络请求安全

### 3.1 传输与超时

全仓库三个硬编码端点均为 https：数据源 `AlertPoller.ets:10`、token 上报 `PushService.ets:11`、SettingsService 默认 feed 回退值（353-359 行三处）。超时齐备：轮询 connect/read 各 5s（`AlertPoller.ets:43-44`）、token 上报各 5s（`PushService.ets:81-83`）。证书校验未做任何关闭/自签配置，走系统默认 TLS 校验，合规。唯一例外是 2.2 所述用户可注入 http 地址，整改后收敛。

### 3.2 接口无鉴权与伪造 feed 风险（发现 P1-B）

alerts 拉取为无凭证 GET（`AlertPoller.ets:41-45`），token 上报为无签名 POST（`PushService.ets:80-86`）。公开可拉在演示期是特性，但意味着**端到端无法验证异动内容真实性**：中间人或源站被篡改都可注入诱导内容（对应威胁画像一、三）。端侧防线（AlertFeed 契约追加字段，属演进不属推翻）：

```typescript
// AlertFeed 契约追加：sig?: string（服务端对 items+serverTs 的 HMAC 签名）
// 端侧校验：sig 缺失或校验失败 → 按 ok=false 处理并保留旧数据，绝不渲染未签名内容
```

同时端侧应对 `serverTs`（`model/AlertItem.ets:21`）做新鲜度检查（偏差超阈值视为不可信源），防重放旧异动误导老人。此整改依赖服务端配合，端侧无法独立完成，如实标注。

### 3.3 端侧对畸形数据的防线核查（部分通过）

逐步核对「伪造 feed 能否直接伤害老人」：headline/detail 均直接渲染为 Text（`Index.ets:400-410`），**文本内容原样透传，端侧无内容过滤**；缓解因素有三——播放钮仅在 audioUrl 存在时渲染（390-396 行），伪造音频流需额外通过 prepare 校验；direction 只影响色块颜色（`Index.ets:289-307` 严格三值匹配，畸形值落「平」灰），无注入面；播放内容来自云端 TTS 音频而非文本拼接，端侧无字符串到代码的通道。结论：内容透传本身是产品形态（白话卡片流），防线必须建在签名校验（P1-B）与文案合规（服务端 DKnowC 分类，`model/AlertItem.ets:16` 契约已预留 complianceStatus 字段但端侧未消费——登记为端侧演进项：Unsafe 分类应拒渲染）。

### 3.4 Push Token 上报（合规，两点登记）

上报内容仅 `{ token, bundleName }`（`PushService.ets:85`）：push token 属设备级推送标识，需在隐私政策列明用途（推送异动通知）；bundleName 非个人数据。日志只记录 token **长度**不记录本体（49 行 `token length=${token.length}`），正确脱敏。上报失败仅日志不上重试风暴（87-95 行），无副作用。

## 四、敏感信息处理

### 4.1 日志卫生（逐条核对）

全仓库 hilog 盘点：`EntryAbility.ets:87` 打推送 payload（含 alertId，业务 ID 低敏）；`AlertPoller.ets:72` 打异常响应前 200 字符（诊断用，需注意若服务端未来在响应夹带敏感字段会进日志——登记为服务端契约约束）；`Settings.ets:143` 打 feedUrl（用户自填地址低敏）；`Settings.ets:75,81` 打自选股代码与数量（弱个人信息，release 版建议降噪）；`PushService.ets:49` 仅 token 长度（正确脱敏）。**未发现 token/密钥/个人身份信息入日志**。登记：release 版建议关闭 info 级日志或统一按 `DOMAIN=0x0001`（各文件统一，已具备按域过滤条件）做发布过滤。

### 4.2 权限最小化（发现 P2-C）

`module.json5:40-52` 仅声明两条权限：`INTERNET`（必需）与 `KEEP_BACKGROUND_RUNNING`——后者注释自述「R3 预留，当前未实际调用对应 API」（45-47 行）。按最小权限原则，**未使用的权限应在发布前移除**，需要时随 Push 实装一并加回；保留它会让用户在安装时看到一条无法解释的「后台运行」权限提示，损害信任。

### 4.3 对外暴露面（评估通过）

`module.json5:20` `exported: true` 为 home ability 必需；skills 额外暴露三个自定义 action（30-36 行，小艺链路，对应威胁画像四）。可达性推演：外部 want 只能写入 AppStorage 的 `pendingAlertId/autoPlay`（`EntryAbility.ets:45-68`），而 `playById` 仅在**当前已拉取列表内**按 alertId 匹配（`Index.ets:202-210`），未命中即静默清掉——外部无法注入播报内容或 URL，内容面攻击不可达；残余风险仅恶意反复拉起耗电（低危，登记）。`autoPlay` 无消费者问题归属 A31（P2-3），本篇不重复。

### 4.4 发布构建安全（发现 P2-D）

`entry/obfuscation-rules.txt` 实读为占位文件（注释自述「混淆关闭时的占位规则文件」，仅一条 `-keep-property-name`），release 未开启代码混淆，产物类名/字段名可被静态分析。网络协议已定型、接口少，混淆非强制，但建议发布前在 `entry/build-profile.json5` 打开混淆并补全规则，抬升逆向成本。

另登记一处治理差异：`build-profile.json5:8-9` 实际为 `compatibleSdkVersion/targetSdkVersion: "6.0.2(22)"`，与任务上下文所记「compatibleSdkVersion 20 targetSdk 26」不一致。本篇以仓库实值为准，建议在治理台账修正，避免后续按错误版本评估 API 可用性与权限行为差异。

## 五、数据流与攻击面映射

把端侧全部数据流画出，逐条标注暴露面，作为威胁模型的落地视图。**流入一（feed 拉取）**：网络响应 JSON → parse 为 AlertFeed（`AlertPoller.ets:69`）→ items 经 watchlist 过滤（`Index.ets:161-163`）→ 直接渲染。流入内容含 headline/detail（任意文本）、audioUrl（任意 URL）、direction/kind（枚举）。逐字段评估：文本透传已在 3.3 评估，防线在签名与 complianceStatus；**audioUrl 值得单独走查**——它被赋给 AVPlayer（`AudioPlayer.ets:39`），播放器会向该地址发起网络请求，即伪造 feed 可让老人手机向任意 URL 发起拉流请求。缓解：拉流本身不携带任何凭证或用户数据（GET 无 cookie 无 token），泄露的信息仅为「该 IP 在听一段音频」，且地址必须能返回可解码音频才算成功（prepare 校验，`AudioPlayer.ets:41`）；利用价值低，但配合 P1-B 签名校验后此面同时关闭（未签名 feed 根本进不到播放环节）。**流入二（推送 payload）**：data 字符串 → parse 提取 alertId（`EntryAbility.ets:90-94`）→ 仅作列表内匹配键，无渲染无执行，已评估（4.3 节）。**流入三（want 参数）**：alertId/action，类型边界在 A32 10.1 评估，只读比较无注入。**流出一（token 上报）**：3.4 节已评估，仅 token+bundleName。**流出一（本地写入）**：Preferences 全部键值盘点见 2.1，无外发通道。**不出（无）**：本应用不向任何端点上传用户行为数据——play_history 与 read_alerts 只写本地（`SettingsService.ets:390-445`），grep 实证 SettingsService 无任何 http 引用，这是隐私面最好的现状，登记为产品优势并应在隐私声明中明示「播报历史仅存本机」。

## 六、audioUrl 与 TTS 链路的音频安全补充

顺着流入一的 audioUrl 深挖一层。云端 TTS 音频由 generate-tts 产出（共享上下文：alerts.json 的 audioUrl undefined 时端侧按需调用），意味着 audioUrl 可能指向云函数动态生成的临时地址。两个登记项：其一，若临时地址含签名参数（常见 presigned URL 形态），该参数会出现在端侧内存与潜在日志中——当前端侧未打印 audioUrl（grep hilog 实证无此输出），保持即可，规范登记「audioUrl 不得入日志」；其二，动态生成的地址应有短有效期，防止被提取后长期重放（重放一段旧异动音频对老人是直接的误导源），此为服务端契约要求，端侧配合项是播放失败后走 failedId 红字而不是缓存重试旧地址——现有实现每次点按都重新走 play（`Index.ets:249`），无音频缓存，天然满足，登记为正面设计。

## 七、安全审查checklist（可复用模板）

八问清单，供后续迭代复用。一问：仓库内是否有硬编码凭证（grep 三件套 token/apikey/secret）？二问：本地存储逐键评级，凭证类是否零存储、弱个人信息是否进隐私声明？三问：用户可编辑的地址/配置项，落盘前是否白名单校验？四问：网络端点是否全 https、超时是否齐备、证书校验是否默认？五问：外部输入（feed/推送/want）逐字段走查：能渲染什么、能触发什么请求、能写什么存储？六问：日志逐条评级，token 是否只打长度？七问：权限清单与实际调用是否一一对应？八问：对外暴露的 action/exported，恶意构造 want 的可达性终点在哪？本篇即按此跑完的记录：一问对应第一节实跑命令，二问对应 2.1 表，三问产出 P1-A，四问对应 3.1，五问产出第五节数据流映射与 3.3 畸形数据核查，六问对应 4.1，七问产出 P2-C，八问对应 4.3。与 A32 十问、A34 八问配套，构成三类审查的标准操作单。
