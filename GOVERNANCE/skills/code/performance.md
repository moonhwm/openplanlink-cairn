# 性能优化深度审查——并行策略、SDK单例化、alertId确定性与TTS优先级

> 项目：harmony-app（铃语，鸿蒙适老化股票异动播报应用）。审查对象横跨云函数与端侧：`cloudfunctions/functions/fetch-tushare-data/index.js`（全文 683 行，下称主函数文件）、`cloudfunctions/functions/generate-tts/index.js`、`cloudfunctions/functions/get-alerts/index.js`、`cloudfunctions/functions/broadcast-a2a/index.js`，以及端侧 `entry/src/main/ets/pages/Index.ets`、`entry/src/main/ets/services/AlertPoller.ets`。本文自包含，行号均指当前版本。审查日期：2026-09-23。

## 一、审查范围与结论摘要

性能审查在本项目的语境里有明确的验收终点：老年用户打开应用后多快看到真实卡片、点卡片后多快听到播报、云函数的定时任务多快完成一轮。围绕这条体验链，本篇审查四个主题：名称抓取的市场间并行与页面间串行、CloudBase SDK 的单例化、alertId 的确定性生成、TTS 批量生成的优先级排序。

审查结论分四条。第一，主函数文件已有一处漂亮的并行实践——`getDailyMovers` 用 `Promise.all` 让日线查询与名称映射并行（第 350-358 行），但同一文件内的东财分页抓取仍是三层串行（第 171-203 行），是云函数侧最大的单项时延来源。第二，CloudBase SDK 单例化在主函数文件已正确落地（第 27-37 行），但另外三个云函数每次调用都重新 `cloudbase.init`（generate-tts 第 63-66 行、get-alerts 第 28-29 行、broadcast-a2a 第 29-31 行与 119-121 行），单例化的收益只兑现了四分之一。第三，alertId 现行生成方式 `${symbol}_${秒级时间戳}`（第 442、477 行）在同一交易日重复触发时产生"同股异号"的重复条目，去重机制（第 527-535 行）因此部分失效，五百条截留（第 537-540 行）被重复数据挤占；确定性生成可一并修复。第四，TTS 批量生成对信号卡"一视同仁"（第 595 行截前十后并行发出），没有按信号强度排序，额度紧张时最值得播的卡片不保证先拿到语音。四项优化的共同特点是：不推翻任何架构基调，全部在现有函数边界内完成，且彼此独立可分别合入。

## 二、市场间并行+页面间串行：云函数侧的时延总账

### 2.1 现状并行实践的盘点

先把已有的并行资产盘点清楚，避免重复建设。资产一：`getDailyMovers` 内 `Promise.all` 并行发起 daily 查询与 `getStockNameMap`（第 350-358 行），两者无数据依赖——名称映射补的是 name 字段（第 369-374 行），发生在 daily 返回之后的组装阶段，先并行后组装的次序正确。资产二：主入口把合规检查与 TTS 生成放进同一个 `Promise.all`（第 601-627 行），并用 `Promise.allSettled` 容忍单项失败，合规不阻塞语音、语音不阻塞合规，这个设计同时照顾了时延与隔离性。这两处是正确的样板，后续优化应延续其"无依赖才并行、失败要隔离"的两个前提。

### 2.2 串行抓取的时延账本

东财名称抓取的现状是三层串行：四个市场过滤器逐个执行（第 171 行 for）、每市场内逐页推进（第 172-203 行 while）、页间靠"返回条数小于一百"判尾页（第 201 行）。按全市场约五千五百六十只（与硬编码快照 5560 条互证）、单页一百条计，有效请求约五十六页；再按单次往返五百毫秒（同地域网络的保守值）计，纯串行的网络等待约二十八秒。这笔账还没算上：函数冷启动、trade_cal 与 daily 的前置查询、TTS 批处理与存储回写的后置开销。二十八秒的抓取段放在任何一种函数预算里都是灾难性的，这也是现状必须依赖跨调用存储缓存（cache-strategy.md 第三节）把全量抓取摊薄到两日一次的根本原因——缓存是在为串行慢买单。

### 2.3 正确的切分与并行后的账本

并行化的切分原则在 api-strategy.md 第 3.2 节已确立：四个市场过滤器彼此独立、可安全并行；页面之间有"翻到尾页才知道停"的依赖、必须串行。落成代码即"四条串行翻页链并发推进"：`Promise.allSettled(marketFilters.map(fs => fetchMarketNames(fs)))`，每条链内部保持 while 逐页、链与链之间并发，合并时按 ts_code 去重、单链失败不拖垮整体。并行后的账本：总耗时等于最长链的耗时，沪深主板链约十四页即约七秒，相比二十八秒约四倍提速；对东财的瞬时并发被钉死为四（等于市场数），不随优化升级而失控。这里要明确记录一个刻意的不做：**不做页间并行**。页间并行的前提是预知总页数，盲发超出尾页的请求既浪费配额又提高触发风控的概率，而四倍提速已把抓取段从"灾难性"拉回"可接受"，继续压榨的边际收益撑不起复杂度——性能优化停在收益递减的拐点上，是本篇的方法论立场。

### 2.4 与既有并行的组合关系

市场间并行合入后，整个名称获取段的时延形态变为：缓存命中时毫秒级返回（第一、二层），缓存失效时约七秒完成全量抓取（第三层并行化后），且抓取与 daily 查询的并行关系（第 350-358 行）不受影响——`Promise.all` 里 `getStockNameMap` 内部怎么并行是它自己的事，外层只感知一个总时长。需要重排的只有一处：现状 daily 与名称映射并行时，若名称映射要走七秒的抓取链，daily 的十二秒超时预算应从函数总预算中先扣，两者取时长上限而非求和进入总账，这正是 error-handling.md 第 3.1 节预算守恒原则在并行场景的表述。

## 三、CloudBase SDK 单例化：一处已做，三处未做

### 3.1 现状的不一致

主函数文件第 27-37 行是教科书式的单例：模块级 `_cloudbaseApp` 空值检查、`cloudbase.init` 只执行一次、注释写明动机"避免重复 init 导致连接泄漏"。init 的真实成本包括凭证加载、环境信息解析与内部客户端构造，虽非重量级操作，但每次调用都付一遍纯属浪费；更隐蔽的代价是资源治理——重复 init 产生的客户端对象若未被垃圾回收及时回收，连接与句柄会随调用量累积，长周期运行下构成慢性泄漏风险。主函数文件因为单实例内存缓存的存在天然高频复用 app 实例，是四件里最需要单例也最先做对的。

另外三件的情况：generate-tts 的 `getCloudBaseApp`（第 63-66 行）每次调用都 init 一次，而该函数一次执行内会多次取 app——checkCache（第 74 行）、saveCache（第 98 行）、updateAlertAudioUrl（第 124 行）、uploadToStorage（第 312 行）各取一次，即单次调用至少四次 init；get-alerts 每次 HTTP 请求 init 一次（第 28-29 行），端侧五秒轮询之下它是四件里调用频率最高的，浪费次数也最多；broadcast-a2a 在 getLatestAlerts（第 29-31 行）与 sendPushNotification（第 119-121 行）各 init 一次，且该函数还有 Web 模式常驻进程（第 258-292 行），常驻进程内每次请求重复 init 的累积效应最值得警惕。

### 3.2 统一方案与约束

修复是把主函数文件的写法原样推广，每个文件一份：

```js
// CloudBase SDK 单例（与主函数文件 27-37 行同一写法）
let _cloudbaseApp = null;
function getCloudbaseApp() {
  if (!_cloudbaseApp) {
    const cloudbase = require('@cloudbase/node-sdk');
    _cloudbaseApp = cloudbase.init({ env: process.env.TCB_ENV || '<默认环境ID>' });
  }
  return _cloudbaseApp;
}
```

推广时有三条约束。其一，单例是**文件内单例**而非跨函数共享——云函数间本就进程隔离，各文件各自持有即可，不要为"全局一个"发明跨函数机制。其二，env 值来源保持现状：环境变量优先、缺省回退到代码内的默认环境标识，这一回退值是环境 ID 而非密钥，不违反"不泄露任何 Token/密钥"的红线（真正的密钥均在平台环境变量注入，代码中零字面量）。其三，generate-tts 推广单例时顺手把四次取 app 收敛为入口取一次后传参，函数内四个使用点签名加一个 app 参数——这与 cloud-function-refactor.md 的依赖注入原则同向，两件事可在同一次提交完成。收益量化：get-alerts 在五秒轮询峰值下每小时约七百二十次调用，每次省一次 init；generate-tts 每次调用省三次；数字不大，但这是零风险、零复杂度的纯赚项，且消除了常驻进程的慢性泄漏隐患。

## 四、alertId 确定性生成：从"同股异号"到"同股同号"

### 4.1 现行生成方式的三个问题

`createAlertItems` 第 442 行取秒级时间戳 `now`，第 477 行拼出 `alertId = \`${symbol}_${now}\``。这个设计的隐患在"同一交易日的重复触发"场景下暴露。云函数由定时触发器驱动，同一交易日内多次触发是设计内行为（捕捉盘中变化），但时间戳后缀使每次触发都给同一只股票发一个新 ID：上午十点的 `600176_1771234500` 与下午两点的 `600176_1771250000` 是两个条目。问题有三。其一，去重失效：第 527-535 行按 alertId 去重的本意是"同一异动只存一条"，同股异号使每次触发都成为"新异动"，alerts.json 里同一股票同一天的条目随触发次数线性增长。其二，截留挤占：第 537-540 行只保留最新五百条，重复条目挤掉了本可保留的异动多样性，活跃交易日里五百条上限可能被几十只股票的反复触发填满。其三，端侧去重联动失效：端侧 `readAlertIds`（Index.ets 第 134、361 行）按 alertId 记已读，同股异号使"读过的股票"反复以未读姿态出现，金色圆点提示（Index.ets 第 361-365 行）对老人失去"这条我看过了"的语义。需要说明现行方式的唯一好处：拉起定位用 alertId 找卡片（EntryAbility.ets 第 25-28 行设置、Index.ets 第 138-144 行消费）在任何时刻都能唯一命中，改动时不得破坏这一行为。

### 4.2 确定性生成方案

修复方案是把时间维度从"触发时刻"改为"交易日"：`alertId = \`${symbol}_${tradeDate}\``。tradeDate 已由 `getLatestTradeDate` 给出（yyyymmdd 八位串，第 278-339 行），在 `createAlertItems` 的调用上下文中可直接取得（`getDailyMovers` 第 346 行已取，沿调用链传入即可）。效果：同一股票同一交易日无论触发多少次，alertId 恒定；重复触发自然落入第 527-535 行的去重合并——新数据覆盖旧数据（同一键后写覆盖先写），alerts.json 里每股票每日至多一条，五百条截留可覆盖五百个"股票×日"组合而非五百次触发。端侧联动随之修复：已读标记按股票×日生效，金点语义恢复。拉起定位兼容性论证：同一股票当日多条卡片本就是同一异动的更新，定位到该股票当日卡片正是用户点通知时的心智预期；跨日场景下 alertId 含日期天然可区分。两个边界要交代：其一，若未来引入"同一股票同日多次异动都要独立成卡"的产品需求（如盘中两次不同幅度的脉冲），方案需升级为 `${symbol}_${tradeDate}_${absPct 取整}` 或引入序号，当前按日粒度的产品形态下不需要；其二，`demo-1`（Index.ets 第 15 行）等演示卡的 ID 与真实 ID 空间无碰撞风险（格式不同），无需处理。

## 五、TTS 优先级排序：把额度花在刀刃上

### 5.1 现状的一视同仁与额度的现实约束

主入口第 595 行对信号卡（涨跌幅不低于百分之八，第 451 行判定）截取前十后立即 `Promise.allSettled` 并行发起 generate-tts 调用（第 611-621 行）。问题在于"截取前十"之前的顺序是 movers 的自然顺序（按 daily 返回序），信号强度信息（pctChg 字段就在手上）完全没参与排序——涨幅百分之二十的股票与百分之八点一的股票在队列里机会均等。而额度是真实的紧约束：generate-tts 内的 QUOTA 对象（第 28-51 行）按百炼总额度一百万 token 估算、每字符按二点五倍计量（第 34-36 行），到达八成进入 warning、打满即拒（第 38-40、175-178 行）。当额度紧张或接口部分失败时，"谁拿到了语音、谁没拿到"应当由信号强度决定，而不是由列表顺序这一随机因素决定。

### 5.2 排序与分批的实现

修复是两段小改动。第一段，截取前排序：`signalAlerts = alerts.filter(a => a.kind === 'signal').sort((a, b) => Math.abs(b.pctChg) - Math.abs(a.pctChg)).slice(0, 10)`——按涨跌幅绝对值降序，前十名的构成从"先到先得"变为"最强者优先"。排序键用绝对值是刻意的：跌百分之十二与涨百分之十二对持有人同等紧要，方向色已在卡片层表达（Index.ets 第 289-297 行），语音额度分配不应偏向上涨。第二段，并行改分批：十个 `callFunction` 一齐发出对 generate-tts 是十路并发（每路又各开一条百炼 WebSocket，generate-tts 第 189 行），批发式并发容易同时撞向额度与连接上限；改为按三路一批、批间串行推进，配合 generate-tts 内 QUOTA 的 shouldStop 检查，额度打满时后续批次自然短路，不再白付 WebSocket 建连成本。分批损失的总时延有限：TTS 单次约二至五秒，三批串行最坏约十五秒，发生在存储回写（第 666 行）之前的旁路段，不在端侧五秒轮询的关键路径上。

### 5.3 与已知问题的联动

已知问题清单里"alerts.json 的 audioUrl undefined 端侧按需调 generate-tts"与本节直接相关：预生成覆盖的是排序后的前十名，未进前十的信号卡与全部事实卡在端侧按需补语音。排序优化使这个分工更合理——按需补调的卡片天然是次强信号，老人若真的点开它们，语音晚几秒到达是可接受的代价；而最强的十条异动在卡片到达时语音已就位，"点卡片即听"的核心体验对最紧要的信息保真。额度联动还有一层：端侧按需调用没有 QUOTA 视角（额度记账在 generate-tts 进程内），预生成侧的分批短路因此成为全局额度保护的第一道闸，值得在 generate-tts 的入口日志中同时打印剩余额度档位（第 340-344 行已有此日志，保持）。

## 六、端侧性能防线：渲染与轮询的既有正确实践

端侧两个性能要点已做得正确，本篇记录其原理以防回退，不做改动。其一，`ForEach` 的键值是 `item.alertId`（Index.ets 第 425 行）：键值是 ArkUI 做列表差量更新的依据，五秒一次的全量 `this.items = filtered` 赋值（第 178 行）之所以不引起肉眼可见的闪动，正因为键值稳定时框架只更新内容变化的卡片。这也从端侧反向论证了第四节的价值——alertId 确定性不只影响去重，还直接影响渲染差量计算的命中率；同股异号时代，每次轮询都等于全列表重建。其二，演示卡机制（第 13-23 行）+ 连续失败两次才切换状态（第 195-199 行）+ 指数退避（AlertPoller.ets 第 90-95 行）三者组合，保证了"首屏永不空白"与弱网下的低资源消耗：退避把故障期的请求频率从每五秒一次降到最低每三十秒一次，对老人的设备电量和流量都是实质保护。这两处与云函数侧的优化共同构成体验链的性能下限。

## 六点五、轮询调度形态：链式 setTimeout 的防重入价值

端侧轮询还有一个容易被忽视的调度细节值得记录：Index.ets 第 146-149 行的轮询没有用 setInterval，而是"执行完一轮 refresh 后再 setTimeout 下一轮"的链式结构。两种写法在正常网络下表现无异，差异出现在慢响应场景——setInterval 不管上一轮是否完成，到点就发下一轮，若单次请求耗时超过间隔（弱网下完全可能），请求会堆叠并发，既加倍消耗流量又制造乱序覆盖；链式结构天然防重入，任何时刻至多一个请求在途，间隔退避（第六节）也得以建立在"上一轮已结束"的确定前提上。这个形态与 AudioPlayer 的单实例独占（AudioPlayer.ets 第 9 行静态单 player、第 17-18 行播放前先 stop）是同一设计哲学在两个资源上的应用：对不可堆叠的资源，用结构保证互斥，而不是靠状态标志补救。云函数侧的对应物是 TTS 分批的批间串行（第五节）——三者共同构成"单飞原则"的项目级实现样本，后续任何新增的周期任务（如端侧未来的设置同步）应默认采用链式形态。

## 七、收益汇总与优先级

| 优化项 | 位置 | 预期收益 | 风险 | 建议优先级 |
| --- | --- | --- | --- | --- |
| 市场间并行 | 主函数 171-203 行 | 抓取段 28s→约 7s（约4倍） | 低（并发钉死为4） | 高 |
| SDK 单例化推广 | 另三个云函数 | 每调用省 1-4 次 init，消除常驻进程泄漏隐患 | 极低 | 高（可先行） |
| alertId 确定性 | 主函数 442、477 行 | 去重生效、截留不被挤占、已读语义恢复、渲染差量命中 | 中（需验证拉起定位） | 高 |
| TTS 排序+分批 | 主函数 595-627 行 | 额度紧张时最强信号先得语音；并发受控 | 低 | 中 |
| 页间并行 | 刻意不做 | — | — | 不做（方法论立场） |

排序依据是"收益除以风险"：SDK 单例化几乎零风险可最先合入；alertId 改动触及数据形态，需按第四节的两条边界验证后合入；市场间并行与 TTS 排序相互独立，任意次序。

## 八、验证方法

全部验证以日志与注入为主，不依赖压测环境。市场间并行：在 fetchMarketNames 内打印每请求时间戳，断言四条链首请求几乎同时发出（散布小于一百毫秒）、单链请求严格按页序递增；对照改造前后同一次全量抓取的总耗时日志。SDK 单例：在 init 调用处加计数日志，单次函数执行内断言恰为一次；get-alerts 用连续十次 HTTP 调用断言计数恒为一（同实例内）。alertId：同一 tradeDate 连续触发主函数两次，断言 alerts.json 条目数不增长且该股条目的 close 字段为第二次数值（覆盖语义）；端侧断言 readAlertIds 在第二次拉取后不再出现同股新金点；拉起定位回归：携 alertId 的 want 拉起后 Index.ets 第 138-144 行能命中并触发播报。TTS：mock 十条 pctChg 递减的信号卡，断言 callFunction 的发出顺序与分批节奏（批大小三）；mock QUOTA 打满，断言后续批次零调用。以上用例除市场间并行的总耗时需真实环境外，均可 node:test 注入完成；端侧两条在模拟器人工核对。
