- `Settings.ets`（557行）— 设置页面

## 审查结论

### 1. List 虚拟化 ✅ 已正确使用

`Index.ets` 使用 `List + ForEach`，ArkUI List 组件默认支持虚拟化。ForEach 的键值生成器 `(item: AlertItem) => item.alertId` 正确，确保列表项唯一标识。无需修改。

### 2. 渲染优化

#### P2（已修复）: readAlertIds 线性搜索 → Set 缓存

**位置**: Index.ets ForEach 中 `readAlertIds.includes(item.alertId)`

**问题**: 对每个列表项执行 O(n) 线性搜索。readAlertIds 上限200条，items 上限20条，最坏情况4000次比较。

**修复**: 新增 `private readAlertIdSet: Set<string>`，在 `loadSettings()` 中同步构建，在 ForEach 中用 `readAlertIdSet.has()` 替代 `includes()`（O(1)），在 togglePlay 标记已读时同步更新 Set。

**同步点**:
1. 声明: `private readAlertIdSet: Set<string> = new Set();`
2. loadSettings(): `this.readAlertIdSet = new Set(this.readAlertIds);`
3. ForEach: `if (!this.readAlertIdSet.has(item.alertId))`
4. togglePlay: `if (!this.readAlertIdSet.has(item.alertId)) { ... this.readAlertIdSet.add(item.alertId); }`

#### P3（不修复）: loadSettings() 重复调用

aboutToAppear + onPageShow 都调用 loadSettings()，首次进入页面时可能重复执行。但 Preferences 读取是异步且快速的，且 onPageShow 在从 Settings 返回时必须刷新配置。加标志位会增加复杂度，收益不大。

#### P3（不修复）: playHistory 数组重建

`[historyItem, ...this.playHistory.filter(...)].slice(0, 50)` 每次创建新数组。50条上限，影响可忽略。

### 3. 内存泄漏排查 ✅ 无泄漏

| 资源 | 清理方式 | 状态 |
|------|---------|------|
| timer (setTimeout) | aboutToDisappear 中 clearTimeout | ✅ |
| AudioPlayer.player (AVPlayer) | stop() 中 stop()+release() | ✅ |
| AlertPoller req (HttpRequest) | finally 中 req.destroy() | ✅ |
| AVPlayer 事件监听器 | release() 后自动清理 | ✅ |

### 4. AudioPlayer 竞态分析 ✅ 安全

`play()` 开始时先 `await stop()`（释放旧 player），然后创建新 player。togglePlay 有防连击逻辑（loadingId 检查），不会并发调用 play()。stop() 中 `AudioPlayer.player = null` 同步设置，即使 stop() 的 await 未完成，新 play() 也会创建新 player。✅

### 5. AlertPoller 退避策略 ✅ 正确

失败后间隔翻倍（5s→10s→20s→30s封顶），成功后复位5s。429限流静默跳过不计入连接中断。JSON解析失败记原文前200字符。req.destroy() 在 finally 中确保释放。✅
