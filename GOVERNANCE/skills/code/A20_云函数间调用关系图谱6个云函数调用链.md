# A20｜云函数间调用关系图谱——6 个云函数调用链、依赖关系、数据流向、故障传播路径

> 项目：harmony-app（铃语，鸿蒙适老化股票异动播报）。本篇是六云函数的全景图谱，自包含成文；每条边、每个数据资产都给文件路径与行号证据，全部来自本仓库源码通读（2026-09-23），未做云端实测。

## 二、调用链详解（七条边，逐条给证据）

### 链1：定时器 → fetch-tushare-data → generate-tts（唯一的函数间调用）

fetch-tushare-data 在信号卡合成阶段通过 `app.callFunction({name:'generate-tts', data:{alertId, text}})` 批量调用（index.js:611-626），仅对 `kind==='signal'` 的前 10 条（:595），且用 Promise.allSettled 保证单条失败不拖垮批次；返回体经 `result.value?.result?.success` 判定（:652）——callFunction 的返回包了一层 result，这个解包路径是联调时最容易错的点，图谱必须标注。同时并行跑 DKnowC 合规检查（:601-604），合规结果只加 complianceStatus 元数据不阻断（:629-646）。**全仓库云函数间 callFunction 仅此一处**（grep 验证）。

### 链2：fetch-tushare-data → alerts.json → get-alerts → 端侧卡片流（主干数据链）

生产：fetch-tushare-data 把异动合并进 `alerts/alerts.json`（saveAlertsToDB，index.js:497-558；下载旧文件 :505-512、serverTs 并发写保护 :518-524、按 alertId 去重合并 :527-535、保留 500 条 :537-540、上传 :549-552）。消费：get-alerts 下载同一文件（get-alerts/index.js:32-34，fileID 硬编码 :21），排序截断返回 `{items, serverTs}`（:64-68）。端侧：AlertPoller.ets:41 拼参请求，:79 返回 items，Index 卡片流渲染。注意 get-alerts 的 serverTs 用的是 `Date.now()`（:67）而非文件水位——与写入方的 serverTs（fetch-tushare-data:544）语义不同，这是 A17 篇 P0 修复项的图谱级佐证。

### 链3：alerts.json → broadcast-a2a → Supabase / 华为 Push Kit → 端侧通知（主动推送链）

broadcast-a2a 读同一 alerts.json（:32，与 get-alerts 逐行雷同的 getLatestAlerts :27-48），对每条 `kind==='signal' || direction!=='flat'` 的条目发推送（handleBroadcast :225-230）。推送前从 push_tokens 集合拉活跃 token（:119-123，失败回退环境变量单 token :124-129），先向华为 OAuth 端点换 access_token（:138-146），再 POST `messages:send`（:161-193），payload.data 内联 alertId/symbol/kind/audioUrl（:177-182）——这个 data 就是端侧 EntryAbility.ets:85-95 receiveMessage 解析的对象，构成推送→拉起→定位卡片的闭环。Supabase 广播独立并行（:53-89），未配置时跳过（:54-57）。已知问题注明：此 Push 需换华为 Push Kit REST（本代码已按 REST 实现），AGC 三环境变量未配置时整段跳过（:111-114）。

### 链4：端侧 → push-token-register → push_tokens（注册回填链）

端侧 PushService.ets:80-86 上报 → 云函数查重更新或插入（index.js:29-51）→ broadcast-a2a 的链3读走这份名单。这条链是链3的**前置供给**：没有链4的注册，链3的推送无人可发（只剩 env 兜底单 token）。

### 链5：generate-tts → 百炼 WebSocket / tts 目录 / alerts.json 回写（音频支线）

generate-tts 经 WebSocket 合成（:189 起，协议时序已按阿里云官方文档核实无误，见 A16 篇三），上传 `tts/{cacheKey}.mp3`（:310-334），写缓存 `tts-cache/{cacheKey}.json`（:96-116），并把 audioUrl 回写进 alerts.json 对应 alertId（updateAlertAudioUrl :122-164）。**回写这条边是图谱中最危险的一笔**：它下载-修改-整文件覆盖（:127-158），没有链2生产者那套 serverTs 保护——与链2形成对同一文件的读写竞态（见 5.4）。

### 链6：端侧 → get-alerts/generate-tts 的"按需补音频"（规划态）

已知问题载明"alerts.json 的 audioUrl undefined 端侧按需调 generate-tts"。现状核实：端侧**尚未**实装该调用——Index.ets:208-209 在无 audioUrl 时记日志静默跳过，:226 与 :390 都以 audioUrl 存在为前提。即链6是规划中的边，图谱如实标注"未实装"，避免后人误以为音频兜底已闭环。

### 链7：init-db → 数据库（运维支线）

init-db 建四个集合（init-db/index.js:15），但交叉核实（A18 篇 3.1）真正被链3/链4使用的 push_tokens 不在清单内，清单内四集合无一被运行时使用——图谱上这条边"画错了线"，本身就是一个待修缺陷。

## 五、故障传播路径（八条，逐条推演）

1. **Tushare 40101 → 东财降级**（已发生的已知问题）：callTushare 抛错（fetch-tushare-data/index.js:106-111，token 脱敏 :108）→ daily 失败被 catch 返 null（:353-356）→ movers 为空 → 返回 success:true items:[]（:579-586）。注意传播终点是**静默成功**：主流程靠名称映射的东财多级降级（:123-272：内存缓存→存储缓存→东财刷新→过期缓存→hardcoded-names.js→空 Map）兜住，但"当日异动其实没抓到"这一事实不会以失败形态上报，只能靠日志发现。
2. **generate-tts 失败 → audioUrl undefined → 端侧无播报**：百炼 task-failed/超时（generate-tts/index.js:272-277、197-201）→ callFunction 返回 success:false → 上游只记日志（fetch-tushare-data:656-662）→ alerts.json 无 audioUrl → 端侧静默跳过（Index.ets:208-209）。传播**有界且无害**：卡片照常显示，首屏永不空白约束不被击穿；但用户侧表现为"信号卡没声音"且无任何提示。
3. **tempFileURL 过期 → 播放失败**：audioUrl 是临时链接（generate-tts:320-326）→ 写入 alerts.json 与缓存被长期持有 → 端侧 AVPlayer 报 error（AudioPlayer.ets:34-37）→ onError 回调。传播终点是"点播报钮没声音"，与 2 同形但更晚发生，用户无从归因。
4. **generate-tts 回写覆盖 → 主数据丢失**：时序为 fetch-tushare-data 写入新一批 → generate-tts 持旧快照回写 → 新异动被旧文件覆盖（无 serverTs 检查，generate-tts:127-158）→ get-alerts/broadcast-a2a 读到旧数据 → 端侧丢卡、推送漏发。这是图谱上唯一一条**反向破坏主数据**的传播路径，P0 级。
5. **alerts.json 损坏/缺失 → 全读方空转**：get-alerts 与 broadcast-a2a 的 catch 都吞成空数组（get-alerts:47-50、broadcast-a2a:44-47）→ 轮询返回空 items、广播"success 但 items:[]"（broadcast-a2a:213-219）→ 端侧演示卡兜底（约束内）。故障被伪装成"无异动"，告警缺失（A17 篇五）。
6. **Push 未配置 → 推送链断 → 轮询兜底**：AGC 三变量空（broadcast-a2a:111-114）→ sendPushNotification 跳过 → pushCount=0。端侧 AlertPoller 5 秒轮询是架构级兜底（AlertPoller.ets:20-26 注释自证），传播**按设计终止**。
7. **push_tokens 缺失/污染 → 推送失效**：集合未建（init-db 清单缺陷）→ broadcast-a2a:119-124 读库抛错 → 回退 env 单 token（:124-129）→ 只有一台设备收到推送。或被垃圾注册污染 → 向伪造 token 推送 → 华为侧报错烧配额。
8. **QUOTA 内存态失真 → 生成静默放弃**：额度计数冷启动归零（generate-tts:28-51）→ shouldStop 永远偏低 → 超限时百炼侧失败 → 走路径 2。它是路径 2 的上游诱因之一。

## 六、重复逻辑与治理建议

图谱核对出三处复制粘贴：getLatestAlerts 在 get-alerts:26-51 与 broadcast-a2a:27-48 几乎逐行相同；ALERTS_FILE_ID 三处硬编码（get-alerts:21、broadcast-a2a:22、generate-tts:25）；CloudBase init 纪律不一（fetch-tushare-data:28-37 单例，generate-tts:63-66、get-alerts:28-29、broadcast-a2a:29-30 每调新 init）。云函数间无法共享模块，治理路径：短期统一各文件内常量与单例写法；中期按 A17 方案C 把 alerts.json 集合化，让 get-alerts/broadcast-a2a/generate-tts 回写全部改走数据库（读写语义由数据库保证，重复读文件逻辑自然消亡）；`serverTs` 语义统一为"文件/集合数据水位"（A17 篇 P0）。演进优先级：④回写加保护（止血）→ ①②集合化（治本）→ ③链6按需音频实装（体验闭环）。

## 八、调用链时序图（一条异动的完整一生）

以一条信号卡从行情到耳边的时间线串起全部七条链（含规划态的链6）：

```
T+0s    定时器触发 fetch-tushare-data
T+1s    getLatestTradeDate 命中缓存(内存/存储)，getDailyMovers 并行:
        callTushare('daily') ──┬─ 40101/失败 → 降级路径(五.1)
                               └─ 成功 → 名称映射五级降级补全名称
T+3s    createAlertItems 产出 N 条异动(≥8% 标 signal)
T+3s    signal 前10条并行: callFunction('generate-tts') ×10 + DKnowC ×10
T+4s    generate-tts: checkCache(存储) → miss → WSS 握手 → run-task
        → task-started → continue-task+finish-task → 收二进制帧
T+16s   task-finished → 上传 tts/{key}.mp3 → 写 tts-cache → 回写 alerts.json(无保护!)
T+18s   fetch-tushare-data 汇总 audioUrl → saveAlertsToDB(带 serverTs 保护) → 覆盖写
        ↑ 注意: generate-tts 的回写(T+16s)与主写入(T+18s)同窗竞态(五.4)
T+18s   [手动/Event] broadcast-a2a: 读 alerts.json → 拉 push_tokens →
        华为OAuth换token → messages:send → 端侧通知栏
T+18s   端侧(任意时刻的前台轮询): AlertPoller 5s一拍 GET /alerts →
        get-alerts 下载 alerts.json → {items,serverTs} → 卡片流渲染
T+20s   用户点卡片/点通知: onNewWant(alertId) 定位 → audioUrl 有→AVPlayer 播
        audioUrl 无→[规划链6]端侧按需调 generate-tts 补音频
```

时序图暴露三个结构性事实：其一，链1 的 TTS 生成（T+4s~T+16s）占掉函数 60 秒预算的大头，10 条并发时它是长尾；其二，链5 回写与链2 主写入天然同窗（都发生在批次尾部），五.4 的覆盖竞态不是理论风险而是每批必遇的常态窗口；其三，链6 未实装前，TTS 失败的那部分信号卡永远没有音频（五.2 传播有界但不可自愈）——这为链6 实装提供了优先级依据。

## 九、降级矩阵（全链路一览）

| 故障点 | 现有降级 | 降级后用户体验 | 断点兜底 |
|---|---|---|---|
| Tushare 40101 | 名称层有五级降级；daily 层无(返空) | 无新卡，老卡仍在 | 端侧演示卡+旧数据 |
| generate-tts 失败 | allSettled 隔离，卡片照发 | 卡在、无声 | 规划链6 按需补 |
| tempFileURL 过期 | 无 | 点播无反应 | 无(需 A16 P0) |
| alerts.json 损坏 | 吞成空列表 | 空态演示卡 | 备份双写(A17 6.2) |
| AGC/Push 未配置 | 整段跳过(设计内) | 轮询兜底，无通知 | AlertPoller 5s |
| push_tokens 缺失 | env 单 token 兜底 | 仅调试机收到 | init-db 补清单(A18) |
| Supabase 未配置 | 跳过(设计内) | 不影响主链 | — |
| CloudBase 平台故障 | 无(底层) | 全链停 | 演示卡+退避轮询 |

矩阵的读法：设计内降级（Push/Supabase 未配置）与被动降级（Tushare、TTS）都止步于"体验降级"；真正无兜底的是 tempFileURL 过期与 alerts.json 损坏两格——它们不触发任何告警路径，用户侧表现为无解释的静默故障，应最先补齐（分别对应 A16 篇与 A17 篇的 P0）。

## 十、演进路线与图谱变更预判

按"止血→治本→体验"三步走，每步对图谱的改造：**第一步止血**（不动拓扑）：generate-tts 回写加 serverTs 保护、get-alerts 失败显式化、init-db 补 push_tokens、凭证吊销——四项都是边属性修复，七条链的结构不变。**第二步治本**（换总线）：alerts.json → alerts 集合化后，链2 变为"fetch-tushare-data upsert 集合 → get-alerts/broadcast-a2a 查询集合"，链5 回写变为单字段 update，读写矩阵的竞态行整体消失，get-alerts 的读放大随查询即 limit 而消亡——这是拓扑收益最大的一步，代价是三个函数同时改造需一次联调窗口。**第三步体验**（补边）：实装链6 端侧按需 TTS，依赖第二步的换链服务（端侧零依赖约束下换链必须在云端做）。预判的图谱终态：六函数拓扑不变、文件总线退役为备份资产、唯一跨函数调用（链1）保持——架构基调（EntryAbility/Index/AudioPlayer/AlertFeed 契约）全程不被触碰，符合共享约束"勿推翻"。

## 十一、依赖方向与健康度判定

把七条链抽象成依赖箭头后的结构性结论：**箭头方向**——init-db→库、fetch-tushare-data→{generate-tts, alerts.json, 外部三源}、generate-tts→{百炼, 存储三资产, alerts.json}、get-alerts→alerts.json、broadcast-a2a→{alerts.json, push_tokens, 外部两通道}、push-token-register→push_tokens、端侧→{get-alerts, push-token-register}。两个值得警惕的结构特征：其一，**alerts.json 是双写单读枢纽**——两个写方（fetch-tushare-data 主写、generate-tts 支线回写）共享一个无锁文件，而全系统没有任何一个组件对它做并发仲裁，这在单实例定时触发下靠时序侥幸成立，触发频率一高即破（五.4）；其二，**generate-tts 是唯一被 callFunction 的函数，同时又是唯一回写主数据的函数**——权力最大的节点恰恰是审查发现缺陷最密的节点（A16 篇三个 P0/P1），风险集中度与缺陷密度重合，是整个图谱最该盯的坐标。健康判定给一个简单规则：**任何"支线写主线"的箭头都必须带与主线同级的保护，否则从图上剪掉**——本图当前唯一违反该规则的箭头就是 generate-tts→alerts.json。

## 十二、故障演练剧本（五分钟一次的主动验证）

按剧本注入故障，验证降级矩阵（九）与故障路径（五）是否如推演般表现：**演练一（TTS 断供）**：临时改掉 DASHSCOPE_API_KEY 触发 fetch-tushare-data——预期信号卡照常产出、audioUrl 缺失、日志十连 `TTS FAIL`（fetch-tushare-data:658-661），端侧卡片流无感。**演练二（存储文件损毁）**：手工把 alerts.json 写成非法 JSON——预期 get-alerts 返回空 items（五.5 的伪装形态）、broadcast-a2a 返回 success+空列表，此时若直接观察到告警缺失，即坐实 A17 篇 P0 的必要性。**演练三（推送未配置）**：留空 AGC 三变量触发 broadcast-a2a——预期日志 `Push Kit not configured ... skipping push`（broadcast-a2a:112）、pushCount=0，端侧仅轮询可见数据，演练通过标准是"无报错"。**演练四（token 库污染）**：向 push_tokens 灌一个假 token 再广播——预期华为侧返回错误、真实设备不受影响，观察无效 token 是否被回收（4.1 的欠账在演练中现形）。四个剧本全部只动环境变量与测试数据，不改代码，可作为每次大改后的回归例行——故障传播路径纸面推演一百遍，不如演练一遍。

## 十三、全链路不变式（Invariant 清单）

无论后续怎么改，五条不变式必须始终成立，违反任何一条即架构回归：**I1** alerts.json 的 items 中每条必有 alertId 且全局唯一（fetch-tushare-data:527-535 的 Map 去重保证写入侧，generate-tts 回写不得破坏）；**I2** get-alerts 返回体恒为 `{items:AlertItem[], serverTs}` 结构（AlertItem.ets:19-22 契约，端侧 JSON.parse 直接依赖）；**I3** 端侧任何路径不得因服务端故障白屏或崩溃（首屏永不空白约束，由端侧演示卡兜底，服务端任何改动不得移除"可判定故障"的信号——这正是 A17 显式化的图谱意义）；**I4** kind=signal 的播报文本必须先经 DKnowC 检查或至少带 complianceStatus 元数据（fetch-tushare-data:601-646，信号三禁的机器侧落点）；**I5** 播报音频内容与卡片文字一致（generate-tts 的 text 由上游拼 `headline。detail` 传入，fetch-tushare-data:617，任何人改文案模板时两端必须同步）。评审任何涉及这六个函数的改动时，先对照 I1-I5 再看细节——不变式是图谱的骨架，链与资产只是血肉。

## 十四、六函数职责边界与耦合评分

从图谱视角给每个函数做单一职责判定与耦合度量（耦合数=直接依赖的外部资产与函数数，据第一节表与第三节数据流图统计）：

| 函数 | 职责一句话 | 职界判定 | 耦合数 | 备注 |
|---|---|---|---|---|
| fetch-tushare-data | 采集行情、筛异动、编排合成与合规 | 编排者，边界天然宽 | 6（Tushare/东财/DKnowC/generate-tts/alerts.json/name-map） | 编排职责合理，但回写保护等纪律要最严 |
| generate-tts | 文本转音频并落盘 | **越界**：多做了"回写主数据" | 4（百炼/tts 目录/tts-cache/alerts.json） | 剪掉回写箭头即归位（见十一） |
| get-alerts | 只读轮询出口 | 干净 | 1（alerts.json） | 全图最纯粹，改动风险最低 |
| broadcast-a2a | 双通道分发 | 干净但读径重复 | 5（alerts.json/push_tokens/Supabase/华为） | 读逻辑与 get-alerts 重复（六） |
| push-token-register | 设备登记 | 干净 | 1（push_tokens） | 死导出待清（A19 4.2） |
| init-db | 建集合 | 清单错位 | 1（库） | 画的线不对（链7） |

评分结论：六个函数里四个边界干净，两个有问题——generate-tts 的越界写与 init-db 的错位清单，恰好就是 A16/A18 两篇的头号发现；图谱判定与逐函数深审的结论互相印证，说明静态分析没有漏掉大结构。耦合总数十六个外部触点里，alerts.json 一家占了五条读写边——治本方案（十步二）把这个枢纽换成数据库后，五条边全部改语义，其余触点不动，改造成本与收益比最优。

## 十五、图谱使用说明与维护纪律

这份图谱的三种用法：**改前查**——动任何函数前先看读写矩阵（四）确认自己碰的资产还有谁在读；**改后核**——改动落地后对照不变式（十三）跑一遍演练剧本（十二）；**新人读**——按第八节时序图从一条异动的一生入手，十分钟建立全链心智。维护纪律三条：①新增任何函数间调用（callFunction）必须同步补链与矩阵行，当前全图仅链1 一处，新增即重大事件；②新增任何存储资产（文件或集合）必须进读写矩阵并指定唯一写者，双写枢纽是本图最大教训；③每次架构级改动（如集合化）后重画数据流图，旧图归档不删——图谱的演变史本身就是架构决策史。本图与 A16-A19 四篇构成完整闭包：四篇各审一函数一深井，本篇给全流域一张浅图，深浅互证，任何一篇的 P0 都能在图上找到结构性位置与传播半径。

## 十六、结语

六函数构成的这张图，本质是一个"单生产者、多消费者、文件总线"的最小可行架构：fetch-tushare-data 独自生产，get-alerts 与 broadcast-a2a 各消费一份，generate-tts 在生产线上补一道音频工序，push-token-register 与 init-db 一个供给推送名单、一个打地基。它的简洁是优点——七条链、八个资产，一张表就能穷尽；它的脆弱也源于同一处——五条边压在一个无锁文件上，支线回写没有与主线同级的保护。演进方向因此极其明确：先给危险箭头加保护（四项止血），再把文件枢纽换成数据库（治本），最后补上按需音频的规划边（体验）。全程不动六函数拓扑、不动端侧契约、不动架构基调——图谱给出的最有价值的判断是：**这个系统不需要重构，需要的是把三条已经画歪的线重新画直**。
