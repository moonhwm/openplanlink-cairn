# 缓存策略有效性深度审查——六层降级链的TTL优化与一致性保障

> 项目：harmony-app（铃语，鸿蒙适老化股票异动播报应用）。审查对象：云函数 `cloudfunctions/functions/fetch-tushare-data/index.js` 中 `getStockNameMap`（第 123-272 行）的六层缓存降级链，并横向对照同文件交易日缓存（第 79-81 行）与 `cloudfunctions/functions/generate-tts/index.js` 的 TTS 文本缓存（第 72-116 行）。本文自包含，行号均指当前版本。审查日期：2026-09-23。

## 一、审查范围与结论摘要

股票名称映射是播报链路里"看不见但缺不得"的一环：Tushare daily 接口的 name 字段经常为空，缺了映射表，端侧卡片只能显示 `600176` 这类代码，"大字白话"的适老化承诺就落空。正因为它"缺了就出洋相、坏了不报错"，它的缓存策略值得单独审查——缓存策略差的典型症状不是崩溃，而是"慢、旧、时好时坏"，这三类症状在本链路全部找得到对应代码。

审查结论分三句话。第一，链路设计方向正确：六层降级从新鲜到陈旧、从动态到静态、从网络到本地，最后一层永远能返回一个可用对象，下游无需判空，这个骨架应当保留。第二，TTL 设置基本合理但存在两处失真：内存层二十四小时的 TTL 对云函数实例的实际存活期而言形同虚设，而真正承担跨调用复用职责的存储层却缺少主动刷新的错峰机制。第三，一致性保障是全链最薄弱的一环：过期数据回填内存缓存时被盖上"当前时刻"的新鲜戳（第 154、247、262 行），stale 数据因此被洗白成新鲜数据继续服务二十四小时；存储回写无并发保护，多实例同时冷启动会互相覆盖；写后读依赖对象存储的可见性语义但从未验证。本文给出逐层 TTL 优化表、三处一致性缺陷的修复方案、命中率埋点设计与验证方法。

## 二、六层链路总览与逐层剖析

### 2.1 链路结构

以第 123-272 行为准，六层降级的完整结构与关键参数如下表。表中"命中率"一列为按调用形态的定性估计，定量验证见第六节埋点设计。

| 层 | 数据源 | 位置 | TTL/新鲜度 | 覆盖范围 | 估计命中时点 |
| --- | --- | --- | --- | --- | --- |
| 1 | 模块级内存 `cachedNameMap` | 84-86、125 行 | 86400000 毫秒（24h） | 同一函数实例存续期 | 同实例内的后续调用 |
| 2 | CloudBase 存储 `stock-names/name-map.json`（新鲜段） | 131-157 行 | 按 `updatedAt` 判 24h | 全实例、全地域共享 | 冷启动或实例更换后 |
| 3 | 东方财富列表接口（4 市场 × ≤20 页） | 162-234 行 | 无（实时抓取） | 全市场实时 | 前两层失效时，每实例每次至多一轮 |
| 4 | CloudBase 存储（过期段，同一文件） | 236-254 行 | 无限（有数据就用） | 全实例共享 | 东财失败时的救命层 |
| 5 | 硬编码快照 `hardcoded-names.js` | 256-267 行 | 静态（2026-09-21 抓取，5560 条，147121 字节） | 打包进代码 | 第四层也失败时 |
| 6 | 空 Map | 269-271 行 | 无 | 无 | 绝对兜底，保证返回类型契约 |

第六层的存在常被误解为"失败兜底"，其实它是**契约保障层**：`getDailyMovers` 第 357、361 行无条件调用 `nameMap.get` 与 `nameMap.size`，返回类型恒为 Map 才能让下游不必判空。这一层必须保留，且永远不该被优化掉。

### 2.2 与姊妹缓存的结构对照

同仓库还有两个同构缓存，对照着看能发现本次审查对象缺失的要素。其一，交易日缓存（第 79-81 行）：TTL 一小时，与上游 trade_cal 接口"每小时限流一次"的配额精确对齐——TTL 等于配额窗口，这是"按上游约束定 TTL"的正面示范。其二，TTS 文本缓存（generate-tts/index.js 第 72-116 行）：以播报文本的 SHA256 前十六位为键、缓存音频地址、无 TTL——因为同一段播报文本的音频永远有效，"按数据本质定 TTL"的另一个正面示范。反观名称映射缓存：内存层与存储层都取二十四小时，但这个数字既不对应任何上游配额（东财接口没有明确频控），也不对应数据变更周期（股票改名、ST 摘帽、退市这类事件一年发生一次量级），更不对应实例存活期。三个数字里唯一说得通的理由是"拍脑袋的整数值"。这就是 2.3 节 TTL 优化的出发点。三者在统一维度上的对照如下表，"判据来源"一列是本节的核心结论：一个站得住的 TTL 必须能说出它来自哪条判据。

| 缓存 | 键 | TTL | 判据来源 | 并发保护 |
| --- | --- | --- | --- | --- |
| 交易日缓存 | 进程内单值 | 1 小时 | 上游配额窗口（trade_cal 每小时一次） | 无需（写频极低） |
| TTS 文本缓存 | 文本 SHA256 前16位 | 无限期 | 数据本质（音频对同文本永有效） | 无（幂等重复写） |
| 名称映射·内存层 | 进程内单值 | 24h（名义） | 无明确判据 | 无 |
| 名称映射·存储层 | 固定云路径单文件 | 24h | 无明确判据 | 无（缺概率回写） |

## 三、TTL 逐层优化

### 3.1 内存层：二十四小时是名义值，实际由实例存活期封顶

第 86 行注释写"24小时缓存"，但云函数实例的生命周期由平台回收策略决定，事件函数实例通常存活几分钟到几十分钟量级（具体数值依平台弹性伸缩而定，未实测验证）。这意味着内存层的真实 TTL 是 `min(24h, 实例剩余寿命)`，绝大多数时候后者更短——二十四小时这个数字从未真正生效过。这并非缺陷而是云函数的物理事实，需要修正的是**对它的定位**：第 119 行注释称"同一次函数调用内复用"，这一句才是内存层的真实价值——同一调用内 `getDailyMovers` 与后续可能的重复调用不重复走网络；跨调用的复用是意外之喜，不是设计承诺。建议把注释改为如实陈述，避免后人按"24h 生效"去做依赖它的优化决策。若确要拉长实例级复用，正确抓手是降低实例冷启动频率（如平台的最小实例数配置），而不是调大这个常数。

### 3.2 存储层：二十四小时可以放宽，但要有错峰与下限校验

存储层是跨调用复用的主战场，它的 TTL 决定了东财接口被全量抓取的频率。名称映射的数据变更周期分析：股票改名是公司行为，一年发生个位数次；ST 标记变更按季度批量发生；退市摘牌月度级。以"数据时效要求"论，七十二小时都不会造成用户可感知的错误——名称最多"旧"两天，而适老化播报对名称时效的容忍度远高于对行情数值的要求。建议把存储层判定 TTL 从 24 小时放宽到 48 小时（取保守值而非理论上限），并把抓取动作放进"业务低峰窗口"：本函数由定时触发器驱动，触发时刻已知，把"是否刷新"的判断加上"当前是否为低峰时段"的条件，避免开盘后的行情高峰与全量抓取叠加。配套一个下限校验：东财抓取结果少于硬编码快照条数的九成（即少于约五千条）时视为不完整数据，拒绝回写存储层并维持旧缓存——半截数据比旧数据危害大，这个校验当前代码完全缺失（第 207 行只判 `size > 0`）。

### 3.3 过期层与硬编码层：无 TTL 是正确的，但快照会腐化

第四层"有数据就用"与第五层"静态快照"都不设 TTL，这是正确的取向：兜底层的使命是"有比没有强"，加 TTL 只会把本可救急的旧数据拒之门外。但第五层有一个独特的风险——**快照腐化**。`hardcoded-names.js` 是 2026-09-21 的静态快照，它会随时间无限变旧：新上市股票查无名称、改名的股票给出旧名、已退市股票占着键位。快照不会崩坏但会静默变臭，且没有任何机制提醒。建议三件事：其一，在快照文件头部已有生成日期注释（第 1-2 行）的基础上，把日期与条目数做成导出常量，编排层加载时打印"快照年龄"，超过九十天在日志中告警提示重新抓取；其二，在第 3.2 节下限校验中把快照条数作为基准线，使快照同时充当"完整性标尺"；其三，建立季度刷新流程，用东财全量抓取的现成代码重新生成快照——刷新脚本复用第 5.4 节的抓取函数，成本近乎为零。

### 3.4 优化后的 TTL 总表

| 层 | 现状 TTL | 建议 TTL | 判据 |
| --- | --- | --- | --- |
| 内存 | 24h | 维持 24h，注释改为"实例存续期内" | 实际由实例寿命封顶，常数不承担功能 |
| 存储新鲜段 | 24h | 48h + 低峰窗口刷新 | 名称变更周期 >> 48h，降低全量抓取频率一半 |
| 过期段 | 无限 | 无限 + 条目数下限校验 | 兜底使命：有比没有强 |
| 硬编码 | 静态 | 静态 + 90 天年龄告警 + 季度刷新流程 | 快照腐化可观测化 |

## 四、一致性保障：三处缺陷与修复

### 4.1 核心缺陷：过期缓存被洗白

这是全链最严重的一致性缺陷。原代码第 150-156 行的逻辑是：发现存储缓存已过期 → 把过期数据装进内存缓存 → 把 `cachedNameMapTs` 刷成 `Date.now()` → 继续尝试东财刷新。第 246-247 行与 261-262 行的兜底路径同样如此。后果推演：某日东财接口故障、刷新失败，过期的名称映射被装入内存并盖上当前时间戳；此后二十四小时内，第 125 行的 TTL 判断都会认为这份过期数据"新鲜"，即便存储层随后被其他实例成功刷新，本实例也浑然不觉；更坏的是，若这份实例存活期内再次走到"东财失败"路径，它会把自己的过期数据继续传下去。一句话：**兜底数据的"我何时装入"被当成了"数据本身多新"，两个语义在缓存槽里混为一谈。**

修复方案是把"装入时刻"与"数据新鲜度"拆成两个独立字段，TTL 判断只认数据新鲜度：

```js
const nameMapCache = {
  map: null,
  fetchedAt: 0,   // 数据真实抓取时刻（东财成功时为 now；stale 兜底时为存储的 updatedAt）
  source: '',     // 'eastmoney' | 'stored-fresh' | 'stored-stale' | 'hardcoded' | 'empty'
};

function isCacheFresh(cache, now, ttl) {
  return cache.map && (now - cache.fetchedAt) < ttl;
}
```

东财刷新成功时 `fetchedAt = Date.now()`、`source = 'eastmoney'`；stale 兜底时 `fetchedAt = new Date(stored.updatedAt).getTime()`（数据真正的生日）、`source = 'stored-stale'`。如此，过期数据装入内存后 TTL 判断依然判它过期，不会阻止后续轮次的刷新尝试；`source` 字段同时让每层命中在日志中可归因。该修复与 cloud-function-refactor.md 第 5.2 节的 `kind` 三值设计是同一件事的两个视角，可随该重构一并落地。

### 4.2 并发回写：无保护的写放大与互相覆盖

两个实例同时冷启动（定时触发器并发或平台扩容）且存储缓存恰好过期时，两者都会走"东财全量抓取 → 回写存储"的路径，产生三重后果：东财承受双倍全量流量；两次 uploadFile 互相覆盖，虽然载荷内容几乎相同不致错乱，但 `updatedAt` 取胜者的时刻，另一个实例刚写入的缓存瞬间被判过期作废；抓取期间两者各自占用十五秒级的外呼预算。修复按代价从低到高三档。第一档（推荐，零成本）：**概率回写**——仅在满足 `Math.random() < 1/并发估计` 时执行 uploadFile，把多实例同时回写的概率压到接近一，缓存内容本就同构，漏写的实例下次仍能读到别人的写入。第二档：回写前先读一次存储的 `updatedAt`，若与本次进入时读到的相同（说明无人更新过）才回写，形成乐观锁；代价是最坏情形多一次下载。第三档：用数据库集合或分布式锁做真互斥，成本最高且引入新依赖，除非出现真实的写冲突事故，不建议。

### 4.3 写后读可见性：未验证的假设

第 212-226 行 uploadFile 成功后即认为持久化完成，第 131 行起的 downloadFile 在下一次调用中能否读到这次写入，取决于 CloudBase 对象存储的一致性语义——若为最终一致，存在一个短暂窗口读到旧版本甚至找不到文件。当前代码从未验证这一点，好在后果轻微：读旧版仅意味着下次多抓一次，读不到则走兜底链，都不会错。处理方式是把假设显式化：在存储契约注释中注明"回写后立即可见是假定而非保证，兜底链覆盖其失效情形"，并在验证方法中加一条一次性实测（写入后立即读取一百次，统计读到新版本的延迟分布）。这与 saveAlertsToDB 的情形不同——alerts.json 第 520-524 行已有 serverTs 比较的并发写保护，且端侧轮询容忍秒级陈旧，两个文件的存储一致性要求本就不该套用同一标准。

### 4.4 与 alerts.json 缓存的职责边界

顺带厘清一个易混点：`stock-names/name-map.json` 与 `alerts/alerts.json`（第 497-558 行）同在 CloudBase 存储但一致性要求截然不同。alerts.json 是交易性数据——端侧按 serverTs 增量拉取，写入有五百条截留与 alertId 去重（第 526-540 行），并发保护是正确性问题；名称映射是装饰性数据——最多造成个别卡片显示代码而非名称，并发保护只是效率问题。审查中曾考虑给名称映射加 serverTs 式保护，结论是不加：装饰性数据的保护成本应远低于其错误代价，4.2 节第一档已足够。

## 五、命中率与失效模式的定性推演

按调用形态推演六层的期望命中分布。常态（东财正常、存储健康）：首调实例命中第二层，同实例后续调用命中第一层，第三层以上几乎不出场——这正是设计意图。东财接口故障日：第三层失败后落到第四层，用户侧无感（名称最多旧几天），这正是降级链的价值时刻。存储文件意外丢失且东财故障（双故障）：落到第五层硬编码快照，新上市股票查无名称，第 369-374 行回填失败、卡片显示代码——发生率极低但症状可见，4.1 的 source 日志让这类日子可归因。全面失效：第六层空 Map，等于退回"无名称映射"的历史状态，仍不崩溃。推演的结论：链路的失效模式全部落在"降级变旧"而非"崩溃出错"一侧，方向健康；唯二需要堵上的洞就是 4.1 的洗白与 4.2 的写放大。

还有一组值得预演的日历型交互：周末与节假日。周末交易日缓存过期后，第 322-338 行的日期推算兜底返回最近周五，daily 查询照常执行，名称映射链路本身不受影响；但周一开盘若恰逢存储缓存过期，全量抓取与当日行情拉取会在同一函数实例内叠加执行，这是"低峰窗口刷新"判据里必须把"交易日早间"而非"自然日早间"设为禁刷窗口的原因——日历语义要以市场日历为准，而不是以墙钟日历为准。节假日后首个交易日的推演同理，此处不再展开，验证方法第七步的灰度观测应覆盖至少一个完整周以捕捉该形态。

## 六、监控埋点设计

现状日志已分层打印（每层命中各有独立文案），缺的是结构化与聚合性。建议在编排层统一打印单行 JSON：`{layer: 'mem'|'stored-fresh'|'eastmoney'|'stored-stale'|'hardcoded'|'empty', size, ageMs, durationMs}`，一次调用恰好一行，六层取值可枚举。由此可直接聚合出三个指标：各层命中率分布（验证第三节 TTL 调整的效果）、东财层出场频率（高于预期说明前两层失效异常）、stale 与 hardcoded 层出场日历（出现即触发人工检查）。埋点实现约束：不引入任何指标上报 SDK，沿用 console.log 由平台日志服务聚合，与项目零三方依赖约束一致。

## 六点五、回滚与渐进发布

上述改动彼此独立，可拆为三个发布单元按风险升序上线。第一个单元是纯观测性的 source 字段与单行 JSON 日志，无行为变更，随时可发，且它同时是后两个单元的验证前提——没有它，TTL 调整的效果无从度量。第二个单元是洗白修复与下限校验，二者只影响"何时刷新、是否回写"，不影响读取路径，发布后观察一日内 stale 层出场频率应上升（不再被洗白掩盖），这是修复生效的信号而非退化。第三个单元是 TTL 放宽与低峰窗口，依赖前两个单元的数据先行观察一周后再动。每个单元独立提交独立回滚，回滚均不涉及存储载荷变更——source 与 fetchedAt 只存在于内存与日志，存储文件的五字段契约（names/updatedAt/count/source）全程不变，新旧代码可交叉读写同一文件，这使渐进发布期间的实例混布不构成风险。

## 七、验证方法

验证分四步。第一步，单元验证洗白修复：mock 存储返回 updatedAt 为四十八小时前的载荷，mock 东财抛错，断言修复后缓存槽的 `fetchedAt` 等于载荷的 updatedAt 而非 `Date.now()`，且下一轮调用不再命中该槽。第二步，单元验证下限校验：mock 东财返回四千条（低于快照九成基准），断言不回写存储、返回旧缓存。第三步，一致性实测：对同一函数实例连续触发十次调用，断言第一层命中十次中至少九次（实例存活的前提下）；双实例并发触发，断言存储文件的 updatedAt 变更次数显著少于触发次数（验证概率回写）。第四步，七日灰度观测：对比调整前后东财层的出场次数（预期因 TTL 放宽约减半）与名称覆盖率日志（第 383-384 行，预期不变）。其中第三步的实例存活时长依赖平台实际行为，若单测环境无法稳定复现，则以日志中 layer 分布近似验证并在记录中注明局限。
