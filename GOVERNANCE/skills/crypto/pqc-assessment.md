# PQC 迁移评估框架：现状评估 → 风险识别 → 迁移路径 → 验证

> 适用项目：harmony-app（铃语，鸿蒙适老化股票异动播报，纯 ArkTS + 云函数）。
> 本文件为 crypto 技能域的知识资产，自包含、可持久化；引用的项目文件（EntryAbility.ets、Index.ets、PushService.ets、alerts.json、AlertFeed 契约等）以项目仓库内的实际路径为准。
> 外部事实核验说明：NIST 后量子标准（FIPS 203/204/205，2024 年发布）、RHEL 10 携带 OpenSSL 3.2 并在 TLS 中提供 ML-KEM 混合密钥交换等事实，已经 2026-09-23 的 Web 检索核验（Red Hat 官方文档与博客）。

## 一、为什么必须做 PQC 迁移评估

后量子密码（PQC）迁移不是"换一个算法"的单点工程，而是对全部密码使用点的系统性重构。驱动评估的两个威胁模型：

1. **CRQC（密码学相关量子计算机）**：一旦出现，Shor 算法可在多项式时间内攻破 RSA、ECC（含 SM2 所依赖的椭圆曲线离散对数）；Grover 算法对对称密码（AES、SM4）只提供平方级加速，通过加倍密钥长度（AES-256、SM4 保持 128 位需评估）即可缓解。
2. **HNDL（现在窃取、以后解密，Harvest Now Decrypt Later）**：攻击者今天截存密文，等量子计算机成熟后回溯解密。这意味着：**数据保密寿命 + 迁移周期 > 量子威胁到达时间** 的系统，今天就已经暴露。

Mosca 不等式是评估的总纲：设数据需要保密的年限为 X，迁移完成所需年限为 Y，CRQC 出现的预期年限为 Z，则当 **X + Y > Z** 时必须立即启动迁移。对铃语这类以公开市场行情播报为主的应用，多数数据保密寿命短，但**鉴权凭据（Tushare token、百炼 TTS APIKey、未来华为 Push Kit REST 的客户端凭据）长期有效**，X 值大，是 PQC 评估中的第一优先对象。

另一个容易忽视的事实：**签名与身份认证同样受威胁**。AlertFeed 数据源的完整性校验如果今天建立在 ECC/RSA 签名上，攻击者未来可伪造签名注入虚假播报内容，对老年用户群体的诱导风险远高于数据泄露本身——这直接触碰项目合规红线（不承诺收益、不催促交易）。

## 二、阶段一：现状评估（建立密码资产清单 CBOM）

现状评估的产出物是一份**密码物料清单（CBOM, Cryptographic Bill of Materials）**，它是后续三个阶段的唯一事实基础。没有 CBOM 的迁移必然遗漏。

### 2.1 盘点维度

| 盘点对象 | 铃语中的落点 | 需记录的字段 |
|---|---|---|
| 传输通道 | FEED_URL 拉取 AlertFeed、AudioPlayer 播云端 TTS 音频流（AVPlayer）、云函数调用 generate-tts | TLS 版本、密钥交换组、证书链算法与有效期、是否固定证书 |
| 鉴权凭据 | Tushare token（已因 40101 失效降级东财）、百炼 TTS WebSocket 凭据、AGC 配置、Push Kit 客户端凭据（待接入） | 存储位置、用途、有效期、轮换方式 |
| 应用层密码 | alerts.json 缓存的防篡改校验（如未来引入）、本地偏好数据加密 | 算法、密钥长度、模式、密钥来源 |
| 服务端密码 | 云函数出口、X 服务器（FEED_URL 后端）的证书与握手配置 | OpenSSL/GnuTLS 版本、crypto-policies 级别 |
| 代码内密码 | 零三方依赖约束下的 ArkTS 系统密码接口调用点（cryptoFramework） | 接口、算法参数、调用频率（注意 Index.ets 的 5s 前台轮询会放大高频校验成本） |

### 2.2 盘点方法

- **静态扫描**：对 ArkTS 源码与云函数代码做关键词扫描（`RSA`、`ECDSA`、`SHA1`、`createCipher`、`http.createHttp`、硬编码密钥模式），输出调用点清单。零三方依赖是优势——密码调用全部落在系统能力上，扫描面小且确定。
- **动态探测**：对 FEED_URL 与 TTS 音频域名执行握手探测，如 `openssl s_client -connect host:443 -tls1_3` 观察协商出的分组（关注是否仍停留在传统 ECDHE），或 `nmap --script ssl-enum-ciphers` 枚举套件。
- **文档对齐**：以 AlertFeed 接口契约为准，标记每个字段在传输与落盘（alerts.json）阶段是否已有完整性保护。

### 2.3 输出物模板

CBOM 每行一条：`编号 | 资产 | 位置(文件路径/域名) | 算法与参数 | 用途 | 数据保密寿命 | 依赖的证书/密钥 | 已知问题`。阶段一验收标准：清单覆盖上表全部五个维度，且每条都有文件路径或域名可回溯。

## 三、阶段二：风险识别（评分与分级）

有了 CBOM，逐条计算风险分。推荐三因子乘积模型：

**风险值 R = E × L × V**
- E（暴露度）：该密码使用点是否面向公网、是否传输可被截存的长期有效数据。1=仅本地、2=内网/短连接、3=公网高频。
- L（数据寿命）：凭据或数据需要保密的时间。1=<30 天、2=1 年内、3=多年或无限期。
- V（算法脆弱度）：1=对称密码（AES-256/SM4）、2=SHA-2/SM3 哈希、3=RSA/ECC/SM2 公钥密码（量子脆弱）。

### 3.1 铃语风险矩阵（示例判定）

| 资产 | E | L | V | R | 判定 |
|---|---|---|---|---|---|
| FEED_URL 的 TLS 通道（若为传统 ECDHE） | 3 | 2 | 3 | 9 | 高：HNDL 可截存 AlertFeed 明文前向保护的只是会话，但若凭据走该通道则升级 |
| Push Kit REST 客户端凭据 | 3 | 3 | 3 | 9 | 高：长期有效 + 公网传输 + RSA/ECC 体系 |
| 百炼 TTS APIKey | 3 | 3 | 3 | 9 | 高：与上一条同因 |
| TTS 音频流（AVPlayer 播放） | 3 | 1 | 3 | 9→降 | 音频内容为公开行情播报，寿命极短，实际按中风险处置 |
| alerts.json 本地缓存 | 1 | 1 | 1 | 1 | 低 |
| 东财 API 降级通道（当前无鉴权） | 3 | 1 | 3 | 9→降 | 公开行情数据，中低风险，但通道完整性影响内容可信 |

注意：评分的目的不是算出一个精确数字，而是**强制排序**。同为 9 分的资产，还要按"是否可立即替换"做二次排序——这直接决定阶段三的路径。

### 3.2 必须单列的两类风险

1. **供应链密码债**：AGC、云函数运行时、华为 Push Kit REST 的服务端策略不受本方控制，只能"探测 + 推动上游"，要在 CBOM 里标注"外部依赖，无直接控制权"。
2. **密码刚性**：任何把算法名写死在调用点的代码（如硬编码 `'RSA2048|SHA256'`）都是迁移阻力。铃语若在 PushService.ets、AudioPlayer 中出现此类写法，风险记为"结构性"，即使算法本身暂不紧急。

## 四、阶段三：迁移路径（密码敏捷性优先）

### 4.1 核心原则：先建敏捷性，再换算法

直接把 RSA 换成 ML-DSA 是错误路径；正确路径是先让所有密码使用点经过一层**可配置的抽象**，算法选择变成数据（配置/协商结果）而非代码（硬编码字符串）。

```typescript
// common/AlgRegistry.ets —— 密码敏捷性抽象（示意，保持零三方依赖）
export interface FeedSignatureVerifier {
  /** 返回算法标识，便于审计与协商降级 */
  readonly algId: string;
  verify(payload: Uint8Array, signature: Uint8Array): Promise<boolean>;
}
```

### 4.2 混合过渡（Hybrid）策略

在过渡期同时使用传统算法与 PQC 算法（如 TLS 的 X25519+ML-KEM 混合密钥交换），安全性取"两者都破才破"。这解决了"PQC 算法尚新、实现可能有缺陷"与"传统算法量子脆弱"的两难。对铃语的现实含义：

- **传输层**：FEED_URL 与 Push Kit 所依赖的服务端若部署在 RHEL 10，OpenSSL 3.2 已提供 ML-KEM 混合交换能力（详见 rhel10-crypto.md），端侧 ArkTS 的 http/AVPlayer 栈跟随系统协商即可，**端侧无需自研 PQC**。
- **应用层**：鸿蒙 cryptoFramework 目前不提供 ML-KEM/ML-DSA，应用层签名继续用 SM2（配合密评要求），在抽象接口后预留 PQC 实现位，等待系统能力开放。这一判断要写入 CBOM 的"外部依赖"栏并定期复核。

### 4.3 排序与节奏

按"风险值 × 可替换性"排出四波：第一波是**长期有效凭据的通道升级**（凭据不落明文、通道混合化）；第二波是**公开但需防伪造的播报内容签名**（保完整性，防虚假信息诱导老年用户）；第三波是**本地缓存与设备密钥**（多数本就是对称密码，仅需确认长度）；第四波是**归档数据**。每波之间保留一个完整回归周期（首屏演示卡、轮询兜底、播报链路全部回归），任何一波失败可独立回滚。

回滚预案是迁移路径的组成部分而非附件：每波必须定义"配置回退点 + 密钥双活窗口"（新旧密钥同时可验，见 key-lifecycle.md 的轮换设计），并预先演练一次回滚。

## 五、阶段四：验证

验证分四类，缺一不可，全部通过才算本波完成：

1. **功能验证**：握手成功、签名验签通过、AlertPoller 5s 轮询无异常重试风暴；服务未连通时首屏仍显示带"示例"字样的演示卡（这是项目的不可逾越约束，验证脚本必须覆盖）。
2. **性能验证**：与阶段一记录的基线对比。关键指标——TLS 握手延迟增量（混合交换的公钥更大，预期有可感知但可接受的增量）、单次验签耗时、轮询周期内总开销。老年用户设备性能偏弱，性能预算应按低端机型设定，而非旗舰。
3. **互操作验证**：新旧客户端 × 新旧服务端的四象限矩阵（特别是降级路径：不支持混合的旧端必须仍能完成传统握手，不能因迁移直接断服）。
4. **合规与安全验证**：确认没有引入明文凭据日志（项目红线：不泄露任何 Token/密钥）；对照 crypto-law-compliance.md 复核密码应用合规项未回退。

### 5.1 通过标准（示例）

- 握手成功率 ≥ 基线的 99.9%；低配真机播报卡片端到端耗时增幅 ≤ 10%；验签失败率无上升；回滚演练一次成功；CBOM 更新并归档至 GOVERNANCE/skills/crypto/ 目录。

## 七、常见误区清单

- 只盯数据加密、忽略签名与凭据的长期性（HNDL 的主要受害面恰恰是凭据）。
- 在端侧自研 PQC 原型并上生产（违反零三方依赖精神且实现风险极高；正确做法是跟随系统能力与服务端协商）。
- 把 PQC 迁移当作一次性项目而非年度复评（CBOM 每半年复核一次，CRQC 预期与系统能力都在变化）。
- 迁移期间放松对现存问题的处置（Tushare 40101 降级、broadcast-a2a 待换 Push Kit REST 这些已知问题与迁移并行推进，不能互相阻塞）。
