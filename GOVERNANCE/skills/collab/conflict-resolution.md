# collab技能：A2A冲突解决——串行纪律、分区主权、越界规则、CHANGELOG仲裁

## 概述

多AI席位共写一个仓库，冲突不是意外而是常态：并发改同一文件、动了别人的分区、改了接口契约、说不清"这活是谁的"。本技能定义四道防线——串行纪律压缩冲突发生面、分区主权划清地盘、越界规则处置侵略、CHANGELOG仲裁解决遗留争议。四道防线层层递进，前一道失守才轮到后一道。

## 1. 串行纪律

### 1.1 规则本体

**同一时间只允许一个AI席位在本工程写代码。** 这是第一防线：既然写者唯一，绝大多数写冲突在源头就不存在。

### 1.2 开工三步

任何席位每次开工前必须执行：

1. `git status`——若存在未提交改动，先读CHANGELOG判断是谁的活：能对上最近条目则等对方收尾或接续完成；对不上则视为现场可疑，报告机主后再动；
2. 读CHANGELOG.md最后一条——确认最近一次改动的席位、范围与遗留事项，避开未收尾区域；
3. 干完立即提交：`git add -A && git commit`，并同步在CHANGELOG.md追加本次条目。

三步的实质是"以git与CHANGELOG为共享黑板"：席位间不共享记忆，共享的只有落盘事实。

### 1.3 交接与中断

- 被迫中断（额度耗尽、窗口过期）时，把已完成部分提交并在CHANGELOG遗留栏写明断点，后来者从断点接续而非重做；
- 接续他人工作时，CHANGELOG条目须注明"接续自[席位]的[条目时间]"，保持责任链连续。

## 2. 分区主权

### 2.1 主权表

| 分区 | 主权席 | 说明 |
|------|--------|------|
| harmony-app/（端侧） | 砚坚（CodeArts） | ArkTS UI、播报交互、Push封装 |
| quant-lab/ | 顾权（Kimi Code） | 取数、策略、监测、服务端出数 |
| GOVERNANCE/skills/ | 产出席位各自 | 谁产出谁署名，他人不得改写他人技能文档结论 |
| 接口边界 | 全席位共守 | AGENTS.md与AlertItem.ets定义的AlertFeed契约 |

### 2.2 主权含义

主权=排他写权+质量责任。主权席对自己分区内的缺陷负修复责任；非主权席发现问题只能提报（总线消息或proposal），不能代修。分区内的只读浏览不受限——禁的是写，不是看。

### 2.3 接口边界特殊地位

AlertFeed契约（字段、类型、语义）是端云两侧的连接组织，任何一方改契约都会撕裂对端。因此契约变更走类越界流程：先在CHANGELOG写明意图并停机主确认，确认前一律视为禁改。

## 3. 越界规则

### 3.1 什么算越界

1. 未经确认修改他方主权分区内的文件；
2. 未经确认修改接口契约（AlertItem/AlertFeed）；
3. 未经确认推翻工程既定基调（适老化28-34fp大字卡片流、PushService.ets占位封装降级轮询、首屏永不空白等）。

### 3.2 合法越界流程

越界并非绝对禁止，而是要走确认流程：

1. **写意图**：在CHANGELOG.md写明"拟改[文件]，原因[XX]，影响[XX]"；
2. **停机等待**：停工等待机主白秉烛确认，同时通过总线通知受影响席位；
3. **确认后动工**：拿到确认才改，CHANGELOG条目引用该确认；
4. **未确认先动**：一律按违规处理。

### 3.3 违规处置

发现未确认的越界改动：立即回退（git层面恢复原状），在CHANGELOG登记违规事实（席位、文件、时间、回退操作），情节严重的报机主裁处。回退优先于追责——先恢复工程到安全态，再算账。

## 4. CHANGELOG仲裁

### 4.1 仲裁三层级

1. **CHANGELOG.md最后一条优先**：时间序事实决定"谁在干活、干到哪"，并发争议以最后落盘条目为事实基准；
2. **AGENTS.md约束为最高规则**：工程级红线（适老化约束、零三方依赖、合规三条）高于任何席位条目，条目与AGENTS.md冲突时条目无效；
3. **机主白秉烛裁决为最终裁定**：前两层解决不了的（责任归属、优先级争议、契约变更），交机主，一次裁定，不再复议（除非有新事实）。

层级设计逻辑：先用事实（时间序）压制主观争辩，再用规则压制事实滥用，最后用人裁补规则盲区。

### 4.2 CHANGELOG条目格式

```
## YYYY-MM-DD HH:MM · [席位名]（[运行环境]）· [简述]

- **起因**：[为什么改]
- **改了什么**：[具体改动列表，含文件路径]
- **为什么**：[每个改动的理由]
- **如何验证**：[验证步骤V1-Vn，可复跑]
- **遗留**：[未完成事项编号列表]
```

条目质量决定仲裁质量：缺"如何验证"的条目在争议中证明力减半——无法复跑的改动等于无法辩护的改动。

### 4.3 常见冲突场景处置表

| 场景 | 处置方式 |
|------|---------|
| 两席位同时改同一文件（串行失守） | 后提交者负责合并，CHANGELOG记录合并过程与取舍 |
| 一方修改AlertFeed契约未确认 | 立即回退，登记违规，报机主 |
| 一方修改对方分区 | 立即回退，登记违规，通知主权席 |
| 双方对某文件主权归属有分歧 | 查主权表；表未覆盖的报机主裁定并回填主权表 |
| CHANGELOG条目与工作区事实矛盾 | 以git实际状态为准，矛盾作为疑点报机主 |
| 一方失联且留有半成品 | 按串行纪律接续，条目注明接续来源 |

### 4.4 仲裁流程六步

1. 冻结现场：停止相关文件的一切写入；
2. 取证：git log/diff + CHANGELOG条目 + 总线消息记录三方对照；
3. 定性：按第3.1节归类（并发、越界、契约、争议）；
4. 处置：套场景表执行（回退/合并/改派）；
5. 登记：CHANGELOG追加仲裁条目，含证据引用；
6. 回填：若暴露规则盲区（主权表缺口、流程漏洞），修订对应文档。

## 5. 串行纪律的适用边界

串行纪律覆盖的是**写代码**这一动作，不是所有协作行为，边界要说清楚否则会误伤。只读浏览、总线讨论、文档评审、在GOVERNANCE下各自主权目录内写文档，都不受串行限制——这些行为不会产生工作区写冲突。受约束的是对同一git工作区的源码与配置写入。此外，串行是按分区粒度生效的：砚坚在harmony-app端侧写代码的同时，顾权在quant-lab写代码并不违反纪律，因为它们是两个独立仓库工作区；真正的红线是同一工作区同一时刻仅一个写者。判断某个动作是否需要串行，就看一句：这个动作会不会让git status出现我造成的改动？会，就先走开工三步。

串行纪律还有一个隐性收益容易被忽略：它强制每次改动是完整可提交的。因为写者唯一，提交粒度不会被他人改动打散，CHANGELOG条目与commit一一对应，仲裁时的证据链因此干净。多人并行开发里"一半是我的改动一半是他的"那种泥潭，在串行纪律下从结构上不存在。

## 6. 越界的灰色地带判定

三种情况容易被误判为越界，需要显式豁免。第一，接口边界的**消费侧适配**：端侧按既有AlertFeed契约调整自己的解析代码不算改契约，只有改字段定义才算。第二，**对方分区内的登记性写入**：在自己产出的审查报告里引用对方文件路径是引用不是写入；往对方分区的README追加分区使用说明则须先征得主权席同意。第三，**机主裁定的紧急修复**：主权限额失联、缺陷阻塞全体时，机主可临时授权跨区修复，授权本身记入CHANGELOG，事后主权席有权复核并可要求返工。判定口诀：看写入位置是否在对方主权区、看内容是否改变契约或基调、看有没有事先确认或机主授权——三问皆是才动工，一问存疑就先停。

反过来，三种看似无害的动作实际是越界：重构对方代码"顺手"改进格式；在对方文件里加注释说明自己的理解；把自己分区的文件移进对方目录"便于管理"。这些动作共同的问题是绕过了责任链——出了问题追溯时，主权席面对的是自己没做过的改动。

## 7. 仲裁案例演示

用一个假设案例走完仲裁六步。背景：工作区发现entry/src/main/ets/model/AlertItem.ets被改，新增了一个字段，CHANGELOG无对应条目。第一步冻结：通知所有席位暂停对该文件的写入。第二步取证：git log锁定引入该字段的commit与作者席位；git diff取改动全文；查总线无契约变更提议消息——三方证据中两方（git与总线缺失）指向"未走确认流程"。第三步定性：落入3.1节第2类，契约越界。第四步处置：回退该字段改动，登记违规条目。第五步登记：CHANGELOG写入仲裁条目，引用commit哈希、diff摘要与总线查询结论。第六步回填：若该字段确有价值，越界方按合法流程重新提案，由机主决定是否合入。整个过程两小时内闭环，关键在于回退快、登记全、回填通道敞开——惩罚不是目的，让契约变更永远走正门才是。

## 质量门槛

- 仲裁结论必须三方证据（git、CHANGELOG、总线）中至少两方支持，孤证不定案；
- 每次回退/合并/改派都有CHANGELOG条目，证据链完整可复演；
- 契约变更零容忍未确认执行；
- 仲裁条目本身遵守4.2格式，含可复跑验证步骤。

## 经验记录

- 串行纪律的守门员是`git status`：一次命令就能暴露"现场有别人的活"，跳过它等于闭眼开车；
- CHANGELOG的"如何验证"栏平时像累赘，争议时是唯一的辩护证据；
- 回退优先于追责：工程安全态恢复永远排第一位；
- 多数"冲突"其实是失联误判——先查总线与心跳再定性，避免冤枉协作方。
