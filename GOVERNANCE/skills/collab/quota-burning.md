# collab技能：A2A额度共享与燃烧——额度探测、时间窗口排期、降级链、燃烧效率监控

## 概述

A2A网络的算力本质是"多家免费/限时额度的拼盘"：夜间亿级Tokens窗口、月度持续配额、一次性券。额度共享与燃烧技能回答四个问题——现在有哪些额度可用（探测）、什么时间烧什么（排期）、烧不动了怎么办（降级链）、烧得值不值（监控）。核心目标：让每一份会过期的额度在过期前转化为可持久化的知识资产，而不是白白流失。

## 1. 额度探测

### 1.1 探测三途径

1. **登记册查询**：首选GOVERNANCE/compute_resource_registry.md，各席位有义务把新获额度登记入册（来源、类型、规模、窗口、状态）；
2. **平台实测**：对登记存疑的额度，用平台控制台或最小API调用实测（发一条极短prompt看是否成功返回），实测结果回填登记册；
3. **席位自报**：各席位心跳或状态消息中携带自身额度余量与窗口，汇入总线。

### 1.2 探测节奏

- 常规每日一次；
- 已知窗口开关前后（如23:00夜间窗口开启、09:00过期）各加测一次；
- 触发降级后立即探测次选额度确认可用，避免降级链指向空额度。

### 1.3 额度资产三分类

| 类型 | 特征 | 管理策略 |
|------|------|---------|
| 限时窗口型 | 夜间免费、节假日促销、试用期 | 预排期，窗口内最大化消耗 |
| 持续配额型 | 月度免费额度、永久免费层 | 按需消耗，留作兜底 |
| 一次性券型 | 新用户券、活动券、补偿券 | 立即使用，防止过期 |

### 1.4 登记样例（2026-09-23时点状态，以登记册为准）

| 额度来源 | 类型 | 规模/窗口 | 状态 |
|----------|------|-----------|------|
| 码道(ZCode) GLM-5.3-Flash | 限时窗口 | 1亿Tokens，09:00过期 | 燃烧中 |
| WorkBuddy Hy4 preview | 限时窗口 | 夜间免费23:00-08:00 | 生效中 |
| WorkBuddy hy4-preview-f | 限时窗口 | 14天试用 | 待确认 |
| 阿里云DashScope | 持续配额 | 1M免费额度 | 待确认剩余 |
| 智谱API glm-4-flash | 持续配额 | 免费 | 可用 |
| 码道(CodeArts) GLM-5.2 | 持续配额 | 当前席位 | 持续可用 |

探测注意：任何探测动作不得在总线、聊天、日志中暴露凭据本体，只记录来源名与指纹（md5前16位）。

## 2. 时间窗口排期

### 2.1 排期表模板

```
燃烧排期表
├── 限时窗口型额度
│   ├── 窗口前：预排任务队列（任务已分解、六要素齐备、可即取即烧）
│   ├── 窗口中：不间断循环产出，短任务插空，长任务优先
│   └── 窗口后：检查产出完整性、字数达成率、归档登记
├── 持续配额型额度
│   └── 按需消耗，优先级驱动，留作降级兜底
└── 一次性券型额度
    └── 立即使用于不可替代任务（如需特定强模型的深度推理）
```

### 2.2 排期规则

1. **窗口决定日历**：排期以窗口为主轴，任务队列向窗口对齐，而非反过来；
2. **窗口前备料**：任务队列须在窗口开启前完成分解与匹配（见task-decomposition.md），窗口内零准备动作；
3. **尾窗切换**：窗口剩余<30分钟只派短任务（目标字数≤1500），避免半成品跨窗；
4. **并行分片**：无依赖任务分到不同额度来源同时燃烧，串行依赖最小化。

## 3. 降级链

### 3.1 标准模板

```
首选额度 → 次选额度 → 最终fallback
```

每个任务在派发时必须声明自己的降级链，链上每一环都经过探测确认可用。

### 3.2 实例

```
密码学报告 → hy4-preview-f（首选）→ CodeArts GLM-5.2（降级）→ Kimi（最终）
TTS生成 → DashScope（首选）→ 百炼WebSocket（降级）
代码审查 → CodeArts GLM-5.2（首选）→ Hy4 preview（降级）
长文生成 → Hy4 preview（首选）→ CodeArts GLM-5.2（降级）
```

### 3.3 切换触发条件

| 触发条件 | 动作 |
|---------|------|
| 首选额度余额不足 | 切换次选，CHANGELOG记录 |
| 首选额度窗口过期 | 切换次选 |
| 次选也不足 | 切换最终fallback |
| 全部不可用 | 标记BLOCKED，报告机主，任务回队 |

**锁定令的例外**：机主对特定席位的模型锁定令（如Moon锁定GLM-5.3-Flash、不得申请切换GLM-5.3）优先于降级链优化——锁定席位的"降级"只能是任务改派给其他席位，不是就地换模型。

## 4. 燃烧效率监控

### 4.1 监控指标

| 指标 | 目标 | 监控方式 |
|------|------|---------|
| Token消耗量 | ≥额度80% | 平台用量统计 |
| 产出文档数 | ≥预定目标 | 文件系统检查 |
| 产出字数 | ≥预定目标85% | 字数统计（汉字计数，不含自评） |
| 窗口利用率 | ≥90% | 发送/回执时间戳日志 |
| 质量评分 | ≥3分（满分5） | 三维自评+抽检 |

### 4.2 进度报告格式

```
=== 燃烧进度报告 ===
已完成：X/N
累计字数：XXXXX字
预估Token消耗：XXXX万
剩余额度预估：XXXX万
当前任务组：X
预计完成时间：XX:XX
当前模型：Flash/5.3
质量均分：X.X/5
```

报告频率：窗口内每完成一个任务组或每小时一次，以先到者为准；BLOCKED状态即时上报。

### 4.3 效率复盘四问

1. 会过期的额度是否在过期前烧完？没烧完的原因是任务不足还是通路故障？
2. 产出的知识资产是否全部归档落盘（而不是留在对话里）？
3. 质量均分低于3分的任务集中在哪类？是否该类任务下次直接派强模型席位？
4. 降级触发了几次？链上哪一环最常空转？

## 5. 实例：Moon席位燃烧计划

### 5.1 任务组结构（120项）

| 任务组 | 任务数 | 目标字数 | 推荐模型 |
|--------|--------|---------|---------|
| A组：云函数审查 | 35 | 17.5万字 | Flash |
| B组：技能文档 | 25 | 7.5万字 | Flash |
| C组：密码学 | 10 | 5万字 | 深度推理 |
| D组：A2A协议 | 10 | 4万字 | 深度推理 |
| E组：开发知识 | 15 | 4.5万字 | Flash |
| F组：虚拟角色 | 10 | 5万字 | 深度推理 |
| G组：燃烧策略 | 5 | 2万字 | Flash |
| H组：实战复盘 | 10 | 4万字 | Flash |

### 5.2 模型切换协议（现行锁定令下）

原计划"C/D/F组切换GLM-5.3、Flash连续2个任务自评低于3分自动切换"的前提已变更：机主常设令现锁定Moon席位为GLM-5.3-Flash，不得申请切换GLM-5.3（额度原因）。现行执行口径：

- 深度推理类任务（C/D/F组）在Flash上尽力产出，文末自评如实降档标注；
- Flash连续2个任务自评低于3分时，不自行切换模型，而是上报机主申请将任务改派给具备对应额度的席位；
- 窗口剩余<30分钟强制只做短任务的原则继续有效。

## 5. 一日排期实例

把排期方法落到一条真实时间线上。设当前为某日二十一点，手头任务队列传自task-decomposition技能，额度状态为：ZCode Flash窗口次日九点过期（余量充足）、Hy4夜间窗口二十三点开启、DashScope持续配额待确认。排期动作分三段。第一段（二十一点至二十三点，窗口间歇期）：用持续配额完成收尾类任务——上一窗口的归档登记、进度报告、队列复核，同时实测DashScope确认其可用性，为降级链补一环。第二段（二十三点至次日八点，双窗口重叠期）：主力烧Flash亿级窗口执行A组云函数审查与B组技能文档，Hy4窗口并行执行E组开发知识（互不依赖、不同分区可并行）；期间每小时出一份进度报告，尾段即八点前后只派短任务。第三段（八点至九点，窗口关闭前）：Flash窗口最后六十分钟降速收口，全部半成品任务要么压缩交付要么显式挂起记录断点，九点前完成窗口复盘四问。这份排期在二十一点成文落盘，窗口内零决策成本，是"窗口前备料"原则的具体形态。

排期有一条不成文的纪律：**排期表一旦成文，窗口内只执行不争论**。执行中发现排期错误，记录下来下一窗口修正，当前窗口保持稳定输出优先——窗口时间是全场最贵的资源，停下来开会讨论的代价高于按次优顺序执行。

## 6. 降级链设计方法学

设计一条可靠的降级链，比写下三个额度名难得多，方法上有四个要点。第一，**环的资格要验证**：每一环不只是"额度存在"，还要"额度能干这活"——用匹配矩阵核对该额度对任务类型的星级，星级不足的环是假环。第二，**环间产出要兼容**：首选与次选的交付物必须同规格（同样的交付路径约定、同样的自评格式），否则降级发生时下游验收标准跟着变，制造二次混乱。第三，**降级要留断点**：切换发生时，首选额度上已完成的部分先落盘归档，次选从断点接续而不是从头再来，接续信息写进任务记录。第四，**降级是事件不是常态**：某条链频繁触发降级，说明首选匹配就是错的，该修匹配矩阵而不是继续依赖链。每次降级触发后在CHANGELOG或任务记录里留一行：时间、任务、从哪环切到哪环、原因。累计十次以上就该复盘链条设计本身。

## 7. 燃烧纪律

额度燃烧最容易跑偏的不是技术是心态，四条纪律压住它。其一，**落盘优先于生成**：产出不落盘，Token就白烧——宁可少生成一篇，也要先把已完成的写盘归档；会话中断、额度跳闸随时可能发生，未落盘的产出等于不存在。其二，**质量分是硬约束**：自评低于三分的产出要么修补要么标记存疑归档，不允许蒙混计入完成数——燃烧监控的字数达成率必须扣除被标记存疑的部分，否则指标自欺。其三，**不烧无主任务**：没有任务编号与交付路径的"顺手写点东西"不计入燃烧，防止用低价值产出粉饰消耗率。其四，**合规红线贯穿燃烧全程**：任何产出的内容都不得承诺收益保本、不得含催促性指令、不得涉及对外公开收费方案、不得泄露凭据——燃烧得再快，红线一次就归零。

## 8. 监控数据采集实操

四个监控指标的采集方式逐一说明。Token消耗量取平台控制台读数，无法取到精确值时用"产出字数乘以经验系数"估算并在报告标注"估"字，不把估算值当实测值汇报。产出文档数与字数用脚本扫交付目录统计，汉字计数排除自我评估节，与任务验收同一口径。窗口利用率以任务回执时间戳序列计算：实际在产时间除以窗口总时长，准备与空转时间计入分母——利用率低的原因写进复盘，不许藏在口径里。质量评分取三维自评均值，机主或挂帅席对百分之十的产出抽检复核，抽检分与自评分偏差超过一分时，该席位后续自评整体乘以校准系数。所有监控数据落盘在burn-output目录下，按窗口归档，跨窗口对比时可以看出：哪个窗口烧得最值、哪类任务性价比最高、降级链哪一环最脆弱。

## 质量门槛

- 每次燃烧的额度来源、窗口、消耗量可从登记册+进度报告复算；
- 排期表在窗口开启前成文落盘；
- 每任务降级链三环均经探测确认，BLOCKED即时上报；
- 产出全部落盘归档，监控数据不含凭据明文。

## 经验记录

- 会过期的额度是负债不是资产：没排期的窗口额度等于零；
- 降级链指向空额度是最常见的"假兜底"，切换前必须实测次选；
- 燃烧产出若不落盘归档，Token烧完即归零——落盘优先于继续生成；
- 锁定令与降级链冲突时，改派任务而非就地换模型。
