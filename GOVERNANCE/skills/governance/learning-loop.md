# 技能：闭环学习方法

> 所属：GOVERNANCE/skills/governance/ ｜ 版本：v1.1 ｜ 日期：2026-09-23 ｜ 适用项目：harmony-app（代号铃语，鸿蒙适老化股票异动播报应用）

## 一、定位与总览

闭环学习是治理体系把"做过的事"变成"可复用能力"的标准流程，五步依次为：

**结果记录 → 质量评估 → 模式识别 → 技能编写 → 复用（回流到记录）**

一句话定义每步：结果记录——把发生了什么以可核查形式落盘；质量评估——给产出与记录本身打三维分；模式识别——跨事件找重复，提炼可泛化规则；技能编写——把模式写成技能文档；复用——下个同类任务先查技能库，用后回填效果，回到第一步。

循环不设终点：复用的效果本身成为下一轮记录素材，形成螺旋上升。这个方法要对抗的是代理会话的天然缺陷——每次会话结束，对话记忆即蒸发，如果没有闭环，项目会永远在"发现同样的问题、犯同样的错"上打转；有了闭环，第一次踩坑的成本才能摊销到之后每一次复用上。

触发时机：每次任务完成、每次事故处置完毕、每次 24 小时实验复盘（见 24h-autonomy.md 第 3.4 节）、每次交接收尾（见 handover-protocol.md），都是一次循环的起点。触发判定表：

| 事件类型 | 是否触发循环 | 首步时限 |
|---|---|---|
| 日常小改动 | 只记不评（首步即可） | 当日 |
| 事故处置完毕 | 全循环 | 处置后 24 小时内 |
| 实验复盘 | 全循环 | 复盘期内 |
| 交接收尾 | 全循环 | 自检通过后 |
| 红线相关事件 | 全循环且模式判定从速 | 立即 |

## 二、第一步：结果记录

### 2.1 载体（按优先级）

1. `GOVERNANCE/CHANGELOG.md`：一切变更与事件的时间线主账本，条目格式遵循 changelog-format.md 五要素；
2. 实验目录 `GOVERNANCE/experiments/24h-YYYYMMDD/`：实验类事件的 metrics.csv、incident.md、report.md；
3. `GOVERNANCE/KNOWN-ISSUES.md`：缺陷与现状登记。

### 2.2 最小记录单元（三件套）

现象（可核查证据：日志行、截图路径、接口返回码）、处置（改了哪个文件或配置）、结果（有效/无效/部分有效）。缺证据的现象一律降级为"待核实"，不得作为后续归纳依据——这是防臆测进入闭环的第一道闸门：把猜测当事实记录，后面的模式识别会把错误放大成规则，比不记录更糟。

### 2.3 记录的输入输出

本步输入：任务产出物、日志、截图、当时的判断。动作：按五要素落账、KNOWN-ISSUES 登记。输出：完整条目与证据文件。本步产出即质量评估的对象，记录写得含糊，评估就无据可评。

## 三、第二步：质量评估

对刚完成的任务或处置评三维分（各 1-5）：

- 正确性：结论与改动是否与事实相符，有无把臆测当事实；
- 完整性：要求覆盖的点是否全覆盖（对照任务清单或实验指标表）；
- 可复用性：换一个会话或接手者，凭留下的材料能否复现同样结果。

评分纪律：分数必须附一句话简述并指向具体事实；正确性打 5 分须能通过"冷启动复现"想象测试（见 skill-doc-format.md 第四章）；任一维度 ≤2 分时，必须在 CHANGELOG 条目的"遗留什么"里登记改进动作，否则本次评估无效。评估对象包括记录本身——如果复盘时发现记录缺证据，评估的就是"记录质量差"这件事，它同样是一条待改进记录。

## 四、第三步：模式识别

跨记录找重复，操作步骤四拍：

1. 聚簇：每周或每个实验复盘时，把近期 CHANGELOG 与 incident 记录按主题聚簇（数据源、TTS、推送、首屏、合规、治理流程）；
2. 判定：同簇同类事件 ≥2 次，才升级为候选模式；单次偶发（如一次网络抖动）只进 KNOWN-ISSUES，不成模式；
3. 表述：候选模式写成一条可泛化规则，句式固定——"当 X 条件出现时，应当 Y，因为 Z"；
4. 分类：区分工程模式（如外部依赖与预设不符时占位/降级保主链路）与治理模式（如记录缺失导致复盘失明）。

聚簇的实操做法：把近期条目逐条抄到一张草稿上，在相关条目间画连线，凡是连成两节点以上的线就是一个候选簇。工具不重要，重要的是逐条过目——模式的敌人是"懒得翻旧账"。

### 模式句式正反对照

坏表述（叙事散文）："这次数据源挂了，我们切了备用源，效果不错，以后也可以这么干。"——不可执行、不可证伪、无法转成技能段落。

好表述（规则句式）："当外部依赖返回鉴权失效或服务不可用错误时，应当先切换备用源或占位降级保住主链路与首屏兜底，因为用户侧服务连续性优先于后端完美性；凭据补救另行异步处理，凭据本身不入文档。"——当 X、应当 Y、因为 Z 三段齐全，可直接作为技能的方法主体句。

## 五、第四步：技能编写

按 skill-doc-format.md 六步流程把模式写成技能文档：

- 落盘位置：`GOVERNANCE/skills/<分类>/<主题>.md`；治理类入 skills/governance/；工程集成类可入 skills/integration/；
- 命名：主题式短横线命名，与既有五技能（24h-autonomy、changelog-format、skill-doc-format、learning-loop、handover-protocol）风格一致；
- 硬要求：过该规范第三章五门槛与冷启动验证；写完追加 CHANGELOG 条目并登记技能索引；
- 拒绝越级：只有第三步产出的候选模式才可成文，防止单次事件稀释技能库信噪比。

一条候选模式不必强行独立成文：若它与既有技能高度相关，优先修订既有技能并递增版本号，而不是新建文件。技能库的价值密度取决于每篇都被高频复用，而不是篇数多少。

## 六、第五步：复用与回流

1. 先查后做：任务启动时先看技能索引 `GOVERNANCE/skills/README.md`，与本任务相关的技能必须先读再动手；
2. 失效即录：执行中发现技能误导或失效，当场记录（这就是新循环的第一步），复盘时修订技能并递增版本号；
3. 有效即注：执行有效，在收尾 CHANGELOG 条目的"为什么"里注明依据了哪个技能，便于统计命中率；
4. 回流成环：复用效果进入下一轮记录，循环回到评估环节，闭环不中断。

回流是五步中最容易被忽略的一步：技能写完如果没有"用后回填"的机制，命中率永远无法统计，技能库的健康度就只剩体感。回流的成本极低（收尾条目里多写一句），收益是整个循环的度量基础。

## 七、循环度量与健康度

| 指标 | 含义 | 健康值 |
|---|---|---|
| 记录率 | 事件具备三件套记录的比例 | 100% |
| 模式转化率 | 候选模式中最终成文技能的占比 | ≥50%（过低说明识别太滥） |
| 技能命中率 | 新任务启动时命中可复用技能的比例 | 逐季上升 |
| 技能失效率 | 复用时发现技能误导的比例 | ≤20%（过高说明工程演化快于文档，需集中修订） |
| 闭环周期 | 事件发生到技能成文的中位时长 | ≤2 周 |

度量数据来源即 CHANGELOG 与技能索引，无需另建系统；每月复盘时顺带核算一次即可。指标越界的处置：记录率 <100% 先补记录再谈其他；失效率 >20% 暂停新技能编写，集中两周做存量修订——继续写新技能只是往一个漏的桶里加水。

## 八、项目实例走查一（Tushare 40101 降级东财）

用真实事件走完五步，作为执行模板：

1. 结果记录：CHANGELOG 追加条目（工程-数据源，降级动作，依据 40101），KNOWN-ISSUES 登记凭据失效；
2. 质量评估：核对降级后 FEED 数据满足 AlertFeed 契约、卡片流不空白——正确性 4（涨跌幅精度字段未核对）、完整性 4、可复用性 4，简述指向具体字段；
3. 模式识别：与"百炼 TTS 仅支持 WebSocket""broadcast-a2a 推送需换华为 Push Kit REST""PushService.ets 占位封装待 AGC 配置"聚簇，得到候选模式："当外部依赖与预设不符或不可用时，应当先占位/降级保住主链路与三底线，因为用户侧服务连续性优先于后端完美性"；
4. 技能编写：该模式可沉淀为"外部依赖降级预案"技能（规划中，拟落盘 `GOVERNANCE/skills/integration/degradation-playbook.md`，成文前在本文档与索引中标注"规划中"）；
5. 复用：下次接入新外部依赖（如华为 Push Kit REST 落地）时，先读该技能再动手，处置完毕回填效果，开启下一轮循环。

## 九、项目实例走查二（首屏演示卡兜底）

第二个真实场景，演示治理模式的提炼：

1. 结果记录：一次会话发现服务未连通时首屏短暂无内容，随后补上"带示例字样演示卡"逻辑，条目落账；
2. 质量评估：正确性 5（有截图与代码路径佐证）、完整性 3（未覆盖冷启动飞行模式场景）、可复用性 4，完整性扣分点登记为遗留；
3. 模式识别：与"alerts.json 的 audioUrl 为 undefined 时端侧按需调 generate-tts""PushService 未配置 AGC 前降级轮询"聚簇——三件事的共同点是"外部条件不满足时端侧必须有兜底而非空白/报错"，得到候选治理模式："当任何外部条件（数据源、音频、推送、网络）不满足时，应当让端侧呈现兜底内容而非空白或异常，因为适老用户对空白与报错的容忍度极低"；
4. 技能编写：该模式已在 24h-autonomy.md 的指标体系与安全阀中部分固化（首屏非空白 100%、演示卡兜底），后续可整合为独立"端侧兜底设计"技能（规划中）；
5. 复用：任何新增卡片类型（如公告类异动）设计评审时先过这条模式——新卡片必须回答"数据缺失时显示什么"，答不出不予合入。

两例对照可见：实例一产出工程模式（降级预案），实例二产出治理模式（兜底设计），两者句式一致但去向不同——前者进 integration 技能，后者反哺实验指标与评审门槛。

## 十、反模式与对策

1. 只记录不评估：账本很厚但没有分数与简述，复盘无从下手。对策：评分纪律绑定 CHANGELOG 遗留字段；
2. 越级归纳：单次事件直接写成技能，稀释信噪比。对策：≥2 次聚簇判定硬门槛；
3. 技能僵尸化：写完从不复用、从不修订，命中率永远为零。对策：复用回填机制与失效率指标；
4. 循环断裂在回流：任务开始不查技能库，闭环退化为单向流水账。对策：任务启动清单第一项就是查索引；
5. 模式句式失守：候选模式写成叙事散文而非"当 X 应当 Y 因为 Z"，无法直接转化为技能的规则段。对策：第四拍句式模板，不合式即打回重写。
