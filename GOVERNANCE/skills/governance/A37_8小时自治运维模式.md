# A37 — 8小时自治运维模式

## 概述

从2026-09-23的8小时自治运维会话中提炼的可复用执行模式。该模式验证了单AI席位在明确约束下可稳定自治运行8小时+，完成8项任务（H1-H8），无需人工干预。

## 适用场景

- 机主委派长周期自治运维任务（4小时以上）
- 需要系统性推进多个独立任务单元
- 需要在任务完成后自动沉淀知识资产

## 执行步骤

### 1. 时间线规划（开工前）

将可用时间划分为N个时段（H1-HN），每个时段分配一个独立任务单元：

```
H1 → H2 → H3 → ... → HN
```

**规划原则**：
- 高优先任务排在前面（防止时间不足时低优先任务挤占高优先任务时间）
- 每个任务单元有明确的输入、输出和验证步骤
- 任务单元之间相对独立，前一个任务的失败不阻塞后一个任务

### 2. 任务分解

每个任务单元包含：
- **目标**：一句话描述要完成什么
- **输入**：需要读取哪些文件/数据
- **输出**：要产出哪些文件/修改
- **验证**：V1-V5验证步骤
- **遗留**：未完成项的明确记录

### 3. 串行纪律执行

遵循 AGENTS.md §三串行纪律：
1. 开工前 `git status` + 读 CHANGELOG 最后一条
2. 执行任务
3. 立即 `git add -A && git commit`
4. CHANGELOG.md 追加条目（谁/何时/改了什么/为什么/遗留什么）

### 4. 闭环学习（每个任务完成后）

1. **结果记录**：CHANGELOG.md追加条目
2. **质量评估**：执行验证步骤V1-V5
3. **模式识别**：从个案中提炼共性
4. **技能编写**：将模式编写为可复用技能文档
5. **下次复用**：遇到同类任务时引用已有技能

### 5. 知识资产交叉引用

在技能索引中维护交叉引用矩阵，确保：
- 新技能文档与相关已有技能建立关联
- 技能复用统计及时更新
- 缺口清单反映最新状态

## 质量门槛

- 每个任务单元必须有验证步骤（V1-V5）
- 每次代码修改必须通过 git commit 提交
- CHANGELOG 条目必须包含"改了什么/为什么/如何验证/遗留"
- 技能文档必须遵循 FORMAT_SPEC.md 格式规范
- 串行纪律不可违反（一次只允许一个AI席位写代码）

## 经验记录

### 从本次8小时运维中提炼的模式

1. **重构改造旧代码清理模式**：并行化/异步化重构时，新旧代码并存期间应使用 TODO 标记标注待删除区域，避免遗漏（P0 BUG根因）

2. **Set缓存优化模式**：在 ForEach 中对每个列表项执行 `Array.includes()` 是 O(n) 查找，改为 `Set.has()` 可 O(1)。需在所有赋值点同步更新 Set。

3. **报告熔铸整合模式**：两份有重叠内容的报告整合为一份时，消除重复段落，保持逻辑连贯，原始报告保留作为溯源参考。

4. **缺口清单动态更新模式**：每次完成文档补齐后立即更新缺口清单状态，新增缺口及时登记。

5. **环境变量审计模式**：grep `process.env.` 获取全量环境变量引用，与 .env 文件对照，确认敏感变量在 .gitignore 中。
