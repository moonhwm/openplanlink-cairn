# 技能：交接协议

> 所属：GOVERNANCE/skills/governance/ ｜ 版本：v1.1 ｜ 日期：2026-09-23 ｜ 适用项目：harmony-app（代号铃语，鸿蒙适老化股票异动播报应用，纯 ArkTS + 云函数）

## 一、目的与适用场景

席位交接（Moon 更替、工程角色换人、长期中断后恢复、席位扩编）是知识资产流失风险最高的时刻：对话记忆不可迁移，聊天记录不可检索，未落盘的"潜规则"随人消失。本协议用"分级材料清单 + 固定阅读顺序 + 验收自检"把交接变成可核查的流程，而非一次聊天。

交接失败的代价要量化地看：一个接手者如果漏读了已知问题清单，很可能把"Tushare 已降级东财"当成自己的新发现，重复排查半天；如果漏读了红线清单，第一篇产出就可能写出承诺收益的文案。本协议的所有设计，都是为了让这两类事故在结构上不可能发生。

适用场景：任何形式的接任者进入工程；交出方离场前的收尾；恢复一个搁置已久的会话或工程分支。

## 二、交接三原则

1. 文档优先于记忆：一切交接以落盘文档为唯一媒介，口头与聊天内容仅作导航，不作为事实来源——文档会留在仓库里被后续席位继续核对，聊天记录不会；
2. 顺序阅读：材料按第四章顺序读，跳读等于漏读，尤其是红线与已知问题两块，漏读的后果不对称；
3. 验收自检：接手者必须通过第五章自检清单才算交接完成，"我大致看过了"不算通过，自检结果本身要落账。

## 三、必读材料清单（三级分级）

### 3.1 P0 必读（缺一不可，预计 60-90 分钟）

| # | 材料 | 内容与理由 | 验收问题 |
|---|---|---|---|
| 1 | `GOVERNANCE/README.md`（治理总纲） | 席位权责、不可逾越约束、合规三条红线 | 红线是哪三条？ |
| 2 | 本文件 `GOVERNANCE/skills/governance/handover-protocol.md` | 交接流程本身 | 交接期行为约束是什么？ |
| 3 | `GOVERNANCE/KNOWN-ISSUES.md` | 当前坏在哪里：Tushare 40101 已降级东财 API；百炼 TTS 仅支持 WebSocket；broadcast-a2a 推送需换华为 Push Kit REST；alerts.json 的 audioUrl 为 undefined 时端侧按需调 generate-tts | 当前数据源是谁？为什么？ |
| 4 | `GOVERNANCE/CHANGELOG.md` 最近 20 条（倒序） | 项目怎么走到今天 | 最近一次重大降级动作是什么？ |

P0 的选取标准：读漏任何一份都会导致接手者做出危险动作。红线清单防越界，已知问题防重复排查，时间线防误解现状成因。

### 3.2 P1 应读（预计 90-120 分钟）

| # | 材料 | 内容与理由 |
|---|---|---|
| 5 | `GOVERNANCE/skills/governance/` 五技能全文 | 既定打法：实验方法、账本规范、文档规范、学习闭环、交接协议 |
| 6 | `GOVERNANCE/skills/README.md` 技能索引 | 技能库全景与任务命中入口 |
| 7 | `entry/src/main/ets/entryability/EntryAbility.ets` | 架构入口：Push 初始化 + onNewWant 带 alertId 拉起定位 |

| 10 | AlertFeed 数据契约（FEED_URL 待 X 服务器落地） | 端云唯一接口契约 |

注：第 7-10 项按 Stage 模型默认目录书写，若工程结构调整，以实际路径为准；若 P0/P1 所列治理文件尚未建立，接手者应把"补齐该文件"登记为 CHANGELOG 遗留事项，而不是跳过——缺文件本身是最高优先级的交接发现。

### 3.3 P2 选读（按需）

最近一次 24 小时实验报告（`GOVERNANCE/experiments/` 下最新目录，读 report.md 即可）、云函数源码（generate-tts、数据聚合）、`GOVERNANCE/skills/integration/` 等扩展技能（规划中）。选读的判断标准：接手者的第一项任务落在哪个模块，就优先读哪个模块的 P2 材料。

## 四、阅读顺序与理由

固定顺序：**总纲 → 已知问题 → 时间线 → 技能 → 代码**。

理由逐层展开：先读总纲，知道什么不能碰——红线与约束先行，防止上手第一件事就越界；再读已知问题，知道现在哪里是坏的——避免把已知缺陷当新发现重复排查，也避免踩进别人已经绕开的坑；再倒序读时间线，知道缺陷是怎么来的、为什么那样处置——例如不理解 40101 事件，就会不理解为什么数据源代码里留着一段注释掉的 Tushare 调用，甚至好心把它"清理"掉；然后读技能，掌握既定打法，避免重新发明流程——五个技能就是这个项目的操作手册；最后带着以上全部背景读代码，此时每一行代码都有语境，占位、降级、兜底各有其名，效率最高。

最大反模式是把顺序倒过来：一上来读代码，一周后仍分不清哪些是占位、哪些是降级、哪些不能动，然后开始"顺手优化"，破坏架构基调。

### 4.1 分日阅读计划（完整交接场景）

| 时间 | 内容 | 产出 |
|---|---|---|
| 第1日上午 | P0 四项 + 第五章自检初测 | 标出答不出的题 |
| 第1日下午 | P1 第 5、6 项技能库 + 回看 P0 补漏 | 自检复测通过 |
| 第2日上午 | P1 第 7-10 项代码走读，对照已知问题逐条定位 | 每条已知问题找到对应代码位置 |
| 第2日下午 | P2 按任务选读 + 首个只读观察任务 | 交接验收条目落账 |

压缩版（中断恢复场景）只需第 1 日：P0 加自检即可恢复工作，P1 在随后三天内补齐。

## 五、接手验收自检（10 问）

接手者须能不查资料闭卷回答以下问题；答不出 ≥2 题回到 P0 补读后再验：

1. 三条内容红线是什么？各自边界？
2. 适老化的字体与文案硬约束是什么（28-34fp、大字白话卡片流、禁 K 线图等复杂图表）？
3. 首屏永不空白如何兜底？演示卡必须带什么字样？
4. 当前数据源是谁？为什么？恢复 Tushare 需要什么？
5. alerts.json 里 audioUrl 为 undefined 时端侧行为是什么？
6. PushService 现状与目标链路分别是什么？
7. Stage 模型下本项目的 SDK 版本（compatibleSdkVersion 20、targetSdk 26）与零三方依赖约束是什么？
8. CHANGELOG 五要素是哪五项？
9. 什么情形必须触发 24 小时实验安全阀？
10. 接手第一个 24 小时允许做什么、禁止做什么？

闭卷的含义：不看仓库不查文档口头作答，答完自行对原文核对。抄文档作答等于没测——自检测的是留存率，不是复制能力。

## 六、交接期行为约束（接手者首个 24 小时）

1. 只读观察：允许读文档、读代码、跑构建、看日志；禁止修改代码与配置（活跃事故处置除外，且处置后立即按 changelog-format.md 补条目）；
2. 不推翻架构基调：EntryAbility、Index 卡片流、AudioPlayer、AlertFeed 契约视为不可变基线，改造提案先落文档再议；
3. 不泄露凭据：文档、日志、代码注释、对话中均不得出现 Token/密钥原文；
4. 全程带标签：交接期所有动作在 CHANGELOG 中以 `[交接期]` 阶段标签 + `#handover` 标签记录。

只读期存在的理由：接手者头一天的理解必然不完整，此时做的任何"改进"都是在误解基础上动刀；而只读观察产出的疑问清单，恰恰是检验交接质量的最好样本。

## 七、场景变体

三种交接形态共用材料清单，差异在流程裁剪：

| 场景 | 材料范围 | 自检 | 交出方动作 |
|---|---|---|---|
| 完整交接（换人） | P0+P1，P2 按需 | 10 问全测 | 收尾五动作全做 |
| 长中断恢复（同人回归） | P0 第 3、4 项 + 自检 | 抽测 4、5、6、9 四问 | 无交出方，自任交出：先更新 KNOWN-ISSUES 再自测 |
| 扩编接入（新增席位） | P0 + P1 中与本席位相关模块 | 10 问全测 | 由 Moon 代行收尾，明确新席位权责边界 |

长中断恢复最容易被忽视：中断超过两周，即使是原作者也要按恢复流程走 P0——工程在中断期内可能已被其他席位改动，昨天的记忆比没有记忆更危险。

中断时长的判定阈值：中断两周以内且 CHANGELOG 无其他席位新增条目，视为短中断，倒序读最近五条账目后直接继续工作；中断超过两周，或中断期内账本有任何新增，一律按长中断恢复流程完整走 P0 四项。判定本身花不了五分钟，误判的代价是把过期认知带进决策，而过期认知比空白认知更难自我察觉。

## 八、交接双方职责与收尾动作

交出方收尾五动作：

1. 按第三章清单逐项核对材料在位且为最新版本；
2. 未完成事项逐条落入 CHANGELOG 条目的"遗留什么"，不留口头账；
3. KNOWN-ISSUES.md 更新到当前真实状态；
4. 技能索引指向有效（失效技能标注待修订）；
5. 追加最后一条条目：`[时间] [原席位] [交接期] 交接完成，接任者为 <席位标识> #handover`。

接手方收尾三动作：

1. 完成第五章自检，把答题结果（含答错的与补读记录）追加为 CHANGELOG 条目，WHO 写新席位、阶段写交接期；
2. 首个自主任务完成后执行一次完整学习闭环（learning-loop.md 五步）；
3. 首周内对任一技能文档执行一次冷启动验证（skill-doc-format.md 第四章），结果回填技能修订。

交接验收条目模板：

```markdown
- **[YYYY-MM-DD HH:mm (+08:00)] [接手席位] [交接期]**
  - 改了什么：完成交接验收自检，10 问通过 10（首次 8，补读 P0 第 3 项后复测通过）。
  - 为什么：按 handover-protocol.md 第五章要求留痕；错题集中在已知问题清单第 X 条。
  - 遗留什么：P2 云函数源码未读，首个任务涉及 generate-tts 时先补读。#handover
```

## 九、反模式

1. 口头交接：靠聊天与记忆，文档零更新，两周后知识归零。对策：交接双方约定"不落账不算交接完成"；
2. 全量倾倒：把仓库所有文件扔给接手者"自己看"，无分级无顺序，红线最容易被漏。对策：严格按 P0/P1/P2 分级投喂并限时；
3. 带病交接：已知问题不登记就让接手者接盘，接手者把已知缺陷当新发现重复排查。对策：交出方收尾把 KNOWN-ISSUES 更新设为硬性动作；
4. 越权热身：接手第一天就重构，违反只读约束与架构基调。对策：首个 24 小时只读约束写成可打勾清单；
5. 自检走过场：10 问抄文档作答，未真正闭卷。对策：自检结果落账，错题与补读记录一并留痕；
6. 中断恢复凭记忆：老作者跳过 P0 直接动手，把过期认知当现状。对策：两周阈值判定，超时必走 P0。

### 自我评估
- 正确性：4分 材料清单、自检问题、场景变体全部锚定项目共享事实（架构基调、已知问题、约束、既有技能路径与 SDK 版本），Stage 默认路径已注明"以实际为准"；治理配套文件若未建立已有登记指引。
- 完整性：5分 覆盖清单、顺序、分日计划、自检、行为约束、场景变体、双方职责、验收模板与反模式；未含多席位并行交接的冲突处理。
- 可复用性：5分 分级表格、分日计划、10 问清单、验收条目模板可直接执行，交出/接手双方动作各自成列，可打勾验收。
- 字数：约2650字（实测2643汉字，正文不含自评）
- 使用模型：GLM-5.3-Flash
