# 技能：CHANGELOG 条目规范

> 所属：GOVERNANCE/skills/governance/ ｜ 版本：v1.1 ｜ 日期：2026-09-23 ｜ 适用项目：harmony-app（代号铃语）

## 一、目的与适用范围

CHANGELOG 是 harmony-app 治理体系的"时间线主账本"：任何席位（Moon 或各工程角色）、任何变更（代码、文档、配置、实验、事故处置、交接）都必须追加条目。本规范定义条目的五要素结构、标准模板、分类标签与质量门槛，适用于项目全生命周期的所有记录场景。

设计目标只有一个：让三个月后没有任何对话记忆的读者，凭单条条目就能还原"当时谁在什么阶段、动了哪个文件、出于什么依据、留下了什么坑"。账本的第一读者不是写它的人，而是接手者、审计者与未来的自己——这三类读者共同的特征是没有当时的上下文。

## 二、存放位置与追加规则

1. 单一账本：全项目仅 `GOVERNANCE/CHANGELOG.md` 一个账本，不按模块拆分，保证时间线全局可排序；
2. 倒序追加：新条目置于条目区顶部第一条；
3. 只追加不改写：已写入条目不得修改或删除；发现写错，另追加更正条目并引用原条目时间戳；
4. 时间戳格式 `YYYY-MM-DD HH:mm (+08:00)`；同批次多条目时间允许相同，用序号区分；
5. 无事之日不强制写"无异常"，但实验日、交接日、事故日、红线处置日必须有条目。

单一账本的理由要说明白：按模块拆账本看似清爽，实则破坏全局排序——当一次故障同时涉及端侧与云函数时，拆分的账本让人在两份文件间来回拼时间线，遗漏几乎必然发生。检索问题应该交给标签与全文搜索解决，而不是交给账本分叉。

## 三、五要素详解

### 3.1 谁（WHO）

写席位与角色，不猜自然人身份。合法取值示例：`Moon`、`工程-端侧`、`工程-云函数`、`工程-数据源`、`治理-审计`。禁止"我""某人"这类指代；交接期写明来龙去脉，如 `工程-端侧(交接自Moon)`。多席位协作时只写主责席位，协作者写进"改了什么"的正文里。

### 3.2 何时（WHEN）

时间戳 + 阶段标签。阶段取值固定：`常驻`、`实验24h窗口A/B/C/D`（与 24h-autonomy.md 的窗口命名一致）、`交接期`、`事故处置`、`复盘`。阶段标签让倒序阅读时能快速过滤出关键时期；跨阶段的动作（如实验窗口内触发安全阀后处置）取动作实际发生时所处的阶段，并在正文注明来源窗口。

### 3.3 改了什么（WHAT）

必须给出可定位对象：文件路径（如 `entry/src/main/ets/pages/Index.ets`）、函数或组件名、云函数名、或文档路径。变更动词用白名单：新增/修改/删除/回滚/降级。一个条目只写一件事；一次提交包含多件事就拆成多条（拆分示例见 6.6 节）。量化信息能写则写：改轮询间隔就写明从多少秒到多少秒，改重试次数就写明次数与间隔，"调整"后面必须跟数字。

### 3.4 为什么（WHY）

写动机与依据。依据可以是：外部事件（如 Tushare 返回 40101）、合规红线要求、实验报告结论、已知问题编号、架构基调约束。禁止"优化""完善""调整细节"这类零信息量表述——它们的问题不在于简短，而在于无法证伪：读者既不能判断改动是否必要，也不能在同类问题复发时检索到这条记录。

### 3.5 遗留什么（LEFT）

未完成事项、风险、接手提示，必须写；确无遗留也要显式写"无遗留"，不允许留空。这是五要素中最常被漏掉、却对接手者最有价值的一项。遗留分三类措辞：未完成（事项+完成条件）、风险（现象+触发条件+观察方式）、接手提示（路径+先看什么）。

### 3.6 五要素缺失速查表

| 缺失要素 | 典型症状 | 补救方式 |
|---|---|---|
| 谁 | 无法追责也无法请教 | 更正条目补席位 |
| 何时 | 无法与日志对齐 | 更正条目补时间戳 |
| 改了什么 | 复盘时找不到改动位置 | 更正条目补路径 |
| 为什么 | 改动是否必要无法判断 | 更正条目补依据 |
| 遗留什么 | 同类问题复发无人预警 | 更正条目补遗留，并评估是否入 KNOWN-ISSUES |

注意补救一律走追加更正条目，不回头改原文——账本的可信度建立在不可改写之上。

## 四、标准模板

```markdown
- **[YYYY-MM-DD HH:mm (+08:00)] [WHO] [阶段标签]**
  - 改了什么：[变更动词] `文件路径` 的 [对象]，一句话说明。
  - 为什么：[动机]；依据：[外部事件/红线/报告/已知问题#编号]。
  - 遗留什么：[未完成/风险/接手提示]（或"无遗留"）。#标签
```

## 五、分类标签

条目尾部可带标签便于检索：`#feat #fix #docs #governance #incident #experiment #handover`。强制项：事故条目必带 `#incident` 并引用证据路径；实验条目必带 `#experiment` 并引用实验目录路径（如 `GOVERNANCE/experiments/24h-20260924/`）；交接条目必带 `#handover`。标签是检索入口而非装饰，一条条目标签数不超过两个，贴满标签等于没有标签。

## 六、正反例对照

### 6.1 反例：全要素缺失

`- 修了一些问题，系统更稳定了。`

无身份、无时间、无对象、无依据、无遗留，检索价值为零，复盘时无法归因。

### 6.2 正例：数据源降级（取材项目真实事件）

```markdown
- **[2026-09-20 15:40 (+08:00)] [工程-数据源] [常驻]**
  - 改了什么：降级数据源主链路：Tushare 返回 40101（token 失效）后切换为东财 API 拉取异动行情，Tushare 调用保留注释代码。
  - 为什么：token 失效且当日无新凭据可用，异动播报不能断流；依据：外部事件 40101 + 首屏永不空白约束（无数据时只剩演示卡不可接受）。
  - 遗留什么：恢复 Tushare 需新 token，凭据不落库不入文档；东财字段到 AlertFeed 契约的映射仅核对主字段，涨跌幅精度字段未核对——接手者若发现卡片数值精度异常，先查此映射。#fix
```

### 6.3 正例：云函数重试逻辑

```markdown
- **[2026-09-21 11:05 (+08:00)] [工程-云函数] [常驻]**
  - 改了什么：修改 generate-tts 重试逻辑：WebSocket 连接失败重试 2 次，间隔 3 秒。
  - 为什么：alerts.json 的 audioUrl 为 undefined 时端侧按需调 generate-tts，而百炼 TTS 仅支持 WebSocket，偶发握手失败导致卡片无语音；依据：已知问题清单。
  - 遗留什么：重试次数硬编码在函数内未配置化；如后续压测再参数化。#fix
```

### 6.4 正例：治理与交接

```markdown
- **[2026-09-23 22:30 (+08:00)] [治理-审计] [交接期]**
  - 改了什么：新增 `GOVERNANCE/skills/governance/handover-protocol.md`，定义席位交接必读材料清单与阅读顺序。
  - 为什么：席位更替时知识依赖对话记忆，接手方上手慢且易漏红线；依据：治理总纲"文档优先于记忆"原则。
  - 遗留什么：KNOWN-ISSUES.md 条目编号体系尚未与 CHANGELOG 时间戳打通，跨文件检索暂靠全文搜索。#handover
```

### 6.5 正例：实验宣告与事故

```markdown
- **[2026-09-24 08:20 (+08:00)] [Moon] [常驻]**
  - 改了什么：新增实验目录 `GOVERNANCE/experiments/24h-20260924/`，宣告 24 小时自治实验开窗，四窗口排期 08:30 起算。
  - 为什么：数据源降级与 TTS 重试两项变更落地后需整体验证自持能力；依据：24h-autonomy.md 实验方法。
  - 遗留什么：准备期五项清单已全部打勾；FEED_URL 所在服务器当日无迁移计划。#experiment

- **[2026-09-24 13:12 (+08:00)] [工程-端侧] [事故处置]**
  - 改了什么：回滚 Index.ets 当日误提交的轮询间隔改动（10 秒回退为 5 秒），进程重启一次。
  - 为什么：实验窗口B发现间隔改动未走变更流程且导致异动卡片延迟；触发安全阀第 6 条外的记录类异常，属 P2；证据：logs-windowB.txt 第 214-230 行。
  - 遗留什么：误提交来源待查（是否有人违规在冻结期部署）；后续处置见 incident.md。#incident
```

### 6.6 批量变更拆分示例

坏条目（一条打包三件事）：

`- 更新了播报模块：改了音频重试、换了数据源、调了卡片字号。`

拆成三条：generate-tts 重试一条（云函数席位）、数据源降级一条（数据源席位）、卡片字号一条（端侧席位，写明 fp 值从多少调到多少、是否仍在 28-34fp 区间内）。拆分的原则：按"谁负责+改哪个文件"切分，一条条目对应一个可回滚单元。

### 6.7 反例：WHY 缺失与遗留留空

```markdown
- **[2026-09-22 09:00 (+08:00)] [工程-端侧] [常驻]**
  - 改了什么：修改 Index.ets 轮询间隔。
  - 为什么：优化。
  - 遗留什么：
```

三处违规：依据缺失（为何改间隔？改到多少？影响什么？）、遗留留空、无标签。正确写法应写明动机与依据，遗留写明新间隔对数据实时性与耗电的影响。

## 七、写入前自查清单

1. 五要素是否齐全？无遗留时是否显式写了"无遗留"？
2. WHAT 是否含可定位的文件路径或对象名？量化信息是否带数字？
3. WHY 是否引用了可核查的依据？
4. 是否一条目只写一件事？
5. 是否夹带 Token/密钥原文？有则立即脱敏重写；
6. 时间戳与阶段标签是否符合第二章格式？
7. 事故/实验/交接类是否带强制标签并引用证据路径？
8. 若是更正条目，是否引用了原条目时间戳？
9. 遗留是否写清了类别（未完成/风险/接手提示）与观察方式？

## 八、与其他技能的衔接

- learning-loop.md 的"结果记录"步骤以本规范条目为载体，条目质量决定闭环质量；
- handover-protocol.md 要求接手者倒序精读最近 20 条，五要素齐全是阅读效率的前提；
- 24h-autonomy.md 的准备期宣告、窗口小结落账与复盘总结，均按本规范追加；
- skill-doc-format.md 的修订登记与版本递增，同样以本规范条目为落账形式。

## 九、常见坏味道与对策

1. 账本分叉：在模块目录另建局部 changelog，时间线断裂。对策：发现即合并回主账本，局部文件改为指向主账本的说明文件；
2. 追溯改写：偷偷修改旧条目，破坏审计可信度。对策：更正一律走追加，git 层面保留历史；
3. 批量打包：把一次提交二十个文件的改动写成一条，事后无法定位单一文件的变更动机。对策：按可回滚单元拆条；
4. 证据悬空：事故条目写"已修复"但无日志或截图路径佐证。对策：事故条目证据路径设为必填，缺路径不收账；
5. 遗留黑洞：条目写完遗留留空，风险无人接。对策：自查清单第 9 条把遗留类别与观察方式作为验收点。
