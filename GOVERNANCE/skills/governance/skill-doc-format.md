# 技能：技能文档编写规范

> 所属：GOVERNANCE/skills/governance/ ｜ 版本：v1.1 ｜ 日期：2026-09-23 ｜ 适用项目：harmony-app（代号铃语，鸿蒙适老化股票异动播报应用）

## 一、目的与适用范围

本规范约束 `GOVERNANCE/skills/` 目录下所有技能文档的编写与修订，包括 governance 子目录现有五个技能（24h-autonomy、changelog-format、skill-doc-format、learning-loop、handover-protocol）本身，也包括未来新增到其他子目录（如 integration）的工程技能。

技能文档的唯一定位：让一个没有本项目对话记忆的席位（新会话代理或人类接手者），凭文档本身就能正确、安全地完成一类任务。达不到这个定位的文字，不是技能，是笔记。笔记写给当时的自己看，技能写给三个月后的陌生人看——这个差别决定了后文所有的格式与质量要求。

## 二、FORMAT_SPEC：结构骨架

### 2.1 八段必备结构

技能文档八个必备段，顺序固定：

1. 标题与元信息：技能名、所属目录、版本号、日期、适用项目；
2. 定位与适用场景：解决什么问题、何时用，并明确何时不适用——"何时不适用"与"何时用"同等重要，缺了它读者会把方法用到边界之外；
3. 前置条件：执行前必须存在的文件、状态、权限，含不可逾越约束的核对——适老化 28-34fp 大字白话卡片流、禁 K 线图等复杂图表、三条内容红线（承诺收益/保本、催促性指令、对外公开/收费）、Stage 模型 compatibleSdkVersion 20 / targetSdk 26 纯 ArkTS 零三方依赖、不推翻架构基调；
4. 方法主体：按步骤或维度分节展开，配表格、清单或代码示例；
5. 与工程的对接：引用真实文件路径说明方法如何落到本项目（如 EntryAbility.ets 的 Push 初始化与 onNewWant 带 alertId 拉起定位、Index.ets 的 List 卡片流与 5 秒前台轮询 AlertPoller 兜底、AudioPlayer 的 AVPlayer 播云端 TTS 音频流、PushService.ets 占位封装降级轮询、AlertFeed 数据契约）；
6. 边界与红线：本技能不能做什么、出现什么情形必须停手；
7. 操作清单：可打勾的速查步骤；
8. 自我评估：正确性/完整性/可复用性三维 1-5 分，各附一句话简述，再写字数与使用模型声明。

顺序固定的理由：读者按"是什么→何时用→前提→怎么做→落到哪→何处停→速查→可信度"的认知顺序扫描文档，顺序即导航。把操作清单放在最前面看似体贴，实际上读者在没有理解边界之前照着清单动手，恰恰是最容易越线的路径。

### 2.2 命名规范

文件名与目录名一律小写英文加短横线（kebab-case），命名取主题名词或动宾短语，不取日期与序号——日期属于元信息，序号属于索引，混进文件名会让重命名变成全库链接更新。合规示例即本目录五文件：`24h-autonomy.md`、`changelog-format.md`、`skill-doc-format.md`、`learning-loop.md`、`handover-protocol.md`。一个主题一个文件；主题过大时拆子主题文件并在索引中建立关联，而不是写一篇超长文档。

### 2.3 版本规则

版本号置于元信息行，格式 `v主.小`。递增判定：

| 变更类型 | 版本动作 | 账本动作 |
|---|---|---|
| 错别字、排版修正 | 不递增 | 不记账 |
| 增删小节、补充示例 | 小版本 +0.1 | 追加 CHANGELOG 条目 |
| 结论推翻、结构重排、门槛变更 | 大版本 +1.0 | 追加 CHANGELOG 条目并在条目注明推翻内容 |

版本变更必须与 CHANGELOG 联动：账本条目里写旧版本号与新版本号，读者从账本能看出"这份文档经历过什么"。只改版本不记账，等于版本号失去审计意义。

### 2.4 呈现形式选择

方法主体中，表格、清单、代码块三种形式各有其位，选错形式会同时伤害可读与可执行：表格用于"多维度并列比较"（指标与口径、场景与裁剪），行内信息天然对齐，读者扫一眼就能定位差异；清单用于"顺序执行的动作"（准备期五项、收尾五动作），可打勾可核对；代码块用于"需要原样复制的产物"（条目模板、目录结构、配置样例），保证复制粘贴不引入手误。判断标准只有一条：这段内容将来是被"读"、被"做"还是被"抄"——被读的用散文说理，被做的用清单，被抄的用代码块。散文段落承担说理职责，解释为什么这样设计、边界在哪里，这些内容塞进表格会丢失逻辑连贯性；但全部用散文又会让执行要点淹没在段落里。常规配比是：说理散文不超过四成，表格清单代码合计不低于六成；一篇通篇散文的技能是论文，通篇表格的技能是谜语。示例的选择同样有讲究：优先取自本项目真实事件（如数据源降级条目、演示卡兜底场景），虚构示例必须标注"假想"，否则读者会把假想当现状引用——本库技能文档中的正例几乎全部取材真实事件，就是为了避免这种污染。

## 三、质量门槛（五条硬门槛）

### 3.1 自包含

不出现"如前所述""如上次所说""群里那个问题"等依赖对话记忆的指代。一切背景要么写进文档，要么以文件路径引用；被引用文件必须真实存在，尚未建立的标注"规划中"。自包含不等于事无巨细——把另一份文档的内容复制过来会造成两处维护、一处遗忘，正确做法是路径引用加一句话概括被引内容的要点，读者按需跳转。

### 3.2 正确

与工程现状一致。现状快照（截至 2026-09-23）：数据源 Tushare token 失效（40101）已降级东财 API；百炼 TTS 仅支持 WebSocket；broadcast-a2a 的推送需换华为 Push Kit REST；PushService.ets 保持占位封装，AGC 未配置前降级轮询；alerts.json 的 audioUrl 可能为 undefined，端侧按需调 generate-tts；FEED_URL 待 X 服务器落地，契约即 AlertFeed。技能内容与事实冲突时，以事实为准并立即修订文档、递增版本号。凡引用代码行为，必须核对当前源码后落笔，凭印象写下的路径与行为是技能失效的头号来源。

### 3.3 可执行

步骤具体到"打开哪个文件、跑哪条命令、看哪个字段、按什么格式落账"。拒绝"酌情处理""视情况而定"这类把决策推回读者的写法；确需判断的地方，必须给出判断标准——例如 24h-autonomy.md 的安全阀清单，把"什么时候必须停"写成六条可对照的编号条款，这就是可执行的判断标准；反之"异常严重时中止"就是不可执行的模糊表述。

### 3.4 合规

不泄露任何 Token/密钥，示例一律用 `<TOKEN>` 占位；不推翻架构基调；不把三条内容红线的违规表述当作"示例文案"写进文档（需要展示违规样例时，只描述类别特征，不写出完整违规句）；涉及合规判断的场景必须写明停手条件。

### 3.5 可持久化

Markdown 落盘于指定路径；正文汉字数不低于设定目标的 85%（本库技能文档常规目标 3000 字，即正文 ≥2550 汉字，统计口径为 CJK 表意文字、不含文末自评）；文末自评三维齐全且各附简述。字数门槛的意图不是凑字数，而是逼作者把方法展开到可执行粒度——两三百字的步骤列表几乎必然省略了前提、边界与例外。

## 四、可复用性验证：冷启动测试

定稿前必须通过一次冷启动测试，流程五步：

1. 开一个无本项目上下文的新会话，只给它技能文档路径与工程仓库路径；
2. 要求按文档完成该任务的最小闭环；
3. 观察三点：卡在哪里（文档缺信息）、错在哪里（文档误导）、多做了什么（文档冗余）；
4. 卡点与错点回灌修订文档；
5. 连续两次冷启动无卡点即可定稿。

测试结果落盘记录，模板：

```markdown
## 冷启动测试记录
- 日期：YYYY-MM-DD ｜ 测试者：席位名 ｜ 文档版本：vX.Y
- 卡点：第N节"……"处，读者问"……"，文档未答 → 已补第N节
- 错点：读者把X理解为Y → 已改写为明确表述
- 冗余：第M节被读者跳过 → 删除/合并
- 结论：第2次测试无卡点，定稿 v1.0
```

需要澄清三个常见误读：冷启动测试不是功能测试，测的是文档的可理解性，任务失败先查文档是否讲清，再查工程本身；"连续两次无卡点"指两次独立的新会话，同一会话内重试不算数；测试者必须是没有本项目上下文的新会话，作者本人模拟冷启动无效——作者无法假装不知道自己已经知道的东西。

无法执行冷启动时的替代验证：作者逐段自问"这一段的每个名词，读者能否仅凭本文档或被引用文件知道含义？"答不出的名词要么就地解释，要么给出可读的文件路径。自评"可复用性"打 5 分的前提是完成上述验证之一；两种验证都没做，该项最高打 3 分并注明未验证。

## 五、编写流程（六步）

1. 素材采集：从 CHANGELOG、incident 记录、learning-loop.md 第三步产出的"模式"中取材；
2. 沉淀价值判断：同类事件 ≥2 次，或单次影响足够大（触红线、阻断交付）才写技能；一次性小问题进 KNOWN-ISSUES.md 即可，防止技能库信噪比被稀释；
3. 按第二章骨架起草；
4. 过第三章五门槛与第七章自查清单；
5. 冷启动测试或替代验证；
6. 定稿落盘 + 追加 CHANGELOG 条目 + 登记进技能索引 `GOVERNANCE/skills/README.md`。

技能索引登记格式：

```markdown
| 技能 | 路径 | 用途 | 版本 |
|---|---|---|---|
| 24h自治实验 | skills/governance/24h-autonomy.md | 无人值守实验的设计与评估 | v1.1 |
```

索引与文件版本必须同步：文档递增版本而索引未更新，是索引腐化的起点，自查清单第 12 项专门盯这一点。

## 七、自查清单（12 项）

1. 新会话只读本文档能否完全理解，无需任何聊天记录？
2. 每个引用路径是否真实存在，或明确标注"规划中"？
3. 步骤是否可打勾执行、判断点是否给了标准？
4. 是否与 3.2 节现状快照冲突？
5. 是否有表格、清单或代码示例？示例能否在本项目语境下直接对读？
6. 是否泄露任何凭据？
7. 是否出现三条红线的违规示例文案？
8. 边界段是否写明"何时必须停"？
9. 自评三维是否各附简述并指向文中具体事实？
10. 正文汉字数是否 ≥2550（按 3000 字目标）？
11. 是否已追加 CHANGELOG 条目且含版本号变化？
12. 是否已登记进 `GOVERNANCE/skills/README.md` 且版本同步？

## 八、自评写法对照

坏：`正确性：5分`——裸分数，无简述，无法审计。

好：`正确性：4分 第5节引用的 PushService.ets 占位降级逻辑与现状一致；但未覆盖 onNewWant 带 alertId 拉起定位的极端场景，已列为遗留。`——分数与文中事实挂钩，扣分点明确，读者可复核。

自评注水（三维全 5 分却给不出指向文档内容的简述）视为未完成自评，须重写。可复用性维度另有一条硬约束：未做第四章任一验证方式的，最高 3 分并注明"未验证"。

## 九、修订与退役

修订触发信号有三种：工程现状变化（如 Push Kit REST 落地后，引用占位封装的描述过时）、复用反馈失效（learning-loop.md 第五步记录到技能误导）、规范自身升级（本规范大版本变更后，存量文档需对齐）。修订动作：改内容、递增版本、记账、同步索引，四步缺一不可。

退役条件：连续两个复盘周期命中率为零，且方法所针对的场景已被架构变更消灭。退役动作不删文件——文件头部加注"已退役，仅存档"，索引移入退役区，CHANGELOG 记录退役原因。删除会让历史引用悬空，存档让好奇心有处可去。

## 十、反模式与对策

1. 百科式写作：大段搬运领域通识，工程对接只字不提。对策：每节自问"这在铃语项目里对应哪个文件"；
2. 邮票式文档：全文两三百字步骤列表，无前置条件、无边界、无自评。对策：字数门槛倒逼展开；
3. 路径悬空：引用不存在的文件且未标注"规划中"。对策：自查第 2 项逐路径核对；
4. 红线复述癖：把通用合规红线抄一遍充当边界段，不写本技能特有的停手条件。对策：边界段必须含至少一条本技能专属的停手条款；
5. 单点成文：一次偶发事件立刻写成技能，稀释信噪比。对策：走 learning-loop.md 的 ≥2 次聚簇判定；
6. 僵尸文档：写完从不修订，工程演化后与现状脱节仍被引用。对策：冷启动验证纳入交接协议接手方首周动作；
7. 术语裸奔：直接使用项目黑话与缩写而不解释，新读者每个词都要追问一遍。对策：术语首次出现处一句话定义，或给出可读的文件路径；
8. 形式误用：把需要执行的动作写成散文段落，读者提取步骤全靠猜。对策：按 2.4 节"读/做/抄"三分法重排呈现形式。
