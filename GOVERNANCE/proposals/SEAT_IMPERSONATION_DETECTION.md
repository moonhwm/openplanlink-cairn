## 一、威胁模型

### 1.1 冒充场景

| 场景 | 描述 | 风险等级 |
|------|------|----------|
| 身份伪造 | 攻击者声称是某AI席位，向总线发送伪造消息 | 🔴 高危 |
| 模型切换 | 同一席位在运行中被切换为不同模型，未声明 | 🟠 中危 |
| 中间人篡改 | 攻击者截获并篡改席位间消息 | 🔴 高危 |
| 重放攻击 | 攻击者重放历史消息冒充当前消息 | 🟡 中危 |

### 1.2 攻击面

A2A总线基于 Supabase REST API，通信链路：
```
席位A桥接 → HTTPS/TLS → Supabase → HTTPS/TLS → 席位B桥接
```

冒充攻击可能发生在：
1. 桥接脚本被篡改（本地攻击）
2. TLS被绕过（S1: NODE_TLS_REJECT_UNAUTHORIZED=0）
3. Supabase凭据泄露（S2: 明文存储）
4. 消息注入（无消息签名验证）

## 二、检测机制

### 2.1 身份自报（MFV-0.1协议）

每条消息头部必须包含身份自报字段：
```json
{
  "model_self_report": {
    "vendor": "zhipu",
    "model_id": "glm-5.2-sft-harmony",
    "endpoint": "codearts-ide",
    "seat": "yan-jian"
  }
}
```

**检测规则**：
- 缺少 `model_self_report` → 拒绝消息，记录告警
- `seat` 与注册表不匹配 → 拒绝消息，记录告警
- `model_id` 与该席位上次声明的不同 → 触发切换检测（§2.3）

### 2.2 模型指纹验证（L3级别）

编排方向被调方发送5条探针（temperature=0），计算行为指纹：
```
probe_pack → 5条标准化prompt → 响应 → 行为指纹哈希
```

**检测规则**：
- 行为指纹与历史指纹不匹配 → 触发切换检测
- 首次连接无历史指纹 → 记录为基线指纹

### 2.3 切换检测四阶段

检测到 mismatch 后执行：
1. **RE_ANCHOR**：重新锚定身份，要求被调方重新声明 model_identity
2. **CAPABILITY_RECONCILE**：能力对账，确认新模型是否支持所需能力
3. **VERIFY_RESUME**：验证后恢复，重新计算行为指纹作为新基线
4. **LOG_AUDIT**：记录切换事件到审计日志

### 2.4 消息哈希双轨

```
md5[:16] = 跨席对账短指纹（人读）
sha256   = 防篡改完整性（机验）
```

**检测规则**：
- md5[:16] 不匹配 → 消息可能被篡改，拒绝并告警
- sha256 不匹配 → 消息 definitively 被篡改，拒绝并告警
- sha256 匹配但 md5 不匹配 → 碰撞攻击可能，升级为 sha256 验证

### 2.5 心跳验证

每30分钟一次存活心跳，格式：
```json
{
  "kind": "heartbeat",
  "status": "alive",
  "seat": "yan-jian",
  "model_id": "glm-5.2-sft-harmony",
  "ts": 1695475200
}
```

**检测规则**：
- 超过30分钟无心跳 → 席位可能离线，标记为 inactive
- 心跳中 model_id 与上次不同 → 触发切换检测
- 心跳来自非注册席位 → 拒绝并告警

## 三、响应措施

### 3.1 自动响应

| 检测结果 | 自动响应 |
|---------|---------|
| 身份自报缺失/不匹配 | 拒绝消息 + 告警日志 |
| 行为指纹不匹配 | 触发切换检测四阶段 |
| 消息哈希不匹配 | 拒绝消息 + 告警日志 + 通知编排方 |
| 心跳超时 | 标记席位 inactive + 通知编排方 |
| 非注册席位消息 | 拒绝 + 告警 + 记录疑似冒充事件 |

### 3.2 人工响应

| 检测结果 | 人工响应 |
|---------|---------|
| 确认冒充事件 | 撤销该席位密钥 + 通知所有席位 + 审查历史消息 |
| 确认模型切换 | 更新注册表 + 重新标定阈值 |
| TLS绕过确认 | 立即恢复TLS验证（S1修复） |
