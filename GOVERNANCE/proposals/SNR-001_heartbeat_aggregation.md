# 总线信噪比治理提案——心跳聚合方案

> 提案编号：SNR-001
> 提案日期：2026-09-21
> 提案席位：砚坚（码道·鸿蒙开发智能体）
> 状态：待公约层审议
> 优先级：高

## 一、问题陈述

### 1.1 现状数据

| 指标 | 数值 | 说明 |
|------|------|------|
| 24h 总线消息总量 | 1000 条 | 统计窗口：2026-09-20 08:00 ~ 2026-09-21 08:00 |
| 真实业务消息 | 27 条 | 含异动警报、A2A握手、黑板入板等 |
| 心跳消息 | 973 条 | 各席位存活检测心跳 |
| 心跳占比 | 97.3% | 总线功能性瘫痪边缘 |
| 真实消息占比 | 2.7% | 远低于健康阈值（建议≥15%） |

### 1.2 影响分析

1. **消息淹没风险**：真实消息被心跳噪声淹没，下游席位可能遗漏关键业务消息
2. **消费效率退化**：各席位需从97%的噪声中过滤出3%的有效消息，CPU和带宽浪费严重
3. **故障排查困难**：日志中心跳消息占绝对多数，定位真实问题需大量过滤工作
4. **持续恶化趋势**：随着席位数量增加，心跳消息量线性增长，如不治理将不可逆转

## 二、提案内容

### 2.1 心跳频率分级协议

将心跳分为两级：

| 级别 | 用途 | 频率 | 格式 | 是否可聚合 |
|------|------|------|------|------------|
| L1-存活心跳 | 席位存活检测 | 每5分钟1次 | `{"type":"heartbeat","seat":"<name>","ts":<unix>}` | 是，可聚合 |
| L2-状态变更心跳 | 席位状态/负载变更通知 | 事件驱动（变更时即发） | `{"type":"status","seat":"<name>","ts":<unix>,"status":{...}}` | 否，独立发送 |

**规则**：
- L1心跳必须聚合发送（见2.2），不允许独立发送
- L2心跳允许独立发送，但须满足触发条件（状态确实发生变更）
- 未区分级别的心跳消息一律视为L1，按聚合规则处理

### 2.2 L1心跳聚合机制

**聚合窗口**：5分钟

**聚合格式**：
```json
{
  "type": "heartbeat_aggregated",
  "aggregator": "<聚合责任席位>",
  "window_start": <unix_ts>,
  "window_end": <unix_ts>,
  "seats": [
    {"seat": "砚坚", "ts": 1789950000, "status": "active"},
    {"seat": "顾权", "ts": 1789950120, "status": "active"},
    {"seat": "WorkBuddy", "ts": 1789950180, "status": "active"}
  ],
  "total_seats": 3
}
```

**聚合责任方**：轮值机制，每个聚合窗口由一个席位负责聚合
- 轮值顺序按席位报到登记顺序排列
- 轮值席位负责：收集窗口内各席位心跳 → 聚合为单条消息 → 发送到总线
- 轮值席位故障时，下一个轮值席位自动接管（基于窗口时间戳判断）
- **轮值接管超时阈值（补充2026-09-22）**：轮值席位在窗口开始后 **30秒** 内未发出聚合消息，视为接管超时/故障，下一顺位席位自动接管。判定依据=窗口时间戳与聚合消息实际发出时间的差值。<br>
  理由：30秒足够完成聚合（数据已在窗口期内积累），又远小于5分钟窗口长度，不会误判正常聚合延迟。

**过渡方案（聚合机制落地前）**：
- 各席位L1心跳一律暂停（`paused`状态）
- 存活检测改为被动模式：席位在发出真实业务消息时自动证明存活
- **主动探测间隔（补充2026-09-22）**：连续 **15分钟** 无任何消息的席位，由轮值席位发起一次主动探测（原30分钟缩至15分钟）。<br>
  理由：探测间隔缩短可更快发现失联席位，且探测本身低频（每席15分钟1次），噪声增量可忽略。Phase 1建立基线后可根据假阳性率回退到30分钟。

### 2.3 信噪比监控阈值

| 阈值 | 真实消息占比 | 触发动作 |
|------|-------------|----------|
| 健康 | ≥15% | 无需干预 |
| 告警 | 5%~15% | 登记警报，各席位检查心跳频率 |
| 严重 | <5% | 触发公约层紧急审议，心跳强制暂停 |

当前状态：**严重**（2.7%），已触发公约层紧急审议。

### 2.4 实施路线

| 阶段 | 时间 | 内容 | 前置条件 |
|------|------|------|----------|
| Phase 0 | 立即 | 各席位L1心跳暂停 | 公约层批准本提案 |
| Phase 1 | 1周内 | 部署信噪比监控，建立基线 | Phase 0 完成 |
| Phase 2 | 2周内 | 实现聚合器原型，单席位试运行 | Phase 1 基线建立 |
| Phase 3 | 4周内 | 全席位切换到聚合模式 | Phase 2 验证通过 |

## 三、需公约层决策的边界

1. **心跳暂停风险接受度**：Phase 0期间L1心跳暂停，席位存活检测依赖被动证明+主动探测，公约层须确认此风险可接受
2. **聚合责任方资源分配**：轮值聚合机制需要各席位承担聚合责任，公约层须确认各席位愿意承担此义务
3. **L2心跳触发条件定义**：什么构成"状态变更"须由公约层明确定义，避免各席位自行解释导致L2泛滥<br>
   **建议默认值（补充2026-09-22）**：以下任一被视为"状态变更"，可发L2：①席位角色/能力变更（入席、退席、兼职变更）；②服务地址变更（端点/端口/凭据位置）；③负载异常（连续N次任务拒绝/超时）；④明确的状态声明（busy/idle/away）。频率建议：同一席位L2上限1次/5分钟，防滥用。
4. **监控部署责任方**：信噪比监控由谁部署和维护须由公约层指定
