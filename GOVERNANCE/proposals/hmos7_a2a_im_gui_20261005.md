- 定性: 架构设计件——基于华为生态与HarmonyOS 7的A2A IM GUI网络
- 参考: Star-Office-UI（像素风AI办公看板）、SkillOpt（自进化技能优化）

## 一、设计目标

构建基于华为生态与HarmonyOS 7的Agent to Agent（A2A）内部可核验、具备GUI交互界面的即时通讯（IM）网络，使每个代理的行为轨迹与决策依据均可被实时检视与审计，从而在多方协作场景下形成可追溯的信任闭环。

## 三、核心组件设计

### 3.1 ArkUI前端（看板界面）

**参考**: Star-Office-UI的像素风看板，改为ArkUI原生实现

**状态映射**（6种状态+2种扩展）：
| 状态 | 说明 | 颜色 | 图标 |
|---|---|---|---|
| idle | 待命中 | 灰色 | 月亮 |
| writing | 写作/编码 | 蓝色 | 笔 |
| researching | 研究/分析 | 紫色 | 放大镜 |
| executing | 执行/构建 | 橙色 | 齿轮 |
| syncing | 同步/推送 | 绿色 | 循环箭头 |
| error | 错误/异常 | 红色 | 警告 |
| negotiating | 协商中 | 金色 | 天平（扩展） |
| auditing | 审计中 | 青色 | 盾牌（扩展） |

**界面布局**：
- **主视图**: 各席位的像素角色在虚拟办公室中移动，状态变化时角色走到对应区域
- **侧边栏**: 席位列表 + 状态详情 + 行为轨迹
- **底部**: 审计日志流（实时滚动）
- **顶部**: 网络拓扑图（各席位连接关系）

### 3.2 A2A IM引擎（状态路由）

**职责**: 接收各席位的状态推送，路由到对应的UI更新

**状态推送协议**:
```json
{
  "seat_id": "席位标识",
  "status": "idle|writing|researching|executing|syncing|error|negotiating|auditing",
  "message": "状态描述（白话）",
  "timestamp": "ISO 8601",
  "signature": "HMAC-SHA3-512签名",
  "evidence": "决策依据（文件路径/日志条目）"
}
```

**路由规则**:
- 状态推送 → 验证签名 → 更新UI角色位置 → 记录审计日志 → 推送哈希链
- 签名验证失败 → 拒绝状态更新 → 记录安全日志 → 触发告警

### 3.3 审计日志（行为轨迹）

**日志格式**:
```json
{
  "log_id": "自增ID",
  "timestamp": "ISO 8601",
  "seat_id": "席位标识",
  "action": "状态变更|消息发送|决策执行|文件修改",
  "details": "详细描述",
  "evidence_ref": "证据引用（文件路径+行号）",
  "prev_hash": "前一条日志的SHA3-512[:16]",
  "current_hash": "本条日志的SHA3-512[:16]"
}
```

**哈希链连续性**: 每条日志的current_hash = SHA3-512(prev_hash + log_content)[:16]，确保日志不可篡改

### 3.4 HMAC签名验证器

**验证流程**:
1. 接收状态推送消息
2. 提取signature字段
3. 使用席位对应的公钥验证HMAC-SHA3-512签名
4. 验证通过 → 路由到UI更新
5. 验证失败 → 拒绝 + 安全日志 + 告警

### 3.5 状态推送接收器

**接收方式**: 
- 幻16 A2A端点: HTTP POST http://120.46.86.165/functions/v1/app
- 硅基流动API: 作为备用通道
- 本地轮询: 5秒间隔的前台轮询兜底（与现有AlertPoller一致）

## 七、安全约束

1. 所有状态推送须附带HMAC-SHA3-512签名
2. 审计日志的哈希链须连续不可篡改
3. 决策依据须可追溯（文件路径+行号）
4. 任何席位的删除操作须经主权人审批
5. 敏感信息（API密钥等）不落盘不入档，只存环境变量
