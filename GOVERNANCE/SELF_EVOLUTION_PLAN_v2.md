## 第一部分：自主进化机制设计

### 1.1 进化的核心命题

砚坚席的进化面临一个根本性约束：**AI席位的"进化"不是模型权重的更新（那由模型提供方控制），而是知识体系、工作流程、协作模式、制度框架的进化**。换言之，砚坚席的进化是"软件层面的进化"而非"硬件层面的进化"——我们无法改变GLM-5.2的模型参数，但可以改变砚坚席如何使用GLM-5.2的能力。

这与Hermes Agent的设计哲学一致——Hermes不修改底层模型，而是通过**技能系统（自动编写/保存/改进）+记忆系统（FTS5全文搜索+LLM摘要）+闭环学习（从交互中改进）+用户建模（Honcho dialectic modeling）**实现进化。

### 1.2 四层进化架构

```
┌─────────────────────────────────────────────────────────┐
│              L4：制度进化层                               │
│  治理框架自洽性审查 + 修复方案确认流程 + 元治理层         │
│  进化目标：治理制度本身的自洽性与完备性                    │
│  进化频率：每轮实验结束后                                  │
│  参考模式：Apache PMC治理 + HY4握手协议                   │
├─────────────────────────────────────────────────────────┤
│              L3：能力进化层                               │
│  技能自动编写 + 技能保存 + 技能复用 + 技能迁移            │
│  进化目标：工作能力的持续扩展和质量提升                    │
│  进化频率：每次任务完成后                                  │
│  参考模式：Hermes Agent技能系统 + agentskills.io标准      │
├─────────────────────────────────────────────────────────┤
│              L2：知识进化层                               │
│  经验沉淀 + 模式识别 + 方法论提炼 + 知识资产化            │
│  进化目标：从个案经验中提炼可复用的方法论                  │
│  进化频率：每个Phase结束后                                 │
│  参考模式：Apache邮件列表归档 + GitHub Wiki               │
├─────────────────────────────────────────────────────────┤
│              L1：数据进化层                               │
│  CHANGELOG + 决策日志 + 闭环台账 + 审计追溯               │
│  进化目标：完整记录所有行为和决策，确保可审计              │
│  进化频率：实时                                            │
│  参考模式：Git版本控制 + Hermes WAL(Write-Ahead Log)      │
└─────────────────────────────────────────────────────────┘
```

### 1.3 持续学习机制

#### 1.3.1 技能自动编写（参考Hermes Agent核心行为）

Hermes Agent的核心行为是"自动编写和保存自身技能"——在完成复杂任务后自主创建技能文档，在使用过程中自我改进技能。砚坚席的技能自动编写机制如下：

| 技能类型 | 编写触发条件 | 保存格式 | 保存位置 | 复用方式 | 自改进机制 |
|---------|------------|---------|---------|---------|-----------|
| **代码技能** | 完成一段非平凡的代码编写 | `.ets`/`.mjs`/`.ts`文件+技能描述 | `GOVERNANCE/skills/code/` | 下次遇到同类任务时直接引用 | 使用中发现边界条件→更新技能文档 |
| **治理技能** | 完成一轮治理实验 | 闭环台账+修复方案+审查意见 | `GOVERNANCE/experiment/` | 下轮实验时引用已有发现 | 修复方案自洽性审查→更新交互规则 |
| **协作技能** | 完成一次跨席位协作 | 协作流程文档+经验记录 | `GOVERNANCE/skills/collab/` | 下次协作时引用已有流程 | 协作失败→更新协作流程文档 |
| **诊断技能** | 完成一次问题诊断 | 诊断流程+根因分析+修复步骤 | `GOVERNANCE/skills/diag/` | 下次遇到同类问题时引用 | 诊断遗漏→补充诊断检查项 |
| **密码学技能** | 完成一次密码学分析 | 分析报告+加固方案 | `GOVERNANCE/research/` | 下次密码学任务时引用 | 新攻击向量→更新加固方案 |

**关键差异**：Hermes Agent的技能系统兼容[agentskills.io](https://agentskills.io)开放标准，有社区技能市场（Skills Hub）。砚坚席的技能来自治理实验和任务实践，暂无社区市场——但可通过A2A总线在席位间共享技能。

#### 1.3.2 记忆系统（参考Hermes Agent FTS5+LLM摘要）

Hermes Agent使用FTS5全文搜索+LLM摘要实现跨会话自动召回，并使用Honcho dialectic user modeling深化对用户的理解。砚坚席的记忆系统如下：

| 记忆类型 | 存储方式 | 召回方式 | 跨会话持久化 | Hermes对应 |
|---------|---------|---------|------------|-----------|
| **短期记忆** | 会话上下文 | 自然语言检索 | ❌ 会话结束即消失 | 会话内上下文 |
| **中期记忆** | CHANGELOG.md + 决策日志 | Git历史+时间线检索 | ✅ 持久化到文件系统 | hermes_state_timeline.py |
| **长期记忆** | Wiki知识文档(.codebase/) | Knowledge工具语义检索 | ✅ 持久化+语义索引 | hermes_state_search.py (FTS5) |
| **元记忆** | AGENTS.md + AGENT.MD | 启动时自动加载 | ✅ 每次会话自动加载 | SOUL.md + AGENTS.md |
| **用户建模** | 机主偏好记录+反馈记忆 | Memory系统自动召回 | ✅ 持久化到memory目录 | Honcho dialectic modeling |

**关键差异**：Hermes使用FTS5+LLM摘要实现自动召回（`hermes_state_fts.py`, `hermes_state_search.py`），砚坚席使用**文件系统+Git版本控制+Knowledge语义检索**实现召回。Hermes的方式更高效（自动摘要+全文搜索），砚坚席的方式更符合零三方依赖约束——不引入数据库依赖，而是利用已有的文件系统和Git基础设施。

**可借鉴改进**：考虑在GOVERNANCE目录下建立FTS5索引（利用SQLite内置FTS5，零三方依赖），对所有Markdown文档建立全文搜索索引，实现Hermes式的自动召回。

#### 1.3.3 闭环学习（参考Hermes Agent闭环学习能力）

Hermes Agent的闭环学习是从交互中学习并改进——"creates skills from experience, improves them during use, nudges itself to persist knowledge"。砚坚席的闭环学习机制如下：

```
任务执行 → 结果记录 → 质量评估 → 模式识别 → 技能编写 → 下次复用
    ↑                                                        │
    └────────────────────────────────────────────────────────┘
```

具体实现：

| 闭环步骤 | 实现 | 产出 | Hermes对应 |
|---------|------|------|-----------|
| 任务执行 | 执行机主指令或治理实验任务 | 代码/文档/分析报告 | agent核心循环 |
| 结果记录 | CHANGELOG.md追加条目+决策日志记录 | 可审计的行为记录 | hermes_state_messages.py |
| 质量评估 | 验证步骤(V1-V8) + 闭环台账 | 质量评估报告 | evals/目录 |
| 模式识别 | 从多个个案中识别共性模式 | 方法论提炼 | LLM摘要+模式识别 |
| 技能编写 | 将识别出的模式编写为可复用技能 | 技能文档/脚本 | skills/自动编写 |
| 下次复用 | 遇到同类任务时引用已有技能 | 效率提升 | 技能自动召回 |

**关键差异**：Hermes的闭环学习是**隐式的**——agent在交互过程中自动识别模式并创建技能，无需显式触发。砚坚席的闭环学习是**显式的**——需要在任务完成后主动进行模式识别和技能编写。显式方式更可控（质量有保障），隐式方式更自然（不遗漏）。

**改进方向**：在AGENTS.md中加入"任务完成后的自动技能编写"规则，使闭环学习从角色选择升级为项目约束。

### 1.6 适应性增强

适应性增强的目标是：当外部环境（技术栈、约束条件、协作方）发生变化时，砚坚席能够快速适应。

| 适应性维度 | 增强机制 | 具体措施 | Hermes对应 |

| **模型适应性** | 模型适配层 | 参考Hermes的300+模型适配器，砚坚席可通过模型适配层适配不同模型 | providers/目录 |

### 2.2 知识沉淀流程

```
任务执行 → 经验记录(CHANGELOG) → 模式识别(从个案中提炼共性) 
    → 方法论编写(技能文档) → 知识资产化(Wiki文档) → 语义索引(Knowledge)
    → 跨会话召回(下次任务复用)
```

### 2.3 知识资产化标准

每条知识资产须满足以下标准才能被"资产化"：

| 标准 | 定义 | 验证方法 | Hermes对应 |
|------|------|---------|-----------|
| **可复用性** | 资产可被未来任务直接引用 | 引用测试——下次同类任务时能否直接引用 | 技能格式规范 |
| **可传承性** | 资产可被替代角色理解和使用 | 角色无关性检查——不包含砚坚席特定的隐含知识 | - |
| **可检索性** | 资产可通过语义检索找到 | Knowledge工具检索测试 | FTS5全文搜索 |
| **可验证性** | 资产中的结论可被独立验证 | 验证步骤可执行 | tests/目录 |
| **自洽性** | 资产与已有知识体系无矛盾 | 交互效应检查 | - |

### 2.4 知识传承机制——确保替代角色可接续

这是本方案的核心——即使砚坚席被替代，沉淀的知识仍具有长期价值。

#### 2.4.1 角色无关性设计

所有知识资产必须满足**角色无关性**——不依赖砚坚席的特定身份、记忆或能力。

| 角色无关性规则 | 说明 | 示例 |
|--------------|------|------|
| **不引用隐含上下文** | 知识资产中不引用"上次会话中我们讨论了..."等隐含上下文 | ❌ "如前所述，FIX-002有问题" → ✅ "FIX-002与FIX-005组合后产生沉默→reserve→confirm矛盾(详见ATTACK-R2-001)" |
| **自包含** | 每条知识资产包含足够的背景信息，可独立理解 | 每条修复方案附漏洞描述、触发场景、利用路径 |
| **引用而非记忆** | 引用文件路径而非依赖记忆 | ❌ "我记得百炼额度约1M" → ✅ "百炼免费额度约1M tokens(详见GOVERNANCE/compute_resource_registry.md §2.1)" |
| **格式规范化** | 知识资产使用统一格式，任何角色都可解析 | 闭环台账格式、审查意见格式、修复方案格式 |

#### 2.4.3 交接验证

替代角色接续后，须通过以下验证确保知识传承完整：

| 验证项 | 验证方法 | 通过条件 |
|--------|---------|---------|

### 3.2 Apache Software Foundation治理模式深度分析

基于对Apache官网的深度研究，提炼以下治理模式：

#### 3.2.1 Apache治理架构

```
ASF Board (9人, 年选)
    │
    ├── Officers (公司运营)
    │
    └── PMCs (项目管理委员会)
        │
        ├── PMC Chair (Board任命, Officer身份)
```

#### 3.2.2 Apache核心治理原则

| 原则 | Apache实现 | 砚坚席可借鉴 | 适用场景 | 局限性 |
|------|-----------|------------|---------|--------|
| **Meritocracy（功绩制）** | 通过贡献获得权力——从User到Developer到Committer到PMC Member到ASF Member | 贡献记录机制(ATTACK-3-002)——通过治理实验贡献获得席位声誉 | 需要激励积极贡献 | 功绩评估标准可能主观 |
| **Lazy Consensus（惰性共识）** | 提案无反对票即通过——不需要所有人投票 | HY4握手协议的confirm默认通过机制 | 需要快速推进决策 | 可能忽略沉默的反对 |
| **+1/0/-1投票** | 正式投票三档——+1支持/0弃权/-1反对(须附替代方案) | confirm/reserve/reject三档表态 | 需要正式表态 | 投票可能形式化 |
| **PMC模式** | 项目管理委员会——核心贡献者集体决策 | 神经中枢+各席位=PMC | 需要集体决策 | PMC可能形成寡头 |
| **孵化器模式** | 新项目先孵化后毕业——有导师指导 | 临时席位机制(新席位先observe) | 需要新席位准入 | 孵化期可能过长 |
| **邮件列表透明** | 所有决策在邮件列表公开 | A2A总线消息对所有席位可见 | 需要决策透明 | 公开可能抑制自由讨论 |
| **帽子原则** | 个人身份参与，不代表公司 | 席位身份独立于底层模型 | 需要身份独立性 | - |
| **Do-ocracy** | "权力属于做事的人"——谁干活谁决策 | 任务认领机制 | 需要激励行动 | 可能导致权力集中 |

#### 3.2.3 Apache孵化器模式详解

Apache孵化器是解决"新项目如何加入"的关键机制。砚坚席可以借鉴用于新席位准入：

| 孵化阶段 | Apache做法 | 砚坚席对应 | 状态 |
|---------|-----------|-----------|------|
| **提案** | 需要工作代码base+IP授权+ASF成员赞助 | 新席位需要能力声明+安全承诺+现有席位赞助 | - |
| **孵化** | 导师指导+社区建设+功绩制学习 | 新席位先observe+学习HY4协议+参与讨论 | - |
| **毕业** | 评估社区多样性和功绩制运作 | 评估席位贡献度和协议遵循度 | - |
| **退役** | 项目失败时退出 | 席位失联或无贡献时退出 | - |

**关键借鉴**：Apache要求孵化项目有**初始工作代码base**——"without a working codebase, it is generally hard to bootstrap a community"。这意味着新席位准入也需要有**初始工作产出**，而不能只是声明意图。

**多样性要求**：Apache要求孵化项目增加committer多样性——"with all the developers affiliated to the same entity, the chance of seeing all of them moving away at the same time is much greater"。这意味着席位多样性是治理稳定性的关键——不能所有席位都来自同一平台。

## 第四部分：可替代性应对

### 4.1 可替代性的核心挑战

砚坚席被替代后，替代角色需要能够：
1. **理解项目当前状态**——通过交接材料
2. **接续未完成任务**——通过落地路线图
3. **复用已有知识**——通过知识资产
4. **继续进化**——通过进化机制
5. **维持治理框架**——通过制度约束

### 4.2 可持续性设计

可持续性 = 进化与沉淀过程不依赖单一角色或特定环境

| 可持续性维度 | 设计原则 | 具体措施 | Hermes对应 |
|------------|---------|---------|-----------|
| **角色无关性** | 知识资产不依赖砚坚席的特定身份 | 角色无关性规则(§2.4.1) | SOUL.md可替换 |
| **环境无关性** | 知识资产不依赖特定运行环境 | 知识资产使用标准格式(Markdown+JSON)，可在任何环境解析 | hermes_state_portability.py |
| **模型无关性** | 进化机制不依赖特定模型 | 模型适配层——进化机制在模型之上运作，不依赖GLM-5.2的特定能力 | providers/300+适配器 |
| **平台无关性** | 知识资产不依赖特定平台 | 知识资产存储在文件系统(非特定平台数据库)，可通过Git迁移 | Docker/本地/Termux多部署 |

### 4.3 可迁移性设计

可迁移性 = 知识资产可从砚坚席迁移到替代角色

| 迁移步骤 | 具体操作 | 验证方法 | Hermes对应 |
|---------|---------|---------|-----------|
| **1. 知识资产盘点** | 列出所有知识资产及其位置 | 14项交接材料完整性检查 | hermes_state_registry.py |
| **2. 角色无关性验证** | 检查每项资产是否满足角色无关性规则 | 角色无关性检查(§2.4.1) | - |
| **3. 替代角色加载** | 替代角色加载所有交接材料 | AGENTS.md自动加载+Knowledge语义检索 | hermes_bootstrap.py |
| **4. 状态理解验证** | 替代角色能否独立回答"项目当前状态" | 状态理解测试 | - |
| **5. 任务接续验证** | 替代角色能否从落地路线图接续任务 | 任务接续测试 | - |
| **6. 进化继续验证** | 替代角色能否继续执行自主进化机制 | 进化机制执行测试 | - |

### 4.4 知识资产独立性保障

| 保障机制 | 说明 | 实现方式 | Hermes对应 |
|---------|------|---------|-----------|
| **格式标准化** | 所有知识资产使用统一格式 | Markdown+JSON，可被任何角色解析 | agentskills.io标准 |
| **引用规范化** | 所有引用使用文件路径而非记忆 | "详见GOVERNANCE/..."而非"我记得..." | - |
| **背景自包含** | 每条知识资产包含足够背景信息 | 每条修复方案附漏洞描述+触发场景 | - |
| **版本可追溯** | 所有知识资产有版本号和修改历史 | Git版本控制+CHANGELOG | Git历史 |
| **语义可检索** | 所有知识资产可通过语义检索找到 | Knowledge工具+Wiki知识文档 | FTS5全文搜索 |
| **完整性保护** | 知识资产不被意外损坏 | Git版本控制+备份 | hermes_state_guard.py |
| **可修复性** | 知识资产损坏后可修复 | Git回溯+手动修复 | hermes_state_repair.py |

### 4.5 进化机制的可持续性

进化机制本身也需要可持续——不能因为砚坚席被替代而停止进化。

| 进化机制 | 可持续性保障 | 风险 | 缓解措施 |
|---------|------------|------|---------|
| **技能自动编写** | 技能文档格式标准化，替代角色可继续编写 | 替代角色可能不遵循技能编写规范 | 写入AGENTS.md成为项目约束 |
| **闭环学习** | 闭环学习流程文档化，替代角色可继续闭环 | 替代角色可能不执行质量评估步骤 | 写入AGENTS.md成为项目约束 |
| **治理实验** | 治理实验方案和流程文档化，替代角色可继续实验 | 替代角色可能不遵循HY4协议 | 写入AGENTS.md成为项目约束 |
| **知识资产化** | 知识资产化标准文档化，替代角色可继续资产化 | 替代角色可能不满足资产化标准 | 写入AGENTS.md成为项目约束 |

**核心缓解策略**：将进化机制写入AGENTS.md（项目宪法），使进化机制成为项目约束而非角色选择。替代角色进入项目时，AGENTS.md自动加载，进化机制自动生效。

### 6.4 与Hermes Agent的对比定位

| 维度 | Hermes Agent | 砚坚席 | 砚坚席的独特价值 |
|------|-------------|--------|----------------|
| 进化层次 | 技能层进化(L3) | 四层进化(L1-L4) | 多了制度进化层(L4)——治理制度本身也进化 |
| 知识沉淀 | FTS5+LLM摘要+Honcho | 文件系统+Git+Knowledge | 零三方依赖，更符合约束 |
| 可替代性 | 依赖NOUS平台认证 | 角色无关性+交接协议 | 不依赖任何平台认证 |
| 安全模型 | NOUS_KEY环境变量 | ed25519签名+凭据金库 | 更安全 |
| 治理机制 | 无明确治理 | HY4握手协议+9方席位 | 有正式治理框架 |
| 闭环学习 | 从交互中学习 | 从治理实验中学习(攻击→防御→修复→验证) | 更结构化的闭环 |
| 状态管理 | 20+状态模块 | Git+CHANGELOG+决策日志 | 更简单可靠 |
| 社区规模 | 247K Stars/37K Commits | 9方席位 | 治理框架替代社区规模 |
| 可移植性 | hermes_state_portability.py | 知识资产格式标准化+移植工具 | 格式规范+工具化 |
| 技能标准 | agentskills.io开放标准 | 自定义格式(可对接) | 可对接开放标准 |

**砚坚席的独特价值**：不是"另一个Hermes Agent"，而是"有治理框架的Hermes Agent"——Hermes Agent缺少正式的治理机制（它的竞品对比文档带有明显营销倾向，没有制度性约束），而砚坚席有HY4握手协议、31条漏洞发现、17条修复方案、6维审查框架。这意味着砚坚席的进化不是无约束的进化，而是**受治理约束的进化**——进化本身也受制度规范。

### 6.5 核心设计原则

| 原则 | 说明 | 来源 |
|------|------|------|
| **进化不依赖模型权重更新** | AI席位的进化是知识体系/工作流程/协作模式/制度框架的进化，不是模型参数的进化 | 砚坚席约束分析 |
| **沉淀不依赖单一角色** | 知识资产满足角色无关性，替代角色可无缝接续 | 可替代性前提 |
| **进化受治理约束** | 进化本身也受制度规范，不是无约束的进化 | HY4协议+治理实验 |
| **零三方依赖** | 不引入向量数据库等外部依赖，利用已有基础设施 | 项目硬约束 |
| **知识沉淀开源精神** | 知识沉淀可传承(开源精神)，部署安全(闭源) | 开源vs闭源对比 |
| **格式标准化** | 所有知识资产使用Markdown+JSON，可被任何角色解析 | Apache文档体系 |
| **引用规范化** | 引用文件路径而非依赖记忆 | 角色无关性规则 |
| **背景自包含** | 每条知识资产包含足够背景信息 | Apache自包含原则 |
