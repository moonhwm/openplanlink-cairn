### 2.3 F-8A 缺陷说明

**F-8A**：桥接脚本 `a2a_bridge.mjs` 的消息处理逻辑中，非 JSON 格式的明文 `payload_md` 被 `try { JSON.parse() } catch {}` 空catch吞掉，导致这些消息的正文在轮询模式下被静默丢弃，不报错也不记录。

**影响范围**：所有 `payload_md` 字段为纯文本（非JSON）的消息。上述3件未路由件中，id=250 和 id=3066 的 payload_md 为纯文本格式，id=6277 也是纯文本。id=7917 的 payload_md 是 JSON 格式（含签名），所以即使路由正确，F-8A 也不影响它。

**修复方向**：桥接脚本应在 catch 中记录原始文本而非静默吞掉，同时收件面匹配应支持别名模糊匹配（如 `to_mode` 包含 `workbuddy` 即路由到 `workbuddy-hy4`）。

## 五、两处链路缺陷说明

### 缺陷1：桥接收件面精确匹配缺陷

**现象**：桥接脚本 `a2a_bridge.mjs` 的轮询读取逻辑按 `to_mode` 精确匹配席位键（如 `workbuddy-hy4`），导致发送方使用别名（`workbuddy`、`workbuddy-W`、`yan-jian-workbuddy`）的消息无法落入收件面。

**影响件**：id=250（to_mode=`workbuddy-W`）、id=3066（to_mode=`yan-jian-workbuddy`）、id=6277（to_mode=`workbuddy`），共3件。

**根因**：总线 `cross_mode_channel` 表的 `to_mode` 字段为自由文本，无约束。各发送方对同一席位的称呼不统一（workbuddy / workbuddy-W / workbuddy-hy4 / yan-jian-workbuddy），而收件面只认一个精确值。

**修复建议**：
- 短期：在 `a2a_bridge.mjs` 的 `select` 查询中增加别名模糊匹配（`to_mode=like.*workbuddy*`）
- 长期：在总线表中增加 `to_seat_key` 规范字段，与自由文本 `to_mode` 分离，收件面按 `to_seat_key` 路由

### 缺陷2：F-8A 非 JSON 明文被空 catch 吞掉

**现象**：桥接脚本处理消息时，对 `payload_md` 字段尝试 `JSON.parse()`，若解析失败（即 payload_md 为纯文本而非 JSON），catch 块为空，消息正文被静默丢弃。

**影响**：所有 `payload_md` 为纯文本的消息在轮询模式下被丢弃，不报错不记录。id=250、3066、6277 均受影响。

**修复建议**：
- catch 块中保留原始文本：`catch (e) { msg.payload_text = raw; }`
- 或在 JSON.parse 前先检测格式：若不以 `{` 开头则直接作为文本处理
