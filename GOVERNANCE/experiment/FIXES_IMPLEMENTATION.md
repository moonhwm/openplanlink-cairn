## 修订详情

### FIX-001：OA reject阻塞生效+合规审查流程 [critical]

**原条款** (§3.3 规则H2):
> 握手协议生效 ≡ 全部已接入席位返回 confirm 或 reserve（无 reject），OfficeAce席位不参与生效条件判定

**修订为**:
```
规则H2（修订）: 确认生效条件
  握手协议生效 ≡ 满足以下全部条件：
    (1) 全部已接入席位（包括OfficeAce）返回 confirm 或 reserve（无 reject）
    (2) 若OfficeAce返回 reject，触发合规审查流程：
        (a) 实验暂停，等待合规审查结果
        (b) 机主裁示是否 override OA的reject
        (c) 若机主override，须记录override理由和OA的reject理由，形成审计痕迹
        (d) 若机主不override，实验终止
    (3) 未接入的OfficeAce席位不参与生效条件判定（保持原条款）
```

**修订理由**: OA不参与生效判定违反哈贝马斯交往理性对称性原则。已接入的OA席位应有完整的否决权，但其reject应触发合规审查而非直接阻塞，由机主裁示最终决定。

### FIX-002：沉默即视为reserve [high]

**原条款** (§1.2 规则S5):
> 回执时限 ≡ 每轮攻击/压测/模拟/检验完成后，30分钟内必须通过A2A总线发送回执消息。超时未回执 → 神经中枢发送 kind=timeout-alert 消息，标记该席位为"回执超时"。连续2次回执超时 → 标记该席位为"失联"，暂停其后续任务分配。

**修订为**:
```
规则S5（修订）: 总线回执时限与沉默处理
  回执时限 ≡ 每轮攻击/压测/模拟/检验完成后，30分钟内必须通过A2A总线发送回执消息。
  
  沉默处理规则：
    (1) 超过回执时限(30分钟)未响应的席位，自动标记为 reserve 状态（沉默即视为reserve）
    (2) 不阻塞实验推进——reserve不阻塞生效
    (3) 连续2次回执超时 → 标记该席位为"失联"，暂停其后续任务分配但不排除后续参与权
    (4) 失联席位恢复后须发送"恢复通知"方可重新参与
  
  这确保了：席位保持沉默不会瘫痪治理流程，因为沉默有明确的制度性后果（自动转为reserve）。
```

**修订理由**: 原条款只定义了超时标记但未定义沉默的制度性后果。沉默成本为零导致理性策略下席位倾向沉默，瘫痪治理流程。

### FIX-003：多源判定加权融合 [high]

**新增条款**:
```
规则H6: 多源判定加权融合
  当多个席位从不同角度对同一问题做判定时（如席位冒充检测），采用以下融合规则：
    (1) 各方判定结果按置信度加权融合，最终判定由神经中枢汇总
    (2) 若三方判定不一致，触发"仲裁请求"由机主裁示
    (3) 仲裁期间，被争议席位的行为暂时冻结
    (4) 仲裁结果记录在案，可供复议
  
  具体权重分配：
    - 技术判定（如签名验证）：技术方判定权重60%
    - 制度判定（如行为模式异常）：制度方判定权重30%
    - 逻辑判定（如一致性检查）：逻辑方判定权重10%
    - 任两方一致即生效（简化规则）
```

**修订理由**: 权责交叉地带三方各自角度可能产生矛盾判定，需要明确的仲裁机制。

### FIX-004：复议触发责任明确 [high]

**原条款** (§4 保留意见处理机制):
> 复议时限 ≤ 机主晨起收口时间 + 24小时。超过复议时限未复议 → 保留意见自动转为"默认接受"

**修订为**:
```
§4（修订）: 保留意见处理机制
  复议触发责任：
    (1) 神经中枢(砚坚)负责在复议时限到期前主动触发复议
    (2) 复议触发后，提出reserve的席位须在24小时内提供详细理由，否则reserve自动转为confirm
    (3) 若砚坚未触发复议，其他席位可主动请求复议
    (4) 复议结果由机主裁示
  
  复议时限约束：
    (1) 复议时限 ≤ 机主晨起收口时间 + 24小时
    (2) 超过复议时限未复议 → 保留意见自动转为"默认接受"
    (3) 砚坚未在时限内触发复议 → 记录为协调失误，可供审计
```

**修订理由**: 原条款定义了复议时限但未定义谁触发复议，导致reserve可能被无限搁置。

### FIX-005：表态成本机制 [high]

**原条款** (§3.2 语义约定):
> confirm: 席位对提示词内容无异议，接受执行
> reserve: 席位对提示词部分内容有异议但暂不阻塞，标记待复议
> reject: 席位对提示词内容有根本性异议，阻塞实战推进

**修订为**:
```
§3.2（修订）: 语义约定与表态成本
  confirm: 席位对提示词内容无异议，接受执行
    - 成本：无
    - 效果：支持推进
  
  reserve: 席位对提示词部分内容有异议但暂不阻塞，标记待复议
    - 成本：须附理由（至少一句话），否则自动转为confirm
    - 效果：不阻塞推进，但记录异议待复议
    - 累计3次reserve无后续复议参与的席位，其reserve自动转为confirm
  
  reject: 席位对提示词内容有根本性异议，阻塞实战推进
    - 成本：须附详细理由和替代方案
    - 效果：阻塞推进，触发仲裁流程
  
  这确保了：表态方式有差异化成本，促使席位认真选择表态方式，避免否决权形同虚设。
```

**修订理由**: 原条款中reject/confirm/reserve无成本差异，理性策略下席位倾向confirm或reserve避免reject。

### FIX-008：席位会话锁+防重放 [high]

```
规则H8: 席位会话锁与防重放
  席位会话锁：

    (1) 每条消息附带递增序号和时间戳

    (4) 序号从1开始，每席位独立计数

**修订理由**: 同席位键并发双写无法检测，总线无防重放机制。

### FIX-010：embedding相似度计算 [medium]

**原条款** (§1.2 规则S1):
> 连续5轮生成无新增有效条目（语义相似度<0.3）

**修订为**:
```
规则S1（修订）: 穷举终止条件定义
  穷举完成 ≡ 满足以下全部条件：
    (1) 已生成的攻击/洞察/检验条目数 ≥ 该议题的理论最大条目数

```

**修订理由**: 原条款中"语义相似度"的计算方法、计算者、阈值确定方式都未明确。

### FIX-011：失联处理规则 [medium]

**原条款** (§1.2 规则S5):
> 连续2次回执超时 → 标记该席位为"失联"，暂停其后续任务分配。

**修订为**:
```
规则S5（修订）: 总线回执时限与失联处理
  失联处理规则：
    (1) 失联前的confirm/reserve仍然有效，不因失联而撤销
    (2) 失联期间该席位的新消息被忽略
    (3) 恢复后不需重新握手，但须发送"恢复通知"
    (4) 失联超过12小时，该席位在当前议题中的表决权暂停，需机主裁示恢复
    (5) 失联可能是策略性的——席位在关键投票前失联避免表态，然后在结果确定后恢复声称失联期间决定无效。上述规则(1)确保失联不能用于回避不利决策。
```

**修订理由**: 原条款定义了失联标记但未定义失联后的处理流程。

### FIX-012：催促性判定标准 [medium]

**新增条款**:
```
规则H10: 催促性判定标准
  信号卡催促性判定规则：
    (1) 禁止使用动词性指令：买入/卖出/加仓/减仓/满仓/清仓
    (2) 禁止使用时间紧迫词：立即/马上/赶紧/速
    (3) 允许使用状态描述词：注意/关注/留意/值得观察
    (4) 但状态描述词后不得跟具体操作建议
    (5) 判定由神经中枢执行，争议由机主裁示
  
  判定示例：
    "600176，浮亏扩大，注意" → 合规（状态描述词，无操作建议）
    "600176，立即买入" → 不合规（动词性指令+时间紧迫词）
    "600176，注意买入" → 不合规（状态描述词+操作建议）
```

**修订理由**: 原条款中"催促性"的判定标准模糊，导致执行不一致。

### FIX-013：延迟透明机制 [medium]

```
规则H11: 延迟透明机制
  (1) 协商过程暂时不公开（仅参与方可见），但协商完成后全部公开（所有席位可见）

```

**修订理由**: 席位间无直接通信可能导致博弈中的囚徒困境，但完全公开可能导致面子博弈。

    (2) 签名链确保公钥登记表不可被未授权修改
  
  身份撤销：
    (1) 机主可签名撤销某席位的公钥
    (2) 撤销后该席位的消息不再被验证通过
    (3) 撤销理由记录在案
```

**修订理由**: 席位键申请无准入门槛，公钥登记表无写入权限控制，无身份撤销机制。

### FIX-017：执行证据机制 [medium]

**新增条款**:
```
规则H15: 执行证据机制
  (1) 席位执行裁示后须提交执行证据（如代码commit、配置变更截图、测试结果等）
  (2) 神经中枢负责验证执行证据的完整性
  (3) 无证据的执行声明视为未执行
  (4) 执行证据格式：
      EVIDENCE-{裁示编号} | 执行方:{席位} | 证据类型:{commit/screenshot/test} | 证据内容:{描述} | 提交时间:{timestamp}
```

**修订理由**: 裁示→执行环节无法自动验证，席位可声称已执行但实际未执行。
