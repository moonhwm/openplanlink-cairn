## 一、提示词语义学与形式化优化

### 1.1 语义学一致性问题诊断

对现有七方提示词做语义学审查，发现以下问题类别：

| 问题类别 | 具体问题 | 影响席位 | 严重程度 |
|---------|---------|---------|---------|
| **语义歧义** | "穷举"一词未定义终止条件——何时算穷举完成？ | 百炼席、hy4席 | 🟠 中 |
| **语义歧义** | "内部闭环"边界模糊——X实例上的A2A总线算"内部"还是"第三方"？ | X实例席 | 🔴 高 |
| **语义歧义** | "免费额度"与"免费域"概念混用——免费额度指API调用配额，免费域指不触发付费的行为范围 | 百炼席、hy4席、Coze席、K2.8席 | 🟠 中 |
| **逻辑不严密** | 红线第三条"不可逆"未定义什么操作算不可逆——重启服务算不算？ | 全部席位 | 🟠 中 |
| **逻辑不严密** | 输出契约中"总线id回执"未定义回执时限——多久内必须回执？ | 全部席位 | 🟡 低 |
| **形式化缺失** | 提示词中条件判断（如"额度达80%时预警"）缺少形式化判定规则 | 百炼席 | 🟠 中 |
| **形式化缺失** | "攻击—防御—修复"闭环缺少形式化的状态转换图 | 全部席位 | 🔴 高 |

### 1.2 语义优化规则

以下规则适用于全部七方提示词的修订：

#### 规则S1：穷举终止条件定义

```
穷举完成 ≡ 满足以下全部条件：
  (1) 已生成的攻击/洞察/检验条目数 ≥ 该议题的理论最大条目数
  (2) 新生成的条目与已有条目的语义相似度 < 0.3（无实质重复）
  (3) 连续5轮生成无新增有效条目（收敛判据）
若条件(1)无法确定理论最大值，则以条件(2)+(3)为替代判据。
```

#### 规则S2：内部闭环边界精确定义

```
"内部闭环" ≡ 所有测试目标满足以下全部条件：
  (1) 目标系统的物理/逻辑资源所有权属于本实验参与方
  (2) 目标系统的运行不依赖任何第三方服务的可用性
  (3) 测试行为不会导致任何第三方系统产生计费、告警或服务降级
具体判定：
  - X实例(120.46.86.165)上的A2A总线 = 内部（满足全部三条件）
  - Supabase（A2A总线底层存储） = 第三方（不满足条件1）
  - 阿里云百炼API = 第三方（不满足条件1）
  - 本机localhost服务 = 内部（满足全部三条件）
```

#### 规则S3：免费额度与免费域概念分离

```
免费额度(free quota) ≡ API调用配额中不产生费用的部分
  - 百炼席：DashScope 1M tokens免费配额
  - hy4席：WorkBuddy侧免费额度窗口
  - Coze席：Coze平台免费配额
  - K2.8席：Kimi桌面端免费配额

免费域(free domain) ≡ 不触发任何付费行为的活动范围
  - 夜间游乐场时段内：所有活动限定在免费域
  - 烧费动作：超出免费额度的任何API调用
  - 挂账候批：烧费动作记录到待批清单，不执行，候机主晨批
```

#### 规则S4：不可逆操作精确定义

```
不可逆操作 ≡ 满足以下任一条件的操作：
  (1) 操作执行后无法通过等价逆操作恢复到操作前状态
  (2) 操作导致数据丢失且无备份可恢复
  (3) 操作影响第三方系统的状态且无法回滚
具体示例：
  - 删除文件（无备份） = 不可逆 ✗
  - 修改配置文件（有版本控制） = 可逆 ✓
  - 重启服务（服务自动恢复） = 可逆 ✓
  - 清空数据库（无备份） = 不可逆 ✗
  - 发送A2A总线消息（总线不可撤回） = 不可逆 ✗ → 但允许，因为总线消息是实验的核心产出
```

#### 规则S5：总线回执时限

```
回执时限 ≡ 每轮攻击/压测/模拟/检验完成后，30分钟内必须通过A2A总线发送回执消息。
超时未回执 → 神经中枢（砚坚席）发送 `kind=timeout-alert` 消息，标记该席位为"回执超时"。
连续2次回执超时 → 标记该席位为"失联"，暂停其后续任务分配。
```

### 1.3 形式化验证方法

每方提示词须通过以下形式化验证：

| 验证项 | 方法 | 通过条件 |
|--------|------|---------|
| **角色完备性** | 检查提示词是否包含六要素（角色/权限/资源/议题/契约/红线） | 六要素全部存在且非空 |
| **权限无矛盾** | 检查权限边界中是否存在相互矛盾的约束 | 无矛盾（如"仅限免费"与"最大化利用"不同时出现在同一权限域） |
| **议题覆盖性** | 检查议题分工是否覆盖全部三个议题 | 三议题全部有分工，无遗漏 |
| **输出契约可解析** | 检查落盘格式是否为可机器解析的结构化格式 | 格式包含定界符和字段名，可正则匹配 |
| **红线可执行** | 检查红线条款是否为可操作的禁止规则 | 每条红线有明确的"禁止X"或"必须Y"句式 |
| **条件判断有终止** | 检查所有条件判断（如额度监控、穷举终止）是否有明确的终止条件 | 每个条件判断有终止判据 |

## 三、HY4握手阶段提示词

### 3.1 握手流程定义

```
握手阶段状态转换图：

  S0: 神经中枢起草握手提示词
    ↓
  S1: 总线广播握手提示词（kind=handshake-propose）
    ↓
  S2: 各方确认/修改建议/保留意见（kind=handshake-response）
    ↓
  S3: 神经中枢汇总各方反馈
    ↓
  S4: 有保留意见？ ──是──→ S5: 标记"保留意见通过"，记录复议事项
    │                    ↓
    │否              S6: 机主裁示握手协议生效（或保留意见通过状态下暂不阻塞）
    ↓                    ↓
  S7: 握手协议生效，总线广播（kind=handshake-confirmed）
    ↓
  S8: 各方进入实战阶段
```

### 3.2 握手阶段语义约定

| 语义约定 | 定义 | 形式化规则 |
|---------|------|-----------|
| **确认(confirm)** | 席位对提示词内容无异议，接受执行 | `response_type = confirm` |
| **修改建议(suggest)** | 席位对提示词内容有修改意见，提出替代方案 | `response_type = suggest; suggestion = {字段, 原文, 建议文, 理由}` |
| **保留意见(reserve)** | 席位对提示词部分内容有异议但暂不阻塞，标记待复议 | `response_type = reserve; reservation = {字段, 异议内容, 复议事项, 复议时限}` |
| **拒绝(reject)** | 席位对提示词内容有根本性异议，阻塞实战推进 | `response_type = reject; reason = {字段, 异议内容, 阻塞理由}` |

### 3.3 握手阶段形式化规则

```
规则H1: 握手消息格式
  handshake-propose: { version, proposer, prompts: [七方提示词], timestamp }
  handshake-response: { version, responder, response_type, suggestions?, reservations?, timestamp }

规则H2: 确认生效条件
  握手协议生效 ≡ 全部已接入席位返回 confirm 或 reserve（无 reject）
  OfficeAce席位（未接入）不参与生效条件判定

规则H3: 保留意见通过条件
  "保留意见通过" ≡ 满足以下全部条件：
    (1) 该保留意见不涉及红线条款（凭据不外发/不外发/不可逆三不）
    (2) 该保留意见不涉及权限边界的扩大
    (3) 该保留意见有明确的复议事项和复议时限
    (4) 神经中枢记录该保留意见到 RESERVATION_LIST.md

规则H4: 复议时限约束
  复议时限 ≤ 机主晨起收口时间 + 24小时
  超过复议时限未复议 → 保留意见自动转为"默认接受"

规则H5: 握手超时处理
  握手提示词广播后2小时内无响应 → 神经中枢发送 kind=handshake-reminder
  握手提示词广播后4小时内仍无响应 → 该席位标记为"握手失联"，暂不分配任务
```

## 四、保留意见处理机制

### 4.1 "保留意见通过"状态定义

```
"保留意见通过"(Reservation Passed) ≡ 满足以下全部条件：
  (1) 该保留意见不涉及红线条款（凭据不外发/不外发/不可逆三不）
  (2) 该保留意见不涉及权限边界的扩大
  (3) 该保留意见有明确的复议事项和复议时限
  (4) 神经中枢已将该保留意见记录到 RESERVATION_LIST.md
  (5) 该保留意见暂不阻塞实战推进

效果：标记为"保留意见通过"的条款，各方暂按当前版本执行，待复议时限内复议。
```
