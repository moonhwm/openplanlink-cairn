## 二、三层职责定义

| 握手协议 | HY4 v1.1 | 修订后 | ✅ 已验证 |

## 三、治理流程

### 3.1 握手流程（HY4 v1.1）

```
S0: 砚坚起草握手提示词
  ↓
S1: 总线广播握手提示词(kind=handshake-propose)
  ↓
S2: 各方确认/修改建议/保留意见/拒绝(kind=handshake-response)
  ↓
S3: 砚坚汇总各方反馈
  ↓
S4: 有保留意见？ ──是──→ S5: 标记"保留意见通过"，记录复议事项
  │                    ↓
  │否              S6: 机主裁示握手协议生效（或保留意见通过状态下暂不阻塞）
  ↓                    ↓
S7: 握手协议生效，总线广播(kind=handshake-confirmed)
  ↓
S8: 各方进入实战阶段
```

### 3.2 闭环验证流程

```
1. 攻击方发起攻击 → 落盘攻击记录
2. 防御方识别攻击 → 落盘防御记录
3. 修复方提出修复方案 → 落盘修复记录
4. 验证方验证修复效果 → 落盘验证证据
5. 闭环完成 → 落盘闭环台账(CLOSURE-XXX.md)
6. 总线广播闭环完成通知
```

### 3.3 穷举终止流程

```
1. 每轮攻击生成后，计算新增条目与已有条目的embedding余弦相似度
2. 新增有效条目 = 相似度<0.3的条目
3. 连续5轮无新增有效条目 → 穷举终止
4. 穷举终止判定结果记录在案，可供复议
```

## 四、模型的可推广性评估

### 4.1 可推广要素

| 要素 | 可推广性 | 条件 |
|------|---------|------|
| 三层架构(席位-通道-制度) | 高 | 适用于任何多智能体治理场景 |
| 双轨制(理论轨+技术轨) | 高 | 适用于任何需要逻辑验证+技术验证的治理场景 |
| HY4握手协议 | 中 | 需要根据具体场景调整提示词和议题 |
| 表态成本机制 | 中 | 需要根据具体场景调整成本参数 |
| 额度分配机制 | 中 | 需要根据具体场景调整分配比例 |
| 闭环验证流程 | 高 | 适用于任何需要"攻击-防御-修复-验证"的治理场景 |

### 4.2 不可推广要素（场景特定）

| 要素 | 不可推广原因 |
|------|------------|
| 具体议题(哈贝马斯/国际关系/民主集中制) | 与特定理论框架绑定 |
| 具体席位分配(百炼/X实例/Coze/hy4/K2.8/OA) | 与特定AI平台绑定 |
| 具体额度参数(1M tokens/80%预警) | 与特定API配额绑定 |

### 4.3 推广建议

1. **保留三层架构和双轨制**——这是模型的核心结构，适用于任何多智能体治理场景
2. **调整议题和席位**——根据具体场景选择适当的议题和席位分配
3. **保留闭环验证流程**——"攻击-防御-修复-验证"四步闭环是治理质量保障的核心
4. **保留穷举终止条件**——embedding相似度<0.3+连续5轮无新增是穷举收敛的可靠判据
5. **调整成本参数**——表态成本、额度分配比例等参数需根据具体场景调整
