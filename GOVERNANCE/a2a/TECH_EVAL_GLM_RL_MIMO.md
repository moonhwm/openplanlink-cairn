## 2. 强化学习（RL）方案评估

### 2.1 必要性与适用场景

| 评估维度 | 分析 |
|----------|------|
| **RL能解决的痛点** | ①播报内容个性化排序（用户点击行为→卡片优先级优化）；②TTS播报节奏自适应（用户听力习惯→语速/停顿调整）；③异动筛选策略优化（历史命中率→筛选阈值动态调整） |
| **适用场景** | 适老化播报内容排序、用户偏好学习、异动信号筛选阈值调优、播报时机优化 |
| **不适用场景** | 代码生成（确定性任务，RL无优势）、合规审查（规则明确，不需学习）、密码学操作（安全敏感，不可学习试错） |
| **与现有方案对比** | 当前方案是静态规则（DEMO_ITEMS兜底+固定筛选逻辑），RL可使其变为动态自适应 |

### 2.2 与现有ArkTS工程的结合方式

| 层面 | 路径 | 可行性 |
|------|------|--------|
| **训练侧** | 在CloudBase云函数中收集用户行为数据（点击/播放/跳过/停留时长）→ 离线训练RL策略模型 → 导出为轻量推理模型 | 中——需搭建数据采集+训练管线 |
| **推理侧** | 将训练好的策略模型转为ONNX/TFLite格式 → ArkTS通过NAPI加载 → 端侧推理 | 低——HarmonyOS NAPI对ML推理支持有限，且零三方依赖约束 |
| **替代方案** | 云函数侧RL推理：端侧上报上下文 → 云函数返回排序/筛选策略 → 端侧执行 | 高——不违反零三方依赖约束 |
| **反馈闭环** | 端侧埋点 → CloudBase数据库存储 → 定期离线训练 → 更新云函数策略 | 中——需建立完整数据管线 |

### 2.3 方案对比

| 维度 | 当前GLM-5.2/ArkTS直接调用 | RL增强方案 |
|------|--------------------------|-----------|
| **效果提升** | 静态规则，所有用户相同策略 | 个性化排序，点击率预计提升15-30% |
| **响应速度** | 端侧即时（本地规则） | 云函数往返+200-500ms延迟 |
| **资源消耗** | 零额外消耗 | 训练需GPU算力，推理需云函数调用 |
| **可解释性** | 高（规则透明） | 低（策略模型黑箱） |
| **维护成本** | 低（改规则即可） | 高（需训练管线+模型版本管理） |
| **合规风险** | 低 | 中（用户行为数据采集需隐私合规） |

### 2.4 成本与风险

| 维度 | 估算 | 说明 |
|------|------|------|
| **训练数据获取** | 3-6个月用户行为数据积累 | 需先部署埋点，再积累数据 |
| **算力投入** | 训练约$500-2000/轮（云GPU） | 轻量策略模型，不需大规模训练 |
| **工程改造量** | 中等（埋点+数据管线+策略云函数+端侧适配） | 约2-4周开发周期 |
| **模型稳定性风险** | 策略可能过拟合小样本 | 需A/B测试框架和回退机制 |
| **可解释性风险** | 策略决策不透明 | 需可解释性工具+人工审计 |

## 4. 方案对比与推荐

### 4.1 四方案对比矩阵

| 维度 | A.维持现状 | B.RL增强 | C.MiMo接入 | D.组合方案（C+B） |
|------|-----------|---------|-----------|------------------|
| **推理延迟** | 3-8s | +200-500ms（云推理） | 待测（预计1-3s） | 待测+200-500ms |
| **理解深度** | 中（GLM-5.2 SFT） | 不变 | 待测（mimo-v2.5-pro） | 待测 |
| **多轮一致性** | 低（切换断裂风险） | 不变 | 高（Self-Evolve+反思我） | 高 |
| **上下文窗口** | 128K-200K | 不变 | 待测（官网称300K/1M） | 待测 |
| **个性化能力** | 无（静态规则） | 有（RL策略） | 有（Smart调度） | 最强 |
| **自进化能力** | 无 | 有（训练迭代） | 有（Self-Evolve引擎） | 最强 |
| **工程改造量** | 零 | 大（2-4周） | 小（1-2天） | 大（2-4周） |
| **成本** | 零 | $500-2000/轮训练 | API调用费（待确认） | API费+训练费 |
| **可解释性** | 高 | 低 | 中（仿生大脑可观测） | 中低 |
| **合规风险** | 低 | 中（数据采集） | 低（API调用） | 中 |
| **回退难度** | — | 中（需保留规则版本） | 低（切回GLM端点） | 中 |

### 4.2 推荐路径

**推荐：D.组合方案（MiMo接入 + RL增强），分阶段实施**

**理由**：
1. MiMo接入成本低（1-2天）、回退容易（切回GLM端点），可立即获得Smart调度+自进化+更大上下文窗口
2. RL增强在MiMo接入后实施，因为MiMo的Self-Evolve引擎可辅助RL策略训练
3. 两者互补：MiMo解决模型能力瓶颈，RL解决个性化适配瓶颈

### 4.3 实施里程碑

| 里程碑 | 内容 | 预计周期 | 验收标准 |
|--------|------|---------|---------|
| **M1: MiMo API接入** | ①注册MiMo开放平台账号→②获取API key→③在云函数中添加MiMo端点配置→④A/B测试GLM vs MiMo | 1-2天 | 云函数可调用MiMo API，返回结果与GLM对比 |
| **M2: A2A桥接注册** | ①在registry.json中添加MiMo为第6个agent→②分配角色（co-orchestrator或独立角色）→③配置MFV指纹验证 | 1天 | MiMo出现在registry中，探针可发送 |
| **M3: 端侧A/B测试** | ①云函数双模式（GLM/MiMo）→②对比播报内容质量、响应延迟、合规准确性→③收集量化指标 | 3-5天 | 量化对比报告：延迟/质量/合规各维度 |
| **M4: RL数据采集** | ①端侧埋点（点击/播放/跳过/停留时长）→②CloudBase数据库存储→③数据清洗管线 | 1-2周 | 埋点数据入库，可查询用户行为序列 |
| **M5: RL策略训练** | ①离线训练策略模型→②A/B测试框架→③灰度发布 | 2-4周 | A/B测试显示点击率提升≥15% |
| **M6: 全链路切换** | ①MiMo为主+GLM为fallback→②RL策略上线→③监控+回退机制 | 1周 | 生产环境稳定运行7天无回退 |
