# 05 · 事件顺序性保证与因果一致性：happened-before关系的工程化

## 一、问题背景

推送系统里"先发生的事件后到达"是常态：重试可能乱序、Webhook并发投递可能乱序、跨分区存储也可能乱序。如果消费者直接按到达顺序应用状态变更，就会出现"任务先completed又回到working"的倒灌。顺序性问题的本质是因果一致性——需要表达事件之间的happened-before关系，并让消费端能够检测与纠正乱序。

## 二、排序模型的三个层次

第一层是全局有序：所有事件进单一序列，实现简单但吞吐受限，仅适合小规模。第二层是分区间有序：以实体（如taskId）为分区键，同一任务的事件严格有序，不同任务之间无序。这是绝大多数推送系统的合理选择，因果一致性天然成立，因为一个任务的状态因果链是串行的。第三层是无序加显式因果标记：事件携带causes字段或向量时钟，消费者自行重建偏序。Webhook场景推荐第二层，并配两个辅助字段：sequenceNumber（同任务单调递增）与occurredAt（发生时间）。到达顺序应用规则：仅当新事件的序号大于已应用的最后序号才应用；小于则丢弃（迟到重复）；等于则冲突告警。

## 三、消费端有序应用的实现

```python
class TaskView:
    def __init__(self):
        self.applied_seq = {}   # taskId -> last applied seq

    def apply(self, evt):
        last = self.applied_seq.get(evt.taskId, 0)
        if evt.sequenceNumber < last:
            return "stale-drop"        # 迟到的旧事件，忽略
        if evt.sequenceNumber == last:
            return "duplicate-alert"   # 序号冲突，人工介入
        self.applied_seq[evt.taskId] = evt.sequenceNumber
        self.mutate(evt)
        return "applied"
```

并发投递时以taskId为键加互斥锁或路由到同一worker，保证apply的原子性，锁内只做比较与应用两步。

## 四、落地检查清单

- 是否定义了分区键并保证同键事件在生产端串行生成
- 序号生成是否在分区内单调严格递增（不允许回绕）
- 消费端是否实现"只前进不后退"的序号检查
- 序号冲突（相等但不一致）是否触发告警而非静默
- 时间戳是否只用于诊断而不用于排序裁决
- 并发消费者是否按键哈希到固定worker
- 缺号检测是否接入（长时间缺口触发补拉）
- 文档是否明确"跨任务不保证顺序"的边界

因果一致性是重试乱序的解药，也是幂等去重之外的第二道消费防线。
