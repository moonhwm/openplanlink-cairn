# 01 · A2A协议中推送通知的语义模型与任务生命周期映射

## 一、问题背景

A2A（Agent-to-Agent）协议把跨Agent协作抽象为"任务"（Task）这个一等公民。客户端把请求提交给远端Agent后，任务会经历 submitted、working、input-required、completed、failed、canceled 等一组状态。如果客户端只能靠反复轮询 tasks/get 来感知变化，网络开销与延迟都会被放大。推送通知（push notification）的出现，正是为了让服务端在任务状态跃迁时主动告知客户端。但"通知"并不是简单的消息转发，它携带的是一套语义承诺：什么时候发、发什么、发了之后意味着什么。理解这套语义模型，是后续做SSRF防护、重试与幂等地基。

## 二、语义模型的三层拆解

第一层是触发语义。通知只在任务发生不可忽略的跃迁时发出，例如从 working 到 input-required，或从 working 到 completed。同一状态内的进度更新是否推送，取决于配置的粒度开关，这决定了消费者需要处理的噪音水平。第二层是内容语义。A2A 的事件体通常包括 taskId、contextId、eventType（如 status-update 或 artifact-update）、事件发生时间戳以及可选的载荷。通知应当自描述，消费者不应当为了理解事件被迫回源查询，但也不应把整个任务快照塞进每条通知，二者之间需要按消费场景权衡。第三层是交付语义。推送天然基于至少一次投递的假设：网络可能重发、代理可能复制、生产者可能在超时后重试。因此通知语义里必须显式声明"重复是正常现象，去重是消费方义务"，这一条直接决定了幂等键的地位。

## 三、生命周期到事件的映射实现

把任务状态机与事件类型建立稳定映射，是保证消费者可以只依赖事件流重建任务视图的关键。下面给出一个最小映射表及其伪代码：

```python
TRANSITIONS = {
    ("submitted", "working"):          "task.status-update",
    ("working",   "input-required"):   "task.status-update.needs-input",
    ("input-required", "working"):     "task.status-update.resumed",
    ("working",   "completed"):        "task.status-update.final",
    ("working",   "failed"):           "task.status-update.final",
    ("submitted", "canceled"):         "task.status-update.final",
}
def emit(old, new, task):
    key = (old, new)
    etype = TRANSITIONS.get(key, "task.artifact-update")
    if etype.endswith(".final"):
        push(task.subscriber, envelope(task.id, etype, final=True))
    else:
        push(task.subscriber, envelope(task.id, etype, final=False))
```

终态事件必须标记 final，消费者看到 final 后可以安全释放订阅资源；非终态事件则允许继续累积。映射表集中定义而不是散落在业务代码里，可以避免漏发与错发。

## 四、落地检查清单

- 是否为每一个终态跃迁定义了唯一的 final 事件类型
- 事件体是否包含 taskId、contextId、eventType、occurredAt 四要素
- 状态机映射是否集中管理并附有单元测试覆盖每个跃迁
- 非终态进度通知是否有粒度开关，避免事件风暴
- 消费文档是否明确写出"至少一次投递、可能重复"的交付假设
- 订阅建立与任务创建是否原子，避免创建后订阅前的窗口丢事件
- 终态事件发出后是否停止该任务的一切后续推送
- 事件中是否存在敏感字段未脱敏就外发

满足以上各条，通知语义层才算闭环，后续的重试与幂等设计才有明确的契约可依托。
