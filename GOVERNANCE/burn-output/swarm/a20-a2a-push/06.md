# 06 · 通知与轮询的互补语义：长任务的混合拉推策略

## 一、问题背景

纯推送系统有一个隐蔽缺陷：推送失败且重试耗尽时，事件就"消失"在死信区里，除非有人盯着告警。纯轮询则有延迟与开销问题。成熟的A2A实现往往采用推拉结合：推送负责及时性，轮询负责兜底对账。这种混合策略需要明确两者的语义分工，否则会出现双通道重复触发、状态不一致等新问题。

## 二、混合策略的分工设计

推送通道承担"低延迟通知"，尽力而为但可能重复、可能失败；轮询通道承担"最终对账"，周期性拉取任务真值快照。两者读取的是同一个持久事件日志或同一张任务表，因此天然收敛。对账轮询的触发有三种方式：固定周期（简单但有空转）、指数拉长（无变化时周期翻倍，有变化时重置）、事件驱动补偿（推送失败计数超阈值时立即对账一次）。推荐后两者组合。轮询响应应当返回全量快照加当前序号，消费端用快照的序号与本地已应用序号比较，快照新则覆盖本地视图。由于快照是幂等的（同一序号的快照内容相同），重复轮询无副作用。

## 三、对账合并的实现骨架

```python
def reconcile(local_view, remote_snapshot):
    if remote_snapshot.sequenceNumber <= local_view.applied_seq:
        return ReconcileResult(action="noop")
    # 快照比本地新：直接以快照为准，并补齐差异审计
    diff = diff_states(local_view.state, remote_snapshot.state)
    local_view.replace_with(remote_snapshot)
    if diff.has_missing_events:
        fetch_events(local_view.task_id,
                     since=local_view.applied_seq + 1,
                     upto=remote_snapshot.sequenceNumber)
    return ReconcileResult(action="overwritten", diff=diff)
```

关键点：快照覆盖优先于事件回放，因为快照是权威真值；差异审计只用于发现推送链路的质量问题。

## 四、落地检查清单

- 是否声明"推送为优化、轮询为真相"的总体原则
- 轮询周期是否支持指数拉长与事件触发重置
- 快照是否携带序号与版本，供幂等比较
- 推送失败达到阈值是否自动触发一次对账
- 对账覆盖是否留下差异审计日志
- 双通道并发到达是否以序号裁决而非时间戳
- 客户端退避拉取是否服务端提示（如Cache-Control）
- 死信区事件是否在对账后自动标记"已过时"避免重放误导

拉推互补让通知语义从"尽力而为"升级为"最终确定"，也为重试上限的设定提供了安全网。
