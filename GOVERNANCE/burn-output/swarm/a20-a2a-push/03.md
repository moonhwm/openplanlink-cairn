# 03 · 投递语义边界：at-least-once、at-most-once与exactly-once的现实取舍

## 一、问题背景

分布式消息投递有三种理想语义：至多一次（at-most-once）、至少一次（at-least-once）、精确一次（exactly-once）。Webhook与A2A推送的工程现实是：网络与重试决定了"至少一次"几乎是唯一可行的起点，而"精确一次"在开放网络上并不存在，只能在消费端通过幂等近似达成。把这条边界讲清楚，可以避免团队在不切实际的承诺上浪费成本。

## 二、三种语义的真实代价

至多一次意味着发送方发完即忘、不重试，丢消息率取决于网络质量，适合允许丢失的指标上报类场景。至少一次要求发送方在未收到确认时重试，代价是重复不可避免，接收方必须幂等。精确一次要求跨发送与接收两端维持共享状态（事务或去重表），在单系统内部可借两阶段提交或事务性消息实现；但跨组织Webhook里，双方没有共享存储，"精确一次"只能退化为"至少一次投递加恰好一次处理"。这个区分至关重要：投递语义由协议与网络决定，处理语义由应用决定。A2A推送应显式选择至少一次投递，并在文档中写明消费者的幂等责任。

## 三、至少一次投递的实现骨架

```python
def deliver_with_retries(event, sink, clock, max_attempts=5):
    for attempt in range(1, max_attempts + 1):
        try:
            resp = sink.post(event.url, json=event.body,
                             timeout=(3, 10))
            if 200 <= resp.status_code < 300:
                return DeliverResult(ok=True, attempts=attempt)
            if resp.status_code == 429:
                wait = parse_retry_after(resp) or backoff(attempt)
                clock.sleep(wait); continue
            if 500 <= resp.status_code < 600:
                clock.sleep(backoff(attempt)); continue
            return DeliverResult(ok=False, reason="client-error",
                                 status=resp.status_code)
        except (Timeout, ConnectionError):
            clock.sleep(backoff(attempt))
    return DeliverResult(ok=False, reason="exhausted")
```

该骨架体现三条规则：2xx视为成功；429按对端指示等待；5xx与网络错误退避重试；其余4xx视为永久失败不重试。

## 四、落地检查清单

- 协议文档是否显式声明投递语义为"至少一次"
- 消费者指南是否给出幂等处理的最小示例
- 成功判定是否严格限定在2xx区间
- 4xx是否被归类为不可重试并进入告警
- 重试上限与总截止时间是否可配置
- 是否区分"投递重复"与"处理重复"两类指标
- 是否有丢事件演练（断网重放）验证至少一次成立
- 是否避免向用户承诺"绝不重复"这类精确一次话术

明确语义边界后，重试策略与幂等键的设计空间就被精确圈定，不再摇摆。
