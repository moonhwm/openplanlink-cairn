# 10 · 推送内容粒度控制：全量快照与增量delta的权衡

## 一、问题背景

设计通知载荷时的第一个分叉是：每条推送携带实体完整状态（全量快照），还是只携带变化部分（增量delta）。全量让消费者无状态可依、实现简单；增量让带宽最小、语义精确，但要求双方维护版本与顺序。粒度选错，轻则流量浪费，重则消费端状态机漂移。

## 二、两种模式的适用条件

全量快照适用于：实体体量小（几KB内）、消费者可能随时加入且没有历史上下文、或实体本身没有可分解的内部结构。其幂等性天然好——同一序号的快照内容一致，重复应用无副作用。增量delta适用于：实体大、变更频繁、且能定义稳定的字段级差异。它依赖两个前提：事件严格有序（丢失即状态漂移）与消费端持久保存版本号。实践中推荐的混合方案是"增量为主、周期性快照对账"：日常推delta，每N个事件或每T秒推一次快照纠正累计漂移；消费端发现序号缺口时主动请求快照重建。粒度还应可配置：订阅时声明snapshot或delta偏好，服务端据此生成对应形态。

## 三、订阅级粒度与合并的实现

```python
def build_payload(task, since_seq, granularity):
    if granularity == "snapshot":
        return {"kind": "snapshot", "seq": task.seq,
                "state": task.full_state()}
    delta = task.diff_since(since_seq)
    if delta is None or delta.too_large():        # 差异过大退化为快照
        return {"kind": "snapshot", "seq": task.seq,
                "state": task.full_state()}
    return {"kind": "delta", "seq": task.seq, "base": since_seq,
            "changes": delta.changes}
```

消费端处理规则：snapshot直接整体覆盖；delta要求base等于本地seq，不匹配则触发快照请求，绝不带病应用。

## 四、落地检查清单

- 实体体量与变更频率是否支撑所选粒度
- delta是否带base版本号供消费端校验连续性
- base不匹配时是否强制走快照重建路径
- 是否提供周期性快照对账消除累计漂移
- 差异过大时是否自动降级为快照
- 订阅协议是否允许声明粒度偏好
- 快照序号与增量序号是否同一序列空间
- 消费端是否持久化本地版本号而非仅存内存

粒度控制连接了通知语义与带宽成本，并为幂等提供了"快照天然幂等"这条捷径。
