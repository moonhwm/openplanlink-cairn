# 08 · 通知确认机制：ACK/NACK语义与消费者响应码约定

## 一、问题背景

Webhook投递的成功判定看似简单——返回200就算成功——但工程实践中充满歧义：消费者返回202算不算确认？500之后立刻恢复算不算永久失败？返回200但正文写着error又算什么？没有明确的ACK/NACK语义，发送方的重试决策就失去依据，最终表现为重复轰炸或事件丢失。

## 二、响应码契约

推荐契约：2xx区间（200、201、202、204）一律视为确认成功，其中202表示"已受理、异步处理中"，发送方不得因202重发；3xx不视为成功，重定向不跟随（详见SSRF篇），按失败处理并告警；408、425、429视为可重试，429优先尊重Retry-After头；其余4xx（400、403、404、410等）视为永久拒绝，进入死信而非重试——特别是410 Gone应触发"订阅失效"流程，自动下线该回调端点；5xx视为暂时性失败，按退避重试。响应体约定：确认成功时返回空体或简短JSON；若消费失败但HTTP层必须200（如网关固定改写），必须在体内用机器可读字段表达NACK，并约定该场景下发送方依据体NACK重试——但这属于下策，首选仍是正确使用HTTP状态码。

## 三、发送方判定实现

```python
def classify(resp) -> Decision:
    code = resp.status_code
    if 200 <= code < 300:
        return Decision.ACKED
    if code in (408, 425, 429):
        return Decision.RETRY_LATER(
            delay_hint=resp.headers.get("Retry-After"))
    if code == 410:
        return Decision.UNSUBSCRIBE
    if 400 <= code < 500:
        return Decision.DEAD_LETTER(reason=f"permanent-{code}")
    return Decision.RETRY_LATER(delay_hint=None)  # 5xx
```

消费端务必遵循"先落盘后响应"：把事件写入本地接收日志并提交后，才返回2xx；任何业务处理失败都不应改成非2xx去触发发送方重试，除非希望整条事件重投。

## 四、落地检查清单

- 契约文档是否逐区间写明发送方行为（确认/重试/死信/下线）
- 202是否被明确为最终确认而非待定
- 3xx是否禁止跟随并告警
- 410是否联动订阅自动下线流程
- Retry-After是否支持秒数与HTTP日期两种格式
- 消费端是否做到"先持久化后应答"
- 业务失败与接收失败是否区分处理路径
- 响应体是否避免携带内部堆栈等敏感信息

清晰的ACK/NACK契约是重试引擎的输入信号，也是双方责任划分的法定边界。
