# 11 · 多Agent场景下的通知路由与目标寻址：AgentCard中的webhook声明

## 一、问题背景

单个客户端订阅单个任务的通知很简单；但当编排层同时协调数十个上游Agent、每个Agent各自回推事件时，"谁来收、收谁的、按什么规则分发"就成了系统性问题。A2A用AgentCard描述Agent能力，通知路由信息也应有一等公民的声明位置，否则路由规则散落在配置文件与口头约定里，迟早失控。

## 二、路由声明的设计

AgentCard中与推送相关的声明包括：是否支持推送通知能力（capabilities.pushNotifications）、默认回调协议与鉴权方式（如支持HMAC签名的webhook v1）、以及可选的事件类型订阅过滤声明。客户端在建立任务时通过tasks/pushNotificationConfig/set登记具体回调端点，该配置绑定于任务级而非全局，方便同一下游为不同任务使用不同端点。编排层的路由器则以"任务到端点"的映射表为核心，依据事件信封中的taskId反查订阅配置，再依据eventType做细粒度过滤——下游只声明感兴趣的类型集合，路由器在出口过滤，减少无效外发。多下游扇出时，每个下游独立计数与重试，互不拖累；一个下游持续失败不得阻塞其他下游的投递。

## 三、路由器的实现骨架

```python
ROUTING = {}   # taskId -> list[Subscription]

def register(task_id, url, types, auth):
    ROUTING.setdefault(task_id, []).append(
        Subscription(url=url, wanted=set(types), auth=auth,
                     failure_count=0, state="active"))

def fanout(evt):
    subs = ROUTING.get(evt.taskId, [])
    for s in list(subs):
        if s.state != "active" or evt.eventType not in s.wanted:
            continue
        result = deliver_isolated(s, evt)   # 独立超时与重试
        if result.permanent_failure:
            s.state = "suspended"; alert(s)
```

deliver_isolated强调隔离：每个订阅独立的超时、并发与重试预算，并按订阅维度熔断。

## 四、落地检查清单

- AgentCard是否声明推送能力与鉴权方式
- 回调配置是否任务级登记、可查询可撤销
- 是否支持eventType级订阅过滤
- 多下游扇出是否彼此隔离、独立重试
- 单下游连续失败是否熔断并告警而非拖垮全局
- 路由表变更有无审计日志
- 订阅是否有默认过期时间，需续订才延续
- 撤销订阅后是否停止一切外发并清理队列

路由与寻址是多Agent协作的神经系统，声明式配置让它在规模下依然可审计。
