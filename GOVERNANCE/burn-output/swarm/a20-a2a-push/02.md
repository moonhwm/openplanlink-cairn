# 02 · Webhook事件负载设计：信封结构与事件类型体系

## 一、问题背景

Webhook是服务间异步通知的事实标准，但很多系统的负载设计随意：有的直接把内部领域对象序列化了事，有的字段命名每次发版都变。消费者一旦依赖了不稳定的结构，升级就变成连锁故障。良好的事件负载设计要在"足够自描述"与"足够稳定"之间取得平衡，核心手段是引入统一信封（envelope）与受控的事件类型体系。

## 二、信封结构设计

信封是所有事件共有的外层结构，与业务负载解耦。推荐字段包括：eventID（全局唯一、可用于去重）、eventType（带命名空间的类型标识）、occurredAt（事件真实发生时间）、sequenceNumber（同实体内单调递增序号，用于排序）、producer（生产者标识）以及data（业务负载）。信封字段必须向后兼容：只增不改不删。业务负载放在data内，允许按事件类型演进。这样消费者只需解析信封就能完成路由、去重与排序，不必理解每种业务负载的内部结构。 eventType 建议采用 "domain.entity.action.version" 的形式，例如 task.status.changed.v1，版本后缀给负载演进留出余地。

## 三、类型体系与代码骨架

事件类型体系应当用注册表集中管理，禁止字符串散落：

```json
{
  "eventID": "evt_01H9ZK3W2P",
  "eventType": "a2a.task.status.changed.v1",
  "occurredAt": "2026-08-27T14:03:11Z",
  "sequenceNumber": 42,
  "producer": "agent-orchestrator-03",
  "data": {
    "taskId": "task_7f3a",
    "from": "working",
    "to": "completed"
  }
}
```

```python
REGISTRY = {}
def register(etype):
    def deco(cls):
        REGISTRY[etype] = cls
        return cls
    return deco

@register("a2a.task.status.changed.v1")
class TaskStatusChanged:
    task_id: str
    from_state: str
    to_state: str
```

注册表同时驱动文档生成与消费者端的反序列化校验，新增类型必须先注册再发送，防止"幽灵事件"流入下游。

## 四、落地检查清单

- 信封字段是否固定且承诺向后兼容，只允许新增
- eventID 生成策略是否全局唯一且不可预测
- occurredAt 与推送时间是否分开记录，便于诊断延迟
- 是否提供 sequenceNumber 支持同实体事件排序
- eventType 是否带命名空间与版本号
- 业务负载是否全部收敛在 data 字段内
- 是否发布机器可读的schema（JSON Schema）供消费者校验
- 枚举值变更是否走新增事件类型而不是改旧值
- 大对象是否用引用链接而非内嵌，避免负载膨胀

信封与类型体系是通知语义的载体，稳定它，SSRF防护、重试与幂等才有可靠的抓手。
