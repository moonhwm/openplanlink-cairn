# 02. MCP规范授权层设计：传输解耦、资源服务器语义与发现机制

> 摘要：解析MCP规范如何把授权建立在OAuth 2.1之上，包括资源服务器语义、401引导流程、受保护资源元数据与授权服务器元数据发现，以及stdio与HTTP传输在授权上的差异。

## 一、授权与传输解耦的设计哲学

MCP规范刻意不在协议消息里定义"登录"指令，而是复用HTTP层的授权原语。对基于HTTP的传输（Streamable HTTP、已废弃的HTTP+SSE），MCP服务器必须实现OAuth 2.1资源服务器行为：不签发令牌、只校验令牌；对stdio等本地传输，规范将授权交给操作系统权限与进程边界处理。这种解耦带来两个直接收益：其一，授权升级（例如从密码到通行密钥）不需要改MCP协议本身；其二，成熟的OAuth生态（网关、AS产品、审计工具）可以直接复用。

对Client侧的规范要点包括：所有MCP OAuth客户端默认视为公共客户端，必须使用PKCE；授权请求必须携带resource参数（RFC 8707）以锁定受众；重定向URI必须精确匹配注册值。

## 二、401引导与元数据发现流程

Client第一次访问一个受保护的MCP服务器时，并不知道该用哪个授权服务器。规范定义了引导流程：

```text
1. Client ──GET /mcp（无令牌）──> MCP Server
2. Server ──401 + WWW-Authenticate: Bearer resource_metadata="<url>"──> Client
3. Client ──GET /.well-known/oauth-protected-resource──> Server
   返回 { "authorization_servers": ["https://as.example.com"] }
4. Client ──GET https://as.example.com/.well-known/oauth-authorization-server──> AS
   获得 authorization_endpoint / token_endpoint / registration_endpoint 等
5. Client 走授权码+PKCE流程，带 resource=https://mcp.example.com/mcp
6. Client 携带 access_token 重试MCP请求
```

这一流程（参考RFC 9728与RFC 8414的元数据格式）让服务器可以随时更换或共用AS，也让多服务器共享同一AS成为可能。工程上要为元数据端点设置合理缓存与过期策略，避免每次请求都做发现。

## 三、资源服务器侧的校验义务

MCP服务器收到带令牌的请求后，至少完成以下校验，任何一步失败都应返回401或403与结构化错误码：

- [ ] 校验签名（JWKS拉取与轮换缓存）
- [ ] 校验exp/nbf/iat，允许有限时钟偏移
- [ ] 校验aud等于本服务器资源标识符，iss匹配预期AS
- [ ] 校验scope是否覆盖本次调用的工具所需权限
- [ ] 多租户场景校验租户声明与路径/请求体一致
- [ ] 校验失败时返回`WWW-Authenticate: Bearer error="invalid_token", error_description="..."`

## 四、常见实现误区

第一类误区是把MCP服务器同时实现成AS与RS但共享签名密钥，导致任意自签令牌都能通过校验，应隔离签发与校验密钥用途。第二类是忽略resource参数，令牌audience缺失，为令牌直通和跨服务器重放埋下隐患。第三类是stdio服务器误以为"本地就是安全的"，把高权限凭据通过环境变量注入子进程且不做二次确认。理解规范分层之后，下一节进入威胁模型，看攻击者如何利用这些薄弱点。
