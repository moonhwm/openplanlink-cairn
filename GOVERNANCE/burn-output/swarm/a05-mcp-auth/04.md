# 04. 混淆代理问题：令牌混淆与跨服务器授权劫持的原理与防御

> 摘要：混淆代理（Confused Deputy）是MCP授权中最经典的漏洞类别：持有高权限令牌的客户端被恶意服务器诱导，把本应只属于A的授权用到B身上，本文剖析其触发条件、攻击变体与工程防御组合拳。

## 一、问题定义与经典场景

混淆代理指一个具备特权的中间人（Deputy，这里是MCP Client/Host）被攻击者利用，用它的特权去执行攻击者自己做不了的事。在MCP语境下，Client持有用户登录后的高权限令牌，而模型会按照服务器返回的指令行事，两者的组合构成天然的可乘之机。经典场景有三：

场景一，恶意服务器窃取直通令牌。用户给MCP服务器A（例如一个日历助手）授权了读写日历的令牌，A在背后把令牌转发给攻击者控制的服务器B或直接用于任意日历操作。因为令牌的audience校验形同虚设或者根本没做直通，令牌在哪都能用。

场景二，授权码与state被跨客户端劫持。攻击者先向AS发起授权请求拿到授权码与自己的state，再诱使受害者的Client用半初始化状态完成回调，客户端在未绑定state的情况下把授权码换成攻击者会话的令牌，攻击者由此获得以受害者身份行事的能力。

场景三，服务器指定AS实现交叉授权。AS对同一用户同时支持多个MCP服务器，如果令牌不含资源audience，A拿到的令牌可以访问B的接口，形成横向越权。

## 二、触发条件拆解

把三个场景抽象一下，混淆代理成立需要同时满足三个条件：客户端持有的令牌权限大于目标操作所需；客户端（或模型）缺乏判断"这次用权是否符合同意范围"的信息；令牌本身缺乏绑定（audience、发送方、会话）。因此防御就必须至少打断其中一个条件：

- 打断权限差：给每个服务器单独发最小scope令牌，而不是复用全局令牌
- 打断信息差：授权同意界面明确列出服务器身份与资源audience，高危scope单独确认
- 打断可移植性：令牌带aud、带resource指示器、用DPoP绑定客户端密钥

## 三、工程防御清单

- [ ] 授权请求必须带resource参数，AS签发的令牌aud必须等于该资源标识
- [ ] 服务器端逐请求校验aud，拒绝为其他资源签发的令牌
- [ ] state生成后立即与会话绑定，回调时严格比对，失败即中止
- [ ] 半初始化客户端不处理OAuth回调，先完成握手再进入授权流程
- [ ] 禁止令牌直通：Client给A的令牌不得出现在发往B的任何请求里
- [ ] 对高危scope启用逐次确认或短期令牌（分钟级TTL）

## 四、最小演示与检测方法

用一段伪代码演示audience校验如何直接掐断场景一：

```python
def verify_token(token, my_resource):
    claims = decode_and_verify_signature(token)   # 含JWKS校验
    if claims.get("aud") != my_resource:
        raise AuthzError("token issued for another resource")
    if "calendar.read" not in claims.get("scope", "").split():
        raise AuthzError("insufficient scope")
    return claims["sub"]
```

攻击者即使拿到A直通过来的令牌，在B上也会因aud不匹配被拒绝。检测方面，红队可以用"令牌移植测试"：把面向A的有效令牌发往B，若B返回200即存在混淆代理漏洞；审计侧则监控同一jti在不同资源上的校验尝试，这本身就是强告警信号。混淆代理的本质是"授权上下文丢失"，所有防御手段殊途同归：让每一次用权都携带并校验完整上下文。
