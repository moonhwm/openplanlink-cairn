# 01. MCP认证与授权体系总览：角色、信任边界与参考架构

> 摘要：本文梳理MCP（Model Context Protocol）在认证与授权上的角色划分、信任边界与参考架构，为整个"MCP认证与授权"知识体系建立统一术语与总体地图。

## 一、为什么MCP需要独立的认证授权设计

MCP把大模型应用（Host与Client）与外部能力提供方（MCP Server）彻底解耦，任何人都可以编写并发布MCP服务器。于是凭证、数据与指令要在多个信任域之间流动：用户浏览器、桌面Host、本地或远程Client、MCP服务器、上游业务API，链条上每一跳都可能成为令牌泄漏或权限放大的位置。与单体Web应用不同，MCP的调用是"代理式"的——用户并不直接持有发往MCP服务器的请求，而是由模型代为构造，因此传统"同源Cookie+服务端会话"的假设不再成立。MCP规范据此把授权从传输层剥离出来，规定基于HTTP类传输的服务器必须按OAuth 2.1资源服务器语义工作，把认证问题转化为标准的令牌问题。

核心角色可以概括为四类：

- **资源所有者（RO）**：最终用户，拥有上游数据与操作的许可。
- **MCP Client**：嵌入在Host中的应用，充当OAuth公共客户端，负责发起授权、保管令牌、附加令牌到请求。
- **MCP Server**：OAuth意义上的资源服务器（RS），负责校验令牌、执行scope约束、暴露tools/resources/prompts。
- **授权服务器（AS）**：签发令牌、维护用户同意与客户端注册信息，可与MCP Server同域也可独立部署。

## 二、信任边界与参考架构

绘制信任边界时要回答三个问题：谁签发身份（AS）、谁消费令牌（RS）、令牌能否被中转（代理链）。推荐参考架构是"AS独立、RS按资源划分、Client只持有面向本RS的令牌"。典型时序如下：

```text
用户 ──登录/同意──> 授权服务器(AS)
AS  ──access_token(aud=MCP Server A)──> MCP Client(Host内)
Client ──Bearer token + JSON-RPC请求──> MCP Server A(RS,校验签名/exp/aud/scope)
MCP Server A ──RFC8693令牌交换(降权,aud=上游API)──> 上游业务API
```

这条链路上有三条不可跨越的红线：第一，Client不得把面向服务器A的令牌直接转发给服务器B（令牌直通反模式）；第二，MCP Server不得默认信任模型转述的"用户已经同意"，高危操作必须回到可验证的授权凭据；第三，任何一跳的审计事件都要能追溯到唯一的用户主体与令牌标识（jti）。

## 三、总体能力地图

后续知识可以按四个维度展开，彼此保持MECE：

- **认证与令牌**：OAuth 2.1流程、PKCE、JWT校验、刷新轮换、DPoP/mTLS绑定（对应第7-18题）。
- **令牌传递与代理链**：令牌直通风险、RFC 8693交换、资源指示器、网关/BFF重构（第19-24题）。
- **最小权限与策略**：scope设计、策略引擎、人类在环、多租户隔离（第25-30题）。
- **审计与运营**：审计事件模型、不可抵赖、异常检测、合规映射（第37-42题）。

## 四、落地检查清单

- [ ] 明确每个MCP Server的资源标识符（resource identifier），令牌audience与之绑定
- [ ] Client全部按公共客户端处理，授权码流强制PKCE
- [ ] 高危工具列出所需scope，服务器端逐工具校验而非一次全量放行
- [ ] 每次令牌校验失败返回结构化错误（WWW-Authenticate），便于Client重授权
- [ ] 审计日志覆盖：谁、用哪个客户端、访问哪个资源、携带什么scope、结果如何
- [ ] 威胁建模文档与架构图同步更新，标注所有令牌驻留位置

理解了这张总图，后续每一篇都在其中某个局部做深挖，最终拼出完整的MCP认证授权防线。
