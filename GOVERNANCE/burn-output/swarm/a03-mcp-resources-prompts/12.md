# 12 资源订阅：resources/subscribe与updated通知

> 摘要：本文讲解MCP订阅机制的两条消息（subscribe请求与updated通知）、服务器能力声明、订阅表维护的实现模式，以及从轮询升级到推送的工程路径。

## 一、订阅机制的协议形态

轮询读取是资源消费的兜底方式，但对变化稀疏的资源 wasteful，对变化密集的资源又滞后。MCP为此提供订阅机制，由两条消息构成闭环：客户端调用resources/subscribe，参数为目标资源URI；此后该资源内容变化时，服务器主动推送notifications/resources/updated，客户端收到后重新执行resources/read获取新内容。通知本身不携带内容，只携带"变了"这一事实，设计上把传输体积压到最小。服务器是否支持订阅由初始化能力声明决定：capabilities.resources.subscribe为true时客户端才可调用，否则必须降级为轮询。这个能力位是客户端策略分支的依据，未声明而调用将得到方法不存在或错误响应。

```json
{ "method": "resources/subscribe", "params": { "uri": "db://metrics/queue-depth" } }
{ "method": "notifications/resources/updated", "params": { "uri": "db://metrics/queue-depth" } }
```

## 二、服务器订阅表的实现模式

服务器侧的核心数据结构是订阅表：URI到订阅者集合的映射，配合订阅者到URI集合的反向索引以支持会话清理。实现要点有五。写入去重：同一客户端对同一URI的重复订阅应幂等合并，计数或直接忽略。变更挂钩：内容写入路径统一经过"变更通知"函数，查表广播updated，忘挂一处就产生"静默过期"这类最难排查的缺陷。批量化：一次发布影响大量URI时（目录重建、批量导入），逐条广播会形成通知风暴，应做窗口合并或改为通知父级目录资源。生命周期：会话断开时清理其全部订阅，防止僵尸订阅累积。背压：订阅数与广播速率设上限，超限返回资源不足错误而非无界排队。

## 三、客户端策略：从轮询到推送

客户端的标准姿势是三段式：优先订阅，能力允许即对关注的URI建立订阅；失败降级，订阅报错（资源不支持、瞬态故障）则退回自适应轮询（指数退避加抖动，上限受资源dynamicity约束）；读后校验，收到updated不盲信，重读时以内容版本戳比对，相同则视为抖动丢弃。订阅粒度应贴合用户注意力：只订阅当前视图打开的资源与模型正在引用的资源，视图关闭即取消订阅，避免为不可见状态付费。连接级故障（传输断开重连）后必须重建全部订阅并全量重读一次，因为断连期间的变更不会有通知补偿。

## 四、语义陷阱与测试要点

订阅机制有三个易踩的语义陷阱。其一，updated通知到读取之间存在窗口，读取结果可能又落后于最新变更，客户端要以"最终一致"心态设计UI，而非假设原子性。其二，updated可能在读取前连续到达多次，合并处理即可，重复读取浪费但无害。其三，子树订阅的粒度由服务器解释，客户端不能假设订阅目录就一定覆盖全部子项变更，需在文档确认。测试用例应覆盖：订阅后首读与通知顺序；服务器重启后订阅是否需要重建；未订阅URI绝不产生通知；订阅数达到上限时的行为。订阅把资源体系从"拉模型"升级为"推模型"，是动态资源实时性的基础设施，其正确性依赖服务端挂钩完备与客户端降级链路的双重严谨。
