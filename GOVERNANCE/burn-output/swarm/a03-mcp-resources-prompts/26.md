# 26 提示消息中的内容组合：Text、Image与EmbeddedResource

> 摘要：本文解析prompts/get返回消息中content的三种形态——纯文本、图片与嵌入资源——的组合规则、适用场景与实现细节。

## 一、三种内容形态

提示消息的content字段是一个标签联合体，有三种主要形态。TextContent：type为text，携带字符串，是最常用的形态，承载指令、背景说明、示例等一切文字内容。ImageContent：type为image，data为base64图片数据、mimeType声明图片格式，用于把截图、图表、设计稿直接带入对话。EmbeddedResource：type为resource，内联一个资源对象（uri、mimeType、text或blob内容），让提示直接携带结构化上下文而不仅是提及。三种形态可以混用于同一messages数组的不同消息，也可以在数组级组合：先一条嵌入资源的消息铺垫上下文，再一条文本消息下达指令，形成"材料在前、任务在后"的经典编排。

```json
{ "messages": [
  { "role": "user", "content": { "type": "resource",
      "resource": { "uri": "file:///api/openapi.yaml",
                    "mimeType": "text/yaml", "text": "openapi: 3.1.0\n……" } } },
  { "role": "user", "content": { "type": "text",
      "text": "以上是API规范，请生成一份前端调用示例文档。" } } ] }
```

## 二、嵌入资源与文本引用的选择

把资源带进提示有两条路：嵌入（EmbeddedResource直接内联内容）与引用（文本中写URI，消费时再读）。选择依据四个因素。时效性：内容在get时已确定且必须精确（如当时的diff快照）用嵌入；希望消费时取最新（如实时指标）用引用。可用性：客户端必须能读到URI才能解引用，跨服务器或需要授权的URI用嵌入更稳；反之引用可节省get响应体积。体积：大资源嵌入会让get响应膨胀，应引用或嵌入摘要。语义边界：嵌入内容有明确的结构边界（它是资源，有URI与类型），模型对"这是外部材料"的认知比裸文本更清晰，利于防注入分区。实践中推荐默认嵌入小型关键材料、引用大型或动态材料。

## 三、图片形态的使用纪律

图片形态服务于真正需要视觉理解的任务：UI审查、图表解读、截图诊断。纪律包括：只嵌入与任务直接相关的图片，装饰性图片徒耗token与注意力；压缩与缩放到任务所需分辨率，截图全屏原始尺寸往往浪费；mimeType与实际编码一致；多图场景在文本消息中明确编号与顺序（"图1为登录页，图2为报错弹窗"），避免模型错配。文本中引用图片时用相邻消息排列建立对应关系。另需注意多模态能力协商：并非所有下游模型都支持图片，客户端应具备把图片降级为占位说明（"此处有一张截图，描述：……"）的能力，提示服务器作者则应把图片作为可选增强而非唯一信息载体。

## 四、组合编排模式与校验

成熟的提示组合有三种编排模式。线式（最常用）：材料消息在前、指令消息在后，一条对话线。分角色式：assistant消息先出现说明处理框架（如"我将分三步审查：结构、安全、性能"），user消息随后给出材料，利用角色对比强化结构。多材料分块式：多个资源各自成消息，每条消息配一行文本标签（"材料一：数据库Schema"），模型可按标签引用。服务端实现get时应对产出做自校验：消息非空、content形态合法、嵌入资源的uri字段存在、总尺寸在配置上限内；校验失败宁可返回错误也不要输出残缺模板。内容组合是提示表达力的物质基础，组合得当的提示能让模型开局就进入最佳工作状态。
