# 09 resources/templates/list与ResourceTemplate结构

> 摘要：本文详解资源模板接口的请求响应结构、ResourceTemplate各字段的语义、模板与静态资源的关系处理，以及服务端模板注册的设计模式。

## 一、接口定位与响应结构

resources/templates/list与resources/list平行存在，专用于返回参数化资源家族的模板定义，同样支持cursor分页与pageSize建议。响应中的每一项是一个ResourceTemplate对象：

```json
{
  "resourceTemplates": [
    {
      "uriTemplate": "weather:///{city}/current",
      "name": "城市实时天气",
      "description": "获取指定城市的当前天气摘要，city为城市拼音名",
      "mimeType": "application/json"
    }
  ],
  "nextCursor": null
}
```

四个字段的语义：uriTemplate是RFC 6570形式的URI模板，定义实例的生成规则；name与description面向用户与模型，说明该家族提供什么、参数如何取值；mimeType声明展开后实例的内容类型。模板不直接出现在resources/list中，客户端依据模板自行构造实例URI再调用resources/read。模板的存在使服务器无需枚举无限或海量实例（每座城市的天气、每个订单号、每条日志日期），这是MCP资源伸缩性的关键支柱。

## 二、模板与静态资源的关系

模板与静态列表共同构成发现面，设计时必须处理二者关系。互补原则：静态资源表达"具体存在的关键个体"，模板表达"可按需生成的族群"；例如根README是静态资源，其下全部文档用模板覆盖。互斥原则：同一URI模式不应同时通过静态列表和模板暴露，否则客户端可能对同一资源建立两条发现路径，去重逻辑复杂化。提示原则：description中写明实例构造规则与参数合法性，甚至给出示例URI，让模型可以零文档完成构造。若某家族实例数量有限且高度常用（如固定的十二个报表），应降级为静态列表，把模板留给真正开放式的参数空间。

## 三、服务端模板注册的设计模式

实现上推荐"模板注册表"模式：每个模板是一个声明式对象，包含匹配器（uriTemplate编译结果）、参数校验器、读取处理函数、缓存策略。请求到达时按注册顺序匹配模板，编译期完成URI解析，避免每请求正则重编译。注册表示例结构：

```text
registry = [
  { template: "weather:///{city}/current",
    validate: { city: /^[a-z-]+$/ },
    handler: fetchCityWeather,
    cache: { ttl: 300, key: "wx:{city}" } },
  { template: "db://{table}/{id}",
    validate: { table: enumOf(TABLES), id: /^\d+$/ },
    handler: readRow, cache: { ttl: 30 } }
]
```

该模式的优点是模板即配置，新增家族零散改动；校验器集中，安全审查有单点；缓存策略随模板声明，运维可视化。

## 四、分页、排序与模板治理

模板数量通常远小于静态资源，但同样需要分页语义以保持契约一致。治理要点：模板纳入版本管理，uriTemplate变更视为破坏性变更需走弃用周期；description中的参数说明与校验器实际规则必须同步，漂移会制造客户端构造失败；为每个模板建立最小集成测试——合法参数展开可读、非法参数返回明确错误、静态列表无重叠。模板体系把"发现"与"生成"分离，是资源子系统从目录服务进化为参数化内容服务的关键一步。
