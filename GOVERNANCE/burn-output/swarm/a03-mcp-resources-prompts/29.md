# 29 prompts/list_changed与提示的运行时动态性

> 摘要：本文讨论提示目录的动态性机制：list_changed通知的触发时机、客户端缓存失效流程、提示热更新的工程实现，以及版本协调与一致性保障。

## 一、提示目录为什么需要动态化

提示集并非一成不变：服务器升级会带来新提示，运营活动会临时上架专题提示，权限变化会让某些提示对特定用户消失，插件式的服务器架构甚至允许第三方在运行中注册提示家族。如果客户端只在连接初始化时拉取一次提示列表，它将与服务器真实状态逐渐脱节，用户看到陈旧的目录、调用已下架的提示、错过新增的能力。为此MCP在能力声明中提供prompts.listChanged位，服务器将其设为true即承诺：提示目录发生结构性变化时，主动推送notifications/prompts/list_changed通知。客户端收到后重新执行prompts/list刷新本地目录。这个机制与资源侧的list_changed完全同构，把"目录刷新"从客户端猜测式的定时轮询升级为服务器确认式的按需失效，既节省了无谓的重复拉取，又把目录更新的可见延迟压缩到一次网络往返。

## 二、触发时机与通知语义

list_changed的设计语义是"结构变化"而非"内容微调"。应当触发通知的事件包括：新增提示、删除提示、修改提示的name或参数结构（arguments的增删改）、权限导致的可见性翻转。不应触发的事件示例：仅修改description文案、调整内部模板措辞——这类不改变目录结构的更新可以等到客户端下次get时自然生效，频繁触发通知只会造成无意义的全量重拉。通知本身不携带变更明细（协议的通知形态只有事件本身），客户端的标准响应是重新list。实现精细化的服务器可以在通知后配合分页cursor的版本闸门，让客户端能判断"是追加还是重构"，但客户端不应依赖这种扩展，标准路径仍是全量重拉加本地差分。

```text
时序示例：
server: 上下线提示"migration-check"
server -> client: notifications/prompts/list_changed
client -> server: prompts/list
server -> client: 新目录（含/不含 migration-check）
client: 本地差分 -> 更新命令面板 -> 必要时提示用户新命令可用
```

## 三、客户端缓存失效流程

客户端的标准流程分四步。收到通知后标记本地目录为stale；在下一次用户访问提示入口（打开命令面板、输入斜杠）时触发重拉，而不是通知到达立即抢拉——把刷新推迟到真正需要时，摊平突发通知的成本；重拉后做本地差分，识别新增、移除、变更三类，增量更新UI状态（保留用户正在填写的参数草稿不被清空，除非该提示已消失）；对正在使用中的提示（用户已选中、参数已填）做优雅处理——提示仍可提交（服务器会返回最后的裁决），但面板标注其已从目录移除。重连场景必须视为一次隐式list_changed：断连期间的一切变化都没有通知补偿，重连后无条件重拉目录，这是与订阅重建同构的纪律。

## 四、服务端热更新与一致性

服务端实现热更新需要提示注册表支持运行时变更：注册与注销接口加锁保护、目录快照原子切换（读侧永远看到一致版本）、变更聚合（短窗口内多次变更合并为一次通知，防止抖动）。一致性要求有三点。原子性：list响应必须是某一时刻的完整快照，绝不出现半新半旧的混排。幂等性：重复通知导致重复list是无害的，服务器不得因此报错。版本协调：若cursor分页跨变更发生，遵循与资源列表相同的闸门策略——返回当前页并提示结构已变，由客户端决定续读或重扫。治理层面，提示的上下架应留审计记录（谁、何时、哪个提示、什么原因），临时提示要设置自动下架时间，防止"活动结束了命令还在"这类僵尸目录项。动态性让提示目录成为活的产品界面，而通知机制的正确实现决定了它给人的感觉是"智能更新"还是"随机抽风"。
