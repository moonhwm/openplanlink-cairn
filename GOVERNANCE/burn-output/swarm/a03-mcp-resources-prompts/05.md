# 05 resources/read返回结构与text/blob双通道

> 摘要：本文拆解resources/read响应中contents数组的结构、text与blob两条内容编码通道的选择规则、错误表示方式，以及大内容与多内容项的工程处理。

## 一、响应结构总览

resources/read是资源子系统的取数原语：客户端以URI为参数发起读取，服务器返回contents数组。每一项的结构为：uri（标识内容来源，通常等于请求URI，重定向场景下可为实际地址）、mimeType（可选类型声明）、以及二选一的内容字段text或blob。text是UTF-8字符串，用于一切人类可读与结构化文本；blob是base64编码字符串，用于二进制字节流。返回数组而非单项，是为了优雅支持"一次URI读出多段内容"的场景，例如压缩包内多文件、复合文档的多章节、一次投影生成的多表片段。协议要求text与blob互斥出现，服务端不得同时填充。

```json
{
  "contents": [
    {
      "uri": "file:///docs/arch.md",
      "mimeType": "text/markdown",
      "text": "# 架构说明\n\n本文档描述……"
    }
  ]
}
```

## 二、双通道选择规则

编码通道的选择以"内容是否能无损表示为UTF-8文本"为分水岭。能：JSON、Markdown、CSV、日志、源码一律走text通道，避免base64带来的33%体积膨胀与解码成本。不能或不应：图片、音视频、PDF、加密数据、含非法UTF-8字节的私有格式走blob通道。边界情形需注意：包含大量emoji或CJK的文本仍是合法UTF-8，走text；含NUL字节的"伪文本"必须走blob，否则多语言运行时会在字符串截断处静默丢失数据。另一个易错点是大小写：base64编码应使用标准字母表，MIME类型声明与实际编码不符会让客户端解码崩溃。服务端实现时应建立"编码器表"，按mimeType路由到对应通道，禁止逐接口手工判断。

## 三、错误表示与部分失败

读取可能因资源不存在、无权限、临时不可用而失败。MCP基于JSON-RPC 2.0，整体失败通过错误响应表达，常用错误码语义为：资源不存在映射到-32002（与协议定义的资源错误区间一致），内部错误映射到-32603。多内容项场景下若只有部分失败，推荐两种策略：其一，整体失败，语义最干净，客户端重试逻辑简单；其二，返回成功项并在每项附描述性说明，但这要求客户端理解部分失败语义，契约复杂度上升。除非业务强需求，优先整体失败。错误消息中不得包含内部堆栈、文件系统绝对路径或账号信息，只给用户可理解的短语与追踪ID。

## 四、大内容处理纪律

resources/read没有协议级分块原语，大内容需要设计层面的对策，可按序尝试：内容裁剪，服务器依据资源语义返回摘要或首屏段落并附"取全文"的子资源URI；视图参数化，通过资源模板把大文档按章节、时间窗切分为可独立寻址的小资源；blob直传，对图片等二进制先压缩再编码，并声明实际尺寸供客户端预判预算；消费端熔断，客户端对超过阈值的内容截断注入并明确标注"已截断"。配套的观测手段包括记录每次读取的字节数分布与P99延迟，为阈值调优提供数据。text/blob双通道加上这些纪律，resources/read才能在从百字节的配置到数十兆的媒体之间都保持稳定的服务质量。
