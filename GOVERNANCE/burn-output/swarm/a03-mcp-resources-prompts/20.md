# 20 大资源传输：大小限制、分块与blob编码

> 摘要：本文处理大体积资源的传输工程：协议层的尺寸约束分析、内容切分策略、base64 blob的效率优化，以及客户端预算感知的消费协议。

## 一、尺寸问题的三个层面

大资源对MCP体系施加三重压力。传输层：单个JSON-RPC消息体积膨胀，stdio下受管道缓冲影响，HTTP下受请求体限制，超大消息还拖累序列化与反序列化耗时。会话层：许多客户端对单响应设上限，超限直接失败或截断，行为因实现而异。上下文层：即使传输成功，把数十万字塞进模型上下文窗口既昂贵又降低注意力质量。因此大资源治理必须在三个层面同时设防：服务器侧出口设硬上限（例如单内容项若干MB），超限走切分或摘要；传输侧对blob做压缩优化；消费侧建立预算协商，让客户端在读取前知道内容的量级。尺寸元数据应尽量前置到列表阶段（扩展信息或description注明），避免客户端盲目读取。

## 二、内容切分策略

MCP没有协议级分块原语，切分以"资源设计"形态实现，有四种成熟策略。章节切分：按文档结构（标题、段落）切为子资源，父资源提供目录（含各章子URI与摘要），语义边界完整，首选。窗口切分：按行号或字节窗口参数化，模板如`log://app/{date}?offset={n}&limit={m}`，适合日志与流式文本，需提供总长度信息以支持进度显示。页化切分：表格类资源按主键游标分页，每页独立可缓存。摘要加详情：顶层资源只提供摘要与统计，明细按需下钻。切分的公共纪律：每块自带上下文头（属于哪个父资源、第几块、时间戳），块间有导航链接（前后块URI），单块尺寸上限统一配置。

```json
{
  "contents": [{
    "uri": "log://app/2026-09-22?offset=0&limit=500",
    "mimeType": "text/plain",
    "text": "…500行…"
  }]
}
```

配套响应约定：内容首行附`# 分块 1/N 总行数 12840`类元信息，客户端据此渲染分页控件。

## 三、blob通道的效率优化

二进制大内容必须走blob（base64）通道，体积膨胀约1.33倍，优化空间集中在三处。压缩前置：对可压缩格式（文本类二进制、未压缩图片的容器）先压缩再编码，mimeType标注实际格式，压缩率常抵消膨胀还有余。格式降级：按消费目的选码率，预览场景提供缩略图资源（低分辨率），原图独立URI按需取。缓存友好：blob内容不可变时（内容寻址URI）可设置长缓存，避免重复传输；可变内容附版本戳到query，既保新鲜又可缓存。服务端还应限制并发大blob的编码任务数，base64编码是CPU密集操作，洪峰时排队会放大延迟。

## 四、消费侧预算协议

客户端应实现预算感知的三步消费协议：读元数据（列表或目录资源）估算量级；按预算选择性读取（优先摘要、关键章节）；注入前裁剪并明确标注"已省略N行"。与模型的协作同样重要：把目录与分块信息注入上下文，让模型可以自主决定"再取第X章"，将大文档消费从一次性塞入转为按需检索，这既是性能优化也是质量优化——上下文越聚焦，模型注意力越有效。大小治理的终极目标：任何体量的底层资源，在MCP体系内都以有限尺寸、可导航、可放弃的形态被消费，系统永不因单个资源过大而失去响应性。
