# 03 资源内容类型与MIME协商机制

> 摘要：本文解析MCP资源体系中mimeType字段的语义、常用类型选型、自定义类型的扩展方式，以及客户端与服务端围绕内容类型进行协商与降级的工程实践。

## 一、mimeType的协议语义

在MCP的Resource元数据与resources/read返回的contents项中都存在可选的mimeType字段，它向客户端声明"这份内容以什么格式编码"。协议本身对取值不做强约束，遵循MIME规范（RFC 6839系列）的type/subtype形式。这个字段的战略价值在于：它把"内容"与"如何消费内容"解耦。客户端拿到一段文本后，是原样注入上下文、按Markdown渲染、解析JSON后摘要，还是交给专门插件展示，取决于类型声明而非猜测。缺失mimeType时，客户端通常按纯文本处理，这在JSON或二进制场景会直接导致体验劣化，因此服务端应尽量显式声明。

类型声明还影响token效率。对大模型而言，application/json的内容可以被客户端做结构化预处理（抽取关键字段、压缩空白），text/markdown可以保留结构注入，image/png则走多模态通道而非文本通道。同一个资源，类型声明正确与否，可能造成数倍token消耗差异。

## 二、常用类型选型表

| 内容形态 | 推荐类型 | 说明 |
|---------|---------|------|
| 自然语言文档 | text/markdown | 保留标题结构，利于模型分段理解 |
| 结构化记录 | application/json | 客户端可校验、摘要与字段裁剪 |
| 纯文本日志 | text/plain | 逐行注入，配合分页 |
| 图片资源 | image/png、image/jpeg | 多模态消费通道 |
| 二进制对象 | application/octet-stream | blob编码传输 |
| 结构化表格 | text/csv | 轻量且模型识别良好 |

选型的总体原则是"最具体的不撒谎的类型"：能用具体类型就不要用通配的octet-stream，能用text/markdown就不要含糊地写text/plain，同时绝不为讨好客户端而伪造类型。

## 三、自定义类型与参数化扩展

当内置类型不足以表达语义时，MIME允许使用vendor树扩展，例如`application/vnd.acme blueprint+json`，在subtype中同时携带厂商标识与结构化后缀。这样客户端即使不认识该厂商类型，也能借助`+json`后缀做兜底解析。配套纪律有三条：自定义类型必须在服务器文档与资源description中说明消费方式；必须提供到标准类型的降级路径（如同时可读为JSON）；不要用自定义类型包装本可用标准类型表达的内容，徒增客户端适配成本。

```json
{
  "contents": [
    {
      "uri": "db://crm/customers/8848",
      "mimeType": "application/json",
      "text": "{\"id\": 8848, \"name\": \"示例客户\", \"tier\": \"VIP\"}"
    },
    {
      "uri": "file:///logo/banner.png",
      "mimeType": "image/png",
      "blob": "iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAYAAAAfFcSJAAAADUlEQVR42mP8z8BQDwAEhQGAhKmMIQAAAABJRU5ErkJggg=="
    }
  ]
}
```

## 四、客户端协商与降级策略

服务端声明类型后，消费侧应实现分级的协商逻辑：第一步精确匹配，命中即走专门渲染器；第二步结构化后缀匹配，`+json`、`+xml`后缀触发通用解析器；第三步主类型匹配，`text/*`统一按文本注入并保留原始标记；最后兜底为octet-stream处理，展示元信息并允许用户手动下载或以十六进制预览。反向协商同样重要：客户端在读取前无法改变资源的编码，但可以在列表阶段依据mimeType过滤展示（例如只把文本文档纳入@引用候选），并在上下文预算紧张时优先裁剪低信息密度类型。测试环节应覆盖类型缺失、类型与实际内容不符、超大base64图片这三类脏数据，确保降级链路不崩溃。类型体系看似只是标注问题，实则是资源层可消费性的基石。
