# 06 资源URI规范：scheme选择、规范化与稳定性

> 摘要：本文讨论MCP资源URI的scheme命名空间选择、路径段编码与规范化规则、稳定性约束，以及可测试的URI治理流程。

## 一、scheme命名空间的选择

URI scheme是资源身份的第一语义层。MCP不维护中心化的scheme注册表，服务器拥有自定义scheme的命名自由，但这恰恰要求自律。选择scheme时有三条路径：复用标准scheme，file://、https://直接继承既有语义与工具链，适合内容确实以该形式存在的场景；使用领域惯用scheme，如git://、postgres://，借助生态心智降低理解成本；自造品牌scheme，如acme-crm://，适合聚合多数据源的统一投影层。自造scheme的命名应简短、全小写、含组织标识，避免与既有注册scheme冲突（可对照IANA注册表检查）。关键纪律是一个scheme一个语义：绝不在同一scheme下混装"文件、数据库、操作结果"等异质内容，否则客户端无法建立任何可靠假设。

## 二、路径段编码与规范化

路径段必须做百分号编码，保留字与空格不得裸露出现。规范化规则应在服务器内统一实现并在文档中公示：百分号编码统一大写或统一小写；空格编码为%20而非加号（加号仅是query编码惯例）；路径段内的斜杠必须编码为%2F以维持段结构；Unicode先用UTF-8再逐字节编码。两个等价写法若都接受，必须在入口归一化为同一规范形，否则同一资源会分裂出多个URI身份，破坏客户端去重、订阅与缓存。服务器可暴露规范化校验函数供测试使用：

```text
normalize("db://crm/Clients/欧阳%20公司") -> "db://crm/clients/%E6%AC%A7%E9%98%B3%E5%85%AC%E5%8F%B8"
assert normalize(u) == normalize(canonical_form(u))  # 幂等性
```

## 三、稳定性约束与版本演进

URI稳定性是客户端长期引用的基础。工程上应遵守：身份字段（主键、slug）进路径，投影字段（排序、字段裁剪、格式）进query；主键策略选用自然稳定键或可持久化的代理键，不用会漂移的自增序列重启值；URI一经公开即进入兼容性承诺范围，重命名必须提供旧URI到新URI的长期映射或过渡期。内容演进与URI演进分离：内容格式升级通过mimeType与内容协商完成，不轻易改动URI结构；确需结构变更时，采用"新路径并行+旧路径冻结只读+文档标注弃用周期"的三段式。任何变更都应记录在变更日志中，注明影响的URI模式。

## 四、URI治理流程清单

- 建立URI模式注册表：每个scheme下的路径模式、语义、负责人、引入版本；
- 新模式评审三问：是否与既有模式重叠？是否可被资源模板表达？五年后仍成立吗；
- 自动化一致性测试：全量资源URI经规范化后无重复，模式与注册表匹配率百分之百；
- 泄漏扫描：URI与query中不得出现密码、令牌、内部主机名；
- 文档同步：URI模式变更与客户端集成指南同一提交内更新。

URI是资源层的公共契约面，规范与稳定的URI体系能让订阅、缓存、引用等高级机制在无特判的前提下正确运转，其投入回报在整个MCP服务生命周期中持续复利。
