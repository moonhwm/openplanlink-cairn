# 01 MCP资源(Resource)核心语义与URI寻址模型

> 摘要：本文剖析MCP中资源作为"服务器可寻址、客户端可引用的只读上下文单元"的核心语义，并系统给出URI寻址模型的设计准则、典型映射模式与实现要点。

## 一、资源的定义与语义边界

MCP（Model Context Protocol，模型上下文协议）将资源定义为服务器暴露给客户端的只读数据单元，由统一资源标识符（URI）唯一寻址。资源的设计初衷是向大模型提供上下文：文件内容、数据库记录、API响应、日志片段、Schema文档等都可以被建模为资源。与工具（Tool）强调"执行动作、产生副作用"不同，资源在语义上是"被读取的上下文"，客户端读取资源后通常将其注入模型上下文窗口，而不触发外部状态变化。这一分工是MCP三大服务器原语（资源、提示、工具）中最基础的切分：资源管数据、提示管交互模板、工具管行为，三者互斥且合起来覆盖了"给模型看什么、怎么引导它、让它做什么"的完整问题空间。

资源的核心字段包括uri（唯一标识，必填）、name（人类可读名称）、description（语义说明）与mimeType（内容类型）。客户端在resources/list响应中看到的每一项都是这些元数据的集合，而真正的内容要靠resources/read按URI获取。换言之，列表阶段是"目录"，读取阶段才是"正文"，这种两段式设计让服务器可以用轻量元数据描述海量资源，而不必在列表时就把全部内容装载进内存，也为客户端的按需加载与缓存提供了天然切点。

## 二、URI寻址模型的设计准则

资源URI是整个资源子系统的主键，其设计直接决定客户端能否正确发现、引用和去重资源。工程上应遵循以下准则：第一，scheme必须语义化，例如file://表示本地文件、db://或postgres://表示数据库对象、api://表示远端接口投影，让客户端仅凭前缀即可推断内容来源；第二，路径应当体现资源层级，父路径是子资源的语义容器，便于客户端构建树状浏览视图；第三，URI一旦发布就应保持稳定，避免把自增ID、时间戳等易变值放进路径，防止客户端缓存的引用失效；第四，查询参数只承载筛选与视图参数，不承载身份信息，身份信息全部编码在路径段中。

```json
{
  "resources": [
    {
      "uri": "db://crm/customers/8848",
      "name": "客户 8848 档案",
      "description": "CRM系统中客户主档的完整记录",
      "mimeType": "application/json"
    },
    {
      "uri": "file:///reports/2026/q3-summary.md",
      "name": "三季度总结报告",
      "mimeType": "text/markdown"
    }
  ],
  "nextCursor": null
}
```

## 三、典型映射模式与实现要点

把既有系统映射为资源时有三种常见模式。文件系统映射最直接：目录对应集合资源，文件对应单项资源，URI直接复用路径；数据库映射常用"库/表/主键"三级路径，把一行记录建模为单项资源，把视图或查询结果建模为集合资源；REST映射则把远端GET端点投影为资源，注意只映射幂等读取类端点，POST类操作应交给工具而非资源。实现时还应处理三类边界：资源可能消失（读取时返回错误而非空内容）、资源可能巨大（需要分块或摘要策略）、资源可能敏感（默认不进列表、按需授权暴露）。

## 四、常见陷阱清单

- 把可变操作塞进资源语义，导致客户端缓存与订阅机制全部失真；
- URI中混入会话ID等临时状态，同一资源在不同会话呈现不同URI，破坏去重；
- 列表接口一次性返回全量内容而非元数据，造成启动风暴；
- mimeType缺省或与实际内容不符，客户端解码失败；
- 未对URI做规范化（大小写、百分号编码），同一资源出现多个等价URI。

遵循以上准则，资源层就能成为整个MCP服务端最稳定、最可复用的底座。
