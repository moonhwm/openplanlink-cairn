# 02 资源与工具的语义边界：何时暴露为资源而非工具

> 摘要：本文给出区分资源与工具的判定框架、四象限决策法与服务器实现层面的混合模式，帮助设计者在"数据"与"行为"之间划出清晰且可维护的边界。

## 一、为什么边界问题重要

MCP同时提供资源与工具两个原语，初学者最常犯的错误是语义错位：把只读查询做成工具、把带副作用的操作做成资源。语义错位的代价是系统性的。工具调用在客户端侧通常伴随用户确认与审计日志，而资源读取往往被自动注入上下文；若把敏感查询伪装成资源，就绕过了确认与审计；若把纯读取包装成工具，用户会被无意义的确认弹窗轰炸，交互成本陡增。更隐蔽的是缓存问题：客户端可以放心缓存资源内容，却绝不能缓存工具结果，语义错位会让缓存策略与失效机制全部建立在错误前提之上。因此边界划分不是风格问题，而是安全、性能与可审计性的共同基础。

判定本质上一句话：资源是"名词"，回答"模型可以知道什么"；工具是"动词"，回答"模型可以做什么"。读文件、查记录、取Schema是资源；发邮件、写数据库、触发部署是工具。

## 二、四象限决策法

用两个维度切分：是否有副作用（横轴）、是否需要参数化计算（纵轴）。第一象限（无副作用、静态数据）毫无疑问是资源，例如配置文件、文档段落。第二象限（无副作用、需要参数）优先用资源模板（ResourceTemplate）表达，例如`db://logs/{date}`按日期取日志，参数即URI变量，客户端可以在补全接口辅助下填写。第三象限（有副作用、需要参数）是典型工具，如`create_issue(title, body)`。第四象限（有副作用、无参数）仍应建模为工具，例如"立即同步"这类触发型动作。灰色地带是"重计算查询"：语义上只读但消耗巨大，此时建议仍用资源模板暴露，同时在服务器侧做限流与缓存，而不是为了限流把它改成工具。

```text
决策流程：
1) 调用两次结果是否一致且无外部状态变化？ → 否：工具
2) 是否：是 → 继续
3) 结果是否主要作为模型上下文被"阅读"？ → 是：资源/资源模板
4) 是否需要在读取前执行昂贵计算或聚合？ → 是：资源模板+服务端缓存
5) 客户端是否需要逐字引用其内容（如@引用）？ → 是：资源
```

## 三、混合模式：一个能力同时暴露两种视图

现实系统中常见同一数据源同时暴露资源与工具的情况，这不违反MECE，而是面向不同消费者的一体两面。例如代码仓库服务器：`repo://files/{path}`资源供客户端注入源码上下文；`search_code(query)`工具执行全文检索并返回命中片段。检索结果本质是计算产物，参数空间巨大且结果集动态，用工具表达更贴合"请求-执行-响应"的心智模型；而文件内容是稳定可寻址的，用资源表达才能享受订阅、缓存与@引用红利。设计混合模式时的纪律是：资源视图必须无副作用、可缓存、URI稳定；工具视图承担全部不确定性。两视图共享底层实现，但对外契约各自完整。

## 四、落地检查清单

- 逐项审计现有暴露面：每个只读工具是否应降级为资源模板；
- 敏感数据是否误入资源列表（应改为授权后动态暴露）；
- 工具描述中是否混入"获取/查询"类纯读动词，误导模型选择；
- 资源读取路径上是否存在隐式写操作（如读时计数器自增），若有则迁移或消除；
- 是否为同一数据维护了资源与工具双视图并保持描述一致。

边界清晰之后，资源层获得"安全地懒加载与缓存"的资格，工具层获得"严格确认与审计"的纪律，整套协议栈才能各司其职。
