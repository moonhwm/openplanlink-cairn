# 44 服务端资源缓存：版本戳、ETag式校验与条件读取

> 摘要：本文讨论服务器进程内缓存的进阶设计：版本戳的生成与传播、ETag式条件读取的实现语义、single-flight与结果复用窗口，以及缓存与上游变更流的对接。

## 一、版本戳的生成与传播

服务端缓存的核心账本是"每个缓存键关联的版本戳"。版本戳的生成有三种方式：继承式（上游自带版本号或修改时间，直接透传，最准确）；派生式（内容入库时计算哈希，以哈希为版本，适用于无版本概念的上游）；自增式（服务器在每次写路径挂钩时对键自增计数器，实现最简但依赖挂钩完备——任何绕过挂钩的写入都会造成版本漏更，是隐蔽缺陷源）。版本戳的传播路径要全覆盖：读取响应中附带（客户端据此做对账）、订阅通知后客户端探测时可比对、列表阶段对高敏资源可暴露档位信息。版本戳必须对"规范化内容"计算，否则无关字段的序列化差异（时间戳字段、键序）会造成假版本翻动，缓存与订阅双双抖动。

## 二、ETag式条件读取

条件读取把"变没变"的判定权收归服务器，省去传输整份内容。语义：客户端读取时携带已知版本（作为read请求的扩展参数或query约定），服务器比对当前版本——一致则返回精简的"未变更"响应（携带当前版本号），不一致则返回完整内容与新版本。这个语义与HTTP的ETag/If-None-Match同构，工程成熟度极高。实现要点有三：判定必须原子（比对与取内容在同一临界区内，否则竞态窗口内可能"判定未变但随即变更"）；未变更响应也要走完整的审计与限流（轻量不等于免检）；版本参数缺失时退化为无条件读取，保证老客户端兼容。条件读取的适用场景：订阅通知后的对账、客户端TTL到期的确认、轮询型消费的低成本高频率探测。

```text
read(uri, if_version=42):
    v, content = store.get(uri)
    if if_version == v:
        return { status: UNCHANGED, version: v }   # 精简响应
    return { status: OK, version: v, contents: content }
```

## 三、single-flight与结果复用窗口

服务器缓存必须配备两项并发机制。single-flight：同键的并发未命中请求合并为一次上游调用，其余请求挂起等待共享结果；挂起队列也要有超时与上限，上游慢时宁可让部分请求直接降级也不要无限堆积。结果复用窗口：对昂贵计算类资源（聚合、检索），设置短复用窗口（例如五秒），窗口内的重复请求共享同一结果并在响应中标注计算时间——窗口本质是"对新鲜度的显式让步"，换取上游保护。两项机制的开关与参数按资源计算成本等级配置，成本等级在资源注册时登记，动态性高的资源窗口趋零、成本低的资源窗口从宽。

## 四、缓存与上游变更流的对接

失效的黄金路径是上游变更事件直达缓存层：数据库的逻辑变更流触发行级键失效、文件监听事件触发文件键失效、远端webhook触发投影键失效。对接纪律：事件去重（同一版本的事件只失效一次，事件自带版本号时直接比对）；失败补偿（事件流断连时，重连后对该期间可能受影响的键做批量版本校验，而不是天真假设无变更）；顺序无关（失效操作幂等，乱序到达的多版本事件以最终全失效为准）。无法获得变更事件的上游，退化为周期性版本扫描（低峰时段批量校验版本戳）加保守TTL，并把"该家族无事件源"标注在资源元数据中，让客户端知道其新鲜度上限。

## 五、内存布局与失效执行

服务端缓存的工程细节决定其可靠性：键空间按资源家族分片（按前缀），失效与逐出可以按片操作；存储用字节不可变条目（内容序列化后的字节串加元数据头），替换即整条目换新，杜绝读写交错；失效队列与读路径解耦（失效事件先进队列，工作线程异步执行，洪峰时合并），但权限类失效必须同步执行（等不到异步，安全优先）。容量治理：全局内存上限、按家族配额、LRU加TTL双重淘汰，超限先淘汰复用窗口外与低频键。最后，把缓存层的命中率、失效队列深度、single-flight合并率接入监控，异常波动往往比业务告警更早暴露上游问题。
