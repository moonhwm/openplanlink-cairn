# 25 MCP提示(Prompt)核心语义：list/get与用户控制原则

> 摘要：本文阐述MCP提示原语的核心语义：prompts/list与prompts/get的接口结构、提示作为"用户控制的交互模板"的定位，及其与资源、工具的本质区别。

## 一、提示的定位与接口结构

MCP中的提示（Prompt）是服务器定义的可复用消息模板，设计定位是"用户主动选择的交互入口"，典型形态是斜杠命令：用户在客户端选中某个提示、填入参数，客户端调用prompts/get获得一组结构化消息，再将其作为对话起点交给模型。接口有两条：prompts/list返回提示目录（支持分页），每项含name、description、可选arguments声明；prompts/get按name与参数实参取回实例化结果。

```json
{ "method": "prompts/get", "params": {
    "name": "code-review",
    "arguments": { "language": "typescript", "diff_uri": "file:///d/1.diff" } } }

{ "messages": [
    { "role": "user",
      "content": { "type": "text", "text": "请审查以下TypeScript变更：\n……" } } ] }
```

返回结构的核心是messages数组：每条消息有role（user或assistant）与content（文本、图片或嵌入资源）。服务器通过预编排的角色序列引导对话开局，例如先assistant说明将如何处理、再user给出任务与上下文，形成比单条指令更丰富的模板语义。

## 二、用户控制原则

提示与工具的根本区别在控制权归属：工具由模型决定是否调用（模型主权），提示由用户决定是否使用（用户主权）。这一定位带来三条实现约束。客户端呈现：提示应作为显式UI元素（命令面板、斜杠菜单）供用户挑选，模型不会也不应"自动发现并执行"提示。用户确认：带参数的提示在执行前应让用户看到参数并确认，尤其是参数会触发资源读取或影响内容方向的场景。信任传递：提示内容以服务器作者的可信度背书进入对话，客户端应展示提示来源（哪个服务器）让用户知情。违背用户控制的实现（比如让模型枚举并调用prompts/get来"自我升级"）会造成权限模型混乱，是明确的反模式。

## 三、提示与资源、工具的协作

提示不是孤立原语，而是组合的粘合剂：prompts/get返回的消息中可以包含嵌入资源（EmbeddedResource形态，即直接内联资源内容）与资源引用，也可以在文本中引导后续工具使用。经典组合模式：code-review提示把diff作为嵌入资源带入、在模板中约定审查框架、模型随后自主调用只读工具探查更多上下文。这样三层分工清晰：用户选模板定方向、资源供上下文、工具做执行。服务器设计提示时应明确本提示的"资源依赖清单"（需要哪些URI）与"工具期望"（期望模型使用哪些工具），前者决定参数设计，后者写进模板文本的引导段。

## 四、实现要点与边界处理

实现层面的要点：arguments声明用JSON Schema风格描述每个参数的名称、描述、必选性，供客户端渲染表单与校验；未知提示名的get请求返回明确错误而非空结果；提示实例化应当无副作用（get本身只生成消息，不做业务动作）。边界处理包括：参数缺失必填项时提示明确错误；参数值进入模板必须转义防注入（详见安全专题）；提示返回的消息量也要考虑上下文预算，模板中嵌入大资源不如嵌入引用。提示是把"专业使用姿势"产品化沉淀的机制，服务器作者把领域工作流写成提示，用户一键复用，这正是MCP生态可组合性的体验支点。
