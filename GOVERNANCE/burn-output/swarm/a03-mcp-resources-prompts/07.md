# 07 资源元数据设计：name、description、mimeType与扩展字段

> 摘要：本文给出资源元数据四个核心字段的高质量编写规范、面向模型与面向人的双读者平衡策略，以及元数据质量的度量与回归方法。

## 一、name字段：短而可辨

name是资源在列表与UI中的第一呈现，设计目标是"在脱离上下文时可辨认"。规范上，长度控制在八十字符以内，避免截断；以内容主体开头而非修饰语开头，例如"客户8848档案"优于"关于客户8848的完整档案记录"；同类资源保持命名公式一致，让用户在列表中可模式化扫读；不要内嵌URI、ID之外的技术噪声（如内部表名、机器代号）。当资源来自资源模板实例化时，name应体现参数值，例如"订单ORD-2041的物流轨迹"，让用户不必展开即可判断相关性。name不做唯一性承诺，唯一身份永远由uri承担，因此切不可用name做去重键或外键。

## 二、description字段：写给两个读者

description同时服务两类读者：浏览列表的人类用户，以及决定是否读取该资源的模型。面向人类，要说清内容范围与时效；面向模型，要包含可检索的关键词与使用前提。推荐的四要素写法：是什么（内容概述）、覆盖什么（范围与粒度）、何时有用（适用问题类型）、有何限制（敏感级、更新频率）。长度以一到三句为宜，过短丧失信息量，过长污染列表视图。反模式包括：与name完全重复；堆砌营销形容词；嵌入会过期的统计数字（"共3,204条"这类应放入内容而非描述）。

```json
{
  "uri": "db://wiki/runbooks/payment-timeout",
  "name": "支付超时处置手册",
  "description": "支付网关超时告警的标准处置流程，覆盖诊断顺序、回滚步骤与升级路径；适用于支付链路告警响应场景，每周由SRE复核更新。",
  "mimeType": "text/markdown"
}
```

## 三、mimeType与扩展字段

mimeType的编写规范在前文类型专题已详述，此处强调元数据视角的一致性：同一资源模式必须声明同一类型；类型随内容版本演进时，在变更日志中登记。除协议标准字段外，服务器常有扩展诉求，例如暴露内容大小、最后更新时间、所属业务域。扩展字段的实施纪律：优先放进description的自然语言中而非私造协议字段，保证所有标准客户端可见；确需结构化时，使用带命名空间前缀的自定义字段并在文档声明，绝不占用保留字段名；扩展信息不得与标准字段矛盾。这样既满足富元数据需求，又不破坏协议互操作性。

## 四、元数据质量度量与回归

元数据是"写给未来的检索索引"，需要工程化的质量保障。可建立四项度量：覆盖率，mimeType与description的填充比例；一致性，同模式资源的name公式一致率；新鲜度，description中陈述性内容与实际的偏差率；有效性，客户端实际读取行为与description的相关性（可通过"列表曝光后未被读取的占比"间接观测）。回归手段包括：CI中跑元数据lint规则（长度上限、禁词表、公式校验）；抽样人工评审纳入发布检查单；把"模型能否仅凭元数据正确选择资源"作为集成评测用例。元数据投入小、杠杆大，是资源层性价比最高的质量工程。
