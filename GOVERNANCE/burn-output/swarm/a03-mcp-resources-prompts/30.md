# 30 提示执行中的进度报告与取消语义

> 摘要：本文讨论prompts/get长耗时执行时的两项协作机制：基于进度令牌的进度通知流，以及客户端发起的取消通知，覆盖参数设计、实现模式与边界场景。

## 一、为什么get也需要进度与取消

prompts/get通常被理解为轻量的模板渲染调用，但在严肃的生产实现中它可能相当重：提示实例化要读取多个资源（远端API、大文件），要做参数化的数据聚合，甚至触发一次预计算（把当时的数据快照固化进模板材料）。这类get的耗时可能达到数秒到数十秒，用户面对无反馈的等待会重复点击、误判卡死。MCP的通用机制——进度令牌与取消通知——因此同样适用于get路径：请求参数中携带progressToken，服务器在执行过程中周期性发出进度通知；用户放弃等待时，客户端发出取消通知，服务器终止剩余工作并释放资源。把这两项机制引入提示执行，是提示从"演示级模板"走向"生产级工作流"的分水岭。

进度令牌的传递方式是在get请求的params中附带_progressToken字段（实现上通常以保留字段或元参数形式出现），客户端负责生成与跟踪该令牌。服务器发出的每条进度通知都引用令牌，携带progress（当前进度）、total（可选总量）与message（人类可读的阶段描述），例如"正在拉取近三十天指标，约完成七成"。客户端把这些通知转译为进度条或阶段文案，用户的等待就从黑箱变成了可感知的过程。

## 二、进度通知的实现模式

服务端实现进度上报的推荐模式是"阶段化任务图"：把get的执行分解为若干阶段（校验参数、读取材料A、读取材料B、组装模板），每个阶段开始与结束时上报，进度值按阶段权重映射到零到一百的区间。材料读取类的异步步骤，在全部并发完成后统一推进，避免多路进度来回跳动。上报频率要有节流，长阶段内部每隔固定时间或固定工作量上报一次即可，高频通知只消耗带宽不增加信息量。message文案面向用户而非开发者，写"正在获取销售数据"而不是"GET /api/sales 200"。

```json
{ "method": "notifications/progress",
  "params": { "progressToken": "pt-17", "progress": 40, "total": 100,
              "message": "已取得会议名录，正在读取最长的一份转写……" } }
```

## 三、取消通知的语义与实现

取消在MCP中以notifications/cancelled通知实现：客户端携带被取消请求的id与可选的reason发出，服务器收到后应尽快终止该请求的处理，并以该id返回一个错误响应（如请求被取消的错误码），让等待端的状态机闭合。实现纪律有五条。取消是协作式的：服务器必须主动检查取消标志（阶段边界检查令牌注册表），协议没有抢占式杀线程的能力，长循环内部要留检查点。资源回收：取消后要清理已建立的中间状态——半开的上游连接、临时缓存、进度令牌注册项。幂等与竞态：取消到达时请求可能已完成，此时忽略取消并正常返回结果即可，不能因迟到取消而报错。客户端侧：发出取消后仍要等待服务器的终结响应才算关闭，UI立即置为"已取消"但底层等待静默完成。审计：取消事件记录频次，某提示的取消率异常高通常意味着执行过慢或默认参数不合理，是产品信号而非噪声。

## 四、边界场景与体验设计

边界场景有三个值得专门设计。第一，不可取消段：某些上游调用一旦发出不可中止（副作用型预计算），服务器应上报"进入不可取消阶段"的进度消息，客户端把取消按钮降级为"在后台继续"。第二，取消后的结果丢弃：若材料已读齐、模板已组装完毕，取消到达在返回前一瞬，直接返回结果比强行丢弃更友好，取消语义以"用户不再等待"为准而非"结果必须销毁"。第三，进度缺失兼容：老服务器不支持进度，客户端的等待界面要有无限期的阶段文案兜底（"正在准备，可能需要一些时间"），并对超长等待提供主动取消。体验设计上，进度与取消是同一枚硬币的两面：只有进度没有取消，用户被锁死在等待里；只有取消没有进度，用户不知道该不该取消。两者齐备，长耗时get才配得上"专业工具"的体验标准。
