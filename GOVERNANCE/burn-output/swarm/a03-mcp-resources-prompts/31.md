# 31 completion/complete：提示参数自动补全机制

> 摘要：本文讲解MCP的补全原语completion/complete：请求结构中ref对提示与资源模板的双目标引用、补全值的返回契约、服务端实现策略与客户端交互设计。

## 一、补全原语的定位与请求结构

参数化交互的最后一公里是输入辅助：用户在提示参数表单里打出" Olym"希望直接补出"Olympia"，在资源模板参数里输入日期前缀希望看到候选列表。MCP为此定义了补全能力，服务器可选实现completion/complete方法。它的请求结构由三部分组成：ref（补全目标引用，指向某个提示或某个资源模板）、argument（正在输入的参数名与当前已输入的值）、补全上下文（其余参数的已填值，供服务器做依赖型补全）。ref有两种形态：指向提示时为{name: "提示名"}，指向资源模板时为{uriTemplate: "模板串"}。这种双目标设计让同一套补全交互同时服务提示表单与资源URI构造器，客户端只需一套下拉逻辑。

```json
{ "method": "completion/complete", "params": {
    "ref": { "type": "ref/prompt", "name": "summarize-meeting" },
    "argument": { "name": "transcript_uri", "value": "file:///meetings/09" },
    "arguments": { "style": "brief" } } }

{ "completion": { "values": [
    "file:///meetings/0922-product.md",
    "file:///meetings/0921-design.md" ],
  "total": 2, "hasMore": false } }
```

## 二、返回契约与补全质量

响应的completion对象包含values（候选值数组）、total（候选总数）、hasMore（是否还有更多）。客户端据此渲染下拉，hasMore为true时展示"继续输入以缩小范围"的提示。契约层面有三条隐含规则：values必须已经过前缀过滤（服务器只返回与当前输入匹配的项，不做客户端再过滤的假设）；排序即推荐（首位是服务器认为最可能的项，客户端默认高亮首位）；补全值必须是"填入后合法"的完整值（补全日期参数时返回完整日期而非片段），客户端填入后无需二次加工。质量层面，好的补全遵循"最近使用优先、高频优先、依赖感知"的组合排序：用户上周用过三次的会议文件排在字典序前面；当style参数为detailed时优先返回转写质量更高的文件。补全还必须克制数量：默认返回十项以内，匹配过多时靠hasMore引导用户继续输入，超长下拉等于没有补全。

## 三、服务端实现策略

实现补全的推荐架构是"候选源管道"：静态源（枚举、目录）、历史源（该用户最近使用记录）、语义源（按参数相关性检索）。管道依次查询、合并、按策略排序、截断。工程纪律包括：每请求设硬超时（如两百毫秒），补全是打字间交互，慢补全不如无补全，超时返回已收集的部分结果加hasMore；候选查询必须走索引而非全表扫描，输入前缀天然适合前缀索引；权限过滤内置——补全候选必须与最终校验同一套授权，用户在候选里看到无权项、提交时被拒是最糟糕的体验；频率限制防滥用，补全接口的高频特性使它成为最容易被刷的端点。

## 四、客户端交互设计与降级

客户端的补全交互设计有五个要点。触发时机：输入停顿约一百五十毫秒后发起（防抖），避免每键一请求。呈现方式：下拉浮层，支持键盘上下选择与回车确认，Esc关闭且不改动已输入内容。渐进披露：候选含说明时悬浮展示来源，帮助用户理解为什么出现这个建议。失败静默：补全请求失败绝不打断输入，直接不显示下拉即可——补全是增强而非依赖。降级路径：服务器未实现complete方法（能力位未声明或返回方法不存在）时，客户端回退到本地历史补全（该参数的最近输入记录）或纯手输。补全机制看似小功能，但它决定了参数化提示在真实用户手中的填表效率，是服务器实现完整度的重要分水岭，值得像主路径一样认真测试：前缀匹配正确性、排序稳定性、权限一致性、超时部分返回、空结果不报错。
