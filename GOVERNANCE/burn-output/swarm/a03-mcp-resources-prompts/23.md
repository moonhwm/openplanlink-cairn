# 23 能力协商中的resources能力声明与降级策略

> 摘要：本文解析初始化握手中capabilities.resources的能力位语义（subscribe、listChanged），讨论客户端依据能力位构建功能矩阵与多档降级策略的方法。

## 一、能力位的语义

MCP连接建立时的initialize握手中，服务器在capabilities对象里声明自己支持的可选特性，资源相关的能力位有两个。subscribe：为true表示服务器支持resources/subscribe与updated通知，客户端可以建立订阅；缺省或false则客户端只能轮询。listChanged：为true表示服务器会在资源列表结构变化时发送notifications/resources/list_changed，客户端可以缓存列表并增量刷新；否则客户端必须把列表视为易变，每次都重新拉取。能力声明是单向的服务器自我描述，客户端据此裁剪自己的行为：未声明的能力绝不调用，声明了的能力也只作为可用性依据而非质量承诺（例如订阅可能对特定URI失败，仍需读取层兜底）。

```json
{
  "capabilities": {
    "resources": { "subscribe": true, "listChanged": true },
    "prompts": { "listChanged": true }
  }
}
```

## 二、客户端功能矩阵

客户端应把能力位编译成内部功能矩阵，每个功能标注依赖的能力位与降级路径。资源领域的典型矩阵：实时刷新功能依赖subscribe，降级为自适应轮询；目录缓存功能依赖listChanged，降级为短TTL重拉或用户手动刷新；@引用的基础功能无能力依赖（list与read是必备方法），任何合规服务器可用；模板填充功能依赖templates/list返回非空。矩阵的价值在于让产品功能与协议能力解耦：功能设计时声明理想路径与可接受路径，运行时按握手结果自动选择，用户无需感知服务器档位差异。矩阵还应处理版本维度：不同协议版本引入的特性（如补全接口）要结合协商出的版本号共同判定。

## 三、降级策略设计

降级策略有三条设计原则。平滑性：降级后用户体验等价或可接受，而非功能消失——轮询替代订阅时保持界面同样"自动更新"，只是频率受限；订阅失败（特定URI不支持）时静默回退到该URI的轮询，其余订阅不受影响。透明性：降级状态对用户与日志可见，至少在诊断面板标明"当前为轮询模式，刷新间隔X秒"，避免把性能问题排查引向错误方向。资源纪律：降级路径自身要节约——轮询间隔按资源dynamicity分级（静态资源分钟级，动态资源秒级封顶），并随页面不可见状态暂停。能力位变化（重连后能力缩水）时，客户端必须重新评估矩阵，果断关闭相应功能，不做任何"试探性调用"。

## 四、服务器侧的能力演化

服务器演化能力集时要遵守兼容纪律：新增能力位是安全变更，老客户端忽略未知字段即可；撤回能力位是破坏性变更，需要版本协商与过渡期。实现上建议能力位与真实支持严格对齐——声明了subscribe就必须对全部可订阅URI工作，部分支持的实现宁可拆分为按URI的运行时反馈（订阅报错触发客户端局部降级），也不要虚标。测试矩阵应覆盖"能力组合×客户端功能"的交叉验证：无subscribe、无listChanged、双缺省、双全开四种服务器与功能矩阵的匹配，确保每格行为符合设计。能力协商是MCP生态多样性的润滑剂，严谨的双向配合让新旧服务器与客户端能够安全共存。
