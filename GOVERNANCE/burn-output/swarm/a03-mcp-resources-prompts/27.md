# 27 提示参数设计：JSON Schema、必选与可选

> 摘要：本文系统讲解MCP提示的arguments声明机制：参数的结构化描述方法、必选与可选的取舍原则、参数校验与默认值策略，以及面向客户端表单渲染的描述工程。

## 一、arguments声明的结构与语义

提示的参数声明位于提示对象的arguments数组中，每一项包含三个字段：name（参数名，客户端提交时的键）、description（参数语义说明，渲染表单时的标签与提示文案）、required（是否必选，缺省视为可选）。这套声明的本质是一份轻量JSON Schema：它告诉客户端"这个提示吃哪些参数、每个参数是什么意思、哪些不填就不能用"。声明质量的直接产物是客户端的参数表单——description写得好，用户不需要文档就能正确填写；声明缺失或含糊，用户面对裸输入框只能猜测。协议要求客户端在prompts/get时提交arguments对象，键为参数名、值为字符串，未声明的额外键应由服务器宽容忽略或明确拒绝，二选一并保持一致。

```json
{ "name": "summarize-meeting",
  "description": "把会议记录整理为决议、待办与风险三段摘要",
  "arguments": [
    { "name": "transcript_uri", "description": "会议记录资源的URI，如 file:///meetings/0922.md",
      "required": true },
    { "name": "style", "description": "摘要风格：brief（三行内）或 detailed（含发言归属）",
      "required": false }
  ] }
```

## 二、必选与可选的取舍原则

必选参数是"没有它提示无法执行"的硬依赖：缺少转写内容的会议摘要、缺少目标语言的翻译请求都属此类。可选参数是"改变行为但不决定可行性"的调节旋钮：风格、篇幅、侧重。设计时的取舍原则有四条。第一，必选宜少：每增加一个必选参数，用户完成表单的摩擦就多一分，理想状态是一个必选参数加两到三个可选参数。第二，必选参数应该承载"内容寻址"而非"格式偏好"：指明要处理什么（URI、ID、日期）是必选，说明怎么处理（风格、粒度）是可选。第三，可选参数必须有稳定的默认行为，并在description中写明默认值是什么，让"不填"成为显式可预期的选择而非未知行为。第四，参数之间存在依赖时（选了advanced就必须提供token），在description中说明依赖关系，复杂依赖则考虑拆分为两个提示，不要让一个提示的参数空间变成迷宫。

## 三、参数校验与错误反馈

服务端在prompts/get入口必须执行三层校验。结构层：必选齐全、类型为字符串、键名已知；缺失必选项返回结构化错误并指明缺哪个参数，错误消息直接可展示给用户。值域层：对有格式约定的参数做校验——URI参数先做语法解析再验证scheme是否在本服务器域内，日期参数校验格式与范围，枚举参数校验取值集合；非法值返回错误及期望格式的说明。语义层：参数指向的对象是否存在（URI对应的资源能否读取）、当前主体是否有权访问。三层校验的错误码与文案分层设计，结构错误可以由客户端预拦截（依据声明做前端校验），值域与语义错误只能服务端裁决。所有校验都必须在模板插值之前完成，绝不把未校验的参数直接拼进提示文本。

## 四、面向表单渲染的描述工程

arguments声明是客户端渲染输入控件的全部依据，description工程因此有具体规范：写清楚取值形态（"ISO日期，如2026-09-22"、"资源的URI，可从@选择器粘贴"）、给出示例、说明默认行为（"留空时使用brief风格"）、标注依赖（"仅当detail模式需要"）。客户端侧的配合实现包括：依据description关键词启发式选择控件（含"URI"字样则提供资源选择器，含枚举说明则渲染下拉）；提交前本地预校验（必选非空、格式粗检）以减少往返；错误回显把服务端错误定位到具体输入框。进阶的参数设计还可以借助补全接口（completion/complete）为参数提供动态建议，这将在专门章节展开。参数是提示与用户之间的表单契约，声明严谨、校验分层、描述面向真人，三者齐备，提示才能在陌生用户手中即开即用。
