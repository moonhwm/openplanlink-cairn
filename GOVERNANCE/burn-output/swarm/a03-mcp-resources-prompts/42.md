# 42 订阅驱动的缓存失效：updated通知与重新读取

> 摘要：本文深入订阅机制与缓存的联动：updated通知作为失效信号的消费流程、版本对账免重读优化、通知风暴的抑制手段，以及无订阅能力时的失效替代方案。

## 一、通知到缓存失效的标准流程

订阅驱动的失效是MCP资源缓存最优雅的形态：客户端订阅其缓存的资源，updated通知即该缓存键的失效信号。标准消费流程分五步：收到通知，标记对应缓存键为stale（不立即删除，旧值在重读成功前仍可服务降级）；按需或立即触发重读（策略取决于该资源的消费紧迫度：界面可见立即读，后台关注懒读）；重读时携带版本对账（见下节）；读取成功则以新内容与新版 本替换缓存并解除stale；读取失败则保留旧值并延长标注"获取更新失败，当前展示可能过期"，进入退避重试。流程的关键纪律是"先标记后处理"：通知处理必须是异步非阻塞的，通知到达的瞬间只做标记，重读排队执行，防止通知洪峰直接转化为读取洪峰。

## 二、版本对账与免重读优化

updated通知不携带内容也不携带版本，朴素实现下每次通知都触发一次全量重读。但很多通知是"抖动"——内容实际未变（同一版本重复广播、无效字段更新、订阅系统的周期性心跳）。版本对账机制把重读变成两段式：轻量请求只取当前版本号（协议内的实现可以是带版本提示的read，由服务器在未变化时返回精简响应；或利用内容内嵌的版本字段），版本未变则免重读直接确认缓存，版本已变才拉取全文。免重读的收益在高频变更资源上尤为显著：队列深度类资源每秒变化，但订阅者真正需要的是秒级最新值，合并窗口内的多次通知用一次版本对账加一次内容读取即可覆盖。实现上服务器应支持"版本未变返回轻量响应"的读取形态，客户端则把版本对账作为重读的前置步骤默认开启。

```text
on_updated(uri):
    mark_stale(uri)
    enqueue(()->{
        v = probe_version(uri)          # 轻量版本探测
        if v == cache[uri].version:     # 抖动
            unmark_stale(uri); return
        content = read(uri)             # 确实变了，全量读取
        cache[uri] = (v, content); unmark_stale(uri)
    })
```

## 三、通知风暴的抑制

三类场景会产生通知风暴，需要分级抑制。批量变更风暴：服务器一次导入影响数千URI，逐条广播形成风暴；服务器侧做窗口合并（五十毫秒内同子树的变更合并为父级目录的一条通知），客户端侧对同批通知去重排队。级联重读风暴：一条通知触发一次重读，若重读本身是昂贵操作（触发服务器再计算），几千订阅者的重读就是自我DDoS；对策是服务器读取路径的结果复用窗口（同键并发与短窗内请求共享一次计算）加客户端重读的随机延迟抖动。回声风暴：客户端读取引发的间接变更（读取计数器类副作用，虽是反模式但存在于遗留系统）再次触发通知形成回环；识别特征是通知间隔与重读延迟强相关，根治靠消除读路径副作用，缓解靠通知去重阈值。

## 四、无订阅能力时的替代失效

服务器未声明subscribe能力时，客户端缓存只能依赖替代失效机制，按可靠性排序：TTL轮询（按资源声明或历史观测的变更频率设定TTL，到期后后台刷新，主流程先服务旧值）；读时校验（每次消费前做轻量版本探测，未变免读）；用户触发刷新（界面提供刷新按钮并把"数据可能非最新"的提示常态化）。替代机制的组合原则：TTL做兜底、读时校验做精确化、用户触发做逃生门。还要处理能力漂移：重连后服务器能力变化（原支持订阅现在不支持）时，客户端必须检测并降级到替代机制，缓存标记从"订阅保证"改为"TTL保证"，且这种降级要在诊断面板可见。

## 五、一致性与体验的平衡

订阅失效的最终目标是体验：用户看到的关键数据"足够新"且系统负担可控。实践配置建议：可见性分级——界面焦点资源立即重读、次可见资源懒重读、后台关注TTL化；陈旧度可见——stale期间UI轻标注"更新中"，失败则标注"可能过期"；预算封顶——单客户端每秒重读上限，超限请求排队，宁可晚新不可打死。把这三条做成缓存模块的默认策略，订阅驱动的失效就能在正确性与体验之间长期稳定运行。
