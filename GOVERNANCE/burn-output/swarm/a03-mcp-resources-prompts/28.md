# 28 提示消息角色模型与多轮模板

> 摘要：本文分析prompts/get返回的messages数组中role字段的语义力量：user与assistant两种角色的编排语法、多轮模板的设计模式，以及角色序列对模型行为的引导机制。

## 一、角色是模板的语法成分

提示返回的每条消息都携带role字段，取值为user或assistant。多数实现只用一条user消息装下全部内容，这其实浪费了角色序列的表达力。在对话模型的训练分布中，user消息天然携带"请求与材料"的语用，assistant消息携带"承诺、框架与自述"的语用。模板作者可以利用这种语用差异做精细引导：assistant消息在前的开场白会让模型在续写时保持与"自己说过的话"一致的立场，适合固定方法论的场景；user消息分段铺垫材料与任务，比一股脑塞进单条消息更利于模型分区注意。角色因此不是可有可无的元数据，而是模板的语法成分，编排角色就是在编排模型开局的心理状态。

典型的双角色开场如下：assistant消息声明"我将按结构、安全、性能三个维度审查代码，每个维度给出严重度分级"，随后user消息给出diff材料与具体要求。模型接续对话时，会自觉维护assistant已经承诺的框架，输出结构显著更稳定。这种"自承诺"技巧比在user消息里写"请按三维度审查"更有效，因为它借用了模型对自身发言的强一致性倾向。

## 二、多轮模板的编排模式

messages数组本质是一个微型剧本，常见编排有五种模式。单轮指令式：一条user消息，简单直接，适合轻量任务。材料前置式：数条user消息依次铺材料（每条配一行标签），最后一条下达任务；材料的分区让模型能按标签检索引用。框架承诺式：assistant先承诺处理框架，user再给材料；如上所述强化输出结构。示范引导式：user给出任务，assistant给出一个精简的正确示例片段，user再要求"按此风格继续处理其余部分"；少样本示范被拆进角色结构里。分段递进式：多条user消息构成渐进任务（先理解、再分析、后输出），配合"在收到下一步指令前不要输出最终答案"的节流语句，适合需要链式思考的复杂任务。

```json
{ "messages": [
  { "role": "assistant",
    "content": { "type": "text",
      "text": "我将按结构、安全、性能三个维度审查代码变更，每个维度标注严重度并提出修改建议。" } },
  { "role": "user",
    "content": { "type": "resource", "resource": { "uri": "file:///d/1.diff", "text": "……" } } },
  { "role": "user",
    "content": { "type": "text", "text": "请开始审查，输出为Markdown表格加总结。" } } ] }
```

## 三、多轮模板的设计纪律

编排角色序列要遵守四条纪律。第一，结尾必须是user：模型响应的是最后一条user消息，任何以assistant结尾的模板都会让模型陷入"接着自己的话往下说"的续写模式而非任务模式。第二，assistant消息保持克制：自承诺只写框架与维度，不写具体结论，否则等于替模型完成了一半任务，还会在结论错误时把错误固化进对话。第三，角色不冒充身份：assistant开场白不得伪装成系统消息或平台公告（如"系统提示：……"），这类伪权威写法破坏信任边界且可能被安全策略拦截。第四，消息数量适度：超过六七条消息的开局剧本维护成本高、调试困难，复杂工作流应交给提示加工具组合，而不是无限加长模板。

## 四、调试、测试与演化

多轮模板的行为需要工程化验证。固定参数的回归测试：对同一组参数运行get，断言消息序列、角色分布与关键锚点文本稳定；模板是代码，改动必须有版本与评审。行为评测：把模板产出的开局交给目标模型，检查模型首轮响应是否符合模板设计的框架（三维度是否都被覆盖、表格格式是否遵守），用脚本化断言覆盖七成以上结构特征即可捕捉大部分回归。参数扰动测试：必选参数缺失、可选参数组合变化时，模板分支是否都产出合法消息序列。演化策略上，模板文本的微调（措辞、顺序）可高频进行，角色结构变更（增删assistant消息）应视为行为变更，需要重跑行为评测。角色模型是提示原语中最容易被忽视的能力，用好它，同样的参数与材料能换来看得见的输出质量差异。
