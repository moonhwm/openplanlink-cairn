# 02 Tool的输入输出契约：JSON Schema在MCP中的角色

## 一、契约优先的设计观

在MCP体系中，每一个工具都通过一份JSON Schema向外界声明自己的输入契约。这份Schema不是文档附注，而是协议的一等公民：客户端依据它构造调用请求，服务器依据它校验参数，模型依据它理解"该传什么、怎么传"。契约优先的含义是：先把Schema设计清楚，再写实现代码。经验表明，先写代码后补Schema的团队，往往产出口径含糊的参数定义，模型调用时频繁出现参数类型错误与幻觉字段，事后再修Schema又要面对兼容性包袱。

JSON Schema在MCP中承担四重角色。第一是描述角色，把人类语言难以精确表达的参数约束翻译成机器可读的结构；第二是校验角色，服务器端可以基于同一份Schema做入参校验，拒绝畸形请求；第三是引导角色，模型在生成参数时会参考Schema中的类型、枚举与必填约束，从而显著降低无效调用率；第四是演进角色，Schema的版本变化构成工具版本化讨论的基础，后续章节会展开。

## 二、输入契约的构成要素

一份规范的inputSchema至少包含类型声明、属性定义、必填清单三部分。MCP约定顶层必须是object类型，即所有参数都通过命名属性传入，这与JSON-RPC的位置参数风格形成对照。命名参数的好处是模型生成时不容易错位，也便于后续无痛新增可选参数。

```json
{
  "name": "create_task",
  "description": "在指定项目中创建一个任务，返回任务ID。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "project_id": {
        "type": "string",
        "description": "目标项目标识，形如 prj_ 前缀加12位随机串"
      },
      "title": {
        "type": "string",
        "description": "任务标题，不超过120个字符"
      },
      "priority": {
        "type": "string",
        "enum": ["low", "normal", "high"],
        "description": "优先级，默认 normal"
      },
      "due_date": {
        "type": "string",
        "description": "截止日期，ISO 8601 格式，如 2026-09-30"
      }
    },
    "required": ["project_id", "title"],
    "additionalProperties": false
  }
}
```

上述示例体现了几个要点：每个属性都有description，枚举值封闭了取值空间，必填清单最小化，additionalProperties设为false以杜绝幻觉参数。description写得越具体，模型犯错的概率越低，例如"形如 prj_ 前缀"这样的提示能引导模型不再凭空编造标识格式。

## 三、输出契约的结构

工具的输出同样需要契约化思维。MCP的tools/call返回结果由两部分组成：一是面向模型消费的content数组，其中每一项带有MIME类型，常见的是text/plain文本；二是面向客户端程序化处理的structuredContent对象，它应当是输出Schema（outputSchema）的一个实例。为工具声明outputSchema后，服务器返回的结构化内容就有了稳定形态，客户端可以做类型检查、结果路由与自动渲染，而不必解析自然语言。

设计输出内容时要遵循"模型友好"原则：文本内容应当简洁、信息密度高，把最关键的结论放在开头；大块数据不要全量塞进text，而应放入structuredContent或以资源引用的形式返回。一个常见的反例是把整张表格序列化为上千行文本返回，直接把上下文窗口占满。合理做法是文本只返回摘要与统计，明细交给结构化字段或资源。

## 四、错误也是契约的一部分

错误输出必须与成功输出一样被认真设计。MCP区分两类错误：一类是协议层错误，通过JSON-RPC错误返回，表示请求本身不合法或服务器崩溃；另一类是工具执行错误，通过结果中的isError标志返回，表示工具正常被调用但业务执行失败。面向模型的设计应尽量使用后者，因为isError结果中的文本会进入模型上下文，模型可以读到失败原因并自行重试或修正参数。错误文本要写清楚三件事：发生了什么、原因是什么、建议怎么改，例如"项目不存在：prj_xxx 未找到，请先调用 list_projects 获取有效项目ID"。这种"可恢复错误"的设计，把一次失败转化为模型的下一次正确尝试。

## 五、契约设计核对清单

落笔Schema前，建议按以下清单逐项自查：

- 顶层类型是否为object，参数是否全部命名化。
- 每个属性是否都有description，格式示例是否具体。
- 必填参数是否压缩到最小集合，可选参数是否给出默认行为说明。
- 取值空间能否用enum、pattern、minimum等约束封闭。
- 是否设置additionalProperties为false并声明additionalProperties错误提示。
- 输出是否区分text摘要与structuredContent明细，是否声明outputSchema。
- 错误返回是否使用isError加可读文本，而非直接抛协议错误。
- Schema与实现代码是否同源生成，避免两处维护产生漂移。

## 六、契约与实现的同源管理

契约最大的敌人是漂移：Schema写的是一套，实现做的是另一套。破解之道是让契约成为唯一事实源。实践中可选三条路径。路径一是Schema先行，即先在独立文件中维护Schema，代码从Schema生成参数解析与校验逻辑，任何修改都先改Schema再同步生成。路径二是代码先行，即在实现中以类型注解或配置形式表达参数，再由构建脚本导出Schema，注册工具时直接使用导出结果。路径三是双向校验，即单元测试中对每个工具跑一组正例与反例，正例必须通过校验，反例必须被拒绝，把契约的执行纳入持续集成。无论选择哪条路径，都应杜绝"文档里一份Schema、代码里另一份判断"的双头维护。

还要注意Schema方言问题。JSON Schema存在多个草案版本，不同客户端对format、oneOf等关键字的支持程度不一。面向互操作的工具应尽量使用各草案交集内的关键字，避免依赖冷门特性，并在服务器自测时至少用两种主流校验器各跑一遍，确保行为一致。

## 七、小结

JSON Schema是MCP工具与世界沟通的法律文本。输入契约约束模型如何构造请求，输出契约为客户端提供可编程的稳定接口，错误契约为模型提供自我纠错的通道。三者合一，工具才从"能调用的函数"升级为"可信赖的系统能力"。同时，契约必须与实现同源管理，防止漂移侵蚀其权威性。下一篇将深入参数类型的选择与组合策略。
