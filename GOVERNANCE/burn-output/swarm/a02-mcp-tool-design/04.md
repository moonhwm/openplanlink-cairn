# 04 面向LLM的工具设计原则：可发现性、可理解性与Token经济

## 一、使用者是模型的特殊性

传统API的设计者面向的是人类程序员：他们读文档、写示例、调试代码，具备强大的容错与推理能力。MCP工具的使用者是大型语言模型，它通过上下文窗口一次性"看到"所有工具的清单与Schema，在几十次推理轮次内完成选择与调用。这带来三个根本差异：第一，模型对工具的理解完全来自清单文本，没有外部文档可翻；第二，模型的注意力有限，工具越多、描述越长，选择准确率越低；第三，模型的输出是概率性的，模糊的Schema必然放大幻觉参数。因此面向LLM的工具设计，本质上是在为一位"读过一次说明书就要上岗"的操作员编写说明书。

由此推导出三大原则：可发现性（模型能找对工具）、可理解性（模型能用对参数）、Token经济（说明书本身不构成负担）。三者层层递进，共同决定工具集的调用成功率。

## 二、可发现性原则

可发现性要求模型在众多工具中快速锁定正确目标。落地方法有四条。其一，工具按业务域分组命名，用前缀制造语义聚类，例如db_query、db_migrate、db_stats，模型在搜索记忆时更容易联想到同族工具。其二，名称自解释，避免缩写与内部黑话，search_customer_orders远好于scq。其三，对语义相近的工具，在description中显式写出差异与选择条件，例如"按邮箱精确查找用find_user_by_email，模糊搜索用search_users"。其四，控制工具总数，一个服务器暴露上百个工具时，模型的选择错误率显著上升，应当裁剪、合并或按需动态暴露。

```text
工具清单占用估算（示例）：
每个工具平均占用 = 名称(约10 token) + 描述(约60 token) + Schema(约150 token)
50个工具 ≈ 11000 token 常驻上下文
结论：低频工具应从静态清单移除，改为搜索式发现
```

## 三、可理解性原则

可理解性要求模型不仅选得对，还能一次把参数填对。关键手段是把约束写进Schema而不是写进散文。枚举用enum封闭，格式用pattern锚定，范围用minimum与maximum限定，必填用required声明。参数description要给出具体示例值，"日期，格式YYYY-MM-DD"比"日期"有效得多。对容易误解的参数，直接写反例："page从1开始计数（不是0）"。

另一个容易被忽视的方面是返回值的可理解性。模型会阅读工具返回文本来决定下一步，因此返回文本应包含状态、关键数据与下一步提示，例如"已创建任务 task_1024，可调用 assign_task 指派处理人"。返回内容本身就是对话的一部分，设计得好可以引导模型少走弯路。

## 四、Token经济原则

Token经济要求把上下文窗口当作稀缺资源来经营。具体策略包括：第一，裁剪低频工具，将使用率排在尾部的工具下线或改为按需注册；第二，压缩描述，删除营销性形容词，保留操作语义与约束；第三，Schema中避免深层嵌套与超长枚举，枚举超过三十项时改用查询工具动态检索；第四，返回值做摘要化处理，大结果集分页或转资源引用；第五，利用客户端能力裁剪，例如通过配置只暴露当前任务相关的工具子集。

值得建立度量闭环：记录每次对话的token构成、工具选择正确率、参数校验失败率与平均调用轮次。这些指标能客观告诉我们哪个工具的描述在浪费注意力，哪个Schema在诱导错误。设计原则若没有度量支撑，就会退化为个人品味之争。

除了数据裁决，还应注意版本迭代对注意力的影响。每次新增工具，整个清单对所有会话的边际成本都会上升，因此新增工具应附一份"清单影响评估"：预计调用频次、替代了哪些既有工具、是否可以顺带裁剪旧工具。把"增一个工具"与"减一个工具"捆绑决策，是防止工具清单单向膨胀的制度性手段。长期看，工具集的规模应当与用户任务分布定期对齐，而非只增不减。

## 五、设计原则落地清单

- 工具集是否按业务域分组，命名是否自解释且风格统一。
- 语义相近工具的差异是否在描述中显式声明。
- 参数约束是否尽量Schema化，示例值是否具体。
- 常驻清单的token总量是否被度量与控制，低频工具是否裁剪。
- 返回文本是否包含状态、要点与下一步引导。
- 是否建立了选择正确率与失败率的回归度量。

## 六、从指标反推设计的迭代闭环

Token经济若只停留在原则层面，很快会被业务压力冲垮：每个团队都觉得自己的工具重要，都要求进默认清单。破解之道是把度量做成例会机制。每两周拉取一次数据：各工具的调用次数、被选中后又立刻换用其他工具的次数、参数校验失败率、平均每个会话的token消耗构成。把这些数字放在同一张表上，裁剪决策就不再是口味之争，而是数据裁决。对调用次数极低但语义覆盖完整的工具，可改为"二级清单"——由一个search_tools式的元工具按需检索并动态注册，这在第38篇动态工具发现中会详细展开。

另一个实用技巧是控制Schema的重复度。多个工具若共享同一组分页参数，可以在服务器实现中复用Schema片段，虽然对外仍需展开为完整JSON，但展开由构建工具完成，人工只维护片段定义。这样既保证了客户端的兼容性，又降低了维护成本。

## 七、小结

面向LLM的设计是把"说明书一次读懂、参数一次填对、清单不占空间"作为目标函数。可发现性解决选哪个，可理解性解决怎么传，Token经济解决值不值得。下一篇聚焦其中最微观也最影响成功率的一环：工具描述文本的具体撰写方法。
