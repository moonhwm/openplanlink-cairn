# 06 错误响应设计：工具错误与协议错误的分界

## 一、两类错误的分界线

MCP把失败分成两个层次：协议错误与工具错误。协议错误通过JSON-RPC的标准错误对象返回，表示请求本身有问题——方法不存在、参数非法、服务器内部崩溃等，它由客户端传输层处理，错误细节默认不会进入模型上下文。工具错误则通过tools/call结果中的isError标志表达，表示工具被合法调用、但业务执行没有成功，其携带的文本内容会返回给模型阅读。这条分界线的设计意图十分明确：凡是模型能够理解并尝试修复的失败，都应该走isError通道；只有模型无能为力的系统性故障，才走协议错误通道。

错误分类错误的后果很实际。把业务失败抛成协议错误，模型看不到失败原因，只能盲目重试或放弃任务；把系统崩溃包装成isError，模型会对着"数据库连接超时"这类它无法解决的信息反复尝试，浪费轮次并可能放大故障。正确分类是错误响应设计的第一课。

## 二、工具错误的返回规范

工具错误结果由isError标志与content数组构成，文本要遵循"事实、原因、建议"三段式。事实说明发生了什么，原因解释为什么，建议给出下一步动作，最好直接点名可用的补救工具。

```json
{
  "content": [
    {
      "type": "text",
      "text": "创建工单失败：项目 prj_ab12 不存在或无访问权限。请先调用 list_projects 确认项目ID后再试；若需新项目请调用 create_project。"
    }
  ],
  "isError": true
}
```

三段式的价值在于把错误变成模型的"纠错指令"。相比之下，只返回"失败"两个字的工具，等于把模型推向随机重试。对于部分成功的批量操作，错误文本还应写明成功与失败的分界，例如"第1至3条成功，第4条因邮箱格式错误失败，可修正后重试该条"，避免模型全量重复提交。

## 三、协议错误的使用场景与错误码

协议错误适用于四类场景：调用未知工具名、参数不符合JSON-RPC规范、服务器过载或不可用、鉴权失败。错误对象包含code、message与可选data字段。常用代码区间可参考JSON-RPC惯例：

- -32700 解析错误：请求体不是合法JSON。
- -32600 无效请求：请求结构不符合规范。
- -32601 方法不存在：调用了未声明的工具。
- -32602 参数无效：参数无法解析为合法的调用请求。
- -32603 内部错误：服务器未捕获的异常。

服务器实现时应避免把内部错误的堆栈细节直接暴露给客户端，message只需概括性描述，详细堆栈写入服务端日志，并附带请求追踪标识以便排查。

## 四、错误信息的安全边界

错误文本会进入模型上下文，也可能被转述给最终用户，因此必须做信息收敛。第一，不回显凭据：鉴权失败时只说"凭据无效"，不要复述提交的token内容。第二，不泄露内部拓扑：数据库错误只说"存储服务暂不可用"，不要带出主机名、端口与连接串。第三，不暴露敏感业务数据：删除失败时不要把目标记录的完整内容附在错误里。第四，对外部第三方错误做转译：把上游服务的原始报错加工成面向模型的语义化描述，同时记录原始报错供审计。

```python
# 错误信息收敛的伪代码示意
def call_tool(name, args):
    try:
        return execute(name, args)
    except NotFoundError as e:
        return tool_error(f"未找到目标对象：{e.key}。请检查标识符来源。")
    except UpstreamError as e:
        log.warning("upstream failed", trace_id=e.trace_id, raw=e.raw)
        return tool_error("上游服务暂时不可用，请稍后重试；连续失败请联系管理员。")
    except Exception:
        log.exception("unexpected")
        return protocol_error(-32603, "内部错误，请稍后重试")
```

## 五、可重试错误与不可重试错误

从客户端视角，错误还应区分"可重试"与"不可重试"。限流、暂时不可用、超时属于可重试，错误文本可附上建议等待时间；参数错误、权限不足、目标不存在属于不可重试，重试必然再次失败。在文本中显式写出"请稍后重试"或"请修正参数后重试"，能引导模型采取正确策略，避免对确定性失败做无意义重试。这一区分与后续幂等性篇章直接相关：只有幂等工具才适合自动重试，非幂等工具的重试必须依赖幂等键保护。

## 六、超时与取消的配套处理

错误响应设计离不开超时与取消两个伴生议题。长时间运行的工具应当在初始化握手时声明执行能力上限，客户端据此设置合理的超时时间。服务器侧的最佳实践是：执行超过阈值时主动通过进度通知汇报状态，让客户端有机会选择继续等待或取消；收到取消请求后，尽快终止底层任务并返回"已取消"结果，而不是让任务在后台无声继续。取消后的返回应明确区分"取消成功，未产生任何效果"与"取消请求到达时任务已接近完成，效果可能已产生"，这个区分对非幂等工具尤为重要——前者可以安全重试，后者必须由人工确认现状后再决定。进度通知与取消机制的协议细节将在第39篇调用上下文中详细讨论，这里仅强调：错误设计必须把它们纳入同一张状态表，超时不是简单的失败，而是"结果未知"的独立状态。

结果未知（unknown outcome）与确定失败（definite failure）是两类不同的错误：确定失败可以立即补救，结果未知则要求先查询再行动。工具返回文本中显式标注这一状态，能避免模型在结果未知时贸然重复提交。

## 七、核对清单

- 业务失败是否统一走isError通道而非协议错误。
- 错误文本是否包含事实、原因、建议三段。
- 是否点名了补救工具与下一步动作。
- 批量操作是否报告部分成功的边界。
- 错误是否收敛了凭据、拓扑与敏感数据。
- 可重试与不可重试是否有明确提示。
- 服务端日志是否保留了追踪标识与原始报错。

错误响应设计的成熟度，往往决定一个MCP工具在真实对话中的鲁棒性。模型不怕失败，怕的是读不懂失败。下一篇开始进入Schema设计的纵深：参数类型的选择与适用场景。
