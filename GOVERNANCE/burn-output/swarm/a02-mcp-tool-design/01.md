# 01 MCP协议中Tool的概念与定位：Tool、Resource、Prompt的区别

## 一、MCP三大原语概览

模型上下文协议（Model Context Protocol，简称MCP）是一个开放协议，它为大型语言模型与应用系统之间定义了标准化的连接方式。MCP在服务器端暴露的核心原语（primitives）共有三类：Tools（工具）、Resources（资源）与 Prompts（提示模板）。这三者承担着完全不同的职责，理解它们的边界，是设计一个高质量MCP服务器的第一步。很多初学者会把三者混为一谈，例如把一段只读的配置文本封装成工具，或者把一个需要执行的动作做成资源，这些错位设计会直接降低模型调用的准确率，也会放大安全风险。

三类原语的定位可以用一句话概括：资源是"给模型读的数据"，工具是"让模型做的动作"，提示是"帮用户起的头"。从协议的角度看，服务器开发者对三者的控制粒度也不同：工具由服务器定义并由模型自主决定是否调用；资源同样由服务器暴露，但其消费方可以是模型也可以是人类用户；提示则是服务器预先打包好的、面向特定任务场景的交互模板，通常由用户主动选取。

## 二、Tool的定义与生命周期

Tool是MCP中唯一具有"执行副作用能力"的原语。一个工具由名称、描述、输入Schema（inputSchema）以及可选的标注（annotations）组成。服务器通过 tools/list 方法向客户端声明全部可用工具；模型在对话中决定调用某个工具时，客户端通过 tools/call 请求发起执行，服务器执行后返回文本内容或结构化内容（structuredContent）。

工具的典型生命周期包括四个阶段：注册（服务器在启动或运行期声明工具清单）、发现（客户端拉取清单并注入到模型上下文）、调用（模型产出工具名与参数，客户端转发）、返回（服务器给出结果或错误）。整个链条中，模型只负责"决定与构造"，真正执行发生在服务器侧，这就是为什么工具设计必须严肃对待鉴权、幂等与副作用声明——这些议题在后续章节中会逐一展开。

```json
{
  "tools": [
    {
      "name": "get_weather",
      "description": "查询指定城市的当前天气。city_code为城市行政区划代码。",
      "inputSchema": {
        "type": "object",
        "properties": {
          "city_code": { "type": "string", "description": "6位城市代码，例如 110000" }
        },
        "required": ["city_code"]
      }
    }
  ]
}
```

## 三、Tool与Resource的区别辨析

工具与资源最容易混淆，因为两者都能把信息交给模型。判断标准是"控制流归属"：如果客户端只是想获取一份只读数据，且不需要模型参与决策，就应该是资源；如果获取过程需要模型以特定参数发起、并且可能改变世界状态，才是工具。资源以URI标识（例如 config://app/v1），支持订阅变更通知；工具没有URI，只有名称与Schema。

另一个差异是缓存与安全策略。资源是明确只读的，客户端可以放心缓存、预取、并行读取多个资源而不产生副作用；工具调用则默认可能产生副作用，客户端必须逐次转发并如实报告结果，绝不能擅自"代答"或合并。把只读查询做成工具的代价是：模型上下文被多余的Schema占用、调用轮次变多；把写操作做成资源的代价则是：协议层面完全失去了对副作用的约束框架，等于绕过了安全护栏。

## 四、Tool与Prompt的区别辨析

Prompt是服务器预先编排好的提示模板，通常包含固定的指令文本、可选的参数占位符，以及引用哪些资源或工具的暗示。它服务于"工作流的起点"：用户在客户端界面上选择一个提示，例如"代码审查"，客户端把模板展开后交给模型。工具则服务于"执行的中段"：模型在推理过程中根据上下文自主决定调用。简言之，提示由用户驱动、一次性注入，工具由模型驱动、按需触发。

三者协同的典型场景是：用户选择"数据库巡检"提示模板，模板中注入了连接信息资源（只读配置），并指引模型按顺序调用 check_schema、check_slow_query 等工具。此时提示负责编排意图，资源负责提供上下文，工具负责执行动作，各司其职。

## 五、常见错配案例剖析

实践中最常见的错配有三种。第一种是"查询工具化"：把读取一条数据库记录做成工具，模型每次都要走完整的调用往返，参数Schema与返回文本反复占用上下文窗口，而实际上这些数据完全可以作为资源由客户端按需注入。第二种是"动作资源化"：把触发一次构建、发送一条消息的接口伪装成资源返回，客户端在不知情的情况下可能预取或缓存它，造成意外的重复执行，这类设计在生产环境中曾引发重复下发工单的事故。第三种是"提示工具化"：把固定的指令文本包装成工具让模型调用，结果模型调用后得到的只是一段提示词，白白消耗了一轮交互。这些案例说明，原语选择不是风格问题，而是正确性与成本问题。

还有一种隐蔽的错配是"同一能力重复暴露"：既提供资源又提供功能相同的工具，模型在面对两份等价能力时会随机摇摆，调用行为变得不可预测。规范的做法是只保留一种入口，或者在工具描述里明确说明它与某个资源的差异与适用条件，让模型在语义层面可以区分。

## 六、选型决策清单

设计服务器前，建议用如下清单逐项核对，避免原语错配：

- 数据是否只读且可用URI稳定标识？是则优先设计为Resource。
- 该能力是否必须由模型在推理中触发执行？是则设计为Tool。
- 是否存在状态改变、外部系统写入、资源消耗？是则必须是Tool，并补充annotations声明。
- 该内容是否是面向特定任务、由用户主动选取的模板？是则设计为Prompt。
- 同一份只读数据是否会被多个工具重复内嵌？考虑改为Resource并让工具仅返回引用。

正确区分三类原语，不仅能缩小攻击面、降低token消耗，也让工具的Schema设计、幂等与版本化议题有了清晰的讨论对象。后续章节将默认以Tool为对象，深入其输入Schema、幂等性、副作用治理、组合编排与版本演进的每一个设计细节。
