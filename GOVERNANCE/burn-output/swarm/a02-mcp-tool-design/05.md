# 05 工具描述文本的撰写：让模型正确选择与正确传参

## 一、描述文本的两种失败

工具描述文本的失败有两种典型形态。第一种是"选错工具"：用户要查询订单，模型却调用了创建订单的工具，原因往往是两个工具的描述边界模糊，模型无法区分。第二种是"传错参数"：工具选对了，但参数值是幻觉，例如日期格式错误、枚举值拼写不符、标识符被凭空编造。两种失败都指向同一个根源——描述文本没有把关键信息传递到位。本篇给出一套可直接套用的撰写方法，覆盖工具级描述与参数级描述两个层级。

## 二、工具级描述的四段式模板

推荐使用"做什么、何时用、何时不用、返回什么"的四段式结构。这个模板强迫作者回答模型最关心的四个问题，避免想到哪写到哪。

```json
{
  "name": "cancel_order",
  "description": "取消一个尚未发货的订单（做什么）。仅当订单状态为 pending 或 paid 时可取消，已发货订单请使用 request_return（何时用/何时不用）。取消成功后返回订单最终状态与退款流水号，退款将在三个工作日内原路退回（返回什么）。本操作会向客户手机发送取消通知短信（副作用提示）。"
}
```

四段式之外，还可以视需要补充副作用提示与相近工具指引。副作用提示让模型在自主决策时更谨慎，也帮助客户端判断是否需要人工确认；相近工具指引例如"与close_order的区别：close_order用于正常完结，cancel_order用于撤销未履约订单"，能显著降低选错率。

## 三、参数级描述的撰写要点

参数描述的目标是让模型一次填对值。要点有六条。第一，写明格式并给出示例，例如"ISO 8601日期，如2026-09-30，不要含时间部分"。第二，写明取值来源，标识符类参数必须指明来源工具，例如"由list_projects返回的project_id，不是项目名称"。第三，写明单位与默认行为，例如"条数，默认20，最大100"。第四，写明大小写与空白规则，枚举敏感的场合要显式说明"必须是小写"。第五，对易混参数写反例，"page从1开始（不是0）"。第六，约束优先放进Schema的enum、pattern等关键字，描述只做补充说明，不要用散文重复Schema已有的约束，避免两处不一致。

## 四、描述撰写的反模式清单

以下反模式在真实项目中反复出现，撰写时应逐条规避：

- 空泛型："处理数据"。模型完全无法判断何时该用。
- 复述型：描述只是把参数名翻译一遍，没有增量信息。
- 营销型：堆砌"强大""智能""一站式"等形容词，占用token且无操作语义。
- 内部黑话型：使用只有本团队才懂的缩写与代号。
- 边界缺失型：不写前置条件，导致模型在不满足条件时贸然调用。
- 重复型：多个工具描述几乎相同，模型只能随机选择。
- 超长型：数百字的描述淹没关键约束，注意力被稀释。

还有一个易被忽略的细节：描述中的数量词与量纲要精确。"几个""大量""近期"这类模糊词对模型几乎无信息量，应改写为"最多20个""超过1000条时自动分页""最近7天内"。同理，涉及时间、时区、货币的参数描述必须写明默认时区与币种，否则模型的本地知识会随意填补空缺。描述文本的严谨度，最终会以参数校验通过率的形式被量化回报。

## 五、描述质量的经验证法

写完描述后，建议用三个问题自检。第一问：只看清单里的名称与描述，能否在一分钟内向新同事讲清这个工具的用途与边界？第二问：把两个语义相近的工具并排放置，描述是否足以让人做出正确选择？第三问：模型实际调用中，参数校验失败的报错是否与描述缺失直接相关？第三个问题需要依托调用日志做归因，把高频报错逐条映射回描述文本的修改项，形成"日志驱动的描述迭代"闭环。

更系统的做法是构建描述的回归用例集：准备一批典型任务描述与期望调用的工具及参数，每次修改描述后跑一遍模拟调用，对比通过率。这套用例集与第48篇讨论的版本治理结合，能防止描述被无意修改后无人察觉。

## 六、描述与提示词、文档的分工

工具描述不是孤岛，它与会话级提示词、外部文档构成三层信息体系。会话级提示词负责交代任务背景与整体目标，例如"你是运维助手，优先使用只读工具诊断"；工具描述负责单个工具的调用语义；外部文档负责纵深细节。分层的意义在于控制重复：不要把使用规范全文塞进每个工具的描述，也不要指望系统提示词能替每个工具解释参数。一个常见的失衡是把大量操作规范写进系统提示词，结果工具一多提示词膨胀失控；反过来，把任务级约束硬塞进工具描述，又会随清单常驻浪费token。经验法则是：任务级约束放会话提示，工具级语义放描述，领域知识放文档与资源。

描述文本与CHANGELOG也存在协作关系：当描述的行为语义发生变化，例如默认值从20改为50，必须在变更记录中登记，因为下游提示词可能引用了旧行为。这一点将在版本化篇章中再展开。

## 七、一份完整的参数描述示例

```json
{
  "name": "schedule_report",
  "inputSchema": {
    "type": "object",
    "properties": {
      "report_type": {
        "type": "string",
        "enum": ["daily", "weekly", "monthly"],
        "description": "报表周期，必须为枚举值之一，小写。"
      },
      "cron_expr": {
        "type": "string",
        "description": "可选。Cron表达式，5段式（分 时 日 月 周），如 '0 8 * * 1' 表示每周一8点。省略时按report_type使用默认时点。"
      },
      "recipients": {
        "type": "array",
        "items": { "type": "string" },
        "description": "接收邮箱列表，1到20个，需为企业域名内邮箱。"
      }
    },
    "required": ["report_type", "recipients"],
    "additionalProperties": false
  }
}
```

这份示例中，每个参数都有格式示例、来源约束与默认行为说明，枚举与数组约束完全Schema化。描述文本的撰写是工具设计中投入产出比最高的环节：改动成本极低，却能直接抬升调用成功率。下一篇转入错误响应设计，讨论失败时如何让模型自我纠正。
