# 02 · Sampling协议规范精读：sampling/createMessage的请求与响应结构

> 一句话摘要：本文逐字段精读采样能力的协议报文——服务器发出的createMessage请求、客户端返回的CreateMessageResult，以及角色、内容类型、能力声明等规范细节，为后续参数篇与实现篇打底。

## 一、能力前提与方法名

Sampling是客户端能力，客户端在初始化握手的capabilities中显式声明`{"sampling": {}}`，服务器才被允许发起采样请求。采样方法名为`sampling/createMessage`，是少数由服务器向客户端发送的JSON-RPC请求之一。规范明确其设计意图：服务器无需自带模型API密钥即可获得补全能力，模型选择权与最终审批权保留在用户侧。这一设计把"谁付token账、谁控模型、谁担数据责任"三个问题统一收敛到客户端，是理解采样一切安全讨论的起点。

请求方向反转带来一个常被忽略的实现细节：客户端成了请求的处理方，因此客户端要为该方法注册请求处理器，并处理"无审批UI时怎么办"的兜底——规范允许客户端直接返回错误（例如`-32601`方法不存在或应用层错误），服务器必须能优雅降级。

## 二、请求参数结构

请求params的字段如下：`maxTokens`（必填，整数，本次补全的token上限）、`messages`（必填，采样消息数组，元素含`role`取user或assistant与`content`）、`systemPrompt`（可选，系统提示词）、`includeContext`（可选，取`none`/`thisServer`/`allServers`，声明希望注入多少客户端会话上下文）、`modelPreferences`（可选，模型偏好）、`stopSequences`（可选，停止序列数组）、`metadata`（可选，扩展元数据）。一个最小而完整的请求示例如下：

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "sampling/createMessage",
  "params": {
    "maxTokens": 512,
    "systemPrompt": "你是严谨的代码审查助手，只依据给定材料回答。",
    "includeContext": "thisServer",
    "messages": [
      { "role": "user", "content": { "type": "text", "text": "分析此函数的边界条件" } },
      { "role": "assistant", "content": { "type": "text", "text": "请提供函数体。" } },
      { "role": "user", "content": { "type": "text", "text": "def f(n): return 1 if n<2 else f(n-1)+f(n-2)" } }
    ],
    "modelPreferences": {
      "hints": [ { "name": "reasoning" } ],
      "intelligencePriority": 0.8,
      "costPriority": 0.2
    },
    "stopSequences": [ "END" ],
    "metadata": { "intent": "code-review", "contextUri": "file:///repo/src/f.py" }
  }
}
```

## 三、响应结构与约束

客户端返回的CreateMessageResult包含四个字段：`role`固定为`assistant`；`content`为补全内容（文本、图像或音频之一）；`model`为实际使用的模型标识字符串（供服务器记录与审计）；`stopReason`说明终止原因，规范列举了`end_turn`、`stop_sequence`、`max_tokens`、`context_length`与`other_error`等取值。规范还强调：若底层模型产生了内部思考（thinking）内容，客户端不得将其放入content返回，必须先行剥离；`model`字符串应如实反映所用模型，避免服务器侧审计失真。

```json
{
  "role": "assistant",
  "model": "client-local-router/gpt-class",
  "stopReason": "end_turn",
  "content": { "type": "text", "text": "该函数缺少n为负数与非法输入的防护……" }
}
```

## 四、规范留给实现的自由度

规范刻意留白之处值得逐条记录：其一，客户端如何呈现审批（弹窗、横幅、静默策略）完全由实现决定，规范只以"SHOULD"级别的措辞要求人类可见的批准环节；其二，`modelPreferences`只是偏好而非强制，客户端可以忽略；其三，`includeContext`只是服务器声明的期望，客户端有权注入更少上下文以保护隐私；其四，错误响应没有专用错误码，可复用JSON-RPC标准错误或`isError`语义。这些自由度正是各客户端产品差异化的空间，也是跨客户端兼容性测试必须覆盖的矩阵点。后续篇目将分别深入参数语义（第6-10篇）、审批流（第14-21篇）与安全边界（第22-29篇），此处建立的报文级精确认知是所有后续讨论的共同语言。
