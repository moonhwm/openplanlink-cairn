# 01 · MCP反向能力全景：Sampling、Roots、Elicitation的协议地位与三角关系

> 一句话摘要：MCP在"客户端调用服务器"的正向能力之外，定义了三类由服务器反向驱动客户端的能力——采样（Sampling）、根（Roots）与启发（Elicitation），三者共同构成反向通道，本文给出其全景定位、职责边界与协同关系。

## 一、正向与反向：MCP控制流的两条主线

MCP（Model Context Protocol）的基础心智模型是"宿主—客户端—服务器"三层：宿主（Host）是面向用户的AI应用，客户端（Client）为每个服务器（Server）建立一条有状态会话，服务器向客户端暴露工具、资源与提示词。这是正向能力：请求由客户端发起，服务器被动应答。但真实世界的智能体场景需要反向的通道：服务器在执行任务中途需要借助客户端所持有的模型、上下文与用户注意力。为此协议在JSON-RPC双向请求的基础上定义了三类反向能力：Sampling让服务器向客户端请求一次模型补全；Roots让服务器向客户端查询工作区边界；Elicitation让服务器向用户请求一段结构化输入。三者都不是"服务器自己更强大"，而是"服务器借用客户端所处生态的资源"，这正是反向能力的本质。

理解这一点的工程意义在于：反向能力的实现义务主要落在客户端一侧，服务器只是发起方与消费者。客户端必须为采样弹出审批、为根维护工作区列表、为启发渲染表单。任何一环缺失，反向能力就退化为不可用或被静默拒绝，因此在做架构评估时，"客户端支持度"是第一检查项。

## 二、三兄弟的职责切分

三类反向能力在协议中的定位可以用一张切分表说清楚：

- Sampling（采样）：方向为服务器→客户端；借用的是客户端的LLM访问权；典型场景是服务器在工具执行中需要模型判断、摘要或路由；核心风险是数据外泄与提示注入。
- Roots（根）：方向为服务器→客户端；借用的是客户端对工作区边界的认知；典型场景是限定检索范围、理解多仓库布局；核心风险是把信息性边界误当访问控制。
- Elicitation（启发）：方向为服务器→客户端；借用的是用户的注意力与决策；典型场景是缺少必要参数时向用户补问；核心风险是钓鱼式伪造与过度打扰。

从MECE角度看，三者分别对应"模型资源、上下文资源、人力资源"三个互斥维度，覆盖了服务器反向借力的全部渠道，也分别对应不同的审批与安全设计。实践中容易混淆的是Sampling与Elicitation：前者问的是模型，后者问的是人；前者传递的是对话内容，后者传递的是结构化表单（受JSON Schema约束），两者不可互换。

## 三、三角协同：一次典型任务的完整走线

假设一个代码审查MCP服务器要分析当前仓库：第一步，服务器向客户端发送`roots/list`，拿到`file:///repo`等工作区根，据此确定扫描范围；第二步，服务器读取代码后在内部生成初步结论，但由于需要更高质量的综合判断，它构造`messages`并发起`sampling/createMessage`，请客户端侧的模型补全审查摘要；第三步，若发现缺少用户意图信息（例如"关注安全还是性能"），服务器发起`elicitation/create`向用户补问。三个反向请求串联，构成一次完整的反向协作链。

```json
{
  "jsonrpc": "2.0",
  "id": 101,
  "method": "sampling/createMessage",
  "params": {
    "maxTokens": 1024,
    "messages": [
      { "role": "user", "content": { "type": "text", "text": "请总结以下变更的风险点……" } }
    ],
    "modelPreferences": { "hints": [ { "name": "high-reasoning" } ] }
  }
}
```

## 四、安全边界的总纲

反向能力每一条都是权限的让渡：把模型调用权、工作区知识、用户注意力交到服务器手里。因此协议规范的立场非常克制——采样"应当"经过用户审批，根"只是"信息性建议，启发"必须"用户显式提交。这三句克制的表述决定了安全设计的基调：客户端是守门人，服务器是申请人；任何把申请人当守门人的设计（例如服务器自证安全）都是错的。后续各篇将分别展开审批流、注入防御与权限分离的具体实现，本文作为全景篇，先确立"三条反向通道、三类被借资源、一个守门客户端"的结构性认知框架，供后续分解引用。
