# 19. 去重窗口与幂等记录的存储设计

## 概述：幂等不是承诺，是有保质期的设施

幂等去重靠幂等记录撑着：查重、占位、回放结果全依赖这张表的存在与正确。但记录不能无限保留——存储成本线性增长，业务语义上过老的重复也不该拦截（用户半年后重下一次同样的订单是合法新意图）。于是每个幂等系统都要回答三个问题：记录保留多久（去重窗口）、记录里放什么（存储内容）、记录怎么过期（清理机制）。这三个答案合起来，就是幂等设施的存储设计。

## 去重窗口的确定逻辑

窗口下限由重试行为决定：必须覆盖客户端最大重试周期加网络最大滞留时间，再加故障停机恢复时长。例如客户端指数退避最长重试15分钟、消息队列故障可能滞留2小时、极端停机6小时，窗口至少取24小时才安全。窗口上限由业务语义决定：同一意图在多久之后重现应视为新请求。金融类操作倾向长窗口（7天到30天），内容生成类可短（24小时到72小时）。两相权衡取大者；无法确定时宁可偏长，因为窗口过短的后果是重复执行，而偏长只是多占存储。窗口边界上还要定义清晰的切换语义：窗口内命中记录返回旧结果，窗口外同键视作新请求，二者对客户端的表现必须稳定可预期。

## 存储内容与表结构

幂等表的核心列包括：幂等键（唯一约束所在）；关联对象引用（taskId或结果指针）；状态（PENDING表示占位执行中，DONE表示完成）；结果引用（指向真实结果的存储位置，而非结果本体）；创建时间与过期时间。关键取舍有三。其一，存引用不存本体：结果可能是大JSON或大文件，塞进幂等表让表膨胀，存指针指向对象存储或结果表更健康。其二，PENDING要有租约：占位后执行方崩溃，记录永远PENDING会阻塞后续重复请求，租约过期后允许重新占位执行。其三，索引只为幂等键建唯一索引，别为查询方便乱加二级索引，这张表写入极热，结构越简越好。

## 表结构与生命周期示意

```sql
CREATE TABLE idempotency (
  idem_key     VARCHAR(64) PRIMARY KEY,   -- messageId或业务幂等键
  task_id      VARCHAR(64),               -- 关联任务
  state        VARCHAR(8)  NOT NULL,      -- PENDING / DONE
  result_ref   VARCHAR(256),              -- 结果指针，非本体
  lease_until  TIMESTAMP,                 -- PENDING租约
  created_at   TIMESTAMP   NOT NULL,
  expires_at   TIMESTAMP   NOT NULL       -- 过期时间=created_at+窗口
);
-- 查重命中且 state=DONE 且未过期 => 回放 result_ref
-- 命中且 PENDING 且租约未过 => 返回处理中，稍候重试
-- 命中且 PENDING 且租约已过 => 重新占位执行
-- 未命中 => 占位执行
```

## 存储设计要点清单

- [ ] 窗口下限覆盖最大重试周期加滞留加停机恢复时长；
- [ ] 窗口上限服从业务语义，不确定时宁长勿短；
- [ ] 存结果引用不存结果本体，控制表体积；
- [ ] PENDING带租约，过期可重占，防永久阻塞；
- [ ] 唯一约束只建在幂等键上，表结构极简；
- [ ] 清理任务按expires_at滚动删除，避开写入高峰；
- [ ] 窗口边界语义文档化：内回放、外新建，行为稳定。

## 小结

幂等存储设计三问三答：窗口由重试行为下限与业务语义上限夹逼得出；内容以引用代替本体、以租约激活PENDING；过期靠滚动清理收尾。这张看似朴素的小表，是整个exactly-once大厦的地基——它的任何缺陷，都会在最高频的路径上被放大成生产事故。
