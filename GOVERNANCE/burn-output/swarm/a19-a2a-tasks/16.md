# 16. 至少一次、至多一次与精确一次的语义层次

## 概述：投递语义的光谱

分布式消息与任务系统绕不开三兄弟：至少一次（at-least-once）、至多一次（at-most-once）、精确一次（exactly-once）。任务生命周期的每个环节——提交、状态事件、产出物推送、完成通知——都要先回答"我承诺什么投递语义"，才能设计对应机制。混淆三者是多数重复执行与丢失结果事故的根源。清晰的路线是：默认至少一次加重试，用幂等去重把至少一次收敛为效果上的精确一次，只有在不允许重复且允许丢失的场景才选至多一次。

## 三种语义的承诺与代价

至少一次承诺不丢：发送方失败就重试，直到确认。代价是可能重复——网络抖动下接收方已收到但确认丢失，重发导致一份数据两次到达。它实现最简单，是超时重试的默认行为。至多一次承诺不重：发送一次，成败听天。代价是可能丢——消息在途丢失就永久丢失。它适合可容忍缺失的采样、指标类数据。精确一次承诺每个消息恰好被处理一次：既不丢也不重。代价最昂贵：它从来不是单一机制能达成的，而是至少一次传输加接收端幂等去重的合成效果，且只在一个精心划定的作用域内成立（同一 Kafka 主题、同一数据库事务边界），跨系统边界后语义降级回至少一次。

## 任务生命周期各环节的语义选型

提交环节：客户端到服务端选至少一次加重试，服务端用messageId幂等去重，合成效果上的精确一次任务创建。状态事件流：SSE通道本身是至多一次（断线即丢），因此需要断线补齐机制（重连拉取历史或tasks/get对账）把整体拉回至少一次，消费端按事件序号去重防重。产出物推送：同事件流，靠游标续传加序号去重。完成通知（webhook）：推送方带重试的至少一次，接收方按通知标识幂等处理。跨代理编排：子任务结果回传父任务，同样至少一次传输加幂等折叠。可见模式高度一致：传输层全部至少一次，语义保证全部由接收端幂等完成。

## 语义合成的实现骨架

```text
语义选型速查：
  提交任务       => at-least-once 传输 + messageId 去重 = 效果精确一次
  状态事件       => at-most-once 通道 + 断线补齐 + 序号去重 = 至少一次起步
  完成通知       => at-least-once 推送 + 通知幂等 = 效果精确一次

```

## 语义选型要点清单

- [ ] 每个环节显式声明投递语义，不默认、不含糊；
- [ ] 精确一次=至少一次传输+接收端幂等，是合成效果非原生属性；
- [ ] 去重记录与副作用在同一事务边界内落库；
- [ ] 跨系统边界语义降级，边界处重新引入幂等；
- [ ] 至多一次只用于可容忍丢失的数据，任务与结果不适用；
- [ ] 作用域要说清楚：对谁精确一次、在多长时间窗内精确一次。

## 小结

投递语义光谱上没有免费午餐：至少一次换来可能重复，至多一次换来可能丢失，精确一次是传输与幂等的合成品且只在明确作用域内成立。任务生命周期的标准答案高度一致——所有传输走至少一次，所有语义保证交给接收端幂等，去重记录与副作用同事务落库。理解这个合成结构，是进入exactly-once专题的前提。
