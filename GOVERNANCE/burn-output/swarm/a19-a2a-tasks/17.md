# 17. 网络重试导致重复提交的检测与去重

## 概述：重试是重复之母

超时重试是分布式系统的生存本能，也是重复提交的万恶之源。典型剧本：客户端发出tasks/send，网络在响应回程丢包，客户端超时判定失败，重发同一请求；而服务端其实已收到并开始执行——第一次请求在途、第二次请求落地，同一个业务意图跑了两遍。更糟的变体是重试风暴：网关抖动引发批量客户端同时重试，放大流量数倍。检测与去重的目标，是让"重试"这个正当行为不再引发"重复执行"这个不当后果。

## 重复的四种形态

形态一：同连接快速重发。客户端实现简陋，超时阈值过短，同一请求秒级重发多次。特征是messageId完全相同，时间戳密集，最易识别。形态二：跨进程重启重发。客户端崩溃重启后丢失"已发送"记忆，再次提交同一业务意图。若重启后messageId重新生成则完全无法靠协议识别，只能靠业务幂等键。形态三：中间层重放。网关、代理、消息队列的重试机制在网络栈中间层重放请求，客户端毫不知情。形态四：用户重复点击。界面上没有防抖与禁用，用户连点三次产生三个"看起来不同"的请求。前三种靠messageId或业务键机器去重，第四种要靠前端防抖加后端业务键双保险。

## 检测机制的设计

检测的核心是把"重复"从模糊感觉变成可判定谓词。第一道：协议层谓词，messageId相同即重复，查幂等表即可判定，成本最低。第二道：业务层谓词，业务键相同（同一订单号、同一文档指纹加指令）即重复，需要业务建模配合，覆盖messageId重新生成的场景。第三道：内容层谓词，请求体哈希相同且时间窗内到达即疑似重复，作为兜底告警信号，不自动拦截（同内容合法重复提交是存在的）。三道防线依次收窄：协议层拦机器重试，业务层拦意图重复，内容层只报警不动作。

## 去重执行的模式

```python
async def handle_send(message):
    # 第一道：协议层查重（唯一约束原子占位）
    if not idempotency.try_insert(message.message_id):
        prior = idempotency.load(message.message_id)
        if prior.state == "DONE":
            return prior.result          # 回放首次结果，不重复执行
        if prior.state == "PENDING":
            return retry_later_hint()    # 首次仍在执行，引导稍候
    # 第二道：业务层查重（可选）
    if message.metadata.get("biz_key"):
        existed = tasks.find_by_biz_key(message.metadata["biz_key"])
        if existed:
            return existed.snapshot()
    # 首次请求：执行并回填幂等记录
    task = await execute_and_create(message)
    idempotency.complete(message.message_id, task.id)
    return task
```

## 重试去重要点清单

- [ ] 客户端超时阈值要覆盖服务端P99处理时间，减少误判重试；
- [ ] 重试必须携带相同messageId，换新标识等于放弃机器去重；
- [ ] 服务端幂等表以messageId唯一约束，占位加回放两态处理；
- [ ] 业务幂等键覆盖跨重启场景，键设计纳入业务建模；
- [ ] 内容哈希相同只告警不拦截，保留合法重复空间；
- [ ] 网关层重试要有上限与抖动，防重试风暴放大；
- [ ] 前端提交按钮防抖加禁用，用户层先挡一道。

## 小结

重复提交的治理是三道漏斗：协议层messageId拦机器重试，业务层幂等键拦意图重复，内容层哈希做兜底告警。客户端侧的配合同样关键——超时阈值合理、重试复用标识、前端防抖。服务端以唯一约束原子占位，把"查重与执行不原子"这个最后漏洞焊死，重试才能从风险变成可靠的容错手段。
