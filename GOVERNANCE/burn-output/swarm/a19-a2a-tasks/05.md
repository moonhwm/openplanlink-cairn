# 05. 任务取消（tasks/cancel）与竞态处理

## 概述：协作式取消而非强杀

tasks/cancel是客户端表达"不再需要结果"的协议动词：携带taskId（与可选的取消说明消息）请求服务端终止任务。必须先澄清语义边界：A2A的取消是协作式取消，服务端收到请求后尽力停止执行并最终把任务落到canceled终态，客户端不能假设请求发出瞬间任务即死。这与操作系统级的强杀不同——代理可能正处在不可中断的模型推理、外部调用或事务中段。因此取消的正确心智模型是"提出取消申请，然后等待或确认canceled终态"，而不是"调用即生效"。

## 取消请求与响应形态

请求结构简单：params携带taskId与可选message说明取消原因。服务端的即时响应通常是确认受理（任务状态可能仍在working），真正的canceled终态通过后续查询或事件流到达。规范允许服务端拒绝取消：如果任务已经完成或失败，取消请求应返回错误；如果任务已处于canceled，再次取消通常幂等返回当前状态。客户端拿到响应后不能立刻释放全部资源，应当继续观察直到终态确认，否则可能出现"本地已放弃、远端仍在烧算力"的孤儿任务。

## 竞态窗口：取消与完成的双重冲刺

取消最棘手的是竞态：客户端发出cancel的同时，服务端恰好完成任务，两路事件交错。可能出现三种结局。第一，取消先到：任务转canceled，随后的完成产出被丢弃或标记为迟到结果。第二，完成先到：任务已落completed，取消请求返回错误，客户端需接受既成结果并正常消费产出。第三，几乎同时：服务端内部以状态机的原子迁移裁决，先成功落库者生效。协议层面的原则是终态唯一且不可逆——一个任务不可能既completed又canceled，裁决权在服务端状态机的串行化逻辑。客户端要做的，是把"取消后仍收到正常产出"视为合法场景处理，而不是当成异常。

## 竞态处理的工程模式

```python
async def cancel_task(session, task_id):
    # 第一步：提交取消申请
    resp = await session.send("tasks/cancel", {"taskId": task_id})
    # 第二步：等待终态确认，而不是假设立即生效
    while True:
        task = await session.send("tasks/get", {"taskId": task_id})
        state = task["status"]["state"]
        if state == "canceled":
            return "canceled"
        if state in ("completed", "failed", "rejected"):
            # 竞态落败：任务先一步完成，接受结果
            return f"race-lost:{state}"
        await asyncio.sleep(0.5)
```

## 取消侧工程要点清单

- [ ] 取消是申请制，发出后必须等待canceled终态确认；
- [ ] 取消已终态任务会收到错误，客户端要分类处理而不是崩溃；
- [ ] 取消与完成竞态时，以服务端状态机裁决为准；
- [ ] 取消后收到产出物属合法迟到数据，按需丢弃或标记；
- [ ] 取消说明消息有助于服务端做补偿与审计，建议填写；
- [ ] 对流式任务，取消申请发出后事件流可能仍有尾部事件，读完final再收尾；
- [ ] 批量场景要有取消风暴的限流，防止连锁雪崩。

## 小结

tasks/cancel的工程本质是处理异步世界里的"意图与现实的时差"。协作式取消意味着客户端永远在申请，服务端永远在裁决，中间的竞态窗口靠状态机原子性与终态唯一性兜底。把取消当成一次小小的分布式协调来设计，才能避免孤儿任务、双重结果与客户端状态错乱。
