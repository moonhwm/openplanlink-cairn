# 11. 状态机在客户端SDK中的实现模式

## 概述：把协议词汇变成客户端骨架

任务生命周期的客户端体验，取决于SDK如何封装状态机。裸用协议动词，调用方要自己处理事件分派、终态判定、断线对账、输入等待，代码重复且易错。好的SDK把这一整套逻辑收敛为一个状态机对象：外部事件（SSE事件、轮询快照、推送通知）作为输入，驱动内部状态迁移；调用方只面对回调、Future或async迭代器三种高级接口。本文梳理四种主流实现模式及其适用场景。

## 四种实现模式

模式一：Future/Promise封装。SDK的send方法返回一个可等待对象，内部完成订阅或轮询，终态到达时resolve（completed）或reject（failed/rejected），canceled则按调用方策略归入二者之一。适合"发出去等结果"的简单场景，缺点是无法观察中间过程与处理input-required。模式二：回调订阅。调用方注册on_status、on_artifact、on_message回调，SDK分派事件。灵活但容易陷入回调地狱，且要处理回调内的异常隔离。模式三：async迭代器。把事件流抽象为async for，调用方在循环里自己决定何时提前退出，中间过程与终态统一在一条代码路径上表达，是流式场景的最自然形态。模式四：显式状态机对象。SDK暴露状态与可触发动作（respond、cancel、refresh），调用方查询状态并主动行动，适合需要人工介入交互性等待的长流程，例如审批类任务。

## 核心内聚逻辑：无论哪种模式都要做对的事

封装形式可以变，五件事必须内聚在SDK里。其一，事件归一：SSE事件、轮询快照、推送通知三种来源统一成同一内部事件流，去重靠序号或快照时间戳。其二，终态判定集中：唯一函数判定终态，判定后冻结状态机、触发收尾钩子。其三，input-required提升：把交互性等待显式暴露给调用方（抛特定异常、回调特定钩子、或迭代器产出特定条目），绝不让它伪装成慢任务。其四，断线对账：连接断开时自动tasks/get校准状态，再决定重连续传还是直接收尾。其五，资源清理：终态或取消后自动退订、注销推送配置、关闭连接，杜绝泄漏。

## async迭代器模式示例

```python
async for ev in client.run_task(message):
    if ev.type == "status":
        if ev.state == "input-required":
            answer = await ask_human(ev.task.status.message)
            await ev.respond(answer)        # 续写消息恢复执行
        elif ev.state == "working":
            log.progress(ev.task.id)
    elif ev.type == "artifact":
        await sink.write(ev.artifact)       # 增量消费产出物
# 循环自然结束 => 终态已到，final已见
result = ev.task                            # 最后事件携带终态快照
```

## SDK设计要点清单

- [ ] 事件归一：三种事件来源统一为内部单一事件流；
- [ ] 终态判定集中一处，判定后状态机冻结；
- [ ] input-required显式暴露，配套respond与cancel动作；
- [ ] 断线自动对账（tasks/get校准）后再决定重连策略；
- [ ] 终态即清理：退订、注销配置、关连接一步完成；
- [ ] 回调模式要做异常隔离，单个回调异常不炸整机；
- [ ] 状态机可导出快照，支持进程重启后恢复观察。

## 小结

客户端SDK的价值在于把协议动词翻译成调用方的自然语言：等结果的用Future，看过程的用迭代器，管交互的用显式状态机。形式可以选，内聚的五件事不能省——事件归一、终态集中判定、输入等待提升、断线对账、终态清理。做好这五件，调用方就能用十行代码安全地驾驭一个可能长达数小时的任务生命周期。
