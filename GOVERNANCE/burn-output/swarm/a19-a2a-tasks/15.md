# 15. 幂等键设计：contextId与taskId的分工

## 概述：两个标识，两种使命

任务生命周期里的标识系统常被混为一谈：contextId、taskId、messageId三个东西各自承担不同使命。taskId是任务本体的唯一标识，由服务端分配，生命周期内不变，是查询、取消、订阅的锚点。contextId是会话标识，串联同一交互脉络下的多条消息与多个任务，承担上下文连续性。messageId是消息级标识，由客户端生成，是去重与关联的最小单元。幂等设计的要害在于：谁生成、何时生成、重复出现时系统如何反应。

## 幂等键的三个层次

第一层：消息级幂等。客户端为每条发送的消息生成全局唯一messageId，服务端收到后先查重：若该messageId已处理过，直接返回上次的结果而不重复执行。这是抵抗"客户端超时重发"的第一道防线。第二层：任务级幂等。taskId由服务端生成，天然不会撞；但客户端若想"同一个业务意图只产生一个任务"，需要在metadata或扩展字段里携带业务幂等键，服务端按业务键查重建任务。第三层：会话级连续性。contextId让重试后的消息正确落回原会话，避免上下文断裂。三层各司其职：messageId防消息重放，业务键防任务重复，contextId保上下文连续。

## 设计误区与正确姿势

误区一：拿taskId当幂等键。taskId是服务端产物，客户端发请求时还没有它，第二次重试也拿不到同一个taskId（除非续写），根本无法承担幂等职责。误区二：messageId用自增序号。跨进程重启后序号回卷，查重失效；必须用全局唯一且跨重启稳定的生成方式（随机标识、内容哈希加随机数）。误区三：查重窗口不设期限。幂等记录永久保留既贵又危险——半年后同一messageId重现可能是业务上合法的新意图；应设去重窗口（如24到72小时），窗口外重复按新请求处理。误区四：查重与执行不原子。查到无记录后、执行前，另一个并发请求也查到无记录，双双执行。需要以幂等键为唯一约束做原子插入占位。

## 幂等占位的实现示意

```sql
-- 幂等表以 message_id 为唯一约束，占位即插入
INSERT INTO idempotency (message_id, task_id, state, created_at)
VALUES (:message_id, :new_task_id, 'PENDING', :now)
ON CONFLICT (message_id) DO NOTHING;
-- 影响行数=1 => 首次请求，继续执行
-- 影响行数=0 => 重复请求，读取已有记录并回放结果

SELECT task_id, state, result_ref FROM idempotency
WHERE message_id = :message_id;
-- state=PENDING：前序请求仍在执行，稍候再查或等待回调
-- state=DONE   ：直接返回 result_ref，不重复执行
```

## 幂等键设计要点清单

- [ ] messageId客户端生成、全局唯一、跨重启稳定；
- [ ] 业务幂等键放扩展字段，服务端按键查重建任务；
- [ ] contextId保会话连续，重试消息回落原上下文；
- [ ] 去重记录设窗口期限，窗口外按新请求处理；
- [ ] 占位插入以唯一约束保证原子，防并发双执行；
- [ ] PENDING状态的重复请求返回"处理中"而非报错；
- [ ] 幂等记录里存结果引用而非大对象，控制存储成本。

## 小结

幂等键体系是三层分工的精巧结构：messageId管消息重放，业务幂等键管任务重复，contextId管上下文断裂。设计上的四条红线——别拿taskId当幂等键、别用回卷序号、别无限期查重、别让查重与执行脱节——每一条都是实战血泪。占位加唯一约束的原子模式，则是把幂等从口头承诺变成物理保证的关键一步。
