# 14. 状态回放：通过历史Artifact与Message重建任务轨迹

## 概述：生命周期要能倒着读

任务向前跑，工程却经常需要向后读：故障排查要还原"当时到底发生了什么"，审计合规要证明"结果是怎么来的"，客户端崩溃恢复要重建"我消费到哪里了"，新接管的观察者要理解"这个任务经历了什么"。回放能力就是把任务生命周期从单向流逝变成可倒放的关键：基于持久化的历史消息、状态时间线与产出物序列，重建任务在任意时刻的视图。没有回放能力的系统，每次故障排查都是考古现场。

## 回放的三类素材

素材一：状态时间线。任务记录里保存每次状态迁移的（状态、时间戳、触发原因）三元组序列，构成生命周期的骨架。落库方式可以是状态历史表（每次迁移插一行），也可以是事件日志的投影。素材二：消息历史。task.history里的往来消息，按序号与方向排列，展示双方的对话过程。素材三：产出物版本链。Artifact按artifactId分组、按追加序号排列，配合lastChunk/append标记，可以重建产出物逐块成型的过程。三类素材的共同要求是追加不可改：回放的前提是历史不可篡改，这与终态不可变约束一脉相承。

## 回放模式与实现要点

模式一：快照加日志。任务当前状态是快照，历史是日志，任意时刻视图等于初始快照重放日志至该时刻。查询接口暴露historyLength即可实现窗口回放。模式二：事件溯源。把状态迁移本身建模为事件序列存储，当前状态是事件的折叠结果，回放即全量折叠。适合需要完整审计链的场景，代价是查询要做投影。模式三：对账式重建。客户端侧的轻量回放：本地缓存已收事件加tasks/get全量快照比对，找出缺口并补齐，用于断线恢复。实现要点包括：回放接口要支持按时间或序号截取；回放结果与实时快照要有一致性校验手段（比对终态与事件计数）；回放读路径与在线写路径隔离，避免排查查询拖慢生产。

## 回放重建示意

```python
def replay(task_id, upto_seq=None):
    events = store.load_events(task_id, upto=upto_seq)
    view = {"state": "submitted", "messages": [], "artifacts": {}}
    for ev in events:
        if ev.kind == "status-update":
            view["state"] = ev.state           # 按序折叠状态
        elif ev.kind == "message":
            view["messages"].append(ev.message)
        elif ev.kind == "artifact-update":
            bucket = view["artifacts"].setdefault(ev.artifact_id, [])
            bucket.append(ev.chunk)            # 追加重建产出物
            if ev.last_chunk:
                view["artifacts"][ev.artifact_id] = merge(bucket)
    return view                                 # upto_seq=None 即完整轨迹

def verify_replay(task_id):
    v = replay(task_id)
    snap = store.load_task(task_id)             # 当前权威快照
    assert v["state"] == snap.status.state, "回放与快照不一致"
```

## 回放能力要点清单

- [ ] 状态时间线、消息历史、产出物版本链三类素材追加式保存；
- [ ] 历史记录不可篡改，与终态不可变同样刚性；
- [ ] 回放接口支持窗口截取（按序号或时间）；
- [ ] 回放结果与权威快照有一致性校验（状态与计数对账）；
- [ ] 回放读路径与在线写路径隔离，防排查压垮生产；
- [ ] 客户端崩溃恢复用轻量对账式回放：本地缓存加get补缺；
- [ ] 审计场景保留完整事件链，满足可解释性要求。

## 小结

回放让任务生命周期拥有记忆：状态时间线给骨架，消息历史给血肉，产出物版本链给成果演化。快照加日志、事件溯源、对账重建三种模式按需选用，一致性校验保证倒放与正放同真。可回放的任务系统，才经得起故障排查、审计合规与崩溃恢复三重拷问。
