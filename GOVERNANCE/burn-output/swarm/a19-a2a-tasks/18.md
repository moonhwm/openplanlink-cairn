# 18. exactly-once消费的挑战：双边际竞态

## 概述：为什么精确一次这么难

exactly-once消费的承诺是"每条消息恰好被处理一次"，但朴素实现总在两个边缘上翻车：处理成功但确认丢失，重试导致重复处理；先确认再处理，崩溃导致消息丢失。这两个边缘合成所谓双边际竞态——任何"处理"与"确认"的先后安排，单独看都合理，组合起来不是重复就是丢失。理解这对矛盾的不可调和性，才能明白为什么真正的解法不是寻找完美时序，而是把处理与确认绑进同一个原子边界。

## 双边际的两种翻车剧本

剧本一：先处理后确认。消费者执行完业务逻辑，正要提交消费位移时崩溃。重启后位移未提交，消息被重新投递，业务逻辑再执行一遍——重复处理。窗口虽小但高频场景下必然命中，且业务副作用（扣减、发通知、写结果）已经出门，无法收回。剧本二：先确认后处理。消费者先提交位移再处理消息，处理中途崩溃。重启后位移已前移，消息不会重投——丢失处理。比重复更严重，因为连"发生了什么"的痕迹都没有。两种剧本互为镜像，单纯调整顺序只是把风险从一种失败换成另一种。

## 解法的本质：坍缩原子边界

所有可信的exactly-once方案共享同一本质：把"记录已消费"与"执行副作用"放进同一个原子提交里，让外部观察者看不到中间态。落地形态有三种。形态一：共享事务。消费位移与业务结果写同一个数据库，一个事务提交，崩溃后要么都生效要么都不生效，重投时靠业务幂等键识别已处理。形态二：两阶段写入加幂等。位移系统与业务存储分离时（如消息队列加数据库），接受至少一次投递，在业务侧建幂等表：处理前原子占位，重投命中占位即跳过。形态三：单写者分区。让同一分区同一时间只有一个消费者持有独占租约，配合租约内批量原子提交，减少并发面。三种形态殊途同归：原子边界内做判定，边界外只见结果。

## 共享事务的骨架示意

```sql
BEGIN;
  -- 业务副作用
  INSERT INTO task_results (task_id, artifact_ref, ...)
  VALUES (:task_id, :artifact_ref);
  -- 幂等占位（唯一约束）：重投时本事务整体失败回滚
  INSERT INTO consumed_events (event_seq, task_id)
  VALUES (:event_seq, :task_id);
  -- 消费位点（与业务同库才可行）
  UPDATE consumer_offsets
  SET last_seq = :event_seq
  WHERE consumer_id = :consumer_id AND last_seq < :event_seq;
COMMIT;
-- 重投场景：consumed_events 撞唯一约束 => 事务回滚 => 上层识别为已消费，跳过
```

## 双边际治理要点清单

- [ ] 处理与确认不允许存在可观察的中间态，先想原子边界再写代码；
- [ ] 位移与业务可同库时用共享事务，一锤定音；
- [ ] 位移与业务分离时业务侧建幂等表，占位唯一约束兜底；
- [ ] 幂等记录保留期覆盖最大重投窗口（含故障停机时长）；
- [ ] 消费者重启后从已提交位点恢复，不凭内存记忆；
- [ ] 分区独占租约减少并发面，租约过期要有 fencing 防僵尸写；
- [ ] 对账任务周期性比对事件源与已处理表，兜住漏网。

## 小结

双边际竞态揭示了exactly-once的真相：不存在完美的时序安排，只存在被坍缩掉的中间态。共享事务、幂等占位、单写者租约三种形态都是原子边界的变体。把"已消费"的记录与副作用的执行焊进同一个提交，两个边缘同时消失，剩下的只是需要耐心设计的工程细节。
