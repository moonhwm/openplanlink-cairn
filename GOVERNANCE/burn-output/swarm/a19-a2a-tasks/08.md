# 08. 非终态与终态的划分：为何如此设计

## 概述：二分的深层动机

把任务状态切成"非终态"与"终态"两个世界，是A2A任务模型里最重要的一次二分。它回答了一个分布式系统的根本问题：什么时候可以释放资源、停止等待、开始消费结果、做最终决策？终态集合的存在，给了这个问题一个协议级的、无歧义的答案。理解这次二分的设计动机，比记住枚举本身更重要——因为所有围绕重试、超时、清理、对账的工程决策，都从"是否终态"这一个问题派生出来。

## 终态的三条设计判据

一个状态被划入终态，通常满足三条判据。第一，事实已闭合：任务的结果性质已经确定（成功、失败、取消、拒绝、失管），不存在"再等等也许会变"的可能。第二，承诺已终止：服务端不再对该任务的推进做任何承诺，不再调度算力，不再发送状态更新；客户端也不再需要保持任何等待结构。第三，记录不可变：终态落定后，任务快照进入只读区间，后续任何读取都应得到同一结果。这三条判据共同保证了终态的"不可逆、可缓存、可归档"三重性质，也让终态成为天然的缓存失效边界与审计锚点。

## 非终态的暂停谱系

非终态一侧则构成一个"暂停谱系"：submitted与queued是资源性等待（还没轮到），working是执行性进行（正在做），input-required与auth-required是交互性等待（等对方动作）。谱系的意义在于：不同类型的非终态对应不同的客户端策略与不同的超时基线。资源性等待适合长超时加周期性探活；执行性等待适合流式观察或心跳容忍；交互性等待则需要明确的用户通路与提醒升级机制，因为它们等待的对象不是系统而是人。把非终态一律当成"还在跑"处理，是生命周期管理中最常见的粗糙化错误，直接后果是input-required任务被超时策略误杀。

## 划分带来的工程红利

二分结构给实现带来了三重红利。其一，等待循环可以写成统一骨架：循环观察状态，终态即退出，非终态按类型分派策略，逻辑清晰且可测试。其二，缓存与失效简单：任务终态后快照永不变，可以放心长缓存；非终态期间快照随时可能更新，只能短缓存或不缓存。其三，清理策略有明确起点：归档、TTL计费、存储降级，都从终态时刻起算。反过来，如果终态集合不封闭、允许"复活"，这三重红利全部崩塌——这正是下一批文档要展开的"终态不可逆约束"。

```python
def lifecycle_loop(task_id):
    while True:
        task = fetch(task_id)
        state = task["status"]["state"]
        if is_terminal(state):
            return task                    # 闭合：唯一出口
        dispatch_non_terminal(state, task) # 分派：等待/输入/授权
        sleep_with_backoff()
```

## 划分要点清单

- [ ] 终态判据：事实闭合、承诺终止、记录不可变；
- [ ] 非终态谱系：资源性等待、执行性进行、交互性等待三类；
- [ ] 交互性等待必须有用户通路与升级机制，不能靠系统超时兜底；
- [ ] 等待循环以"终态是唯一出口"为骨架；
- [ ] 缓存策略以终态为失效边界；
- [ ] 清理与计费从终态时刻起算。

## 小结

终态与非终态的二分不是枚举的简单归类，而是分布式协作的契约基石：它定义了资源释放的边界、结果消费的许可、记录冻结的时刻。非终态内部的暂停谱系进一步指导差异化等待策略。掌握二分，等于掌握了任务生命周期工程决策的总开关。
