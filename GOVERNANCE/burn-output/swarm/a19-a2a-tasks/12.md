# 12. 服务端状态机的持久化与恢复

## 概述：状态机活着，更要活得过重启

服务端任务状态机如果只活在内存里，一次进程重启、一次部署滚动、一次实例漂移，就会让所有在途任务变成孤儿：客户端还在等，服务端已失忆。生产级实现必须把状态机状态持久化，并在进程恢复时把未终态任务重新接管。持久化与恢复设计的核心矛盾是：状态迁移要低延迟（高频小写入），恢复要完整（状态加执行进度可重建），两者对存储与写入路径的要求不同。

## 持久化内容的三层结构

第一层是任务记录本体：taskId、contextId、当前状态、时间戳、元数据，这是tasks/get与迁移校验的依据，每次状态变化都要原子落库。第二层是消息与产出物：history消息、Artifact块，追加式写入，量大但可异步化，策略上允许短暂不可见换取吞吐。第三层是执行器私有进度：代理内部的阶段指针、中间变量、外部调用游标。这层不属于协议字段，但不落库就无法恢复执行；通用做法是执行器周期性把进度检查点写进任务metadata或独立进度表，恢复时从最近检查点续跑或降级重跑。三层分开管理，各自选择写入时机与存储介质，避免"全量同步写"把状态机拖成瓶颈。

## 恢复流程与接管语义

进程启动时执行三步恢复。第一步扫描：查询所有非终态任务，按状态分类。第二步接管：working任务重新调度执行（从检查点续跑或按策略重跑），queued任务重新入队，submitted任务补启动；input-required与auth-required任务无需执行接管，它们等的是客户端动作，只需恢复观察通路（重新登记推送、允许get）。第三步对账：与事件流的已发事件比对，恢复期间若错过状态变化（例如崩溃前已迁working但事件未发），补发或依赖客户端对账机制。接管语义必须幂等：实例可能多次重启，重复接管同一任务不能产生重复执行或重复产出——这为exactly-once话题埋下伏笔。

## 持久化与恢复的实现示意

```python
class TaskStore:
    def transition(self, task_id, new_state, extra=None):
        # 原子条件更新：终态不可改 + 并发安全
        n = db.execute(
            "UPDATE tasks SET state=:s, ts=:t WHERE task_id=:id "
            "AND state NOT IN ('completed','failed','canceled','rejected','unknown')",
            {"s": new_state, "t": now(), "id": task_id})
        if n == 0:
            raise IllegalTransition(task_id, new_state)
        self.outbox.append(task_id, new_state)  # 与状态同事务写事件发件箱

    def recover(self):
        for task in db.query("SELECT * FROM tasks WHERE state NOT IN (...)"):
            if task.state in ("working", "queued", "submitted"):
                scheduler.enqueue(task, resume_from=task.checkpoint)
            # input-required / auth-required：仅恢复观察通路
            watcher.rebind(task)
```

## 持久化恢复要点清单

- [ ] 状态迁移用条件更新原子落库，终态物理不可改；
- [ ] 状态变化与事件发布写同一事务（发件箱模式），防状态与事件脱节；
- [ ] 三层内容分开：任务记录同步写、消息产出物异步追加、执行检查点周期写；
- [ ] 恢复按状态分类接管：执行类重调度、等待类只恢复观察；
- [ ] 接管幂等，多次重启不产生重复执行；
- [ ] 恢复期与客户端对账机制衔接，容忍短暂信息差。

## 小结

服务端状态机的持久化是"活得过重启"的保险：三层内容分而治之，条件更新守住终态不可变，发件箱绑住状态与事件的一致。恢复流程则按状态分类接管，执行类重新调度、交互类恢复观察，且全程幂等。这套地基打牢之后，才谈得上更高阶的分布式扩展与精确一次执行语义。
