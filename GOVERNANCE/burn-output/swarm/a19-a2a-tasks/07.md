# 07. TaskState枚举全解：从submitted到terminal

## 概述：状态是生命周期的语言

任务生命周期的一切对话都围绕TaskState展开：客户端按状态决定等待、补充输入还是收尾；服务端按状态执行迁移、清理与通知。A2A规范定义了一组明确的状态枚举，每个状态都有"谁可以看到它、何时进入、下一步去哪"的完整语义。把枚举当成协议词汇表逐词精读，是避免生命周期实现歧义的基本功。需要注意的是，不同协议版本对枚举集有过微调，实现时应以所用版本的规范文本为准，但核心骨架长期稳定。

## 非终态逐项解析

submitted表示服务端已受理任务、尚未开始实质执行，是多数任务的起点。queued表示任务进入排队区，等待执行资源，常见于高并发网关后面的场景，它让客户端能区分"没开始"与"开始了但慢"。working表示代理正在执行，期间可穿插多条working状态更新，用于心跳式报活与进度粗报。input-required表示任务暂停等待客户端补充信息——表单确认、缺失参数、澄清问题都会落到这个状态，客户端必须响应（续写消息）或取消，否则任务将长期悬挂。auth-required表示任务需要补充认证或授权才能继续，典型于调用过程中发现权限不足，客户端完成授权流程后推动任务恢复。这五个状态共同构成"可继续"区间：任务还活着，未来仍开放。

## 终态逐项解析

completed表示任务成功终结，产出物齐备，客户端可消费结果。failed表示执行失败，status.message通常携带失败原因，客户端按错误分类决定重试或上报。canceled表示任务被取消成功终结，可能是客户端主动申请，也可能是服务端策略性中止。rejected表示服务端在受理阶段即拒绝执行——能力不匹配、参数非法、策略禁止等，它与failed的区别在于"没做"与"做了没成"。最后是unknown：这是一个特殊状态，服务端用它声明"任务生命周期已超出本方管理范围"——例如任务已过期清理、任务归属已转移，它同样是终态语义，客户端收到后应停止一切重试，转入重新提交或人工介入流程。

## 状态判断的实现示例

```python
TERMINAL_STATES = {"completed", "failed", "canceled", "rejected", "unknown"}

def on_state(task):
    state = task["status"]["state"]
    if state in TERMINAL_STATES:
        finalize(task)          # 终态：收尾、释放资源、审计归档
    elif state == "input-required":
        prompt_user_input(task) # 等待输入：发起交互或按策略取消
    elif state == "auth-required":
        start_auth_flow(task)   # 补充授权后恢复
    else:
        keep_waiting(task)      # submitted/queued/working：继续观察
```

## 状态语义要点清单

- [ ] 非终态：submitted、queued、working、input-required、auth-required；
- [ ] 终态：completed、failed、canceled、rejected、unknown；
- [ ] 终态不可逆，任何实现不得从终态迁出；
- [ ] input-required与auth-required需要客户端显式响应，否则任务悬挂；
- [ ] unknown意味着生命周期结束且不可续，应停止重试；
- [ ] 状态判断逻辑集中在单一模块，避免散落各处的if-else分叉。

## 小结

TaskState枚举是任务生命周期的语法：五个非终态描述"进行中的各种暂停形态"，五个终态描述"结束的各种方式"。其中input-required与auth-required最容易被忽视——它们不是失败，而是等待；unknown最容易被误读——它不是未知，而是不再归我管。逐词吃透枚举语义，状态机实现才有可靠的地基。
