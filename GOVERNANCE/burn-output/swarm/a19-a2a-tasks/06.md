# 06. 任务推送通知（pushNotification）机制与webhook配置

## 概述：反转控制的方向盘

流式订阅要求客户端保持长连接，这对服务器间协作并不友好——调用方往往是后端服务，无法常驻一条SSE连接等结果。推送通知机制反转了控制方向：客户端预先登记一个webhook地址，任务状态发生关键迁移（尤其是进入终态）时，服务端主动向该地址发送通知。这样客户端只需一个常驻的接收端点，就能服务成千上万个并发任务，无需为每个任务维持连接。推送通知与流式订阅并不互斥：前者负责关键节点唤醒，后者负责细粒度观察，混合使用是常见架构。

## 配置方法与协议动词

推送配置通过独立的管理动词完成：tasks/pushNotificationConfig/set写入配置，get读取，list列举，delete删除。配置的核心字段包括：url即回调地址；token是客户端提供的验证令牌，服务端回显在通知中以供接收方确认来源；authentication携带向webhook端点认证所需的凭据方案（如Bearer方案，凭据本体由安全渠道管理，绝不在协议报文中明文传输密钥）；可选的eventTypes收窄触发范围。配置粒度可以是单个任务，也可以绑定到contextId让整个会话的任务复用。示例配置如下，注意其中没有任何真实密钥，仅示意结构。

```json
{
  "jsonrpc": "2.0",
  "id": "req-2001",
  "method": "tasks/pushNotificationConfig/set",
  "params": {
    "taskId": "task-7f3a2b",
    "pushNotificationConfig": {
      "url": "https://ops.example.internal/hooks/a2a-task",
      "token": "random-nonce-issued-by-client",
      "authentication": {
        "schemes": ["bearer"]
      }
    }
  }
}
```

## 通知的签名验证

推送通知必须验证真实性，防止伪造回调注入假终态。业界通行做法是服务端用非对称密钥对通知体签名（如JWT或HTTP签名），接收方通过JWKS端点获取公钥验签。验证链条包括：校验签名与时间窗、校验token回显与预期一致、校验taskId属于本方发起的任务、校验状态迁移合法。任何一环失败都应拒收并告警。接收端处理通知后应返回2xx确认；通知投递通常带重试策略，接收方要保证处理幂等——同一通知重复到达不产生重复副作用，这与任务幂等语义一脉相承。

## 推送链路工程要点清单

- [ ] webhook地址必须走传输加密，端点不可暴露在公网无认证状态；
- [ ] token由客户端生成，接收端逐条比对，防跨任务伪造；
- [ ] 验签公钥通过JWKS动态获取，支持密钥轮换；
- [ ] 通知处理幂等，重复投递不产生重复副作用；
- [ ] 通知只是唤醒信号，任务真相仍以tasks/get快照为准；
- [ ] 收到终态通知后拉取快照对账，再驱动下游流程；
- [ ] 配置支持任务级与会话级两层，避免逐任务重复登记；
- [ ] 对通知端点做限速与来源校验，防被打爆。

## 小结

推送通知把任务生命周期的"知道结果"这一刻从拉模式变成推模式，是服务器间大规模协作的基础设施。安全上它引入了新的信任边界，签名验证与token回验缺一不可；语义上它只是唤醒信号，任务真相永远回到tasks/get对账。配置管理、验签、幂等消费三件事做好，推送链路才算真正可用。
