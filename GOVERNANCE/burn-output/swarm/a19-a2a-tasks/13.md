# 13. 多Agent协作场景下的复合状态机

## 概述：任务生任务，状态套状态

单个任务是台面上的状态机，多代理协作则掀开了台面下面更复杂的一层：一个编排代理接收任务后，把工作拆给多个执行代理，每个子代理又有自己的任务生命周期。于是出现了复合状态机——父任务的状态不再是简单枚举的直线推进，而是由子任务状态聚合派生。复合状态机的正确性，决定了"看起来一个任务"的背后几十个协作实体能否步调一致。

## 两种编排拓扑

拓扑一：顺序链。子任务依次执行，前一个的产出作为后一个的输入，父状态近似为"当前子任务的状态"。实现简单，恢复容易，但延迟叠加、无并行收益。拓扑二：并行扇出聚合。父任务同时派发N个子任务，聚合策略决定父状态：全部成功才算completed；任一失败即failed（快速失败）；或按配额容忍部分失败（如十取七）。并行拓扑下父状态是子状态的函数，聚合函数的选择就是业务语义的选择，必须在编排层显式声明，不能含糊。混合形态（DAG）则是两者的组合，用依赖图表达先后与并行。

## 父状态派生与一致性挑战

复合状态机的核心难题是父状态与子状态的因果一致。第一，派生即时性：子任务落终态后，父状态应尽快重算，但"尽快"不能以乱序为代价——子任务终态事件可能乱序到达编排层，派生逻辑必须基于全量子任务快照而非增量流水。第二，取消的级联：父任务canceled应级联取消所有未终态子任务，反过来单个子任务canceled未必取消父（取决于聚合策略）。第三，恢复的分层：编排层重启后既要恢复父任务状态机，也要逐个接管子任务，两层恢复的顺序与幂等要分别成立。第四，input-required的上浮：子任务等待输入时，父任务对客户端呈现的应是统一的input-required，输入内容要路由回正确的子任务，这要求编排层维护父子映射并做输入路由。

## 编排层聚合器示意

```python
AGGREGATORS = {
    "all-must-succeed": lambda rs: "completed" if all(
        r == "completed" for r in rs) else (
        "failed" if any(r in ("failed", "rejected") for r in rs)
        else "working"),
    "quorum": lambda rs, q: ("completed" if sum(
        r == "completed" for r in rs) >= q else
        "failed" if sum(r in ("failed", "rejected", "canceled")
                        for r in rs) > len(rs) - q else "working"),
}

def on_child_terminal(parent_id):
    kids = store.children_of(parent_id)
    new_state = AGGREGATORS[parent.policy](
        [k.state for k in kids], parent.quorum)
    if is_terminal(new_state):
        for k in kids:                     # 级联取消未终态子任务
            if not is_terminal(k.state):
                cancel_task(k.id)
    parent.transition(new_state)           # 原子迁移父状态
```

## 复合状态机要点清单

- [ ] 聚合策略显式声明：全成功、快速失败、配额容忍三选一或有据自定义；
- [ ] 父状态派生基于全量子任务快照，防乱序增量误判；
- [ ] 父取消级联子任务，子终态按聚合策略影响父；
- [ ] 子任务input-required上浮为父任务输入等待并正确路由；
- [ ] 两层恢复各自幂等，顺序为先子后父对账；
- [ ] 父子血缘关系持久化，供审计与追踪穿透；
- [ ] 子任务数量设上限，防扇出爆炸拖垮系统。

## 小结

复合状态机把任务生命周期从单体扩展到编队：聚合策略定义父子状态的换算律，级联规则定义取消的传播律，上浮路由定义输入的传导律。三层规则都写进编排层的显式代码，而不是散落在各代理的隐式默契里，多代理协作才能在故障与重启之下依然步调一致。
