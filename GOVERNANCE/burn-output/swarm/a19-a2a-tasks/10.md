# 10. terminal状态之后的行为约束：不可变区间

## 概述：终点之后没有剧情

任务落入终态后，生命周期进入"不可变区间"：状态不再变、核心字段不再改、结果不再追加。这条约束看似简单，却是整个信任模型的支柱。客户端之所以敢在看到completed的瞬间触发下游流程、敢把终态快照写进本地缓存与结算记录，正是因为协议承诺这个结果永不再变。任何"终态后还想改点什么"的冲动——补一条产出物、改一下失败原因、把failed修正为completed——都必须被架构性禁止，或者通过规范的新机制（如重新提交新任务）来表达。

## 服务端约束：落库与访问两层

服务端的不可变约束分两层。落库层：终态记录物理上禁止更新，实现手段包括条件更新（update where state not in terminal）、触发器拦截、或终态记录迁移到只读归档表后原表删除。访问层：tasks/get对终态任务永远返回同一快照；tasks/send对终态任务的续写请求返回错误而非创建变体；tasks/cancel对终态任务返回错误；事件流对终态任务不再有新事件，final事件已是最后一条。两层缺一不可：只做访问层拦截，内部任务仍可能被改，审计对账时就会翻车；只做落库层拦截，协议出口可能被劣质代码绕过。

## 客户端约束：消费终态的正确姿势

客户端同样要遵守不可变区间的纪律。第一，终态即停止观察：收到终态后退出等待循环、退订事件流、注销推送配置，不要继续占用资源。第二，终态即最终决策依据：基于completed触发交付、基于failed决定重试（重试是提交新任务，不是复活旧任务）、基于canceled做清理。第三，终态快照可以长期缓存：键是taskId，值是整个快照，无需失效策略。第四，警惕"终态后又收到事件"的异常：合法场景仅限迟到的传输层残余（final之后通道里残留的少量数据），任何声称状态又变化的事件都应视为对端违约，以tasks/get快照裁决并上报。

## 不可变区间的实现示意

```sql
-- 落库层：条件更新保证终态不可改
UPDATE tasks
SET status_state = :new_state,
    status_timestamp = :now
WHERE task_id = :task_id
  AND status_state NOT IN
      ('completed','failed','canceled','rejected','unknown');
-- 影响行数为0 => 非法迁移或竞态，拒绝并告警
```

```python
def submit_followup(original_task, new_message):
    if is_terminal(original_task.status.state):
        # 不复活旧任务：派生新任务，血缘上挂接旧任务
        return create_task(
            context_id=original_task.context_id,
            message=new_message,
            metadata={"derived_from": original_task.id},
        )
```

## 不可变区间要点清单

- [ ] 终态落库用条件更新或归档只读表物理保证；
- [ ] 协议出口（get/send/cancel/事件流）对终态行为一致；
- [ ] 重试等于新任务加血缘标注，不等于复活旧任务；
- [ ] 终态快照可长期缓存，键为taskId；
- [ ] 收到"终态后再变化"信号视为对端违约，以快照裁决；
- [ ] 审计与结算以终态时刻为锚点，读取具备可重放性。

## 小结

不可变区间是终态承诺的物理化身：落库层锁死记录，访问层锁死行为，客户端侧锁死消费纪律。所有"改结果"的需求都被引导到"派生新任务"的正道上，血缘关系保住可追溯性。守住这条区间，终态才配作为下游一切决策的最终依据。
