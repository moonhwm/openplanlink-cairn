# 01. A2A协议中Task对象的核心地位与生命周期总览

## 概述：为什么任务是一等公民

A2A（Agent2Agent）协议把跨代理协作的核心抽象定为Task（任务），而不是单纯的请求-响应。设计动机在于：大模型代理的工作往往耗时不可预测、产出分阶段到达、过程需要可观察、结果需要可追溯。如果沿用一次性的无状态调用，客户端只能阻塞等待或盲目轮询，既浪费连接资源，也无法表达"取消""续传""补齐"这类生命周期语义。任务对象因此成为协议中的一等公民：它有服务端分配的唯一标识taskId，有贯穿会话的contextId，有一组明确定义的状态，以及挂在其下的消息与产出物集合。理解任务生命周期的第一步，是把任务看成"协议层的工单"：提交、受理、执行、产出、终结五个环节环环相扣，每个环节都有对应的协议动词与状态语义。

## 任务在协议中的定位

任务承担三重职责。第一，它是对话锚点：客户端发出消息后得到taskId，此后查询进度、订阅事件流、请求取消、配置推送通知，全部以taskId为参数展开；contextId则把同一会话内的多个任务与消息串成上下文链，服务端可据此维持多轮记忆。第二，它是结果容器：任务下的Artifact（产出物）与Message（中间消息）按时间顺序累积，客户端既可以流式消费，也可以事后整体拉取。第三，它是治理单元：配额计量、审计留痕、超时回收、重试去重，都以任务为自然粒度，这使得跨组织协作具备了可结算、可追责的基础。

## 生命周期五阶段总览

任务生命周期可以划分为五个阶段。提交阶段：客户端通过tasks/send或tasks/sendSubscribe把消息投给远端代理，服务端校验后创建任务并返回初始状态（submitted或queued）。执行阶段：代理进入working状态，期间可能发出多条状态更新与增量产出物，也可能转入input-required等待客户端补充输入。产出阶段：Artifact逐步落位，客户端边收边用。终结阶段：任务落入completed、failed、canceled、rejected四类终态之一，此后任何状态变更都不被协议允许。归档阶段：任务记录在服务端保留一段时间供对账与审计，最终由清理策略回收。每个阶段都有独立的失败模式，这正是后续四十七个子题逐一展开的骨架。

## 核心字段与结构示例

一个典型的任务对象包含以下关键字段：kind标识这是task而非message；id即taskId；contextId关联会话；status包含state与可选的message与timestamp；artifacts数组承载产出物；history数组保存历史消息（按需返回）；metadata承载扩展字段。

```json
{
  "kind": "task",
  "id": "task-7f3a2b",
  "contextId": "ctx-91c0",
  "status": {
    "state": "working",
    "timestamp": "2026-08-27T14:03:22Z"
  },
  "artifacts": [
    {
      "artifactId": "art-1",
      "name": "draft-report",
      "parts": [{ "kind": "text", "text": "第一章节草稿……" }]
    }
  ],
  "history": [],
  "metadata": {}
}
```

## 生命周期管理要点清单

- [ ] 每个任务必须有服务端生成的全局唯一taskId，客户端不得自造；
- [ ] contextId与会话绑定，用于串联多轮交互与多个任务；
- [ ] 状态枚举以协议规范为准，服务端不得私造终态；
- [ ] 终态一旦落定，任务即进入不可变区间；
- [ ] 产出物与中间消息分离存放，便于流式与整体两种消费方式；
- [ ] 元数据字段只放扩展信息，不承载核心状态。

## 小结

任务对象是A2A协议的脊柱，提交、执行、产出、终结、归档五个阶段构成完整生命周期。把任务当工单管理，而不是当请求处理，是构建可靠跨代理系统的心法。后续文档将分别深入提交语义、状态机、幂等去重、游标消费等专题，逐一拆解每个阶段的工程细节。
