# 直方图与分位数：P50/P95/P99时延的正确计算与解读

> 一句话摘要：本文讲清直方图分位数（quantile）的估计原理、桶边界设计、跨实例聚合的正确姿势、平均值的陷阱，以及分位数告警与SLO统计的实践要点。

## 一、为什么平均值会撒谎，分位数说什么

时延分布是重尾的：大多数请求快、少数请求极慢。平均值被长尾拉高，掩盖两头真相——P50两百分秒、P99两秒的系统平均可能是三百毫秒，看起来"还行"，但每一百次访问就有一次糟糕体验。分位数把分布摊开：P50（中位数）代表典型体验，P95代表"二十次里最差那次"，P99代表重度用户的日常（活跃用户请求多，撞上长尾的概率远高于一次性的数学直觉），P99.9用于识别极端离群。解读纪律：报耗时必须带分位数而非只报均值；对比两个版本必须对比同分位数；P99波动大是常态（样本少），判断劣化要看持续趋势与置信区间，不做单点惊呼。

## 二、直方图如何估计分位数：桶与插值

Histogram不存每个值，而是把观测值落入预设桶并累计计数：le=10ms桶、le=50ms桶……查询P95时找到累计计数达到总数百分之九十五的桶，再用桶内线性插值估计具体值。这带来两个直接推论。推论一：桶边界决定精度——P95恰好落在宽桶（如100ms到500ms之间只有一个边界）时，插值误差可达桶宽的一半；想准确监控P95=300ms，边界应在250/300/350附近密布。推论二：分位数可以跨实例正确聚合——各实例上报的是桶计数，聚合端把各实例同桶计数相加再算分位数，数学上依然正确（这正是Histogram优于Summary的原因，第25篇）。桶设计建议：十到十五个桶，边界围绕SLO阈值与关键档位（如100/200/300/500/800/1200/2000/5000ms）；边界一旦上线不可随意改（同指标两套桶无法聚合），改桶等于换指标名做迁移。

Histogram查询示意（PromQL）：

```text
# P95耗时（跨全部实例聚合后计算，先sum再算quantile）
histogram_quantile(0.95,
  sum by (le, function) (rate(invoke_duration_ms_bucket[5m])))

# 错误做法：先算各实例P95再平均 —— 分位数不可平均
avg(histogram_quantile(0.95, rate(invoke_duration_ms_bucket[5m])))  # ✗

# SLO：800ms内完成的请求占比（快于阈值的比例）
sum(rate(invoke_duration_ms_bucket{le="800"}[5m]))
  / sum(rate(invoke_duration_ms_count[5m]))

# apdex近似：(满意+0.5×容忍)/总数，用桶计数直接组装
( sum(rate(bucket{le="300"}[5m])) + 0.5*sum(rate(bucket{le="1200",le!="300"}[5m])) )
  / sum(rate(count[5m]))
```

## 三、聚合粒度、窗口与噪声

分位数查询的稳定性受三个参数影响。窗口（range）：rate的窗口决定样本量，五分钟窗口在高QPS下P99稳定、低QPS函数（每分钟十次调用）五分钟只有五十个样本，P99本质是"最慢那次"，波动剧烈——低流量函数应放宽窗口（三十分钟）或改用"SLO达标率"这种比例型SLI（比例比分位数对样本量更鲁棒）。聚合维度：按函数聚合是默认；按版本聚合对比是刚需（发布回归检测）；但多维同时切（函数×版本×地域×渠道）会把每格样本摊薄，噪声放大，看板设计要克制维度。步长（step）：告警查询步长太细会锯齿误报，太粗会延迟感知，典型一到三分钟。

## 四、分位数告警的实践

分位数告警的三种模式。模式一阈值型：P95>SLO阈值持续五分钟告警——简单常用，注意加"持续"条件抗毛刺。模式二基线型：P95相对上周同时刻劣化超百分之三十告警——捕捉"仍在阈值内但显著劣化"的回归，适合已长期达标的成熟服务。模式三燃烧率型（第06篇）：把"分位数超标的请求视为失败"定义延迟SLI，按错误预算燃烧率告警——与可用性SLO统一治理，是高级形态。此外永远配置P99看板但不建议直接对P99做页级告警（噪声大），P99更多用于事后分析与容量规划（按P99×并发预留容量）。

分位数实践检查清单：

```text
[ ] 一切耗时展示带分位数；对比同分位数；均值仅辅助
[ ] 桶边界围绕SLO阈值布点；10-15桶；边界不轻易改
[ ] 跨实例先sum桶计数再quantile；禁止分位数平均
[ ] 低流量函数放宽窗口或改达标率SLI
[ ] 分位数告警：阈值持续型/环比基线型/燃烧率型三选或组合
[ ] P99看板必有、页级告警慎用；容量规划用P99
```

## 五、分位数误用的三个真实案例

案例一"平均P95"：某团队看板把各区域P95求平均当全局P95汇报，多区域负载差异使真实全局P95比汇报值高四成，SLO达标判断长期失真——修复为全局桶聚合后计算。案例二"桶太宽"：直方图桶边界设为零点一秒与一秒两档，监控目标P95=三百毫秒的服务时P95永远显示为区间中点，优化前后的变化完全不可见——按目标值加密桶边界后才有分辨率。案例三"低流量P99惊魂"：每分钟十次调用的函数，五分钟窗口P99就是最慢一次请求，锯齿状曲线触发多次误告警——改为三十分钟窗口加最小样本量条件后平稳。三个案例的共同教训：分位数是分布的函数，脱离样本量、桶设计、聚合方式谈分位数数值都是危险的。

## 六、把分位数教给团队

分位数概念在团队里常被误用，值得做一次显性的培训与文档化：内部维基维护一篇"分位数使用守则"，内容就是本篇的三块——为什么不用平均值、聚合的正确公式、窗口与样本量的关系；新人体检时完成一道实测练习（给定直方图桶数据手算P95并与系统对答案）；看板上的分位数面板统一加一句脚注说明聚合口径（"全局桶聚合计算，窗口五分钟"）。这些小动作的成本极低，却能系统性消除"平均P95"这类流传最广的错误。

## 结语

分位数是时延观测的通用语言，而直方图是让这门语言跨实例、可聚合、可长期保存的载体。把桶设计、聚合公式、窗口选择这三件基础工打牢，P50/P95/P99才真正可信，SLO与告警才有坚实的数字底座。
