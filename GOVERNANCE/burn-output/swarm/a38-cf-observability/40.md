# 成本数据采集：用量指标与账单数据的对账体系

> 一句话摘要：本文讲解云函数成本数据的三层来源（实时用量估算、日级用量明细、月度账单实测）、估算模型的构建方法，以及三层间对账校准的闭环机制。

## 一、成本数据的层次：实时性换精确性

成本观测的困境是"精确的数据太慢（账单滞后数小时到数天），快的数据不精确（实时指标需估算单价）"。解法是三层金字塔。层一实时估算层：用平台实时指标（调用量、计费时长、内存档位、流量）乘以价目表单价，秒级刷新成本速率——服务于"此刻烧钱多快"与异常检测。层二日级明细层：多数平台提供按资源维度的日级用量文件（CSV/API），粒度到函数、包含精确计费时长与请求计费——服务于成本看板的日更曲线与归因。层三月度账单层：账单实测值，含折扣、阶梯、预留实例冲抵等估算难以覆盖的细节——服务于模型校准与财务对账。三层各有盲区：估算层不知道折扣、明细层滞后一天、账单层不可拆分到函数（部分平台账单只到大类）。因此必须互相校准，而不是互相替代。

## 二、估算模型的构建与管道

构建每函数每小时的成本估算流水线。输入：调用次数、计费时长合计（GB秒或毫秒×内存档位折算）、出口流量、预留实例配置。计算：按第39篇公式乘单价表。输出：fn_cost_hourly{function}时序指标（供看板与告警）加日汇总表（供归因）。工程要点四条。第一，单价表配置化：单价是参数不是代码，厂商调价时改配置即可；单价表带生效日期，历史数据按当时单价回放。第二，计费时长的精确获取：优先用平台暴露的计费时长指标（如Billed Duration）；没有则用日志自测时长向上取整到计费粒度估算，误差要在对账中量化。第三，预留与按量分列：预留实例费按配置常驻计入（分摊到小时），调用发生时不再重复计按量费（预留实例的调用不计按量）——估算模型里必须区分流量落在预留还是按量，否则重复计费导致估算虚高。第四，管道即代码：拉取、折算、落库的作业用定时函数或调度器实现，产物（指标与明细表）进统一存储。

估算管道伪码：

```python
PRICE = load_price_table(region="cn-east-1", date=today)

def hourly_cost(fn_usage):                    # 每函数每小时
    compute = (fn_usage.provisioned_gb_s * PRICE.provisioned_rate
               + fn_usage.on_demand_gb_s * PRICE.compute_rate)
    requests = fn_usage.invocations * PRICE.request_rate
    egress   = fn_usage.egress_gb * PRICE.egress_rate
    return compute + requests + egress

# 定时任务：每小时聚合平台用量→估算→打点
for fn in platform.list_functions():
    u = collect_hourly_usage(fn, hour=h)
    emit("fn_cost_cny_hourly", value=hourly_cost(u),
         labels={"function": fn.name, "region": fn.region})
```

## 三、对账闭环：三层互检与偏差处置

对账是估算体系可信的来源，三个方向的互检。日检（估算 vs 日明细）：每日比较两层的每函数成本，偏差超过百分之五的函数列入调查清单——常见原因：计费粒度取整规则理解错、折扣未入模型、平台指标统计口径差（含/不含重试）。月检（日明细汇总 vs 账单）：账单的函数计算大类总额与日明细总和比对，账单更小通常意味着折扣或阶梯（把折扣系数回填估算模型），账单更大意味着遗漏项（VPC连接费、额外区域、镜像存储）。专项检（成本指标 vs 财务系统）：季度把成本看板的月度数与财务云费用报表核对，口径对齐（含税与否、账户拆分），差异写成对账备忘录。处置纪律：每个偏差要么修正模型、要么文档化"已知偏差及原因"，不允许长期挂账不管——挂账偏差会让所有成本数据失去公信力。

对账看板的关键视图：三条曲线叠加（实时估算累计、日明细累计、账单月度点），偏差带（估算与明细的差百分比时序）；偏差超阈自动开调查工单并指派成本owner（第41篇角色）。

## 四、多账户多区域的复杂度管理

真实环境常有多个云账户（生产/测试/不同业务线）与多区域部署。管理要点：账户与区域作为成本数据的第一级维度（比函数更高层），账单按账户拉取、明细按区域拆分；汇率与币种统一（多云场景折算到记账本位币，汇率用财务口径的月度固定汇率而非实时汇率）；跨区域流量费专项标注（跨区数据传输单价高且常被遗漏在估算里）；标签体系补位——平台账单支持按资源标签分账时，强制每个函数打业务标签（team/product），账单直出业务维度成本，估算模型同步带标签。

成本数据管道检查清单：

```text
[ ] 三层管道建立：实时估算指标/日级明细表/月账单拉取
[ ] 单价表配置化带生效日期；调价改配置不改代码
[ ] 预留与按量分列计算；计费取整规则经过验证
[ ] 日检偏差>5%开调查工单；月检回填折扣系数
[ ] 季度与财务对账留备忘录；无长期挂账偏差
[ ] 账户/区域一级维度；币种按财务口径；跨区流量单列
[ ] 函数强制业务标签；账单支持标签分账
```

## 五、账单API的限制与应对

实现账单拉取时会遇到平台API的现实限制：查询频率限制（需要缓存与退避）、分页与超时（大账户月账单拉取要分片）、数据粒度不足（部分平台账单只到产品大类，函数级要靠用量明细补）、历史数据保留窗口（账单API可能只提供近几个月，长期数据要自存快照落库）。应对原则：拉取任务幂等可重跑、每次全量校验后落自有数据库、对API变更（字段更名、口径调整）建立监控与告警——管道静默失败一个月才发现的代价是整月数据不可信。

## 结语

成本观测的可信度来自三层数据的互相制衡：估算给速度、明细给粒度、账单给真相，对账机制让偏差无处遁形。当成本数据与财务报表能对上、且每分钱都能拆到函数，成本优化（第43篇）才有了可以下刀的精确地图。
