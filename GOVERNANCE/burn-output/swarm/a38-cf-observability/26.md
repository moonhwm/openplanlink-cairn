# 指标基数控制与标签设计规范

> 一句话摘要：本文讲解指标基数（cardinality）的成因与爆炸案例，标签设计的白名单制度、基数预算与监控方法，以及高维分析需求的正确出口（日志与追踪而非指标）。

## 一、基数是什么以及它为什么致命

一个指标的时间序列数＝各标签取值数的乘积。例如invoke_duration_ms带三个标签：function（50个函数）、code（20种错误码）、region（3个地域），序列数=50×20×3=3000条，可控。但若加一个user_id标签（一百万用户），序列数变成三十亿——这就是基数爆炸。后果是链式灾难：存储端序列数与写入量暴涨（费用失控）、查询聚合变慢、后端可能直接限流或丢弃新序列（数据静默丢失）、极端情况后端OOM。真实事故模式通常是渐进的：某天上线一个带trace_id的"调试指标"，当天就新增百万序列；或者错误码标签意外混入了动态值（如把超时毫秒数当code），序列每天自增。因为爆炸往往在"看起来无害的标签"上发生，必须制度化防御而非靠自觉。

## 二、标签设计规范：白名单与低基数原则

标签设计四条铁律。第一，低基数硬上限：任何标签的活跃取值数（如三十天内出现的不重复值）不超过一千，单个指标的活跃序列数不超过五千；超限的设计退回重做。第二，受控词表：所有枚举型标签（错误码、渠道、状态）的取值来自代码库里的常量表，新增值走PR评审；运行时出现词表外的值归并为OTHER并计数告警——防动态值混入。第三，禁止清单（一票否决）：user_id、order_id、trace_id、IP、URL全文、异常消息、任何哈希值，一律不得做标签。第四，维度最小化：每个标签都要回答"我会用这个维度切片看图或告警吗"，不会就删；标签是给聚合用的，不是给单点查询用的。

高维需求的正确出口对照表：

```text
需求                          | 错误做法            | 正确做法
按用户排查某次请求             | user_id做标签       | 日志查tenant/user，trace看树
看某订单的处理过程             | order_id做标签      | 业务Span属性+日志检索
按完整URL分析流量             | url全文做标签       | 路由模板化(/orders/{id})做标签
异常消息分类                   | message做标签       | error_code受控词表做标签
按版本灰度对比                | git hash做标签      | 别名/版本号(低基数)做标签
```

## 三、基数预算与事前拦截

把基数管理变成预算制度。事前：新指标上线必须声明预估序列数（各标签取值数乘积），超过阈值的需架构评审通过并给降基数方案；CI里扫描代码中的指标定义，检测禁止清单字段名命中（标签名含id、uuid、hash等模式的加人工确认）。事中：接入网关或后端统计每指标活跃序列数，设两级水位——超过预算百分之八十预警给指标owner，超过百分之一百二十自动拒绝新序列并告警（宁可丢新序列不可拖垮后端）。事后：月度基数报表，Top序列数指标排名与环比，异常增长启动治理（通常是词表失控或调试指标忘删）。

指标定义评审模板示例：

```yaml
metric: invoke_duration_ms
type: histogram
labels:
  - {name: function,   values: 50,  source: "平台函数名,受控"}
  - {name: trigger,    values: 6,   source: "枚举词表"}
  - {name: cold_start, values: 2}
estimated_series: 50*6*2*12buckets = 7200   # 超阈值→需评审
note: 桶数计入序列数(直方图每桶一条序列)
mitigation: 若超预算，去掉trigger标签改看日志
```

注意直方图的隐藏放大：每个桶是一条独立序列，二十个桶的直方图序列数是计数的二十倍，预算计算必须含桶数，桶边界设计要克制（十到十五个桶通常足够支撑P99精度）。

## 四、基数监控与治理运营

三个持续监控指标：全局活跃序列数（环比突增告警）、单指标序列数Top榜、词表外值占比（OTHER比率）。治理动作库：删标签（最常见，多数标签没人用）、词表归并（合并语义相近的码）、改日志（高维需求迁出）、直方图减桶。一个易被忽视的源头是"环境标签"：staging环境的调试流量会给每个指标翻倍序列，非生产环境指标单独命名空间或降采样上报，是成熟团队的标配。

基数治理清单：

```text
[ ] 标签活跃值≤1000；单指标序列≤5000(含桶)；词表外归并OTHER
[ ] 禁止清单硬卡：任何ID/哈希/IP/消息全文
[ ] 新指标声明预估序列数过评审；CI扫描禁止字段
[ ] 两级水位：80%预警owner、120%拒新序列告警
[ ] 直方图桶数计入预算；非生产指标独立空间或降采
[ ] 月度基数报表+Top榜治理例行化
```

## 五、一个基数事故的解剖

用一个典型事故说明治理价值。某晚告警后端响应变慢，排查发现一个"调试用"指标把HTTP响应状态行做成了标签，当晚爬虫流量带来数千种非预期取值（乱码路径、各种状态组合），序列数从三千涨到四十万，写入放大导致后端接近瘫痪。复盘暴露四个缺口：上线未经序列数预估（第26篇预算制度可拦截）、词表外值未归并OTHER直接放行、基数水位告警存在但阈值过松（百分之一百二十才拒新）、调试指标忘删。四项缺口对应四项修复全部落地后，该类事故归零。教训的普遍意义：基数事故不是概率问题，是没有制度时的必然问题——只需要一个不小心的开发者加上一个没有闸门的管道。

## 结语

基数是指标体系的高利贷：透支一天，用数月的存储费用与查询卡顿偿还。白名单标签、序列预算、水位拦截三道闸门建立后，指标库才能长期保持"小而快"，而高维分析交给日志与追踪各司其职。
