# 告警渠道集成：电话、短信、IM机器人与邮件的工程实践

> 一句话摘要：本文比较四类告警通知渠道的特性与适用场景，讲解通知模板设计、值班呼叫链、多渠道编排与送达保障，以及通知疲劳的渠道层防御。

## 一、渠道特性矩阵：对的方式叫对的人

四类主流渠道各有不可替代的位置。电话：穿透力最强（必然打断），成本最高（打扰性大），仅用于P1——且要能自动连续呼叫值班链（一号未接转二号）而非单次拨打。短信：送达率较高且不依赖安装应用，适合P1的备份渠道与弱网场景（值班者所在环境IM不可达）；注意内容长度限制，只放最关键信息加短链。IM机器人（钉钉、飞书、Slack、企业微信）：日常主渠道，支持富卡片（关键数字、按钮、链接直达看板与Runbook）、群协作可见性（值班群全员知情）、以及可交互动作（按钮触发认领、回滚、静默）。邮件：非紧急的批量信息（日报、周报、慢速档工单、复盘记录），可检索可归档，不适合任何需要及时响应的场景。核心编排原则：P1=电话+短信+IM群@值班者三路并发；P2=IM强提醒（加急/专属铃声）；P3=工单系统+IM普通消息；P4=仅进报表。渠道选择的试金石：这个严重度需要几分钟内被看到？需要就必有电话或强提醒，不需要就不许用强提醒。

## 二、通知模板设计：一条通知即一个行动入口

通知不是"告知发生了什么"而是"给出下一步动作的入口"。模板要素分级：必含——服务名、严重度、一句话影响（用户视角）、触发数字（当前值与阈值）、时间；强烈建议——看板直达链接、Runbook链接、认领按钮、关联事件号（第33篇事件聚合后多条告警共号，通知里报事件而非散告警）；禁止——堆砌原始查询语句、无解释的指标名、超过十行的堆栈（放链接）。IM卡片模板示例：标题"【P1】order-api可用性燃烧"，正文三行（影响、数字、首步建议），底部四个按钮（认领、看板、Runbook、静默1h）。模板变量集中管理（通知中心统一渲染），各渠道适配裁剪（短信只保留前两行加链接）。同一事件的多渠道通知内容同源生成，避免各渠道信息不一致。

## 三、值班呼叫链与送达保障

电话呼叫链的工程要点：呼叫序列=值班者手机（间隔两分钟两次）→备岗（两次）→主管（两次），全部未接转人工兜底（7×24应急台）或自动升级策略（第34篇）；呼叫内容TTS播报"严重度、服务、事件号、回复方式"，支持按键确认接警（按键即Ack，系统登记确认时间）。送达保障三层：第一层送达回执——每个渠道跟踪送达状态（电话接通、短信回执、IM送达），P1在两分钟内无任何渠道送达成功自动降级重试并升级备用通知树；第二层渠道健康监控——通知服务自身是关键设施，对其API错误率、延迟、余额（短信条数、电话分钟数）设监控与余量告警（余额不足提前预警，通知渠道欠费停机是真实事故模式）；第三层演练验证——每月一次合成P1（标注test）走全渠道验证链路，包括凌晨时段电话链有效性。

通知编排配置示例：

```yaml
notify_policy:
  P1:
    parallel:
      - call: [ primary(2x,2m间隔), backup(2x), lead(2x) ]
        tts: "P1事件{{event_id}}，{{service}}可用性燃烧，按键1确认"
      - sms: [ primary, backup ]
        body: "[P1]{{service}} {{metric}}={{value}} 详情 {{short_link}}"
      - im: { room: oncall-order, card: p1_card, at: [primary] }
    ack_timeout: 5m → 升级(第34篇链)
    retry_on_undelivered: { after: 2m, fallback_tree: true }
  P2:
    im: { room: oncall-order, card: p2_card, urgent: true }
    ack_timeout: 30m
  P3: { ticket: true, im: { room: team-log, card: p3_card } }
  P4: { digest: weekly }
channel_health:
  - { name: sms, metric: deliver_rate, warn: <98%, credit_alert: <5000条 }
  - { name: call,  metric: connect_rate, warn: <95% }
```

## 四、渠道层的疲劳防御与治理

渠道层是防疲劳的最后阀门。四项防御：时段策略——非P1通知默认工作时间聚合发送（夜间P3/P4静默到早九点汇总），P2夜间降为IM不打扰模式（除非用户显式开启）；个人偏好——值班者可设置个人渠道偏好（IM偏好者夜间P2仅强提醒），但P1电话不可关闭（安全下限）；聚合粒度——同一事件窗口内的同源通知合并（第33篇），渠道侧再按"事件"折叠会话线程（IM里同一事件的多条更新进同一thread）；静默回路——通知卡片上的静默按钮带默认时长（一小时）与工单必填，防止无限期静默。治理度量：各渠道的送达率、确认及时率、夜间打扰量（人均每周夜间强提醒次数，超标削减规则）；季度审查渠道成本（电话与短信费用Top来源是否为重复通知）。

渠道集成检查清单：

```text
[ ] 渠道矩阵: P1三路并发(电话链+短信+IM@)、P2强提醒、P3工单
[ ] 通知模板: 影响一句话+数字+三链接+认领按钮；多渠道同源渲染
[ ] 电话按键确认=Ack；呼叫链2/2/2次序；人工兜底台
[ ] 送达回执+渠道健康与余额监控；月度合成P1全链演练
[ ] 夜间非P1聚合；P1电话不可关；静默带TTL
[ ] 季度审查: 送达率/确认及时率/夜间打扰量/渠道成本
```

## 六、渠道成本与供应商分散

通知渠道本身有运营成本与单点风险。成本侧：电话与短信按条计费，通知风暴时费用可观，对电话类渠道设每日条数上限与超额告警（防止"用钱砸醒"变成烧钱）；IM的webhook与卡片有频率限制，超限会被静默丢弃，发送端要有退避重试。风险侧：单一IM平台故障（历史上多次发生）会让P2以下全部失明，至少保留一条独立通道（短信网关或备用IM）作为灾备，并在月度渠道演练（第38篇第四节）中轮换验证。所有渠道凭据集中管理、季度轮换、过期前告警——通知系统的密钥失效是最讽刺的静默故障。

## 结语

渠道集成是告警体系与人的接口层：分级映射渠道、通知即行动入口、送达有保障、打扰有节制。电话为刀刃、IM为主力、短信为备份、邮件为档案——四者编排得当，重要信号永不丢失，值班者的睡眠也不会被无谓透支。
