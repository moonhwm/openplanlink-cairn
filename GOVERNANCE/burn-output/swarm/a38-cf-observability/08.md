# JSON日志规范设计：字段、层级与命名约定

> 一句话摘要：本文给出一套可直接落地的云函数JSON日志字段规范，覆盖顶层必填字段、嵌套层级设计、命名约定、值类型标准以及规范治理机制。

## 一、顶层字段集：必填、推荐、可选三档

规范的主体是一张分层字段表。必填字段保证每条日志可定位、可关联：ts（整数毫秒UTC时间戳）、level（debug/info/warn/error四档字符串）、event（受控词表事件名）。推荐字段在有上下文时必填：function（函数名）、env（环境标识）、version（发布版本或别名）、trace_id、request_id、instance_id、tenant_id。可选字段按场景：logger（代码模块路径）、trigger（触发类型）、status（ok/error）、total_ms与各类耗时字段、error_code、stack（异常堆栈字符串）、data（业务负载对象）。

分档的意义在于执行力度：必填字段缺失视为数据违约，采集端可拒收并计数告警；推荐字段由logger库自动注入所以实际缺失率应接近零；可选字段自由使用但受基数与体积约束。特别注意version字段要能定位到代码提交——用发布别名或git短哈希，排障时才能对上代码行。

## 二、命名约定与值类型标准

命名约定有六条。第一，全小写加下划线：request_id而非requestId或REQUEST_ID，多语言序列化习惯不同，只有强制统一才能跨函数聚合。第二，布尔值用is_/has_前缀且值为true/false小写。第三，耗时一律整数毫秒并以_ms结尾（db_ms、queue_lag_ms），禁止秒与浮点。第四，字节数以_bytes结尾，计数以_count或_total结尾，比率以_ratio结尾且值域0到1。第五，ID类字段统一字符串类型，即使看起来是数字（user_id装"456"而非456），防止大整数精度与类型混用。第六，时间类字段除ts外，业务时间用ISO8601字符串并以_at结尾（paid_at）。

值类型标准：数字不带引号；null表示"有此字段但无值"，字段缺省表示"不适用"，两者语义不同不要混用；数组只用于同质元素（如sku列表），异质信息用对象；字符串中禁止换行符，多行内容（堆栈）压缩为带\n转义的单行由日志系统展示时还原。

## 三、层级设计与data对象的边界

顶层字段保持精瘦（建议不超过二十五个），业务细节全部下沉到data对象。data内部再按领域分组：data.order、data.payment、data.actor等，避免一个平铺大对象。层级过深的代价是查询要写data.order.id这样长路径，所以约定最深三层。event字段与data的关系是"事件名概括发生了什么，data装载发生时的细节快照"。一条事件的data结构应当由该事件的定义文档约束（类似事件Schema），新增字段向后兼容、只增不改语义。

层级设计示例：

```json
{
  "ts": 1740000000456,
  "level": "info",
  "event": "payment_succeeded",
  "function": "pay-callback-fn",
  "env": "prod",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "total_ms": 340,
  "data": {
    "order":   { "id": "O-556231", "amount_cents": 9900, "currency": "CNY" },
    "payment": { "channel": "wallet", "paid_at": "2026-08-27T14:00:00Z" },
    "actor":   { "tenant_id": "t-2049", "user_id": "u-88" }
  }
}
```

注意amount用分做整数（amount_cents）而非浮点元，规避浮点误差；currency显式携带。

## 四、规范治理：文档、校验与演进

规范要有治理机制才能长寿。文档层面：字段表与事件词表维护在仓库的单文件（YAML或Markdown），每次改动走评审。校验层面：CI中用JSON Schema校验logger包的测试输出；线上在采集管道末端抽查，统计必填字段完整率、命名违规率（如出现驼峰字段）、超深层级率，三个指标上看板，超标告警。演进层面：字段只增不删；改名需双写一个迁移周期（新字段写入、看板切读新字段、停写旧字段）；废弃字段在文档标记deprecated并注明移除时间。体积层面：单条日志建议软上限4KB、硬上限16KB，超限时data先裁剪数组再截断并加truncated=true标记。

字段规范速查清单：

```text
[ ] 必填：ts(ms整数UTC)/level/event(词表)
[ ] 自动注入：function/env/version/trace_id/request_id/instance_id
[ ] 命名：snake_case；布尔is_前缀；耗时*_ms整数
[ ] ID一律字符串；金额用分整数；比率0-1
[ ] 业务细节进data，最深三层；顶层≤25字段
[ ] 单条软限4KB；null与缺省语义区分
[ ] 词表+Schema入库；CI校验；双写迁移改名
```

## 五、规范的执行机制：让契约活在组织里

规范文档最常见的命运是写完即过时，必须配套三种执行机制让它保持生命力。第一是代码化校验：把字段规范转成机器可读的Schema文件，日志封装库在测试环境对每条输出做校验，违约日志在本地开发时就报错，而不是等到线上看板缺数据才发现。第二是评审锚点：代码评审清单里固定三项检查——新事件是否入词表、新增字段是否符合命名与类型约定、data层级是否超三层；让规范成为评审的肌肉记忆。第三是定期审计看板：每周自动统计线上数据的规范健康度，包括词表外事件占比、驼峰命名违规字段数、超体积日志占比、必填字段缺失率，四个数字发给各团队负责人，用公开的透明度推动整改。三种机制分别覆盖事前（库校验）、事中（评审）、事后（审计），缺任何一环规范都会逐渐失守。此外规范本身要有版本号与变更公告，跨团队协作时明确"本服务日志遵循v2.1规范"，避免对接方按旧文档解析。

## 六、字段规范的版本化实践

补充最后一块拼图：规范文档本身要版本化管理。字段表与事件词表存放于独立仓库并打版本号，封装库发布时声明依赖的规范版本，跨团队对接时以版本号对齐；每次规范变更生成变更日志（新增了什么、废弃了什么、迁移期多长），并同步更新Schema校验文件与示例日志。当审计或排查需要回溯历史数据的语义时，旧版规范文档就是唯一可靠的字典——没有版本化的规范，半年前的日志字段含义将无人能解释，数据资产随之贬值。

## 结语

一份严格的字段规范是日志资产化的前提：它让"查某个租户的错误分布"、"按版本对比耗时"这类问题变成一次字段查询而非一次数据工程。规范的价值随函数数量与团队规模指数增长——三个函数时规范显得繁琐，三百个函数时规范就是救命的秩序。最好的时机是第一个函数上线之前，其次是现在。
