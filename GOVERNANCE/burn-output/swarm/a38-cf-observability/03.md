# 云函数生命周期与可观测数据采集点

> 一句话摘要：本文沿"冷启动—初始化—调用处理—响应—冻结/回收"的函数生命周期，逐段标注各阶段可观测数据的采集点、字段要求与注意事项。

## 一、理解生命周期：为什么采集点必须跟着生命周期走

云函数的一次完整生命周期包含多个阶段。以主流FaaS平台为例：平台收到触发请求后，若无可用实例则先拉起执行环境（创建容器或微虚拟机），下载代码与层，启动运行时进程，这个阶段叫冷启动；接着执行用户的初始化代码（全局作用域、init回调、连接外部资源的逻辑），进入就绪状态；随后每次调用到来，框架把事件交给处理函数，执行业务逻辑并返回响应；调用间隔中实例可能被冻结（CPU暂停但内存保留），下次调用直接复用，即为热调用；长时间无流量后实例被回收。不同的故障与性能问题发生在不同阶段：冷启动慢在拉起与初始化，业务慢在处理阶段，连接错误常发生在冻结后复用时。观测数据如果不区分这些阶段，P95耗时里混着冷启动开销，分析就会失真。

因此采集设计的核心原则是：每条观测数据都要能回答"它发生在生命周期的哪个阶段"。日志要区分初始化日志与调用日志；指标要区分冷调用与热调用的时长；追踪的根Span要从进入处理函数开始，而初始化耗时用单独的指标记录。

## 二、各阶段采集点详解

第一阶段是冷启动阶段。开发者能观测的主要手段是平台提供的初始化耗时指标（如各云厂商的Init Duration、Provisioned Latency）以及初始化代码中主动打的日志。采集要点：在全局初始化代码的开头与结尾各打一条日志，记录初始化总时长与主要步骤耗时；不要在初始化日志里放request级字段（此时还没有请求）；给初始化日志一个独立标记字段如phase=init，避免与调用日志混淆。注意冷启动的构成里，平台侧的拉起时间用户不可控，可控的是初始化代码的体积与外部连接建立方式，所以初始化日志要把"建立数据库连接""加载配置""加载模型文件"等步骤分别计时。

第二阶段是调用处理阶段，这是观测数据最密集的地方。入口处应立即生成或提取关联键：同步HTTP触发时从请求头提取trace_id，异步触发时从事件元数据提取或新建。处理过程中的每个关键业务步骤都可以打结构化日志；调用下游时创建子Span。出口处无论成功失败都要保证一条收尾日志，包含本次调用总耗时、下游耗时分布与结果状态。异常路径尤其重要：必须捕获所有未处理异常，输出带堆栈的错误日志后重新抛出，让平台正确计数错误并触发DLQ等机制。

第三阶段是冻结与回收阶段。这个阶段最容易产生的坑是：冻结期间TCP连接可能被对端或NAT悄悄断开，而实例毫不知情，恢复执行后第一次调用数据库就报连接已重置。对应的采集手段包括：在每次下游调用失败时记录错误码与连接年龄，统计"冻结后首次调用失败率"这一自定义指标；对连接对象记录创建时间戳，超过阈值的连接主动重建并打日志。

以下给出生命周期各阶段采集点清单：

```text
阶段        | 采集点                          | 数据类型        | 关键字段
冷启动/初始化 | init开始/结束日志；初始化分步计时 | 日志+自定义指标  | phase=init, init_ms, step
调用入口     | 关联键提取，入口日志             | 日志+Span起点    | trace_id, request_id, trigger
业务步骤     | 关键节点日志，子Span            | 日志+Span        | step, 下游服务名, 耗时
调用出口     | 收尾日志（成功/失败均要）        | 日志+Span结束    | status, total_ms, error_code
异常路径     | 捕获异常打堆栈后重抛             | 错误日志+错误计数 | stack, error_code
冻结复用     | 连接健康检查与重建日志           | 日志+计数器      | conn_age_ms, reused
```

## 三、代码骨架示例

下面是一个Node.js函数生命周期观测的骨架代码，展示初始化计时与调用阶段的结构化采集：

```javascript
// 初始化阶段（冷启动时执行一次）
const t0 = Date.now();
const db = createDbPool();              // 记录耗时
const config = loadConfig();            // 记录耗时
const initMs = Date.now() - t0;
logger.info({ phase: 'init', init_ms: initMs, steps: { db: 120, config: 35 } },
            'function initialized');

// 调用阶段（每次触发执行）
exports.handler = async (event, ctx) => {
  const started = Date.now();
  const traceId = extractTraceId(event) || newTraceId();   // 关联键
  const log = logger.child({ trace_id: traceId, request_id: ctx.requestId });
  try {
    const result = await business(event, log);              // 内部各步骤打点
    log.info({ status: 'ok', total_ms: Date.now() - started }, 'invoke done');
    return result;
  } catch (err) {
    metrics.inc('invoke_errors_total', { code: err.code || 'unknown' });
    log.error({ status: 'error', stack: err.stack, total_ms: Date.now() - started },
              'invoke failed');
    throw err;                                              // 让平台计数错误
  }
};
```

## 四、采集点与阶段归因的联动

采集点齐备之后，分析端要把耗时拆解成"冷启动开销+初始化开销+处理耗时"三段，并分别建立指标。排障时先看该次调用是冷是热，再看各段耗时归属。一个实用技巧是在日志里带instance_id（可用随机数在初始化时生成），同一instance_id的首次调用即冷调用，这在不依赖平台指标时也能自行统计冷启动占比。

## 五、实例复用与观测数据的对应陷阱

最后补充一个高频陷阱：实例复用会让"实例级"与"调用级"的观测数据出现纠缠。全局变量在复用实例中跨调用存活，缓存命中率、连接池状态这类实例级指标看似属于某个函数，实际只反映"这个实例的局部历史"；若把多实例的缓存命中率简单平均，会得到与任何真实实例都不相符的数字。正确做法是区分两类统计口径：实例级指标只用于诊断单实例异常（如连接泄漏），全局结论必须基于调用级聚合重新计算。此外要警惕调用序号带来的偏差：低流量函数的实例常常每次都被回收，统计到的"热调用占比"会系统性偏低，与高流量函数不可直接横向比较，比较时应同时给出实例存活时长的分布。

## 结语

生命周期是云函数观测的骨架坐标系。把每个阶段的采集点定义清楚、把每条数据标注到阶段上，冷启动优化、错误归因、连接复用治理才有可信的数据基础。下一篇将深入其中最敏感的一段——冷启动的测量与归因方法。
