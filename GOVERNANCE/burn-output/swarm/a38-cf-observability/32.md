# 告警规则设计：静态阈值、同比环比与SLO燃烧率

> 一句话摘要：本文对比三类告警规则——静态阈值、动态基线（同比环比/异常检测）、SLO燃烧率——的原理、适用场景与配置陷阱，给出云函数场景的规则选型组合。

## 一、静态阈值：简单有力但有适用域

静态阈值是"指标越过固定线就告警"：P95>800ms、错误率>1%、队列积压>10000。它的优点是可解释、可审计（阈值与SLO对齐时天然合理）、行为稳定。陷阱有三个。陷阱一阈值拍脑袋：阈值应来自SLO目标或历史分布（如P95基线的一点五倍），而非整数偏好；写进告警注释里注明依据。陷阱二不随流量适应：错误率百分之一在大流量下是海量用户受损、在小流量下是两三个请求，静态阈值无法区分——低流量时段要么误报要么漏报，补救是给比率类告警加最小样本量条件（如五分钟调用数大于五百才判比率）。陷阱三毛刺敏感：必须配持续时间（for 3m到5m）与窗口平滑，否则一次GC停顿就触发。静态阈值最适合：有明确承诺的指标（SLO阈值）、应为零的指标（限流/DLQ）、容量水位（并发限额的百分之八十）。

## 二、动态基线：同比环比与异常检测

动态基线回答"相对于它自己的过去，现在异常吗"。最实用的两种。同比环比：当前值对比一周前同时段（周同比抗工作日模式）或前一时段，偏离超比例（如P95环比劣化百分之三十）告警。它捕捉"绝对值仍达标但显著劣化"的回归（新版本把P95从300推到450，仍在800阈值内，用户已感知变慢）。配置要点：偏离比例按指标方差定（时延类百分之三十起，流量类百分之五十起，太灵敏必噪音）；加保护条件（基线窗口本身要正常，异常对异常会漏报）。统计异常检测（3-sigma、ESD、预测区间）：适合周期性强的流量指标（下单量的分钟级周期），由系统自动学基线。工程建议：异常检测只用于"发现型"指标（流量、业务量），"承诺型"指标（错误率、P95）用SLO规则——机器学的基线解释成本高，故障时刻要向管理层解释"为什么告警"，静态与SLO规则更可辩护。

同比环比规则示例：

```yaml
- name: p95-regression-vs-week
  expr: |
    p95_now = histogram_quantile(0.95, sum by(le)(rate(fn_duration_bucket[30m])))
    p95_base = histogram_quantile(0.95, sum by(le)(rate(fn_duration_bucket[30m] offset 7d)))
    p95_now > 200 AND p95_now > 1.3 * p95_base
  for: 15m            # 持续劣化才报，抗短时抖动
  severity: P3        # 回归类通常是P3(仍达标但变差)
- name: traffic-anomaly
  expr: abs(rate(orders_total[10m]) - rate(orders_total[10m] offset 1h)) 
        / rate(orders_total[10m] offset 1h) > 0.6
  for: 10m
  severity: P2        # 业务量骤变优先级高
```

## 三、SLO燃烧率：面向错误预算的规则

第06篇定义了燃烧率，本篇落地为规则。标准多窗口组合（Google SRE推荐）：快速页级——1小时窗口燃烧率>14.4且5分钟窗口>14.4（对应两小时烧掉一个月预算的百分之五）；慢速工单——6小时>6且1小时>6。燃烧率把"多严重、多持久"编码进规则：短而剧烈（快速档）立即页人；长而温和（慢速档）转工单处理。云函数场景的两点适配：其一异步链路的SLI统计有时滞（第06篇），燃烧窗口要覆盖统计延迟，否则故障结束才触发；其二按服务（而非函数）建SLO告警，函数级异常应被服务级燃烧捕获——避免每个函数一套燃烧规则造成风暴。燃烧率告警的注释里带上当前预算余额，帮值班者判断紧急程度。

## 四、规则组合策略与验收

三类规则的角色分工：SLO燃烧率当主哨兵（用户视角），静态阈值守硬承诺（应为零指标、容量水位），动态基线捕回归（性能与业务量）。配置组合模板：核心服务=SLO双档+P95环比+流量异常；长尾函数=错误率静态（带最小样本量）+限流即报；成本类（第42篇）=预算燃烧率。验收方法两条：回放历史——用过去三十天数据回放新规则，统计触发次数并逐条人工判读"该不该报"，误报率超三成就改；故障演练注入——人为注入错误率与延迟，验证规则在承诺时间内触发（MTTD达标）。规则全部以代码形式入库（rules as code），评审、变更、回滚走Git流程，禁止在管理界面手改导致配置漂移。

规则设计检查清单：

```text
[ ] 阈值有依据(SLO/历史分布)并注明；比率类配最小样本量
[ ] 全部规则带for持续时间；窗口步长按流量分级
[ ] SLO双档燃烧率为主哨兵；应为零指标无条件即报
[ ] 回归类用同比环比；发现型流量可用异常检测
[ ] 新规则上线前历史回放误报<30%；故障注入验证MTTD
[ ] 规则即代码入库，禁界面手改
```

## 五、阈值的定期评审与知识沉淀

阈值不是一劳永逸的数字，要有评审节奏与沉淀机制。季度阈值评审：对全部阈值类规则过三件事——当前值与阈值的距离分布（长期贴着阈值跑的要么阈值松要么系统临界）、历史触发质量（精准率复核）、业务变化是否要求调整（流量翻倍后旧的绝对值阈值可能不再合理）。知识沉淀：每条规则的注释里维护"阈值依据"段落，记录设定时的数据基础与历次调整原因——半年后没人记得"为什么是八百毫秒"，注释就是唯一防线。一个实用习惯：把阈值依据链接到SLO文档或历史分析报告，让每个数字都有出处可查。

## 结语

规则设计是科学与克制的结合：静态阈值守住承诺，动态基线嗅出回归，燃烧率对齐用户体验。三类规则各司其职、历史回放把关上线质量，告警的"精准"就从口号变成可验收的工程指标。
