# 自定义Span与业务语义埋点设计

> 一句话摘要：本文讲解何时值得创建业务级自定义Span、业务属性（订单号、租户、渠道）的选择与命名、用Exemplar打通指标与追踪，以及埋点的治理与代码库封装模式。

## 一、自动埋点与业务埋点的分工

平台与OTel自动埋点覆盖的是技术边界：HTTP调用、数据库操作、队列收发——它们回答"慢在哪个基础设施组件"。但业务排障常需要更细的问题：下单请求里"风控决策"这一步花了多久？"优惠券核算"是否是热点路径的瓶颈？这些业务步骤对自动埋点不可见，需要开发者手动创建业务Span。分工原则：技术边界交给自动埋点（不要重复包装），业务关键步骤（一次外部调用覆盖不了的复合逻辑）才建业务Span，判据是"如果这段逻辑可能成为故障嫌疑点或优化对象，就值得一个Span"——例如风控决策、价格计算、库存锁定、积分变更；而"参数校验""日志组装"这类纯内存轻逻辑不值得。

业务Span的粒度以五十毫秒到五百毫秒的复合步骤为宜：太细则树噪音大、采样负担重；太粗则失去定位能力。命名用"领域.动作"格式（risk.evaluate、pricing.calc、inventory.lock），与事件词表同源管理，保证跨函数聚合时同名步骤可比。

## 二、业务属性的选择与规范

业务Span的属性（attributes）是其价值所在：它们让"按业务维度过滤追踪"成为可能。属性分三类。第一类标识类：order_id、payment_id——用于从业务单号反查trace（前提是该属性进了追踪后端的可检索白名单，第20篇）；注意标识类属性只在错误/慢请求被尾部采样保留的树里可靠存在，不能假设全量。第二类维度类：tenant_id、channel、product_line——低基数字符串，用于按业务切片分析（如"安卓渠道的追踪树里风控步骤是否更慢"）。第三类结果类：risk_pass=true、discount_amount_cents、retries——记录步骤的决策结果，排障时看到的不只是"多久"还有"结果是什么"。规范沿用第08篇：snake_case、毫秒_ms、分为单位的金额、布尔is_/动词过去式；单Span属性不超过十五个，高基数值（全量用户ID）不入属性。

业务埋点代码示例（Node.js）：

```javascript
async function evaluateRisk(order, ctx) {
  return tracer.startActiveSpan('risk.evaluate', async (span) => {
    span.setAttributes({
      'biz.order_id': order.id,
      'biz.channel': order.channel,               // 低基数维度
      'biz.amount_cents': order.amountCents,
    });
    const t0 = Date.now();
    try {
      const decision = await riskEngine.decide(order);
      span.setAttributes({ 'risk.passed': decision.passed,
                           'risk.score': decision.score });
      if (!decision.passed) span.addEvent('risk_rejected',
                                  { 'risk.reason': decision.reason });
      return decision;
    } catch (e) {
      span.setStatus({ code: 2, message: 'risk_engine_error' });
      throw e;
    } finally {
      span.setAttribute('risk.duration_ms', Date.now() - t0); // 兜底记录
      span.end();
    }
  });
}
```

注意addEvent的用法：瞬时的分支事实（被拒原因、走了缓存、触发降级）用事件比属性更语义化，树上看得到时间点。

## 三、Exemplar：打通指标与追踪的最后一跳

Exemplar机制把指标数据点与典型trace关联：直方图的某个桶或计数器的一个采样点携带"产生它的trace_id"。排障时在Grafana的P95直方图上发现某时刻劣化，悬停即可拿到该桶的exemplar trace_id，一键跳到追踪树。这让"指标发现异常→追踪看现场"从人工换查询变成一次点击。实现要点：OTel SDK开启exemplar支持（基于轨迹采样保留），指标导出OTLP带exemplars，Grafana配置exemplar链接模板指向追踪后端的trace查询URL。业务埋点配合exemplar的额外收益：业务指标（下单量按渠道）也能跳到对应trace，业务与技术的观察在同一界面闭环。

## 四、埋点治理与库化封装

业务埋点会失控（乱命名、属性膨胀、忘了end导致悬挂Span），治理三招。第一，库化封装：把startBizSpan(name, attrs)做成内部库，内置命名词表校验（未注册的名字打警告日志）、属性类型校验、try/finally自动end，从源头防悬挂与乱名。第二，埋点清单：每个函数的README或注释里登记它产出哪些业务Span与属性，评审时对照，防止重复与遗漏；新Span入词表走PR。第三，健康监控：统计悬挂Span率（end缺失）、未注册命名率、单Span属性超限率三个指标，异常告警提醒治理。

业务埋点检查清单：

```text
[ ] 业务步骤建Span判据：可能是嫌疑点/优化点的复合逻辑
[ ] 命名"领域.动作"入词表；粒度50-500ms；纯内存轻逻辑不建
[ ] 属性三类：标识(可检索)/低基数维度/结果；≤15个；高基数禁入
[ ] 分支事实用addEvent；异常Span标ERROR
[ ] Exemplar开启：指标桶携带trace_id，看板一键跳树
[ ] 库化封装：命名校验+自动end+悬挂监控三项内置
```

## 五、埋点的性能开销预算

业务埋点不是免费的，要给它明确的性能预算并持续测量。开销构成：Span创建与属性序列化的CPU时间（单Span典型在微秒到几十微秒级）、导出批量的网络与内存、属性字符串的GC压力。预算约定：单请求全部埋点开销不超过总耗时的百分之一（P50口径），内存增量不超过函数档位的百分之二；监控手段是封装库自测——记录每请求的Span数与埋点耗时（在封装层打点），超预算的函数自动告警进入埋点瘦身清单。瘦身手法按优先级：删未被查询过的属性、合并相邻短Span、把高频分支事件改为计数器。经过预算约束的埋点体系才能既看得见业务又不拖慢业务。

## 六、埋点与业务代码的边界约定

最后明确埋点代码与业务代码的边界：埋点调用尽量不侵入业务逻辑主体，优先通过装饰器、中间件、框架钩子注入（如路由级自动建Span、注解声明式属性），业务函数保持纯净可测试；确需在业务体内打点的，约定埋点行有统一注释标记（便于审计与迁移）；单元测试不为埋点写断言（埋点是旁路关注点），但契约测试统一校验封装库的输出结构。边界清晰的好处：埋点体系重构（换库、改规范）时业务代码零改动，业务重构时埋点也不散落丢失。

## 结语

自动埋点给出系统的骨架，业务埋点注入系统的灵魂。克制而有词表地建业务Span、让关键业务单号可反查、用Exemplar把指标与追踪焊在一起——观测体系就从"看见基础设施"进化到"看见业务本身"。至此追踪专题完结，接下来进入指标体系。
