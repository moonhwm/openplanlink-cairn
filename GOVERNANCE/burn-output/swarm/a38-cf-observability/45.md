# 可观测看板设计原则与Grafana实战

> 一句话摘要：本文总结可观测看板的十条设计原则（分层、场景导向、黄金信号优先等），并以Grafana为载体讲解变量模板、面板选型、告警联动与看板治理的实战配置。

## 一、看板设计的十条原则

看板是把观测数据变成认知的界面，设计原则决定其效率。一、场景导向：每块看板服务一个明确场景（值班总揽、服务详情、发布观察、成本经营），不做"什么都有"的大杂烩。二、分层下钻：总揽—服务—函数三层（第28、41篇），上层只放结论级数字，细节靠点击下钻。三、黄金信号优先：值班总揽首屏必是流量、错误、耗时、饱和四象限（第23篇）。四、一板一问题：每个面板的标题写成问题（"错误率是否在恶化？"），看的人不用猜面板意图。五、默认时间窗与场景匹配：总揽默认一小时（值班视角）、服务详情默认二十四小时（排障）、趋势面板默认三十天。六、注释化：发布事件、告警事件、活动标注叠加在曲线上（annotations），让"曲线为什么跳"可解释。七、阈值与SLO线：关键面板画上SLO目标线与预算线，好与坏一眼可判。八、克制色彩：红色只表错误、绿色只表健康，多余色彩全部去掉；曲线数量单面板不超过五条。九、可跳转：面板到日志（带时间窗与trace_id变量）、到追踪、到Runbook的链接配齐（第20篇exemplar、第37篇）。十、有owner：每块看板有负责人与最后校验日期，失修看板下线。

## 二、Grafana实战：变量模板与面板选型

变量模板（variables）是复用的核心：定义service、function、env三个级联变量（数据源指向服务目录或标签值），一套"函数详情看板"服务所有函数，避免上百个复制面板漂移。面板选型映射：调用量与错误率→时间序列（timeseries，错误率画SLO线）；错误码构成→堆叠面积或饼图（table亦可）；耗时分位数→时间序列多线（P50/P95/P99）或直方图热力图（面板时长分布随时间变化，定位"什么时候开始慢"极好用）；饱和类（并发、队列）→时间序列加阈值带（gauge仅适合大屏总览）；排行类（Top成本函数、Top错误码）→表格带条形内嵌；燃烧与预算→仪表盘加时间序列双用。查询纪律：所有查询带时间窗与索引标签（第20、28篇），面板description里写明指标口径。

看板JSON骨架（fragment）：

```json
{
  "title": "函数详情 - ${function}",
  "variables": [
    { "name": "env", "query": "label_values(fn_invocations_total, env)" },
    { "name": "function", "query": "label_values(fn_invocations_total{env=\"$env\"}, function)" }
  ],
  "panels": [
    { "type": "timeseries", "title": "Q: 错误率是否恶化?",
      "targets": [{ "expr": "sum(rate(fn_errors_total{function=\"$function\"}[5m])) / sum(rate(fn_invocations_total{function=\"$function\"}[5m]))" }],
      "thresholds": [{ "value": 0.005, "color": "red" }],
      "description": "平台错误口径，SLO线0.5%" },
    { "type": "heatmap", "title": "Q: 耗时分布何时开始劣化?",
      "targets": [{ "expr": "sum by (le) (increase(fn_duration_ms_bucket{function=\"$function\"}[$__interval]))" }] },
    { "type": "table", "title": "Q: 错误集中在哪些码?",
      "targets": [{ "expr": "topk(10, sum by (code) (increase(fn_errors_total{function=\"$function\"}[1h])))" }] }
  ],
  "links": [
    { "title": "跳转日志", "url": "https://logs/explore?function=${function}&from=${__from}&to=${__to}" },
    { "title": "Runbook", "url": "https://wiki/rb/${function}" }
  ]
}
```

## 三、告警联动与大屏

看板与告警的双向联动：告警消息带看板深链（第38篇通知模板），点开即达现场上下文；看板面板可内嵌告警状态（stat面板显示当前告警红黄绿），值班者在看板内直接感知哪些规则在触发。大屏（TV模式）设计更极简：只放四黄金信号加当前事件列表，五米外可读的字号，无交互；大屏的价值是团队氛围级的共同态势感知，不放细节。发布观察看板（专用场景）：新旧版本双曲线同图（按version标签过滤）、灰度比例进度条、发布窗口内的SLO燃烧对照——发布期间的值班者盯这一块即可，它是第35篇发布管控的观测端。

## 四、看板治理：防止看板农场腐化

看板会自然繁殖与腐化（复制修改后失修、指标下线后面板报错无人清）。治理机制：看板目录化（按场景分文件夹，命名规范"场景-对象"），注册制（新看板进目录需登记场景与owner）；季度巡检（owner跑一遍全部面板，查询报错与明显失真的修或删）；使用度量（Grafana的看板访问统计），三个月零访问的看板归档；面板查询性能审计（慢查询面板优化或加缓存，看板拖垮指标后端是真实事故）。看板复用优于新建：改变量不如先搜目录，已有八成相似的就fork后收敛差异。

看板建设检查清单：

```text
[ ] 十原则评审新看板：场景/分层/黄金信号/问题式标题
[ ] 变量模板复用：一套函数详情看板服务全部函数
[ ] 面板选型匹配数据形态；热力图看分布劣化
[ ] 注释叠加发布与告警事件；SLO/预算线必画
[ ] 三链路齐备：看板↔日志↔Runbook跳转
[ ] 治理：目录注册/季度巡检/零访问归档/慢查询审计
```

## 五、看板评审：新看板的上岗考试

新看板合入前过一次十分钟的评审，检查四问：给谁看（场景明确且与现有看板不重叠）、首屏是否在十秒内回答该场景的核心问题（找三个目标用户实测）、每个面板的查询是否走索引（附查询计划或耗时证明）、下钻与跳转是否真实可达（点过每个链接）。评审不过的常见修改：拆分到正确的场景看板、删掉没人看的面板、调整默认时间窗与面板顺序。评审制度与目录注册制、季度巡检、零访问归档配套，构成看板的准入与退出闭环，防止看板农场野蛮生长。

## 结语

看板是观测体系的脸面，更是认知效率的杠杆：一套分层、场景化、可下钻、有注释的看板群，能把"系统怎么样"的答案时间从十分钟压到十秒。原则先行、模板复用、治理保鲜——让看板始终是资产而不是负担，这是把四十八篇里的数据工程兑换成日常价值的最后一公里。
