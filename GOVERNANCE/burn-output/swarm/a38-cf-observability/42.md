# 成本异常检测与预算告警：FinOps的守门机制

> 一句话摘要：本文讲解云函数成本异常的四种模式与检测方法、预算体系（总预算/服务预算/函数预算）的设计、成本燃烧率告警的实现，以及异常处置的闭环流程。

## 一、成本异常的四种模式与检测思路

成本异常的模式比想象中丰富，逐一定义检测思路。模式一用量突增型：调用量或计费时长陡增（重试风暴、被刷、业务循环bug）——检测用成本速率的环比异常（当前小时成本速率对比上周同时段超两倍即告警），比日级账单快数小时发现。模式二单位成本恶化型：总成本正常增长但每千次调用成本上涨（新版本变慢、内存档位误调、依赖膨胀）——检测盯单位经济学指标（第41篇视图三）的环比，比盯总额更早发现效率退化。模式三僵尸消耗型：无业务流量但持续计费（预留实例利用率趋零、测试函数定时器空转、消息循环自触发）——检测用"零调用函数仍有成本"与"预留利用率低于阈值"的清单式扫描，日检即可。模式四计划外资源型：新函数上线、新区域开服、VPC连接等附加项在预算外出现——检测用"成本构成结构突变"（新增费项或某费项占比突变）。四种模式的共性：都要求成本数据实时化（第40篇估算层），用日账单永远只能事后诸葛。

## 二、预算体系：三层预算与配额联动

预算不是单个数字而是体系。层一总预算：云函数+观测数据的月度总额，由财务与工程共定，配全局告警。层二服务预算：按服务目录拆分（第28篇），每服务月度额度，服务负责人认领——这是责任制的关键层，预算要与服务业务量挂钩（旺季上调），僵化的定额逼出"月底不敢上线"的扭曲行为。层三专项预算：观测数据（日志/追踪/指标）单列预算——它最容易被忽视且增速最快；预留实例池单列（其固定成本的审批口径不同）；测试环境单列。预算的配额联动：预算不应只是告警，可联动硬限制——测试环境配额超限自动暂停定时器（软限制），防刷场景对公开触发函数设置调用上限（超过即拒绝并告警，兼顾成本与安全）。

预算与燃烧率配置示例：

```yaml
budgets:
  - name: faas-total
    amount: 120000CNY/month
    alerts:
      - { at: 50%, sev: P4, to: finops-digest }
      - { at: 80%, sev: P3, to: platform-lead }
      - { at: 100%, sev: P2, to: eng-manager }
    burn_alert:                 # 燃烧率(对齐SLO告警思想, 第32篇)
      - { rate: 1h_consumed > 3% of monthly, sev: P2 }
      - { rate: 6h_consumed > 10% of monthly, sev: P3 }
  - name: svc:order-api
    owner: team-order
    amount: dynamic: base(30000) * seasonality(orders_volume)
    alerts: [ { at: 80%, sev: P3, to: team-order-lead } ]
  - name: observability-data
    amount: 25000CNY/month
    hard_rules:
      - { match: env=staging, limit: 5000, action: throttle_logging }
  quota_guards:
    - { fn_group: public-api, invoke_cap_daily: 5e6,
        on_exceed: "reject+alert(P2)" }   # 防刷限流
```

## 三、成本燃烧率告警的实现

把SLO燃烧率思想（第06、32篇）移植到成本：月预算的"允许平均燃烧速率"=预算/月时长；实际燃烧率=当前消耗速率/允许速率。配置双档：快速档（一小时烧掉月预算的百分之三以上→P2，可能正被刷或重试风暴）；慢速档（六小时烧掉百分之十以上→P3，结构性问题）。实现要点：消耗速率来自估算层的fn_cost_hourly聚合（第40篇）；告警注释自动附Top消耗函数排行与环比倍数（"热点：sync-fn，环比×8.2，调用量主导"），让接警者第一眼有归因线索；与调用量告警联动抑制——若已有限流/重试告警在处理，成本告警自动标注关联事件（第33篇抑制思想）。误报控制：成本有自然波动（大促、月初结算批量任务），燃烧告警加"非计划内流量"判据（无发布无活动标识时才升级，可通过配置的活动日历豁免）。

## 四、异常处置闭环与演练

成本异常的处置流程要像技术故障一样有闭环。响应分级：疑似刷量/重试风暴（P2）按安全与稳定性Runbook处置（限流、封禁、修复重试逻辑）；单位成本恶化开工程工单进入优化流程（第43篇）；僵尸消耗直接清理（下线函数、释放预留、关闭定时器，处置时长目标一周内）。每次处置记录"异常发现时间、根因、止损金额、修复动作"，月度汇总成"异常损失账"——这是预算体系改进的证据（哪些预算要调、哪些配额要加）。演练：季度注入一次合成异常（临时调高一测试函数内存档位×8），验证燃烧告警的触发时效（目标一小时内）与通知链路；演练也检验成本Runbook的可执行性（成本异常同样需要Runbook：谁有权调档位、谁有权释放预留、紧急止血的动作顺序）。

成本守门机制检查清单：

```text
[ ] 四类异常各有检测：速率环比/单位成本/僵尸清单/构成突变
[ ] 三层预算：总额/服务(业务量动态)/观测与预留专项
[ ] 燃烧率双档告警：1h>3%、6h>10%；注释带Top归因
[ ] 配额联动：测试环境软限、公开函数防刷上限
[ ] 处置闭环：分级Runbook+止损金额记录+月度异常损失账
[ ] 季度异常演练验证触发时效；成本Runbook可执行
```

## 五、成本告警与SLO告警的协同

成本异常与服务异常常常同源（重试风暴既是成本事件也是SLO事件），两类告警要协同而非各叫各的：同一根因触发时，成本告警应关联到已有的SLO事件（复用第33篇抑制机制），避免值班者收到两套独立通知；事后复盘时两类损失合并报告（"该故障烧掉预算百分之三、多耗成本两千元"），让技术故障的经济后果可见。反向协同同样存在：为保SLO的自动扩容会推高成本，扩容动作应自动打成本注释到看板（第45篇annotation），让"为什么这个时段成本高"有据可查。

## 结语

成本异常的破坏力不亚于服务故障，但它的"告警体系"常缺位。把FinOps的守门机制建得和技术告警一样完整——实时数据、多层预算、燃烧率告警、闭环处置、定期演练——云的弹性才真正可控：放大容易，收回也要快。
