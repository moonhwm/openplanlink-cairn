# 追踪驱动的故障排查模式：慢调用与错误传播定位

> 一句话摘要：本文以两个高频故障场景（P95劣化的慢调用定位、错误传播链定位）为线索，演示"指标发现—追踪定位—日志取证—验证修复"的完整排障工作流与思维模式。

## 一、场景一：P95耗时劣化的定位工作流

告警：下单服务延迟SLO燃烧率超标，P95从600毫秒涨到2.3秒。第一步看指标分维度切片：按函数、版本、下游切分P95——若劣化集中在新版本，指向发布回归；若集中在某个下游，指向依赖劣化；若全维度均匀上涨，怀疑平台或网络层。假设切片显示order-create-fn的P95劣化且主要发生在调用库存服务的Span上。第二步打开追踪列表：过滤"服务=order-create，耗时>2秒，最近30分钟"，任选三五个trace对比结构。观察要点有三个：树里哪个Span最厚（耗时最长）；慢Span是单个还是批量；慢Span的属性（重试次数、结果码）。第三步形成假设：三个trace里库存Span都是一点八秒且重试属性为1——像是单次调用超时重试后成功。第四步日志取证：打开慢Span的关联日志（trace_id跳转），看到库存调用第一次"connection reset"第二次成功；再查instance_id维度，发现问题集中在少数实例——冻结后连接失效的典型模式（第03篇）。第五步验证与修复：给下游连接加健康检查与失效重建，灰度后对比新旧版本P95。整个流程的关键是每一步都有明确的观察对象与判据，不靠猜。

慢调用定位的检查要点清单：

```text
[ ] 切片维度：函数/版本/下游/地域/租户，先定位劣化集中在哪
[ ] 追踪观察：最厚Span、慢Span占比、重试属性、冷热标记
[ ] 区分模式：普遍变慢(容量/下游) vs 尾部变慢(超时重试/冷启动)
[ ] 日志取证：慢Span窗口的错误日志、实例分布、连接年龄
[ ] 修复后对比：新旧版本P95、重试率指标随发布曲线恢复
```

## 二、场景二：错误传播链的定位工作流

告警：支付回调函数错误率从百分之零点一跳到百分之十二。第一步看错误码分布：错误集中为INVALID_SIGNATURE一种码。第二步看追踪：过滤"服务=pay-callback，状态=ERROR"的trace，打开树看到根Span标记ERROR，属性里error_code=INVALID_SIGNATURE；关键动作是往上看：该trace的上游是谁（回溯生产者link）——发现是支付渠道的webhook触发。第三步判断边界：是渠道改了签名算法，还是我方验签逻辑bug？看时间维度：错误开始时间精确到分钟，对齐发布记录——恰逢我方半小时前发布过验签依赖升级。第四步日志取证：取error日志中的原始签名头与密钥版本属性（密钥本身不落日志，第11篇），确认新版本用了错误的密钥别名。第五步处置：回滚版本，错误率回落；随后复盘补防：验签失败告警加渠道维度、发布检查单加"密钥别名变更确认"。这个场景体现的模式是：错误定位要同时向内看（自己的逻辑与发布历史）与向外看（上游输入是否突变），追踪树的上下游关系正是这两看的地图。

## 三、通用思维模式：三类证据的交叉验证

两个场景共用一套思维框架。第一，时间对齐：任何异常先画时间轴——异常起点、发布事件、配置变更、依赖方公告，人类的故障九成与变更相关，对齐时间轴常直接破案。第二，维度下钻：从全局到局部逐层切片（服务→函数→版本→实例→请求），每层找"劣化最集中的切片"，孤立看总数会被稀释掩盖。第三，三角互证：指标提供"有多少、有多坏"，追踪提供"怎么发生的"，日志提供"具体细节"，三者结论矛盾时优先怀疑数据口径（如指标含平台重试而trace只记一次）。此外有两个防坑提醒：采样偏差——你看到的trace经过错误优先采样，不要用它算错误率（第19篇）；幸存者偏差——超时被平台杀掉的请求可能没有完整trace，要配合平台的超时计数指标看全貌。

## 四、把工作流固化为Runbook

上述模式应沉淀为每个服务的排障Runbook，结构统一：症状与对应告警名；第一步看什么图、判据是什么；分支决策树（如"若劣化集中新版本→走发布回滚流程"）；每步的查询语句模板；升级路径（何时拉入下游团队）。Runbook的价值在于把资深工程师的定位直觉转化为团队任何人可执行的步骤，并随每次复盘迭代。

排障Runbook骨架示例：

```markdown
## 告警：order-service P95燃烧率超标
1. 打开看板「下单链路总览」，确认劣化幅度与开始时间
2. 切片对比：版本维度 —— 新版本独有劣化？→ 执行§回滚流程
3. 追踪过滤：service=order-create AND duration>2s AND span.status=ERROR
   观察最厚Span与重试属性，截图入工单
4. 日志取证：trace_id跳转，提取error_code与instance分布
5. 若指向下游：查依赖看板+联系值班（升级矩阵见附录）
6. 恢复后30/60分钟各复查一次燃烧率，确认SLO回落
```

## 五、复盘模板：让每次排障变成资产

排障结束不等于工作结束，用统一模板复盘才能把经验固化。模板五要素：时间线（告警、确认、止血、恢复各时间点，来自第37篇的处置记录）；根因陈述（一句话技术根因加一句话流程根因——为什么没有更早发现、为什么没有更早阻止）；观测评估（这次哪些观测数据起了作用、哪些缺失、哪些误导）；行动项（按"防复发、早发现、快恢复"分类，每项有负责人与截止日）；度量回看（一个月后核对MTTD与MTTR是否真的改善了）。复盘文化的要求是对事不对人，行动项必须可验证，否则复盘会退化为仪式。

## 结语

追踪不是装完就生效的水电，排障能力来自把"指标切片、追踪看树、日志取证、时间对齐"练成固定动作。两个场景、一套框架、一份Runbook——当每次故障都让Runbook变厚一点，团队的可观测投资才算真正回本。
