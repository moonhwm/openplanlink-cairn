# 自定义业务指标上报：计数器、Gauge与直方图实践

> 一句话摘要：本文讲解指标四种类型（Counter、Gauge、Histogram、Summary）的语义与适用场景，云函数环境下批量异步上报的工程要点，以及业务指标选型与命名实践。

## 一、四种指标类型的语义与选型

Counter（计数器）：只增不减的累计值，如订单创建数、错误次数、消息消费数。语义纪律：永远配合rate()使用看增速，绝不直接比较两个时间点的原始值（实例重启后计数从零开始，跨实例聚合靠的是"增速"而非绝对值）。Gauge（瞬时值）：可升可降的当前状态，如队列深度、缓存命中率、当前并发、剩余配额。适合"水位类"观测，告警常用阈值比较。Histogram（直方图）：把观测值分桶累计（如耗时落在0-10ms、10-50ms桶各多少次），存储端可聚合出任意分位数。服务耗时、下游延迟、报文大小的标准选型。Summary（摘要）：客户端直接计算分位数上报，精度高但分位数不可跨实例再聚合（数学限制：分位数不能平均），多实例的函数场景基本应弃用，统一用Histogram。

选型速判：累计事件用Counter；状态水位用Gauge；一切"值的分布"（耗时、大小）用Histogram；Summary仅在单实例进程内观测时考虑。云函数是多实例天然分布式的环境，这一组合（Counter+Gauge+Histogram）覆盖百分之九十九的需求。

## 二、云函数上报的工程要点

函数环境上报指标有三个特殊约束：实例短命（计数器累计值随时归零）、CPU与内存按档位计费（上报开销要轻）、出口网络走VPC或公网（要批量压缩）。工程要点五条。第一，异步批量：指标在内存聚合（如每分钟或每批N条flush），不阻塞业务路径；实例冻结前尽力flush，接受极端情况的少量丢失——用"发送失败计数"自监控丢失量。第二，时序标签要稳定：标签集在实例生命周期内固定复用（预分配序列），避免每条指标新建序列对象造成内存与GC压力。第三，命名与标签遵循第05篇规范（_total/_ms后缀、低基数标签）。第四，导出协议用OTLP或厂商监控SDK，端点凭据走环境变量（严禁硬编码，第11篇原则同源）。第五，上报的指标自己也要有对账：入口日志统计的次数与计数器增速定期对账，偏差大说明有路径漏上报。

多语言上报示例（Python，OTel指标API）：

```python
from opentelemetry import metrics

meter = metrics.get_meter('fn.order')

orders_created = meter.create_counter(
    'biz_orders_created_total', unit='1',
    description='订单创建累计')
handle_duration = meter.create_histogram(
    'biz_handle_duration_ms', unit='ms')
queue_depth = meter.create_observable_gauge(
    'biz_queue_depth', unit='1')     # 观测型gauge用回调采集

def handler(event, ctx):
    t0 = time.time()
    order = create_order(event)
    orders_created.add(1, {'channel': order.channel})   # 低基数标签
    handle_duration.record(round((time.time()-t0)*1000))
    return ok(order)

# queue_depth 回调：每次采集周期由SDK拉取
@queue_depth.observe
def _observe(options):
    return [(mq.depth('orders'), {'queue': 'orders'})]
```

## 三、业务指标的设计模式

四个高频模式。模式一"漏斗指标"：把业务转化漏斗的每层做成同构Counter（visit→add_cart→checkout→paid），漏斗率=gauge派生或看板端rate相除，运营与排障共用。模式二"结果码指标"：所有业务结果按码计数（result_code维度受控词表），成功失败一目了然，比日志聚合便宜得多。模式三"过程分解指标"：复杂处理函数把各阶段耗时分别记Histogram（validate_ms、risk_ms、persist_ms），配合总耗时可定位时间花在哪段。模式四"体验类Gauge"：如"消息积压可消化时间=积压量/消费速率"（派生gauge），直接表达用户等待预期，比裸队列深度更贴近业务语义。

反模式同样四条：标签放用户ID（基数爆炸，第26篇专题）；一个指标塞二十个标签（组合爆炸）；用Gauge记累计事件（丢失"增速"语义且重启后跳变）；每个函数自定义一套命名（跨函数不可比）。

## 四、上报可靠性验证

指标体系的"静默失败"很常见（SDK配置错、端点不可达、标签类型错被丢弃），必须主动验证：本地开发用metrics测试后端（如Prometheus测试 exporter）断言指标存在；上线后用对账任务——按小时比较"日志入口计数×采样还原"与"指标增速"，偏差超百分之五告警；金丝雀指标（每分钟固定+1的heartbeat counter）用于确认管道端到端存活。

自定义指标落地清单：

```text
[ ] 选型纪律：累计Counter/水位Gauge/分布Histogram；弃Summary
[ ] 异步批量+冻结前flush；丢失量自监控计数
[ ] 命名后缀与低基数标签入规范；词表化管理result_code等
[ ] 漏斗/结果码/阶段分解/体验Gauge四模式按需采用
[ ] 对账任务：日志计数 vs 指标增速，偏差>5%告警
[ ] heartbeat金丝雀指标守护管道存活
```

## 六、指标SDK自身的开销控制

上报体系的开销常被忽略，这里给出控制手段。聚合优先：能在内存预聚合的（如计数器累加、直方图内存桶）绝不在每次调用都序列化发送，SDK的批量周期（十到六十秒）是第一杠杆。指标集瘦身：启动时把本函数会用到的指标与标签组合预创建为固定序列对象，运行期只更新值不新建序列，内存与GC双双下降。异常路径降级：导出失败时指标进入有界环形缓冲，缓冲满则丢最旧并计数，绝不允许指标子系统反噬业务内存（有界性是硬要求）。最后用冷启动视角审视：SDK初始化（建连、握手）会加到init_ms上，选择懒初始化（首次调用时建连）与连接复用，把指标子系统的冷启动贡献控制在十毫秒以内，并用第04篇方法实测验证。

## 结语

自定义业务指标让观测从"系统活着吗"升级到"业务在正常运转吗"。类型选对、批量上报、对账验证三件事做扎实，业务指标就能用指标级的成本（便宜、可告警、可长期保留）承载原本只能靠日志回答的问题。
