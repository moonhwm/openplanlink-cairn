# 日志级别体系与采样策略

> 一句话摘要：本文定义云函数环境下的四级日志语义与升降级规则，讲解按级别差异化保留与按流量/状态采样的完整策略，平衡观测完整性与存储成本。

## 一、日志级别的语义重塑：每个级别必须有排他定义

多数团队的日志级别是混乱的：error里混着业务分支，warn满天飞，info里塞满调试细节。要让级别体系可用，必须给每个级别一个排他性定义并强制执行。error：本次调用未能完成预期职责，或虽完成但触发了补偿/降级动作；必须附带error_code与堆栈（如适用）；每条error都应值得被统计进错误率。warn：调用完成但出现需要关注的异常征兆——重试后成功、降级可用、接近阈值、遇到脏数据跳过；warn应"可解释"，一条持续两周没人处理的warn要么升级处理要么降级为info。info：关键业务节点与调用生命周期事件（入口、出口、关键状态迁移）；info是生产默认级别，词表事件大多落在这里。debug：过程细节与变量快照，生产环境默认不输出或重采样输出，排障时临时打开。

配套两条纪律。第一，禁止"以防万一"式打日志：写日志前先回答"这条日志触发时我会做什么动作"，答不上来就删。第二，级别必须与动作挂钩：error进错误率告警，warn进周报复盘，info支撑审计与排障，debug只服务临时排障。这样级别才成为体系的一部分而非装饰。

## 二、按级别差异化保留与输出策略

不同级别的数据价值密度差异巨大，应差异化对待。info及以上：全量输出，保留三十到九十天，热存七天支持快速查询。debug：生产默认关闭（通过环境变量或配置中心开关），临时开启只针对目标函数并自动在若干小时后关闭，避免开完忘关导致日志暴涨。error：全量保留且保留期最长（一年以上合规归档），因为错误样本是稀缺资源。此外可对info中的大字段（data里的列表、快照）做条件输出：请求正常时不带响应体摘要，出错时才带上。

输出频率本身也要预算：单个函数的info事件数每次调用不宜超过十条，热点路径循环体内禁止打info（循环日志改聚合：循环结束后打一条带次数与耗时的汇总日志）。

## 三、采样策略：四种模式与组合

高流量函数全量保留info既贵也无必要，采样是标准解法。第一种是错误优先采样：错误与warn永不采样必须全保留；info按比例采样（如百分之十）；这保证"出问题的请求证据完整，正常的请求省着存"。第二种是尾部延迟采样：结合追踪信号，只保留P95之外慢请求的完整日志——慢请求最值得事后分析，正常快请求的日志价值低。第三种是状态采样：函数按调用结果分流，失败调用全保留、成功调用低比例保留。第四种是新版本加权：灰度函数或新发布版本的日志保留率临时调高（如百分之百观察一小时），稳定后再回落。

实现要点是采样决策在日志库层统一封装，业务代码无感知，且采样率可配置中心动态调整。注意采样对统计的影响：按百分之十采样的info事件做计数统计时要乘以十还原，且只用于量级估计，精确统计必须依赖指标而非采样日志。

采样策略配置示例：

```yaml
logging:
  defaults:
    levels: ["error", "warn", "info"]       # debug默认不输出
    retention:
      error: 400d
      warn: 90d
      info: 30d
  sampling:
    rules:
      - match: { function: "order-create-fn", level: "info", status: "ok" }
        keep_ratio: 0.10                     # 正常请求info保留10%
      - match: { level: "error" }
        keep_ratio: 1.0                      # 错误全保留
      - match: { version_tag: "canary" }
        keep_ratio: 1.0                      # 灰度版本全保留
      - match: { slow_request: true, level: "info" }
        keep_ratio: 1.0                      # 慢请求全保留
  debug_switch:
    enabled: false
    auto_off_after: 4h                       # 防止忘记关闭
```

## 四、验证与治理机制

采样与级别策略上线后要持续验证三点。一是完整性验证：定期抽查错误请求，确认其全部日志（含info）都在——如果错误请求的info被采样掉了，排障链路就断了，错误优先规则失效。二是成本验证：日志存储费用按函数排名，占比异常的函数检查是否循环打日志或字段膨胀。三是信号衰减验证：统计warn的周新增量与处理率，长期不处理的warn降噪处理。

日志级别与采样治理清单：

```text
[ ] 四级定义成文且评审时检查级别使用是否合规
[ ] error附error_code+堆栈；warn必须可解释可处理
[ ] debug默认关、开关自动回收、循环内禁打info
[ ] 错误/warn永不采样；info按状态差异化采样
[ ] 灰度版本与慢请求日志临时全保留
[ ] 采样日志统计需还原系数；精确量走指标
[ ] 每月复核：日志费用Top函数、warn处理率、必查字段完整率
```

## 五、级别变更的审计与责任

级别调整与采样配置变更本身要留下审计痕迹：谁在何时把哪个函数的info采样率从百分之十调到百分之一、谁临时打开了debug开关，都应记录变更人与理由，纳入周报复核。实践中出现过多次"有人排障时打开全量日志，忘记关闭，一周后日志费用翻了五倍"的事故，审计加自动回收是唯一的系统性解法。同时建议把级别决策权与采样配置权分开：开发者可以决定打什么级别，但生产环境的采样率与开关由平台组统一管理，避免每个团队各自为政造成费用失控。

## 结语

级别体系解决"什么值得记"，采样策略解决"留存多少"，两者合起来是日志的经济学。核心原则只有一条：稀缺的存储留给稀缺的信息——错误与异常永远全量，正常与细节按需采样。做到这点，日志费用可控而排障能力不打折。
