# 追踪数据的存储与查询：从Span到服务拓扑图

> 一句话摘要：本文讲解追踪后端的存储模型（宽表、索引、TTL）、影响查询体验的索引设计、从Span聚合出服务拓扑与依赖统计的方法，以及追踪查询的典型模式与性能优化。

## 一、追踪后端的存储模型

追踪数据落地有三种主流模型。模型一：宽列存储（Jaeger/ClickHouse/Tempo风格）——每行一个Span，列包含trace_id、span_id、parent_id、服务名、操作名、耗时、状态、属性（JSON或展开列）、时间戳；按trace_id聚簇或建索引，查一个trace即按trace_id拉取全部行重建树。优点是灵活可聚合（直接SQL出依赖图、分位数），成本可控；缺点是trace_id索引的写放大。模型二：对象存储打包（Tempo的"trace即对象"路线）——Span写入时按trace_id聚合成块存对象存储，索引只存trace_id到块的映射（甚至只存CRC省索引）。优点是存储成本极低、适合海量低频回溯；缺点是按服务/耗时等维度检索弱，需要配合指标（exemplars）跳转。模型三：厂商托管——平台内置，开箱即用但受限于其查询能力。规模参考：日均千万级调用的系统，按错误慢请求加百分之一正常采样，典型日增Span量在千万到亿级，宽表模型配合TTL完全可承载；预算敏感或回溯周期长的场景适合模型二。

TTL策略与日志分层类似：追踪默认保留七到三十天（排障窗口），价值密度低于日志的错误样本可导出到归档库长存。属性字段要控制数量（高基数属性如user_id不作索引列，仅留JSON内可查）。

## 二、查询的典型模式与索引设计

追踪查询有五种高频模式，索引设计逐一覆盖。模式一：按trace_id取整树——最高频，trace_id强索引（聚簇最优）。模式二：按服务名+时间窗+条件（错误、耗时区间、操作名）列表——服务名+时间分区索引，错误与耗时作为可过滤列。模式三：按tag/属性检索（如order_id=xxx找到对应trace）——这要求业务把关键业务ID作为受控属性（第22篇），对低基数白名单属性建二级索引，高基数属性靠采样留存的关联（从日志拿trace_id再查树）。模式四：聚合统计——服务依赖、操作耗时分布、错误码分组，走预聚合表或离线管线（小时级汇总到指标表），不在原始Span上实时大聚合。模式五：从指标下钻（exemplars）——直方图某分位桶关联典型trace_id，点一下直达现场，是"指标发现异常、追踪看现场"的体验闭环。

查询性能优化三原则：必带时间窗（分区裁剪）；必带服务名或trace_id之一（索引命中）；避免前导通配的属性值匹配（索引失效），属性查找用等值或精确前缀。

## 三、从Span聚合服务拓扑

服务拓扑图是Span数据的最大增值产物。生成方法：抽取所有CLIENT（含PRODUCER）Span，边＝（调用方service.name → 被调方peer.service），按窗口聚合统计调用量、错误率、耗时分位数；服务节点度数＝调用出入边数。得到的有向图再叠加健康着色（错误率超标标红）即成依赖地图。工程要点：第一，peer.service词表受控（第15篇），否则同一下游出现mysql/mysql-prod/rds-01三个节点，图不可读；第二，异步边（队列）用虚线表达并在边上标注队列名与排队延迟（第18篇的queue_lag_ms），与同步边区分；第三，图的时效性——依赖关系按天级快照保存，支持"上周拓扑与本周对比"，发现依赖突变（新服务被引入、某下游解耦）。第四，自环与循环引用正常存在（函数互调），渲染时做分层布局避免视觉混乱。

拓扑数据还派生两个治理报表：影子依赖清单（生产实际存在但架构图没有的依赖——通常是绕过审批的私接调用）；孤儿服务清单（无任何调用方的服务——疑似废弃，进入下线评审）。

## 四、查询工作流与SOP固化

把高效查询固化为排障SOP：第一步从告警/看板拿服务名+时间窗；第二步用"错误+服务"列表定位异常trace（或从日志拿trace_id）；第三步打开树看最长路径与错误节点；第四步跳转该Span窗口日志确认细节。SOP里写明每步的预期耗时（如trace查询应在三秒内返回），超时即是后端索引问题，转基础设施排查。

追踪存储与查询检查清单：

```text
[ ] 存储模型选型明确：宽表（灵活聚合）vs 对象打包（低成本回溯）
[ ] TTL分层：默认7-30天；错误样本归档长存
[ ] 五类查询各有索引支撑：trace_id/服务+时间/白名单属性/预聚合/exemplars
[ ] 查询三纪律：时间窗+服务名+等值匹配；禁前导通配
[ ] peer.service词表受控；异步边虚线+排队延迟标注
[ ] 拓扑按天快照、支持对比；影子依赖与孤儿服务月度报表
[ ] 排障SOP含查询耗时预期与超时升级路径
```

## 五、查询能力的推广与培训

追踪系统建好后最大的浪费是"只有两个人会用高级查询"。推广三招：第一，把高频查询固化成保存的查询模板与看板按钮（"最近错误Trace""最慢Trace Top10"），一键可用不需要学查询语法；第二，开展三十分钟的实战工作坊，用一条真实慢请求走完"列表—树—日志跳转"全流程，比任何文档有效；第三，把追踪查询嵌入日常流程——发布观察、周报慢请求清单、故障复盘都引用Trace链接，让"看树"成为肌肉记忆。度量推广效果用"周活跃追踪用户数"与"人均周查询次数"，低于团队规模的三成说明可用性或培训有问题。

## 结语

追踪数据的价值最终兑现于查询体验：三秒打开一棵树、一次点击从指标到现场、一张可信的拓扑地图。存储模型与索引设计决定这一切的底座，聚合管线与SOP决定上层的效率。下一篇回到具体排障场景，实战演练"慢调用与错误传播"的定位模式。
