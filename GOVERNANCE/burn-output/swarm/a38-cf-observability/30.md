# 指标数据存储原理与降采样策略

> 一句话摘要：本文讲解时序数据库存储指标的基本原理（LSM、时间分片、标签倒排）、高基数的存储代价、降采样与保留策略的设计方法，以及成本估算与容量规划。

## 一、时序库如何存指标：三个核心机制

理解存储原理才能理解成本结构。机制一：面向时间分片。时序数据按时间块组织（常见每两小时一块），块内按序列排序存储，查询带时间范围时整块跳过无关数据——这是"查询必须带时间窗"成本收益的根源。机制二：标签倒排索引。每个序列由标签集唯一标识，倒排索引支撑"按标签选择序列"；基数爆炸的第一现场就是这个索引：一百万高基数标签意味着一百万索引项与一百万独立序列，写入时每次都要定位序列——这就是第26篇基数治理的存储侧解释。机制三：压缩与编码。时序值用差分/Gorilla类编码（相邻点差值极小，压缩比常见十倍以上），但只有"同一序列内相邻点"才能享受；频繁新建序列（动态标签）使压缩失效。三个机制合成的成本公式：总成本≈序列数×索引与元数据成本＋总点数×存储成本＋查询扫描量×计算成本。降基数、降点数、降扫描是三大省钱杠杆。

## 二、降采样：设计原则与执行方案

降采样指把细粒度原始点聚合成粗粒度点以降低长期点数，例如一秒级原始数据保留十五天，之后只保留五分钟聚合与一小时聚合。设计四原则。第一，可聚合性优先：预聚合成"可再次聚合的形态"——计数器存为窗口增量（和可再求和）、直方图存桶计数和、比率拆成分子分母两序列；绝不预聚合成分位数或比率本身（第28篇数学陷阱）。第二，分层保留与查询透明：原始十五天、五分钟九十天、小时四百天；查询层根据时间范围自动路由粒度（查近一小时用原始、查近一年用小时），用户无感知。第三，聚合窗口与标签保持：降采样只减点不减维（标签原样保留），除非专门做维度裁剪（长期层可丢弃冷维度如instance）。第四，边界处理：窗口聚合要处理稀疏序列（无数据的窗口不造零点，除非是真实计数语义）与时区对齐（对齐UTC整点，日报按业务时区在查询层转换）。

降采样任务配置示例：

```yaml
downsampling:
  - metric: fn:invocations
    keep: { raw: 15d, "5m": 90d, "1h": 400d }
    rules:
      - { src: raw, dst: "5m",  fn: sum_per_5m }      # 计数→窗口和
      - { src: "5m", dst: "1h", fn: sum_of_5m }        # 粗层由细层再聚
  - metric: fn:duration_ms_bucket
    rules:
      - { src: raw, dst: "5m",  fn: sum_by_le }        # 桶计数求和
      - { src: "5m", dst: "1h", fn: sum_by_le }
  on_missing_window: skip                              # 稀疏序列不造点
  drop_labels_after: { "5m": [instance] }              # 粗层裁实例维度
```

## 三、保留策略与数据生命周期的联动

保留策略回答"每一层留多久"，输入三方面：排障需要（原始粒度覆盖典型故障回溯窗，两周足够绝大多数）、趋势需要（容量规划要同比年数据，小时级一年）、合规与审计（成本与容量的历史证据，月级快照长期归档）。与第14篇日志分层呼应，指标分层更简单（指标天然小），但同样需要"删除证明"能力（某些合规场景要求可证明过期数据已物理删除）。执行层的两个工程细节：过期删除要用时序库的原生TTL（块级删除，便宜）而非查询式删除（昂贵）；变更保留策略前先算清成本影响（缩短原始层保留常能省下大头，因为原始点数占总量八成以上）。

## 四、成本估算与容量规划

指标存储容量的估算公式：总点数≈序列数×每序列每分钟点数×保留分钟数。例：五千序列、每序列每分钟一点（含直方图多桶已折算进序列数）、原始保留十五天：5000×1×21600分钟=一点零八亿点，按压缩后每点一点五字节估约一百六十MB——指标其实很便宜，贵的永远是基数失控（序列数乘一万，一切乘一万）。规划节奏：按月复核序列数与点数增速（业务增长百分之三十则指标预算同步涨）；新建函数走指标评审（第26篇）从源头控；预留接收端与查询的容量水位（写入QPS、并发查询数），避免大促流量把观测管道先打挂——观测系统自身的容量也要有SLO。

降采样与存储检查清单：

```text
[ ] 预聚合保持可再聚合形态：增量/桶和/分子分母，禁聚分位数比率
[ ] 分层保留+查询自动路由粒度；用户无感知
[ ] 粗层裁剪冷维度；稀疏序列不造点；窗口对齐UTC
[ ] 删除走原生TTL块级；保留策略变更前做成本测算
[ ] 月度复核序列数/点数增速与水位；观测系统自身有容量SLO
```

## 五、存储选型的量化对比

最后给一组选型参考维度：同为Prometheus生态，自建单机Prometheus简单但无高可用；VictoriaMetrics压缩率与乱序写入支持突出，remote write场景的性价比常最优；Thanos与Mimir提供对象存储-backed的长存储与全局查询，适合多集群。量化对比的指标：每百万样本的存储字节数、每秒百万样本写入的CPU消耗、常见查询（单序列、聚合、分位数）的P95延迟、高基数场景的稳定性表现。选型方法是用真实流量的镜像回放压测一周，而不是看评测文章——各家的压缩与索引实现差异会让结论因数据形态（序列数、点密度、标签结构）而完全不同。

## 结语

指标存储的成本结构决定了治理方向：基数决定一切，降采样与分层保留是第二杠杆，查询纪律是第三杠杆。理解"序列×点数×扫描"的三元成本公式，指标体系就能在业务增长中保持线性可控。指标专题至此完结，下一篇进入告警体系。
