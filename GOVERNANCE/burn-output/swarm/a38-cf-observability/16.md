# OpenTelemetry在云函数中的接入原理与实战

> 一句话摘要：本文讲解OpenTelemetry（OTel）的核心组成（API/SDK/传播协议/Collector），云函数接入的三种模式（厂商托管层、SDK手动埋点、扩展层Agent）与导出配置实践。

## 一、OTel的组成与为什么它是事实标准

OpenTelemetry是CNCF的可观测数据采集标准，目标是让埋点代码与后端解耦：今天把Span发给A厂商，明天换B厂商或自建，代码一行不改。它的组成分四层。API层：应用代码面对的接口——Tracer、Span、Propagator（上下文编解码）等，以依赖库形式引入。SDK层：API的实现，管采样、批处理、资源标注（Resource：服务名、版本、环境）、导出（Exporter）。传播协议：跨进程传递上下文的编码格式，事实标准是W3C Trace Context（traceparent头）与Baggage；OTel默认兼容旧格式（b3、jaeger头等）以便存量系统互通。Collector层：独立部署的接收—处理—导出管道，做采样决策、富化、多后端分发。对云函数的意义尤其大：函数环境里Agent常驻不便，OTel以轻量SDK加Collector组合，成为跨厂商迁移与混合云观测的通用底座。

## 二、云函数接入的三种模式

模式一：平台托管集成。主流FaaS平台提供"一键开启OTel"，平台自动注入追踪层：入口自动建根Span、常见客户端（HTTP、数据库驱动）自动埋点、自动导出到平台后端。优点是零代码五分钟接入；局限是自动埋点覆盖面取决于平台（通常是HTTP与主流数据库），自定义业务Span仍需写代码，且数据被锁定在平台后端。模式二：SDK手动接入。函数引入OTel SDK（各语言包：opentelemetry-js/python/java/go），代码里startSpan/endSpan，通过OTLP协议导出到自建Collector或任意兼容后端。控制力最强、可移植，代价是代码侵入与包体积（几十到上百KB，对冷启动有轻微影响）。模式三：扩展层Agent。函数旁挂一个OTel Collector扩展（Lambda Extensions机制或自定义运行时侧车），SDK只负责本地HTTP导出到localhost的Agent，Agent负责缓冲、批量、重试、多目标分发。优点是导出逻辑不占函数执行时间片、实例销毁时Agent有flush机会，数据丢失更少；缺点是内存开销增加（Collector约几十MB）与镜像管理成本。

选型建议：起步用模式一快速覆盖平台内链路；需要跨后端、自定义语义、或平台无托管能力时上模式二；高价值链路对数据完整性要求高时升级模式三。三模式的埋点代码可以完全一致（都写OTel API），差别只在初始化与导出配置，这正是API/SDK分离的好处。

## 三、SDK接入的实战配置

以Node.js函数为例的最小可用接入：初始化时注册TracerProvider、资源标注、OTLP导出与批量处理；入口包装器里用W3C上下文延续trace。

```javascript
// tracing.js —— 初始化（冷启动执行一次）
const { NodeSDK } = require('@opentelemetry/sdk-node');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-http');
const { Resource } = require('@opentelemetry/resources');
const { SEMRESATTRS_SERVICE_NAME, SEMRESATTRS_SERVICE_VERSION } =
  require('@opentelemetry/semantic-conventions');

const sdk = new NodeSDK({
  resource: new Resource({
    [SEMRESATTRS_SERVICE_NAME]: process.env.FUNCTION_NAME,   // 拓扑节点名
    [SEMRESATTRS_SERVICE_VERSION]: process.env.FN_VERSION,
    env: process.env.ENV,
  }),
  traceExporter: new OTLPTraceExporter({
    url: process.env.OTLP_ENDPOINT,     // Collector地址，从环境变量读取
  }),
  batchSpanProcessor: { maxQueueSize: 2048, maxExportBatchSize: 512,
                        scheduledDelayMillis: 1000 },
});
sdk.start();
// 注意：实例冻结前无法可靠shutdown，接受批量发送的少量丢失，
// 高价值链路改为同步导出或扩展层Agent flush。
```

```javascript
// handler包装：延续上游trace + 自动根Span
const { trace, context,Propagation, ROOT_CONTEXT } = require('@opentelemetry/api');
const propagator = new Propagation();   // W3C默认

exports.handler = async (event, ctx) => {
  const carrier = extractHeaderCarrier(event);            // 从触发事件取头
  const parentCtx = propagator.extract(ROOT_CONTEXT, carrier);
  const tracer = trace.getTracer('fn');
  return tracer.startActiveSpan(`${process.env.FUNCTION_NAME}.http`,
    { kind: 1 /*SERVER*/ }, parentCtx, async (span) => {
      span.setAttribute('faas.cold_start', isCold());
      try {
        const out = await business(event);
        span.setStatus({ code: 1 }); return out;
      } catch (e) {
        span.setStatus({ code: 2, message: e.code || 'error' });
        span.recordException(e); throw e;
      } finally { span.end(); }
    });
};
```

## 四、资源标注、导出与常见坑

资源（Resource）标注决定数据归属，必须统一：service.name用函数名（与peer.service词表一致）、service.version关联发布、deployment.environment区分环境；缺资源标注的Span在拓扑里成为孤儿节点。导出配置三要点：批量参数权衡内存与延迟；导出端点与认证凭据从环境变量或密钥管理服务注入（严禁硬编码）；异步导出在函数冻结场景的丢失窗口要有认知并按第19篇的采样与优先级策略兜底。常见坑：自动埋点与手动Span重复计时（同一HTTP调用出现两个Span）——保留自动埋点则业务代码不要再包一层；上下文丢失于回调（旧式回调API要用context包装）；包体积膨胀影响冷启动——按需引入检测包而非全家桶。

OTel接入检查清单：

```text
[ ] 三种模式选型明确：托管起步/SDK自控/扩展层高可靠
[ ] Resource统一：service.name=函数名、version、env
[ ] 入口W3C延续上游trace；下游请求注入traceparent
[ ] 批量导出参数与丢失窗口经过评估；端点凭据走环境/密钥服务
[ ] Span上限与裁剪规则生效；无重复埋点
[ ] 依赖包按需引入，冷启动影响已测量
```

## 五、OTel版本升级与兼容治理

OTel生态迭代快，版本治理要未雨绸缪。三条纪律：其一，API与SDK版本解耦使用——业务代码只依赖稳定的API包（trace、metrics接口），SDK与exporter由封装层统一锁定版本，升级SDK不动业务代码；其二，升级走灰度节奏——新SDK先在测试函数与灰度函数运行两周，验证Span结构、资源属性、导出吞吐无回归后再全量推进，重大版本（协议或语义约定变更）附迁移文档；其三，语义约定（semantic conventions）的字段名变更是最常见的静默破坏源——升级前diff新旧版本的属性名（如http.url到url.full的迁移期），确认看板与依赖图查询所引用的属性已同步更新，否则拓扑图会一夜之间丢节点。建议维护一个OTel配置基线仓库，记录当前锁定的版本、自定义的Resource属性、启用的instrumentation清单，升级评审以它为准。

## 六、导出通道的故障演练

OTel导出链路自身的故障要在演练中验证过才可信：模拟Collector端点不可达（改错端点配置），观察SDK的行为——批量队列应按配置堆积并按上限丢弃最旧（drop计数可见），业务调用不应被阻塞或变慢；恢复端点后导出应自动续传，丢失窗口与drop计数能对上。再模拟慢端点（延迟十秒响应），确认超时与重试配置生效而非无限等待。把这两个演练纳入上线前的验收清单与季度混沌项目，导出通道从"假设它可靠"变成"验证过它可靠"。

## 结语

OTel把"埋一次点、到处可发"变成现实，是云函数追踪体系抵抗厂商锁定的基石。接入路径清晰：先托管快速见效，再SDK标准化代码，最后按需加Collector增强可靠性。下一篇深入这套体系最精巧的部分——上下文如何跨函数、跨队列、跨异步边界传播。
