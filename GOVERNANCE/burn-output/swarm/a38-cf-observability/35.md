# 错误预算与SLO告警实践：从预算消耗到发布管控

> 一句话摘要：本文把第06篇的SLO理论落成日常实践：预算仪表盘、多窗口燃烧率告警配置、预算耗尽时的发布管控流程，以及预算数据驱动的稳定性决策案例。

## 一、预算仪表盘：让预算消耗可见可议

SLO要影响决策，先要被看见。预算仪表盘的三屏设计。屏一服务总揽：每个核心服务一行——SLO目标、当前达成率、预算剩余百分比、燃烧速率（快慢两档窗口）、趋势箭头。预算剩余低于百分之二十五的行标黄、低于百分之十标红。屏二燃烧分析：选定服务后展示预算消耗的时间线（每天烧了多少、被什么烧的——按错误码与故障事件标注），回答"预算花在哪"。屏三发布关联：把发布事件（版本上线时间线）叠在燃烧曲线上，直观呈现"每次发布烧了多少预算"，这是发布质量的量化证据。仪表盘数据来源：SLI指标管线（第23至28篇）加事件表（故障与发布记录）；每天定时计算预算快照落库，历史可回溯。

## 二、多窗口燃烧率告警的完整配置

燃烧率告警的实操细节在第31、32篇基础上补齐三件。第一，SLI管道先行：可用性SLI=成功调用/总调用（排除项在分子分母同时排除，第06篇），延迟SLI=达标调用/总调用；两个SLI各自一套燃烧告警。第二，双档窗口配置：快速档（1h×14.4 且 5m×14.4，两分钟for，P1页级）捕捉急性故障；慢速档（6h×6 且 1h×6，P2工单级）捕捉慢性渗漏（每天漏一点，一周烧完预算）。第三，恢复与关闭：燃烧率恢复正常持续十分钟自动resolved；慢速档告警在预算恢复（错误率回落）后关闭。云函数特有注意：异步链路SLI的统计延迟要纳入窗口选择（第06篇），且重试放大期间（上游重试导致失败激增）燃烧率会瞬间尖峰，for条件与双窗口"且"逻辑天然过滤大部分此类毛刺。

燃烧率告警配置实例：

```yaml
- name: order-avail-burn-fast
  expr: |
    (1 - sli:order_availability:ratio_rate1h)  / (1 - 0.995) > 14.4
    and
    (1 - sli:order_availability:ratio_rate5m)  / (1 - 0.995) > 14.4
  for: 2m
  severity: P1
  annotations:
    summary: "下单可用性预算快速燃烧(1h/5m)"
    budget_note: "按当前速率约{{2h}}烧完月预算"
    runbook: "https://wiki/rb/order-burn"
- name: order-avail-burn-slow
  expr: |
    (1 - sli:order_availability:ratio_rate6h) / (1 - 0.995) > 6
    and (1 - sli:order_availability:ratio_rate1h) / (1 - 0.995) > 6
  for: 30m
  severity: P2
```

## 三、预算驱动的发布管控流程

预算的真正威力在管控发布。流程设计：发布前检查——CI/CD流水线读取预算剩余，低于百分之二十五时非修复类发布需SRE会签，低于百分之十时自动冻结（仅允许修复与回滚类变更），冻结与解冻的判定是自动的、公开的（每次拦截记录工单）。灰度期间——新版本按小比例放量，实时对比新旧版本对该服务SLI的贡献（按版本标签切片，第27篇），若灰度版本的错误率贡献使燃烧率超快速档阈值，自动回滚。发布后——七十二小时观察窗内的新增燃烧归因到该发布，计入"发布燃烧账本"；月度复盘展示各团队的发布燃烧排名，把"发布质量"从感觉变成数据。要防止的异化：为保预算而故意把SLI口径做松（排掉真实失败）——口径变更需评审并留痕；以及在预算充裕时肆无忌惮地发危险变更——预算是信任额度，CI里仍要有常规质量门禁，两者并行。

## 四、实践案例：一次预算告警的完整处置

时间线复盘一个典型场景。14:02 慢速档燃烧告警（P2工单）：下单可用性过去六小时燃烧率八倍。值班工程师打开预算仪表盘屏二，看到燃烧自13:30开始、错误码集中为INVENTORY_TIMEOUT；比对发布线，13:25有版本上线（库存客户端依赖升级）。按Runbook执行：灰度该版本发现错误率立即复现→回滚→14:20燃烧率回落→预算曲线趋平。复盘结论：发布引入连接池配置缺陷；发布燃烧账本记该版本消耗预算百分之四；行动项：发布模板增加连接池冒烟测试、慢速档告警提前到燃烧率六倍触发（原来八倍）。这个案例展示了闭环价值：预算发现异常、仪表盘归因、Runbook行动、复盘反哺规则——四个环节各出一份力。

SLO告警实践检查清单：

```text
[ ] 预算仪表盘三屏上线：总览/燃烧分析/发布关联
[ ] 可用性与延迟双SLI各配快慢两档燃烧告警
[ ] CI集成预算检查：<25%会签、<10%自动冻结(留痕)
[ ] 灰度按版本切片对比SLI，超阈值自动回滚
[ ] 发布燃烧账本与月度排名；口径变更需评审
[ ] 每次燃烧事件复盘并回改规则(阈值/窗口/Runbook)
```

## 五、预算沟通中的常见争议与裁决

预算机制运转中会出现典型争议，提前定好裁决原则。争议一"冻结影响业务上线"——裁决原则：冻结是保护用户的合约条款，业务方可选择消耗自己服务的预算豁免（把稳定性风险显式转移给请求方并留决策记录），但不能默认豁免。争议二"SLO定太松导致预算永远用不完"——季度评审收紧目标（长期达成率超过百分之九十九点五的目标应收紧），松目标等于没有预算约束。争议三"非我方责任的预算消耗（云厂商故障）"——SLI排除项中定义厂商责任窗口（有厂商公告的事件期），该期间消耗不计入团队预算，但必须记录与复盘依赖风险。

## 结语

错误预算把"稳定还是快"的路线之争变成一本可查的账：预算内放心迭代，预算见底冻结变更，燃烧异常自动叫醒。当发布、告警、复盘都围绕这本账运转，SLO就不再是墙上的文档，而是系统里活的治理机制。
