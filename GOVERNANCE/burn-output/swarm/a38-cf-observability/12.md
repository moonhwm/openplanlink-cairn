# 日志上下文注入：请求ID、租户ID、版本号的自动附加

> 一句话摘要：本文讲解如何让trace_id、request_id、tenant_id、version、灰度标记等上下文字段在云函数中全自动注入每条日志与指标，消除手工传递的遗漏与成本。

## 一、为什么必须自动化注入

排障的第一动作是"把一次请求的所有日志拉出来"，这要求每条日志带同一个trace_id。如果靠开发者在每个函数里手工把event里的字段拼进日志，结果必然是：一半函数忘了打、字段名不一致、异步分支断链。人工纪律在几十个函数、多名工程师、多语言栈的规模下不可持续，唯一可靠的方案是库层自动注入：日志库从当前上下文（线程局部变量、协程上下文、async hooks）读取关联键，序列化时自动写入，业务代码对关联键零感知。

自动注入的价值不止排障。注入tenant_id后，日志才能按租户聚合出"某租户的错误率"这类视角；注入version后，灰度发布才可对比"新旧版本的耗时与错误"；注入灰度标记后，问题版本可以分钟级回滚定位。上下文字段是日志从"记录"变成"多维数据"的维度来源。

## 二、注入的实现机制：各语言的上下文载体

自动注入的技术核心是"调用级上下文"的载体。Node.js用AsyncLocalStorage（async hooks机制）：入口包装器把trace_id等写入storage，pino封装从storage读取注入child logger；异步链路自动传播。Python用contextvars.ContextVar：入口bind，structlog的merge_contextvars处理器自动合并；注意实例复用时入口必须重新bind覆盖旧值。Java用MDC/ThreadContext：入口put、finally里clear，logback encoder自动输出；必须清理，否则下一个复用调用的日志会带上前一个请求的trace_id，造成灾难性的串号。Go用context.Context显式传递：slog的logger.With随ctx携带，标准做法是handler入口构造logger并向下传ctx；Go没有隐式上下文，这是它的类型系统决定的，封装函数接收ctx即可统一。

包装器模式示例（Node.js，入口统一包裹）：

```javascript
const { AsyncLocalStorage } = require('async_hooks');
const storage = new AsyncLocalStorage();

function withContext(event, ctx, fn) {
  const traceId = extractTraceId(event) ?? newTraceId();
  const tenantId = parseTenant(event);
  return storage.run({ trace_id: traceId, request_id: ctx.requestId,
                       tenant_id: tenantId }, fn);
}

// pino封装：每条日志序列化前自动合并上下文
function makeLogger(base) {
  return {
    info: (obj, msg) => emit('info', obj, msg),
    error: (obj, msg) => emit('error', obj, msg),
    // ...
    _merge: (o) => ({ ...storage.getStore(), ...base, ...o }),
  };
}

exports.handler = async (event, ctx) =>
  withContext(event, ctx, async () => {
    // 业务代码里任何地方调用log.info，trace_id/tenant_id自动在场
    log.info({ event: 'order_created', data: { order_id: 'O-1' } });
  });
```

## 三、上下文从哪里来：各类触发源的提取规则

上下文的来源因触发方式而异，注入器需要一张提取规则表。HTTP/API网关触发：trace_id优先取请求头标准字段（traceparent/W3C头或厂商头），没有则生成；tenant_id从认证后的JWT声明或路径/域名提取。队列触发：从消息属性（message attributes）里取上游塞入的trace上下文；没有则用消息ID做关联键并新建trace。定时触发：每次执行生成新trace_id，同时带schedule名做维度。事件总线/发布订阅：从事件的元数据字段取，规范要求发布方把上下文放进信封。函数间直接调用：调用方负责在payload信封里带上下文，被调方入口提取。这套规则的实质是第17篇"上下文传播"在日志侧的落点：提取规则与追踪传播规则共用同一张表，避免两套口径。

除请求级上下文外，还有部署级上下文：function、env、version从平台环境变量读取（process.env.FUNCTION_NAME等），实例级上下文instance_id在初始化时生成随机值。三级上下文（部署级静态、实例级半静态、请求级动态）分别缓存，性能开销可忽略。

## 四、验证与守护机制

自动注入要有守护，防止悄悄失效。三个手段：一是完整率指标——对入库日志统计trace_id字段填充率、tenant_id填充率，低于阈值（如99%）告警，通常意味着新函数没用标准包装器或某触发源提取规则缺失；二是金丝雀测试——测试环境对每种触发源各发一条请求，断言日志里上下文字段非空且贯穿；三是串号检测——Java等MDC场景抽查同一instance连续两条日志的request_id是否不同，相同即清理遗漏。此外版本字段要能与部署系统对账：看板上按version聚合时，每个在跑版本都应在部署记录中存在。

自动注入落地清单：

```text
[ ] 各语言选定上下文载体（ALS/contextvars/MDC/ctx）并封装入口包装器
[ ] 提取规则表覆盖全部触发源：http/队列/定时/事件总线/直调
[ ] 部署级/实例级/请求级三级上下文分层注入
[ ] Java MDC入口覆盖、finally清理；Python实例复用时重bind
[ ] trace_id与追踪系统同源（traceparent解析优先）
[ ] 完整率指标+按触发源金丝雀+串号检测三项守护上线
```

## 五、上下文丢失的排查手法

当串号检测或完整率指标报警时，按固定手法排查。第一步定位模式：丢失是全量缺失（某函数所有日志都无trace_id，说明没用标准包装器）、还是部分触发源缺失（只有队列触发的日志缺失，说明该触发源的提取规则没实现）、还是间歇性串号（同一请求的日志带上了别人的tenant_id，说明异步上下文在某个回调边界丢失或实例复用未重置）。第二步用最小复现：对每种触发源各发一条带标记的测试请求，逐跳检查字段在哪一跳消失。第三步查异步边界：Promise链、线程池、新开协程是上下文丢失的三大高发点，Node中未经过storage.run包装的回调、Java中MDC未复制到新线程、Python中未传递context的线程任务，都会让注入静默失效。修复后把该触发源或边界模式加进金丝雀用例，防止回归。

## 结语

上下文自动注入是观测体系里投入产出比最高的工程：一次封装，此后每条日志天然携带排障所需的全部维度。它也是后续追踪、指标标签的地基——同一套上下文被三种数据复用，体系才真正咬合成一体。
