# 告警分级与路由：严重度映射、值班表与升级策略

> 一句话摘要：本文定义P1到P4的严重度判定标准与响应时限，讲解告警到值班表的归属路由、按时间与未确认自动升级的机制，以及多团队协作场景的路由设计。

## 一、严重度分级：判定标准必须客观可裁

分级混乱的告警体系等于没有分级。各级的判定锚点是"影响面×紧迫性"。P1（紧急）：核心服务不可用或数据错误，用户正在受损，需立即处置（五分钟内响应、全员动员、必要时拉起应急指挥）。判据举例：主下单接口成功率跌破百分之九十、资金核算错误、数据泄露迹象。P2（严重）：部分用户或重要功能受损、性能严重劣化，三十分钟内响应。判据：某渠道支付失败率百分之二十、P95超阈值三倍、队列积压影响时效承诺。P3（一般）：潜在风险或轻度影响，当日或次日处理。判据：错误率抬升但仍达标、容量水位百分之八十、DLQ出现零星消息。P4（提示）：趋势与观察项，周会处理。判据：环比劣化、预留实例利用率偏低。两条纪律：判据写进告警注释，分级争议以"用户影响"为最终裁决而非"技术上看起来多严重"；分级与通知方式、响应SLA、升级链三件事在制度里绑定，防"全是P1"的通胀。

## 二、归属路由：告警找到正确的团队

路由解决"通知给谁"，核心是归属关系的唯一性。第一层按服务路由：每个服务有唯一owning team（服务目录是权威源，告警标签里的team必须与服务目录一致——目录失准是路由错乱的最大根源，季度对账）。第二层按组件分诊：一条服务告警内再按告警类型分流：基础设施类（限流、OOM、冷启动激增）路由到平台/SRE组，业务逻辑类（错误码、转化骤降）路由到业务开发组；分诊依据告警的alerttype标签，规则在路由配置中显式表达。第三层兜底路由：归属不明的告警进值班长（chief on-call）统一分诊，宁可一人辛苦不可全员轰炸。服务目录的数据结构：服务→团队→值班表→升级链，一处维护处处引用；服务下线、团队调整时同步更新，孤儿告警（目录中无归属）月度清零。

路由配置示例：

```yaml
routes:
  - match: { team: order, alerttype: infra }
    receiver: sre-oncall           # 基础设施类→平台值班
  - match: { team: order }
    receiver: order-oncall         # 其余→业务值班
  - match_re: { service: "pay-.*" }
    receiver: payment-oncall
  - receiver: chief-oncall         # 兜底：无匹配→值班长分诊
escalations:
  - receiver: order-oncall
    steps:
      - { after: 10m_unacked, to: order-backup }    # 未确认→备岗
      - { after: 20m_unacked, to: order-lead }      # 仍未确认→主管
      - { after: 30m_unacked, to: engineering-mgr } # 继续升级
```

## 三、升级策略与值班制度设计

升级解决"第一责任人没响应怎么办"。机制三段：未确认升级（P1十分钟、P2三十分钟无ack自动升级到备岗与主管）、持续未恢复升级（P1持续一小时升级到管理层并考虑启动应急预案）、跨团队升级（定位到根因在他队时，工单转派并保持联合响应，根因方接手计时）。值班制度的配套：轮换周期建议一周（太短交接疲劳、太长 burnout），手递手交接文档（当前进行中事件、已知风险、静默清单）；值班豁免（发布周、休假）；值班负载度量（每周人均P1/P2次数超阈值要扩编轮换池）。升级链上的每一级都必须是"真实会被电话叫醒的人"，电话号码过期是P1事故扩大的经典原因——联系方式季度验证。

## 四、多团队与外部依赖的路由

两种特殊场景。场景一多团队共同拥有的链路（下单=订单组+支付组+风控组）：SLO级告警（面向用户）发给"链路owner"（订单组）并抄送相关组，组件级告警各归各组；链路owner负责端到端协调，避免"三个组都说自己组件正常"的扯皮——SLO视角的owner制是解药。场景二外部依赖故障（第三方支付渠道挂了）：告警路由到业务组但标注"external-dep"标签，Runbook指引是"启动降级开关/公告"而非"修复对方"；外部依赖的告警单独统计，作为供应商评估证据（第44篇成本与质量联动）。

分级路由检查清单：

```text
[ ] P1-P4判据客观成文；注释带判据；绑定通知方式与响应SLA
[ ] 服务目录为路由唯一权威；team标签与目录一致；季度对账
[ ] 组件分诊规则显式化；兜底值班长；孤儿告警月度清零
[ ] 未确认升级(10/20/30分钟)、持续升级、跨团队转派计时
[ ] 值班轮换周制+交接文档+负载度量+联系方式季度验证
[ ] SLO告警归链路owner；外部依赖标注并走降级Runbook
```

## 五、轮值机制与知识传递

分级路由的执行质量最终取决于值班者的能力分布，轮值与知识传递是隐形基础设施。轮值设计：主值班与备值班成对轮换，两人错开交接（避免同时疲劳）；值班周期一周，值班前完成"值班检查单"（确认通知渠道可达、了解进行中事件、读过本周更新过的Runbook）。知识传递的三个仪式：交接会（十五分钟过遗留事件与风险）、月度故障案例分享（第36篇数据的活用）、值班互助通道（值班者遇到不会处置的情况可呼叫的二线知识组，降低"不敢值、瞎处置"）。度量的指标是值班胜任度：新人从入队到可独立值班的中位时长、值班期间的错误处置率，前者目标一个月内、后者通过影子期考核压到最低。

## 结语：

分级是告警的音量键，路由是告警的地址簿，升级是告警的保险丝。三者共同保证"对的事，以对的紧急度，找到对的人，并在无人应答时自动加码"——这是值班体系可靠的全部秘密。
