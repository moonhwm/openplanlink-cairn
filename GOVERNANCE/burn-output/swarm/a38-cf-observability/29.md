# Prometheus生态与云函数指标的对接：Pull与Push的取舍

> 一句话摘要：本文分析Prometheus拉取（Pull）模型与云函数短生命周期实例的根本矛盾，讲解Pushgateway、远程写入、OTLP桥接三种对接方案及其适用边界。

## 一、Pull模型与函数环境的根本矛盾

Prometheus的经典工作方式是周期性抓取（scrape）目标的/metrics端点：它假设目标长驻、地址可发现、指标在端点累积等待拉取。云函数把这三个假设全部击穿：实例按需创建、秒级销毁，Prometheus来不及发现更来不及抓取（服务发现在实例存活窗口内完成注册的概率渺茫）；实例销毁时未被抓走的计数就地蒸发；函数也不该为被抓取而开放HTTP端点（安全面与冷启动负担）。结论直接明了：原生Pull模式对接云函数不可行，必须走Push语义的变通。但Prometheus生态（查询语言、告警规则、Grafana面板）价值巨大，所以工程实践是"保留Prometheus生态、替换采集通道"。

## 二、三种对接方案对比

方案一Pushgateway：函数把指标推到常驻的网关暂存，Prometheus照常抓网关。这是官方给批处理/短任务的标准答案，但用在函数场景有三个坑：其一，Pushgateway的指标按job/instance标签分组，多实例函数推同名指标会互相覆盖，必须给每个函数实例造唯一instance标签——而唯一标签恰恰制造基数问题（第26篇），且实例消亡后其序列残留，需要TTL清理机制；其二，计数器的rate语义破坏：网关暂存的计数器在实例重启后回跳，rate出现负向毛刺；其三，网关单点且无高可用原生方案。适用边界：低频批处理函数（每天跑几次的ETL），给每个执行批次一个instance标签、执行完主动删除组，可勉强用好。方案二远程写入（Remote Write）：函数内SDK（如prometheus client的push模式或自封装）把指标样本经remote write协议直推Prometheus兼容存储（VictoriaMetrics/Thanos Receive/Mimir），完全绕开抓取。云函数的最佳主流选择：批处理与长驻接收端天然匹配、多写入者安全、时序库原生去重。代价是需要部署接收层与认证管理。方案三OTLP桥接：函数按OTLP导出到Collector，Collector用prometheus exporter暴露或直接remote write——与第16篇追踪接入共用一条管道，运维收敛。推荐组合：函数→OTLP→Collector→（remote write→VictoriaMetrics/Thanos；同时暴露Grafana）。

三种方案对比速查：

```text
方案            | 原理              | 适用                 | 主要风险
Pushgateway     | 函数推、Prom拉网关 | 低频批处理任务        | 覆盖/残留/基数/单点
Remote Write    | 函数直推时序库     | 在线服务函数(主流)    | 需建接收端与认证
OTLP+Collector  | 统一管道转发       | 全栈标准化(推荐)      | Collector运维成本
```

## 三、Remote Write方案的落地要点

落地清单五条。第一，SDK选择：优先OTel指标SDK配OTLP HTTP导出（与追踪同管道），或prometheus client配remote write exporter；两者都支持批量。第二，命名空间隔离：函数指标带resource属性（function/env），Collector侧转成指标标签；用Prom命名规范重组（如fn_前缀），避免与集群内其他指标冲突。第三，认证与网络：接收端启用令牌认证，凭据经密钥管理注入环境变量（第11篇纪律）；跨VPC走内网端点。第四，乱序与迟到：实例冻结后flush的样本可能乱序到达，选支持乱序写入的存储（VictoriaMetrics原生支持，Thanos需配置）；采样周期对齐到整分钟减少乱序窗口。第五，抓取语义的替代验证：原来靠up与scrape_duration监控采集健康，Push模式下改用heartbeat金丝雀指标（第25篇）与"序列新鲜度"告警（某指标超过两倍周期无新样本即告警）。

Remote Write最小配置示例（Collector侧）：

```yaml
# otel-collector-config.yaml 片段
receivers:
  otlp: { protocols: { http: { endpoint: "0.0.0.0:4318" } } }
processors:
  batch: { timeout: 10s }
  resource:
    attributes:
      - key: fn.name       # OTel资源属性转Prom标签
        action: upsert
exporters:
  prometheusremotewrite:
    endpoint: "https://metrics-recv.internal/api/v1/write"
    headers: { Authorization: "Bearer ${env:RW_TOKEN}" }   # 凭据走环境变量
service:
  pipelines:
    metrics:
      receivers: [otlp]
      processors: [batch, resource]
      exporters: [prometheusremotewrite]
```

## 四、混合环境的统一视图

现实中函数与容器/虚机服务长期共存，统一视图的组织：采集侧各走各的合适通道（容器Pull、函数Push），存储侧汇入同一时序库（Mimir/VictoriaMetrics多写），标签规范统一（service.name、env词表一致，第05篇契约跨采集通道生效）。跨通道对账：同一服务的函数侧计数与容器侧计数做总量核对，防止"一半指标丢在某个通道"而无人察觉——新鲜度告警按通道分别部署。

对接方案检查清单：

```text
[ ] 明确弃用原生Pull对接函数；按场景选Pushgateway/RemoteWrite/OTLP
[ ] 在线服务走RemoteWrite或OTLP管道；批处理可Pushgateway+TTL清理
[ ] 接收端认证走密钥管理；内网端点；支持乱序写入
[ ] up告警替代方案：heartbeat金丝雀+序列新鲜度告警
[ ] 命名空间与标签规范跨通道统一；多通道总量对账
```

## 五、联邦查询与多集群视图

多集群（多区域、多账号、多云）的Prometheus生态常用联邦（federation）或全局视图层组织。联邦的两层设计：各区域Prometheus保存本区域原始指标（区域排障快），全局层仅抓取聚合后的关键序列（各服务的RED汇总、全局额度类指标），注意联邦抓取的必须是聚合表达式导出的少量序列而非全量原始数据，否则全局层成为瓶颈。替代方案是 Thanos/Mimir 的全局查询：数据留在各集群对象存储，查询层跨集群下推执行——查询性能依赖时间分片与标签分片做裁剪。云函数指标的分布式上报与这套体系天然契合：函数推到区域接收端，区域Prometheus或对象存储沉淀，全局视图按服务聚合。设计原则始终是：原始数据就近、聚合数据上行、查询下推。

## 结语

Prometheus生态与云函数的联姻关键在于认清"抓取已死、推送当立"：用Remote Write或OTLP管道保住查询、告警、看板的整套生态资产，用金丝雀与新鲜度告警补上采集健康的盲区。通道可以异构，契约必须统一——这是混合观测架构的主心骨。
