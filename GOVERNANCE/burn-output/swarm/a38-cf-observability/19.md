# 采样策略：头部采样与尾部采样在Serverless中的取舍

> 一句话摘要：本文对比追踪采样的两大流派——头部采样（入口决定、省资源但盲抽）与尾部采样（出口决定、智能但复杂），给出云函数场景的混合采样方案与实现要点。

## 一、为什么必须采样以及采样的两难

追踪数据的价值密度不均：正常且快速的请求树千篇一律，慢请求与错误请求的树才是金子。全量采集高流量函数的代价包括：函数CPU与内存被序列化导出占用、网络与后端存储费用线性增长、查询噪音淹没重点。但采样过狠又会在故障时恰好错过现场。两难的核心是"决策时机的信息差"：在请求入口做采样决策时，你不知道它会不会出错（信息少）；在请求结束时决策信息完整（知道结果与耗时），但那时数据已经产生并占用了函数资源，省的只是后端与网络。头部采样在入口省一切，尾部采样在出口保重点，混合两者是实践主流。

## 二、头部采样：机制、配置与适用

头部采样在trace创建时掷骰子：按trace_id的确定性哈希（保证同一trace全链路一致采样决策，否则下游记录上游丢弃、树残缺）以比例p保留，采样标志随traceparent传播，全链路所有Span生产者服从同一决策。优点：实现简单、函数侧资源节省彻底（未采样的Span根本不生成）、决策一致性好。缺点：盲抽——采到的九成五是无聊的正常请求，故障小流量场景（如错误率百分之一）可能一个错误样本都没采到。配置经验：头部采样率按流量分层——核心低流量函数百分之一到百分之十足够出统计；超高流量函数千分之一；但要注意概率对长尾的影响：当天总调用量一千万、采样千分之一，也有一万个样本，分位数统计依然稳定，但"某次具体客户投诉的请求"大概率没有样本——这是头部采样的固有盲区，必须靠日志兜底（日志按第09篇错误优先保留）。

## 三、尾部采样：策略组合与实现位置

尾部采样在trace完整结束后按策略决定去留，可以做到"错误全留、慢请求全留、正常按小比例留"。典型策略组合：错误优先（任何Span为ERROR的trace保留百分之百）；慢请求优先（根Span耗时超P95阈值的trace保留）；新版本优先（灰度版本的trace提高保留率）；正常兜底（其余保留百分之一）。挑战是工程位置：纯函数侧实现有缺口——trace的末端Span可能在最后一个函数结束后才齐全，而函数实例随时销毁，函数内做尾部决策拿不到全链路信息。正确位置是Collector（或平台追踪后端）：函数全量导出（或经高比例头部预采样）到Collector，Collector按trace_id聚合完整树后执行尾部策略。这带来两个成本：一是函数到Collector的传输量变大（被预采样的部分），二是Collector需要聚合缓冲（trace_id键控窗口，典型三十秒到两分钟）。Serverless的现实折衷：函数侧做"保守头部采样"（如百分之二十五到百分之一百，兼顾资源）加Collector侧尾部精选（错误慢请求全留，正常降到千分之五），两层组合逼近"重点全量、正常省存"的理想。

Collector尾部采样配置示例（OTel Collector processor）：

```yaml
processors:
  tail_sampling:
    decision_wait: 30s            # 等待trace聚合完整
    num_traces: 100000            # 聚合窗口容量
    policies:
      - name: errors-all
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow-requests
        type: latency
        latency: { threshold_ms: 1500 }
      - name: new-version
        type: string_attribute
        string_attribute:
          key: service.version
          values: ["canary-.*"]
          enabled_regex_matching: true
      - name: baseline
        type: probabilistic
        probabilistic: { sampling_percentage: 0.5 }
```

## 四、采样的配套纪律与验证

采样体系要有四条纪律。第一，决策一致性：同一trace全链路同一决策，用确定性哈希而非各节点独立随机。第二，统计修正：按采样率看分布时记住样本是有偏的（错误被加权保留），做错误率统计用指标不用trace；trace只用于定性定位与结构分析。第三，白名单通道：支持"指定trace_id强制保留"的开关（如排障时从日志拿到trace_id后打开抓取），与按租户/用户的定向全采（大客户链路全量保留）。第四，采样率是配置不是代码：放配置中心，可按函数、按流量时段动态调整，大促前临时提高。

验证方法：注入已知比例的错误请求，核对后端错误trace留存率是否接近百分之百；注入正常请求核对留存率接近配置值；观察trace完整率（树没有中途断采的痕迹——若链路中某函数未服从同一决策会出现半棵树）。

采样策略检查清单：

```text
[ ] 两层结构：函数侧确定性头部预采样 + Collector尾部精选
[ ] 尾部策略：错误全留、慢于阈值全留、灰度版本加权、正常低兜底
[ ] 采样率集中配置、按函数/时段可调；大促预案就绪
[ ] 白名单：按trace_id/租户定向全采通道可用
[ ] 错误率等精确统计走指标；trace仅做定性结构分析
[ ] 季度验证：错误留存率≈100%、正常留存率≈配置值、无半树
```

## 五、采样与审计留痕的冲突处理

合规审计场景常要求"特定类型操作全量留痕"，这与采样体系天然冲突。解法是通道分离：审计事件不走追踪采样逻辑，作为独立事件流（audit命名空间）全量保留（第13篇的审计分流路由），追踪体系里的对应Span只是引用其trace_id用于跳转；这样审计的完整性不受采样策略影响，采样的灵活性也不被合规要求绑架。另一类冲突是排障时"想看的那条恰好没被采到"，除了白名单通道，还要给值班者一个仪式化的兜底：从日志确认该请求存在但无trace时，明确记录"该请求未入采样"，避免重复盲目检索浪费时间。

## 结语

采样本質是给追踪数据做价值排序：用头部采样控资源，用尾部采样保重点，用指标补统计，用白名单救个案。四件套到位，追踪系统既能扛住高流量的成本，又不会在故障来临时两手空空。
