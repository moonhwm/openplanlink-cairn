# 端到端可观测架构案例：电商下单链路的完整实践

> 一句话摘要：本文以电商下单链路（网关→订单函数→库存/支付/积分→队列→回调）为载体，串联前文全部专题，展示一个真实Serverless链路的可观测架构设计、数据流与排障实战。

## 一、链路背景与观测需求分析

案例链路：客户端→API网关→order-create函数（调库存服务、写订单库、发消息）→订单队列→pay-callback函数（验签、更新订单、通知积分服务）→下游业务方。观测需求按角色展开：值班团队要"下单成功率与P95的实时答案"；订单组要"错误按码分布、按租户分布"；支付组要"回调验签失败率、渠道对比"；管理层要"每单成本与SLO达成"；所有角色共享"一次投诉订单的完整故事还原"能力。架构设计因此覆盖五层数据面：结构化日志（订单域与支付域各配事件词表）、分布式追踪（同步段W3C传播+异步段消息信封传播，第17、18篇）、指标（服务级SLI+函数级RED+业务计数器）、SLO与告警（下单服务双SLI+燃烧率）、成本管道（按服务分账+单位经济学）。部署形态：平台原生采集日志与指标，OTel SDK负责追踪经Collector汇入自建后端，成本管道独立定时任务（第40篇）。

## 二、关键实现节点串讲

节点一网关：注入或透传traceparent（第17篇透传纪律）；网关层记录入口时延（不含函数执行的纯网关开销）。节点二order-create：入口包装器延续trace、绑定tenant_id上下文（第12篇）；业务Span覆盖库存检查、订单落库、消息发布（第22篇）；出口无论成败打invoke_done/invoke_error收尾日志；下单业务计数器orders_created_total{channel}上报（第25篇）。节点三订单队列：消息属性携带trace信封与born_at时间戳（第18篇）；queue_lag_ms指标消费侧测量。节点四pay-callback：从消息属性提取上下文，验签失败单独错误码INVALID_SIGNATURE计数；支付成功事件audit.payment_succeeded路由到审计日志库（第13篇合规分流）。节点五积分通知：异步扇出，link关联原始订单trace。全链路采样策略：函数侧头部采样百分之二十五，Collector尾部保错误与P95外慢请求（第19篇）；日志错误全保留、正常info采样百分之十（第09篇）。

架构数据流图（文本示意）：

```text
客户端 ──HTTP(traceparent)──> API网关 ──> order-create函数
   │透传trace                    │SERVER根Span+结构化日志
   │                             ├──CLIENT Span→库存服务
   │                             ├──CLIENT Span→订单DB
   │                             └──PRODUCER Span→订单队列(消息属性带trace+born_at)
   ▼                                        │
指标: RED+业务计数 ──> 指标库 ──> 看板/SLO   ▼(lag指标)
日志: stdout JSON ──> 日志服务(审计分流)   pay-callback函数
                                          │验签/更新/通知(Span+日志)
追踪: OTel→Collector(尾部采样)→追踪后端    └─> 积分服务(link关联)
成本: 用量+价目表→估算→成本库→单位经济学看板
告警: SLO燃烧率(P1/P2) | 应为零:限流/DLQ | 成本燃烧(第42篇)
```

## 三、排障实战：一次客诉的十分钟还原

周三14:20，客服转来客诉：租户t-2049反馈订单"转圈不付款"。值班工程师操作流水：第一步全局看板——下单服务成功率正常、无告警，排除全局故障；第二步日志检索tenant_id=t-2049近半小时——找到订单O-771233的invoke_done日志，total_ms四百一十正常，订单已创建；第三步按order_id查审计与业务事件——发现该订单无payment_succeeded事件，队列消费日志显示该消息三次投递均失败（错误码INVALID_SIGNATURE，attempt=3），消息已进DLQ；第四步跳转该消息trace_id打开追踪树——pay-callback的验签Span为ERROR，属性显示密钥版本v2，而发布记录显示当日13:50支付密钥轮换上线；第五步根因确认：新密钥在某区域未生效，回调验签用错版本。处置：DLQ重放工具带密钥版本参数重放（止血，订单完成），密钥配置修复（根治）。全程十一分钟，五个动作各用一层观测能力：看板定面、日志定点、事件定时、追踪定因、发布记录定责——这正是五层数据面协同的价值证明。

## 四、体系运行数据与迭代

该案例体系运行三个月的关键数据：MTTD从四十二分钟降至六分钟（SLO燃烧告警替代人肉发现）；MTTR中位数五十五分钟（Runbook覆盖全部P1/P2）；告警精准率百分之六十八（月度评审维持，第36篇）；观测成本占比百分之十八（采样与分层控制在健康区间）；每单成本下降百分之二十二（内存调优+取整治理，第43篇）。迭代方向：积分服务的追踪补全（当前是盲区，链路完整率百分之八十九）、DLQ自动重放的人工确认门（防错误消息重放放大）、租户维度的单位经济学看板开放给商务（第44篇场景三）。

案例架构检查清单：

```text
[ ] 五层数据面就位: 日志/追踪/指标/SLO告警/成本
[ ] 同步段traceparent透传; 异步段消息信封+born_at
[ ] 业务Span+业务计数器+审计事件分流三件套
[ ] 两级采样: 追踪25%头部+尾部保错误慢请求; 日志错误全留
[ ] 客诉还原SOP: 看板→日志→事件→追踪→变更记录五步
[ ] 月度复盘迭代: MTTD/MTTR/精准率/观测占比/单位成本
```

## 五、案例的迁移性与裁剪指南

把这套案例架构迁移到其他业务时按流量与复杂度裁剪：低流量场景（日调十万级）可裁掉两级采样（全量保留也不贵）、预聚合可简化为直查原始数据；高流量场景反而要加强采样与预聚合，并增加区域维度切片；强合规行业要扩审计通道与删除演练（第11、14篇）；异步比重高的业务要把第18篇的异步拼接与队列延迟测量做深。不变的骨架是五层：结构化日志、追踪串联、指标与SLO、分级告警带Runbook、成本管道——裁剪的是每层的深度而非层级本身。

## 结语

把四十余篇专题压进一条真实链路，答案浮出水面：可观测体系不是工具的堆叠，而是围绕"还原真相的速度"组织起来的数据工程。当任何一笔订单的命运都能在十分钟内被完整讲述，这套体系就通过了最好的验收。
