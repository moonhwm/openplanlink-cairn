# SLI/SLO/错误预算：Serverless场景的落地方法

> 一句话摘要：本文讲解SLI（服务等级指标）的选择、SLO（服务等级目标）的制定、错误预算的计算，以及如何在云函数架构下实现SLO驱动的监控与告警闭环。

## 一、从"监控指标"到"服务质量目标"的思维转变

传统监控思维盯着资源与技术指标：CPU多高、内存多少、QPS多大。这种思维的问题是无法回答"用户到底满不满意"——函数内存用了百分之八十，用户体验可能毫无影响；而错误率只要涨到百分之一，用户就开始骂人。SLO方法把视角换成用户可感知的质量：先定义SLI（用什么指标度量用户体验），再定SLO（这个指标要达到什么水平），最后推导错误预算（允许的失败额度）。错误预算是SLO方法的精髓：它把"稳定性"从模糊的追求变成可以花销的预算，预算内可以放心发版做实验，预算耗尽就必须冻结变更专心修稳定性。

对云函数而言，常见的SLI选择有三类。可用性类：成功请求数除以总请求数（注意要把平台限流、用户主动取消与系统故障区分开，只有系统责任的部分才计入失败）；延迟类：耗时低于某阈值（如八百毫秒）的请求占比，即"按时完成率"；正确性类：业务结果正确的比例，例如对账后发现的重试率、补偿率。SLO的制定要基于用户期望与历史数据：取过去三十天P95的实际表现，略加收紧作为目标，而不是拍脑袋定三个九。

## 二、SLO的制定流程与示例

制定流程分五步。第一步圈定服务边界：一个SLO对应一个用户可感知的服务（如"下单接口"），它背后可能是三个函数加两个托管服务，SLO度量的是端到端结果而非单个函数。第二步选择两到四个SLI，覆盖可用性与延迟，宁少勿多。第三步用滚动窗口数据评估现状，确定可达性。第四步写下SLO文档：指标定义、目标值、窗口（如三十天滚动）、排除项（计划内维护、用户参数错误）。第五步把SLO接入看板与告警（见第四节）。

一个云函数服务的SLO定义示例：

```yaml
service: order-api                  # 由 order-create-fn + pay-fn 组成
window: 30d_rolling
slo:
  - name: availability
    sli: sum(rate(success_invocations)) / sum(rate(total_invocations))
    target: 0.995                   # 30天内失败预算 0.5%
    exclude:
      - client_error_4xx
      - planned_maintenance_window
  - name: latency
    sli: ratio(invocations where duration_ms < 800)
    target: 0.99                    # 99%请求快于800ms
budget_policy:
  - budget_remaining < 25%: 仅允许修复类变更，发版需SRE会签
  - budget_remaining < 10%: 冻结非紧急变更
  - budget_burn_alert: 1小时烧掉>5%预算 → 页面级告警
```

这份定义的关键细节：排除项必须显式写明，否则用户传错参数造成的4XX会悄悄吃掉预算；预算策略要提前与业务方约定，否则耗尽时的"冻结发版"会变成扯皮。

## 三、错误预算的计算与燃烧率告警

三十天窗口的预算消耗速度本身就是信号。定义燃烧率（burn rate）＝实际错误消耗速度／允许的平均消耗速度。例如可用性SLO为99.5%，允许平均每天烧掉约0.0167%的预算；如果某小时错误率达到2%，燃烧率约为12倍，意味着按这个速度十小时就烧完全月预算。多窗口燃烧率告警是SLO体系的标准实践：同时计算"1小时窗口燃烧率超过14.4"与"5分钟窗口燃烧率超过14.4"（短窗口保证快速触发），或"6小时窗口超过6"且"1小时超过6"（长窗口减少误报）。这样告警直接对齐用户体验受损这一事实，而不是对齐某个技术阈值。

实现上，燃烧率可以用指标查询表达：错误率SLI的burn rate＝(1－实际成功率)／(1－目标)。云函数场景要注意异步链路的SLI统计延迟——队列积压导致的失败可能滞后暴露，必要时要为异步链路单独设定"积压消化时间"这类代理SLI。

## 四、SLO驱动的日常运转

SLO不是文档，而是运转机制。每日站会看预算剩余；每次事故复盘回答"消耗了多少预算"；每季度复核SLO目标是否该收紧（长期大幅超额完成说明目标定松了，浪费了迭代速度）或放松（长期完不成且影响交付）。发布决策引用预算状态。同时防止两个异化：一是把SLO当KPI硬压数字而非改进工具；二是SLI定义掺水（把系统故障归为用户错误）来自欺欺人。

SLO落地检查清单：

```text
[ ] 每个面向用户的服务有一页SLO文档（SLI定义+目标+窗口+排除项）
[ ] SLI数据来自端到端观测而非单函数指标
[ ] 错误预算剩余量在看板首页可见
[ ] 配置了多窗口燃烧率告警（快速+慢速两档）
[ ] 预算耗尽的变更冻结策略已获业务方书面确认
[ ] 事故复盘记录预算消耗并归因到具体环节
[ ] 每季度评审SLO达成情况并修订目标
```

## 五、SLO的团队沟通与反对意见处理

推行SLO时必然遇到几类反对意见，提前准备回应能减少阻力。其一"SLO是形式主义"——回应是把SLO与切身利益绑定：展示预算耗尽冻结发版如何替代过去的人为扯皮，用一次真实故障的预算消耗数据说明其决策价值。其二"定目标会背锅"——回应是明确SLO用于指导工程投资而非绩效考核，文档中显式声明这一原则，并从相对宽松的目标起步逐步收紧。其三"我们没有历史数据"——回应是先用平台原生指标做粗粒度SLI跑一个月，有数据后再正式定目标。落地建议从小处开始：选一个服务、两个SLI、九十天试点，季度末用数据说话再推广。

## 结语

SLI/SLO/错误预算是观测体系的"方向盘"：它决定哪些指标值得看、哪些告警值得发、哪些变更应该停。在云函数这种平台托管大量底层细节的环境里，用户视角的SLO比资源视角的监控更贴近本质。把预算思维建立起来，稳定与迭代速度就不再是对立口号，而是同一本账上的两笔开销。
