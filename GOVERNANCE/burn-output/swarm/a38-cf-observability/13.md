# 日志采集链路：从stdout到日志服务的管道设计

> 一句话摘要：本文解析云函数日志从进程标准输出到日志服务平台的三条采集链路（平台采集、SDK直写、扩展层Sidecar），比较其可靠性、延迟与成本，并给出管道的缓冲、批量与背压设计。

## 一、三条采集链路的形态与取舍

链路一：平台原生采集。函数把日志打到stdout/stderr，运行时把输出行交给平台日志子系统，平台统一投递到日志服务。优点是零依赖、零代码、与函数生命周期完全解耦，是默认首选；缺点是投递通常异步批量，秒级到分钟级延迟，且个别平台对超长行截断（常见16KB上限）、对结构化字段需要额外配置解析规则。链路二：SDK直写。函数内引入日志服务SDK，直接批量发送。优点是控制力强（自定义字段、Project路由、压缩）、延迟低；缺点是占用函数的执行时间片与内存，发送失败会堆积在实例内存，且初始化建连增加冷启动负担。链路三：扩展层/Sidecar。利用平台扩展机制（如Lambda Extensions、阿里云层+自定义运行时）在函数进程旁跑一个采集Agent，函数照常打stdout，Agent负责解析、缓冲、增强（如补地域标签）后投递。优点是业务零侵入且可执行高级处理；缺点是增加镜像与内存开销，配置复杂度上升。

选型经验：默认链路一，把结构化做在日志内容本身；有强定制需求（多目标投递、富化、敏感过滤前置）再上链路三；链路二只用于平台采集能力缺失的场景。任何情况下，业务代码只管"写标准stdout JSON"，不感知链路细节，这是可替换性的前提。

## 二、管道的核心问题：批量、缓冲、背压

采集管道要处理好三个问题。批量：逐条投递费用与延迟都不可接受，标准做法是攒批（如每1024条或每1秒先到者触发）加gzip压缩，压缩后网络与存储成本普遍降到三分之一以下。缓冲：投递目标故障时本地缓存重试。函数实例短命，内存缓冲随实例销毁而丢失，因此要接受"函数日志尽力而为"的现实——error级别日志若要求不丢，SDK直写模式需在返回前同步flush（代价是耗时），或接受平台链路的高可靠投递承诺并对其进行验证。背压：当日志产生速度超过投递速度，管道必须降级而不是拖垮函数：先丢弃debug/info（按采样降级），保error与warn；计数丢弃量并打指标log_dropped_total，让降级可见。

管道参考配置示例：

```yaml
pipeline:
  source:
    type: stdout            # 平台采集或扩展层读取
    multiline: false        # JSON单行原则下无需多行合并
  parse:
    type: json
    keep_raw_on_failure: true   # 解析失败保留原文并计数
  route:
    - name: errors
      condition: level in ["error","warn"]
      destination: logsvc/hot-log        # 保留90天
    - name: info_sampled
      condition: level == "info" AND sample(0.2)
      destination: logsvc/std-log        # 保留30天
    - name: audit
      condition: event startswith "audit."
      destination: logsvc/audit          # 保留400天，单独权限
  sink_common:
    batch: { max_items: 1024, max_bytes: 1048576, flush_interval_ms: 1000 }
    compression: gzip
    retry: { max_attempts: 5, backoff_ms: [100, 400, 1600, 6400, 25600] }
    on_drop: count_to_metric(log_dropped_total) then drop_lowest_level_first
```

## 三、投递语义与端到端验证

要明确管道的投递语义并验证。三个必须回答的问题：日志能丢吗（at-most-once）、必须到吗（at-least-once）、恰好一次吗（exactly-once，日志场景一般不承诺）。error路径的丢失容忍度要与业务约定。端到端验证方法：金丝雀探针——定时函数每分钟打一条带序号的heartbeat日志，观测侧校验序号连续性，缺口即为端到端丢失，同时得到真实端到端延迟分布（发出到可查询）。这个探针便宜且能持续守护管道健康。

另一个被低估的问题是可查询延迟：日志"入库"与"可查询"之间常有索引构建延迟。排障SOP里应写明各链路的预期延迟（平台链路典型十秒内、批量高峰期可能分钟级），避免排障者误判"日志没打"而乱查。

## 四、多目标投递与合规分流

管道的路由能力支撑合规与成本分账：审计类事件（audit.*）单独路由到高保留、强权限的日志库；含个人信息字段的日志路由到有访问审批的库；按环境分流（prod与staging不同Project，权限策略不同）；按租户大客户单独落地以满足合同要求。路由规则与第08篇字段规范绑定——路由条件依赖规范字段（level、event、env），再次说明数据契约是管道设计的前提。

采集链路设计检查清单：

```text
[ ] 默认平台stdout采集；定制需求走扩展层Agent；业务不感知链路
[ ] 攒批+压缩默认开启；背压时先丢info保error并计数
[ ] 明确各级别投递语义并写入SOP；error丢失容忍度获业务确认
[ ] 金丝雀heartbeat探针监控端到端丢失与延迟
[ ] 解析失败保留原文+计数，不静默丢弃
[ ] 审计/含个人信息/普通日志分库路由，保留期与权限差异化
[ ] 单行16KB内的体积纪律（配合截断标记）
```

## 五、多区域与多账号的管道拓扑

规模化后采集管道要面对多区域与多账号拓扑：跨区域拉日志既慢又贵，正确形态是区域就近汇聚——每个区域部署独立采集端与缓冲，区域内投递到就近日志服务入口，再由日志服务本身的跨区同步或中心查询层做聚合视图；账号隔离场景（不同业务线独立云账号）则在各账号内部完成采集投递，权限与合规边界天然清晰，中心侧只做查询联邦而非数据搬运。同时要为管道本身建立元数据监控：每条管道的吞吐、延迟、丢弃计数、重试队列深度集中上一块看板，管道故障（凭据过期、配额打满、端点变更）是观测数据静默断流的最常见原因，没有元数据监控的管道等于没有管道。

## 结语

采集链路是观测数据的第一公里：它决定了数据会不会丢、多快可查、多少钱。设计要点是把复杂度留在管道（批量、缓冲、路由），把简单性留给函数（只管打标准JSON）。用探针持续验证端到端语义，管道才能被信任。
