# 告警体系设计：从指标异常到on-call的完整闭环

> 一句话摘要：本文讲解告警体系的完整闭环设计——从信号选择、规则定义、分级路由、通知触达、值班响应到复盘改进，以及每个环节的质量标准与常见失败模式。

## 一、告警闭环的六个环节

一条有价值的告警走完六站。第一站信号：哪个指标或日志事件值得变成告警？判据是"触发后会有人采取动作"，无人行动的告警是噪音。第二站规则：什么条件触发？持续多久？多窗口确认？规则质量决定误报率。第三站分级：P1（用户受损需立即处理）到P4（观察项）的严重度映射，分级决定通知方式与响应时限。第四站路由：通知给谁？按服务归属路由到值班表，按时间升级（十分钟未确认升级到主管）。第五站响应：值班者确认、按Runbook处置、记录时间线。第六站复盘：告警是否及时、准确？MTTD/MTTR多少？规则要不要调？六站缺一环，体系就漏气：最常见的断点是第六站——没有复盘，规则永不进化，噪音永远在。

## 二、信号选择：什么才配成为告警

告警候选的优先级清单（从高到低）：一，"应为零"的硬信号——限流计数、DLQ投递、OOM、超时被杀、安全告警，非零即报，无条件；二，SLO燃烧率——用户体验受损的直接度量（第06篇）；三，容量水位——并发逼近限额、队列积压消化时间超阈值，给扩容留提前量；四，关键业务量异常——下单量环比骤降（可能上游故障或被刷）；五，依赖健康——下游服务错误率、证书到期、配额余量。明确不告警的：CPU等资源利用率的正常波动（无用户影响）、已收敛到工单的慢性问题、可以从看板发现的信息类变化。经验法则：宁缺毋滥，每条告警上线前写一句"触发时值班者将做什么"，写不出来的不上线。

## 三、规则设计与分级路由的工程规范

规则设计五要素：条件（阈值或表达式）、持续时间（抗毛刺，典型三到五分钟）、窗口与步长（第27篇）、静默条件（维护窗口、发布窗口）、恢复通知（是否发resolved）。分级标准：P1用户直接受损（核心服务不可用、数据错误）；P2部分用户或性能显著受损；P3潜在风险（水位偏高、错误率轻微抬升）；P4信息（趋势提示）。路由矩阵：P1电话加短信加IM并五分钟内响应；P2 IM强提醒加值班群三十分钟；P3工单次日处理；P4周报汇总。升级链：P1十五分钟未确认自动升级下一级值班。每条告警的消息体必须包含：服务名与影响面、关键数字、看板链接、Runbook链接——尤其Runbook链接，它是"收到即可行动"的前提（第37篇）。

告警定义文件示例（YAML，规则即代码入仓）：

```yaml
alerts:
  - name: order-api-error-burn
    expr: burn_rate_1h(slo=order-api-availability) > 14.4
      and burn_rate_5m(slo=order-api-availability) > 14.4
    for: 2m
    severity: P1
    labels: { team: order, service: order-api }
    annotations:
      summary: "下单可用性SLO快速燃烧(1h/5m双窗口)"
      impact: "用户下单失败率升高，预计影响X%请求"
      runbook: "https://wiki/runbooks/order-api-error-burn"
      dashboard: "https://grafana/d/order-api"
  - name: fn-throttled
    expr: sum(rate(fn_throttles_total[5m])) by (function) > 0
    for: 1m
    severity: P1
    annotations: { runbook: ".../throttle", impact: "请求被并发限额拒绝" }
  - name: dlq-delivered
    expr: increase(fn_dlq_total[5m]) > 0
    severity: P2
```

## 四、常见失败模式与治理指标

告警体系的四种经典病。病一告警风暴：一次故障触发五十条衍生告警（每个函数各报一条），值班者 drowned——解药是聚合（同因告警合并为事件）与抑制（根因告警抑制衍生告警，第33篇）。病二狼来了：误报率高导致全员静默——解药是每条告警的误报复盘与规则下线机制。病三孤儿告警：负责人离职、服务下线但告警还活着——解药是告警与服务的归属关系定期对账。病四只报不修：告警确认后无人处置——解药是把确认到处置的时限写进值班制度并纳入考核。度量体系健康的三指标：告警量/周（人均每天超过两条即过载）、精准率（真实故障占比，目标过半）、MTTD与MTTR趋势。月度告警评审会必开：过一遍Top噪音源，当场决定调阈值、降级或下线。

## 五、告警即代码与变更管理

告警配置应与代码同等待遇。落地形态：全部告警规则、路由、抑制、静默策略以声明式文件（YAML）存于版本库，评审合入后由流水线发布到告警系统，界面只读或禁改；每次告警变更走评审——阈值调整要看历史回放数据、新增要看误报预估、删除要注明理由。好处三重：变更有审计（谁在何时为什么改了阈值）、可回滚（坏变更一键回退）、可环境同步（测试与生产规则同源仅参数不同）。配套禁止事项：生产环境直接在管理界面手改规则（漂移之源）、把告警配置写死在某人笔记本的脚本里。告警即代码是第36篇质量循环的基础设施——没有它，月度评审改规则要靠记忆和截图。

## 六、从零建设的最小可行告警集

给从零起步的团队一份最小可行告警集（两周内可建成的骨架）：第一层"应为零"四件套——限流计数、DLQ投递、OOM、超时被杀，全部无条件即报P1/P2；第二层SLO双档燃烧率——先给最重要的一到两个服务配上（可用性与延迟各一）；第三层容量水位——账户级并发使用率超八成预警；第四层管道存活——日志与指标的heartbeat金丝雀。这十来条规则覆盖了大部分真实故障的首次发现，且全部低误报。等这套骨架运转一个月、值班习惯养成后，再按第32篇方法逐步扩充——先让告警被信任，再让告警变全面。

## 结语

告警体系的本质是一台"从数据到行动"的转换机器，它的产品是值班者的注意力。信号严选、规则克制、分级明确、Runbook随行、复盘闭环——五件事到位，告警才能从"讨厌的噪音源"变成"值得信任的哨兵"。后续各篇分别展开降噪、分级、SLO告警等专题细节。
