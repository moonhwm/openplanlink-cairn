# 上下文传播：跨函数、跨队列、跨HTTP的trace链路衔接

> 一句话摘要：本文系统讲解追踪上下文（trace_id、采样标志、业务Baggage）在HTTP调用、消息队列、事件总线、定时任务等边界上的传播机制、信封设计与断链修复方法。

## 一、上下文传播要解决什么问题

追踪树之所以能跨进程生长，靠的是上下文在每一次边界穿越时被显式搬运：调用方把trace_id、父Span标识、采样决策编码进载体（HTTP头、消息属性），被调方解出来延续trace。如果搬运缺失，下游函数只能新开trace，链路断成两截——这是实践中最常见的追踪失败模式，表现为"点开一个慢请求的追踪树，到某个函数就断了"。传播要搬三样东西：标识（trace_id、span_id），采样决策（是否采样的标志位，决定下游是否也记录），以及可选的业务Baggage（如tenant_id、灰度标记，让下游日志与Span自动带维度）。标准编码格式是W3C Trace Context的traceparent头，格式为"版本- trace_id - parent_id - 采样标志"，各语言OTel库的Propagator自动完成编解码。

## 二、四种边界的传播设计

边界一：HTTP/SDK同步调用。最成熟：调用方OTel自动（或手动）在出站请求注入traceparent头；被调方入口提取。要点是确认所用HTTP客户端的自动埋点已启用；自研网关或认证层必须原样透传该头（网关重写请求头是隐蔽的断链源），内部服务链路上的负载均衡器同样要放行该头。边界二：消息队列。生产者把上下文注入消息属性（message attributes/user properties），而非消息体——属性随消息元数据走、消费者可零解析读取。消费者拿到消息后，从属性提取上下文，创建的SERVER Span通过parent指向生产者的PRODUCER Span（或用link关联，取决于队列语义是否允许严格父子）。要点：队列本身不搬属性之外的自定义头，所以一切要放进属性；消息可能被重试多次消费，每次消费的Span都关联同一生产上下文。边界三：事件总线/发布订阅。事件信封（envelope）设计时必须预留trace字段：事件头部包含traceparent与Baggage，发布方SDK自动填充，订阅方触发函数入口提取。自建事件规范时把trace字段写进schema必填项，从制度上防断链。边界四：定时任务与编排。调度器（定时触发器、工作流引擎）生成新trace_id并作为整个批次的根；若批次处理的是此前产生的业务对象，用link关联原始trace。

消息属性传播示例（Python伪码）：

```python
# 生产者：发送前注入
from opentelemetry.propagate import inject

def publish_order(order):
    carrier = {}
    inject(carrier)                                  # 写入traceparent+baggage
    carrier["tenant_id"] = current_tenant()          # 业务维度一并搬运
    mq.send(queue="orders", body=order,
            attributes=carrier)                      # 属性而非body

# 消费者：收到后提取
from opentelemetry.propagate import extract
from opentelemetry.trace import Link

def on_message(msg):
    parent_ctx = extract(msg.attributes)             # 延续上游trace
    links = []
    if msg.attributes.get("origin_trace_id"):        # 批处理/扇出来源
        links = [Link(trace_id_from(msg.attributes["origin_trace_id"]))]
    with tracer.start_as_current_span(
            "order-consumer.mq", kind=CONSUMER,
            context=parent_ctx, links=links) as span:
        span.set_attribute("tenant_id", msg.attributes.get("tenant_id"))
        process(msg.body)
```

## 三、Baggage的设计与克制

Baggage允许把业务维度（tenant_id、ab_group、is_vip）随上下文带到整条链路，下游日志与Span自动获得这些维度，跨服务的"按租户过滤追踪"因此可行。但Baggage要克制：每跳都会被序列化传输，体积膨胀直接增加请求开销；且它随调用链跨信任边界流动，敏感信息（用户手机号、内部标识）禁止放入。规范做法：Baggage仅放三到五个低基数字符串键值，总量限制在一KB内；下游只读不扩展；跨出本系统（调用第三方）前剥离Baggage。

## 四、断链的系统性修复

断链治理分三步。第一步发现：追踪后端统计"孤儿根Span比例"（本应作为子Span却成为新根的函数）与"链路完整率"（入口到末端全通的比例）；按函数排名找断点，通常集中在网关、队列、第三方回调三类位置。第二步修复：对照本篇四边界清单逐项检查（头透传、属性注入、信封字段）；修复后用端到端金丝雀请求验证树深。第三步防回归：把传播字段写入各触发事件的schema必填校验；CI里对每种触发源跑一次链路测试（发请求断言追踪树包含全部预期函数）；网关变更评审时检查traceparent透传规则。

上下文传播检查清单：

```text
[ ] HTTP边界：出站自动注入traceparent；网关/负载均衡透传该头
[ ] 队列边界：上下文进消息属性；消费者提取延续parent
[ ] 事件总线：事件信封schema必含trace字段；SDK自动填充/提取
[ ] 定时/编排：调度器生成根trace；处理存量对象用link关联来源
[ ] Baggage≤5个低基数键、≤1KB；出系统前剥离；敏感信息禁入
[ ] 孤儿根Span比例、链路完整率两项指标上看板
[ ] 每种触发源的链路金丝雀测试入CI
```

## 六、传播链路的安全考量

上下文传播穿过信任边界时要考虑安全面。三个要点：第一，头注入要防伪造——外部客户端可以随意发送traceparent头，入口侧应校验格式合法性（版本、长度、十六进制），非法值丢弃并生成新trace，防止恶意构造的超长头或注入攻击进入内部系统；第二，跨出系统边界（调用第三方、回调外部）时剥离Baggage（前文已述）同时评估是否保留traceparent——保留可串联外部故障排查，但暴露trace_id本身无敏感风险，通常保留；第三，消息属性里传播的上下文要参与消息签名计算或至少做完整性校验，防止被篡改的trace字段污染追踪数据。这些细节在实现提取规则时统一封装，不留给每个函数自行判断。

## 结语

上下文传播是追踪体系的血管系统：标识、采样决策、业务维度沿调用链流动，函数之间才能拼成完整的执行故事。把四类边界的注入/提取规则固化为SDK默认行为与schema校验，断链就从"常态事故"变为"可监控的异常指标"。
