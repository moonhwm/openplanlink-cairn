# 敏感信息脱敏与日志安全治理

> 一句话摘要：本文梳理云函数日志中敏感数据的来源与风险，给出分类分级、出口统一脱敏、正则与令牌化技术方案以及日志安全治理的完整清单。

## 一、日志泄露的独特风险与常见泄露源

云函数日志的泄露风险比传统应用更高，原因有三：一是日志集中存储且全员可查，一旦敏感信息进入日志库，等于把它复制到了一个权限更宽、保留更久的系统；二是函数常作为集成枢纽，事件里天然携带上游凭证（API网关的token、webhook签名、第三方回调报文），整包打印事件是最高频的泄露动作；三是调试压力下的临时打日志常被遗忘，debug级别的请求体全量输出上线后变成定时炸弹。常见泄露源包括：请求头里的Authorization与Cookie、事件体里的手机号身份证银行卡、数据库连接串与内网地址、第三方API密钥、用户密码与验证码、以及内部系统的签名密钥。

泄露的代价不只是隐私合规处罚，还有直接的攻击面暴露：连接串与密钥进日志等于把钥匙挂在门上；内网拓扑暴露帮助攻击者横向移动。因此日志安全必须作为观测体系的一级需求，而非事后补丁。

## 二、分类分级：脱敏策略的前提

先把数据分级，才能定策略。公开级：可任意输出，如订单状态枚举、区域代码。内部级：限内部可见，如内部服务名、错误消息，可入日志但打标。敏感级：必须变形后入日志，如手机号、邮箱、IP、订单号（按业务定）、用户ID。机密级：禁止以任何形式入日志，如密码、token、密钥、验证码、生物特征，出现即阻断并告警。分级的判断标准是"泄露后的最大伤害"而非"看起来像不像敏感"。

对敏感级字段执行变形规则：手机号保留前三后四（138****5678）；邮箱保留首字符与域名（z***@example.com）；身份证保留前六后四（出生日期段隐藏）；IP保留前两段；卡号只留后四位；姓名保留姓。变形必须在日志出口统一执行，而不是每个调用点各自 remembering——人工遵守必然遗漏。

## 三、技术方案：出口统一脱敏的实现

脱敏的正确位置是日志库的序列化层，所有日志经过同一过滤器。实现分三步：字段路径规则（按规范里声明的敏感字段路径精确脱敏，如data.token直接置为[REDACTED]，这是主规则、零误伤）；值模式规则（兜底正则扫描字符串值，匹配手机号、身份证、邮箱、Bearer令牌、以sk_/pk_/AK开头的密钥形状时变形，防止未知路径漏网）；阻断规则（机密级模式命中时丢弃该字段并上报安全事件计数）。性能上正则只扫字符串值且限制长度上限（超过4KB的值直接截断标记），避免大报文扫描拖慢调用。

Node.js出口脱敏过滤器示例：

```javascript
const RULES = [
  { path: /^data\.(token|password|secret)$/i, censor: () => '[REDACTED]' },
  { path: /phone/,  fn: v => String(v).replace(/(\d{3})\d{4}(\d{4})/, '$1****$2') },
  { path: /id_card/,fn: v => String(v).replace(/(\d{6})\d{8}(\w{4})/, '$1********$2') },
];
const PATTERN = /(Bearer\s+[\w.-]+|sk-[A-Za-z0-9]{16,}|1[3-9]\d{9})/g;

function sanitize(value, keyPath = '') {
  if (Array.isArray(value)) return value.map(v => sanitize(v, keyPath + '[]'));
  if (value && typeof value === 'object') {
    const out = {};
    for (const [k, v] of Object.entries(value)) out[k] = sanitize(v, `${keyPath}.${k}`);
    return out;
  }
  if (typeof value === 'string') {
    const rule = RULES.find(r => r.path.test(keyPath));
    if (rule) return rule.censor ? rule.censor(value) : rule.fn(value);
    return value.length > 4096 ? value.slice(0, 4096) + '...[truncated]'
                               : value.replace(PATTERN, '[MASKED]');
  }
  return value;
}
// 注册为pino transport或序列化前钩子：line => JSON.stringify(sanitize(JSON.parse(line)))
```

配套治理动作：日志库内置规则集，业务声明新敏感字段走PR更新规则；日志服务端再开一道服务侧加密与按环境隔离的索引（生产日志库权限最小化）；合规要求全量日志加密存储与传输（TLS），访问审计留痕；定期用"金丝雀"手法验证——在测试环境故意打印含敏感形状的数据，确认出口被变形，未变形即为漏洞。

## 四、治理清单与运营

日志安全治理清单：

```text
[ ] 数据分级文档成文（公开/内部/敏感/机密四档+字段清单）
[ ] 脱敏在日志库序列化层统一执行，路径规则+模式兜底+机密阻断
[ ] 禁打完整请求头/事件体；Authorization/Cookie默认整字段丢弃
[ ] 密钥永不入日志：连接串、AK/SK、签名密钥进环境或密钥管理服务
[ ] 生产日志库访问权限最小化+审计；测试环境禁用生产数据
[ ] 每季度金丝雀演练：投递敏感形状数据验证脱敏命中
[ ] 脱敏命中率与阻断计数上监控，异常飙升触发审查
[ ] 日志保留与销毁策略符合合规（如个人信息留存上限）
```

## 五、日志安全的权限与加密配套

脱敏之外，日志安全的完整拼图还包括访问控制与加密。访问控制遵循最小权限：生产日志库默认只读权限按团队划分，跨团队查询需审批或脱敏视图（敏感字段在视图层再遮蔽一层）；导出与下载操作全部留审计日志，"谁在什么时候看了哪些日志"本身可追溯。加密分三层：传输层全链路TLS（函数到采集端、采集端到存储）；存储侧服务端加密，密钥由密钥管理服务托管并定期轮换；特定合规场景（如涉及个人金融信息）对高敏字段做应用层字段级加密，即使库被拖、脱敏规则被绕过，字段本体仍是密文。最后是删除权的技术兑现：用户依规请求删除个人信息时，冷热各层的删除任务要能按tenant_id或user_id字段定位并物理删除，这在日志分区设计时就要预留可定位性，事后补救几乎不可能。

## 结语

脱敏的本质是把安全要求工程化到数据出口：规则集中、执行自动、验证常态。做到"打印无敏感、命中即变形、机密即阻断"三条，日志库才能放心地开放查询能力，观测体系才不会成为最大的泄露面。
