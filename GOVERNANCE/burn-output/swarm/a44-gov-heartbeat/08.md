# 08. 拉模式探活：中心侧主动探测的设计与实现要点

> 摘要：本文讨论拉模式探活的适用边界、探针类型选择、探测调度与并发控制、结果解释的陷阱，以及探测器的扩展性与自保护设计，并附探测任务调度伪代码。

## 一、拉模式的架构定位

拉模式指检测方主动向被监控对象发起探测请求，依据响应的有无与质量判定存活。它与推模式互补：推模式证明"节点还能发声"，拉模式证明"节点还能被服务"。当被监控对象是黑盒——第三方依赖、数据库、无改造权限的遗留系统——推模式无从谈起，拉模式是唯一选择；当怀疑节点假活时，拉模式提供了独立的第二证据源；当对象数量庞大且多数时间健康时，拉模式可以按需加密探测频率而不惊动节点侧。拉模式的代价是检测方要维护探测连接与调度器，探测语义必须与对象协议匹配，且探测流量本身构成对被监控者的负载。

## 二、探针类型与语义选择

探针按深度分层。传输层探针只验证端口可连接，实现最廉价，但TCP三次握手成功仅代表内核协议栈存活，进程死锁时依然畅通，故只适合作为最外层的粗筛。应用层探针发送协议合法的请求并校验响应，例如HTTP健康端点、数据库执行轻量查询，能暴露应用假死。语义探针更进一步，校验响应内容的正确性，例如健康端点返回的依赖检查结果、只读查询返回的时间戳新鲜度，可发现"能响应但内部已坏"的深层次故障。深度与成本成正比，标准策略是金字塔组合：常态用浅探针高频覆盖，异常嫌疑时逐级加深，确认故障前必须通过语义探针。

选择探针时必须审查其副作用：健康查询不能触发昂贵操作，不能写数据，不能占用锁，不能干扰业务连接池。曾经常见的错误是健康检查端点内部依次探测所有下游依赖，结果下游一抖动，全部实例被判定不健康，健康检查自身成为故障放大器。原则是：健康端点只报告本进程状态，依赖状态由专门的依赖面板表达。

## 三、探测调度与并发控制

```python
# 探测调度器骨架
class ProbeScheduler:
    def __init__(self, registry):
        self.tasks = registry            # [(目标, 探针, 基础间隔)]
    def next_delay(self, target):
        # 健康时按基础间隔；疑似异常时指数加密：间隔/2，下限1s
        if target.consecutive_fail >= 1:
            return max(1, target.base_interval / (2 ** min(target.consecutive_fail, 4)))
        return target.base_interval
    def run(self):
        while True:
            t = pick_due_task()
            t.timeout = quantile_p99(t.rt_hist) * 4 + 200ms   # 自适应超时
            submit(pool_limited, t)                            # 全局并发受控
```

调度设计有三个关键决策。第一，全局并发上限：探测并发必须封顶，防止探测风暴压垮被监控对象或耗尽自身连接资源，超出上限的任务排队延后。第二，自适应超时：固定超时在对象性能漂移后要么过紧要么过松，依据历史响应时间分位数动态计算超时，是拉模式减少误报的核心手段。第三，异常加密探测：首次失败不立即判定，先缩短间隔连续复核，k次失败才升级结论，这既压误报又加快真故障的确认速度。调度去同步同样不可省——上千目标的探测起始时刻必须错开，否则每周期出现一次探测尖峰，对象与探测器双方面临周期性压力。

## 四、结果解释的陷阱

拉模式的误判多源于结果解释的粗糙。陷阱一：把慢当死。响应时间恶化但仍在超时内，是退化信号不是失联信号，应进入不同的事件通道。陷阱二：单路径代表全网。从单一探测点看到的失联可能只是本探测点的网络问题，关键对象必须多探测点交叉，或至少在判定失联前从第二探测点复核。陷阱三：忽略部分失败。十个健康检查项挂了三个，整体返回失败，语义被压缩，应保留分项结果供告警分级。陷阱四：连接复用污染。长连接池中某连接被服务端半关闭，探测恰好复用该连接即误判，探测请求失败后应重建连接重试一次再下结论。陷阱五：探测路径与业务路径不一致，探测走的VIP、业务走的直连，探测结果无法代表业务体验。

## 五、探测器自身的扩展与自保护

探测器水平扩展后，同一目标被多个探测器重复探测，需要一致性哈希或协调服务划分目标归属，并处理探测器故障后的目标接管。自保护方面：探测器应对自身的探测成功率、超时率、队列深度建立监控，当全局超时率骤升时优先怀疑自身或网络，而非批量判定目标失联——这是熔断思想在探测体系的应用。极端情况下应启用"探测静默"：当失败率超过阈值，暂停产生新失联事件，只维持已确认事件的追踪，待环境恢复后恢复探测，避免探测体系在自身故障时制造大规模误报。

## 六、上线检查清单

- 探针深度金字塔化，确认失联必须有应用层以上证据；
- 健康端点无副作用、不探测下游依赖、不占用业务锁；
- 全局探测并发封顶，目标起始时刻去同步；
- 超时依据响应时间分位数自适应，定期用分位数回归校准；
- 首败加密复核，k次失败才升级，判定前第二探测点交叉；
- 探测器自身超时率熔断与探测静默机制就绪；
- 探测路径与业务路径一致性经过核对并在文档中登记。
