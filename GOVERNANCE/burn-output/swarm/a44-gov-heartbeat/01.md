# 01. 分布式心跳体系总体架构与设计目标

> 摘要：本文给出分布式心跳体系的总体参考架构，将存活检测、间隔告警、双轨时基、看门狗四个子系统纳入统一框架，并阐明其设计目标与质量属性权衡。

## 一、心跳体系在分布式系统中的定位

任何分布式系统都必须回答一个基本问题：某个节点现在还活着吗。共识协议需要它判断领导者是否失联，调度器需要它决定是否重新拉起实例，存储系统需要它触发副本补齐，运维体系需要它产生告警。心跳体系就是为回答这个问题而存在的基础设施。它由四条主线构成：存活检测负责采集与判定节点的生死状态；间隔告警负责在心跳缺失或间隔异常时以恰当的节奏通知人与系统；双轨时基负责在墙钟不可信时提供单调可比的时间基准；看门狗负责在检测到停滞后执行强制恢复动作。四者并非孤立功能，而是一条从"感知—判定—通知—处置"的完整链路，任何一环薄弱都会让故障检测形同虚设。

设计心跳体系前必须先明确故障假设。经典的崩溃-停止模型假设节点要么正常工作要么彻底停止，检测只需关注"多久没有消息"；崩溃-恢复模型引入了重启后的状态恢复问题；慢节点模型则要求区分"慢"与"死"；若系统面临拜占庭行为，心跳内容本身也需要认证。故障模型决定了后续所有参数与机制的复杂度上限。

## 二、总体参考架构：五层分解

一个可工程化的心跳体系可以分解为五层。第一层是采集层，包括节点侧的心跳发送器与中心侧的主动探针，负责产生原始的存活信号；第二层是传输层，承载心跳报文，需考虑多路径、压缩、批量与优先级；第三层是判定层，将原始信号转换为二元或连续的置信度结论，典型实现包括固定阈值检测器、Phi Accrual检测器与租约管理器；第四层是决策层，消费判定结果并执行告警分级、故障切换、隔离与自愈；第五层是可观测层，度量心跳延迟分布、误报率、漏报率与时基健康度，反哺参数调优。分层的目的在于让每层可以独立演进：判定算法从固定阈值升级为自适应检测器时，采集与传输无需改动。

```text
┌─────────────────────────────────────────────┐
│ 可观测层：延迟分布 / 误报率 / 时基健康度       │
├─────────────────────────────────────────────┤
│ 决策层：告警分级 / 故障切换 / 隔离 / 自愈      │
├─────────────────────────────────────────────┤
│ 判定层：阈值检测 / Phi Accrual / 租约管理     │
├─────────────────────────────────────────────┤
│ 传输层：多路径 / 批量压缩 / 优先级队列         │
├─────────────────────────────────────────────┤
│ 采集层：心跳发送器(推) / 主动探针(拉)          │
└─────────────────────────────────────────────┘
```

## 三、设计目标与质量属性

心跳体系的核心质量属性可归纳为六项。及时性：从节点失效到被判定失效的时间要短，通常以检测时间分布的P99衡量。准确性：误报率与漏报率要低，误报引发无谓切换甚至脑裂，漏报延长故障时间。低开销：心跳流量与判定计算不能挤占业务资源，大规模集群中这是硬约束。可扩展：节点数从百到十万级时体系应平滑伸缩。可运维：参数含义清晰、可在线调整、行为可预测。可测试：故障场景可通过注入复现，验收标准明确。

这些目标之间存在张力。缩短检测时间最直接的手段是提高心跳频率，但开销随之线性增长；降低误报要求放宽阈值，检测时间必然拉长。工程上不存在同时最优的解，只能依据业务代价函数选取帕累托点。例如金融交易集群宁可承受较高误报也要快速切换，而批处理集群则相反。因此总体架构必须把"参数可配置、策略可插拔"作为一等公民，而不是把常数写死在代码里。

## 四、参考配置清单与反模式

落地时的基线检查清单如下：

- 明确故障模型并写入设计文档，标注是否需要处理慢节点与拜占庭行为；
- 心跳路径与业务路径物理或逻辑隔离，避免业务拥塞导致心跳饿死；
- 判定阈值不使用单一固定值，至少支持按节点分组配置；
- 告警分级与升级策略在体系上线前定义完毕，而非事后补写；
- 时基方案明确墙钟与单调钟的分工及失效切换逻辑；
- 看门狗动作有明确的爆炸半径评估与回滚手段；
- 所有关键参数有对应的监控指标与调优记录。

常见反模式同样值得警惕：把TCP连接不断开等同于进程健康，实际上进程可能死锁而连接仍在；心跳只覆盖部分关键线程，导致假活；告警直接打到个人手机而无聚合，一个月内即产生告警疲劳；看门狗超时后仅记录日志不动作，形同虚设；以及在虚拟机迁移、垃圾回收停顿等常见抖动源未建模的情况下追求过于激进的检测时间。总体架构阶段识别并规避这些反模式，成本远低于上线后返工。

## 五、演进路线建议

心跳体系不必一次建成全部能力，推荐三阶段演进：第一阶段只做存活检测加固定阈值告警，覆盖最常见的崩溃类故障，快速产生价值；第二阶段引入自适应检测器与告警分级治理，把误报率压到业务可接受水平，同时建立双轨时基，为后续精度提升铺路；第三阶段补齐看门狗自动处置与故障注入回归体系，使整个链路从感知到自愈形成闭环。每一阶段的验收都应以误报率、检测延迟与故障演练通过率三项指标为准绳，避免功能堆叠而质量原地踏步。
