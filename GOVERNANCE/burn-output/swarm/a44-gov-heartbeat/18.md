# 18. 容器与Serverless环境中的存活探测：Liveness、Readiness与Startup探针

> 摘要：本文聚焦云原生环境的存活探测：Kubernetes三类探针的语义分工与参数设计、容器环境下心跳的特殊性（进程号变化、优雅终止、资源竞争）、Serverless冷启动与缩容到零的检测策略，并给出探针配置清单。

## 一、容器环境改变了什么

容器化把"节点"的粒度从物理机细化到进程组，存活检测的对象从上百台机器变成数万个Pod，检测语义也随之细化。Kubernetes给出的答案是探针三分法：存活探针决定容器是否需要重启，就绪探针决定Pod是否接入Service端点，启动探针保护慢启动应用免遭前两者的误杀。三分法的本质是把"健康"拆成三个正交问题——进程要不要重启、流量要不要导入、启动是否完成。三者使用相同的探测手段（HTTP、TCP、Exec）却绑定完全不同的处置动作，这正是把检测与处置解耦思想在编排层的标准化落地。配置失误的高发区恰恰在语义混淆：把就绪语义的检查（依赖可用性）写进存活探针，依赖一抖动就触发容器重启风暴，放大故障。

## 二、三类探针的参数设计

存活探针的设计原则是"只看自身"：检查项限定于进程自身状态（线程活性、内部队列、死锁检测端点），绝不在探针里探测下游依赖。参数上，periodSeconds应大于探测目标P99响应时间的数倍，failureThreshold至少三到五次——容器重启是重处置，必须容忍多次连续失败；timeoutSeconds要覆盖慢响应，过紧会让GC停顿被误判。就绪探针的原则是"诚实反映服务能力"：依赖不可用、过载保护触发、预热未完成都应摘除端点，参数可比存活探针敏感，因为摘流量的代价远小于重启。启动探针的原则是"覆盖最坏启动时间"：initialDelaySeconds的固定等待在启动时长方差大时形同虚设，启动探针以低频长超时轮询直到成功，期间禁用存活与就绪检查，是慢启动应用的标配。

```yaml
# 三探针配置示例（慢启动有状态服务）
livenessProbe:
  httpGet: { path: /healthz/self, port: 8080 }   # 只查自身活性
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 5                             # 50s持续失败才重启
readinessProbe:
  httpGet: { path: /readyz, port: 8080 }          # 含依赖与过载状态
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3
startupProbe:
  httpGet: { path: /startupz, port: 8080 }
  periodSeconds: 5
  failureThreshold: 60                            # 最长容忍300s启动
```

## 三、容器特有的陷阱

容器环境引入了一批传统环境不存在的陷阱。其一，优雅终止竞态：Pod收到终止信号后进入宽限期，期间探针仍在执行，若宽限期内探针失败触发重启逻辑，会与终止流程打架；终止路径应与探针路径联动，收到终止信号即主动失败就绪探针摘流量。其二，进程模型变化：容器内一号进程僵死而探针由边车进程应答，形成假活——探针执行体与被检进程必须同生命周期，Exec探针在容器命名空间内执行天然满足，HTTP探针则要求端点由业务进程本身而非代理应答。其三，资源竞争误报：节点资源超卖时，CPU节流让所有容器的探针响应集体变慢，形成批量误判，需要节点级的资源压力信号参与归并（回到第14篇的拓扑归并思想，此处归并键是宿主机）。其四，重启循环放大：存活探针失败重启后，应用启动更慢（缓存冷、回放慢），再次失败再重启，形成雪崩；重启退避策略与启动探针是解药。

## 四、心跳与探针的协同

有自建心跳体系的团队在容器化后常见两套检测并存：编排层探针与自建心跳。协同原则是分层分工：探针负责进程级生命周期（重启、摘流量），心跳体系负责跨进程的体系级判定（主从切换、分区仲裁、全局视图）。两者通过状态互通避免冲突——心跳体系的失联判定应参考探针事件流（容器刚重启过，失联结论要扣除重启窗口），编排层的重启动作应通知心跳体系（epoch变化联动，第13篇）。落地做法：容器启动时向心跳体系注册并携带Pod标识与重启计数，心跳报文的epoch与容器重启计数对齐，检测端据此自动豁免计划内重启期的失联判定。

## 五、Serverless的检测特殊性

Serverless把检测问题再度变形。缩容到零意味着"没有常驻对象可探活"，检测语义从"活着吗"变为"下次调用能拉起吗"，对应手段是周期性的冷启动演练探测与平台层的调用失败率监控。冷启动延迟本身成为存活指标：函数实例拉起超时分布恶化即是平台级异常信号。实例内检测则退化为单次执行的活性——超时即杀，无需探针。对常驻的扩展实例，健康检查由平台执行，粒度与参数不可定制，自建体系只能从调用侧观测（成功率、延迟基线）做外部存活画像。Serverless的存活检测设计要点是把"可调用性"作为一等指标：预热池深度、冷启动P99、并发扩容成功率，这三项取代了传统心跳的位置。

## 六、落地检查清单

- 存活探针只查自身，依赖检查只出现在就绪探针；
- 慢启动应用必配启动探针，不依赖initialDelaySeconds硬猜；
- failureThreshold与periodSeconds的乘积大于已知最长GC与卡顿；
- 终止流程主动失败就绪探针，宽限期内不触发存活重启路径；
- 探针端点由业务进程自身应答，禁止边车或代理代答形成假活；
- 宿主机资源压力参与批量探针失败归并，避免超卖误判风暴；
- 容器重启计数与心跳epoch联动，重启窗口不产生失联误报；
- Serverless场景以可调用性指标（冷启动、扩容成功率）替代心跳基线。
