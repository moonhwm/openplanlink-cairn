# 02. 心跳语义辨析：存活、活性与活跃度的形式化定义

> 摘要：本文对"存活""活性""活跃度"三个常被混用的概念给出可操作的形式化定义，说明它们分别对应故障检测、活性检测与负载画像三类不同问题，并给出判定器的伪代码实现。

## 一、为什么必须区分三种语义

工程讨论中"节点活着"是一个危险的模糊表述。一个进程可能TCP连接正常、能响应ping，但内部工作线程全部死锁；也可能一切正常，只是当前无事可做而没有业务流量；还可能仍在处理请求，但速率已跌落到正常值的百分之一。如果心跳体系只维护一个布尔值"活着/死了"，以上三种状态都会被错误归类，导致该告警的不告警、不该切换的乱切换。把语义拆开，是设计精准检测的前提。

三个概念的分工如下：存活回答"这个执行体是否还在按约定发出生命信号"，它关注的是控制面的存在性；活性回答"这个执行体是否还能在限定时间内完成关键动作"，它关注的是执行面的有效性；活跃度回答"这个执行体当前的工作强度处于什么水平"，它关注的是数据面的量化画像。三者依次递进，存活是必要条件，活性能捕获假活，活跃度则服务于容量与异常检测。

## 二、形式化定义与判定窗口

设节点在时刻序列上发出心跳事件流。存活可形式化为：在长度为W_alive的滑动窗口内收到的心跳数不少于k个，否则判定为失联。k取1即退化为普通的超时判定，k大于1可以过滤单次丢包。活性可形式化为：对一组被标记为关键的路径，最近一次成功完成的时间距今不超过D_deadline，即带截止时间的进展证明。活跃度则定义为窗口内心跳附带的工作计数（如处理请求数、写入字节数）构成的速率序列，正常时构成基线区间，显著偏离时产生事件。

三种定义对应三种失效：失联失效（进程崩溃、断网、被冻结）、活性失效（死锁、活锁、资源耗尽、无限循环）与退化失效（能跑但很慢或吞吐骤降）。值得注意的是活性失效无法靠任何心跳本身发现——死锁的线程完全可以由另一个专门的喂狗线程继续发心跳。因此活性必须由"进展证据"来证明，而非由"信号存在"来证明。

```text
# 三种判定器的伪代码
判定存活(节点n):
    if 当前时间 - n.最近心跳时刻 > W_alive: 返回 失联
    else: 返回 存活

判定活性(节点n):
    for 路径p in n.关键路径集合:
        if 当前时间 - p.最近进展时间戳 > p.截止时间:
            记录活性违规(p); 返回 假活
    返回 健康

判定活跃度(节点n):
    r = n.窗口内工作计数 / 窗口长度
    if r < n.基线下分位 * 0.5: 产生低活跃事件
    if r > n.基线上分位 * 3.0: 产生高活跃事件
    return r
```

## 三、语义到机制的映射

存活语义的实现载体是心跳发送器加超时检测器，心跳报文应当极其轻量，可以在独立的低优先级线程中发送，且发送间隔与网络重传策略解耦。活性语义的实现载体是心跳携带的进展字段：每个关键线程或关键循环定期把自己维护的计数器交给心跳模块，心跳模块只转发"最新值+时间戳"，检测端比较连续多个心跳中计数是否前进。看门狗线程若发现某线程计数长期不动，即在该线程的判定上标记停滞。活跃度语义的实现载体是心跳附带的结构化指标，要求指标定义版本化，检测端按版本解释，避免口径漂移导致误判。

## 四、落地检查清单

- 为每个被监控对象明确标注它需要哪几种语义：数据库实例通常三者都要，缓存节点可只要存活与活跃度；
- 心跳报文中为存活、活性、活跃度保留独立字段，禁止复用同一计数字段表达两种语义；
- 关键路径清单由业务方维护并评审，至少覆盖请求入口、持久化、复制同步三类路径；
- 活性截止时间必须大于该路径P99处理时间的数倍，并随性能基线定期校准；
- 活跃度基线按时间分段建立，识别昼夜与周周期，避免用恒定阈值误判；
- 三种判定结果分别接入不同的告警级别：失联通常critical，假活critical且需人工介入，活跃度异常多为warning供分析；
- 为每种语义编写可注入的故障用例：杀进程测存活、持有锁睡眠测活性、限流注入测活跃度。

语义清晰的另一个收益是可测试性。当判定器输出"假活"而非笼统的"异常"时，值班人员可以直接按预案处置，自动化系统也可以据此选择重启还是隔离。语义混用则是许多事故的根源：曾有系统以"线程仍在发心跳"证明"事务处理正常"，最终死锁持续数小时无人发现。定义先行、机制随后，是心跳体系避免此类陷阱的第一道闸门。

## 五、语义漂移的防护

语义定义还会随系统演进发生漂移，需要专门防护。典型场景包括：某线程从关键路径降级为普通路径但心跳字段未同步调整，导致活性判定覆盖范围悄然缩小；指标定义升级后新旧字段并存，检测端读错字段产生系统性偏差；跨团队复用心跳报文时对字段含义理解不一致。防护手段有三：字段含义与所属语义在接口描述文件中强制标注并由评审把关；语义变更视为不兼容变更，必须走版本号递增与双读迁移；定期用故障注入回验每种语义的判定器是否仍然对准原始定义，把语义正确性纳入回归范围。
