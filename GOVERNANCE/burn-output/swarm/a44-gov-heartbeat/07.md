# 07. 推模式心跳：节点主动上报的设计与实现要点

> 摘要：本文阐述推模式心跳的架构要素，包括发送器设计、报文结构、停顿防护、发送侧背压与多目标上报，并给出实现骨架代码与上线检查清单。

## 一、推模式的架构定位

推模式指由被监控节点周期性主动向检测方发送心跳报文。它是心跳体系最常见的形态，优势明显：状态变化由节点自己声明，语义最直接；网络只需单向可达，穿越NAT与防火墙的约束最小；检测方无需维护探测连接池，扩展压力小。劣势同样清晰：心跳质量取决于节点侧实现，进程假活时心跳可能照发不误；检测方被动等待，无法按需主动核实；大量节点同时发送需要接收侧具备聚合能力。因此推模式的设计重点落在发送器本身的工程质量上——一个实现糟糕的发送器会让整个体系的检测能力大打折扣。

## 二、发送器设计要点

发送器应当是独立的轻量执行体，与业务逻辑彻底解耦。核心要点有五。第一，独立线程或协程：心跳发送不能复用业务线程池，否则业务拥塞时心跳先被饿死，产生大面积误报。第二，非阻塞与超时控制：发送调用必须设置明确的超时，避免一次网络故障让发送器卡死在同步调用上。第三，失败不重试过度：单个心跳丢失在检测端有k连丢容忍，发送侧对失败最多快速重试一次，把可靠性交给周期性本身。第四，发送与采集分离：心跳内容（各线程计数、资源摘要）由采集模块填充，发送器只负责打包与投递，两者通过无锁队列或最新值快照交接。第五，时钟来源统一：报文时间戳一律取单调时钟序列号加墙钟双字段，检测端以序号判进展、以墙钟做参考。

## 三、报文结构设计

```json
{
  "node_id": "node-a42.region1",
  "epoch": 1731024,          // 启动代次号，每次重启递增
  "seq": 9918273,            // 单调递增心跳序号
  "monotonic_ms": 88273412,  // 节点本地单调时钟
  "wall_ms": 1759300800123,  // 节点本地墙钟，仅供参考
  "progress": {              // 关键路径进展证据
    "ingest": 8123456,
    "replicate": 8123100,
    "flush": 8122900
  },
  "load": {"cpu": 0.42, "mem_rss_mb": 1024, "q_depth": 7},
  "schema_ver": 3
}
```

字段设计的原则是：进展证据字段必须独立于发送器自身——由被监督的关键线程更新计数，看门狗只转发，这样计数停滞即暴露假活；epoch字段解决重启后的身份连续性，检测端见epoch跳变即重置该节点历史；schema_ver用于报文演进，检测端按版本解释避免口径错乱。报文体积应控制在几百字节内，大规模集群中这是带宽与解析成本的硬指标。

## 四、多目标上报与背压

单检测点是推模式的可用性瓶颈，标准解法是心跳扇出：同时向两到三个检测点发送，内容一致。扇出带来一致性问题——多个检测点对同一节点可能得出不同结论，收敛责任交给判定层的quorum汇聚，发送侧只保证尽力投递。背压设计同样重要：当检测方过载返回拒绝时，发送器应保持本地节奏不变、只丢弃应答等待，绝不因对端慢而加大发送频率；检测方过载的告警责任在检测方自身，不应转嫁给被监控节点。

```python
# 发送器骨架
class HeartbeatSender:
    def __init__(self, node, targets, interval):
        self.node, self.targets, self.interval = node, targets, interval
        self.seq = load_persisted_seq()          # 重启后延续，不归零
    def run(self):
        while True:
            pkt = self.build_packet()            # 快照读取各线程最新计数
            for t in self.targets:
                try:
                    t.send(pkt, timeout=self.interval/4)
                except Timeout:
                    pass                          # 交给下一周期，不阻塞
            self.seq += 1
            sleep_until_next_tick(self.interval)  # 固定节拍，抖动后立即对齐
```

## 五、发送侧常见故障与防护

发送侧的高频问题包括：心跳线程优先级过低被业务线程饿死——应为心跳线程设置较高调度优先级并纳入活性自检；系统休眠或容器冻结后恢复，出现心跳突发的补发风暴——发送器按节拍对齐，恢复后只发当前状态不回溯补发；本机DNS解析卡住导致发送阻塞——目标地址缓存并异步解析；以及发送器与业务进程分离部署时，业务死了心跳进程还活着——两者必须同生命周期管理，心跳进程应反向监督业务进程，构成互锁。

## 六、上线检查清单

- 心跳线程独立且高优先级，业务线程池打满时心跳节拍不变；
- 每报文含epoch、seq、单调时钟三要素，重启后epoch跳变可被检测端识别；
- 关键路径进展计数由被监督线程自报，发送器不代填；
- 至少双检测点扇出，单检测点故障不产生检测盲区；
- 发送超时小于间隔的四分之一，失败不阻塞下一节拍；
- 系统冻结恢复后无补发风暴，节拍立即重新对齐；
- 报文大小、发送速率纳入本机自监控，异常时本地告警。

## 七、发送器的验证方法

发送器上线前必须经过三类验证。静态验证：代码评审确认发送路径上不存在锁竞争点、无阻塞系统调用、无未设超时的网络请求。动态验证：在预发环境注入CPU饱和、磁盘卡顿、网络丢包三组压力，观察心跳节拍的漂移幅度，要求在业务资源耗尽时心跳间隔仍稳定在设计值的一个较小邻域内。故障注入验证：模拟系统冻结与恢复，确认无补发风暴；模拟检测点全部不可达，确认发送器只积压有限报文而不内存膨胀。三类验证的结论应形成基线记录，作为后续回归的对照。此外建议设置发送器自证机制：报文中的序号连续性由检测端反向校验，序号回跳或突增都会触发对发送器实现缺陷的排查，这类缺陷往往只在特定重启路径下暴露，靠常规测试难以发现。
