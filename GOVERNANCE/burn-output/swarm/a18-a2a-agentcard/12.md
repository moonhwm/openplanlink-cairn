# 12｜发现层互操作清单：客户端实现基线

## 一、为什么需要一份实现基线

前 11 篇拆解了 AgentCard 的字段与发现机制，本篇把它们收拢为一份可执行的客户端实现基线。互操作与安全在发现层的落地形态相同：一套确定性的处理流水线。没有基线时，各实现自行发挥——有的跳过结构校验、有的把验签失败当警告、有的允许 HTTP 回退——任何一处随意都可能成为生态中的最短板，攻击者只需找到最弱的客户端即可完成投毒。

## 二、基线流水线（十步）

```text
1. 定位   ：由带外登记的域名构造 well-known URL，禁止由卡片内容递归发现
2. 传输   ：强制 HTTPS + 证书链校验 + 主机名匹配，禁止降级重定向
3. 获取   ：设置超时与重试上限，记录响应头（缓存策略、签名头）
4. 解析   ：严格 JSON 解析（拒重复键、拒尾随逗号、拒 NaN/Infinity）
5. 结构   ：Schema 校验（必填、类型、枚举、URL 格式）
6. 签名   ：JWS 验签（算法白名单、JWKS 取钥、JCS 规范化）——失败即硬失败
7. 语义   ：协议版本协商、认证方案策略比对、模态求交
8. 指纹   ：对规范化卡片计算指纹，与历史比对（首遇记录、变更告警、回滚检测）
9. 隔离   ：卡片文本进入上下文前做不可信标注与注入扫描
10. 审计  ：以上每步产出结构化日志，供事后追溯与度量
```

## 三、每步的失败处理矩阵

流水线的强度取决于失败处理。矩阵要点：第 2 步证书失败 → 硬失败并安全告警（可能是中间人）；第 4 步解析失败 → 硬失败（畸形 JSON 本身可疑）；第 5 步结构失败 → 硬失败并记录具体字段（供反馈提供方）；第 6 步验签失败 → 硬失败 + 触发投毒事件流程 + 冻结该主体缓存；第 7 步语义不匹配 → 中止本次协作但不算安全事件；第 8 步指纹变化 → 按"内容变更"分级告警（url/security 变更最高级）；第 9 步扫描命中 → 降级为"仅人工审阅后使用"。核心纪律：任何与安全相关的失败都不得被降格为"继续使用但打日志"。

## 四、基线的测试化

基线应转化为测试用例集：对每一步构造正例与攻击样例（畸形 JSON、篡改签名、降级重定向、注入文本、回滚卡片），在 CI 中验证客户端行为符合矩阵。互操作层面，用一组参考卡片（含边界形态：空 skills、多接口、全部开关开启）验证不崩溃、不误拒。这份用例集本身也应纳入版本管理，作为客户端的安全回归资产。

## 五、要点清单

- 发现层基线 = 十步流水线 + 失败处理矩阵 + 测试用例集三件套；
- 最短板原则：生态安全取决于最弱实现，基线用于拉齐下限；
- 安全类失败一律硬失败，禁止降格处理；
- 指纹与审计贯穿始终，为投毒追溯提供证据链；
- 本篇是能力发现分支的收束，下一篇进入投毒攻击面总览。
