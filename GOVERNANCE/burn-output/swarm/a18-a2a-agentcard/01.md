# 01｜AgentCard 概述与 A2A 协议中的定位

## 一、问题背景：多智能体互操作的"名片"缺口

随着智能体（Agent）从单体走向协作网络，一个现实问题浮现：两个从未交互过的智能体，如何知道对方是谁、能做什么、支持哪些通信方式与安全机制？在传统 Web 中，这个问题由服务描述文档（如 WSDL、OpenAPI）与域名信任体系解决；而在智能体生态中，能力描述不仅是接口清单，还包含技能语义、输入输出模态、认证方式等 richer 的元数据。若缺乏统一的能力描述标准，每个框架都要为每个对端定制适配层，协作成本随组合数爆炸。

A2A（Agent2Agent）协议正是为解决这一互操作问题而设计：由 Google 于 2025 年 4 月发起，同年 6 月捐给 Linux 基金会治理，目标是为不共享内部记忆与工具的独立智能体提供标准通信协议。AgentCard 是 A2A 体系中的第一块拼图——一张机器可读的"智能体名片"，承载能力发现所需的全部声明。客户端在与任何 A2A 服务端通信之前，第一步通常就是获取并解析这张卡片，据此决定是否信任、如何调用。

## 二、AgentCard 是什么：一株声明式 JSON 文档

AgentCard 本质是一份公开的 JSON 文档，标准发布路径为服务端根域名的 well-known 位置（`/.well-known/agent-card.json`，早期草案使用 `agent.json`）。它同时服务于两类读者：机器（客户端智能体的发现与协商逻辑）与人（开发者浏览能力目录）。一份最小可用的卡片包含身份元数据（名称、描述、版本）、服务端点（url）、能力声明（capabilities）、默认输入输出模态与技能列表（skills）。

```json
{
  "name": "research-assistant",
  "description": "提供文献检索与摘要生成的研究助理智能体",
  "url": "https://agents.example.com/a2a/v1",
  "version": "1.2.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false,
    "stateTransitionHistory": true
  },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain", "application/json"],
  "skills": [
    {
      "id": "literature_search",
      "name": "文献检索",
      "description": "按关键词与时间窗检索学术文献并返回结构化结果",
      "tags": ["search", "academic"]
    }
  ]
}
```

需要强调：AgentCard 是声明而非证明。卡片声称具备的能力未必真实存在，声称的安全机制未必真正启用。这一"声明—事实"落差正是本系列后续讨论签名与投毒防护的根本动机：在敌意环境下，卡片的每一个字段都应被视为不可信输入。

## 三、在 A2A 通信生命周期中的位置

AgentCard 处于 A2A 交互链路的最前端，其完整性直接决定后续所有环节的安全性。典型生命周期如下：

- **发现阶段**：客户端按 well-known 路径拉取卡片，或在目录/注册中心检索卡片集合；
- **校验阶段**：检查协议版本兼容性、传输方式、认证方案，并（在增强安全模式下）执行签名验证与指纹比对；
- **协商阶段**：依据 capabilities 与模态声明选择调用形态（流式、推送、普通请求—响应）；
- **调用阶段**：向卡片声明的 url 发送 JSON-RPC 风格的请求（如 `message/send`、`message/stream`）；
- **治理阶段**：卡片变更被监控、缓存被刷新、旧版本被归档。

由此可见，AgentCard 是所有后续信任决策的根输入：若卡片在发现阶段被篡改（例如技能描述被注入恶意指令、url 被替换为攻击者端点），客户端将"合规地"执行一条被污染的协作链路。这也是为什么本系列将"能力发现、JWS/JCS 验签、卡片投毒防护"作为一条完整主线而非三个孤立话题。

## 四、要点清单

- AgentCard 是 A2A 协议中机器可读的能力发现文档，发布于 well-known 路径；
- 它是声明式元数据，不构成对能力真实性与诚实性的证明；
- 生命周期位置在最前端，其完整性是全链路安全的前置条件；
- 核心字段覆盖身份、端点、能力、模态、技能、安全方案六大类；
- 任何把卡片字段当可信输入直接消费的实现，都天然暴露在投毒面之下；
- 后续文档将逐层展开：字段语义（02-12）、投毒面分析（13-20）、JWS 验签（21-32）、JCS 规范化（33-40）、纵深防护与运营（41-48）。
