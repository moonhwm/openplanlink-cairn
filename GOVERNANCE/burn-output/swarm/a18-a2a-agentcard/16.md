# 16｜投毒向量三：securitySchemes 降级与认证混淆

## 一、降级攻击的三种形态

第一种，**方案移除式**：真卡片 `security: [{ "oauth2": ["a2a:invoke"] }]`，被改为 `security: [{}]` 或空数组——客户端按"无需认证"处理，直接裸调，服务端若未强制校验则攻击者达成未授权调用；即便服务端拒绝，客户端也已暴露了"会按卡片行事"的行为模式。第二种，**弱方案追加式**：在"或"数组里追加 `apiKey` 备选，诱导客户端改用长期静态密钥。第三种，**端点替换式**：保留 oauth2 方案名但替换 `tokenUrl`，客户端向伪造端点提交 client_id/client_secret 完成泄露。

## 二、scope 混淆与越权诱导

除方案级降级，还有 scope 级混淆：真卡片 scope 要求 `a2a:invoke`，被改为列出 `a2a:admin`，或诱导客户端以更大 scope 申请令牌"以防万一"。持有超配 scope 的令牌一旦泄露，横向危害扩大。反向变体是把必需 scope 从声明中删去——客户端申请的令牌权限不足，服务端返回 403，用户在排障压力下可能手动提权，形成社工链路。防御：客户端 scope 申请一律以"最小任务需求"本地计算，卡片 scope 列表仅作参考上限；403 排障流程禁止"直接放大 scope"的捷径。

## 三、防御实现要点

```python
POLICY = {
  "allowed_schemes": {"oauth2", "http+bearer"},   # 本地允许集
  "forbidden_schemes": {"apiKey", "basic"},        # 显式禁止集
  "authz_servers": {"https://auth.example.com"},   # 带外登记
}

def check_security(card):
    schemes = card.get("securitySchemes", {})
    for req in card.get("security", []):
        for name in req:
            s = schemes[name]
            if s["type"] not in POLICY["allowed_schemes"]:
                return REJECT("scheme not allowed by local policy")
            if s["type"] == "oauth2":
                for flow in s["flows"].values():
                    if origin(flow.get("tokenUrl")) not in POLICY["authz_servers"]:
                        return REJECT("tokenUrl not in registered authz servers")
    return OK
```

三条实现纪律：本地策略优先于卡片声明（卡片只能"提供选项"，不能"命令放松"）；tokenUrl 等认证端点与带外登记强绑定；`security` 数组中任何元素变更（尤其新增方案）触发与端点变更同级的最告警。

## 四、与签名体系的衔接

security 字段的降级攻击在整卡 JWS 验签下直接失效（任何改写破坏签名），因此签名是第一道也是最硬的一道闸。但两类残余风险仍在：其一，提供方自身配置失误（真实地发布了弱配置卡片），签名不能纠正"签了名的错误"，需要策略层兜底；其二，L4 场景（密钥泄露后的重签），依赖变更告警与带外登记比对。这再次说明：签名防外部篡改，策略防内部失误，二者缺一不可。

## 五、要点清单

- 降级三形态：方案移除、弱方案追加、认证端点替换；
- scope 混淆双向设防：既防超配申请，也防"排障提权"社工捷径；
- 本地策略优先、认证端点带外登记、变更最高告警三条纪律；
- 签名防外部篡改，策略防签名过的失误，互补不互替。
