# 04｜capabilities 块：调用形态的布尔开关

## 一、三个开关的语义

`capabilities` 对象只含三个布尔字段，却决定了客户端与智能体交互的全部"形态学"：`streaming` 为 true 时，客户端可使用 `message/stream` 以 SSE（Server-Sent Events）获得增量输出；`pushNotifications` 为 true 时，客户端可为长任务注册 webhook，在任务完成或状态变更时接收异步回调；`stateTransitionHistory` 为 true 时，客户端可查询任务状态流转历史（`tasks/get` 附加历史），用于审计与断点续作。三者默认缺省视为 false，这一保守默认是合理的：宁可少声明能力，不可虚报能力。

```json
{
  "capabilities": {
    "streaming": true,
    "pushNotifications": true,
    "stateTransitionHistory": false
  }
}
```

## 二、开关与真实行为的一致性校验

卡片声明与运行时行为的一致性是信任的试金石。常见的不一致有两类：虚报（声明 true 但实现不支持，客户端调用 `message/stream` 得到 404 或退化响应）与漏报（实际支持但不声明）。前者属于能力欺诈，会导致客户端流程中断；后者只是体验损失。安全审计建议实现"能力探针"：在正式协作前的预检阶段，用无副作用的调用（如一次空任务的状态查询）验证关键开关的真实性，将探针结果与卡片声明比对，不一致即降低信任评分并记录证据。

`pushNotifications` 的验证尤其重要，因为它牵出回调注册面：客户端会把一个 webhook URL 交给服务端。若卡片伪造该开关为 true，攻击者端点可在收到注册请求后回放伪造通知，诱导客户端提前消费"任务完成"状态。注册回调时应要求服务端先证明身份（验签回调负载，或校验一次性注册令牌），再接受后续通知。

## 三、开关被篡改的危害链分析

设想攻击者将真卡片的 `pushNotifications` 从 false 改为 true，`streaming` 从 true 改为 false。客户端行为将发生两处偏移：改用轮询而非流式（体验与效率受损，且轮询接口的鉴权路径可能较弱）；尝试注册 webhook 并泄露回调地址（信息泄露）。再设想 `stateTransitionHistory` 被改为 true：客户端会拉取并展示"历史"，若攻击者端点伪造历史记录，可能误导客户端对任务进度的判断，甚至在下游决策中引入污染。三个开关虽小，但每一个都连接一条真实的数据流，篡改开关等于重定向数据流。

## 四、要点清单

- 三个布尔开关对应流式、推送、历史三条数据通道，缺省按 false 理解；
- 声明与行为不一致分虚报与漏报，虚报应触发信任降级；
- 预检探针可在正式协作前低成本验证开关真实性；
- `pushNotifications` 牵出 webhook 注册面，回调负载必须可验证（签名或一次性令牌）；
- 开关篡改的重定向效果证明：小字段的完整性同样依赖整卡验签；
- `capabilities` 必须整体纳入被签载荷，任何子字段变更都使签名失效。
