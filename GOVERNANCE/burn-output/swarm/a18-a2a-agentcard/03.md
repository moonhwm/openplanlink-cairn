# 03｜卡片版本与协议版本协商

## 一、两个"版本"的区分

AgentCard 体系中存在两个容易混淆的版本概念：`version` 描述卡片内容自身的版本（提供方每修改一次卡片就应当递增），`protocolVersion` 声明服务端实现的 A2A 协议规范版本（跟随协议发布节奏，如 `0.2.x` 到 `0.3.x` 的演进）。前者是内容版本管理，后者是兼容性契约。安全上的常见错误是把两者混为一谈，或只校验其一：只看 `version` 无法发现协议行为不匹配，只看 `protocolVersion` 无法发现卡片内容被静默篡改。

版本协商的基本流程是：客户端在发现阶段读取 `protocolVersion`，与自身支持的版本区间比对；若主版本不兼容，应中止并报告，而非"试一试"。对于次版本差异，客户端应按协议的向后兼容承诺降级使用已稳定的能力子集。卡片自身 `version` 则用于缓存失效与变更检测——任何签名验证都应把 `version` 纳入被签载荷，防止攻击者重放旧版卡片。

## 二、版本回滚攻击的形态

版本回滚（rollback）攻击指攻击者用一张历史版本的合法卡片替换当前卡片，使客户端回退到已废弃的行为上。其危险性在于：旧卡片本身可能带有有效签名（签名未过期时），形式上"验签通过"，但其内容已不再被提供方承认——例如旧版卡片的 `url` 指向已退役的端点、旧版 `security` 允许已被禁用的 API Key 认证。防御要点有三：其一，验签时校验单调性（如要求卡片内含发布时间戳并拒绝早于已见最新值的版本）；其二，客户端维护"已见版本水位线"，对低于水位线的卡片触发人工复核而非直接接受；其三，提供方在轮换内容时同步吊销旧签名（如短有效期签名，见第 30 篇）。

```text
协商伪代码：
supported = 客户端支持的 protocolVersion 集合
if card.protocolVersion 主版本 ∉ supported:
    终止：协议不兼容
elif 次版本存在已知差异:
    降级到稳定能力子集并记录
if card.version < 本地已见最高版本(该 agentIdentity):
    标记"疑似回滚"，进入人工复核
else:
    更新水位线并缓存
```

## 三、版本与缓存、监控的联动

版本字段的第二重价值是充当缓存键与监控锚点。客户端缓存卡片时应以 `(主体身份, version)` 为键，而非仅以 URL 为键——否则 CDN 或中间层可能返回与 URL 不匹配的旧内容。变更监控（第 43 篇展开）以 `version` 递增为正常事件、`version` 不变但内容哈希变化为高优告警事件（这是"内容被篡改且篡改者未递增版本"的强信号）。语义化版本约定（主版本表示破坏性变更）可作为告警分级的输入：主版本跳变应触发全面重审，补丁版本变化可仅做差异记录。

## 四、要点清单

- `version` 管卡片内容、`protocolVersion` 管协议契约，二者都校验；
- 主版本不匹配应当即中止，不做"猜测式兼容"；
- 回滚攻击的表象是"合法旧签名"，必须用时间戳与版本水位线双重拦截；
- 缓存键应绑定主体身份与版本，避免层级缓存错配；
- "version 不变而内容变"是投毒的最强告警信号之一；
- 版本字段必须纳入 JWS 被签载荷的覆盖范围。
