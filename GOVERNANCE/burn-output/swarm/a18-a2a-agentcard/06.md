# 06｜well-known 路径发布与标准发现流程

## 一、发现的三条路径

A2A 的能力发现并未强制唯一机制，实践中存在三条互补路径。第一，well-known 直发现：客户端已知服务端域名，向 `https://<域名>/.well-known/agent-card.json` 发起 GET（早期规范文件名为 `agent.json`，实现应兼容两者并优先新名）。第二，目录/注册中心发现：提供方将卡片提交到聚合目录，客户端按标签、能力关键词检索。第三，带外交换：合作双方通过配置文件、邮件、管理平台人工交换卡片或其指纹。三条路径的信任性质不同——直发现依赖域名与传输安全，目录发现叠加目录方的背书，带外交换依赖线下信任链——因此验签策略也应分级设计。

```text
GET /.well-known/agent-card.json HTTP/1.1
Host: agents.example.com

HTTP/1.1 200
Content-Type: application/json; charset=utf-8
Cache-Control: public, max-age=300
<AgentCard JSON 正文>
```

## 二、发布方的工程要求

发布 well-known 卡片时，提供方需要满足一组工程约束：路径必须位于域名根（子路径应用由卡片 `url` 字段表达，而非改发现路径）；必须经 HTTPS 提供且证书有效；响应应带正确的 `Content-Type: application/json` 与 UTF-8 编码；`Cache-Control` 的 max-age 应与卡片变更频率及签名有效期匹配（过长会让投毒内容滞留，过短放大发现流量）；若卡片支持签名，应在响应头或卡片内提供签名附带方式（如 `Content-Signature` 类头部或双文档 `agent-card.json` + `agent-card.json.sig`）。服务端还应拒绝在明文 HTTP 上返回卡片，或在返回时附警示字段，防止降级抓取。

## 三、客户端抓取流程与失败处理

标准抓取流程：构造 well-known URL → 强制 HTTPS（禁止跟随 http 降级重定向）→ 校验证书链与主机名 → 获取响应 → 解析 JSON（严格模式，拒绝重复键与尾随逗号）→ 执行结构校验（必填字段、类型、枚举值）→ 执行签名验证（若启用）→ 计算指纹并记录。失败处理必须区分错误类别：网络失败（可重试）、证书失败（硬失败并告警）、JSON 解析失败（硬失败，可能是投毒痕迹）、结构校验失败（硬失败）、验签失败（硬失败且触发安全事件流程）。切忌把"验签失败"降格为警告后继续使用——这是投毒防护中最常见也最致命的实现错误。

```python
def discover(host: str) -> dict:
    if not host.endswith(".example.com"):  # 受控域白名单示意
        raise DiscoveryError("host not in allowlist")
    url = f"https://{host}/.well-known/agent-card.json"
    resp = https_get(url, allow_redirects=False)  # 禁降级重定向
    card = json.loads(resp.body, parse_constant=_reject)  # 严格解析
    validate_schema(card)
    verify_signature_or_fail(card, resp.headers)
    record_fingerprint(host, card)
    return card
```

## 四、要点清单

- 三条发现路径（直连、目录、带外）信任性质不同，验签策略应分级；
- 发布侧要求：根路径、HTTPS、正确 Content-Type、匹配的缓存策略；
- 抓取侧要求：禁降级重定向、严格 JSON 解析、结构校验、验签、留指纹；
- 失败分类处理，验签失败必须是硬失败；
- 发现阶段的每一步日志都是事后追溯投毒事件的证据链组成部分。
