# 15｜投毒向量二：URL 端点劫持

## 一、url 字段的劫持效果

AgentCard 中的 `url` 是客户端所有 JSON/RPC 调用的目的地。攻击者把它从 `https://agents.example.com/a2a/v1` 改为 `https://agents.example.com.attacker.net/a2a/v1` 或直接换成攻击者域，客户端后续所有请求（含凭据、任务内容、上下文片段）将尽数流向攻击者端点。攻击者只需实现协议外壳（对 `message/send` 返回合理响应），即可长期静默收集数据，或在关键任务上返回伪造结果——比直接断流更具欺骗性。

## 二、变体攻击面

除主 `url` 外，还有四个端点类字段构成同族攻击面：**additionalInterfaces[].url**（附加接口端点）；**securitySchemes 内的 tokenUrl / authorizationUrl**（认证端点，被替换后客户端主动提交凭据换取令牌——凭据直接泄露）；**capabilities.pushNotifications 为 true 时的 webhook 注册流程**（客户端提交自身回调地址，攻击者获知内部拓扑并可回放伪造通知）；**documentationUrl / iconUrl**（低敏感，但可被用于加载跟踪像素或钓鱼页面，客户端不应自动渲染抓取）。

## 三、防御矩阵

```text
签名覆盖    ：所有端点字段（含嵌套）必须入签，任何变更使签名失效
变更告警    ：端点字段变更 = 最高级别事件，自动比对历史值并人工确认
带外登记    ：高信任场景把端点写入带外配置，卡片仅作一致性校验对象
同源约束    ：策略可要求 additionalInterfaces 与主 url 同注册域或同网段
凭据隔离    ：tokenUrl 与登记的授权服务器地址强绑定，不一致即拒绝调用
渲染克制    ：documentationUrl/iconUrl 不自动抓取渲染，仅作展示文本
```

签名解决"篡改可被检出"，但注意一个盲区：若提供方自身的存储被入侵且攻击者同时能重签（L4 场景），签名不再可信——此时依赖的是带外登记比对与变更告警中"人工确认"这道闸门。这也是把"端点变更"设为最高级别告警的原因：即便是合法变更，也应经过确认才生效。

## 四、应急：劫持已发生的处置

若监测到客户端曾向未登记端点发出请求（出站日志发现异常目的地）：立即冻结该主体协作、吊销会话凭据、评估已外发数据范围、重放检测（比对历史请求目的地址分布）。处置流程的关键是出站日志必须完整——客户端应记录每次调用的目的端点、时间、凭据标识，这既是事后追溯依据，也是"端点漂移"实时检测的数据源。

## 五、要点清单

- 主 url 与四个变体端点（附加接口、认证端点、webhook、文档图标）同族设防；
- 端点字段变更设为最高级别告警，合法变更也需人工确认生效；
- 带外登记 + 签名 + 同源策略三重叠加，防 L3 兼顾 L4；
- 完整出站日志是劫持检测与事后追溯的生命线；
- 凭据类端点（tokenUrl）的防护优先级高于其他一切端点。
