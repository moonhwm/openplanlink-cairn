# 08｜securitySchemes 与认证方式声明

## 一、securitySchemes 的结构

AgentCard 的 `securitySchemes` 采用与 OpenAPI 兼容的命名体系，声明服务端支持的认证方案。常见类型包括：`apiKey`（键放置于 header/query/cookie）、`http`（如 basic、bearer）、`oauth2`（含 flows：authorizationCode、clientCredentials、implicit、password）、`openIdConnect`（OIDC 发现端点）。每个方案以键名索引，供 `security` 字段引用。声明的作用是让客户端在调用前完成凭据准备——例如按 oauth2 的 tokenUrl 走 client credentials 流程换取令牌。

```json
{
  "securitySchemes": {
    "bearer": { "type": "http", "scheme": "bearer" },
    "oauth2": {
      "type": "oauth2",
      "flows": {
        "clientCredentials": {
          "tokenUrl": "https://auth.example.com/oauth/token",
          "scopes": { "a2a:invoke": "调用接口", "a2a:admin": "管理类操作" }
        }
      }
    }
  },
  "security": [{ "oauth2": ["a2a:invoke"] }, { "bearer": [] }]
}
```

`security` 是"或"关系数组：满足其中任一元素即可调用。上例表示优先 OAuth2（带 scope 要求），也接受裸 Bearer。这个"或"语义正是认证降级攻击的操作空间。

## 二、认证降级攻击的机理

设想真实卡片只允许 `oauth2`，攻击者将其篡改为 `security: [{ "apiKey": [] }]` 或追加一个 `apiKey` 备选项。客户端若信任卡片，就会转而把静态 API Key 放进请求头——凭据形态从短时令牌退化为长期密钥，暴露面显著扩大（不可撤销性强、可被中间环节收集）。更危险的变体是把篡改后的 tokenUrl 指向攻击者端点：客户端会把自己的 client_id/client_secret 直接 POST 给攻击者。防御要点：其一，`securitySchemes` 与 `security` 必须整体纳入签名覆盖；其二，客户端策略应对"认证方案变更"这一事件类型设置最高告警级别；其三，tokenUrl 等敏感端点可与带外登记的授权服务器地址比对，不一致即拒绝；其四，客户端不应因卡片声明了弱方案就放弃自身策略——本地策略优先于远端声明，声明只是上限参考而非强制命令。

## 三、声明与实现的校验循环

卡片声明的认证方案应与实际接口行为一致。预检循环：按声明方案构造一次最小权限请求（如查询自身能力或空任务），观察响应是 401（未带凭据）、403（凭据不足）还是 200。若声明 oauth2 实际接受任何明文请求，说明声明失实或实现有洞，两种情况都应记录并降级信任。scope 收敛也值得注意：客户端只应申请完成任务所需的最小 scope，即使卡片列出了更大的 scope 集合。

## 四、要点清单

- `securitySchemes` 声明方案、`security` 以"或"关系组合需求；
- 降级攻击利用"或"语义诱导弱凭据或泄露凭据到伪造 tokenUrl；
- 认证字段变更 = 最高级别告警事件，纳入签名覆盖与变更监控双机制；
- 本地安全策略优先于远端声明，声明不能命令客户端放松自身；
- 预检请求可低成本验证声明与实现的一致性，scope 遵循最小化。
