# 11｜AgentCard 扩展字段与兼容性实践

## 一、扩展机制与命名约定

AgentCard 允许在卡片与 skills 元素上添加自定义字段以承载领域信息（如数据驻留声明、限流配额、服务等级、合规认证）。社区惯例是使用 `x-` 前缀（继承自 OpenAPI 的实践），例如 `x-data-residency: "cn"`、`x-rate-limit: {"rpm": 60}`。约定俗成的规则：标准字段名不得被扩展占用；扩展字段在不被理解时必须可安全忽略——即扩展只增不改地叠加语义，不能改变标准字段的既有含义。

```json
{
  "name": "fraud-scorer",
  "x-data-residency": "cn",
  "x-compliance": ["iso27001"],
  "x-signature": { "alg": "ES256", "jws": "..." },
  "skills": [
    { "id": "score", "x-latency-p99-ms": 450 }
  ]
}
```

## 二、兼容性三原则

扩展实践应遵守三条原则。**前向兼容**：客户端遇到不认识的 `x-` 字段应原样保留（尤其在重新序列化卡片用于验签时，绝不能因不认识而丢弃——丢弃将破坏规范化字节流，详见 JCS 系列）。**语义不越权**：扩展不得用于覆盖标准行为，例如不能用 `x-allow-http` 让客户端接受明文传输，不能用 `x-skip-auth` 免除认证——这类"扩展即漏洞"的设计应在校验阶段被黑名单拦截。**文档化**：每个扩展字段应有公开说明其类型、取值与变更策略，否则生态方只能猜测语义，猜测即风险。

## 三、扩展字段与验签的交互

扩展字段给验签带来两个具体问题。第一，签名覆盖范围必须包含扩展字段：若签名实现只对已知标准字段重建规范化串再验签，攻击者就能通过注入恶意 `x-` 字段绕过完整性保护（签名仍验证通过但内容多了字段）。正确做法是对整卡做 JCS 规范化后验签，扩展字段自然全部入签。第二，扩展字段本身可能承担签名承载（如上例 `x-signature`）：签名字段自身不能进入被签载荷（自引用悖论），实现上应把签名放入独立信封（HTTP 头或伴随文件），或采用"验签前剔除签名字段再规范化"的明确规则——后一种必须极其小心字段剔除的精确性，推荐前者。

## 四、要点清单

- 扩展用 `x-` 前缀，不被理解时必须可安全忽略且不得丢弃；
- 扩展不越权：不得借扩展放宽标准安全语义，校验层设黑名单；
- 验签覆盖必须包含全部扩展字段，整卡规范化是唯一稳妥做法；
- 签名承载推荐外置信封，避免"剔除自身再签"的自引用陷阱；
- 每个扩展字段公开文档化，类型、取值、变更策略三要素齐全。
