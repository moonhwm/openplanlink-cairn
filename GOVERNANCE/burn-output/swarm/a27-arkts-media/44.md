# 44 · 静音模式、响铃模式与勿扰对播放的影响

> 一句话摘要：设备的响铃模式（普通/静音/振动）与勿扰主要约束提示类声音，媒体流通常不受静音开关键影响，但"必达提示"与"尊重用户意图"的边界要靠产品策略与系统开关显式声明，绝不静默绕过。

## 一、模式体系与流类型的交集

移动设备的声音意图由两组开关表达：响铃模式（`AudioManager.getRingerMode()`：`RINGER_MODE_NORMAL` / `RINGER_MODE_SILENT` / `RINGER_MODE_VIBRATE`）与勿扰模式（通知侧的 DND 策略）。它们的作用面主要是提示类声音：铃声、通知音、短提示。媒体类内容（音乐、视频、播客、游戏 BGM）在多数策略下**不受**静音开关影响——用户静音通常是想让世界安静，而不是让主动打开的音乐消失；这与"用户主动播放"的意图优先原则一致。因此应用的第一个设计判断是：我的流属于哪一类（对应第 39 篇的"内容/伴生/必达"三分），内容类无需对静音开关做任何特殊处理，必达提示类才需要评估策略。

## 二、模式感知与播放前置检查

```typescript
import { audio } from '@kit.AudioKit';

export class MannerAwareness {
  private am = audio.getAudioManager();

  ringer(): string {
    switch (this.am.getRingerMode()) {
      case audio.AudioRingMode.RINGER_MODE_NORMAL:  return 'normal';
      case audio.AudioRingMode.RINGER_MODE_SILENT:  return 'silent';
      case audio.AudioRingMode.RINGER_MODE_VIBRATE: return 'vibrate';
      default: return 'unknown';
    }
  }

  // 短提示播放前的策略决策
  shouldPlayAlert(): { play: boolean; reason: string } {
    const mode = this.ringer();
    if (mode === 'silent') {
      // 产品决策点：a) 尊重静音不出声 b) 走静音混音开关出声（第21/39篇）
      return this.policy.allowAlertInSilent
        ? { play: true,  reason: 'policy: mix-with-others' }
        : { play: false, reason: 'respect silent' };
    }
    if (mode === 'vibrate') {
      return { play: this.policy.vibrateWithAlert, reason: 'vibrate mode' };
    }
    return { play: true, reason: 'normal' };
  }
}
```

## 三、产品策略的三个层次

层次一：默认尊重。内容流照播、伴生音效跟随应用内开关、必达提示在静音下默认不出声（转为振动/视觉提示），这是无需解释的稳妥默认。层次二：显式豁免。导航、闹钟类"必须出声"的提示，通过静音混音开关（如版本提供 setSilentModeAndMixWithOthers）在静音下出声，但必须在产品内明示用户"此类提示将在静音模式下播放"，把豁免变成用户知情的选择。层次三：动态引导。检测到静音且产品判断用户可能错过关键信息时，用 UI 提示引导用户调整（如"当前为静音模式，闹钟铃声将被静音，是否调整？"），而不是替用户改系统设置——应用不得擅自修改系统响铃/勿扰状态。勿扰（DND）侧同理：通知类声音受其约束，媒体播放一般不受影响，但带语音播报的功能在勿扰下的降级（改为横幅）要走通知渠道策略，与音频层解耦。

## 四、模式策略检查清单

- [ ] 每条流标注内容/伴生/必达类别，静音下的行为按类成文。
- [ ] 必达提示的静音豁免走系统开关且用户知情，不擅自绕过或修改系统设置。
- [ ] 模式查询放在"播放前决策点"，长会话中辅以变化监听刷新策略。
- [ ] 振动模式的产品语义明确（伴振动出声/仅振动）。
- [ ] 勿扰下的语音播报降级走通知渠道策略，与音频层解耦。
- [ ] 真机验证：静音听音乐不受影响、静音下闹钟类提示按声明的策略表现。
