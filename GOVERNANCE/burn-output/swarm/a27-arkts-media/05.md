# 05 · AVPlayer 倍速、循环与 SeekMode 精讲

> 一句话摘要：倍速由 `setSpeed` 配合 `PlaybackSpeed` 枚举驱动并影响音视频同步，循环由 `loop` 布尔属性实现，而四种 SeekMode 决定了跳转的精度与时延权衡，三者共同构成"播放节奏控制"专题。

## 一、倍速播放 setSpeed 的机制与约束

`avPlayer.setSpeed(media.PlaybackSpeed.SPEED_FORWARD_2_00_X)` 改变的是播放管线的时间基准：音频通过时域拉伸（不变调变速）或重采样处理，视频通过丢帧/重复帧调度追齐，因此倍速对音视频同时生效。可用档位为 `SPEED_FORWARD_0_75_X / _1_00_X / _1_25_X / _1_75_X / _2_00_X / _3_00_X / _3_75_X / _4_00_X`（以所用 API 版本的枚举集合为准），设置非法值会报参数错误。调用合法状态是 playing；倍速改变后通过 `on('speedChange')` 事件确认生效，UI 的倍速按钮选中态应以该事件为准。两个工程要点：其一，倍速期间 `timeUpdate` 的步进会随之变大，进度条自走逻辑要用 `(now - lastTick) * speed` 校准，或直接信任回调值；其二，AVSession 的 `setAVPlaybackState` 里有独立的 `speed` 字段，系统播控中心显示的倍速必须与应用内同步更新，否则锁屏界面会显示错误的档位。

## 二、loop 循环播放的正确用法

循环是 AVPlayer 上少数直接可写的属性：`avPlayer.loop = true` 在 prepared 之后的任意播放相关状态均可设置。置真后播放到结尾会自动从头继续，且**不会**进入 completed 态，stateChange 也不会收到 completed——这是与手动循环最大的行为差异。因此做"单曲循环/列表循环/随机播放"三态切换的播放器时，判断依据必须分开：单曲循环时业务层不监听 completed（或忽略之），列表模式才依赖 completed 推进。循环与 `playbackState` 的 `loopMode` 字段（`avSession.LoopMode.SEQUENCE`/`SINGLE`/`SHUFFLE`）也要在切换时同步写入 AVSession，保证锁屏上的循环按钮与内部状态一致。注意 loop 属性在 `reset()` 后会回到默认 false，换源后需要按业务状态重新赋值。

## 三、SeekMode 四档的选型决策

四种 SeekMode 的本质是"跳转目标是否必须精确对齐目标时间戳"。视频流按 GOP 组织，只有关键帧（同步帧）可以独立解码，因此跳到非关键帧时间点需要从前一个关键帧解码到目标位置：精度高但耗时长；跳到同步帧则零解码浪费：快但最多偏差一个 GOP 长度（通常 1~4 秒）。选型口诀：追剧拖进度条用 `SEEK_PREV_SYNC`（不超前、响应快）；"跳过片头 90 秒"这类精确需求用 `SEEK_EXACT`；字幕对齐、逐句复读用 `SEEK_EXACT`；缓存受限场景用 `SEEK_CLOSEST_SYNC` 避免触发大范围回源。音频文件（MP3/AAC）帧密度高，四种模式差异不大，一般默认即可。

```typescript
enum Scene { DRAG, SKIP_INTRO, LYRIC }

seekFor(scene: Scene, ms: number) {
  const mode = scene === Scene.DRAG ? media.SeekMode.SEEK_PREV_SYNC
             : media.SeekMode.SEEK_EXACT;
  this.avPlayer?.seek(ms, mode);
}
this.avPlayer.on('seekDone', (ms) => this.updateProgressBar(ms));
```

## 四、节奏控制检查清单

- [ ] 倍速档位 UI 选中态以 `speedChange` 事件回写，不本地先斩后奏。
- [ ] 倍速切换后同步更新 AVSession `playbackState.speed`。
- [ ] loop=true 时不再依赖 completed 推进列表；reset 后重新赋 loop。
- [ ] 循环模式切换三处同步：avPlayer.loop、AVSession.loopMode、本地持久化偏好。
- [ ] seek 前检查状态属于 playing/paused/completed，completed 下 seek 后会自动续播。
- [ ] 高倍速（≥3x）下降低 UI 刷新频率，避免 timeUpdate 高频刷新造成耗电。

倍速、循环与跳转组合起来即可支撑听书、网课、短视频等绝大多数节奏型场景，它们与后台播放、焦点恢复联动时的状态一致性问题将在第 45 篇统一收口。

## 五、实战问答与易错点

**问一：设置 1.25 倍速后音调变了还是没变？** AVPlayer 的 setSpeed 做时间拉伸（time-stretch），主流档位下音调基本保持，听感因实现与内容而略有差异。若产品对音质极敏感（音乐精听类），建议限制可用档位到 0.75~2.0；听书类用户普遍接受度高，可放开到 4.0。注意 AudioRenderer 的 setRenderRate 是变速不变调补偿的另一端（第 21 篇），两者不可混为一谈。

**问二：loop=true 时怎么统计"播完一次"？** 循环模式下不会进入 completed，不能靠状态事件计数。可行做法：在 timeUpdate 里检测"位置从大突然回到接近 0"判定一圈完成（加去抖防 seek 误判），或者更可靠地用 duration 与累计播放时长对比估算。如果产品强依赖完播事件（发埋点、解锁下一集），应考虑不使用实例 loop 而由应用层监听 completed 手动重播，把控制权拿回自己手里——这也是"系统便利"与"业务可控"的经典权衡。

**问三：倍速状态在暂停、切歌、打断恢复后会丢吗？** 实例内 pause/play 周期倍速保持；reset 换源后倍速回到默认，必须在换源流程里显式重设；打断（焦点被抢再恢复）后应复核倍速，防止链路重建期间丢失。倍速属于"用户偏好状态"，规范做法是单一来源（用户设置存储）+ 三个写点（倍速按钮、切歌流程、恢复流程）统一从来源读取，而不是各处互相同步。

**问四：SEEK_EXACT 在长视频上很慢，有替代方案吗？** 可以分层 seek：拖拽松手先用 SEEK_PREV_SYNC 拿到快速响应（画面立即出现，位置略偏前），随后立刻再发起一次 SEEK_EXACT 校准到精确位置，用户感知是"先近似后精确"的两段式。内容侧的配合更根本：转码时缩短 GOP、增加关键帧密度可以同时改善所有 seek 模式的速度，这属于服务端调优，但对客户端体验是最大杠杆之一。

**问五：循环+倍速+进度上报叠加后锁屏显示乱跳？** 这是三个特性与第 32 篇状态同步的耦合问题：外推公式里 speed 系数、循环回绕（elapsedTime 突然归零）都要正确反映到 setAVPlaybackState。循环回绕的瞬间要立即推一次快照（不要等心跳），把 elapsedTime 归零的信息带给系统，否则锁屏进度条会按外推继续前冲再猛拉回。同步器要把"回绕"视为与 play/pause 同级的关键时点。
