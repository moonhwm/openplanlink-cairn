# 02 · AVPlayer 创建与初始化：url、fdSrc 与本地文件播放

> 一句话摘要：AVPlayer 支持通过 `url` 字符串与 `fdSrc` 描述符两种数据源注入方式，分别覆盖网络流与本地文件/应用内资源场景，正确选择与及时释放文件描述符是本专题的核心。

## 一、三种典型数据源的选择依据

AVPlayer 的数据源注入发生在 idle 态，共有两条通路。第一条是 `avPlayer.url` 字符串，支持 `fd://<文件描述符>` 与 `http://`/`https://`（含 HLS 的 m3u8）形式，设置成功后实例自动迁移到 initialized 态。第二条是 `avPlayer.fdSrc = { fd, offset, length }` 描述符，它专为"文件内部偏移"设计：应用包内 rawfile 目录中的媒体文件经由 `resourceManager.getRawFd()` 取出的描述符天然带有 offset/length，必须走 fdSrc 而不能直接拼 `fd://` 字符串，否则系统会把整个文件当作从 0 开始读取，产生花屏或解码失败。选择依据可以概括为：网络资源用 http/https 形式的 url；沙箱内完整文件用 `fs.openSync()` 打开后拼 `fd://` 形式的 url；应用包 rawfile 或资源文件（HAP 内嵌音频、提示音）一律用 fdSrc。

## 二、创建与初始化的完整流程

初始化流程要严格遵循"创建、监听、设源、prepare"四步顺序，且监听注册应早于数据源设置，避免初始化过程中突发错误无人接收。示例代码：

```typescript
import { media } from '@kit.MediaKit';
import { fileIo } from '@kit.CoreFileKit';
import { BusinessError } from '@kit.BasicServicesKit';

async function playFromSandbox(path: string): Promise<void> {
  const avPlayer = await media.createAVPlayer();
  avPlayer.on('error', (err: BusinessError) => {
    console.error(`init error: ${err.code}`);
  });
  // 场景一：沙箱完整文件 —— 打开文件取 fd，url 使用 fd:// 协议
  const file = fileIo.openSync(path, fileIo.OpenMode.READ_ONLY);
  avPlayer.url = `fd://${file.fd}`;
  avPlayer.on('stateChange', async (state: string) => {
    if (state === 'initialized') {
      await avPlayer.prepare();
    } else if (state === 'prepared') {
      await avPlayer.play();
    }
  });
}
```

## 三、fd 生命周期与常见错误

使用文件描述符时最容易踩的坑是生命周期错配。第一，`fd` 在 AVPlayer release 之前必须保持有效：如果在 prepare 完成前就把文件 `closeSync` 掉，会触发读取失败并进入 error 态。第二，release 之后应当关闭 fd，否则每播一首歌就泄漏一个描述符，长列表场景下会耗尽进程句柄。第三，rawfile 场景使用 `getRawFd('bgm.mp3')` 返回的 `RawFileDescriptor` 直接赋给 `fdSrc`，播放结束后无需手动关闭（资源管理器统一管理），但沙箱文件场景的 fd 必须自己负责开关闭环。第四，`fdSrc` 与 `url` 是互斥关系，同一实例生命周期内先后设置两者会报非法状态，换源请通过 `reset()` 回到 idle 后再设置。第五，http 播放需要确认 `module.json5` 中已声明 `ohos.permission.INTERNET` 权限，否则错误码 201 会直接打回。

## 四、初始化检查清单

- [ ] `on('error')` 与 `on('stateChange')` 在设置数据源之前完成注册。
- [ ] rawfile 资源使用 `fdSrc + offset/length`，不使用 `fd://` 字符串。
- [ ] 沙箱文件使用 `fs.openSync` + `fd://<fd>`，release 后关闭 fd。
- [ ] 网络播放确认 INTERNET 权限与 HTTPS 证书策略（ATS 默认拦 http，需声明 cleartext）。
- [ ] 换数据源统一走 `reset()`，不复用 url 字段反复赋值。
- [ ] initialize 阶段的超时兜底：网络源建议自行加 8~15 秒超时并 reset 重试。

上述闭环建立后，AVPlayer 的初始化就具备了在业务层复用的稳定性，后续章节的网络缓冲、轨道管理等专题都以此为基座。

## 五、实战问答与易错点

**问一：fdSrc 和 url 能否先用一个、再换另一个？** 不能在同一实例生命周期内直接互换。url 与 fdSrc 都只在 idle 态可写，且语义互斥：设过其中一个后想换数据源，正规路径是 reset() 回到 idle 再设新的。直接在 initialized 态改写另一个字段会得到非法状态错误。封装层应当把"换源"做成原子方法（reset → 设源 → prepare），业务侧永远不直接触碰这两个字段，也就不会踩到这条约束。

**问二：getRawFd 返回的描述符播完要不要手动 close？** 不需要也不应该。rawfile 描述符由 resourceManager 统一持有与回收，应用手动关闭反而可能影响资源管理器内部状态。与之相对，`fs.openSync` 打开的沙箱 fd 必须"谁打开谁关闭"，推荐在 release 完成的回调里统一 closeSync。两类 fd 的责任边界要在封装层写清楚：rawfile 只读不关、沙箱有开必有关，混着管必然出现句柄泄漏或提前失效。

**问三：为什么 fd:// 播放偶尔报格式错误，重试又好了？** 典型原因是 fd 生命周期错配：open 与 set url 之间、或 release 之前的某个环节 fd 被提前关闭，读到的是失效描述符上的随机数据，解封装自然报格式错误。另一种可能是打开模式错误（用了 CREATE 而非 READ_ONLY 导致内容为空）。排查方法是在 open、set url、release、close 四个点打定点日志（第 48 篇锚点法），按时间线核对 fd 编号是否一致、关闭时机是否早于 release。

**问四：HLS 与普通 mp4 的 url 设置有差别吗？** 字符串层面没有差别，都是完整的 http/https 地址，差异在播放行为：HLS 是流式清单，prepare 时长受首片下载影响，videoSizeChange 可能延迟到达，中途分辨率切换会再次触发尺寸事件。工程上要把 HLS 与点播文件区别对待的是超时阈值（HLS 初始化放宽）、缓冲 UI（分片边界可能出现短暂 BEGIN）以及进度条语义（直播型 HLS 的 duration 可能未知或动态增长，seek 的可用范围要以 buffered 信息为准）。

**问五：网络源设了 url 但一直停在 idle 没进 initialized？** 先检查 url 赋值是否真的执行成功：赋值非法协议（比如缺少 fd:// 前缀的裸路径、拼错的 https）会直接触发 error 而非静默失败。其次确认 INTERNET 权限与明文策略。如果这两项都正常，再排查设备网络与 DNS。一个实用的防御写法是设 url 前做协议白名单校验，不认识的来源直接走本地异常分支，避免把配置错误延迟到播放阶段才暴露。
