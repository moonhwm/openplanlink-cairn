# 08 · AVPlayer videoSizeChange 与画面自适应布局

> 一句话摘要：`videoSizeChange` 事件在 prepared 阶段上报真实宽高，布局层必须据此计算宽高比并选择合适的 ImageFit/Aspect 策略，避免拉伸变形与黑边争议。

## 一、为什么必须监听 videoSizeChange

视频源的真实分辨率千差万别：横屏电影 2.35:1、普通剧集 16:9、竖屏短视频 9:16、老片 4:3，而 XComponent 的布局区域通常按设计稿固定。若不依据真实宽高做适配，画面要么拉伸变形（把 16:9 拉成 4:3，人脸变宽），要么随意裁切（竖屏视频在横条容器里只剩中间一条）。AVPlayer 在解封装完成后会通过 `on('videoSizeChange', (w, h) => {})` 上报真实尺寸，该事件通常在 prepared 前后触发一次；直播流中途切换分辨率（HLS 自适应或多机位）时可能再次触发，因此监听应常驻而不是只在初始化时读一次。注意 h 为 0 的特殊情况：纯音频内容或尺寸未知时回调可能带 0，布局要有缺省兜底（按 16:9 处理或隐藏画面区域）。

## 二、宽高比驱动的自适应布局实现

核心思路是把容器做成"按宽高比计算高度（或宽度）"的自适应块，画面用 CONTAIN 语义完整显示，多余部分用黑底：

```typescript
@Entry
@Component
struct AdaptiveVideo {
  @State videoRatio: number = 16 / 9;    // 缺省16:9，事件到达后更新
  private avPlayer?: media.AVPlayer;
  private surfaceWidth: number = 0;      // 容器实测宽

  build() {
    Column() {
      Stack({ alignContent: Alignment.Center }) {
        XComponent({ id: 'v', type: XComponentType.SURFACE, libraryname: '' })
          .controller(this.xctl)
          .onAreaChange((_o, n) => { this.surfaceWidth = n.width as number; })
        // 16:9以内视频高度=宽/比例；竖屏视频则反向限制高度
      }
      .width('100%')
      .aspectRatio(this.videoRatio > 1 ? this.videoRatio : undefined)
      .height(this.videoRatio <= 1 ? '100%' : undefined)
      .backgroundColor(Color.Black)
      .clip(true)
    }
  }

  watchSize(player: media.AVPlayer) {
    player.on('videoSizeChange', (w: number, h: number) => {
      if (w > 0 && h > 0) {
        this.videoRatio = w / h;         // 例：2.35:1电影、9:16竖屏
      }
    });
  }
}
```

## 三、三种适配策略的取舍

策略一"完整显示（CONTAIN 语义）"：按比例缩放到容器内完整可见，留黑边，信息无损，适合长视频与教育内容，是最稳妥的默认策略。策略二"填满裁切（COVER 语义）"：等比缩放至铺满容器、超出部分裁掉，观感沉浸但必然损失边缘信息，适合竖屏信息流里的横屏视频背景化展示，不适合有人物居中偏移风险的课程类内容。策略三"容器反向自适应"：让播放器区域跟随视频比例伸缩（横屏视频占宽 100%、竖屏视频占高 100%），Feed 流与详情页最常用。策略应做成用户可切换（"满屏/适应"按钮），切换只改布局属性，不触碰播放器实例；旋转屏幕（横竖屏切换）时系统会重建或重排组件，注意在 `onAreaChange` 里重新计算并保持 surfaceId 有效。

## 四、画面适配检查清单

- [ ] `videoSizeChange` 常驻监听，支持直播中途变分辨率二次触发。
- [ ] w/h 为 0 或异常值（如 0x0、负值）时使用缺省比例兜底。
- [ ] 默认 CONTAIN 防变形；COVER 场景确认关键内容不会被裁。
- [ ] "满屏/适应"切换只改布局与裁剪参数，不重建 AVPlayer。
- [ ] 横竖屏旋转后重新计算容器尺寸，画面比例与黑边策略一致。
- [ ] 弹幕/字幕浮层跟随视频有效画面区域而非整个容器，避免压到黑边外。

画面适配是"视频能用"到"视频好用"的分水岭，与 Surface 生命周期（第 7 篇）、性能复用（第 47 篇）一起构成视频渲染三板斧。

## 五、实战问答与易错点

**问一：竖屏视频在 16:9 的列表卡片里应该怎么展示？** 信息流场景的惯例是容器跟随内容：卡片高度按 9:16 反算（宽 100% 时高度约为宽的 1.78 倍），完整展示不裁切，黑边交给卡片背景色消化。若产品要求卡片等高（瀑布流统一高度），则必须用 COVER 裁切并接受边缘损失，同时提供点开后的全屏 CONTAIN 视图作为完整观看兜底。两种模式的切换只改布局参数，播放器实例不动（第 7 篇原则）。

**问二：videoSizeChange 到达前就渲染画面，比例闪跳怎么办？** 用缺省比例占位（16:9）+ 事件到达后平滑过渡。视觉优化手段是给视频容器加一个短暂的比例过渡动画（150~250ms），把"从 16:9 跳到 2.35:1"变成一次可感知的形变而不是闪跳；纯黑背景 + 无过渡在深色主题里几乎不可见，浅色主题下更值得做过渡。极端情况下尺寸事件迟迟不来（流异常），要有超时兜底维持缺省比例并上报。

**问三：字幕的安全区域怎么算？** 字幕浮层应贴着"视频有效画面"的底部而不是屏幕底部：CONTAIN 模式下黑边高度 = (容器高 - 画面高) / 2，字幕要从容器底加这个偏移开始排版，否则字幕压在黑边上、离画面过远。COVER 模式下画面被裁，字幕安全区要按"裁切后可见区域"的保守估计（画面中心 80% 宽度）排版，防止关键台词被裁掉。

**问四：旋转屏幕后比例与黑边策略不一致？** 旋转触发组件重建或重排（依应用的方向配置），要在 onAreaChange/页面尺寸变化回调里重算 ratio 与容器尺寸，且策略要与旋转前一致（用户选的 CONTAIN 不因旋转变成 COVER）。用 @State 保存当前策略与 ratio，布局函数纯函数化（输入 ratio+容器尺寸，输出布局参数），旋转只是输入变化，输出自然一致。

**问五：多清晰度切换后 videoSizeChange 会触发吗？** 会，分辨率变化会再次回调。此时布局层要无缝处理比例变化（多数同内容多清晰度比例相同，只有像素密度变化，布局无感知；跨比例的切换如 4:3 老源换 16:9 新源则要重算）。清晰度切换本身走"换源 + 断点 seek"路径（第 9 篇），尺寸事件是它的伴生事件，适配逻辑写一次即可复用。
