# 29 · WantAgent 与后台任务通知联动

> 一句话摘要：WantAgent 描述"点击后台任务通知/系统入口时的启动意图"，音频长时任务通过它把用户带回播放界面，其构造参数（目标 ability、操作类型、请求码）决定回跳行为与冷热启动路径。

## 一、WantAgent 在长时任务中的角色

申请 AUDIO_PLAYBACK 长时任务时，第三个参数 wantAgent 不是可省略的装饰：系统用它构造任务通知的点击行为。用户在后台听歌时，下拉通知栏可以看到常驻的媒体任务标识（系统侧与 AVSession 面板的呈现形态随版本演进），点击它的预期是"回到这个应用、最好直接落到播放页"。WantAgent 就是这段"意图的延迟执行描述"：由 `wantAgent.getWantAgent(info)` 异步构造，info 中最重要的是 `wants`（目标 ability 的 bundleName/abilityName，可带 parameters 自定义参数）、`operationType`（START_ABILITY 启动 / SEND_COMMON_EVENT 发事件等）与 `requestCode`。长时任务场景统一用 START_ABILITY。

## 二、构造与回跳参数传递

```typescript
import { wantAgent, common, Want } from '@kit.AbilityKit';

export async function buildTaskAgent(ctx: common.UIAbilityContext) {
  const want: Want = {
    bundleName: ctx.abilityInfo.bundleName,
    abilityName: ctx.abilityInfo.name,
    parameters: {
      // 自定义回跳标记：onNewDelivery/onCreate里识别并路由到播放页
      'entry': 'from_media_task',
      'page': 'PlayerPage'
    }
  };
  return wantAgent.getWantAgent({
    wants: [want],
    operationType: wantAgent.OperationType.START_ABILITY,
    requestCode: 1001,
    wantAgentFlags: [wantAgent.WantAgentFlags.UPDATE_PRESENT_FLAG]  // 已在栈顶复用实例
  });
}
```

## 三、回跳行为的三条设计决策

决策一，冷热启动统一路由。点击通知时应用可能已被销毁（冷启动走 onCreate/onWindowStageCreate）或仍在后台（热启动走 onNewWant），两处都要解析 want parameters 里的 `entry/page` 标记并路由到播放页，把差异收敛到导航层。决策二，UPDATE_PRESENT 语义。设置"更新已存在实例"类标志可避免热启动时重复新建 ability 实例造成播放状态丢失——播放服务若挂在 ability 上，实例重建等于播放中断。决策三，携带状态而非重建状态。parameters 里只传"路由意图"，不要试图把播放列表、进度等大对象塞进 want（有大小限制且序列化开销大）；正确姿势是回跳后从播放服务单例读取现状，want 只负责指路。

## 四、WantAgent 检查清单

- [ ] 目标 ability 指向承载播放服务的 ability，热启动复用而非重建。
- [ ] parameters 只带轻量路由标记，onCreate/onNewWant 双路径解析。
- [ ] requestCode 常量化管理，多任务场景（如未来的下载任务）各自独立。
- [ ] getWantAgent 失败时降级为不传或空 agent，不阻塞任务申请主流程。
- [ ] 真机验证：冷启动点击、热启动点击、锁屏点击三种路径都落到播放页。
- [ ] 回跳后导航不产生双页面栈（push 前查路由栈）。
