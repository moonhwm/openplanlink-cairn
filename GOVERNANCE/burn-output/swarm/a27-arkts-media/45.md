# 45 · 播放中心架构：统一 PlayerService 封装与状态分发

> 一句话摘要：把 AVPlayer 内核、AVSession、长时任务、打断处理、预加载收敛进一个单例 PlayerService，对外暴露命令方法与状态流，UI 与系统播控都作为订阅者消费同一状态源，是消灭状态分叉的架构答案。

## 一、为什么必须收敛

没有统一服务时，播放逻辑散落在页面组件里，至少产生五类结构性问题：多入口命令（UI 按钮、锁屏、耳机线控、WantAgent 回跳）各自直改播放器，状态互相踩踏；状态镜像（UI、AVSession、后台任务）由各处手工维护，漏一处就分叉；页面生命周期与播放器生命周期错误耦合（返回页面音乐停了、或页面销毁泄漏实例）；打断/设备/焦点横切逻辑在每处命令点重复实现；测试无从下手（必须起真实播放器）。收敛后的 PlayerService 是"命令的单一入口 + 状态的单一出口"：所有来源的命令都调它的方法，所有消费者订阅它的状态流，横切逻辑（打断、任务、同步）只写一遍。

## 二、服务骨架与状态分发

```typescript
export interface PlayerState {
  item?: MediaItem; playing: boolean; positionMs: number; durationMs: number;
  speed: number; buffering: boolean; error?: string;
}

type Listener = (s: PlayerState) => void;

export class PlayerService {
  private static inst: PlayerService;
  static get(): PlayerService { return PlayerService.inst ??= new PlayerService(); }

  private kernel?: media.AVPlayer;               // 第1-14篇能力
  private session?: avSession.AVSession;         // 第30-33篇能力
  private bgTask = new BgTask(ctx);              // 第28篇
  private preload = new PreloadSwitcher();       // 第13篇
  private state: PlayerState = { playing: false, positionMs: 0, durationMs: 0, speed: 1, buffering: false };
  private listeners = new Set<Listener>();

  subscribe(fn: Listener): () => void {          // UI与播控统一订阅
    this.listeners.add(fn); fn(this.state);
    return () => this.listeners.delete(fn);
  }

  // ——命令入口：UI按钮/AVSession命令/耳机事件一律走这里——
  async play(item?: MediaItem) {
    if (item && item.id !== this.state.item?.id) await this.switchItem(item);
    await this.kernel!.play();
    await this.afterStateChange();               // 统一镜像出口
  }
  async pause() { await this.kernel!.pause(); await this.afterStateChange(); }
  async seekTo(ms: number) { await this.kernel!.seek(ms, media.SeekMode.SEEK_EXACT); }
  async next() { /* 列表推进+预加载接管（第13篇） */ }

  // ——横切逻辑唯一实现点——
  private async afterStateChange() {
    this.emit();                                 // 1. 分发给UI订阅者
    await StateSync.push(this.session!, this.kernel!);   // 2. 镜像到AVSession
    this.state.playing ? await this.bgTask.start()        // 3. 对齐长时任务
                       : this.bgTask.stopLater();         //    （滞回窗口）
    this.store.save(this.state);                 // 4. 持久化冷启动恢复（第35篇）
  }

  private emit() { this.listeners.forEach(fn => fn({ ...this.state })); }
}
```

## 三、UI 侧与系统侧的对称接入

页面组件只做两件事：订阅状态流渲染控件（播放按钮、进度条、封面），点击时调用服务命令；组件自身不持有播放器、不注册播放事件。AVSession 命令路由（第 33 篇）指向服务的同名方法，形成对称：`on('play') → svc.play()` 与 `按钮 → svc.play()` 汇于一点。跨页共享（迷你条 + 全屏页）天然成立，因为状态源唯一；后台存活（服务挂载在 Ability 级而非页面级）也天然成立。扩展点通过组合而非继承接入：预加载器、实例池、设备守卫、打断处理器都是可替换的内部组件。测试上，内核可被注入假实现（FakeKernel 模拟状态机迁移），命令—状态—镜像的用例表（第 38 篇矩阵）可以离线回归。

## 四、架构检查清单

- [ ] 单例服务持有内核/会话/任务三件套，命令方法是其唯一公共 API。
- [ ] 状态以不可变对象分发，UI 与播控同为订阅者，无旁路写入。
- [ ] 打断、设备、焦点、任务、同步五类横切逻辑只在服务内实现一次。
- [ ] 内核可注入假实现，核心状态机用例可离线单测。
- [ ] 迷你条/全屏页/锁屏三端同屏一致（订阅同一流）。
- [ ] 服务销毁路径完整（第 12 篇序列），Ability 重建场景可恢复。

架构落地后的最后一层保障是"坏情况设计"：下一篇的错误分类、重试与格式降级。
