# 37 · 音频焦点管理总论：InterruptMode 独占与共享模式

> 一句话摘要：`audio.InterruptMode` 是每个播放实例对焦点体系的参与声明——INDEPENDENT_MODE 全量参与抢占与恢复仲裁，SHARE_MODE 与同类流混音共存，模式选择应按"内容是否可与其他声音叠加"做产品级决策。

## 一、焦点体系的仲裁模型

系统音频服务是所有声音的唯一出口，它维护一张按流用途（usage）与优先级组织的仲裁表：铃声与通话最高（可强制打断一切），语音助手、导航播报次之（常以 DUCK 压低音乐而非完全打断），普通音乐流相互之间是对等竞争关系。仲裁的结果就是打断事件：向被抢占方下发 PAUSE/DUCK/STOP（START 阶段），向被释放方下发 RESUME/UNDUCK（END 阶段），并区分系统已强制执行（FORCE）与建议应用执行（SHARE）。应用侧对这套体系的参与方式由每个播放实例的 `setAudioInterruptMode` 决定，这就是焦点管理的第一道、也是最重要的一道产品决策。

## 二、两种模式的语义与选择

`INDEPENDENT_MODE`（默认）：实例全量参与抢占仲裁——更高优先级流出现时被暂停/压低，对方结束后收到恢复提示；两个同优先级音乐实例先后启动时，后启动者通常抢占前者（策略随系统版本与流用途演进）。`SHARE_MODE`：实例不参与独占竞争，与同时发声的其他流混音共存，也不会因别的音乐应用启动而收到暂停打断。选择决策表：

| 内容形态 | 典型例子 | 推荐 | 理由 |
|---|---|---|---|
| 主内容流 | 音乐、播客、视频原声 | INDEPENDENT | 用户预期"独享出声通道"，被来电打断后可恢复 |
| 必达提示 | 导航播报、跑步提醒 | INDEPENDENT + 高优先级 usage | 需要压低/暂停音乐 |
| 伴生音效 | 游戏枪声、按钮音 | SHARE 或 INDEPENDENT 按产品 | 与自家/他家的音乐叠加是常态 |
| 通话流 | VoIP 双向语音 | INDEPENDENT + VOICE_COMMUNICATION | 通话路由与回声消除链路 |

## 三、模式设置与验证

```typescript
import { audio } from '@kit.AudioKit';

export function applyFocusPolicy(p: media.AVPlayer, kind: 'main' | 'sfx') {
  p.audioInterruptMode = kind === 'main'
    ? audio.InterruptMode.INDEPENDENT_MODE     // 主内容：参与抢占与恢复
    : audio.InterruptMode.SHARE_MODE;          // 伴生音效：混音共存
}

// AudioRenderer 侧等价API（第22篇已展开处理逻辑）
export function applyRendererFocus(r: audio.AudioRenderer, mode: audio.InterruptMode) {
  r.setAudioInterruptMode(mode);
}
```

验证矩阵（真机双应用互测）：本应用 INDEPENDENT + 音乐应用 INDEPENDENT：互抢，后启者占焦点，先播者收 PAUSE，结束收 RESUME。本应用 SHARE + 音乐应用任意：双声叠加共存。本应用 INDEPENDENT + 来电：强制暂停，挂断后 RESUME。本应用 SHARE + 来电：仍会被最高优先级打断（SHARE 豁免的是对等流竞争，不是豁免通话）。这张矩阵是焦点策略评审的核心依据，逐格标注产品预期后再开发。

## 四、焦点策略检查清单

- [ ] 每条播放链路显式声明 InterruptMode，不依赖默认值隐式行为。
- [ ] 多实例应用（音乐+音效）逐实例决策，策略成文并进代码评审。
- [ ] SHARE 的边界向产品讲清：对等流共存，但躲不开通话/铃声级打断。
- [ ] 主内容流的恢复策略明确（自动恢复 vs 手动恢复，见第10篇）。
- [ ] 双应用互测矩阵逐格验证，覆盖来电、导航、语音助手三类对手。
- [ ] 系统版本差异记录在案：仲裁策略随 OS 版本演进，回归测试覆盖。
