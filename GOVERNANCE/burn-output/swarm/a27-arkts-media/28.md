# 28 · backgroundTaskManager 长时任务申请与取消（AUDIO_PLAYBACK）

> 一句话摘要：`startBackgroundRunning(context, BackgroundMode.AUDIO_PLAYBACK, wantAgent)` 换取后台不冻结资格，`stopBackgroundRunning` 在声音停止时立即归还，申请与取消的时机纪律直接决定耗电指标与系统合规性。

## 一、API 语义与调用时机

`@ohos.resourceschedule.backgroundTaskManager` 的 `startBackgroundRunning(context, bgMode, wantAgent)` 是音频类长时任务的运行时入口：context 必须是申请任务的 ability 的 UIAbilityContext；bgMode 传 `backgroundTaskManager.BackgroundMode.AUDIO_PLAYBACK`；wantAgent 用于构造任务通知的点击行为（第 29 篇）。申请成功后系统在该 ability 的后台存续期内豁免冻结。时序上的正确位置是"确认开始出声之后"：内核 play 已成功、AVSession 已同步，再申请任务，避免"任务已申请但播放失败"造成无声保活。取消的对称位置是"确认不再出声"：用户暂停、错误停止、打断 STOP、退出播放模式，都应立刻 `stopBackgroundRunning`。音频长时任务没有固定时长上限，但系统会持续校验"任务类型与实际行为相符"——申请了 AUDIO_PLAYBACK 却长时间无声的应用，面临任务被终止甚至后台受限的处置。

## 二、任务管理器封装

```typescript
import { backgroundTaskManager } from '@kit.BackgroundTasksKit';
import { common } from '@kit.AbilityKit';
import { BusinessError } from '@kit.BasicServicesKit';
import { wantAgent } from '@kit.AbilityKit';

export class BgTask {
  private running = false;
  private ctx: common.UIAbilityContext;

  constructor(ctx: common.UIAbilityContext) { this.ctx = ctx; }

  async start(): Promise<boolean> {
    if (this.running) return true;
    try {
      const wa = await wantAgent.getWantAgent({
        wants: [{ bundleName: this.ctx.abilityInfo.bundleName,
                  abilityName: this.ctx.abilityInfo.name }],
        operationType: wantAgent.OperationType.START_ABILITY,
        requestCode: 0
      });
      await backgroundTaskManager.startBackgroundRunning(
        this.ctx, backgroundTaskManager.BackgroundMode.AUDIO_PLAYBACK, wa);
      this.running = true;
      return true;
    } catch (e) {
      const err = e as BusinessError;
      hilog.error(0x0, 'BgTask', `start fail ${err.code} ${err.message}`);
      return false;                     // 失败降级：仅前台播，提示用户
    }
  }

  async stop(): Promise<void> {
    if (!this.running) return;
    try {
      await backgroundTaskManager.stopBackgroundRunning(this.ctx);
    } catch (e) {
      hilog.warn(0x0, 'BgTask', 'stop fail');   // 幂等：已停不算错误
    } finally {
      this.running = false;
    }
  }
}
```

## 三、高频问题与处置

问题一：申请返回权限错误。回第 27 篇核对双配置（backgroundModes + KEEP_BACKGROUND_RUNNING）。问题二：申请成功，退后台几分钟后仍停。多为任务被系统判定"名实不符"（无声）或设备处于超级省电/后台限制模式；处置：确保任务期间始终有声，向用户说明系统级后台限制的处理入口。问题三：反复申请/取消抖动。快速暂停-播放循环里不要每次都走系统接口，做一个 30~60 秒的"滞回窗口"：短暂暂停保留任务（倒计时内恢复则不撤），超时才真正 stop，兼顾省电与体验。问题四：ctx 生命周期错配。用已销毁 ability 的 context 申请或取消会失败，播放服务应持有当前活跃 ability 的 context，或在 onWindowStageCreate 时刷新引用。问题五：把长时任务当保活手段用于非音频目的——审核红线，绝不可取。

## 四、长时任务检查清单

- [ ] 申请时机在"确认出声后"，取消时机在"确认停声后"，两侧对称。
- [ ] start/stop 做成幂等封装，running 状态自持，避免并发重复调用。
- [ ] 申请失败有降级与用户提示路径，不阻塞前台播放。
- [ ] 暂停-恢复抖动场景启用滞回窗口，超时才真正撤销。
- [ ] context 与承载播放的 ability 对应，ability 生命周期变化时刷新。
- [ ] 耗电测试：后台静置与后台播放两条曲线分开测量并达标。

长时任务解决了"后台活着"，下一篇的 WantAgent 决定点击任务通知时的归宿，把后台用户引回应用。
