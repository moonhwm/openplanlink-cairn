# 38 · 音频打断事件模型：InterruptType / ForceType / Hint 深度解析

> 一句话摘要：打断事件由"类型（开始/结束）× 强制度（系统已执行/建议执行）× 提示（具体动作）"三个维度构成，六种 Hint 与两段式 START/END 时序的组合穷举出应用需要处理的全部局面。

## 一、三个维度的语义

`InterruptEvent`（AVPlayer 侧为 `AudioInterrupt` 结构）的三个字段各管一件事。`eventType: InterruptType`——事件处于抢占生命周期的哪一段：`INTERRUPT_START` 表示焦点被拿走的开始时刻，`INTERRUPT_END` 表示对方归还、本实例重新获得焦点的结束时刻。`forceType: InterruptForceType`——动作的执行主体：`INTERRUPT_FORCE` 表示系统已经在音频服务层替你执行了（例如已直接停流），应用要做的是状态同步与 UI 呈现；`INTERRUPT_SHARE` 表示系统不强制执行，把动作权交给应用，应用必须自行调用 pause/setVolume，否则出现双声混播——这是最容易被忽略的分支。`hintType: InterruptHint`——建议的具体动作：`INTERRUPT_HINT_PAUSE`（暂停）、`INTERRUPT_HINT_RESUME`（恢复）、`INTERRUPT_HINT_STOP`（停止，通常无恢复）、`INTERRUPT_HINT_DUCK`（压低音量让路）、`INTERRUPT_HINT_UNDUCK`（恢复音量）、`INTERRUPT_HINT_NONE`（无动作，仅通知）。

## 二、组合决策矩阵

| eventType | forceType | hintType | 应用应做 |
|---|---|---|---|
| START | FORCE | PAUSE | 系统已停流：同步UI为暂停、标记"可自动恢复"、撤后台任务 |
| START | SHARE | PAUSE | 自行调 pause()，其余同上 |
| START | SHARE | DUCK | 自行 setVolume(低值)，**保持播放** |
| START | FORCE | DUCK | 系统已压低：记录原音量、UI不变 |
| START | 任意 | STOP | 终止播放会话：收尾三层资源（播放器/任务/会话） |
| END | SHARE | RESUME | 可自行 play()（若此前的暂停是被动且未被用户改写） |
| END | FORCE | RESUME | 系统已恢复流：同步UI为播放中 |
| END | SHARE | UNDUCK | 自行 setVolume(原值) |
| END | 任意 | NONE | 通常忽略；防御性同步一次状态即可 |

## 三、时序细节与防御性处理

两段式时序的隐含约束：RESUME/UNDUCK 只会出现在此前收到过 PAUSE/DUCK 的实例上，但间隔可能极长（一通电话 40 分钟），期间用户可能已手动操作过。因此处理器的第一原则是**区分"被动暂停"与"主动暂停"**：收到 START+PAUSE 时置 `interrupted=true`；用户随后主动 play 则清掉该标志（用户已表态，事后迟到的 RESUME 不得再生效）；用户主动 pause 时同样清除（该暂停是用户意志，恢复提示无效）。第二原则是**配对记账**：DUCK 记录压低前的音量原值，UNDUCK 恢复该原值而不是硬编码 1.0（用户可能本来就设了 0.6）。第三原则是**防御乱序**：中断回调可能与应用命令竞态（用户恰在打断瞬间点播放），所有状态迁移做条件校验（当前状态不符则忽略），并允许 NONE 事件触发一次轻量状态对账。第四原则是**联动出口齐全**：任何暂停/停止都要同步第 26 篇的三层（UI、AVSession、长时任务），漏一层就是一类线上缺陷。

## 四、事件模型检查清单

- [ ] 处理器覆盖矩阵全部九类组合，SHARE 分支显式执行动作。
- [ ] 被动/主动暂停标志在用户操作时更新，迟到的 RESUME 不劫持。
- [ ] DUCK/UNDUCK 记账原音量，恢复原值而非常量。
- [ ] STOP 触发三层收尾；长打断后的 RESUME 按业务决定是否续播。
- [ ] 状态迁移全部条件校验，乱序/竞态下幂等安全。
- [ ] 单元测试以矩阵为用例表，模拟器注入事件序列回归。

把这张矩阵内化后，任何打断行为都可以被"哪个维度、什么组合"快速定位，第 39/40 篇分别展开混音与压低两个高频专题。
