# 22 · AudioRenderer 音频打断与焦点响应

> 一句话摘要：AudioRenderer 通过 `setAudioInterruptMode` 声明焦点参与方式、通过 `on('audioInterrupt')` 接收仲裁结果，实时链路（游戏/VoIP）对打断的处理策略与音乐类应用显著不同，关键在"恢复的自主权"决策。

## 一、注册模型与 AVPlayer 的异同

AudioRenderer 与 AVPlayer 共用同一套打断事件模型：先声明模式（`renderer.setAudioInterruptMode(audio.InterruptMode.INDEPENDENT_MODE)` 独占 / `SHARE_MODE` 共享），再注册 `renderer.on('audioInterrupt', (event: audio.InterruptEvent) => {})` 接收回调。`InterruptEvent` 结构包含 `eventType`（START/END）、`forceType`（FORCE/SHARE）、`hintType`（PAUSE/RESUME/STOP/DUCK/UNDUCK/NONE）。差异在于使用姿态：AVPlayer 场景的打断处理以"暂停并等待恢复提示"为主；AudioRenderer 常承载实时会话与交互反馈，策略谱系更宽——VoIP 来电时整个会话让位并可能永久结束，游戏背景总线被抢时降音量而不中断，返听链路甚至不注册独占模式。模式选择详见第 37/39 篇，本篇聚焦事件处理。

## 二、实时链路的打断处理器

```typescript
export class RtInterruptHandler {
  private wasPausedByInterrupt = false;

  bind(r: audio.AudioRenderer, bus: {
    onPause(): void; onResume(): void; onDuck(on: boolean): void;
  }) {
    r.setAudioInterruptMode(audio.InterruptMode.INDEPENDENT_MODE);
    r.on('audioInterrupt', (ev: audio.InterruptEvent) => {
      // FORCE：系统已动作，只做状态同步；SHARE：需自行执行
      const needAct = ev.forceType === audio.InterruptForceType.INTERRUPT_SHARE;
      switch (ev.hintType) {
        case audio.InterruptHint.INTERRUPT_HINT_PAUSE:
          this.wasPausedByInterrupt = true;
          if (needAct) r.pause();
          bus.onPause();                       // 停止生产，防止队列积压
          break;
        case audio.InterruptHint.INTERRUPT_HINT_RESUME:
          if (this.wasPausedByInterrupt) {
            if (needAct) r.start();
            bus.onResume();                    // 恢复生产并flush旧数据（见第18篇）
            this.wasPausedByInterrupt = false;
          }
          break;
        case audio.InterruptHint.INTERRUPT_HINT_DUCK:
          if (needAct) r.setVolume(0.2);
          bus.onDuck(true); break;
        case audio.InterruptHint.INTERRUPT_HINT_UNDUCK:
          if (needAct) r.setVolume(1.0);
          bus.onDuck(false); break;
        case audio.InterruptHint.INTERRUPT_HINT_STOP:
          bus.onPause(); this.teardownSession(); break;   // VoIP：会话级收尾
        default: break;
      }
    });
  }
}
```

## 三、实时链路的特殊决策

第一，生产与消费联动。打断暂停 renderer 的同时必须暂停上游生产（停解码、停拉流、停合成），否则恢复时队列里堆满过期数据；恢复后 VoIP 类应先 flush 再续新帧，音乐类则可续播缓冲。第二，恢复自主权。RESUME 提示只代表"焦点回来了"，是否立刻恢复由业务决定：游戏中若用户已切到别的界面则不自动恢复；K 歌返听被打断后应回到待触发状态而非自动重唱。第三，会话级收尾。STOP 类提示（如对方是通话且策略判定不再恢复）对应的是整个会话的退出流程：停生产、release renderer、更新 UI 与信令状态，不要只停音频留一个僵尸会话。第四，与设备事件协同：耳机拔出在部分设备上以打断事件出现、部分以路由事件出现，两条通道都要订阅并做去重（第 36 篇）。第五，多 renderer 场景（游戏音乐总线+音效总线）每条都要独立注册处理，且策略一致，避免"音乐停了、枪声还在响"的割裂。

## 四、打断响应检查清单

- [ ] 模式显式声明（INDEPENDENT/SHARE），不依赖默认值。
- [ ] FORCE/SHARE 分支处理：FORCE 只同步状态，SHARE 必须自行执行动作。
- [ ] 打断暂停联动上游生产；恢复按业务选择 flush 旧数据或续播。
- [ ] RESUME 不等于必须恢复：用户主动暂停的会话不被自动劫持。
- [ ] STOP 触发会话级收尾，不留僵尸 renderer 与僵尸信令。
- [ ] 多总线分别注册且策略一致；与设备路由事件去重。

AudioRenderer 的焦点处理与 AVPlayer 共享一套系统仲裁，理解了本篇，第 37~40 篇的焦点总论就有了两个视角互证。
