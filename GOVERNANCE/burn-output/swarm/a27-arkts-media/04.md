# 04 · AVPlayer 播放控制：play / pause / stop / seek 全解析

> 一句话摘要：四类基础控制 API 各自只在合法状态下生效且均为异步操作，seek 的结果必须以 `seekDone` 事件确认，stop 与 pause 的资源语义差异决定了它们的使用边界。

## 一、play 与 pause 的异步语义

`play()` 与 `pause()` 返回 Promise，调用成功仅代表"命令已受理"，真正的状态变化要等 `stateChange` 事件回调到 `playing` 或 `paused`。这一设计在快速连续点击（连按暂停/播放按钮）时非常关键：如果业务层在 Promise resolve 后立刻更新 UI 的播放按钮，会出现与真实状态短暂不一致。推荐做法是把"播放中/已暂停"的唯一事实源放在 stateChange 事件上，UI 按钮状态从事件流派生，按钮点击只负责发出 play/pause 命令，这样无论命令来自界面、通知栏 AVSession 还是耳机线控，UI 都不会漂移。另外 `completed` 态调用 `play()` 会从头开始播放，这是列表循环逻辑（非 loop 模式下手动接歌）的天然入口，`on('stateChange')` 收到 completed 即可切下一首。

## 二、stop 与 pause 的资源语义差异

`pause()` 保留解码器与缓冲数据，恢复播放几乎零开销，适合一切临时性停顿；`stop()` 则回收解码器等大部分资源，实例回到 stopped 态，恢复播放必须重新 `prepare()`（代价接近重新初始化）。因此切歌、退出播放页、长时任务取消等"确定性不再继续播"的场景才使用 stop；短暂的 UI 跳转、音频焦点被抢占（对方结束后需要恢复）一律用 pause。stop 之后换源的正规路径是再调 `reset()` 回 idle 重新设源；若确定实例不再复用，直接 `release()` 一步到位，避免"stop 后忘记 reset"导致的僵尸实例。此外注意 `stop()` 在 prepared/paused/playing/completed 均可调，但 idle/initialized 态调用属于非法状态。

## 三、seek 的模式选择与结果确认

`seek(timeMs, mode?)` 用于跳转进度，合法状态为 playing、paused 与 completed。seek 是异步且可能跳到"最近关键帧"的操作，参数二可选 `media.SeekMode`：`SEEK_PREV_SYNC`（跳到目标时间之前的最近同步帧，默认值）、`SEEK_NEXT_SYNC`（之后最近同步帧）、`SEEK_CLOSEST_SYNC`（最近同步帧）、`SEEK_EXACT`（精确到目标时间，可能需要更多解码耗时）。短视频拖进度条用 `SEEK_PREV_SYNC` 响应最快；音频类或歌词逐字对齐场景建议 `SEEK_EXACT`。seek 发起后不要立刻读 `currentTime`，应以 `on('seekDone')` 回调为准刷新 UI，并在连续拖拽时做去抖（例如拖拽中只记录目标值，松手才真正 seek），避免指令排队造成画面抖动。

```typescript
avPlayer.on('seekDone', (doneMs: number) => {
  this.currentTime = doneMs;      // 唯一可信的落点
  this.sliderDragging = false;
});

onSliderChange(targetMs: number, fromUser: boolean) {
  if (!fromUser || this.avPlayer?.state !== 'playing') return;
  // 拖拽去抖：仅松手提交，模式按业务选择
  this.debounce(() => this.avPlayer!.seek(targetMs, media.SeekMode.SEEK_EXACT), 200);
}
```

## 四、控制操作检查清单

- [ ] 播放/暂停按钮状态唯一来源是 `stateChange` 事件，不来自命令调用返回值。
- [ ] `pause()` 后立即 `seek()` 合法，可用于"暂停态拖动预览"。
- [ ] `stop()` 后如需继续播，必须重新 `prepare()`；换源走 `reset()`。
- [ ] completed 态处理列表推进：收到 completed 即预取下一首并切换。
- [ ] 连续 seek 做去抖，UI 进度以 `seekDone` 为准，配合 `timeUpdate` 平滑自走。
- [ ] 每个控制调用都包 try/catch 并区分"非法状态"（忽略）与"真实错误"（上抛）。

把这四个 API 的状态约束与异步语义固化成统一的 PlayerService 方法（play/pause/toggle/seekTo/stopAll），是第 45 篇统一架构的地基。

## 五、实战问答与易错点

**问一：连点播放/暂停按钮出现状态错乱怎么办？** 根因是把"命令"当"状态"用。正确模型：按钮点击只发命令（play 或 pause），播放状态由 stateChange 事件唯一维护；连点时可以做命令合并（在途命令未完成前，新命令覆盖队列），最终以事件回流的最后一个状态刷新 UI。进阶做法是在服务层加"命令序号"，事件回写时携带触发它的序号，旧命令的迟到回执直接丢弃，这样即使快速交替点击也能收敛到正确终态。

**问二：pause() 之后再 play()，为什么偶尔从头播？** 检查是否在 pause 后误走了 stop 或 reset 路径：stop 后必须重新 prepare，而部分封装把 prepare 后的首次 play 实现为从头开始。另一个可能是播放已自然到达 completed，completed 态调 play 语义就是重播，这不是 bug 而是设计；若产品想要"续播到结尾就停"，应在 completed 分支显式维持 UI 的终态而不暴露 play 语义。区分这两种情形的方法是在封装层记录"上一次状态迁移路径"，排障时一眼可见。

**问三：seek 精度为什么有时差一两秒？** 取决于 SeekMode 与内容关键帧间隔。SEEK_PREV_SYNC/NEXT_SYNC 会落到同步帧，偏差上限是一个 GOP 长度（编码端常设 1~4 秒）。需要精确的场景（歌词逐字、教育复读）用 SEEK_EXACT，但要做好耗时预期：解码器需要从上一关键帧解到目标帧，长 GOP 高码率内容可能需要数百毫秒。产品策略可以是"拖拽先用 SYNC 快速响应、停稳后后台再 EXACT 校准"，兼顾手感与精度。

**问四：stop 与 release 之间还要做什么？** 完整序列是 stop → （如需复用）reset → 再次 prepare，或 stop → release 直接终结。stop 之后实例仍占用少量资源（会话、监听），忘记 release 就是泄漏起点（第 12 篇）。常见封装错误是把 stop 当成"安全的中性状态"长期停放实例——不如要么 pause 保活（要快速恢复），要么 release 干净（不播就别占），长期 stopped 停放是最差选择。

**问五：timeUpdate 的回调频率可以调吗？** 回调节奏由系统决定（通常秒级或百毫秒级），应用无法直接配置，能做的是消费侧节流：进度条刷新合并到 500ms 粒度，后台时进一步降频或暂停刷新。高倍速播放时 timeUpdate 步进变大，进度平滑要靠"事件校正 + 帧间插值"实现：收到回调时校准锚点，渲染帧之间按 elapsed×speed 外推，这与第 32 篇 AVSession 的外推机制是同一思想。
