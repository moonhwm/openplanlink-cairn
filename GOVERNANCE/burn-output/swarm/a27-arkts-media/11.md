# 11 · AVPlayer 错误处理、状态恢复与 reset 实践

> 一句话摘要：AVPlayer 的错误以 `on('error')` 事件与 error 态双通道出现，恢复路径只有 reset 与 release 两条，按错误族分类处置并保留断点是播放稳定性的最后防线。

## 一、错误的两条通道与终局状态

AVPlayer 的错误通知有两条并行通道：其一是 `on('error', (err) => {})` 事件回调，携带 `code` 与 `message`；其二是状态机本身进入 `error` 态（通过 stateChange 事件可观察）。关键纪律是：**一旦进入 error 态，实例只接受 `reset()` 与 `release()` 两个调用**，任何 play/seek/setVolume 都会二次抛错。error 态内部又细分可恢复与否：文件不存在、格式不支持、解码器资源耗尽等多为"当前源不可用"，reset 换源后实例仍可复用；而内部服务异常、进程级音频服务断连等严重错误，稳妥做法是 release 后整体重建。错误码区间参考：201 族为权限问题；5400101~5400106 族覆盖内存、状态、参数、编解码、格式、资源等媒体错误类别（具体映射以官方错误码表为准，不要在代码里硬编码数值，应记录日志透传）。

## 二、错误分类处置与断点恢复模式

工程化的处理方式是"分类—处置—恢复"三步：先按错误特征归类，再选择重试或上抛，最后在恢复时保留用户断点。示例：

```typescript
type ErrFamily = 'network' | 'format' | 'state' | 'fatal';

function classify(code: number, msg: string): ErrFamily {
  if (msg.includes('network') || msg.includes('timeout')) return 'network';
  if (msg.includes('format') || msg.includes('unsupported')) return 'format';
  if (code === 5400102) return 'state';     // 非法状态：多为时序问题
  return 'fatal';
}

async onError(av: media.AVPlayer, err: { code: number; message: string },
              ctx: { url: string; positionMs: number }) {
  const family = classify(err.code, err.message);
  hilog.error(0x0, 'Player', `err=${err.code} family=${family}`);
  if (family === 'network' && this.retry < 2) {
    this.retry++;
    const pos = av.currentTime ?? ctx.positionMs;   // 记住断点
    await av.reset();                                // 唯一合法动作之一
    av.url = ctx.url;                                // 重新设源
    av.on('stateChange', async (s) => {
      if (s === 'prepared') {
        await av.play();
        await av.seek(pos, media.SeekMode.SEEK_EXACT);  // 回到断点
      }
    });
  } else {
    await av.release();                              // 兜底释放
    this.reportToUI(family);
  }
}
```

## 三、reset 的正确姿势与三个高频坑

`reset()` 的语义是"清空数据源与配置、回到 idle"，是换源复用实例的正道。坑一：reset 只回状态不清监听。旧实例上按播放项注册的临时监听（如 per-item 的 seekDone 闭包）若不 off，会在复用后串台执行，建议"临时监听用完即 off"或采用一次性守卫标志。坑二：reset 与异步命令竞态。在 play() 的 Promise 还未 resolve 时立刻 reset，部分版本会先回调 stateChange 的中间态，状态分发逻辑必须幂等（同一状态多次回调不产生副作用）。坑三：错误发生时 currentTime 可能已不可信，断点应以最后一次 `timeUpdate` 缓存的值为准，因此播放器封装里应常驻一个"最近进度"字段，每秒更新，错误恢复直接取用。此外，预加载实例池（第 13 篇）中的闲置实例发生错误时，正确动作是直接 release 并重建，不要带病入池。

## 四、错误治理检查清单

- [ ] 所有异步播放 API 调用都包 try/catch，catch 中区分"非法状态忽略"与"真错误上抛"。
- [ ] error 态后仅走 reset/release；重试次数有限（建议 ≤2）并指数退避。
- [ ] 断点来自常驻的最近进度缓存，而非错误时刻的 currentTime。
- [ ] 错误日志带 code/message/源 URL 特征（不含敏感信息），便于离线归因。
- [ ] 临时监听用后 off；reset 后重新注册或用守卫保证幂等。
- [ ] 连续失败后向用户给出可行动提示（检查网络/格式不支持/稍后再试），而非静默失败。

错误处理是"最后一公里"的工程，它决定应用在真实网络与真实文件面前是"偶尔卡住"还是"稳定可用"，其收敛形态见第 46 篇异常兜底专题。
