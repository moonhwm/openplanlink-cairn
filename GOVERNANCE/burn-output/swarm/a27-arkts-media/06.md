# 06 · AVPlayer 音量、静音与声道控制

> 一句话摘要：AVPlayer 层的 `setVolume` 只作用于单个播放实例且范围 0~1，它与系统流音量、AudioRenderer 音量分属三个不同层级，混用层级是音频类应用最高频的缺陷来源。

## 一、三层音量模型必须分清

HarmonyOS 音频体系中的"音量"至少有三个互不替代的层级。第一层是**系统流音量**：由音频服务按流类型（STREAM_MUSIC、STREAM_VOICE_CALL 等）统一管理，用户按物理音量键或控制中心滑条改变的就是它，应用只读或跟随，不应试图独占；第二层是**播放器实例音量**：`avPlayer.setVolume(vol)` 的效果只叠加在本实例输出上，典型取值 0.0~1.0，0 等效于该实例静音，不影响其他应用也不影响系统音量；第三层是**内容增益**：源文件本身的响度（或解码前的增益处理），通常由内容生产端控制。业务上"调节音量"应默认映射到系统流音量（跟随用户习惯），只有"画中画副声道压低""混音场景中背景乐让位人声"这类多实例内部平衡需求才用实例音量。

## 二、setVolume 的行为细节

`setVolume(volume: number)` 在 prepared 及之后的播放相关状态均可调用，取值小于 0 或大于 1 会报参数错误，系统自动做越界钳制与否不可依赖、应自行 clamp。音量变化通过 `on('volumeChange')` 事件确认。两个高频用法：其一，"先淡出再切歌"——用定时器在 300~500ms 内把音量从当前值线性降到 0，再执行切源，可消除硬切爆音；其二，"双实例混音"（背景音乐用 AVPlayer、提示音用 AudioRenderer）时，把背景乐实例临时降到 0.2，实现应用内 ducking。注意实例音量在 `stop()`/`reset()` 后的保持行为没有跨实例承诺，切歌后应显式恢复业务期望值（如 1.0），否则用户会遇到"下一首突然没声音"的问题。

```typescript
// 淡出切歌：线性降音量后换源
async fadeOutThenSwitch(nextUrl: string, steps = 10, stepMs = 30) {
  const p = this.avPlayer!;
  for (let i = steps; i >= 0; i--) {
    await p.setVolume(i / steps);
    await new Promise(r => setTimeout(r, stepMs));
  }
  await p.reset();               // 回 idle
  p.url = nextUrl;               // 换源
  p.on('stateChange', async (s) => {
    if (s === 'prepared') {
      await p.setVolume(1);      // 恢复业务音量，避免“下一首无声”
      await p.play();
    }
  });
}
```

## 三、静音策略与声道处理

静音有两条实现路径：实例级 `setVolume(0)` 与系统级静音开关。实例级静音适合"关闭视频原声、改配音轨"场景：视频教育类应用切换到配音音轨时先把原声音量归零可以避免轨间串音；系统级静音（用户按静音开关）则属于设备状态，应用应通过焦点与响铃模式事件感知（第 44 篇展开）。声道层面，AVPlayer 本身不提供"只播左/右声道"的接口，立体声内容的单边播放需要：优先切到单声道音轨（配合第 9 篇轨道管理）；或在必须 PCM 级处理时改用 AudioRenderer 写入时自行抽声道（第 19 篇）。外接设备（仅左声道的单边音箱、车载音频）场景，通过音频路由层的设备能力查询确认物理声道布局，比在播放层强行处理更稳妥。

## 四、音量控制检查清单

- [ ] 用户可见的音量滑条绑定系统流音量（AudioVolumeManager），不用实例音量冒充。
- [ ] `setVolume` 参数自行 clamp 到 [0,1]，不依赖系统钳制。
- [ ] 音量 UI 状态以 `volumeChange` 事件回写；切歌/reset 后恢复业务音量。
- [ ] 淡入淡出统一封装为工具函数，切歌、打断恢复（UNDUCK 回升）复用。
- [ ] 双实例混音时背景乐实例音量写入持久化偏好，尊重用户上次设置。
- [ ] 系统音量变化时同步 UI 图标（监听 volumeChange 系统事件，见第 43 篇）。

音量分层模型同样适用于 AudioRenderer（它有同名 setVolume），把"层级归属"想清楚，绝大多数"音量不生效/影响别人"的问题都能就地定位。

## 五、实战问答与易错点

**问一：setVolume(0.5) 后感觉只降了一点？** 主观响度与线性音量不是一回事：人耳对响度的感知近似对数，0.5 的线性值在听感上只降了约一档。产品上做"柔和压低"时选 0.2 左右更接近直觉；做音量滑条映射时应用感知曲线（平方或对数映射）而不是线性直连。另外确认没有把实例音量与系统流音量的预期搞混——系统侧没动，整体响度还受用户当前媒体音量控制。

**问二：淡出切歌为什么有时还是有一点爆音？** 检查两个细节：淡出的最后一步是否真的到 0（循环边界条件写错停在 0.1 就会残留可闻残响）；切源动作是否发生在音量到 0 之后（时序上应为最后一步 setVolume(0) 的 Promise 完成后再 reset）。有些设备音频通路的直流偏置也会造成轻微爆破，此时在 0 与静音之外再补一个极短停顿（30~50ms）可以掩盖。

**问三：双实例混音时哪个该被压低？** 原则是"持续内容让位于瞬时信息"：背景乐是持续内容、提示音是瞬时信息，所以压背景乐（0.2 左右）保提示音满音量。两个都是持续内容（音乐+白噪音）时按用户显式设置的类别比例平衡，并各自持久化。应用内 ducking 与系统焦点 DUCK（第 40 篇）要统一进同一个"音量管理器"：应用内压低发生时，系统 UNDUCK 的恢复值应是"应用内当前业务音量"而不是 1.0，两层记账串联而不是各管各的。

**问四：拔耳机后音量变得特别大？** 这是设备通道增益差异叠加的结果：耳机通道与扬声器通道的响度曲线不同，同一音量值在扬声器上主观更响（或更轻）。系统侧通常有通道间音量记忆，应用不该也无法干预通道增益；能做的是产品预期管理：外放前如果是"拔耳机自动续播"场景，建议默认暂停（第 36 篇）而非续播，用户手动恢复时对响度有心理准备。

**问五：音量状态要不要持久化？** 要，但分层持久化：系统流音量不需要应用存（系统自己记）；实例音量中的"用户偏好"（背景乐/音效比例）跟随账号或本地偏好存储；临时性压低（duck 中）绝不持久化。常见事故是把 duck 中的低音量存进了偏好，用户下次进入应用发现声音奇小——duck 状态必须与会话同生命周期，恢复/退出时强制回到记账原值。
