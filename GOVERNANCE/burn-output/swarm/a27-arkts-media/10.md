# 10 · AVPlayer audioInterrupt 打断事件处理

> 一句话摘要：AVPlayer 通过 `audioInterrupt` 事件接收系统焦点仲裁结果，按 `hintType` 分支执行暂停、恢复、停止、压低/恢复音量，并把结果同步给 UI 与 AVSession，是"多应用共存"场景的核心纪律。

## 一、为什么必须在播放器上处理打断

手机上永远有多个应用想发声：来电、导航播报、语音助手、闹钟、其他音乐应用。系统音频服务按流用途与焦点策略统一仲裁，仲裁结果以打断事件下发到每个相关播放器。AVPlayer 默认工作在"独立模式"（`audio.InterruptMode.INDEPENDENT_MODE`）下：当更高优先级的流（如来电）启动时，系统会**强制**暂停音乐；对方结束后，又会下发恢复提示。如果应用不监听 `audioInterrupt`，后果是：被抢占暂停后永远无法自动恢复（用户感知为"音乐莫名停了"）、UI 播放按钮与真实状态脱节、后台长时任务与播放状态不一致导致任务被系统质疑甚至回收。因此打断处理不是可选项，而是音乐类应用的功能完备性底线。

## 二、事件结构与标准处理分支

`avPlayer.on('audioInterrupt', (info: audio.AudioInterrupt) => {})` 的回调结构包含三组信息：`eventType`（打断开始 `INTERRUPT_START` / 结束 `INTERRUPT_END`）、`forceType`（系统已强制执行 `FORCE` / 需应用自行处理 `SHARE`）、`hintType`（建议动作：暂停、恢复、停止、压低音量、恢复音量、无）。标准处理是按 hint 分支并同步全部状态出口：

```typescript
import { audio } from '@kit.AudioKit';
import { media } from '@kit.MediaKit';

export function registerInterrupt(p: media.AVPlayer, sync: {
  onPaused: () => void; onResumed: () => void; muted: (m: boolean) => void;
}) {
  p.audioInterruptMode = audio.InterruptMode.INDEPENDENT_MODE;

  p.on('audioInterrupt', (info: audio.AudioInterrupt) => {
    switch (info.hintType) {
      case audio.InterruptHint.INTERRUPT_HINT_PAUSE:
        p.pause();                      // 对方开始抢占：暂停并记录“可恢复”
        this.resumable = true;
        sync.onPaused();
        break;
      case audio.InterruptHint.INTERRUPT_HINT_RESUME:
        if (this.resumable) { p.play(); this.resumable = false; }
        sync.onResumed();
        break;
      case audio.InterruptHint.INTERRUPT_HINT_STOP:
        p.stop(); this.resumable = false; sync.onPaused();
        break;
      case audio.InterruptHint.INTERRUPT_HINT_DUCK:
        p.setVolume(0.2); sync.muted(true);   // 导航播报类：压低让路
        break;
      case audio.InterruptHint.INTERRUPT_HINT_UNDUCK:
        p.setVolume(1.0); sync.muted(false);
        break;
      case audio.InterruptHint.INTERRUPT_HINT_NONE:
      default:
        break;
    }
  });
}
```

## 三、关键语义细节与常见错误

第一，"可恢复"标志必须有业务判断：来电结束后系统下发 RESUME 提示，但若用户在通话期间主动按了暂停，则不应自动恢复——所以要在用户主动暂停时把 `resumable` 置 false。第二，FORCE 与 SHARE 的区别在于"系统是否已经替你做了"：FORCE 型暂停后播放器已处于 paused，应用要做的是同步 UI；SHARE 型则要求应用自行执行 pause/volume 动作，未执行将出现双声混播。第三，打断处理要与后台任务联动：持续被打断（STOP 或长时间 PAUSE）时应取消音频长时任务（第 28 篇），否则"无声却保持后台"会被系统视为滥用。第四，AVSession 状态必须同步：焦点导致的暂停也要 `setAVPlaybackState(PAUSE)`，否则锁屏控件仍显示播放中。第五，混音类应用（游戏音效、跑步提示音）应评估改用 SHARE 模式或 AudioRenderer 的共享策略（第 37、39 篇），从源头减少打断。

## 四、打断处理检查清单

- [ ] 注册 `audioInterrupt` 于 prepared 前完成；`audioInterruptMode` 显式声明。
- [ ] RESUME 仅在"被动暂停"时自动恢复，用户主动暂停不劫持。
- [ ] DUCK/UNDUCK 成对实现，压低值与恢复值统一常量管理。
- [ ] 打断暂停同步三处：UI 状态、AVSession playbackState、后台任务。
- [ ] 来电场景真机验证；耳机拔出类设备事件与打断事件分别处理（第 36 篇）。
- [ ] 打断风暴（连续多次 START/END）做去抖，避免播放状态抖动。

打断处理做扎实后，应用才能在真实多应用环境里"有礼貌地发声"，这也是第 45 篇统一 PlayerService 必须内置的横切逻辑。
