# 42 · 音频路由切换：扬声器/听筒/蓝牙/耳机切换实践

> 一句话摘要：媒体流路由跟随系统策略由设备接入自动决定，应用可控的切换点是通话类流的通信设备（`setCommunicationDevice`），听筒/扬声器切换是 VoIP 场景刚需，而"替用户改媒体路由"是应当避免的越权设计。

## 一、两类路由权：媒体流与通信流

路由决策权分两条线。媒体线（音乐/视频/游戏）：跟随系统默认路由——插入耳机自动切耳机、连上蓝牙自动走 A2DP、全部拔掉回落扬声器；应用原则上不干预，只感知与提示（第 41 篇），系统设置与控制中心才是用户的合法切换入口。通信线（VOICE_COMMUNICATION 用途的通话流）：走独立的通信设备通道，应用可通过 `AudioRoutingManager.setCommunicationDevice(type, active)` 在听筒与扬声器（以及蓝牙 SCO 等，按版本支持）之间显式切换，这是 VoIP 应用"免提"按钮的实现基础。两条线的分离意味着：给音乐做"切换到扬声器"按钮基本是伪需求（应引导用户用系统入口）；给通话做听筒/扬声器切换是真需求且有官方接口。

## 二、通话免提切换实现

```typescript
import { audio } from '@kit.AudioKit';

export class CallRoute {
  private routing = audio.getAudioManager().getRoutingManager();
  private speakerOn = false;

  async toggleSpeaker(): Promise<boolean> {
    this.speakerOn = !this.speakerOn;
    // 通信设备开关：SPEAKER=扬声器（免提开）；关闭后回落听筒
    const ok = await this.routing.setCommunicationDevice(
      audio.CommunicationDeviceType.SPEAKER, this.speakerOn);
    if (!ok) { this.speakerOn = !this.speakerOn; return false; }   // 失败回滚UI态
    return this.speakerOn;
  }

  async toEarpiece(): Promise<void> {
    if (this.speakerOn) {
      await this.routing.setCommunicationDevice(
        audio.CommunicationDeviceType.SPEAKER, false);
      this.speakerOn = false;
    }
  }

  isSpeakerOn(): boolean { return this.speakerOn; }
}
```

## 三、切换实践的场景细节

场景一：VoIP 免提。切换瞬间通话流重建通路，可能伴随数百毫秒音频空档，UI 不必遮罩，但回声消除链路要重新收敛（远端可能短暂听到回声，属正常收敛过程）。场景二：听筒与蓝牙耳机。通话接通时若蓝牙耳机在线，通信流可能默认走蓝牙，用户点"免提"语义应解释为"切扬声器"，再点回"切回之前的设备"——所以免提状态机要记录"免提前设备"而不只是布尔值。场景三：媒体流的"伪切换"需求。确有产品要在应用内直接选择媒体输出（多房间音箱类），此时应评估系统能力是否开放对应接口；未开放时，正确做法是引导用户到控制中心的输出选择器，而不是寻找旁门。场景四：车载与外接声卡。USB/车载连接后媒体自动路由过去，拔出瞬间回扬声器——这个"突外放"瞬间由第 36 篇的拔出暂停策略兜底，两条机制必须同时在场。

## 四、路由切换检查清单

- [ ] 免提按钮基于 setCommunicationDevice 实现，失败回滚 UI 状态。
- [ ] 免提状态记录"免提前设备"，支持蓝牙→免提→原设备的完整回路。
- [ ] 媒体流不做越权切换，输出选择引导系统入口。
- [ ] 切换空档不遮罩 UI；远端回声收敛期做用户预期管理。
- [ ] 拔出回落扬声器的场景与第 36 篇暂停策略联动验证。
- [ ] 真机矩阵：听筒、扬声器、蓝牙通话（SCO）、车载各路径过一遍。
