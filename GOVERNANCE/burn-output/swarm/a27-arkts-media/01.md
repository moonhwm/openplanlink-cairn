# 01 · AVPlayer 整体架构与状态机详解

> 一句话摘要：AVPlayer 是 HarmonyOS Media Kit 提供的高层音视频播放器，其核心是一套受严格迁移规则约束的状态机，理解状态与合法迁移是正确使用一切播放能力的前提。

## 一、AVPlayer 在媒体体系中的定位

在 HarmonyOS 的 ArkTS 应用开发中，`@ohos.multimedia.media`（新工程中通常通过 `@kit.MediaKit` 引入）向外暴露了两类播放原子能力：一是面向"成品媒体文件"的 AVPlayer，二是面向"裸 PCM 数据"的 AudioRenderer。AVPlayer 内部完成了数据源接入、解封装（demux）、解码（decode）、音频输出与视频渲染的完整链路封装，开发者只需要喂给它一个 URL、一个文件描述符或一段元数据，就能得到与系统音频服务、焦点管理、渲染管线完全打通的播放实例。正因为链路长、内部资源多（解码器、Surface、音频流），AVPlayer 被设计成一个显式状态机：任何 API 只在特定状态下调用才合法，越界调用会抛出 `5400102` 一类的"非法状态"错误，甚至直接把实例打入 error 态。

## 二、状态机的九个状态与合法迁移

AVPlayer 的完整状态集合为：`idle`（已创建未配置）、`initialized`（已设置数据源）、`prepared`（资源就绪可播）、`playing`（播放中）、`paused`（暂停）、`completed`（自然播完）、`stopped`（已停止，资源部分回收）、`released`（已释放，终态）、`error`（错误态）。关键迁移规则如下：`createAVPlayer()` 成功后处于 idle；在 idle 态设置 `url` 或 `fdSrc` 后自动进入 initialized；`prepare()` 只能在 initialized 态调用；视频播放必须在 prepared 之前完成 `surfaceId` 的绑定；`play()`/`pause()` 在 prepared、playing、paused、completed 之间迁移；`stop()` 之后若要复用实例必须重新 `prepare()`；`reset()` 可以从多数非释放态回到 idle 换数据源；`release()` 是不可逆终态，任何异常兜底最终都应走向 release。开发者务必通过 `on('stateChange')` 事件驱动逻辑，而不是"调用后立刻假设状态已变"。

## 三、事件驱动骨架与错误监听

下面是一段最小可用骨架，展示了以状态机为中心组织播放逻辑的推荐写法，所有业务动作都被收敛到 stateChange 回调分支中，保证时序正确：

```typescript
import { media } from '@kit.MediaKit';

export class SimplePlayer {
  private avPlayer?: media.AVPlayer;

  async setup(url: string) {
    this.avPlayer = await media.createAVPlayer();
    this.avPlayer.on('stateChange', async (state: string) => {
      switch (state) {
        case 'idle':          // 刚创建/重置：此时才允许设置数据源
          this.avPlayer!.url = url;
          break;
        case 'initialized':   // 数据源已就绪：发起 prepare
          await this.avPlayer!.prepare();
          break;
        case 'prepared':      // 解封装/解码器就绪：可播
          await this.avPlayer!.play();
          break;
        case 'stopped':       // 停止后资源需重prepare才能复用
          await this.avPlayer!.release();
          this.avPlayer = undefined;
          break;
        default:
          break;
      }
    });
    this.avPlayer.on('error', (err) => {
      // 进入error态后仅可reset或release，禁止继续播放调用
      console.error(`AVPlayer error code=${err.code} msg=${err.message}`);
    });
  }
}
```

## 四、状态机使用检查清单

- 创建后处于 idle，此时才允许设置 `url`/`fdSrc`，其余状态设置会报错。
- `surfaceId` 必须在 prepared 态（play 之前）绑定，晚绑定导致黑屏。
- `seek()` 在 playing/paused/completed 均可调，结果以 `seekDone` 事件为准，不要同步读取 `currentTime`。
- `stop()` 后想换歌应走 `reset()` 回 idle，而不是直接改 url。
- error 态后只允许 `reset()` 或 `release()`，任何 play/seek 都会二次报错。
- 页面销毁路径中必须 release 并解除全部 `on` 监听，防止闭包持有导致泄漏。

掌握状态机之后，后续所有专题（seek 精度、轨道切换、打断恢复）本质上都是"在正确状态下做正确动作"这一原则在不同场景下的展开。

## 五、实战问答与易错点

**问一：调用 play() 后立刻读 currentTime 为什么经常是 0？** currentTime 反映的是状态机推进后的结果，play 命令受理到真正进入 playing 之间有调度延迟，解码首帧尚未渲染时位置自然停在起点。正确姿势是在 stateChange 回调到 playing 之后、或依赖 timeUpdate 事件首次触发再读取。同理，seek 后同步读 currentTime 拿到的是旧值，只有 seekDone 回调参数才是可信落点。凡是"命令后立刻读状态"的写法，都应改为"事件回写状态"，这也是状态机思维与命令式思维的分水岭。

**问二：prepared 和 completed 我都没主动触发，它们从哪来？** prepared 是 prepare() 完成的回调态，completed 是播放到文件末尾时系统自动进入的态，两者都不是应用主动调用的方法名。新手常犯的错误是把 completed 当错误处理（以为播放"卡住了"），或者反过来在 completed 里不做任何事导致列表无法推进。规范做法：completed 是播放列表推进的信号源，收到后立即触发"下一首"逻辑（预加载实例接管或 reset 换源），同时把 UI 的播放按钮复位为可播放状态。

**问三：同一份数据源，为什么有时 initialized 态瞬间就到，有时很久？** url 设置成功即进入 initialized，这一步只做数据源登记所以快；差异通常出在网络可达性上。本地 fd 几乎瞬时，网络源则受 DNS、握手影响，若观察到 initialized 都很慢，应排查网络权限与代理环境而不是播放器本身。真正耗时的 prepare 阶段（建流、探测格式、建解码器）对网络源还叠加首包缓冲，这正是第 3 篇要给初始化加超时兜底的原因。

**问四：reset 之后监听还在吗？状态监听会不会重复触发？** reset 清空的是数据源与部分配置，事件监听默认保留，这是复用实例的前提也是串台风险的来源：如果按播放项注册了带闭包的临时监听（比如引用了当前列表项的 seekDone），复用实例后旧闭包仍会执行。工程对策有两种：临时监听用完立即 off；或注册常驻监听、在回调里通过当前上下文对象取值而不是闭包捕获。状态分发逻辑还必须幂等——同一状态因内部迁移被报告两次时不产生副作用，这是第 45 篇统一服务能稳定运行的基础约束。

**问五：error 态之后还能救回来吗？** 可以，但只有两条路：reset() 回 idle 重新设源（适合数据源类错误），或 release() 彻底销毁（适合严重错误或确定不再使用）。判断标准看错误族（第 46 篇分类学）：网络、文件类错误 reset 后换源或重试通常可恢复；解码器资源耗尽类先释放其他实例再重建；状态类错误（非法调用）本质是自家时序缺陷，运行期忽略该命令并打点，代码层修复才是根治。
