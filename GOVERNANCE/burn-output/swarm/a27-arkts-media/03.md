# 03 · AVPlayer 网络播放与缓冲管理（bufferingUpdate）

> 一句话摘要：网络播放的体验由缓冲事件驱动，AVPlayer 通过 `bufferingUpdate` 事件暴露缓冲开始、结束、百分比与已缓存时长，业务层据此刷新 UI 并实施超时与重试兜底。

## 一、网络数据源与权限前置

AVPlayer 对 HTTP/HTTPS/HLS（m3u8 及其分片）提供原生支持，`url` 直接赋值完整的网络地址即可，HLS 会由内部播放服务完成切片调度与自适应码率处理。前置条件有两项：`module.json5` 中声明 `ohos.permission.INTERNET`；若播放明文 HTTP，还需要在 network 安全策略中允许明文传输（HTTPS 是默认要求），否则请求会被系统安全策略拦截并表现为 201 或网络类错误。网络播放与本地播放最大的差异在于"就绪"不再是瞬时事件：prepared 只代表首帧数据可达、解码器已建立，后续播放过程中仍可能因为带宽波动反复进入缓冲，因此网络场景必须实现缓冲事件监听与 UI 反馈闭环。

## 二、bufferingUpdate 事件模型

`on('bufferingUpdate', (infoType, value) => {})` 回调携带两个参数：`infoType` 标识缓冲信息类别，`value` 为对应数值。常用类别包括：`BUFFERING_BEGIN`（开始缓冲，value 无意义）、`BUFFERING_END`（缓冲结束）、`BUFFERING_PERCENT`（缓冲进度百分比 0~100）、`BUFFERING_CACHED_DURATION`（已缓存内容可播时长，毫秒）、`BUFFERING_PLAYRATE`（当前播放速率基准）。典型处理策略：收到 BEGIN 时在界面上展示加载态并暂停进度条自走；收到 END 恢复；收到 PERCENT/CACHED_DURATION 刷新缓冲条；将 CACHED_DURATION 与 `duration` 相除可估算"可拖拽的安全区间"，用于限制 seek 范围提示。

## 三、缓冲驱动的播放器封装示例

```typescript
import { media } from '@kit.MediaKit';

export class NetworkPlayer {
  private avPlayer?: media.AVPlayer;
  private buffering = false;

  watchBuffering(player: media.AVPlayer, ui: {
    showLoading: (on: boolean) => void;
    onCache: (percent: number, cachedMs: number) => void;
  }) {
    player.on('bufferingUpdate', (infoType: media.BufferingInfoType, value: number) => {
      switch (infoType) {
        case media.BufferingInfoType.BUFFERING_BEGIN:
          this.buffering = true;
          ui.showLoading(true);            // 转圈，冻结进度条
          break;
        case media.BufferingInfoType.BUFFERING_END:
          this.buffering = false;
          ui.showLoading(false);
          break;
        case media.BufferingInfoType.BUFFERING_PERCENT:
        case media.BufferingInfoType.BUFFERING_CACHED_DURATION:
          ui.onCache(
            infoType === media.BufferingInfoType.BUFFERING_PERCENT ? value : -1,
            infoType === media.BufferingInfoType.BUFFERING_CACHED_DURATION ? value : -1
          );
          break;
        default:
          break;
      }
    });
  }
}
```

## 四、弱网兜底与重试策略清单

- [ ] 初始化超时兜底：从设置 url 到 prepared 超过 10~15 秒即 `reset()` 后重试一次，仍失败则上抛错误并展示可点击重试的 UI。
- [ ] 播放中 error 且错误信息含网络类特征时，保留当前进度，重试后 `seek()` 回断点。
- [ ] HLS 弱网下优先在服务端提供多码率，客户端避免自行切换清晰度重建实例。
- [ ] 缓冲 UI 必须与 `bufferingUpdate` 严格对齐，禁止用 `timeUpdate` 停顿来"猜"缓冲。
- [ ] 后台播放（配合长时任务）时缓冲回调照常触发，但应降低 UI 刷新频率以省电。
- [ ] 记录 CACHED_DURATION 用于断点续播：下次启动直接 seek 到已缓存位置可显著提速。

缓存与预取也可在业务层实现：在 Wi-Fi 场景提前把下一集下载到沙箱再以 fd 方式播放，是短视频与播客类应用常见的提速手段，此时网络播放退化为本地播放，稳定性反而更高。

## 五、实战问答与易错点

**问一：BUFFERING_BEGIN 频繁出现，是代码问题还是网络问题？** 先做归因切分：本地源几乎不会触发缓冲事件，所以频繁 BEGIN 基本是网络吞吐跟不上消费速率。客户端能做的有三件事：与内容侧确认码率是否适配目标网络（高码率在弱网必然反复缓冲）、把缓冲 UI 与 BEGIN/END 严格对齐避免"假加载"、在产品层提供"省流模式"降低码率。把每次 BEGIN/END 的时间戳与间隔记录成埋点，能画出用户真实的卡顿画像，这是说服内容侧调码率的依据。

**问二：缓冲百分比和已缓存时长有什么用，进度条该用哪个？** 两者视角不同：PERCENT 是缓冲进度的直观展示，适合加载圈上的百分比；CACHED_DURATION 是可操作的语义数据，用于限制 seek 范围（未缓存区域拖过去必然长等待）与估算断点续播收益。进度条的缓冲底色建议用 CACHED_DURATION/duration 计算，因为它与时间轴同单位、天然对齐；PERCENT 与时长的映射关系在不同实现里有差异，不适合精确画缓冲条。

**问三：seek 到未缓冲区域后一直转圈怎么办？** 这是弱网下最常见的体验塌陷点。处理组合：seek 前用 CACHED_DURATION 判断目标点是否在已缓存区间，区间外给出轻提示（"正在缓冲，可稍候或返回已缓冲区域"）；seek 后进入 BEGIN 时保留用户的目标位置展示（"目标 xx:xx 缓冲中"）而不是退回原进度；超过应用自定的缓冲超时（如 15 秒）后提供"返回原位置"的快捷按钮。这些细节决定了弱网用户对应用的忍耐度。

**问四：弱网重试为什么建议保留断点 seek 而不是从头播？** 用户体验上，重试后从头播等于把失败成本翻倍，用户流失率高。技术上实现并不复杂：错误发生时用常驻的最近进度缓存（每秒 timeUpdate 更新）记录位置，reset 换源成功后 seek 回该位置。要注意 seek 到的位置可能已不在缓冲内，会再次触发缓冲流程，所以重试与缓冲提示要联动设计。重试次数仍要受限（两次为佳），避免在持续断网环境下空耗电量与流量。

**问五：后台播放时缓冲回调还需要处理吗？** 需要，但要降级处理。后台期间 bufferingUpdate 照常触发，UI 不可见时刷新界面是纯浪费，应通过前后台状态判断把回调处理切成两档：前台更新完整 UI，后台只记录数据与维持必要状态（如断点缓存）。若缓冲长时间不恢复且应用在后台，结合长时任务的"名实相符"原则（第 28 篇），长时间无声的任务要考虑撤销，等网络恢复由用户重新发起。
