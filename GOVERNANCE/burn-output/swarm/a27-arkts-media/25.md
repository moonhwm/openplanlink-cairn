# 25 · AVPlayer 与 AudioRenderer 选型对比与混合使用

> 一句话摘要：两套播放原子能力按"输入形态、时延要求、实时性、视频需求"四个维度选型，复杂应用采用"AVPlayer 承载内容流 + AudioRenderer 承载实时层"的双通道混合架构并显式声明各自焦点模式。

## 一、决策维度与选型表

| 维度 | 问句 | 指向 |
|---|---|---|
| 输入形态 | 数据是成品媒体文件/网络流，还是应用持有的 PCM？ | 文件流→AVPlayer；PCM→AudioRenderer |
| 解码责任 | 愿意自己管解封装、解码、seek 语义吗？ | 不愿意→AVPlayer |
| 时延要求 | 端到端需要几十毫秒级吗？ | 是→AudioRenderer 低时延模式 |
| 视频画面 | 需要视频渲染吗？ | 是→AVPlayer（AudioRenderer 无视频） |
| 实时合成 | 声音由算法/网络实时产生吗？ | 是→AudioRenderer 回调供数 |
| 进度语义 | 需要文件级 seek/倍速/轨道切换吗？ | 是→AVPlayer |

典型映射：音乐/视频/播客播放器→AVPlayer；游戏音效总线、K 歌混响返听、VoIP、TTS 流式输出、录音监听→AudioRenderer；"边看视频边聊天"→视频 AVPlayer + 通话 AudioRenderer。

## 二、混合架构的组成与规则

以音乐游戏（背景音乐 + 实时打击音效）为例的标准混合架构：

```typescript
export class DualBusAudio {
  private music?: media.AVPlayer;          // 内容总线：BGM
  private sfx?: audio.AudioRenderer;       // 实时总线：音效

  async start(path: string) {
    // 总线一：AVPlayer，独立模式，接收完整焦点仲裁
    this.music = await media.createAVPlayer();
    this.music.audioInterruptMode = audio.InterruptMode.INDEPENDENT_MODE;
    this.music.url = path;
    this.music.on('stateChange', async s => {
      if (s === 'initialized') await this.music!.prepare();
      if (s === 'prepared') await this.music!.play();
    });

    // 总线二：AudioRenderer，低时延回调供数
    this.sfx = await audio.createAudioRenderer({
      streamInfo: { samplingRate: audio.AudioSamplingRate.SAMPLE_RATE_48000,
        channels: audio.AudioChannel.CHANNEL_2,
        sampleFormat: audio.AudioSampleFormat.SAMPLE_FORMAT_S16LE,
        encodingType: audio.AudioEncodingType.ENCODING_TYPE_PCM },
      rendererInfo: { usage: audio.StreamUsage.STREAM_USAGE_GAME, rendererFlags: 1 }
    });
    this.sfx.on('writeData', b => this.fillSfx(b));   // 命中即合成
    await this.sfx.start();
  }
}
```

混合规则有四条。规则一，职责不越界：长内容、可 seek、带元数据的一律走 AVPlayer；短促、合成、实时的走 AudioRenderer，禁止"用 AudioRenderer 自己解码播整首歌"这类高成本低收益设计。规则二，焦点声明分层：两条总线各自 `setAudioInterruptMode`；若产品允许音效与背景乐共存，统一策略后各自处理 audioInterrupt，避免一边暂停一边继续的割裂感。规则三，音量体系单一：实例音量分属两总线独立设置（BGM 0.8、SFX 1.0 由用户偏好驱动），但对外呈现的"媒体音量"仍跟系统流，UI 不区分两条总线。规则四，生命周期解耦又联动：页面退出时两条总线都要收尾；后台切换时按产品决定（游戏退后台通常双停，音乐类只保 AVPlayer + 后台任务）。

## 三、迁移与退路设计

实践中会出现"先做错再迁移"的情况：最初用 AudioRenderer 自解码播歌，后来迁移到 AVPlayer。设计退路的方式是把"播放会话"抽象为接口（play/pause/seek/getDuration/事件流），两套实现各挂一层适配器，业务层只依赖接口——这正是第 45 篇 PlayerService 的雏形。迁移期以开关灰度两实现并跑，对比进度偏差、打断恢复正确率、耗电指标后切流。反向退路同样存在：AVPlayer 对某冷门格式不支持时，可评估"自解码 + AudioRenderer"兜底，但要先量化工作量，多数情况下"提示格式不支持"是更便宜的答案（第 46 篇）。

## 四、双通道治理检查清单

- [ ] 每条播放链路有明确的选型依据记录，接口抽象屏蔽实现差异。
- [ ] 两总线焦点模式与打断策略成文并一致，联动场景真机验证。
- [ ] 音量偏好分总线持久化；系统音量跟随不分流。
- [ ] 后台/前台切换策略明确（双停或单保），与后台任务申请对齐。
- [ ] 资源收尾模板覆盖两套 API（off→stop→release 等价序列）。
- [ ] 迁移开关灰度运行，对比质量指标后再切流。
