# 单智能体与多智能体系统的边界

## 一、边界问题为何重要

"要不要上多智能体"是工程上被过度肯定的问题。很多系统在单智能体加良好工具调用就能解决的场景里,引入了五六个角色和一套消息总线,结果是延迟上升、调试难度翻倍、失败面扩大。反过来,也有系统把本该并行的检索硬塞进一个长上下文,导致窗口溢出与注意力稀释。划定单/多边界,是所有编排决策的前置问题。

## 二、留在单智能体一侧的判据

满足以下任一判据,优先考虑单智能体(配合工具调用与结构化输出):

- 任务的自然粒度是"一段连续推理",中间产物不需要被独立复用;
- 子步骤之间的信息传递量极大,拆开会导致每个智能体都要重读一遍完整上下文;
- 延迟预算紧张,多智能体间网络往返与排队开销不可接受;
- 团队尚无多智能体可观测性基础设施,出了问题只能靠肉眼看日志。

单智能体优化路径同样有章法:工具清单化、输出结构化、系统提示分节、上下文分级加载。这些手段常常能把表面上"需要多角色"的任务压回单体内完成。

## 三、越界到多智能体一侧的判据

以下信号出现两条以上,值得开始多智能体化:

1. 系统提示已经出现明显的"角色切换"段落,且不同段落的工具集互不重叠;
2. 不同子任务的上下文需求差异大,合并加载造成 token 成本与注意力双浪费;
3. 需要并行(多路检索、多视角生成),串行执行无法满足延迟要求;
4. 需要制衡(生成者不能自己验收自己的产出),单体内无法形成独立视角;
5. 子任务失败需要独立重试,整体重放代价过高。

## 四、边界的量化参考

给出一组经验阈值作为讨论起点,数值应结合自身模型与任务校准:

```text
上下文占比:  单轮对话有效信息占比 < 30% 时考虑拆分
工具数量:    单智能体挂载工具 > 15 个时按域拆分
并行度需求:  独立子任务数 >= 3 且互不依赖时启用扇出
迭代深度:    预期修订轮数 >= 2 时才引入评审环
角色寿命:    一个"角色"存活超过一次完整会话才值得独立成体
```

## 五、过渡形态:体内多角色

在单与多之间存在过渡形态——同一个智能体内用提示词定义多个"子角色",按阶段切换。它保留单进程的调试便利,又获得部分视角分离收益。代价是子角色之间没有真正的信息隔离,上下文污染会随轮次累积。工程上可作为试点:先用体内多角色验证拆分是否有效,有效再固化成真正的多智能体边界,无效则退回,沉没成本最小。

## 六、边界漂移的监控

边界不是一次性划定。建议在系统里埋两类计数:其一,单智能体路径的失败中有多大比例源于"上下文过长"或"角色混淆";其二,多智能体路径的开销中有多大比例来自消息序列化与重复上下文。前者持续走高说明该拆未拆,后者持续走高说明拆得过细。把这两个指标放进运维面板,边界决策就从争论变成数据。

## 七、边界决策的文档化模板

单多边界的每次调整都值得花十分钟文档化,推荐固定模板:调整日期、调整对象(哪个环节从单改多或从多改单)、触发数据(引用监控指标而非体感)、预期改善、回退条件。模板的关键字段是回退条件——事先写明"若四周内指标无改善则回退",能防止沉没成本谬误让错误的拆分无限存活。

边界文档应与架构图联动维护。架构图上每个智能体节点标注其边界版本号,节点的新增、合并、拆分都有对应的边界文档编号。当新人问"为什么检索和摘要分成两个体"时,能按编号取出当时的决策依据,而不是依赖某位老员工的记忆。

跨环节的边界一致性也要定期检查。常见的不一致:上游拆成三个执行者,下游聚合器却按单一产物的格式写解析;或者环内修订者期望完整上下文,边界却把上下文切给了评审者。每季度做一次边界对齐评审,沿数据流走一遍,核对每条边两侧的假设是否仍然成立。

最后,把边界决策纳入回放验证:对历史任务分别用调整前后的边界跑一遍,对比质量与成本。没有回放支撑的边界调整,本质上是在生产环境做实验;有了回放,边界决策就从经验判断升级为受控实验,团队对系统的把握感也随之升级。

## 八、边界决策的责任归属

边界调整容易陷入"人人可提议、无人愿拍板"的困境,必须明确责任归属:单体内部的角色切换由功能负责人决定,单多边界的跨越由模块负责人提议、架构组裁决,跨模块的拆分合并由架构组主持专项评审。责任层级与影响半径对齐,是边界治理的第一原则。

边界决策的信息基础要制度化:单体侧的监控指标(上下文占用、角色混淆失败、工具过载)与多体侧的开销指标(消息序列化、重复上下文)按周汇总成"边界仪表盘"。提议任何调整的人,先引用仪表盘数据说明动机;裁决者依据同一份数据判断。数据同源避免"各说各话"的评审僵局。

新人培养也要围绕边界意识展开:入职培训必含一节"本系统的边界地图",讲清每个多体拆分的来由与代价。理解边界来由的工程师在修改代码时才不会无意中破坏契约——多数边界侵蚀不是蓄意,是无知,而培训是无知最便宜的解药。

最后,把边界变更纳入年度架构回顾:一年内所有调整的清单、效果兑现情况、未兑现的原因分析。回顾的产出指导下一年的边界路线,让这项工作从零散救火变成有方向感的长期经营。
