# 循环终止条件设计

## 一、终止条件是循环的灵魂

迭代类编排模式(评审环、反思环、黑板收敛)的第一设计问题不是"怎么循环",而是"何时停止"。终止条件缺失或含糊的循环有两种下场:永远不满足条件而烧穿预算,或条件形同虚设而过早放行劣质产物。终止条件本质上是质量与成本的交换函数,必须显式设计、显式配置、显式记录。

## 二、四类终止条件

成熟的循环系统同时配备四类条件,任一触发即停:

1. **达标终止**:产物满足全部阻断级标准、重要级标准缺陷数低于阈值。这是唯一的质量出口;
2. **上限终止**:轮数、总调用数、总 token、总耗时任一触顶。这是成本兜底出口;
3. **无进展终止**:连续若干轮产物与评审意见没有实质变化。这是止损出口;
4. **外部终止**:用户取消、上游超时、系统停机广播。这是环境出口。

四类条件的重要性排序是:达标 > 无进展 > 上限 > 外部。无进展排在上限之前,是因为它通常先于上限出现且信息量更大——提前识别能省下注定无效的剩余轮次。

## 三、无进展的量化判定

"没有实质变化"必须量化,推荐两个可组合的指标:

- **产物稳定度**:相邻两轮产物的语义相似度(嵌入余弦)超过高阈值,判定停滞;注意区分"收敛到好答案"与"收敛到坏答案",停滞时必须回看最近一次评审是否通过,通过则是正常收敛;
- **缺陷重叠度**:本轮评审意见与上一轮的重叠比例超过阈值(如八成),说明能修的已修完,剩余缺陷是修不动的硬骨头。

```python
def should_stop(state) -> StopDecision:
    if state.all_blocking_resolved:
        return Stop("accept")                     # 达标
    if state.round >= MAX_ROUNDS:
        return Stop("cap")                        # 上限
    sim = cosine(state.embed[-1], state.embed[-2])
    overlap = jaccard(state.defects[-1], state.defects[-2])
    if sim > 0.95 and overlap > 0.8:
        return Stop("stall")                      # 无进展
    return Continue()
```

## 四、出口状态的分级表达

停止不是二值的成功/失败,出口状态应分级并传递给下游:

- **accept**:达标放行,正常质量;
- **accept_with_caveats**:触上限但有可用产物,输出必须附缺陷清单与未解决问题;
- **stall_reject**:无进展且不达标,返回最佳一轮产物加"已无法自动改进"标记,建议升级人工;
- **abort**:外部终止,清理现场,不留半成品。

下游对 accept_with_caveats 的处理逻辑必须与 accept 不同(至少要展示限定语),否则分级失去意义。

## 五、参数校准方法

终止参数(阈值、轮数上限)的校准流程:取一批带标准答案的历史任务,回放跑不同参数组合,记录质量-成本曲线;在曲线上找"质量增益陡降点"作为参数推荐值;上线后按月用新样本复校。切忌把轮数上限当成质量旋钮无限调大——多数情况下瓶颈在评审标准或修订能力,不在轮数。

## 六、常见反模式

- **单一上限条件**:只有轮数上限没有质量出口,循环沦为固定跑满 N 轮的流水线;
- **软条件硬凑**:达标条件写成"评审者满意",不可机械核对,实际永远由上限兜底;
- **停止即丢弃**:触上限后丢弃全部产物从零失败,而正确动作是回收最佳一轮;
- **终止不留痕**:出口原因不记录,事后无法区分"质量达标"与"预算耗尽",统计质量时两者混为一谈,数据失真。

终止条件的最终检验标准:任意一次循环结束后,仅凭落盘的终止记录,就能回答"为什么在这里停"以及"如果不停还值不值得继续"这两个问题。

## 七、终止条件的配置管理

终止条件的四类谓词要全部配置化,与代码分离,变更走评审。配置项包括:达标条件引用的标尺条款与阈值、无进展判定的相似度与重叠度参数、各类上限的数值、出口状态的降级文案模板。配置带上"变更历史",每次调整记录动机与回看日期。

上线后的首要观察是"出口原因分布":健康系统的达标出口应占多数,上限出口次之,无进展与外部合计不超过两成。达标占比持续低于一半,先怀疑标尺过严或修订能力不足,而不是调参数;上限占比畸高且质量不达标,才考虑放宽轮数——放宽前必须确认缺陷在递减,否则加轮只是加钱。

无进展检测的参数要按任务类型分别校准:相似度阈值对文本类任务与代码类任务的合理值差异很大,统一阈值会让某类任务永远触发不了无进展(或总是误触发)。校准方法:取历史已收敛任务的相邻轮产物计算相似度分布,取分布右侧安全分位为阈值。

一个运维细节:出口状态的统计口径要与用户反馈对齐。定期抽样"accept 出口"的产物做人工复核,若人工不认可率上升,说明达标条件已被绕过或标尺失真——出口条件是质量闸门,闸门本身也需要被检验。

## 八、终止体系的压力设计

终止条件在极端压力下的行为要专门设计:当系统整体降载(见降级机制)时,各循环的终止参数应有联动降档——全局过载时轮数上限自动减半、达标阈值适度放松,让循环快速出清而不是占着资源慢慢磨。终止体系的弹性是系统过载自保的一环,孤立设计的终止条件会在压力时刻成为资源钉子户。

反向压力同样存在:流量低谷期任务稀少,循环可以更宽容(轮数上限放宽,追求质量)。低谷宽、高峰严的双档终止参数,让系统在质量与吞吐间的倾斜随负载呼吸,而不是一条死线管全天。双档切换的判据与冷却期参照负载分档的通用设计。

终止体系的逃生通道:任何循环都保留外部强制终止的接口(运维指令、用户取消),强制终止走的收尾路径与自然终止相同(回收最佳轮、生成保留意见、释放资源)。逃生通道不常走,但它的存在性本身就是设计承诺——一个无法从外部叫停的循环,无论参数多精密,都是潜在的失控源。

压力设计的验收靠极限演练:全系统满载下抽查循环行为,断言终止联动生效;强制终止风暴演练(批量取消),断言收尾路径不因并发而劣化。压力下的终止体系,才是真正被验证过的终止体系。
