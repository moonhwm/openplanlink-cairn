# 上下文管理与 token 预算

## 一、上下文是稀缺资源

多智能体系统里,token 消耗的大头往往不是生成,而是上下文的反复装载:每个角色每次调用都要带任务背景、历史产物、角色指令。扇出宽度乘以循环轮数再乘以背景长度,消耗按乘法膨胀。上下文管理(context engineering)因此成为多智能体工程的独立学科:决定"每次调用看到什么",本质是在分配系统里最贵的稀缺资源——注意力窗口。

## 二、上下文的分层装载

推荐四层结构,按"稳定性"从高到低组织:

```text
L1 角色层:   角色定义、输出契约、风格约束
             (极少变化,可缓存前缀)
L2 任务层:   本次任务的目标、约束、验收标准
             (任务级稳定)
L3 状态层:   协作进展:已完成部分、评审意见、黑板摘要
             (每轮变化, 需要压缩与筛选)
L4 参考层:   证据、检索结果、外部材料
             (体积最大, 按需注入)
```

分层的工程意义在于复用与淘汰:L1 用提示缓存摊薄成本;L3 是压缩的主战场(历史轮次摘要化);L4 严格按当前步骤的需要注入,与步骤无关的材料不带。

## 三、状态层的压缩策略

循环与黑板产生的中间状态最容易失控,压缩三板斧:

1. **摘要化**:历史评审意见只保留"未解决项 + 已解决项清单",逐字记录只存档不进上下文;
2. **选择性遗忘**:与当前步骤无关的分支探索,压缩为一行结论("X 路已排除,理由 Y"),细节留档备查;
3. **窗口滚动**:保留最近两轮的完整状态,更早轮次递降为要点,形成近详远略的滚动窗口。

压缩的纪律:被压缩的内容必须可按需展开(存档加指针),压缩只影响"默认可见性",不影响"可追溯性"。

## 四、预算的分配与执行

token 预算是硬约束,要有分配表与执行器:

```python
@dataclass
class TokenBudget:
    total: int                    # 任务总预算
    reserve: int                  # 收尾与格式化保留
    def grant(self, role: str, purpose: str) -> int:
        return self._alloc[(role, purpose)]

def assemble_context(task, budget):
    ctx = LayeredContext()
    ctx.add_role_layer()                       # L1 固定
    ctx.add_task_layer(task)                   # L2 固定
    ctx.add_state(compress(task.history,
                           cap=budget.grant("state")))
    ctx.add_refs(select(task.evidence,
                        cap=budget.grant("refs")))
    assert ctx.tokens <= budget.total - budget.reserve
    return ctx
```

预算超限时的裁剪顺序要预定义:先裁参考层(换更少但更相关的证据),再压状态层(更激进的摘要),角色层与任务层不动——砍掉任务约束省下的 token,会以产出跑偏的形式加倍偿还。

## 五、上下文污染的防治

上下文不是越多越好,无关内容稀释注意力,甚至诱导角色漂移。防治:证据按相关度排序注入,超阈值截断;不同角色的上下文隔离(评审者不看生成者的辩解,见裁判解耦一章);长会话定期"重置装载"——把累积状态压缩为干净的任务简报,重新开窗,防止历史噪声无限累积。

## 六、验收指标

上下文管理的三个核心指标:token 利用率(产出 token / 装载 token,衡量装载有效性)、上下文命中率(注入的参考材料实际被产出引用的比例,衡量选择相关性)、压缩损伤率(压缩前后任务完成质量的差值,用回放集测量,划定压缩的安全边界)。三者联合优化,警惕单一指标导向——盲目提高利用率而牺牲命中率,是省了 token 赔了质量。

## 七、上下文管理的评审制度

上下文管理要形成评审制度,三类评审定期举行:新任务的上下文设计评审(装载什么、压缩什么、预算多少)、存量任务的上下文审计(实际装载与设计偏离度、token 利用率趋势)、压缩策略评审(各级压缩的安全边界是否仍然成立)。

审计的量化基础是装载日志:每次调用的四层装载量、实际产出中被引用的参考材料、压缩前后任务的完成质量。日志聚合成"上下文账本",账本暴露的典型问题:参考层装载持续膨胀(选择算法的相关性阈值失守)、状态层压缩过度(历史轮次的关键约束被压掉,产物反复违反早已提出的要求)、角色层重复展开(缓存配置失效,前缀每次重算)。

压缩损伤的定期回放:选取压缩前后的同批任务,对比完成质量,损伤率超出安全边界的压缩档收紧。压缩是省钱的手段,损伤率是它的价格标签——不看价格的压缩,省下的 token 会以质量事故的形式加倍偿还。

上下文评审的最后一项是"污染源排查":定期抽检高产出的调用上下文,寻找与任务无关的渗入内容(上游角色的辩解、无关分支的历史、被遗忘的调试指令)。污染的清除比装载的优化更立竿见影——很多质量问题的根源,是上下文里混进了不该在场的东西。

## 八、上下文的资产化管理

上下文管理的高级形态是把高质量上下文当资产管理:沉淀"上下文组件库"——经过验证的任务背景模板、角色定义、输出契约示例,组件化存储与版本管理,新任务组装时从库里取件而非每次手写。组件库的复用带来一致性(同类任务的装载结构稳定)与效率(组装成本摊薄)。

组件的质量门槛:被三个以上任务使用且无负面反馈的上下文块才有入库资格;入库块标注适用场景、维护人、效果数据(使用该组件的任务质量对比);劣化的组件(模型升级后效果下降)及时下架迭代。门槛保证组件库的每一件都是被验证过的,而不是听起来有道理的。

上下文的计量收费机制是进阶治理:各角色按装载量"付费"(从任务预算扣减),促使装载方自觉瘦身——当上下文有价格,免费堆料的习惯自然收敛。计量不必真实结算,虚拟账单的约束力已足够,重要的是让每个组装动作都看到价格标签。

资产化年度盘点:组件库的规模、复用率、质量趋势;上下文成本的构成变化(组件复用带来的成本下降曲线);自产上下文(未用组件的临时装载)的占比演化。资产化的目标是让上下文管理从个人手艺变成组织工艺——工艺的标志,是新手也能组装出合格水平的上下文。
