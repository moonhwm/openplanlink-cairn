# 编排模式选型决策树

## 一、选型错误的代价

编排模式选错不会立刻报错,而是在运行几周后以隐性方式暴露:本该用黑板的系统被写成巨型顺序流水线,任何新增能力都要改主干代码;本该单轮扇出的场景被套上评审环,延迟翻三倍而质量毫无变化。选型问题本质是"用结构换什么"的问题——用结构换吞吐、换质量、换灵活性,三者不可兼得,决策树就是把取舍显性化的工具。

## 二、五问决策树

按顺序回答五个问题,即可走到初始模式。问题的顺序有讲究:越靠前的问题越接近业务本质,越靠后越接近工程细节,先定大结构再定小机制。

```text
Q1 任务能否在派发前被完整分解为互不依赖的子任务?
    能,且子任务结果可机械合并      -> 起点选 [扇出聚合]
    不能,需边执行边发现结构        -> 起点选 [蜂群黑板]
    能分解,但每步质量依赖上一步    -> 起点选 [规划-评审环]

Q2 输出是否存在客观可核对的标准(测试、清单、事实约束)?
    存在且可自动化核对             -> 评审可自动化,允许长循环
    存在但只能主观判断             -> 引入 [裁判席] 承担评价
    不存在                        -> 缩短循环,改为人工抽检出口

Q3 多个执行者结果冲突时谁说了算?
    有权威第三方标准               -> 裁判席单裁
    无权威标准但可多数决           -> 裁判席合议(多数投票)
    冲突罕见且可并列呈现           -> 聚合器直接并列输出

Q4 单次完整执行的成本上限是多少?
    成本敏感(如面向高频入口)     -> 限制扇出宽度与循环轮数
    延迟敏感                       -> 优先并行,牺牲迭代深度
    质量优先(如离线生成)         -> 允许多轮环+多裁判合议

Q5 失败是否可重试、重试是否幂等?
    可重试且幂等                   -> 节点级自动重试
    不可幂等                       -> 环外人工介入,禁止自动重放
```

## 三、从起点模式到组合形态

决策树给出的是起点,不是终点。常见组合路径有三条:

- 扇出聚合 + 裁判席:并行执行者产出候选后,由裁判按评分细则挑选或排序,适合"生成 N 个方案选优"的场景。组合时注意裁判的评分细则必须先于执行者启动而确定,否则裁判会被执行者的输出风格带偏。
- 规划-评审环 + 裁判席:评审者只提意见不拍板,裁判掌握终止权。这一分工的价值在于评审意见可以宽松、发散,而裁决必须严格、可追溯,两种认知任务分离后各自的质量都更容易保证。
- 蜂群黑板 + 裁判席:黑板上的增量由各知识源自发写入,裁判定期检查黑板是否满足验收标准,满足即触发停机。这是"探索自由 + 收敛有据"的经典配对。

## 四、选型核对清单

在写第一行编排代码之前,过一遍以下清单,任何一项答不上来都说明选型尚未完成:

1. 每类参与者的输入输出契约是否已写成数据结构而非口头约定;
2. 循环的最大轮数、扇出的最大宽度是否已设硬上限;
3. 中间产物(计划、评审意见、黑板快照)是否可被外部系统读取;
4. 停机条件是"满足标准"还是"到达上限",两者都有时优先级如何;
5. 模式退化为单智能体路径的降级开关是否存在;
6. 新增一个执行者/评审者需要改动多少处代码,若超过一处则结构过紧。

## 五、反例速查

以下信号提示选型偏离,应及时回调:循环轮数上限从未被触发过,说明环是多余的;扇出结果高度雷同,说明分解维度选错了而非宽度不够;黑板长期无新写入,说明知识源调度条件过严;裁判结论与评审意见长期一致,说明裁判席可合并进评审角色。选型不是一次性活动,应随任务画像变化每季度复评一次。

## 六、选型评审会的组织方法

决策树的价值要靠组织流程兑现。建议把模式选型从个人判断改为结构化评审会:会前发起人填写决策树的五问答卷,附任务样本与延迟成本约束;会上由未参与设计的人主持逐问追问,重点质疑第一问(可分解性判断)——它是后续一切分支的根,根上含糊整棵树都不可靠。

评审会的输出不是"同意与否",而是一份选型记录:所选起点模式、组合形态、被否决的备选及否决理由、三个月后的复评指标。复评指标必须在会前想清楚,例如"引入评审环后缺陷率应下降四成,轮均成本不超过单轮的三倍"。三个月后用实测对照,达标则模式转正,不达标则按备选方案调整。

一个易被忽略的会议纪律:延迟与成本约束要写成数字进会议纪要。"要快一点"不构成约束,"P95 不超过八秒、单请求成本上限两角"才是。数字约束让后续的宽度、轮数、席位数等参数讨论有锚点,也防止上线后用模糊的体感反复推翻选型。

最后,决策树本身也要版本化。每次评审会发现某分支的判据不清或有遗漏,修订决策树并标注版本与修订原因。一年后回看决策树的演化史,能清晰看到团队对任务画像认识的深化轨迹,这份演化记录本身就是最有价值的架构文档。
