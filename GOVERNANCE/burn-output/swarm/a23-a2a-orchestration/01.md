# 多智能体编排模式总览与分类框架

## 一、为什么需要"编排模式"这个概念

当系统里只有一个智能体时,不存在编排问题:一条用户消息进来,一次模型调用,一个回答出去。一旦参与求解的智能体数量超过一个,立刻出现一组新的设计问题:任务如何拆分、结果如何合并、谁先谁后、冲突听谁的、中间状态放在哪里、失败在哪一层兜底。这些问题与具体模型无关、与具体业务也无关,它们是结构性的,因此值得抽象成一组可复用的"编排模式"。

"模式"一词借自建筑与软件工程传统:一个模式描述在特定约束下反复出现的问题与经过验证的解法骨架。多智能体编排模式的价值在于把隐性的架构经验显性化,使团队可以用统一词汇讨论"我们这里用的是扇出聚合还是规划-评审环",而不是每次都从零开始争论架构图。

本知识库将编排模式分为四大原语,后续四十七个子题目都是这四大原语的展开、组合与工程化:

- **扇出聚合(Fan-out / Aggregate)**:一个任务并行派发给多个执行者,结果汇聚成单一输出。解决的是吞吐、覆盖面与视角多样性。
- **规划-评审环(Plan / Review Loop)**:先产出方案,再对方案评审,依据评审意见修订,循环直至满足出口条件。解决的是质量与自我纠错。
- **裁判席(Referee / Judge)**:引入一个与执行者利益解耦的第三方角色,对争议或质量做出裁决。解决的是评价权分散导致的僵局。
- **蜂群黑板(Swarm Blackboard)**:多个智能体围绕一块共享的、可增量读写的工作区协作,无中央指挥,靠停机条件收敛。解决的是任务不可预先分解时的并行探索。

## 二、四原语的二维定位

可以用两个正交维度给四原语定位,这也是选型时的第一张地图:

- **控制流集中度**:从"中央编排器全程指挥"(扇出聚合、规划-评审环)到"去中心化自发协作"(蜂群黑板),裁判席居中,它只接管评价权,不接管执行权。
- **迭代性**:扇出聚合默认单轮(派发-汇聚各一次),规划-评审环与黑板天然多轮,裁判席可以是单次裁决也可以嵌入循环。

| 原语 | 控制流 | 典型轮次 | 核心假设 |
| --- | --- | --- | --- |
| 扇出聚合 | 集中 | 单轮 | 任务可独立并行分解 |
| 规划-评审环 | 集中 | 多轮 | 质量可通过迭代逼近 |
| 裁判席 | 评价集中、执行分散 | 单次或多轮 | 存在可操作的评价标准 |
| 蜂群黑板 | 分散 | 多轮 | 增量改进可收敛 |

## 三、模式的最小描述模板

每个模式条目建议用统一模板记录,便于跨团队对照。模板包含六个字段:

```text
模式名:        扇出聚合
问题:          需要在限定时间内覆盖多个独立子视角
结构:          派发器 -> N 个执行者 -> 聚合器
参与者:        派发器 / 执行者 / 聚合器
失效模式:      执行者超时 / 结果互相矛盾 / 成本爆炸
验证手段:      聚合前校验 + 聚合后抽检
```

## 四、分类框架的边界说明

四大原语并非互斥,真实系统几乎总是组合体。例如"检索增强生成"常见形态是:黑板沉淀检索到的证据(黑板),多个检索器并行取数(扇出),综合器草拟答案后进入评审循环(评审环),最后由一个按评分细则打分的裁判决定是否放行(裁判席)。分类框架的意义不是把系统塞进单一格子,而是保证讨论覆盖以下四个问题域时不遗漏:

1. 并行派发与结果合并归扇出聚合管;
2. 质量迭代与出口条件归规划-评审环管;
3. 争议裁决与评价校准归裁判席管;
4. 共享状态与自发协作归蜂群黑板管。

凡是一个多智能体系统的设计文档无法回答上述四问中任何一问,通常意味着该问域存在结构缺口,应在编码前补齐。后续子题目将按此框架逐一展开,每个子题目聚焦一个可独立决策的工程问题。

## 八、模式语言在团队中的维护

把四大原语变成团队资产,需要的不仅是理解,还有一套维护机制。建议由架构组维护一份"模式登记表",每个在用模式登记六个字段:模式名、适用场景、当前部署位置、责任人、已知失效案例、下次复评日期。登记表每季度复评一次,复评不看文档看数据——该模式上线后的质量增量、延迟与成本变化、故障记录。数据不支持的模式降级为"观察",连续两个观察期无改善的进入退役流程。

模式语言的第二项维护工作是案例化。每个模式至少沉淀三个真实案例:一个成功案例(什么条件下收益显著)、一个失败案例(什么条件下适得其反)、一个边界案例(条件略变结论就反转)。案例的存在让选型讨论有据可依,新人培训也以案例为教材而非抽象定义。

第三项是词汇纪律。会议与设计文档中使用的模式术语必须与登记表一致,禁止同义漂移——"并行分发""多路下发""scatter"若都指扇出聚合,统一用登记表名称。词汇统一看似小事,它决定跨团队沟通时架构信息的保真度。

最后要为模式语言留出演化通道。当实践中出现无法归入四原语的协作结构时,先按"组合形态"记录,积累足够样本后再判断是否提炼为第五原语。原语集合的稳定性来自克制——宁可让组合形态复杂一点,也不要轻易增加顶层概念,概念的通胀会让整个框架失去区分度。
