# 扇出聚合模式原理

## 一、模式定义

扇出聚合(Fan-out / Aggregate)是最基础的多智能体编排原语:编排器把一个任务拆成 N 个互不依赖的子任务,并行派发给多个执行者,等待全部或部分完成后,把结果合并为单一输出。它解决三类问题:吞吐(并行缩短墙钟时间)、覆盖(多视角减少盲区)、健壮(同题多答降低单点失误率)。

模式成立的前提是一条硬假设:子任务之间互不依赖。一旦存在依赖,并行派发就会产出基于过期信息的子结果,聚合阶段才发现矛盾,返工成本高于串行。因此扇出前的第一项工作不是选执行者,而是验证可分解性。

## 二、模式的四个角色

- **分解器(Splitter)**:输入原始任务,输出子任务列表,每个子任务带独立预算与验收口径;
- **派发器(Dispatcher)**:把子任务路由到执行者,管理并发度与超时;
- **执行者(Worker)**:彼此不可见,不共享中间状态,只对分到的子任务负责;
- **聚合器(Aggregator)**:按合并语义把 N 份结果变成一份,是模式中唯一定义"整体质量"的地方。

四个角色里聚合器最容易被轻视。实践中大量扇出系统失败在聚合:执行者质量很好,但聚合逻辑只是简单拼接,输出冗长且自相矛盾。聚合语义必须在设计期显式选定,不能运行时临时拼凑。

## 三、聚合语义的四种基本型

```text
拼接型:  结果按固定顺序连接,适合内容互补的分区任务
择优型:  按评分选一份最佳,适合同题多答的容错场景
投票型:  对可判对的离散答案做多数决,适合事实类问题
综合型:  融合多份结果生成新答案,适合需要超越单源的归纳
```

四种基本型可组合:先投票淘汰离群,再对幸存者做综合。选择判据是子结果之间的关系——互补用拼接、互替用择优、互斥用投票、互启用综合。

## 四、最小参考实现

```python
async def fan_out_aggregate(task, workers, aggregator, quorum=1.0):
    subtasks = split(task)                     # 分解
    sem = asyncio.Semaphore(MAX_CONCURRENCY)   # 背压

    async def run_one(sub):
        async with sem:
            try:
                return await with_timeout(
                    dispatch(sub, workers), sub.budget.timeout)
            except TimeoutError:
                return Partial(sub, status="timeout")

    results = await asyncio.gather(*(run_one(s) for s in subtasks))
    ok = [r for r in results if r.status == "done"]
    if len(ok) < quorum * len(subtasks):
        return degrade(task, results)          # 法定人数不足,降级
    return aggregator.merge(ok)                # 聚合
```

三个细节值得注意:信号量把并发度封顶,防止扇出宽度打垮下游;每个子结果带状态标签,超时不等于失败而是"部分完成";聚合前检查法定人数(quorum),不足则不硬聚。

## 五、扇出宽度与多样性

扇出宽度(并行执行者数量)不是越大越好。宽度带来的收益取决于子结果间的差异度:五个高度雷同的执行者,宽度为五只是五倍成本。提升差异的手段包括:不同的检索源、不同的提示策略、不同的温度采样、不同的工具子集。设计期应给每个扇出维度标注"期望贡献的视角",无法标注的维度删掉。

## 六、失效模式速查

- 分解泄漏:子任务间存在隐性依赖,聚合时才发现互相矛盾;
- 聚合瓶颈:并行执行 3 秒完成,聚合串行处理 30 秒;
- 同质冗余:多路执行者用同一数据源同一策略,宽度徒增成本;
- 慢尾支配:一个超时执行者拖住整体,墙钟时间等于最慢者;
- 部分失败误判:把超时当失败丢弃,而其结果其实已完成九成。

对应的缓解分别为:分解期依赖检查、聚合并行化与流式合并、强制视角标注、慢尾截止与部分结果回收、状态分级而非二值化。这些细节在后续子题目中逐一展开。

## 七、扇出聚合的实施检查单

首次落地扇出聚合的团队,建议按检查单推进,每项有明确的产出物:

- 分解性验证报告:对二十个历史任务样本做人工分解,统计子任务间的依赖检出率,高于两成则先改分解策略而非上线;
- 视角登记表:每个并行执行维度登记其期望贡献的独特视角与数据源,无法填写的维度删除;
- 聚合语义说明:一页纸写清采用哪种合并基本型、法定人数比例、缺席表达方式,评审通过后编码;
- 故障注入用例:超时、部分失败、结果矛盾三类场景的预期行为断言,进集成测试;
- 宽度配置档位:初始宽度、上限、按流量分级的调整预案,连同成本估算进配置中心。

上线后的首个观察期(两周)重点看三个数字:宽度利用率(聚合实际采用的子结果占比,低于六成说明分解或执行有问题)、聚合耗时占比(超过总耗时三成要优化聚合实现)、子结果冲突率(异常升高提示分解维度重叠)。三个数字构成扇出模式的健康基线,后续任何变更以不劣化基线为底线。

常见的第一周故障是慢尾支配:整体延迟总等于最慢一路。先检查超时设置是否与该路实际 P95 匹配,再考虑慢路独占降权。切忌立即加宽度——慢尾问题的解药是截止与隔离,不是更多并行。

## 八、扇出宽度的动态适配

固定宽度在流量波动下总是错的:高峰期过宽拖垮下游,低峰期过窄浪费容量。宽度适配的简单方案是分档配置加负载信号切换:维护三档宽度(保守、标准、激进),按下游负载指标(队列深度、过载错误率)自动换档,切换带冷却时间防抖。方案简单,但要求扇出宽度作为运行时参数贯穿派发器与预算体系。

进阶方案是宽度按任务画像定制:历史统计显示不同任务类型的质量-宽度曲线斜率差异大(事实核查类宽度三即平,创意生成类宽度五仍有增益),为每类任务维护推荐宽度,新任务按相似度匹配初始值,运行中按聚合反馈微调。宽度的个性化是扇出模式从"能跑"到"跑得经济"的分水岭。

宽度适配的护栏:任何自动调整都有上下限,上限保护下游,下限保证基本覆盖;调整动作记录决策依据(当时负载、任务画像),事后可审计;紧急情况下人工锁定宽度的开关常备——自动系统失灵时,人工兜底不能也失灵。

最后,宽度是扇出模式最显性的成本旋钮,它的一切调整都要同步刷新成本预估模型与告警阈值,防止宽度上调后成本告警在半夜响起,而值班人员面对的是三小时前的旧预算表。
