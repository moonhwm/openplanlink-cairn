# 降级与人工接管

## 一、自动化的尽头是诚实的边界

无论编排模式设计得多精巧,总有自动路径处理不了的时刻:预算耗尽、质量不达标、对抗样本触发、外部依赖全面故障。降级(degradation)与人工接管(human takeover)机制决定这些时刻的体验——是体面地交出半成品与风险披露,还是崩溃成一句"出错了请重试"。设计哲学只有一句:永远给用户一个可用的次优选项,以及一条通往人类的路。

## 二、降级阶梯

按质量损失从小到大排列的降级阶梯,逐级跌落:

```text
L0 完整模式:  全流程, 全角色
L1 减配模式:  砍扇出宽度/循环轮数/合议席数, 流程不变
L2 缓存模式:  相似历史任务的既有人工/优质结果
L3 部分交付:  已完成部分的产出 + 未完成清单与原因
L4 引导自助:  结构化的问题澄清 + 检索入口建议
L5 人工通道:  排队转人工, 附完整上下文包
```

关键规则:跌落必须逐级评估,某级失败才进下一级;每级都要快(L1 的减配重跑若注定再超时,不如直接 L3);降级选择记录原因,事后统计各级命中率,优化阶梯本身。

## 三、部分交付的诚实性

L3 部分交付是降级设计的核心,诚实性是它的全部价值:明确列出已完成项(带质量标记)、未完成项(带原因:超时/无证据/置信不足)、对使用者的风险提示(哪些结论缺少哪类支撑)。禁止的做法:把部分结果包装成完整结果、用通用套话掩饰缺口、静默丢弃未完成清单。部分交付的信任收益是长期的——用户宁可要诚实的七成,也不要伪装的十成,后者的败露只是时间问题。

## 四、人工接管的上下文包

转人工不能是"甩手掌柜",必须附上下文包(context handoff):

```python
@dataclass
class HandoffPackage:
    original_request: str      # 原始诉求
    automation_trace: str      # 自动流程做了什么(trace链接)
    partial_output: str        # 已产出与缺口清单
    failure_summary: str       # 卡在哪、为什么、已试过什么
    suggested_focus: str       # 建议人工优先看什么
    urgency: str               # 时效与影响面
```

`suggested_focus` 最影响接管效率——自动系统已经知道哪个环节可疑,把注意力路标递给人,人工的第一分钟不必浪费在重新发现问题上。

## 五、人工结果的回流

人工处理完成后,闭环的最后一环是回流:人工结论作为高置信样本进基准集;触发接管的失效模式转化为对抗样本;若同类接管反复出现,沉淀为新的判例或规则,让自动路径下次能自己处理——降级机制的健康度不看接住了多少,看让多少未来的接管不再发生。

## 六、降级的演练

降级路径是"平时不用,用时必须灵"的设施,必须演练:混沌注入(杀死某个依赖、压缩预算到极限),断言系统跌落到预期层级而非崩溃;接管通道压测(排队、超时、上下文包完整性);部分交付的格式回归。演练频率低于每季度的降级机制,默认视为失效。

## 七、心理与组织层面

降级设计最后落在组织认知:把"降级率"当负面指标考核,团队会倾向于隐藏降级、伪装完整,机制被激励扭曲。正确的姿势:降级率是中性运维指标,与"降级后的用户满意度"、"回流改进的关闭率"一起看。一个坦然展示自己边界的系统,比一个假装没有边界的系统,更配得上信任。

## 七、降级机制的运营治理

降级机制的运营要防止两种退化:降级羞耻(团队把降级当失败,倾向隐藏与回避,数据失真)与降级麻木(降级率长期高位,用户麻木系统也麻木,该修不修)。治理动作:降级率作为中性技术指标进运维报表,不进个人考核;但"降级后满意度"与"降级原因关闭率"进团队指标——前者约束降级质量,后者约束治理速度。

各级降级的配置要定期走查:减配模式的参数(宽度、轮数、席数的减档值)是否与当前满配版本匹配——满配升级后减配参数常被遗忘,降级时拿到的是过时的减配;缓存模式引用的历史结果,其时效性与适用性标注是否更新;人工通道的容量与 SLA 是否随业务量调整。走查每季度一次,配置漂移是降级机制最常见的隐性失效。

上下文包的质量抽检纳入日常:随机抽取转人工的工单,检查上下文包的完整性(五字段齐备、suggested_focus 真的指向了关键问题)。人工处理者对包质量的反馈建立直通渠道,差评的包回溯到生成逻辑改进。

回流闭环的月度盘点:本月人工结论中有多少进了基准、多少失效模式进了对抗集、多少接管场景沉淀成了规则或判例。回流率低说明降级在"兜住"而没在"消化"——兜住是成本,消化才是收益。降级机制的成熟标志,是它的各级通道都随时间变得更少被需要,而不是更多。

## 八、降级体系的演练经济

降级演练本身有成本,要做演练经济:全场景演练每年一次(完整降级阶梯逐级验证),专项演练每季一次(只演最可能触发的两级),桌面推演每月一次(不实际切换,只核对预案与配置的一致性)。三级频率匹配三级成本,把钱花在最可能用到的路径上。

演练的场景库来自真实:每次真实降级事件(无论大小)转化为演练剧本,补充触发条件的时序细节;每次未演练先触发的降级(事故性验证)做双重复盘——降级本身的表现复盘加演练体系为何没覆盖的复盘。场景库因此是事故驱动的活集合,预想的场景与真实场景的差距,靠事故来弥合。

演练的通过标准分层:功能性(降级后系统可用性符合该级定义)、诚实性(用户侧呈现与降级事实一致,无伪装)、恢复性(降级解除后的回升路径顺畅,无残留的减配状态)。三层的权重递增——功能不达标是技术债,诚实不达标是信任债,后者利息更高。

演练发现的问题分级闭环:阻断性缺陷(降级路径崩溃)四十八小时内修复;体验性缺陷(降级文案不清)下迭代修复;建议类进待办。闭环率进演练报告,演练不闭环等于花钱买了个放心错觉,那是所有安全投入里最坏的回报率。
