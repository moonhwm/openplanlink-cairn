# 知识源调度

## 一、调度器:最弱的中央与最难的决策

黑板架构刻意把调度器做"弱"——不做业务判断、不掌握求解逻辑,只负责在已触发的知识源里挑下一个执行的。但弱不等于简单:挑谁先执行的策略,决定黑板是高效收敛还是原地打转。调度是蜂群模式里唯一保留的集中决策点,值得精心设计。

## 二、触发的判定

知识源就绪的判定必须严格:

1. 触发谓词对黑板快照求值为真(纯函数,无副作用);
2. 其声明读取的层处于稳定代(无进行中的冲突消解);
3. 预算余量足以覆盖其成本估计。

三个条件缺一不可,尤其第二条常被忽略——基于正在被推翻的条目推演,是废工作的重要来源。

## 三、优先级函数的构成

经典黑板的"机会主义议程"用机会值(opportunity value)排序,推荐四因子加权:

```text
priority = w1 * gap_criticality      # 能填补缺口的关键度
        + w2 * enables_others        # 解锁价值:多少KS在等它的产出
        + w3 * freshness_decay       # 新鲜度:相关条目刚更新的衰减红利
        - w4 * cost                  # 预计成本惩罚
```

`enables_others` 是最值得投入的因子:找出"卡脖子"的知识源——它的产出是其他多个知识源的触发前提——优先执行能引发连锁推进。这要求调度器维护一个知识源间的静态依赖近似图,由知识源的 reads/writes 声明自动推导。

## 四、并行放行与互斥组

调度不必单线程,但并行要受控:读写集不相交的知识源可同时放行;读写集有交集的归入同一互斥组,组内串行。互斥组的判定可以做得保守(按层粒度)先跑起来,再按实测冲突率细化到条目粒度。

```python
def select(ready, running, bb):
    # 互斥过滤:与在跑KS读写集相交的候选延后
    eligible = [ks for ks in ready
                if not conflicts_with(ks, running)]
    if not eligible:
        return None                    # 本轮不放行,等待回收
    return max(eligible, key=lambda ks: priority(ks, bb))
```

## 五、饥饿与公平

优先级调度的经典副作用是饥饿:低机会值的知识源永远排不上。黑板的特定风险是"边缘知识源"——负责处理罕见但关键情形的模块,长期无触发机会,一旦触发又被高优先级挤压。对策:每类知识源设最长期龄,超龄强制放行一次;或者保留小比例的探索配额,轮转执行低优先级候选,防止议程被主流路线垄断。

## 六、调度预算与止损

调度器持有全局预算表:总代数上限、总成本上限、墙钟上限。每轮放行前检查,触顶即进入收尾模式——只放行"收束类"知识源(汇总、结论、缺口标注),不再放行"扩展类"(新假设、新检索)。这个扩展/收束的知识源分类,应当在注册时声明,它是预算治理的语义基础。

## 七、调度的可解释性

每次放行记录一行调度日志:候选集、各候选的优先级因子分解、选中者与理由。黑板模式的调试大量依赖这些日志——"为什么黑板停在这个状态"的答案,往往就藏在最后几轮的调度决策里。调度不可解释的黑板,出了问题只能靠重放猜测,代价极高。

## 七、调度器的调参与观测

调度器的优先级权重(四因子)没有万能初值,调参流程:先用均等权重跑回放集,记录各知识源的触发频率与产出贡献;按贡献频率比对权重做一轮手动调整;之后每月用线上数据重估一次。调参的目标不是"最优",是调度结果对权重扰动稳定——权重微调导致执行序列剧变的系统,说明因子间高度共线,该合并因子而不是继续细调。

调度日志的结构决定可观测上限:每轮记录候选集、各候选的因子分解值、选中者、放弃原因归类(互斥延后、预算不足、优先级低)。日志要支持两个查询:回放查询(某代为什么选了它)与统计查询(某知识源过去一周的被选率与延后率)。被选率长期为零的知识源要么触发条件过严要么确实无适用场景,两类都该显式处置。

并行放行的互斥组判定要随冲突统计细化:初版按层粒度(同层读写互斥),运行一个月后按实测冲突率降到条目粒度。细化带来的并行度提升通常显著,但每轮细化后要重跑并发等价性测试——粒度越细,竞态窗口越多,等价性断言是唯一的安心来源。

预算尾声的模式切换(探索转收束)要提前演练:人造预算耗尽场景,断言收束类知识源被优先放行、扩展类被拒绝且拒绝被记录。模式切换是黑板"善终"能力的核心,演练不合格的黑板,预算触顶时的产出质量全凭运气。

## 八、调度器的安全审计

调度器掌握执行权,它的安全审计有三个专项:选择完整性——调度日志的真实性审计,抽样核对"当时 ready 集合与优先级计算"是否与日志一致,防止日志美化(记录的选择理由与实际计算不符,掩盖偏好性调度);权重防腐——优先级权重的变更审计,任何权重调整有动机记录与审批,防止知识源通过调整权重获得不当优先;饥饿审计——长期未被调度的知识源清单月度审阅,确认无知识源被静默饿死。

审计的技术支撑是调度器输出的完整日志,包括被放弃候选的因子值。只有选中者日志的调度器无法审计——审计的本质是比较,没有落选者的数据就没有比较的基准。

调度器的故障注入测试:优先级计算服务异常时,调度器应降级为轮转模式(公平但无智能)而非瘫痪;日志服务异常时,调度继续但告警升级(无日志的调度是危险状态,需要人知道)。关键路径的依赖故障都要有降级预案,调度器自己也要遵守它为别人定下的降级纪律。

最后,调度器的变更管理比业务组件更严:任何调度逻辑变更(优先级函数、互斥规则、模式切换)都要在影子模式跑一周(新旧逻辑并行计算,线上用旧、日志记新),比对差异并解释。调度决定每个知识源的机会,它的变更失误是全局性的,谨慎永远不亏。
