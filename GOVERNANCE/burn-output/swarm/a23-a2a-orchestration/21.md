# 差量修订策略

## 一、从"重写"到"修订"

评审环里最常见的浪费,是拿到评审意见后整篇重写产物:已达标的部分被推翻重来,新的错误从重写中引入,评审者下一轮又要从头检查。差量修订(differential revision)主张只改动评审指出的缺陷位置,其余部分保持字节级稳定。它同时改善三个指标:修订成本(改动量小)、稳定性(达标部分不再震荡)、可审计性(每轮 diff 即修订记录)。

## 二、修订指令的编译

评审意见要先编译成修订指令才可执行。编译规则:

1. 每条缺陷生成一条独立指令,指令格式为"定位 + 动作 + 约束";
2. 动作限定为四种原子操作:替换、删除、插入、移动;
3. 约束写明不可触碰的范围——未被告警的部分禁止改动;

```python
@dataclass
class RevisionOp:
    anchor: str      # 定位:引用缺陷报告中的位置描述
    action: str      # replace | delete | insert | move
    payload: str     # 新内容或移动目标
    guard: list[str] # 保护区:本轮不得改动的段落标识

def compile_ops(defects) -> list[RevisionOp]:
    ops = []
    for d in sorted(defects, key=lambda x: -x.severity):
        ops.extend(d.to_ops())          # 一条缺陷可能拆多条指令
    return dedupe_overlap(ops)          # 重叠指令合并
```

指令间的冲突(同一段落既被替换又被删除)在编译期合并消解,不留到执行期报错。

## 三、保护带机制

差量修订的核心纪律是保护带:除缺陷定位点及其必要上下文外,一律不动。工程上把产物划分为可编辑区与保护区,修订执行器在提交前做 diff 审计——改动范围超出指令授权即拒绝本次修订,要求重新生成。这条护栏防止"顺手润色"式的隐性漂移,那种漂移会引入未经评审的新内容,让评审环的保证失效。

## 四、不可回退清单

与保护带配套的是不可回退清单:已在前几轮修复并被评审确认的缺陷,其对应改动列入不可回退集合。本轮修订后自动核对该集合,若已修复项复发(常见于振荡场景),本次修订判为无效,触发无进展检测。两个清单一静一动:保护带管空间范围,不可回退管时间维度,合起来把修订约束在"只许前进"的单调轨道上。

## 五、差量的记录与展示

每轮修订的差量是重要的过程资产,必须结构化落盘:

- **机器可读 diff**:按指令逐条记录执行结果,供自动核对;
- **人读摘要**:按严重度归纳"本轮修了什么、哪些未修、为什么未修";
- **缺陷状态流转**:open -> fixing -> fixed / wont_fix,每个 wont_fix 必须附理由。

未修项的理由分三类要分别统计:预算不足(轮数内没排上)、评审分歧(意见冲突待裁决)、无法修复(超出当前能力)。三类比例是修订器改进方向的直接依据。

## 六、何时允许全量重写

差量修订不是教条,三种情形允许打破:

1. 方向性错误:评审判定整体方向错,局部修补无意义,重写并在新产物上重启评审环;
2. 结构性缺陷:产物的组织方式本身有问题,逐段修订的成本超过重写;
3. 产物过短:改动比例超过六成时,差量的管理开销反超重写。

打破保护带是重决策,必须由裁决者批准并记录,不能成为修订者逃避差量纪律的日常借口。

## 七、验收

差量修订的质量指标两个:修订命中率(指令执行后对应缺陷确实消除的比例)与附带损伤率(未授权位置被改动的比例,护栏生效时应为零)。命中率低说明指令编译有缺陷,损伤率非零说明保护带实现有漏洞。两者都达标,评审环才真正获得"每轮单调变好"的性质,这也是整个规划-评审模式值得付出的根本理由。

## 七、差量修订的实现细节

差量修订的工程核心是修订执行器的可控性。执行器接收指令集后,先在产物的内部表示上做模拟应用,生成预览差异;预览通过保护带校验(改动不越授权区)与不可回退校验(不触碰已锁定修复),两项都过才真正落盘。任何一步失败,整批指令退回重新编译,禁止部分应用——半应用的修订比不修订更糟。

产物的内部表示建议用结构化文档树而非纯文本:树节点的稳定标识让"定位"精确到节点,保护带按节点子树声明,审计diff按节点输出。纯文本上的行号定位在多轮修订后漂移严重,是保护带失守的技术根源。

修订的操作日志要支持"重放验证":给定产物第 K 版与第 K 轮指令集,能确定性重建第 K+1 版(模型生成的新内容按存档回填)。重放验证保证审计时能精确回答"这个改动是哪轮哪条指令造成的",也让修订器本身的回归测试成为可能。

最后一个实践建议:修订器的验收测试里放一组"对抗性指令"——指令间互相冲突、指令定位指向已删除内容、指令要求改动保护区内文本。修订器对对抗性指令的正确反应是拒绝并上报,而不是尽力猜测意图。猜测意图的修订器,迟早把保护带变成建议带。

## 八、修订器的进化与守护

修订器是评审环里最容易被"改进"冲昏头的组件,进化的同时要加守护。进化方向有三:指令编译的智能化(缺陷单自动拆解为原子指令,重叠合并的准确率提升)、保护带的语义化(从节点级保护区升级为语义级——按论点划分保护区,跨节点但同论点的内容同进同退)、差量的可视化(修订建议以对照视图呈现,确认后应用)。

每个进化方向都要过守护检查:智能化不能牺牲确定性(同样的缺陷单,编译出的指令集合必须可复现,引入随机性的智能宁可不要);语义化不能引入模糊(论点划分的标准必须是可计算的规则);可视化不能变成新瓶颈(确认环节的交互成本要低于它拦截的错误收益)。

修订器的守护性测试要常态化:对抗性指令集(冲突、越界、指向失效内容)每周回归;保护带渗透测试(用精心构造的缺陷单诱导越界修改)按月执行;修订审计的抽样(实际 diff 与授权指令的一致性)持续进行。修订器持有产物的修改权,权力越大守护越严。

修订器的最终形态评估不是功能多少,而是两个比例:指令一次通过率(编译质量)与附带损伤率(必须为零)。前者可以持续优化,后者是铁的地板——任何非零的附带损伤,都是保护带的溃口,优先级高于一切新功能。
