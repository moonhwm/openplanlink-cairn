# 编排器的角色与职责定义

## 一、编排器是什么、不是什么

编排器(orchestrator)是掌握控制流的参与者:它决定任务何时派发、派发给谁、结果按什么顺序合并、异常时走哪条分支。在四大原语中,扇出聚合与规划-评审环必须有一个显式编排器,蜂群黑板刻意弱化它,裁判席则与之并列存在。

必须先明确编排器"不是什么":它不是业务逻辑的容器。编排器里出现越多的领域判断(如何理解某个检索结果、某段文本该怎么改写),系统就越难演进,因为这些判断被埋进了控制流。健康的原则是:编排器只操作"任务"与"状态",不操作"内容"。

## 二、编排器的六项核心职责

无论采用哪种原语,一个合格的编排器要覆盖以下职责清单:

1. **任务构造**:把上层请求翻译成带唯一标识、超时、重试策略的任务对象;
2. **派发与路由**:选择执行者集合,写入路由依据以便事后审计;
3. **状态机推进**:维护任务从"已提交"到"已终结"的状态迁移,非法迁移直接拒绝;
4. **结果汇聚**:按模式定义的合并语义(拼接、投票、择优)产出汇总;
5. **异常处置**:超时、失败、部分成功时按预案降级,而非中断全局;
6. **可观测性发射**:每一步输出结构化事件,供追踪与复盘。

## 三、任务对象的参考契约

编排器与执行者之间的一切交互都应通过显式契约,以下是一个最小可行的任务结构:

```python
@dataclass
class Task:
    task_id: str
    kind: str            # 任务类型,路由依据
    payload: dict        # 只读输入
    budget: Budget       # 超时/轮数/调用次数上限
    idempotency_key: str # 幂等键
    deadline: float      # 绝对截止时刻

class Orchestrator:
    def submit(self, task: Task) -> Result:
        plan = self.planner.build(task)
        for stage in plan.stages:
            outcome = self.dispatch(stage)
            if not self.gate(outcome):
                return self.degrade(task, outcome)
        return self.aggregate(plan)
```

注意 `gate` 与 `degrade` 两个钩子:前者是每阶段的放行闸,后者是统一降级出口。把它们做成编排器的显式方法而非散落在分支里的 if,是保持控制流可读的关键。

## 四、编排器的三种实现形态

- **代码形态**:用通用语言把控制流写成代码(如上例),表达力最强,适合控制流稳定、需要版本管理的场景。代价是每次调整流程要走发布。
- **声明形态**:把流程描述成 DAG 或状态机配置,由引擎解释执行,适合流程频繁变化、由非开发角色维护的场景。代价是引擎能力边界内的表达受限。
- **模型形态**:由一个"编排智能体"在运行时自主决定下一步,即所谓动态路由。灵活度最高,但确定性最差,必须配硬预算与白名单动作集。

三者不是互斥的,成熟系统常见"外层声明式 DAG + 节点内代码 + 受限节点用模型路由"的分层组合。

## 五、编排器的反模式

- 巨型编排器:职责清单里的六项之外还塞进内容加工,代码量随业务无限膨胀;
- 隐式状态:状态存在局部变量或闭包里,崩溃后无法恢复,重试语义不明;
- 吞异常:异常被捕获后只打日志继续跑,聚合阶段拿到的是残缺结果;
- 同步阻塞:编排器单线程等待每个执行者,并行度名义存在实际为零;
- 无预算:任何任务都没有上限,一个异常输入可以拖垮整条流水线。

## 六、验收标准

判断一个编排器是否合格,可以用三条硬标准:任一执行者被替换成桩实现时,编排器行为可被完全断言;任一任务在任意状态被杀死后,重启可恢复或可明确放弃;新人只读编排器代码就能画出完整控制流图。三条全过,编排器才算完成了它的本职——让复杂协作看起来井然有序。

## 七、编排器的测试替身策略

编排器作为控制流中枢,其单测的关键是隔离执行者。为每类执行者准备三种测试替身:桩(stub)返回固定结果,验证编排逻辑对正常流的处理;伪(fake)内置简化行为,验证并发与聚合语义;故障替身按脚本注入超时、部分失败、格式错误,验证降级路径。替身库与编排器同等重要,值得专人维护。

编排器的验收测试有三类必须覆盖:全绿路径(所有替身成功,断言聚合顺序与内容)、单一故障路径(每个替身轮流故障,断言降级输出与状态记录)、组合故障路径(两个故障叠加,断言不会出现未定义行为)。组合故障最考验降级逻辑的完备性,也是线上事故的最高发来源。

并发语义的测试需要确定性技术:替身的响应延迟由测试控制而非真实睡眠,用屏障同步各替身的到达时刻,断言聚合在部分到达时的行为。真实异步的竞态在测试中不可复现,受控模拟的竞态才能进断言。

编排器重构时的安全网是快照测试:对一组固定替身脚本,录制完整的事件序列(派发、状态迁移、聚合、降级),重构后重放对比。序列不一致先判断是改进还是回归,判断依据写进重构说明。没有这张安全网的编排器重构,等于闭眼下楼梯——多数时候没事,出事就是大事。

## 八、编排器的性能与容量

编排器是全系统的必经之路,它的性能特性决定整体上限。容量规划的三项输入:峰值请求速率、单请求的编排开销(状态迁移与聚合的计算量)、持久化写入速率。编排器的无模型调用设计让它天然轻量,但聚合大结果集与高频状态落盘会在高流量下成为瓶颈,容量测试要专门覆盖这两个点。

性能优化优先做无侵入的三件:状态批量落盘(按代聚合写入而非逐迁移写)、聚合流式化(子结果到达即部分聚合,不等全量)、事件发射异步化(观测不占主路径)。三件做完仍有瓶颈,再考虑编排器分片(按请求哈希分片,编排器无共享状态所以分片廉价)。

编排器的高可用部署:无状态多实例加任务队列,实例崩溃时在途任务由队列重新投递——这依赖任务幂等(见后文),编排器与幂等体系是共生关系。单实例编排器的系统,其可用性上限就是编排器的可用性,扩容角色毫无意义。

冷启动也要纳入容量考量:编排器重启后的恢复顺序——先恢复队列消费、再放开新请求入口、观测追平后才承接全量。没有恢复顺序的编排器,重启瞬间会被积压与新流量同时打死,可用性部署反而制造可用性事故。
