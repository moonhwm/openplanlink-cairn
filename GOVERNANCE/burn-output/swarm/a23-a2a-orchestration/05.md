# 消息传递与任务抽象

## 一、从函数调用到消息传递

单进程程序里,协作的单位是函数调用:同步、类型化、栈上传递。多智能体系统里,协作的单位必须换成消息:异步、可序列化、可跨进程边界。这个转换不是实现细节,而是语义分水岭——一旦协作以消息为单位,就必须回答调用语义回答不了的问题:消息丢失怎么办、重复到达怎么办、晚到怎么办、乱序怎么办。

消息传递的第一原则是:消息是数据,不是引用。任何把内存对象引用、文件句柄、数据库连接塞进消息体的做法,都会在跨进程瞬间崩溃。因此消息契约必须可序列化,且字段演化要向后兼容。

## 二、任务抽象的三个层次

把"要别人做的事"抽象成什么,决定了系统的可演进性。实践中有三个层次:

- **命令层**:消息就是动作指令,如"检索某关键词"。执行者与指令强耦合,新增能力要新增消息类型。
- **意图层**:消息表达目标与约束,如"在预算 X 内获取关于某主题的可信证据"。执行者自由选择手段,编排器只验收结果。
- **契约层**:消息是一份带验收标准的任务契约,包含输入、输出 schema、预算、幂等键。执行者与派发者只共享契约,互不感知实现。

编排成熟度自下而上递增:命令层写起来最快,契约层扩展成本最低。四大原语里,扇出聚合至少要到意图层(否则并行执行者会重复同一种手段),蜂群黑板要到契约层(知识源完全异构)。

## 三、一个可复用的消息信封

不论层次,消息外层建议统一信封,把传输关心的问题与业务负载分离:

```python
@dataclass
class Envelope:
    message_id: str      # 全局唯一
    correlation_id: str  # 关联同一次上层请求
    causation_id: str    # 触发本消息的上一个消息
    ts: float            # 发出时刻
    ttl: int             # 允许的最大跳数/存活秒数
    kind: str            # 消息类型
    payload: dict        # 业务负载(纯数据)

def validate(env: Envelope) -> None:
    assert env.ttl > 0, "消息已过保质期,应丢弃"
    assert env.kind in REGISTRY, f"未知消息类型: {env.kind}"
    REGISTRY[env.kind].schema.validate(env.payload)
```

三个标识符各司其职:correlation_id 串起一次请求的全部消息用于追踪;causation_id 构成因果链用于复盘"这个结论从哪来";ttl 防止消息在重试风暴里无限繁殖。

## 四、投递语义的选择

消息系统必须在三种投递语义中做出明确选择,并写进契约:

1. **至多一次**:发出即忘,可能丢失。适合可容忍缺角的扇出(少一路结果不影响聚合)。
2. **至少一次**:保证到达,可能重复。要求消费端幂等,适合任务派发。
3. **恰好一次**:工程上通常由"至少一次 + 幂等消费"组合达成,代价是每条消息带上幂等键与去重存储。

实践中最常翻车的是把"至少一次"当"恰好一次"用:执行者收到重复任务各自执行一遍,聚合阶段出现幽灵结果。防御手段是在执行入口处按幂等键做去重闸,先查后做。

## 五、消息顺序与因果

分布式环境下全局顺序既难获得也无必要,真正需要的是因果顺序:回复必须晚于问题出现。用向量时钟或简单的 causation_id 链即可满足大多数编排场景。需要严格顺序的场合(如黑板写入),应把顺序问题转化为存储层的版本控制,而不是让消息层背负排序义务。

## 六、契约测试清单

消息契约要有独立的测试套件,覆盖以下用例:未知 kind 的消息被拒收;payload 缺字段被 schema 拦截;重复消息被幂等闸吸收;ttl 归零消息被丢弃且发出告警;新旧版本字段并存时旧消费者不崩溃。这五个用例通过,消息层才具备被多个原语复用的资格。

## 七、契约演化的兼容策略

消息契约会演化,演化策略决定系统的可维护性。推荐双轨制:新增字段永远可选且带默认值,消费者忽略不认识的字段;删除或重命名字段走两步——先标记废弃(生产者继续填写,日志记录使用方),观察一个完整周期无消费后物理移除。任何一步跳过,都会在某个清晨以序列化错误的形式被追认。

版本协商要有明确规则。消息信封加 schema_version 字段,消费者声明支持的版本区间,派发者据此选择或转换。跨大版本的转换逻辑集中放在适配层,禁止散落在各消费者的解析代码里——散落的适配逻辑在下次演化时无人能完整盘点。

契约测试是演化的守门员。生产者与消费者各自维护契约测试套件,CI 中跑双向兼容检查:新生产者的样例消息能被旧消费者解析,旧生产者的消息能被新消费者解析。双向都绿才允许合并。这套检查把"升级踩坏下游"的经典事故从半夜告警变成流水线红灯。

对智能体系统特有的提醒:提示词也是契约的一部分。角色的系统提示、输出格式说明、few-shot 样例共同构成该角色的行为契约,变更提示与变更代码应走同等评审。实践中大量"没改代码却坏了"的事故,根因是有人随手调整了提示词而未走任何流程。把提示纳入版本管理,是消息契约纪律的自然延伸。

## 八、消息层的容量与背压接口

消息层自身也要可治理。容量属性显式声明:每类消息的平均与峰值大小、预期速率,进注册表。超大消息(如携带完整产物的消息)强制走引用模式——消息体只放存储指针,消费方按需拉取。引用模式的两条纪律:指针带过期时间,过期后消息降级为"内容不可得"而非静默空转;拉取失败的重试与消息重试分层,不互相放大。

消息层的背压接口标准化:队列深度、消费延迟、丢弃计数三项指标按消息类型暴露,上游编排器订阅这些指标做路由决策(见并发控制一章)。指标接口与消息实现解耦——换消息中间件不改编排器的背压逻辑。

死信处理是消息层的收尾设施:超过重试上限的消息进死信队列,死信按原因分类(目标不存在、schema 不符、持续超时),人工处理界面支持重放、修正后重放、丢弃三种动作,全部动作留痕。没有死信设施的消息层,失败消息会以日志形式蒸发,排障时永远缺一块拼图。

最后是消息层的演练:定期注入毒消息(schema 错误、超大消息、循环消息),断言死信路径与背压路径按设计工作。消息层是基础设施,基础设施的失效模式必须在演练里见过,不能在事故里初见。
