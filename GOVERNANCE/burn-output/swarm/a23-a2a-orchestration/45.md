# 用工作流引擎固化编排:DAG 落地

## 一、从代码到 DAG 的得与失

四大原语的参考实现都是代码形态:灵活、类型安全、单测友好。当编排需要被非开发角色审视、流程需要热更新、执行需要跨服务持久化时,把编排固化为工作流引擎执行的 DAG 声明成为主流选择。得:可视化、持久化执行、版本化流程、重试与超时由引擎统一供给。失:表达能力受引擎原语限制,复杂动态逻辑(黑板的自发调度)很难塞进静态 DAG。

因此适用判据明确:控制流相对稳定的扇出聚合与评审环适合 DAG 化;黑板模式保留代码或专用引擎;动态路由放在节点内部做。

## 二、DAG 的节点抽象

把角色调用映射为节点,节点契约统一:

```yaml
# workflow.yaml (示意)
nodes:
  split:
    type: fanout-split
    params: { strategy: by_dimension, max_width: 6 }
  retrieve:
    type: agent-call
    params:
      role: worker
      timeout_s: 30
      retry: { max: 2, backoff: exponential }
    fan_out: from split
  aggregate:
    type: aggregator
    params: { semantics: evidence_merge, quorum: 0.8 }
  review_loop:
    type: loop
    params: { max_rounds: 3, exit: rubric_pass }
edges:
  - [split, retrieve, parallel]
  - [retrieve, aggregate, barrier]
  - [aggregate, review_loop]
```

要点:重试与超时在节点级声明而非代码散落;扇出与汇聚是引擎原语(barrier 语义),不手写 gather;循环节点承载评审环,出口条件引用外部判定的服务而非内联逻辑。

## 三、引擎选型的硬性检查单

选引擎时逐项核对,任何一项不满足都会在后期变成重构噩梦:

1. **节点幂等要求**:引擎重放节点时是否假定幂等(大多数是),与我们的幂等键体系能否对接;
2. **动态图支持**:扇出宽度运行时决定,引擎是否允许子图实例化;
3. **人环节点**:人工接管是否是一等节点类型(带超时升级);
4. **版本化执行**:流程定义升级时,在途实例走旧版还是新版,必须可配置;
5. **可观测出口**:引擎的执行历史能否导出为统一追踪格式,与我们的 span 体系对齐;
6. **本地测试**:流程定义能否脱离引擎服务单测(干跑模式)。

## 四、节点内部的自由区

DAG 固化的是控制流,节点内部保留"自由区":节点内的模型调用、提示组装、内部重试逻辑不受 DAG 约束。分界原则:凡是"要不要继续、走哪条边"的判断上提到图;凡是"这一步怎么做"的细节下沉到节点。把细节抬上图,图会爆炸成几百个节点的面条;把控制流埋进节点,图失去可审计性——分界线本身就是设计质量的度量。

## 五、版本与迁移

DAG 是代码,要有代码级的版本纪律:流程定义进版本库,变更走评审;在途实例默认绑定创建时的版本跑完(避免中途换脑);必须强推新版时提供迁移工具(旧实例状态映射到新图),并在基准集上验证迁移无损。流程热更新的诱惑很大,但没有版本纪律的热更新等于在生产上直接改代码。

## 六、反模式

- 万物皆节点:把提示词级别的小分支也画进图,图复杂度失控;
- 图内藏逻辑:边条件里塞复杂业务表达式,可视化反而更难读;
- 引擎能力崇拜:用引擎的专属特性写流程,失去可移植性,被引擎绑架;
- 无干跑测试:流程变更只能靠上线验证,回归基准空转。

## 七、小结

DAG 化的正确姿势是"骨架上提、血肉下放":控制流获得引擎级的持久化、可视化与统一重试,节点内保留模型时代的灵活性。当一个团队的流程图可以被非开发同事读懂并提议修改时,编排才真正从个人技艺变成了组织资产。

## 七、DAG 化的团队协作

DAG 声明成为流程的正式表达后,团队协作方式随之升级:流程变更以 DAG diff 的形式提交评审,评审者看图与 diff 判断影响面;非开发角色(产品、运营)获得流程的阅读权,他们的修改意见转成变更单由工程实施——流程的可读性把最了解业务的人拉进了改进循环。

节点所有制的建立:每个节点标注责任人,节点的行为契约(输入输出 schema、超时重试语义、自由区边界)变更需责任人会签。跨节点的边变更(流程重组)上升为架构评审。所有权清晰后,节点内部的快速迭代与全局结构的稳定治理并行不悖。

发布流程的适配:DAG 定义与节点代码分仓分节奏发布,定义先行(新节点的代码先上线待命)、定义激活(流量切换到新图)、旧节点观察期后下线。三段式发布让流程变更的回退成本降到最低——回退只是激活指针的切换。

文档与图的一致性靠工具保证:流程文档从 DAG 定义自动渲染,人工只写节点的业务说明。任何需要手工同步的双份表达,半年内必然分叉,分叉的文档比没有文档更有害。DAG 化的最终收益,是让"流程即代码、代码即文档"在协作层面成立——流程的讨论从此有唯一的真相源。

## 八、DAG 治理的组织接口

DAG 化之后,组织与流程的接口要重新定义:流程变更的分级审批(节点内参数调整自主、节点增删与边变更架构评审、跨域流程重组专项评审),分级让高频小改不堵在低频大会上;流程与业务的映射登记(每个业务场景对应的 DAG 版本区间),业务方报障时按映射直接定位流程版本,缩短归因链。

DAG 的环境策略:生产、预发、开发三套环境的流程定义同源不同参(同一 DAG,超时与宽度等参数按环境分级),禁止环境间的定义分叉——分叉的定义让预发验证失去对生产的代表性。参数差异集中在一处配置,差异清单随发布核对。

流程回滚的预案要预先演练:DAG 版本回退时在途实例的处理策略(跑完旧版或迁移到新版)在发布前决定并写入发布单,回滚时不再临场讨论。流程回滚的混乱多数来自在途实例的无预案——版本可以一键切,实例的生命不能一刀切。

最后,DAG 治理的年度审计:流程定义与实际执行的偏差率(绕过 DAG 的直接调用占比,应为零)、变更审批的分级执行情况、环境同源性核查。审计确认治理规则被真实遵守——治理文件的存在不等于治理的存在,审计是两者的桥。
