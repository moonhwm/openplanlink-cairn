# 幂等与重复触发

## 一、重试世界的生存法则

多智能体编排充满重试:超时重试、消息至少一次投递的重复、崩溃后的任务重放、黑板的重复唤醒。每种重试都在问同一个问题:同一件事做两遍,后果是否等于做一遍?幂等性(idempotency)就是对这个问题回答"是"的设计性质。没有它,重试机制越完善,系统越危险——重复的副作用按重试次数累积。

## 二、幂等的三个层级

按实现强度分三级,按代价从低到高:

1. **天然幂等**:操作本身可重复(纯读取、写入固定值、upsert 固定 key)——零成本,设计时优先选;
2. **幂等键防护**:操作带唯一键,执行前查"此键是否已执行",已执行则直接返回上次结果(需要结果存储);
3. **去重闸加补偿**:无法内建幂等时,外层闸门去重,万一漏防由补偿事务撤销重复副作用——最后手段,复杂度最高。

```python
def idempotent_execute(task, store):
    prior = store.get(task.idempotency_key)
    if prior is not None:
        return prior.result            # 重复触发,返回既有结果
    result = actually_execute(task)    # 真实执行
    store.put(task.idempotency_key, result)   # 完成后才登记
    return result
```

登记时机是关键:必须"执行成功后登记",若执行前登记,执行失败会把自己的重试路堵死。

## 三、幂等键的构造

键必须覆盖全部影响输出的输入,且在重试谱系内稳定:同一任务的重试携带同一键;同一任务的重规划派生、黑板的重放触发,键的继承规则要显式声明(通常派生任务用 父键+序号,避免不同派生互相吞并)。键进消息信封,随消息传递,任何一层不得重新生成。

## 四、各原语的幂等要点

- **扇出**:子任务幂等是部分失败重试的前提;聚合器对重复到达的子结果按幂等键去重,防止幽灵翻倍;
- **评审环**:轮次编号进幂等键,第 K 轮的重试不会覆盖第 K+1 轮的产物;修订操作叠加式存储(新版本追加而非覆盖),天然幂等;
- **裁判**:裁决按争议件哈希缓存,重复提交同一争议直接返回既判;
- **黑板**:条目写入用(知识源实例标识 + 触发代 + 序号)做键,重复唤醒导致的重复写入被键去重。

## 五、副作用清单管理

对有外部副作用的动作(发送通知、写外部系统、产生文件),维护副作用清单:每个动作标注幂等级级与防护方式;清单在发布评审时逐项过目,无防护的副作用不得上线。外部系统的幂等经常不在自己控制内,防护落在自己侧:出站动作带去重窗(相同内容在 N 分钟内只发一次),出站前检查回执。

## 六、测试

幂等性必须有专项测试,用例模板:同一任务连续投递两次,断言副作用只发生一次且两次返回一致;投递与执行之间注入崩溃,重启后重试,断言最终一致;并发投递同一键,断言只有一个执行生效。三类用例覆盖了串行重复、崩溃重复、并发重复三种真实来源。幂等缺陷的测试经常在集成环境才暴露,单测里 mock 掉的存储与总线恰好藏住了问题,所以这类用例必须进集成流水线。

## 七、警惕"假幂等"

最危险的形态是看起来幂等实则不然:生成类任务重复执行,输出随机但都被接受,统计上无人察觉;计数类操作依赖读-改-写,并发下丢失更新。识别手段是副作用审计:对每个动作追问"执行两次,外部可观测状态与返回值是否逐位一致",迟疑的动作按非幂等处理加防护。宁可防护过度,不可信任含糊。

## 七、幂等体系的发布检查

幂等防护的发布检查单,每次涉及副作用路径的变更都要过:

- 新增动作的幂等评级:天然幂等、键防护、去重闸加补偿,三级标注进动作注册表;
- 幂等键的构造评审:覆盖性(全部影响输出的输入)、稳定性(重试谱系内不变)、派生规则显式;
- 登记时机确认:成功后登记的顺序在实现中正确,失败不占位;
- 外部副作用的出站防护:去重窗、回执检查、重发策略三件套齐备;
- 集成测试更新:串行重复、崩溃重复、并发重复三类用例覆盖新动作;
- 副作用清单同步:清单文档与代码比对,无未登记的副作用路径。

检查单之外,每季度做一次"幂等红蓝对抗":红队故意构造重复触发(重放旧消息、并发提交同键、崩溃后重启重试),蓝队只能靠监控与日志发现并证明防护生效。对抗结果进台账,防护被穿透的动作当场立项修复。

一个容易忽视的角落:降级路径的幂等。降级时切换的处理逻辑(缓存应答、部分交付)同样要过幂等检查——降级路径平时不跑,恰好最缺测试,而故障时刻的重复触发概率反而最高。降级路径的幂等缺陷,专挑最忙的时候爆炸。

幂等体系的终极状态是"重试自由":任何人任何机制可以放心地对任何任务重试,系统保证结果不变。达到这个状态,重试从危险操作变成常规运维手段,整个系统的容错心智随之升级。

## 八、幂等体系的年度审计

幂等防护的年度审计是一次全面压力验证:全量副作用清单的现场核对(注册表与代码的双向比对,揪出未登记的新增副作用)、每条防护的穿透测试(按三类重复场景实测,验证防护真实生效而非仅存在于文档)、外部依赖的幂等假设复核(下游系统的行为变更可能破坏我方假设,逐家确认)。

审计的深度检查项:幂等键的构造是否随业务演化出现覆盖缺口(新参数影响输出但未进键)、登记时序在异步场景的正确性(执行完成的回调乱序到达时是否误占位)、去重存储的容量与过期策略(键的保留期短于重试窗口会造成防护真空)。

审计发现按严重度分级处置:穿透类(重复副作用实际发生)当周修复并回溯影响范围;缺口类(防护存在但有漏洞)月内修复;假设类(依赖方行为变化)重签确认。全部处置闭环后,审计报告归档并更新副作用清单的基线版本。

幂等体系的成熟度标尺:从"重要动作有防护"到"任何动作天然幂等"(架构上选择幂等性强的操作原语,防护退居例外)。年度审计的长期轨迹应显示防护依赖的持续下降——那意味着团队在设计期就规避了非幂等结构,审计从救火检查演变为确认性巡检。
