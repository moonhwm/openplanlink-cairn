# 并发写与冲突消解

## 一、黑板的第一难题:写冲突

黑板的开放性带来的直接代价是并发写冲突:两个知识源基于同一黑板状态各自推演,同时提交写入,后到的可能覆盖先到的,或者两个写入互相破坏对方的前提。消息传递架构里这个问题被串行化队列天然消解,黑板必须正面处理——冲突消解机制的质量,直接决定蜂群模式的输出质量。

## 二、冲突的三种形态

- **覆盖冲突**:两个写入目标条目相同(同一 hypothesis 被两个知识源各自修订);
- **前提冲突**:B 的写入依赖条目 X,但 A 的写入已使 X 失效(推翻了 X 的前提);
- **语义冲突**:写入本身合法,但两条新条目在语义层互斥(黑板出现矛盾对)。

前两种是写入期问题,第三种是内容期问题,处理通道不同:写入期由黑板仲裁,内容期交给冲突消解知识源或裁判。

## 三、写入仲裁:乐观并发加前提校验

```python
class Blackboard:
    def commit(self, ks_write) -> CommitResult:
        # 乐观并发:提交时校验读取时的前提是否仍然成立
        for dep_id, seen_version in ks_write.read_set:
            cur = self.entries.get(dep_id)
            if cur is None or cur.version != seen_version \
               or cur.superseded_by:
                return CommitResult.CONFLICT  # 前提失效,拒绝
        if self._overlaps(ks_write):
            return MergeOrReject(ks_write)    # 覆盖冲突,走合并
        self._apply(ks_write)
        return CommitResult.OK
```

乐观并发的选择理由:知识源执行耗时长(模型调用),悲观加锁会把黑板退化成串行系统,并行收益清零。代价是提交可能被拒,因此知识源必须把"被拒后重试"视为正常路径——重读黑板、重新推演,而不是原样重放。

## 四、覆盖冲突的合并策略

目标相同的两个写入,按语义可分三种情况处置:

1. **可合并**:两者修改不同字段,黑板做字段级合并,双双生效;
2. **同向增强**:新写入与旧写入一致且信息更多,旧条目 superseded_by 新条目,链式保留;
3. **互斥修订**:两者真的不相容,不静默择一,而是双双入档并生成 conflict 条目挂到结构层,交给消解流程。静默择一是黑板最常见的隐性质量事故——被丢弃的写入里可能有对的那个。

## 五、语义矛盾的消解阶梯

conflict 条目出现后,消解按成本阶梯上升:

- **证据加权**:比较两侧的 provenance 强度(证据数量、来源可靠性),差距显著则强侧胜出,弱侧标记 superseded 且留档;
- **补充裁决**:差距不显著,派发定向知识源补取证据,升格一侧;
- **裁判终裁**:仍不决,打包成争议件提交裁判席,裁决连同依据写入,conflict 关闭;
- **悬置标注**:标尺外的价值性分歧,结论层并列呈现双方,标注"存在未消解分歧",诚实优于硬裁。

## 六、震荡的写入侧防御

两个知识源互相推翻对方的写入(A 写 X,B 推翻 X 写 Y,A 又推翻 Y)是黑板的癌症。防御三件套:推翻计数——同一位置的推翻超过两次即冻结该位置,升级人工或裁判;冷却期——被推翻的写入方向在若干代内不得原样重写;不可回退指针——已被裁判锁定的结论层条目,常规知识源只读,推翻权收归更高层级。

## 七、验收指标

冲突机制的三个监控指标:冲突率(被拒提交占比,过高说明知识源读写集设计过宽)、静默丢弃数(必须为零,任何丢弃都要有 conflict 或 superseded 记录)、同位置推翻分布(长尾出现即震荡前兆)。并发正确性的最终验收是压力复现测试:多知识源并发跑同一初始黑板多次,断言最终结论层的语义等价性——顺序可以不同,结论不容随机。

## 七、冲突消解的实现清单

冲突消解机制的实现按清单验收:

- 乐观并发校验:read_set 版本核对在提交路径上,被拒方拿到失效条目的明确指引;
- 覆盖合并三分支:字段级合并、链式取代、互斥入档加 conflict 条目,三个分支各有测试;
- 静默丢弃为零:任何被放弃的写入都有 superseded 或 conflict 记录,审计脚本断言;
- 消解阶梯:证据加权、补充裁决、裁判终裁、悬置标注四级按序触发,跳级需显式配置;
- 推翻冻结:同位置推翻计数达限自动冻结并升级,冻结条目的解锁权限在高层;
- 冷却期:被推翻的写入方向按代计冷却,冷却期内同向重写被拒;
- 并发压力测试:多知识源并发同位写入,最终状态可枚举且语义等价。

清单之外的两个实现细节:其一,conflict 条目要带"年龄",超龄未消解的 conflict 自动升级优先级并告警——悬而不决的矛盾会持续消耗每个观察它的知识源的注意力;其二,消解决策本身写入黑板(作为结构层条目),让"为什么采纳这边"成为黑板历史的一部分,而非散落在各知识源的内部日志里。

最后一个运维习惯:每周导出冲突热力图——哪些条目位置、哪些类型的断言最常冲突。热力图是黑板质量的透视镜:事实层高频冲突提示检索源的可靠性分化,假设层高频冲突提示任务的内在争议性强,两类结论对应完全不同的治理动作(换源与放宽表达)。

## 八、冲突数据的深度利用

冲突消解的副产品是冲突数据,深度利用三向:冲突预测——统计冲突的前兆特征(同类断言的来源可靠性方差、主题的争议度标签),派发前预判高冲突风险的任务,提前配置更权威的初始来源组合,把冲突消解从事后转向事前预防;来源信誉——冲突裁决的胜负记录汇入来源信誉模型,长期处于败方的来源降权直至出局,信誉模型反哺聚合权重;主题画像——按主题维度的冲突密度制图,高密度主题提示领域本身的争议性或我方证据源的覆盖缺陷,两类结论分别对应不同的补救(表达上标注争议性与扩充信源)。

冲突预测的落地形态是"冲突预算":每类任务的预期冲突率有基线,实际冲突率持续超基线的批次,自动暂停并触发专项检查(是任务画像漂移还是来源质量劣化)。冲突预算防止冲突消解机制在静默中超负荷——消解能力是有上限的,超限的冲突会以未消解状态渗入结论层,那是最坏的泄漏。

冲突数据的存档要注意脱敏:冲突条目含业务实质内容,长期归档前按数据分级处理,敏感冲突只保留统计特征(类型、频率、消解路径),内容按保留期销毁。冲突数据的价值在模式不在个案,脱敏几乎不损失分析价值。

最后,冲突率是黑板健康的综合体温计——检索质量、来源信誉、任务匹配度的问题都会在这里显形。把冲突率曲线挂在黑板运维的首要位置,它是比任何单一组件指标都灵敏的预警器。
