# 可观测性与追踪

## 一、多智能体系统的"黑箱叠加"问题

单智能体的输出好歹是一条可读的对话;多智能体系统的执行是几十次跨角色调用的叠加,任何一次的偏差都可能被下游放大成离谱结果。没有结构化可观测性,排障方式只剩"把所有日志读一遍",这在扇出宽度乘上循环轮数的规模下等于不可排障。可观测性设计的目标:任何一次异常输出,都能在十分钟内定位到"哪个环节、哪次调用、哪个输入"。

## 二、追踪的骨架:关联标识三件套

沿用消息传递一章的标识体系,贯穿所有原语:

- **trace_id**:一次上层请求的全链路标识,所有衍生消息共享;
- **span**:一个参与者的单次执行,记录开始/结束、输入摘要、输出摘要、状态;
- **causation 链**:span 之间的父子关系,还原"这个结论从哪条路径来"。

```python
@dataclass
class Span:
    trace_id: str
    span_id: str
    parent_id: str | None
    role: str          # planner | worker | reviewer | judge | ks
    status: str        # ok | timeout | invalid | degraded
    tokens_in: int
    tokens_out: int
    input_digest: str  # 内容摘要而非全文,控制体量
    output_digest: str

def record(span: Span):
    emit(span)         # 到追踪后端; 关键路径上异步发射
```

## 三、各原语的专属观测点

四大原语在通用骨架外各有必须记录的决策点:

1. **扇出聚合**:分解结果(子任务列表与去重动作)、每路状态分级、聚合决策(选了哪种合并语义、淘汰了谁、为什么);
2. **评审环**:每轮的缺陷清单与严重度、修订差量、出口原因(达标/上限/无进展);
3. **裁判席**:争议件、裁决书、置信度、升级记录;
4. **黑板**:每代快照指针、调度选择与理由、conflict 消解路径、停机原因。

决策点记录的原则:记录"选择"而非只记录"结果"——知道调度器为什么选了知识源 A,比知道 A 执行了要有用得多。

## 四、指标体系的三层

- **资源层**:每角色调用量、token 消耗、延迟分布、失败率;
- **流程层**:循环轮数分布、扇出宽度分布、冲突率、裁决翻转率、黑板代数;
- **质量层**:一次通过率、返工率、保留意见率、人工抽检不一致率。

三层自下而上回答:花了吗、转了吗、值吗。只有资源层的监控是"仪表盘装饰"——钱花了不代表环在转,环在转不代表质量在涨。

## 五、回放与归因

排障的标准动作是回放:按 trace_id 抽取全部 span,按 causation 链渲染成执行图,人工审图定位异常分支。为此 span 的 input_digest 要可展开(存储摘要加指针,全文按需取);黑板任务附加代快照引用;裁决附加争议件引用。归因报告的格式固定:异常现象、放大路径(异常如何传播到输出)、根因环节、修复建议——归因报告按月聚合,是编排模式迭代的一手依据。

## 六、采样与成本

全量追踪的成本可观,分层采样:质量异常的 trace 全量保留;正常 trace 按 1%-10% 采样留档;所有 trace 的资源层指标全量聚合(聚合不存明细)。异常驱动的升级保留:一旦某 trace 被判异常(用户反馈或质检),其已采样的数据自动升级为全量并补采关联上下文。采样率是预算项,进配置可调。

## 七、反模式

日志即追踪(把 print 当观测,无结构无关联);只记成功(失败 span 被吞,排障时恰好最需要的就是失败记录);摘要丢失(只存状态码不存输入摘要,回放无从做起);观测后置(系统跑三个月后才补埋点,前三个月的坑全部无法归因)。可观测性是架构决策,不是运维补丁——设计评审的第一个问题应该是"这个模式的每类失败,我们怎么看见"。

## 七、追踪体系的落地步骤

追踪体系从零建设按四步走:第一步,统一标识——trace/span 生成与传播进消息信封,所有角色的调用框架统一接入,这一步只求标识贯通不求内容;第二步,补齐四原语的决策点记录(扇出的聚合决策、环的出口原因、裁判的裁决依据、黑板的调度理由);第三步,搭指标三层(资源、流程、质量)的聚合管道;第四步,建回放工具——按 trace 渲染执行图,黑板附代快照,裁决附争议件。

各步的验收标准:第一步完成后,任意一个请求能列出全部 span 且父子关系完整;第二步完成后,异常 trace 的初步定位(哪个环节)可以全自动;第三步完成后,日报自动产出三层数字;第四步完成后,十分钟内产出任何 trace 的归因报告初稿。

接入顺序有讲究:先接故障高发的原语(通常是环与扇出),再接其余。追踪建设的投入要跟着事故热点走,平均分配资源会让最重要的环节等到最后。

运行期的两个维护动作:采样率的定期审视(异常率高的任务类型升采样,稳定的降采样,预算动态平衡);span 字段的防腐(新增字段走登记,废弃字段标记,防止半年后没人知道某个字段还算不算数)。追踪数据本身的治理常被忽略,而它决定这套体系三年后是资产还是负担。

## 八、观测数据的隐私与保留

观测体系采集了大量任务内容,隐私与保留策略要前置:追踪数据分级(含用户内容的 span 与纯技术指标分开存储)、内容字段的脱敏策略(摘要化时移除个人标识,业务敏感内容按数据分级加掩码)、保留期限按级别差异化(技术指标长保留,内容类按合规要求短保留)。

访问控制配套:追踪明细的查询权限按需授予(排障时限时提权,过期回收),批量导出走审批。观测数据是排障的资产也是泄露的负债,权限模型参照生产数据从严。

采样与隐私的交互要注意:异常驱动的全量补采可能捕获敏感内容,补采路径同样过脱敏层;黑板的代快照含完整业务状态,快照的观测副本比黑板本体更易被随意访问,要单独设权限。观测基础设施常是数据治理的盲区——它自己就是最大的数据聚合器。

观测体系的容量经营:数据量的增长模型(流量增长乘以字段膨胀),存储与查询的成本年度预算,超预算时的字段裁剪优先级(先裁内容类字段,保住结构性字段)。观测的价值密度差异极大——trace 结构与决策点日志是高密度,内容快照是低密度大体积,经营时区别对待,把存储花在刀刃上。
