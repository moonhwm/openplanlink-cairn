# 并发控制与背压

## 一、为什么扇出系统特别需要背压

扇出聚合模式天然是"放大器":一个上游请求放大成 N 个下游调用。若每个执行者内部又调用外部服务,放大系数继续相乘。没有任何限流时,流量洪峰沿放大链路传导,最先崩溃的往往是配额最少的外部依赖,然后错误反向传播回聚合层,表现为大面积超时与重试风暴。背压(backpressure)就是在放大链路上安装的泄压阀:当下游饱和时,上游主动减速而不是继续加压。

## 二、并发控制的三层限流

并发控制应分层设置,各层保护不同对象:

1. **任务级**:单个上层请求的扇出宽度上限,保护单请求不过度消耗资源;
2. **执行者级**:单个执行者实例的并发处理数,保护其自身与所依赖工具;
3. **依赖级**:对每个外部服务独立设置调用速率上限,保护最脆弱的下游。

三层独立计数、独立熔断,任何一层触顶都在本层排队或降级,不把压力转嫁给更深层。

## 三、信号量与令牌桶的选择

```python
import asyncio

class Dispatcher:
    def __init__(self, per_request=8, global_gap=64):
        self.local = asyncio.Semaphore(per_request)
        self.bucket = TokenBucket(rate=50, capacity=64)

    async def dispatch(self, sub):
        async with self.local:            # 请求级宽度
            await self.bucket.acquire()   # 全局速率
            try:
                return await call_worker(sub)
            finally:
                self.bucket.release()
```

信号量约束"同时在飞的数量",适合保护并发容量;令牌桶约束"单位时间发生速率",适合保护配额型接口。两者解决的问题不同,生产上通常同时使用。注意信号量获取必须带超时——排队过久的子任务其结果时效价值在衰减,超时转降级优于无限等待。

## 四、背压信号的传播

好的背压不只是丢弃,而是把"饱和"这一信息向上游传播,让上游做出知情决策:

- **排队深度上报**:执行者把本地队列深度写入状态,派发器据此调整路由权重;
- **快速失败标记**:下游饱和时返回明确的"过载"错误码,派发器对该执行者熔断一段时间,而非盲目重试;
- **上游降级联动**:全局饱和信号触发上游降低扇出宽度或切换到缓存应答,削峰填谷。

关键纪律:过载错误与业务错误必须区分错误码。把过载当业务失败会触发重试,重试加重过载,形成正反馈雪崩。

## 五、重试风暴的防御

重试是并发的天然放大器,防御手段按优先级排列:

1. **指数退避加抖动**:重试间隔按指数增长并叠加随机抖动,打散重试到达时刻;
2. **重试预算**:全局重试占成功的比例上限,超限后新请求直接快速失败;
3. **舱壁隔离**:不同任务类型使用独立配额池,一种类型的重试洪峰不淹没其他类型;
4. **幂等前提**:仅在幂等键保护下重试,防止重复副作用。

## 六、慢尾治理

并发执行的墙钟时间由最慢者决定,慢尾治理是并发控制的收尾:

- **截止时间传播**:上层 deadline 减去已耗时,剩余量作为子任务的超时,越到后来越紧;
- **部分结果回收**:到达截止时刻,已完成者进入聚合,未完成者标记"未达",聚合器按法定人数决定是否降级;
- **慢执行者隔离**:统计各执行者的长尾延迟,持续超标的降路由权重,直到恢复。

## 七、观测指标

并发健康的最小指标集:各层信号量的等待队列长度与等待时间分布、令牌桶的拒绝率、重试占比、慢尾执行者的 P99 延迟。任何一项持续恶化都是背压参数需要重校的信号,参数调优应以这组曲线为依据,而非拍脑袋改数字。

## 八、限流参数的调优方法

限流参数的初值来自压测而非直觉:对每个下游依赖做阶梯加压,画出延迟-并发曲线,拐点前的一档作为该依赖的并发上限;速率上限按配额文档的八折设定,留出重试与突发余量。压测要用真实负载画像(读放大系数、峰值到达模式),合成均匀流量测出的拐点在真实峰谷面前毫无意义。

参数生效后进入观察调优循环:每周复核三个信号——队列等待时间的 P95(持续增长说明上限偏紧)、下游错误率中的过载占比(非零说明上限偏松)、限流触发率(长期为零的限流器要么参数过松要么形同虚设)。调参幅度每次不超过两成,大跳调整会让曲线失去可比性。

信号量与令牌桶的配比也有讲究:保护容量型下游以信号量为主,令牌桶兜底防突发;保护配额型下游以令牌桶为主,信号量仅防单请求极端并发。两者告警分开接:信号量排队告警提示容量问题,令牌桶拒绝告警提示配额问题,接混了会让值班人员误判方向。

最后,所有限流参数集中管理并带变更审计。散落在代码里的限流常量是运维灾难——出事时没人知道哪里还有一道闸。集中配置、按依赖注册、变更留痕,这套管理动作的价值在第三次紧急扩容时会被深刻体会到。

## 八、过载时的自保动作

限流参数齐全的系统仍会遇到整体过载(流量超容量、下游故障叠加),此时系统要有预演过的自保动作序列,按顺序执行:第一级,新请求准入收紧(排队加优先级,低价值请求直接劝退并告知重试时机);第二级,非关键功能降载(抽检类、离线巡检类任务暂停,腾出容量给在线主路径);第三级,扇出宽度与循环轮数全局降档(减配模式见降级一章);第四级,熔断部分依赖(已知故障的下游整体熔断,相关功能显式不可用而非挂死)。

自保动作的触发条件量化预设:队列深度、过载错误率、延迟劣化幅度各自的阈值与持续时间(避免瞬时抖动误触发)。动作的解除同样量化:指标回稳并持续一段时间才逐级恢复,恢复速度慢于触发速度——快速触发慢速恢复,防止在临界点反复横跳。

自保期间的用户沟通要预先写好文案模板:告知发生了什么、影响哪些功能、预计何时恢复、用户此刻能做什么。过载时刻的系统沟通质量,决定用户对系统的长期信任水位;沉默或含糊的过载,技术处理得再好也是公关失败。

每次过载事件后复盘自保序列的执行:该触发的都触发了吗、触发顺序符合预期吗、恢复过程顺利吗。过载是压力测试的免费现场,复盘认真,下一次的自保就更从容。
