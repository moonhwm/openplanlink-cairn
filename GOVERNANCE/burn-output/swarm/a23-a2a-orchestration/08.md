# 静态扇出与动态扇出

## 一、两种扇出的分野

静态扇出指派发前就已确定子任务清单与执行者集合:宽度、维度、路由全部在编译期或规划期固化。动态扇出指运行时根据中间结果决定是否继续派发、派发什么、派发几路:第一轮结果触发第二轮扇出,宽度随问题难度自适应。

分野的本质是信息时机:拆分所需的信息在派发前是否齐备。齐备用静态——更简单、可预测、易测试;不齐备用动态——覆盖长尾,但控制流复杂度上升一个量级。

## 二、静态扇出的设计要点

静态扇出看似简单,质量取决于分解维度选择。常用维度有四种:

1. **按数据分区**:不同执行者各查一个数据源,互补拼接;
2. **按视角分区**:支持方/反对方/中立方各自论证,聚合时对撞;
3. **按精度分区**:快速粗筛一路、深度精查一路,按时限取用;
4. **按语言或领域分区**:不同语言、不同专业域各配专门执行者。

静态扇出的宽度应做成配置而非代码常量,并给每个宽度档位标注成本估算,让运营可以按流量分级调整。

## 三、动态扇出的触发器设计

动态扇出的核心是"继续扇出"的判定条件,常见触发器有三类:

```text
冲突触发:  多路结果矛盾度超过阈值 -> 对矛盾点定向派发核查任务
置信触发:  聚合结果置信度低于阈值 -> 追加更权威源的窄扇出
覆盖触发:  关键子问题仍无可用答案 -> 仅对空洞部分补派
```

触发器必须是可解释的谓词而非黑盒判断,每次触发记录原因,否则动态扇出会演变成不可控的成本黑洞。

## 四、动态扇出的递归骨架

```python
async def dynamic_fanout(task, max_rounds=3):
    agenda = [task]                      # 待办队列
    findings = []
    for round_no in range(max_rounds):
        results = await parallel_run(agenda)
        findings.extend(r for r in results if r.usable)
        gaps = detect_gaps(findings)     # 空洞/矛盾/低置信
        if not gaps:
            break                        # 收敛,停止扇出
        agenda = plan_narrow_tasks(gaps) # 定向窄扇出
    else:
        log("触发最大轮数,带空洞聚合")
    return aggregate(findings, gaps)
```

骨架里两个防御点:轮数硬上限必须存在,for-else 分支把"未收敛"显式记录而非静默;补派任务是"窄"的——只针对空洞,不整体重来,否则每轮成本不减,总数按几何级数膨胀。

## 五、成本曲线对比

静态扇出的成本是宽度的一次函数,可精确预算。动态扇出的成本是随机的,上限由轮数与每轮宽度之积封顶,期望值取决于触发概率。运营上应分开监控两个指标:静态路径的"宽度利用率"(实际被聚合采用的结果占比),动态路径的"扩展率"(总执行数与首轮之比)。利用率低说明静态宽度冗余,扩展率高说明首轮分解质量差——两个指标分别指向两种治理动作。

## 六、混合策略

生产系统常见"静态打底、动态补洞":首轮按固定维度静态扇出,后续仅对未收敛区域动态补派。这样预算的大头可预测,只有不确定性部分随机。选型的粗判据:请求成本可事先报价的场景用纯静态;质量优先、成本上界宽松的离线场景可用全动态;绝大多数在线场景落在混合档。

## 七、迁移注意

从静态迁往动态时,最大的坑不是技术而是回归基准缺失:动态路径的行为分布改变了,旧的单点断言全部失效。迁移前必须先建立基于性质的测试(输出始终满足验收、轮数不超限、总成本有界),再放开动态触发,否则上线即失去对系统的把握。

## 八、动态扇出的护栏配置实例

动态扇出上线前,护栏参数要成套配置并写入变更单。一组经过验证的参考起点:最大轮数三、每轮最大宽度为首轮的零点六倍(逐轮收窄)、触发器的冲突阈值取余弦相似度零点七五以下、置信阈值按任务校准后的分位数设定、总成本熔断为首轮成本的四倍。数值本身不神圣,成套且显式才神圣——每个参数标注设定依据与调整方向。

触发器的日志要单独成流。每条触发记录:触发的谓词、当时的证据摘要、补派的任务清单、补派结果的增量价值(补派后聚合质量变化)。运行一个月后统计各触发器的"触发后增益":增益为负的触发器关闭或收紧,增益高的触发器考虑开放给更多任务类型。触发器的存废由数据决定,防止动态扇出悄悄变成"总是多跑一轮"的惯性系统。

窄扇出的任务生成要有模板:补派任务只包含空洞描述、已有结论边界、验收标准三部分,禁止把全部历史上下文塞给补派执行者——补派要的是定向火力,不是重火力。上下文瘦身后的补派任务,延迟与成本通常能降到全量重派的三分之一以下。

最后给动态扇出设"静默期":新触发器上线首周只在影子模式运行(记录本会触发但不实际派发),观察期结束后评估再放量。影子模式让激进的动态策略在不花钱的前提下完成试运行,是所有自适应机制的标准上线路径。

## 八、动态扇出的观测专项

动态扇出的行为难以凭直觉掌握,观测要做专项:每轮补派的触发原因、补派任务的实际增量(补派结果被聚合采纳的比例)、扩展率(总执行数与首轮之比)三条曲线按任务类型分列。曲线的组合形态直接指导调参:触发频繁但增量低,触发器阈值过松;触发稀少但单次增量高,阈值可适度放松;扩展率长尾,某些任务陷入反复补派的泥潭,检查空洞检测的判定逻辑。

补派任务的验收要独立于首轮:补派任务同样带验收谓词,不合格的补派结果不进聚合——动态扇出最常见的质量事故,是把"后来补的"当"更用心的",默认采信。补派结果与首轮结果在聚合时同等对待,来源标注但无优先权。

动态扇出的回放测试:构造已知最优补派路径的任务,断言实际补派序列的效率(补派次数不超过预期上限)。回放约束的是成本边界而非精确路径——路径可以不同,烧钱的路径不行。

最后一个组织提醒:动态扇出的参数(触发器、轮数、宽度衰减)变更频繁,全部进配置中心带审计,变更人注明动机。三个月后回看参数演化史,能看到团队对"何时该多查、何时该收手"的认识如何逐步精化——这份演化史是比任何文档都真实的经验积累。
