# 裁判席模式原理

## 一、为什么需要裁判

评审环回答"有什么问题",不回答"听谁的"。当多个执行者结论冲突、评审意见分歧、或产物是否放行存在争议时,系统需要一个拥有终局裁决权的角色——裁判席(Referee)。它与其他参与者的本质区别在于权力类型:执行者有行动权,评审者有发言权,裁判有定夺权。定夺权意味着它的结论就是系统的最终结论,除非被更高层(通常是人工)推翻。

裁判席解决三件事:结论冲突时的裁决、质量争议时的放行判定、规则模糊时的解释适用。它是质量体系的最后一道闸,也是最容易被滥用的一道闸——把本该靠标准解决的问题推给裁判,裁判会沦为昂贵的兜底垃圾桶。

## 二、裁判的权力边界

清晰的边界是裁判可信的前提,建议三条铁律:

1. **只裁不放**:裁判只能对已存在的选项做选择或判定,不能替生成者产出新方案——一旦下场生产,其中立性即告失守;
2. **依规裁判**:每份裁决必须引用裁决依据(标准条款、证据编号、评分标尺档位),无依据的"我觉得"不构成裁决;
3. **单点终局**:同一争议只裁一次,复审必须走更高层级,禁止同级反复重裁,否则裁决沦为新一轮争论的开端。

## 三、裁判席在四种原语中的接法

- **接扇出聚合**:多路结果冲突时,聚合器把冲突项打包成争议件提交裁判,裁判选定后聚合继续。接点在聚合期;
- **接评审环**:评审者只出意见,裁判握出口条件——是否达标、是否无进展、是否升级。接点在终止判定;
- **接蜂群黑板**:裁判周期性巡检黑板,判定是否满足验收触发停机。接点在收敛条件;
- **独立常设**:对高风险产物做放行终审,不嵌入任何环,作为质量体系的最后关卡。

## 四、裁决件的标准结构

裁判的输入必须是结构化争议件,而非一堆聊天记录:

```python
@dataclass
class Dispute:
    question: str        # 待裁决的具体问题
    options: list[Option]# 候选项,各带主张与依据
    criteria: list[str]  # 适用标准条款编号
    evidence: list[Ref]  # 双方共同认可的证据集
    stakes: str          # 裁错的代价描述,影响审查强度

@dataclass
class Verdict:
    chosen: str          # 选定项或判定结论
    basis: list[str]     # 引用的条款/证据
    confidence: str      # high | medium | low
    dissent: str | None  # 少数意见留档(合议时)
```

争议件的 `evidence` 限定为双方共同认可的部分——允许裁判采纳单方未质证的证据,是裁决被翻案的首要原因。`confidence` 为 low 时裁决附带"建议升级复核"标记,自动路由到人工通道。

## 五、裁决的可撤销性

裁判不是绝对正确,体系必须为纠错留门:每份裁决带版本与依据指纹;新证据出现且与原裁决依据矛盾时,可发起重裁,但重裁必须由更高层级启动并在新争议件中显式否定旧依据;裁决历史对下游可见,产物标注其所依赖的裁决编号,裁决被翻时相关产物可追溯召回。无纠错通道的裁判席,单次错误会被体系永久放大。

## 六、反模式

- **裁判滥权**:裁判开始改写产物内容,身份从裁判滑向编辑;
- **无据裁决**:裁决书只有结论没有依据,不可审计也不可纠错;
- **同级重裁循环**:败诉方不断向同一裁判重新提交,争议永不关闭;
- **裁判过载**:所有质量判断都堆给裁判,标准建设荒废,裁判成为全系统最贵的单点。

## 七、小结

裁判席的价值在于用一个小而权威的角色,收束系统中无法自解的争议。它的运行成本(结构化争议件、裁决留档、纠错通道)都是为了让"定夺"这件事可审计、可复盘、可翻案。省掉这些成本的裁判席,只是给随机意见盖了公章。

## 八、裁判席的组织设计

裁判席不仅是技术角色,还是组织设计。裁判席的"编制"要精简:常设席位保持最小必要(多数系统一两位模型裁判加抽检复核就够),特殊领域(法务、安全)按需临时增设。席位膨胀的裁判体系会吸引大量本该由规则解决的问题,组织成本与技术成本同步失控。

裁判的"任期"与轮换:模型裁判的版本变更等同换人,要走金标回归;合议席位定期轮换组合,防止固定小团体的路径依赖。裁判的"考核"只看两个指标:与金标的一致率、被上级推翻率。不考核吞吐——考核吞吐的裁判会倾向于快速了结而非审慎裁决。

裁判席与团队的关系要定界:裁判不参加产前设计讨论(防止先入为主),但参与事后判例复盘(沉淀标准)。裁判对标准的修改建议走正式提案通道,不通过个案"夹带"标准变更——个案里顺手改标准,是裁判席最隐蔽的越权形态。

最后,给裁判席设"免检豁免清单"要严格:哪些产物类型可以不经裁判直接放行,清单白纸黑字且短。豁免清单悄悄变长的系统,一定是裁判环节的延迟或成本出了问题,正确动作是治理裁判环节,而不是扩大豁免。

## 八、裁判席的容灾设计

裁判席是争议的收口点,它自身不可用时争议将积压发酵。容灾设计三层:热备——同构的备席常备,主席故障时秒级接管,裁决缓存双席共享保证接管后的既判连续性;降级链——模型裁判整体不可用时,按预案降级为规则裁决(按预设的默认倾向处理常规类争议,边界类排队等待),用户侧明确提示裁决服务降级中;恢复对账——故障恢复后,比对主备期间的裁决差异,差异样本人工复核,防止切换窗口产生分裂裁决。

裁决数据的容灾与裁决服务同等重要:裁决记录、判例库、校准数据三者的备份策略分级——裁决记录可容忍少量丢失(可重裁),判例库与校准数据必须强持久(丢失等于裁判失忆,重回未校准状态)。恢复演练覆盖三者的分别丢失场景。

裁判席的依赖也要盘点:模型服务、标尺存储、证据检索,任一依赖的故障都会表现为"裁判变笨"而非明确报错。依赖健康度纳入裁判席的监控面板,故障时刻先查依赖再怀疑裁判本身——多数"裁判异常"的真相是裁判瞎了(证据检索挂了)而不是裁判疯了。

容灾的年度演练:模拟主席宕机、模型服务中断、判例库损坏三个场景,断言接管、降级、恢复全链路符合预案。演练脚本与生产预案同库维护,演练即预案的活体文档。
