# HarmonyOS Push Kit服务端REST集成总体架构与端点体系总览

> 摘要：本文系统梳理HarmonyOS Push Kit服务端集成的整体架构、两大核心REST端点（OAuth凭证签发与下行消息下发）以及从AGC开通到联调上线的全链路要素，为REST集成系列专项文档提供总览地图。

## 一、Push Kit在端云消息链路中的角色定位

HarmonyOS Push Kit是华为面向HarmonyOS NEXT生态提供的系统级消息推送服务，其架构由三部分协同构成：其一是AGC（AppGallery Connect）控制台，开发者在此创建应用、开通Push服务、获取应用级凭证（App ID与App Secret，即OAuth语义中的client_id与client_secret）；其二是端侧SDK，应用集成Push Kit后调用getToken能力向推送服务注册设备，换取与设备、应用双维度绑定的推送令牌；其三是服务端REST接口，业务服务器通过HTTPS调用华为推送云，将消息投递到指定Token对应的终端设备。理解这一三角关系是全部集成工作的前提：业务服务器从不直接与终端通信，而是把消息交给推送云，由推送云经过系统级长连接通道送达端侧，再由端侧以系统通知或透传数据的形式呈现。这种托管模式将长连接维护、设备在线调度、通知合规管控等复杂度收敛到华为侧，业务侧只关注"何时、向谁、发什么"。

## 二、核心端点体系与调用时序

服务端集成只涉及两个核心HTTP端点。第一个是OAuth 2.0客户端凭证模式端点，即向授权服务器请求访问令牌；第二个是下行消息端点，用于携带访问令牌提交消息体。整体时序如下：

```text
业务服务器            授权服务            推送服务             终端设备
    |  client_credentials |                    |                  |
    |------------------->|                    |                  |
    |<--access_token-----|                    |                  |
    |        (缓存至过期前刷新)                |                  |
    |  POST /messages/send (Bearer token)     |                  |
    |--------------------------------------->|                  |
    |<--code:80000000 / requestId------------|                  |
    |                                         |--系统长连接下发-->|
    |                                         |                  |--通知/透传
```

时序中的关键约束有三点：访问令牌有效期为小时级（示例场景约3600秒），必须缓存并在过期前主动刷新，禁止每次发消息都重新申请；消息下发必须携带Bearer鉴权头；每次请求都会返回requestId，它是排障与工单沟通的最小追踪单元。

## 三、接入前置条件与工程基线

在真正编码之前，以下前置条件必须逐项闭环，这也是集成联调阶段最常见的返工来源。接入检查清单：

- 在AGC创建HarmonyOS应用并完成包名、签名证书指纹等基础信息登记；
- 在AGC"增长-推送服务"中开通Push Kit，记录App ID，并将App Secret交由密钥管理系统保管（禁止硬编码进代码仓库或前端产物）；
- 端侧工程导入Push Kit（`@kit.PushKit`），完成getToken联调，确认能稳定取到Token；
- 服务端出网到推送域名的HTTPS连通性验证，确认出口IP未被防火墙策略拦截；
- 明确消息分类（category）与自分类权益申请状态，否则营销类消息可能被系统频控或折叠；
- 设计好Token上报、存储、失效清理的服务端数据模型与接口契约。

## 四、常见误区与架构要点

集成实践中有四个高频误区值得在架构评审阶段就规避。第一，把App Secret当作普通配置项散落在多个服务中，导致轮换困难，正确做法是集中到密钥管理服务并支持无损轮换。第二，忽视令牌缓存，导致OAuth端点被高频打爆，既浪费配额又抬升消息时延。第三，把业务可用性完全押在单通道上，没有为推送失败设计降级路径，一旦遇到限流或网络抖动便产生业务事故。第四，忽略requestId与消息体日志的留存，故障复盘时无法定位。总体而言，REST集成的架构基线是：凭证集中托管、令牌池化缓存、消息发送走统一网关、每次调用留痕，这四条贯穿后续所有专项文档，是稳定性与可运维性的地基。后续文档将分别就OAuth细节、错误码体系、限流与重试等主题逐项展开。
