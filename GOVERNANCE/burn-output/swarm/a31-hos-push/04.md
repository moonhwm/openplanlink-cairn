# 下行消息REST接口调用规范：请求结构、鉴权头与响应处理

> 摘要：本文给出HarmonyOS Push Kit下行消息REST接口的完整调用规范，覆盖URL与HTTP方法、必备请求头、请求体的顶层结构与payload嵌套模型、同步响应字段解析与trace留痕实践，并附可运行的请求示例。

## 一、接口基本约定

下行消息接口为HTTPS POST请求，路径为消息发送端点（HarmonyOS Push Kit服务端接口，形如 /v3/messages/send，具体以当前官方文档为准），每次请求完成一批Token的消息下发。请求必须携带三个要素：Authorization头，值为Bearer加空格加access_token，即上一步OAuth获取的访问令牌；Content-Type头，值为application/json，请求体为UTF-8编码的JSON；请求体本身，核心是payload对象。响应同样是JSON，成功时包含业务码（示例场景成功码为80000000）、描述与requestId。需要特别强调同步语义：该接口的返回只代表推送服务"已受理"，不等于消息已到达终端，到达确认依赖端侧行为或回执机制（详见可靠性专项文档），任何把受理当送达的业务设计都埋着可靠性隐患。

## 二、请求体结构模型

请求体顶层为payload包裹，内部三大关键字段：pushToken数组声明目标设备令牌；pushType标识消息用途类别（如服务提醒类、资讯营销类，取值以官方枚举为准），它与通知内的category共同决定系统侧的展示与频控策略；notification对象承载通知内容本体。最小可用示例：

```json
POST /v3/messages/send
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "payload": {
    "pushToken": ["<device-push-token-1>"],
    "pushType": 0,
    "notification": {
      "category": "IM",
      "title": "订单已发货",
      "text": "您的订单已由顺丰揽收，预计明日送达",
      "clickAction": { "actionType": 0, "data": "orderdetail/10086" },
      "badgeAddNum": 1
    }
  }
}

-- 响应示例 --
{ "code": "80000000", "msg": "success", "requestId": "CSrh1b7XRU..." }
```

字段取值均为占位示例；actionType决定点击后的路由行为，data承载目标页面路径或自定义参数，二者语义将在消息体系列文档中逐项展开。

## 三、响应处理与错误分流

调用方对响应的处理必须遵循三层分流。第一层看HTTP状态码：4xx类多为请求格式或鉴权问题，5xx类为服务端或网关异常，网络层异常（超时、连接重置）单独归类。第二层看业务码：成功码直接记requestId入链路日志；鉴权类错误触发令牌强制刷新后单次重试；Token无效类错误驱动Token库清理（详见Token系列文档）；限流类错误进入退避重试或降级通道（详见降级系列文档）。第三层看批次语义：请求内多个Token部分失败时，以响应中按Token维度的错误明细为准做精准清理，而不是整批放弃。参考分流伪码：

```text
if http == 200 && code == SUCCESS:
    log(requestId, tokens, messageFingerprint); return ACCEPTED
else if code in AUTH_ERRORS:
    tokenManager.forceInvalidate(); retry once; else ALARM
else if code in INVALID_TOKEN_ERRORS:
    tokenStore.markInvalid(failedTokens); drop
else if code in THROTTLE_ERRORS or http in (429,5xx):
    backoff(); enqueueRetry(idempotentKey)
else:
    deadLetter(businessId, reason, snapshot)
```

## 四、工程规范清单

将接口调用固化为网关内聚模块时，建议遵守以下规范：所有请求与响应（脱敏Token后）按requestId落日志，保留周期与业务审计要求对齐；请求体在发出前做Schema校验，拦截长度超限与非法字符，避免低级格式错误消耗服务端配额；对单请求Token数量设内部上限并预分片，防止大批量群发时单请求过大导致整批失败；超时建议设置在三到五秒并区分连接超时与读超时；为每个业务消息分配业务侧幂等键，与requestId建立映射，保证重试不产生重复通知；在配置中心维护端点URL与版本号，跟随官方接口演进时可平滑切换。遵守这些规范后，消息下发模块即可达到"可观测、可重试、可审计"的生产标准，后续专项文档将深入错误码体系与限流策略等细节。
