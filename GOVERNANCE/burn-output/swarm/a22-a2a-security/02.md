# 02 A2A认证选项全景：Agent Card 的 securitySchemes 声明

A2A协议的一个关键设计是：服务端 Agent 在 Agent Card 中以机器可读方式声明自己支持的认证方案，客户端据此决定如何携带凭据。这一机制把"认证协商"从文档约定变成了协议行为，但同时也意味着：卡片描述与实际实现不一致时会产生安全裂缝。本篇梳理全部认证选项及其声明语法、协商语义与选型要点。

## 一、Agent Card 中的声明结构

Agent Card 通过两个顶层字段共同描述安全要求：securitySchemes 定义"有哪些方案"，security 指明"哪些端点适用哪些方案"。前者复用 OpenAPI 的安全方案词汇，后者完成方案到端点的绑定。

```json
{
  "name": "行程规划Agent",
  "url": "https://agent.example.com/a2a",
  "securitySchemes": {
    "oauth2cc": {
      "type": "oauth2",
      "flows": {
        "clientCredentials": {
          "tokenUrl": "https://idp.example.com/oauth2/token",
          "scopes": { "tasks:write": "创建任务", "tasks:read": "读取任务" }
        }
      }
    },
    "bearerJwt": { "type": "http", "scheme": "bearer", "bearerFormat": "JWT" },
    "mtls": { "type": "mutualTLS" }
  },
  "security": [ { "oauth2cc": ["tasks:write"] }, { "bearerJwt": [] } ]
}
```

数组语义是"或"的关系：客户端任选一种满足要求的方案即可，这是降级攻击防护（见第12篇）需要重点审视的位置。

## 二、六类认证方案速览

A2A生态中实际可声明的方案及其适用场景如下：

- none（不声明 security）：适合网关已终结身份的内网场景，绝不应暴露到公网。
- apiKey：以请求头或查询参数携带静态密钥，实现最简单，审计与轮换能力最弱。
- http bearer：以 Bearer 令牌调用，通常是 OAuth 2.0 或 OIDC 签发的 JWT。
- oauth2：标准 OAuth 2.0 流程，机器对机器场景用 clientCredentials，用户委托场景用授权码流程。
- openIdConnect：在 OAuth 2.0 之上叠加身份层，可复用 OIDC discovery 与 ID 令牌。
- mutualTLS：双向证书认证，提供传输层与身份的双重绑定，适合高保障场景。

## 三、协商流程与客户端义务

客户端拿到卡片后的标准动作序列是：解析 securitySchemes，与自身可用的凭据类型求交集；若交集为空，应显式失败而不是"裸调"；若多个方案可选，应选择保障强度最高的一种，而不是实现最省事的一种。服务端义务则是对称的：声明了的方案必须完整实现，未声明的方案必须拒绝，避免实现与声明漂移。

一个最小化的客户端选型伪码：

```python
def pick_scheme(card, my_credentials):
    declared = [s for s in card.security]          # 候选方案列表
    usable = [s for s in declared if s.type in my_credentials]
    if not usable:
        raise AuthNegotiationError("无可用的认证方案，拒绝调用")
    return max(usable, key=lambda s: strength_rank(s.type))
```

## 四、选型决策清单

为具体场景挑选方案时，按下列清单逐项核对：

1. 调用主体是纯机器还是代表用户？机器优先 clientCredentials，用户委托优先授权码加 PKCE。
2. 是否跨组织？跨组织优先标准 OAuth 2.0 / OIDC，避免私有 apiKey 体系带来的对账成本。
3. 风险等级多高？涉及资金、敏感数据或高成本算力时叠加 mTLS。
4. 密钥轮换频率要求？短期凭据优先于长期静态密钥。
5. 是否需要委托链追溯？需要则引入令牌交换，而不是让下游 Agent 复用上游令牌。

## 五、常见误配与小结

实践中最常见的三类误配是：卡片声明 oauth2 但实现仍接受明文 apiKey；security 数组把弱方案排在前面诱导客户端降级；tokenUrl 指向与卡片不同源的域而未做任何说明。三者分别对应实现漂移、协商陷阱与端点伪造。声明只是入口，真正的安全取决于声明、实现、验证三者一致，这一原则贯穿后续所有认证篇目。
