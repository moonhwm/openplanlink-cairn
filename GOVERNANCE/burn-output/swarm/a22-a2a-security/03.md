# 03 API Key 认证：适用边界与实施规范

API Key 是最古老的机器认证方式：一串随机字符串，随每个请求发送，服务端查表比对。它的价值在于实现成本近乎为零，几乎所有网关与框架都原生支持；它的代价在于凭据长期有效、无法表达细粒度授权、泄露后影响面大。本篇讨论在A2A场景中何时可以用 API Key、怎样用才安全、何时必须升级。

## 一、原理与安全属性

API Key 的本质是一个共享秘密。它同时承担两个角色：身份标识（这是哪个客户端）与身份验证（证明确实是它）。这两个角色耦合带来固有问题：

- 无法区分"持钥者"与"授权者"，任何拿到钥匙的主体都能完全冒充。
- 不含过期时间与签发者信息，服务端只能靠黑名单或全量轮换来止损。
- 常被放在查询参数中传递，落入访问日志与 Referer 头，扩大泄露面。

因此 API Key 的适用边界是：低价值接口、内网或网关后端、原型与沙箱环境。凡是跨组织、涉及敏感数据或高成本操作的 A2A 调用，都不应只依赖 API Key。

## 二、泄露面盘点与缓解措施

把密钥可能流经的位置列成清单，逐点加固：

1. 传输层：强制 HTTPS，禁止查询参数携带，统一放在 Authorization 或自定义请求头。
2. 客户端存储：使用环境变量或密钥管理服务注入，禁止硬编码进代码仓库与镜像。
3. 服务端存储：只存散列值，与加盐口令同等对待。
4. 日志与链路追踪：在网关与日志中间件中默认脱敏。
5. 版本管理与协作平台：部署预提交扫描规则，拦截疑似密钥的字符串。

服务端比对应使用恒定时间比较，避免时序侧信道逐字节猜解：

```python
import hmac, hashlib, os

def verify_api_key(presented: str, stored_hash: str) -> bool:
    digest = hashlib.sha256(presented.encode()).hexdigest()
    return hmac.compare_digest(digest, stored_hash)
```

## 三、实施规范清单

如果确定使用 API Key，至少落实以下规范：

- 格式：使用密码学随机数生成，保留可识别前缀（如 a2a-live-、a2a-test-）便于日志分类与泄露识别。
- 一客一钥：每个下游 Agent 独立发钥，绝不为管理方便共用一把钥匙。
- 作用域标注：在密钥元数据中记录允许的方法、来源网段与速率上限。
- 轮换机制：支持双钥并行期，新旧钥重叠七至三十天，避免轮换造成中断。
- 吊销通道：提供即时吊销接口，并对连续鉴权失败的钥触发告警与自动冻结。
- 审计字段：每个请求记录密钥标识（非密钥本身）、时间、方法与结果码。

## 四、轮换与到期策略示例

一个可执行的轮换流程伪码如下，把"发新、并行、切换、回收"四步固化到运维脚本：

```text
rotate(client_id):
  1. new_key = gen(prefix="a2a-live-", entropy=256bit)
  2. register(new_key, expiry=+180d, overlap_with=old_key)
  3. notify(client_id, activate=new_key.id, deadline=+14d)
  4. at(deadline): revoke(old_key.id); audit_log("rotated", client_id)
```

## 五、何时升级到 OAuth 2.0

出现以下任一信号就应把该客户端迁移到 OAuth 2.0 客户端凭据模式：需要按任务级别做授权而非全有全无；需要短期令牌降低泄露窗口；需要多环境统一发凭据；需要与第三方组织的身份体系对接。迁移路径是：先让服务端同时接受 API Key 与 Bearer 令牌，观察调用方逐步切换，再设定 API Key 的强制下线日期。总之，API Key 是可接受的起点，但不应是跨组织 A2A 的终点。
