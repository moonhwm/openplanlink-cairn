# 04 OAuth 2.0 客户端凭据授予：机器对机器认证的基石

当两个 Agent 互相调用、背后没有在线用户时，OAuth 2.0 的客户端凭据授予（client_credentials）是事实标准：客户端用自己的身份向授权服务器换一张短期访问令牌，再携令牌访问目标 Agent。它把"长期秘密的暴露面"压缩到与授权服务器的一次交互上，其余所有请求都只携带短命凭据。本篇覆盖流程、客户端鉴权方式、范围最小化与服务端校验要点。

## 一、标准流程与令牌语义

流程只有两步：客户端向 token 端点 POST 身份与所需 scope；授权服务器校验后签发访问令牌。令牌通常是 JWT，携带 iss（签发者）、aud（受众，应为被调 Agent）、sub 或 client_id（调用方身份）、scope、exp 等声明。关键语义是：aud 必须精确匹配目标 Agent，防止令牌被拿到别处重放；exp 控制泄露窗口，机器场景建议十五分钟到一小时之间。

```http
POST /oauth2/token HTTP/1.1
Host: idp.example.com
Content-Type: application/x-www-form-urlencoded
grant_type=client_credentials
&client_id=svc-travel-planner
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=<由客户端私钥签名的短命JWT>
&scope=tasks:write
```

## 二、客户端鉴权的三种方式

token 请求本身的客户端鉴信方式决定了整体强度，从弱到强有三档：

1. client_secret：共享秘密随表单提交，实现简单，但秘密静态存在，泄露即可冒充。仅适合授权服务器完全自管的内网。
2. private_key_jwt：客户端用私钥签一个短命 JWT 作为断言，授权服务器只持有公钥。秘密不出门，天然支持无共享秘密的跨组织协作。
3. mTLS 绑定（RFC 8705）：令牌与客户端证书绑定，即使令牌被截获，没有证书也无法使用，是金融级场景的首选。

跨组织 A2A 建议直接从第二档起步，公钥通过托管好的 JWKS 端点分发，禁止用邮件或聊天工具传密钥文件。

## 三、scope 设计与最小化

scope 是授权服务器对"这个客户端能做什么"的编码。设计准则有四条：按资源与动作命名（tasks:write 而非模糊的 agent:all）；粒度对齐业务风险，高成本技能单列；禁止通配符 scope 进入生产；默认不签发未声明的 scope。服务端收到令牌后要独立复核 scope，不因授权服务器"应该检查过"而跳过——纵深防御要求最后一道门自己上锁。

## 四、服务端校验清单

被调 Agent 校验访问令牌时逐项核对：

- 签名：用授权服务器 JWKS 验签，算法白名单限定 RS256 / ES256，拒绝 none 与算法混淆。
- iss：必须等于配置的签发者。
- aud：必须包含本 Agent 的资源标识。
- exp / nbf：过期与未生效检查，容忍不超过六十秒的时钟偏移。
- scope：与当前方法所需权限比对。
- jti：可选登记以支持吊销检查与重放审计。
- 绑定令牌额外校验确认码（cnf）与通道证书一致。

```python
claims = jwt.decode(token, key_resolver="jwks", algorithms=["RS256", "ES256"],
                    audience=SELF_ID, issuer=EXPECTED_ISS)
require_scopes(claims["scope"], needed={"tasks:write"})
```

## 五、常见失败模式与小结

典型故障包括：令牌缓存不设上限复用到过期前一秒，导致边界时刻大面积 401；多个目标 Agent 共用同一个 aud；把刷新令牌语义错用在无刷新场景。正确姿势是缓存带提前量（如 exp 前六十秒刷新）、一目标一令牌、失败时结构化记录 www-authenticate 响应头辅助排障。客户端凭据授予简洁但不简陋，把它与 private_key_jwt 或 mTLS 结合，即可支撑跨组织机器身份的高保障认证。
