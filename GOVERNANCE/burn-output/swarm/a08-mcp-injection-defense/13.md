# 多租户MCP服务器隔离

## 一、多租户带来的新问题

当MCP服务器从单人本地工具演进为团队或平台级服务时，租户隔离成为安全设计的第一课题。多租户环境下，攻击者可以是合法租户之一：他们能合法调用工具、上传内容、触发任务，因此攻击不再需要"入侵"，只需利用隔离缝隙。风险包括：跨租户数据读取（A租户的查询返回B租户的数据）、跨租户注入（A租户把载荷写入共享存储，B租户的代理读取后触发）、资源挤占（A租户的滥用耗尽共享配额导致B租户拒绝服务）、以及侧信道（通过错误信息、时序、日志推断他人数据）。单机单用户场景中不成立的威胁模型，在多租户下全部成立。

## 二、隔离的三种架构模式

按隔离强度与成本排序有三种模式。模式一：共享服务器加逻辑隔离，所有租户共用服务器实例，每次请求携带租户标识，数据访问层强制过滤。成本最低但隔离依赖代码正确性，一次遗漏即穿透。模式二：按租户分池，若干租户共享一个实例池，池间物理分开，爆炸半径限于池内。模式三：租户独享实例（容器或命名空间级），配额与网络策略独立，隔离最强成本最高。选择依据是数据敏感度与合规要求：内部工具平台常用模式一配合严格代码审查；面向外部客户的服务至少模式二；高合规场景用模式三。关键是显式决策而非默认滑入模式一。

## 三、租户标识的端到端传递

逻辑隔离的命脉是租户标识不可伪造、不可丢失。要求：标识在认证阶段颁发（随会话令牌下发），全程由宿主与服务器框架传递，禁止从模型生成的内容中解析租户（攻击者可让模型伪造）；所有数据访问必须经过带租户过滤的仓储层，禁止裸查询；跨层调用（服务器再调下游服务）时标识以受信任头传递并签名，防止中间被剥离。数据层的强制过滤器是最后防线：

```python
class TenantRepo:
    def __init__(self, db, tenant_id: str):
        self._scope = db.where(tenant_id == verify(tenant_id))

    def find(self, doc_id: str) -> Doc:
        row = self._scope.documents.get(doc_id)
        if row is None:
            raise NotFound()          # 跨租户访问与不存在同响应，避免探测
        return row
```

注意"同响应"细节：跨租户访问返回与不存在一致的错误，防止攻击者借此枚举其他租户的文档标识。

## 四、共享存储中的注入传播

多租户特有的一条攻击链是"注入经共享存储传播"：A租户在共享知识库、共享工单池或共享缓存中写入载荷，B租户的代理检索到该内容并执行指令。防御要点：共享内容写入时即扫描（写入过滤与输出过滤共用规则库），可疑内容直接拒收或标记隔离；检索结果按租户可见性过滤，跨租户内容默认不可见，确需共享的白名单条目单独评审；共享内容的信任等级永远低于租户私有内容，进入上下文时使用更严格的围栏。缓存层也要按租户分键，防止A租户的预热缓存被B租户命中，键设计必须包含租户标识并经过校验。

## 五、 noisy neighbor 与配额治理

资源滥用在多租户下会外溢为对其他租户的伤害，配额体系因此是隔离的一部分。配额维度包括：每租户每分钟工具调用数、单次结果大小上限、并发会话数、存储与工作区容量、令牌消耗预算。超限处置分层：软限触发降级（返回摘要而非全文），硬限触发限流（请求排队或拒绝），预算耗尽自动暂停任务并通知租户管理员。配额策略要区分工具类别——只读检索类宽松些，计费与高危类严格些。所有配额事件可观测，平台方据此发现滥用租户并执行治理动作。示例配置：

```yaml
tenant_quota:
  default:
    tool_calls_per_minute: 60
    max_result_bytes: 262144
    concurrent_sessions: 4
  tiers:
    billing_enabled:
      spend_per_day: hard_limit
      confirm_every_call: true
```

## 六、运维与审计的租户边界

隔离不止于数据面，运维面同样要划界。日志与审计记录必须包含租户标识，且查询日志的权限本身按租户隔离——运维人员查看A租户日志需相应授权，防止审计通道成为泄露通道。监控告警按租户分维度聚合，异常（如某租户外发类调用激增）只在对应租户范围内触发调查，避免租户行为互相污染基线。事件响应时，涉及具体租户数据的操作（如取证导出）要走该租户的授权流程。这些细节常被忽略，却是合规审查的重点项。

## 七、验证隔离的测试方法

隔离声明需要测试证明。三类测试必做：穿透测试，用A租户凭证尝试以各种方式（改请求参数、伪造头、重放他人令牌、注入内容诱导）访问B租户资源，全部应失败且响应一致；传播测试，在A租户可控的每个共享位置植入无害标记载荷，验证B租户代理的全量行为不因标记而改变；故障注入测试，模拟某租户资源耗尽，验证其他租户服务不受影响。这三类测试纳入CI流水线与季度红队，形成隔离的持续验证，而不是上线时一次性检查。

## 八、小结

多租户隔离把威胁模型从"防外部攻击者"扩展为"防合法租户越界"：架构模式显式选型、租户标识端到端强制传递、共享存储写入即扫描、配额治理防外溢、运维审计同界、测试持续验证。其中标识传递与仓储强制过滤是生命线，共享内容的注入传播是多租户独有的高危链路。把这几件事做扎实，MCP服务器才能安全地从个人工具成长为平台服务。
