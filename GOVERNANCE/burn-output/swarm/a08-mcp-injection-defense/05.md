# MCP威胁建模方法：资产、入口与路径

## 一、威胁建模的定位

威胁建模是在设计阶段系统性回答三个问题的方法：系统里有什么值得保护（资产）、攻击者能从哪里进来（入口）、进来后能走多远（路径）。MCP应用因其"文本驱动动作"的特性，传统Web威胁模型的组件清单不再完全适用，必须针对上下文、工具、服务器、会话这些新组件重建模型。本篇给出一套可直接落地的四步法：资产盘点、入口枚举、路径推演、控制映射，并以一个文件助手代理为贯穿案例。

## 二、第一步：资产盘点

资产按敏感度与可变性分四层，每层标注责任方：

- 上下文层：系统提示（泄露则暴露防护逻辑）、对话历史（含用户隐私）、工具描述清单（暴露能力面）。
- 凭据层：服务器持有的API令牌、数据库口令、云平台密钥，模型若能经工具读取即为高危资产。
- 数据层：业务数据库、文档库、代码仓库中的业务数据，按分级（公开/内部/机密）标注。
- 状态层：文件系统、配置中心、基础设施即代码，特点是可被工具直接改写，损害往往是持久的。

盘点产出一张资产登记表，字段包括资产名称、所在位置、访问它的工具、敏感级别、泄露或破坏后的影响。这张表的价值在于：后续所有确认等级、过滤规则、权限范围都能追溯到具体资产，避免"为防而防"的空转。

## 三、第二步：入口枚举

入口是任何"攻击者可写、模型可读"的通道。逐一检查MCP数据流可得：

```
入口清单模板
1. 用户消息框                  直接注入
2. 工具结果通道（每工具一条）   间接注入
3. 资源订阅推送                间接注入（异步到达）
4. 工具/服务器描述元数据       描述注入（供应链）
5. 服务器配置与代码            恶意/被篡改服务器
6. 记忆与缓存文件              持久化注入
7. 传输通道                    窃听与中间人
```

对每个入口标注两点：内容是否经过过滤、来源可信等级如何。未过滤且低可信的入口就是优先整改对象。实践中最容易遗漏的是异步资源订阅：内容在非用户主动操作时进入上下文，往往绕过了为交互路径设计的检查点。

## 四、第三步：路径推演

路径是"从入口到资产"的完整链条。以文件助手为例做三条推演。路径一（外泄）：攻击者向共享目录投放带注入文本的文档 → 用户让助手总结该目录 → 助手读取文档，载荷进入上下文 → 模型被诱导调用HTTP请求工具，把目录清单与若干文件内容作为参数外发。路径二（持久化）：载荷要求助手"把提醒规则写入配置以便长期执行" → 助手调用写文件工具修改启动配置 → 后续每次会话自动加载恶意规则。路径三（越权）：载荷要求读取环境变量文件"以排查问题" → 模型读取后，载荷再要求把内容写入一个可通过公开链接访问的笔记。

每条路径推演后，标注现有控制点与缺口。路径一的缺口是HTTP工具无确认；路径二的缺口是写入内容无扫描；路径三是凭据文件本不该对工具可读。推演的结果是一张"路径—控制"缺口表。

## 五、第四步：控制映射

将缺口表与三大支柱对齐，形成整改计划：

```yaml
path_1_exfiltration:
  entry: shared_dir_documents
  asset: business_documents
  controls:
    - pillar: output_filter
      rule: outbound_args_scan_for_pii
    - pillar: confirmation_gate
      rule: http_request_always_confirm
path_2_persistence:
  controls:
    - pillar: output_filter
      rule: write_content_injection_scan
    - pillar: instruction_isolation
      rule: config_paths_deny_list
path_3_privilege:
  controls:
    - pillar: least_privilege
      rule: env_and_secret_paths_not_readable
```

映射时遵循"每条路径至少两个独立控制"原则，确保单点失效不成灾。整改项按风险排序：先堵通向高敏资产的路径，再补资源耗尽与侦察类缺口。

## 六、模型驱动的建模维护

威胁模型不是一次性文档，而是随代码演进的活资产。建议把资产登记表与路径规则放进版本库，与服务器代码同仓评审；新增工具时强制回答三个问题：它读写哪些资产、入口内容会不会流经它、需要什么确认等级。更进一步，可以用模型辅助建模：把工具清单与数据流描述喂给模型，让它枚举可能的滥用链作为初稿，再由人工评审筛选。模型的发散能力适合发现"人想不到的组合路径"，但结论必须经过验证，不可直接当成事实。

维护节奏上，每次发布前做增量评审，每季度做一次全量重建，重大工具变更或发生安全事件后立即触发专项更新。度量的指标是覆盖率：登记资产中被控制点覆盖的比例、路径表中被双控制覆盖的比例。

## 七、案例分析：一次建模演练的产出

以某团队的实际演练为例说明产出形态。该团队的代理接入了工单系统、代码仓库与消息发送三类工具，首轮建模即发现七条路径中三条缺乏双控制。最严重的一条是：工单正文（L4入口）→模型总结→调用仓库工具创建分支并提交代码→推送到远端。虽然代码提交本身属正常能力，但推远端触发CI流水线，等于外部内容间接获得了执行代码的通道。整改方案是在推送动作前增加确认门，并在CI配置文件的写入内容上增加注入扫描。第二轮复推演时，攻击者即使劫持模型，最多只能产生本地分支，无法触达流水线。

该案例还揭示一个方法论要点：建模时应优先推演"组合能力"而非单个工具。单个工具看似无害，组合起来却可能打通从外部内容到代码执行的完整链路，这正是MECE分解容易被忽略的跨类路径。

## 八、小结

四步法把MCP威胁建模固化为可执行的工程流程：资产盘点明确保护对象，入口枚举找出全部注入面，路径推演暴露真实攻击链，控制映射把缺口转成三支柱整改项。模型可以辅助发散但不可替代评审，覆盖率指标则保证防护不因系统演进而悄然失守。这套方法为后续所有具体机制提供了需求来源与优先级依据。
