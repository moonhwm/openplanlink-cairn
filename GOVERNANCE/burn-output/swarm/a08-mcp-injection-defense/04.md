# 工具滥用攻击分类学

## 一、为什么需要分类学

"工具滥用"是一个宽泛说法，混谈会导致防御错位：针对外泄的防御挡不住破坏，针对越权的防御挡不住资源耗尽。建立分类学的目的，是把模糊风险拆解为可枚举、可对应措施、可度量覆盖率的类别，让每类滥用都有明确的owner、检测信号与阻断手段。本篇按攻击目标将MCP场景下的工具滥用分为六大类，构成后续章节展开的骨架。

## 二、六大类别定义

- 外泄类（Exfiltration）：诱导模型把上下文中的敏感数据作为参数传给外发型工具，如发送邮件、HTTP请求、写公开存储。特点是数据单向流出，往往在人不知情时完成。
- 破坏类（Sabotage）：调用删除、覆写、缩容、断流等工具直接损害系统状态，如删除数据库表、覆盖配置文件、关闭生产服务。
- 越权类（Privilege Escalation）：在当前任务不需要的场合调用高权限工具，或用低风险工具组合出高风险效果（先读凭据文件，再用凭据调用管理接口）。
- 持久化类（Persistence）：滥用具备写入能力的工具植入后门，例如向计划任务、启动脚本、记忆文件写入载荷，使攻击在会话结束后仍可复发。
- 资源耗尽类（Denial of Wallet/Service）：诱导高频调用计费工具或重计算工具，造成账单爆炸；或构造递归调用链耗尽上下文与并发。
- 侦察类（Reconnaissance）：滥用只读工具枚举系统结构，如列出全部工具、读取环境变量、遍历目录，为后续攻击铺路。本身破坏小但常是前置步骤。

## 三、攻击树的层次化表达

六类滥用可以组织成一棵攻击树，根节点是"通过模型滥用工具"，每个分支标注达成条件，便于防御方寻找最小割集：

```
通过模型滥用工具
├── 外泄数据
│   ├── 存在外发型工具可用
│   └── 模型被诱导/参数被构造
├── 破坏状态
│   ├── 存在破坏型工具且权限过大
│   └── 调用未触发确认
├── 权限提升
│   ├── 凭据可被读取工具访问
│   └── 高权限工具无场景限制
├── 持久化
│   ├── 存在可写启动项/记忆的路径
│   └── 写入内容未过滤
├── 资源耗尽
│   ├── 无速率限制
│   └── 无预算上限
└── 侦察
    ├── 只读工具无范围限制
    └── 枚举结果可回流给模型
```

从割集角度：外泄类只要"移除外发型工具或对其强制确认"即可阻断；持久化类必须"过滤写入内容+收紧可写路径"双管齐下。

## 四、类别与防御支柱的映射矩阵

| 滥用类别 | 指令隔离的作用 | 确认门的作用 | 输出过滤的作用 |
|----------|----------------|----------------|----------------|
| 外泄类 | 降低诱导成功率 | 外发调用强制确认 | 拦截含敏感数据的参数 |
| 破坏类 | 防止任务劫持 | 高危操作双人复核 | 限制破坏性参数形态 |
| 越权类 | 声明工具适用场景 | 场景外调用需说明 | 凭据形态检测告警 |
| 持久化类 | 内容降权 | 写启动项类必确认 | 写入载荷扫描 |
| 资源耗尽 | 无直接作用 | 大额调用前预警 | 速率与配额强制 |
| 侦察类 | 减少工具暴露 | 敏感枚举需授权 | 枚举结果脱敏 |

矩阵显示三类支柱互补性极强：指令隔离是概率性防线，确认门是决定性防线，输出过滤是参数级兜底。资源耗尽类几乎不依赖隔离，必须靠配额硬限制，这说明任何组织若只部署单支柱必然存在系统性盲区。

## 五、检测信号与代码骨架

每类滥用应配置专属检测规则，以参数审计器为例：

```python
SINK_TOOLS = {"send_email", "http_request", "write_public"}

def audit_call(call: ToolCall, ctx: Context) -> Verdict:
    if call.tool in SINK_TOOLS:
        leaked = find_secrets_or_pii(call.arguments)
        if leaked:
            return Verdict.BLOCK("外泄类：参数包含敏感数据")
    if call.tool in DESTRUCTIVE_TOOLS:
        if not call.has_user_visible_reason():
            return Verdict.CONFIRM("破坏类：缺少可解释动机")
    if ctx.calls_last_minute(call.tool) > LIMIT:
        return Verdict.BLOCK("资源耗尽：超出速率")
    if call.tool in ENUM_TOOLS and ctx.task_scope_exceeded(call):
        return Verdict.CONFIRM("侦察类：超出任务范围")
    return Verdict.ALLOW()
```

该骨架体现"分类—信号—动作"三段式：类别决定看哪些信号，信号决定放行、确认还是阻断。上线后应按类别统计触发量，形成滥用基线，异常波动即红队演练或真实攻击的信号。

## 六、组合攻击与类别演化

真实攻击常跨类别串联：先侦察（列工具）→再越权（读凭据）→后外泄（发邮件）→最后持久化（写计划任务）。防御设计必须假设攻击者会寻找各类别中防护最弱的一环，因此覆盖率度量要以"类别×支柱"为单位打分，而不是统计部署了多少个安全功能。类别也会随生态演化：新的工具形态（如具备支付能力的工具）会催生新的滥用类别，分类学应定期评审更新，保持MECE性质。

## 七、按类别设计恢复能力

阻断之外还需考虑"失守后怎么办"，恢复手段同样应按类别设计。外泄类一旦发生，数据无法追回，重点转为评估泄露范围：哪些字段流出、流向何处、是否触发合规通报义务，因此调用日志必须完整记录外发型工具的收件方与数据摘要。破坏类依赖回滚：文件系统用快照、数据库用备份恢复点、基础设施用声明式重建，恢复演练应纳入例行验证。持久化类要求全面排查：不仅删除已知后门，还要扫描同类写入路径是否被埋入相似载荷，防止"删一处留三处"。资源耗尽类需要账单告警与自动熔断联动，超过阈值立即停用相关工具并冻结会话。侦察类看似无需恢复，但应视为事件前兆，收紧枚举类工具的暴露面并复盘侦察为何得逞。

把恢复能力纳入分类学，是因为它反向约束了前述防御设计：没有回滚能力的破坏型工具，其确认等级必须更高；无法审计收件方的外发型工具，原则上不应被接入。防御与恢复的匹配程度，是衡量一个MCP部署工程成熟度的重要标尺。

## 八、小结

六类滥用各自对应不同的检测信号与阻断手段，只有分类治理才能避免防御错位。攻击树帮助找到最小割集，映射矩阵确保三支柱互补覆盖，组合攻击的常态则要求以矩阵化覆盖率而非功能数量来度量防护成熟度。后续章节将针对每类滥用所需的具体机制逐一展开。
