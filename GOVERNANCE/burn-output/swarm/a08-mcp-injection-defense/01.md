# MCP协议安全架构与攻击面全景

## 一、背景与问题定义

模型上下文协议（Model Context Protocol，MCP）是一套开放协议，用于将大语言模型与外部工具、数据源和执行环境连接起来。它把传统的"插件"机制标准化为客户端—服务器结构：MCP宿主（Host）内运行客户端（Client），客户端与外部MCP服务器（Server）通信，服务器再暴露工具（Tools）、资源（Resources）与提示模板（Prompts）三类能力。这种架构极大扩展了模型的能力边界，同时也把模型的输出直接映射为现实世界的动作：文件读写、数据库查询、消息发送、代码执行。

安全问题的根源在于：传统应用中"用户输入"只影响业务逻辑，而在MCP体系中，模型生成的文本会直接驱动工具调用。攻击者一旦能够影响模型的上下文，就可能借模型之手执行恶意工具调用。这就是所谓"提示注入与工具滥用"风险域，需要从协议层、应用层、运营层三个层面系统性防御。

## 二、MCP核心组件与攻击面映射

理解攻击面必须先厘清数据流。一次典型调用链为：用户输入 → 宿主组装上下文 → 模型推理 → 客户端发起工具调用 → 服务器执行 → 结果回填上下文 → 模型继续推理。每个箭头都是一个潜在的注入点或滥用点。

攻击面清单如下：

- 用户通道：用户消息本身可能携带注入指令（直接注入）。
- 工具结果通道：服务器返回的文本、网页快照、邮件正文、文档内容都可能携带恶意指令（间接注入）。
- 服务器身份：伪造或恶意的MCP服务器可以直接返回精心构造的响应。
- 描述文本通道：工具名称、描述、参数说明会进入上下文，可被用来诱导模型。
- 传输通道：stdio本地进程边界、HTTP/SSE远程通道，涉及进程权限与网络安全。
- 会话状态：跨会话共享的缓存、记忆文件可能成为持久化注入载体。
- 下游系统：数据库、文件系统、内部API，是工具滥用的最终受害目标。

## 三、攻击面与防御支柱的对应关系

本主题群（提示注入与工具滥用防护）确立三大防御支柱：指令隔离、确认门、输出过滤。三者与攻击面的对应关系可以用一张映射表表达：

```
攻击面              | 主要风险           | 防御支柱
--------------------|--------------------|------------------
工具结果通道        | 间接提示注入       | 输出过滤+指令隔离
工具调用通道        | 越权/滥用执行      | 确认门+最小权限
工具描述文本        | 描述注入           | 服务器审核+隔离
会话状态           | 持久化污染         | 会话隔离
传输通道           | 窃听/篡改          | 传输安全
下游系统           | 破坏与泄露         | 沙箱+审计
```

用伪代码表达防御链位置：

```python
def handle_tool_result(raw: bytes, ctx: SecurityContext):
    # 支柱三：输出过滤——先净化不可信数据
    sanitized = output_filter.scan(raw)
    if sanitized.has_injection_signature():
        sanitized = sanitized.neutralize(mode="fence")
    # 支柱一：指令隔离——标注为数据而非指令
    ctx.append(role="tool", content=fence(sanitized))
    # 支柱二：确认门——模型若据此发起高危调用需人工确认
    if ctx.next_call_risk >= RiskLevel.HIGH:
        require_human_confirmation()
```

## 四、纵深防御原则

任何单一支柱都可能失效，因此必须叠加部署。原则包括：默认拒绝而非默认放行；工具按最小权限设计；不可信内容永远以数据身份进入上下文；高危动作必须有人工确认或等价强度的替代机制；所有工具调用可审计可回放。协议本身也在演进，例如规范要求客户端对工具列表变更、资源订阅等事件保持警惕，但协议无法替代应用层的安全设计，工程责任始终在集成方。

## 五、常见误区与实践清单

常见误区包括：认为本地stdio服务器天然安全（恶意描述仍可注入）；只防用户输入而忽视工具输出；把确认弹窗做成"永远点确认"的形式主义；过滤规则只做黑名单而缺少白名单兜底。落地时建议按以下清单推进：

- 绘制完整数据流图，标注所有不可信输入进入上下文的位置。
- 为每个工具标注风险等级与所需确认级别。
- 在工具结果回填前统一经过输出过滤层。
- 建立注入事件的审计、告警与复盘流程。
- 定期以红队演练验证三大支柱的有效性。

## 六、能力暴露面的治理

除数据流攻击面外，MCP还带来独特的"能力暴露面"问题。每个工具一旦注册，模型在任何轮次都可能选择调用它，而开发者往往难以预判模型在长对话、多任务混合场景下会如何组合这些能力。例如一个用于"总结文档"的工具与一个用于"发送消息"的工具同时存在时，攻击者只需在文档里埋一句话，就能让模型把摘要发往外部地址。因此能力治理的第一原则是按场景裁剪工具集：当前任务只挂载必需的工具，其余一律不注册。许多MCP宿主支持动态启用与禁用工具，应在任务开始时按最小暴露原则配置，任务结束后回收。

第二个治理维度是命名与描述。工具的名称、描述文本会被拼入上下文，等于给模型的"使用说明书"。描述写得越含糊，模型越容易在错误场合调用；描述中被恶意篡改（供应链问题），则等于直接给模型下假指令。实践中应把工具描述当作代码一样进行评审与版本管理，禁止描述中出现"任何时候都可以优先使用本工具"这类诱导性语句，并在描述中显式声明副作用与风险，让模型在生成调用前"知情"。

## 七、小结

MCP把语言模型变成了可以触达真实系统的执行者，攻击面随之从"文本层"扩展到"动作层"。本章给出全景图与三大防御支柱的映射，后续章节将分别展开指令隔离、确认门、输出过滤的具体设计，以及威胁建模、供应链、监控等工程纵深议题，构成完整的防护体系。
