# 沙箱执行环境设计

## 一、沙箱在MCP体系中的角色

沙箱是环境层隔离的核心，它承认一个现实：无论上层防御多努力，总有一些调用会被执行，因此必须保证"被执行也不出事"。沙箱通过限制工具执行时可触达的资源——文件系统、网络、进程、权限——把副作用的爆炸半径压缩到可接受范围。在MCP架构里，沙箱的作用点有三个：MCP服务器自身的运行环境、特定工具（尤其是代码执行、命令执行类）的临时执行环境、以及代理宿主进程的整体权限边界。三者层次不同但设计原则一致：默认无权，显式授予，可审计。

## 二、资源维度的隔离清单

一份可直接使用的沙箱基线清单：

- 文件系统：以只读方式挂载任务必需目录；写入仅允许指向专用工作区；敏感路径（凭据目录、配置目录、系统目录）完全不映射；工作区设配额与文件数上限。
- 网络：默认禁止出站；按域名白名单放行业务必需端点；禁止访问元数据服务地址与内网管理段；DNS解析同样过白名单。
- 进程与系统调用：禁止派生子进程或严格限制；能力列表（capabilities）最小化；资源上限覆盖CPU时间、内存、进程数。
- 身份：以低权限专用账户运行，不属于特权组；每个会话或任务独立身份，避免共享服务账户。
- 时间与环境：设定执行超时与空闲超时；环境变量白名单注入，不继承宿主全部环境。

以容器化为例的最小配置片段：

```yaml
runtime: sandbox
security:
  readOnlyRootFilesystem: true
  runAsNonRoot: true
  capabilities: [""]            # 清空全部能力
  seccompProfile: runtime/default
mounts:
  - {path: /workspace, mode: rw, quota: 512Mi}
  - {path: /taskdocs, mode: ro}
network:
  default: deny
  allow:
    - {host: api.internal, port: 443, proto: tcp}
limits:
  cpuSeconds: 30
  memoryMi: 1024
  wallClockTimeout: 120s
```

## 三、分级沙箱策略

不同风险的工具匹配不同强度的沙箱，避免"一刀切"要么过松要么过严。建议四级：S0无沙箱（纯计算、格式转换类本地函数）；S1轻量隔离（进程级限制，共享文件系统但只读为主）；S2容器隔离（如上基线，绝大多数外部数据处理工具）；S3强隔离（一次性虚拟机或微型虚拟化，用后即焚，用于代码执行、打开不可信文件等高危操作）。分级的依据来自威胁建模中该工具触达的资产等级：能触达机密数据或不可逆状态的，至少S2起步；执行任意代码的，必须S3。工具的沙箱等级应在注册时声明并锁定，运行期不可由对话动态调整。

## 四、网络出口的特殊地位

在数据外泄链条中，网络出口是最后一跳，因此出口管控有极高的杠杆效应。设计要点：白名单精确到域名与端口而非网段；对允许的端点启用内容检查，出站请求体过敏感数据扫描（与输出过滤共享规则库）；统一出口代理强制执行，禁止工具直连；代理日志记录五元组与载荷摘要，作为外泄调查的依据。一个常被忽视的场景是DNS与重定向滥用：工具通过DNS查询或HTTP重定向把数据编码外带，出口代理必须解析并校验重定向目标，DNS仅允许指向受控解析器。代码示例中把出站检查挂在代理层：

```python
def egress_check(request: HttpRequest, ctx: SessionContext) -> Verdict:
    if not in_allowlist(request.host, request.port):
        return BLOCK("出口不在白名单")
    if request.has_redirect_chain():
        for hop in request.redirects():
            if not in_allowlist(hop.host, hop.port):
                return BLOCK("重定向目标不在白名单")
    findings = dlp_scan(request.body)
    if findings:
        return BLOCK("出站内容包含敏感数据", audit=findings)
    return ALLOW()
```

## 五、逃逸面与运维纪律

沙箱不是银弹，要正视逃逸面并配套纪律。已知风险包括：宿主内核漏洞导致容器逃逸，因此内核与运行时要保持更新并启用安全计算配置；共享内核侧信道，高敏感任务应升级到微型虚拟机；挂载卷成为桥梁，工作区内容可能被用于攻击宿主上的其他服务，卷应按会话隔离且用后清理；供应链投毒的沙箱镜像，镜像统一构建、签名验证、来源固定。运维纪律方面：沙箱配置纳入版本管理与定期评审；任何"临时放开"的豁免必须限时、留痕、双人批准；定期做逃逸演练验证配置漂移，漂移即告警。沙箱配置漂移是实践中最常见失效原因，往往源于某次故障排查时的临时修改未被回滚。

## 六、与确认门和输出过滤的协同

沙箱与其他支柱的协同体现在信息流上。沙箱产生的安全事件（越权访问被拒、出站被拦）应回传给确认门作为上下文：例如某工具在沙箱内连续三次尝试访问未授权路径，其后同会话的任何调用都应升级确认。输出过滤则依赖沙箱提供的资源边界做兜底：即使过滤器漏检，外发数据的通道也已被出口管控限定在白名单端点内，攻击者拿不走数据。三者形成"拦在调用前、限在执行中、堵在出口处"的闭环，任何单点缺陷都有下游弥补。

## 七、小结

沙箱设计遵循"默认无权、显式授予、分级匹配、强制出口"四原则，把工具滥用的物理后果锁进笼子。文件系统只读挂载、网络白名单与统一出口代理、一次性执行环境、配置漂移纪律，是落地时最值得优先投入的几件事。沙箱的价值在于把"模型被骗"的损失上限从"整个系统"压缩到"一个工作区"，为整个防御体系提供了最后也是最难被绕过的物理底线，值得每个MCP部署认真对待。
