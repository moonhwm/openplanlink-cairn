# 内存泄漏与OOM问题排查：hidumper、hilog与Profiler协同分析

> 摘要：本文讲解HarmonyOS应用内存问题的排查全流程：内存指标采集（hidumper快照、内存曲线）、泄漏定位（对象持有链分析、快照对比）、常见泄漏模式清单与修复验证方法。

## 一、内存问题的三种形态

内存缺陷在HarmonyOS应用中表现为三种形态。急性OOM：单次加载超大数据（未压缩图片、超长列表一次构建）直接耗尽配额，进程被系统终止；慢性泄漏：对象被意外持有无法回收，内存随使用时长持续爬升，最终在重度用户身上爆发；伪泄漏：缓存设计不当只增不减，技术上不是泄漏但效果相同。三种形态的排查路径不同：急性看崩溃时刻的分配栈，慢性看增长曲线的持有链，伪泄漏看缓存策略的淘汰逻辑。排查的第一步永远是拿到可靠的数据，而不是直接猜测代码。

## 二、内存数据采集三板斧

第一板斧是快照对比：在可疑操作前后各抓一次内存快照，对比增长构成。第二板斧是曲线采样：长跑期间按固定间隔记录进程内存，观察趋势是否收敛。第三板斧是崩溃现场：OOM发生时回收系统记录的终止原因与堆信息。

```bash
# 抓取进程内存详情（pid通过hidumper或bm查询）
hdc shell "hidumper --mem `hdc shell pidof com.example.myapp`" > mem_before.txt

# 执行可疑操作（如反复进入退出图片页）后再抓一次
hdc shell "hidumper --mem `hdc shell pidof com.example.myapp`" > mem_after.txt

# 长跑曲线采样：每30秒记录一次
while true; do
  ts=$(date +%H%M%S)
  rss=$(hdc shell "hidumper --mem $(hdc shell pidof com.example.myapp) | grep -i total")
  echo "$ts $rss" >> mem_curve.log
  sleep 30
done
```

判定经验值：同屏内容不变的前提下，单次进出页面带来的内存应在若干次后收敛；曲线斜率长期为正即存在慢性问题；GC后仍不回落说明对象被强持有。

## 三、泄漏定位的持有链分析

定位泄漏的核心是回答"谁还拿着这个对象的引用"。ArkTS侧的典型持有链包括：全局单例注册了回调未注销、定时器未清理导致闭包持有页面、观察者列表只增不减、组件销毁后异步任务仍持有Store。定位手法是快照对比后按类型聚合：找出数量持续增长的对象类型，回溯其注册或创建点，检查对应的注销或释放路径是否存在。DevEco Studio的Profiler提供可视化的内存分析视图，可以查看堆快照中的对象分布与引用关系，配合代码走查基本可以锁定责任点。原生侧的泄漏（so库分配未释放）则表现为匿名映射增长，需要结合Profiler的内存构成分析与native分配追踪。

## 四、常见泄漏模式与预防清单

高频出现的泄漏模式值得整理成团队的知识库，编码评审按清单预防：

- 页面组件在全局事件总线上注册，销毁时未反注册；
- setInterval/setTimeout持有了组件或Store引用，页面销毁未清除；
- 网络层单例缓存了请求发起页面的回调，响应迟到导致页面无法回收；
- 图片缓存无上限，长列表浏览导致缓存线性增长；
- 长时任务与后台回调持有页面上下文；
- 闭包捕获大对象（整页数据）用于小功能（计数），导致大对象生命周期被意外拉长；
- 观察者数组在异常路径上重复注册。

## 五、修复验证与防线固化

修复泄漏后的验证必须按"可复现曲线"执行：用泄漏时的同参数脚本重跑采样，对比修复前后的曲线形态，确认收敛而非仅仅数值下降。之后把该场景沉淀为自动化防线：内存采样脚本接入流水线的稳定性任务，对关键页面循环执行并断言内存涨幅上限，超标即红灯。这样单个泄漏从"发现-修复"事件进化为"该类场景永久受监控"的制度收益。版本级别还应关注整体内存基线：同一套标准操作序列在相邻版本上的内存峰值对比，基线抬升超过阈值需在版本报告中说明原因，防止功能迭代带来的内存劣化在无人察觉中累积成OOM事故。
