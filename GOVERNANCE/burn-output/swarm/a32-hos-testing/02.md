# 测试用例设计方法在HarmonyOS中的落地：等价类、边界值、场景法与判定表

> 摘要：本文讲解四种经典测试用例设计方法如何与HarmonyOS应用的具体形态结合，包括ArkTS数据模型、ArkUI交互组件与Ability生命周期场景，并给出可执行的落地清单。

## 一、用例设计先于自动化脚本

许多团队的自动化测试建设从"录制回放"开始，却跳过了用例设计这一步，结果是脚本数量庞大但等价类重复严重、边界缺失，测试资产看似厚实却挡不住真实缺陷。用例设计方法的本质是对输入空间做系统性切片：等价类划分解决"测哪些代表性取值"，边界值分析解决"缺陷聚集在哪里"，判定表解决"条件组合如何穷举"，场景法解决"用户真实使用路径如何串联"。对HarmonyOS应用而言，这四类方法分别对应数据校验、数值边界、业务规则与页面流转四个高发缺陷区。

## 二、等价类与边界值：面向ArkTS数据模型

以一个登录表单为例， ArkUI的TextInput组件绑定的@State变量即为输入域。假设用户名规则为6到20位字符，密码为8到16位，先做有效与无效等价类划分：用户名的有效等价类是长度闭区间内合法字符，无效等价类包括过短、过长、含非法字符、空值四类；密码同理。随后对每个区间做边界值补充：5、6、7与19、20、21，以及0（空输入）和超长极端值。Hypium下可用参数化方式组织：

```typescript
import { describe, it, expect } from '@ohos/hypium';

function validateUser(name: string): boolean {
  return /^[A-Za-z0-9_]{6,20}$/.test(name);
}

describe('用户名校验', () => {
  const cases: Array<[string, boolean, string]> = [
    ['abc12', false, '长度5-过短'],
    ['abc123', true,  '长度6-左边界'],
    ['a'.repeat(19), true,  '长度19-右边界内'],
    ['a'.repeat(20), true,  '长度20-右边界'],
    ['a'.repeat(21), false, '长度21-超长'],
    ['ab 123', false, '含空格非法字符'],
    ['', false, '空输入'],
  ];
  for (const [input, want, label] of cases) {
    it(`用例:${label}`, 0, () => {
      expect(validateUser(input)).assertTrue();
      // 失败诊断需要包含label便于定位
    });
  }
});
```

值得强调的是，上述数组中的边界取值不是随手填写，而是从等价类表机械推导出来的，这正是设计方法的价值：新人也能按规则推导出同样的用例集合，评审有了客观依据。

## 三、判定表与场景法：面向业务规则与页面流转

当业务规则由多个条件组合决定时，例如"会员积分兑换"同时依赖用户等级、积分余额、活动开关三个条件，等价类两两组合会产生爆炸，此时应构建判定表：列出条件桩与动作桩，合并相似规则后逐列编写用例。实践中把判定表直接以注释或数据文件形式固化在测试代码旁，能使用例与需求保持同源。

场景法关注的是Ability与页面之间的流转。以电商下单为例，基本流是"浏览商品-加入购物车-结算-支付成功"；备选流包括库存不足、网络中断恢复、支付取消后返回；异常流包括进程被杀后恢复、分布式流转中设备离线。每个场景在Hypium的describe结构中映射为一个it用例，并通过hilog打点验证状态机的实际迁移路径与预期一致。场景法产出的用例最适合沉淀为UI自动化层的冒烟集。

## 四、落地清单与评审要点

将设计方法固化为团队流程，可以参考以下检查清单：

- 需求评审阶段：识别输入域并列出等价类表，标注哪些类合并、哪些保留；
- 边界值阶段：对每个数值与长度区间检查左边界、右边界、边界外一位与空值；
- 规则类需求：条件数大于等于三时必须产出判定表并入库；
- 流程类需求：绘制基本流、备选流、异常流，异常流必须含进程中断与设备离线；
- 用例评审阶段：抽查脚本与设计表的映射关系，删除无断言或重复等价类的用例；
- 维护阶段：线上缺陷复盘时回溯缺失的设计环节并补充到方法模板。

## 五、组合爆炸的收敛：正交表与风险加权

当输入参数较多时，即使做了等价类划分，参数间的两两组合仍可能产生成百上千条用例。此时可引入两两组合（配对）策略：研究表明多数配置类缺陷由两个参数的交互触发，三参数以上交互引发的缺陷占比骤降。做法是把每个参数的有效取值列成因子表，借助正交表或成对生成工具挑选覆盖任意两因子全部取值组合的最小用例集，再叠加风险加权——对历史上出过缺陷或业务权重高的组合额外补强。以设置页的"字体大小、深色模式、语言"三个参数为例，每个参数三个水平，全组合二十七条，成对覆盖后只需九条左右即可覆盖所有两两交互，节省三分之二以上的执行成本。风险加权的关键是维护一份缺陷-参数交互的对照档案：每次线上故障复盘时记录引发问题的参数组合，作为下一轮加权生成的输入，让用例集合随缺陷史自我进化。这样既避免了穷举的资源浪费，又不会因为过度精简而放过高风险交互，是用例设计从艺术走向工程的重要一步。

## 六、优先级排序让设计成果先服务高风险区

设计方法产出的是完备用例集合，但执行资源永远有限，必须排序。推荐的综合排序规则是：先按业务影响与发生概率相乘得到风险值，再按验证成本调节顺序——风险相近时优先执行成本低的自动化用例，让快速反馈先行；风险极高但自动化成本高的场景保留为手工专项，安排在测试轮次早期执行以留出修复时间。每个版本结束后复盘排序命中情况：若高风险用例拦截缺陷的占比持续偏低，说明风险模型失准，需要重新校准影响与概率的评分标准，同时把新近的缺陷史回灌到加权生成过程中，形成闭环。
