# 数据持久化单元测试：Preferences与关系型数据库RDB

> 摘要：本文讲解轻量偏好设置Preferences与关系型数据库@ohos.data.relationalStore两类持久化能力的单元测试方法，包括仓储模式封装、内存假实现、SQL语句与迁移脚本的验证策略及数据脏读场景设计。

## 一、持久层测试的两个层级

持久化代码的测试分两层：逻辑层验证"什么时候读、什么时候写、读了怎么用"，存储层验证"写的能否按约读回、迁移是否无损"。前者不依赖真实存储，用内存假实现替换即可在本地毫秒级完成；后者必须运行在设备侧（模拟器或真机），因为Preferences与关系型数据库的能力依附于系统进程存在。把两层分开的收益是：绝大多数业务分支（缓存失效、默认值回退、脏数据防御）在逻辑层解决，设备侧只保留少量真实性验证，测试矩阵大幅缩小。封装形态推荐仓储模式：每个业务域定义自己的仓储接口（读配置、写配置、按条件查列表），生产环境分别用Preferences与RDB实现，测试环境提供内存版本。

## 二、Preferences仓储的测试

Preferences适合键值型小数据。以设置仓储为例，接口与假实现如下：

```typescript
export interface SettingsRepo {
  getVolume(): Promise<number>;
  setVolume(v: number): Promise<void>;
  getLastUser(): Promise<string | null>;
}

export class MemSettings implements SettingsRepo {
  private m = new Map<string, object>();
  async getVolume(): Promise<number> {
    const v = this.m.get('volume') as number | undefined;
    return v === undefined ? 50 : v;          // 默认值逻辑在这里被测到
  }
  async setVolume(v: number): Promise<void> {
    if (v < 0 || v > 100) { throw new Error('音量越界'); }
    this.m.set('volume', v);
  }
  async getLastUser(): Promise<string | null> {
    return (this.m.get('lastUser') as string) ?? null;
  }
}
```

业务逻辑（如设置页Store）依赖接口编写，测试注入内存版即可验证默认值、越界拒绝、空值回退等全部分支。设备侧再补两三条真实性用例：写入后杀进程重启再读，验证持久生效；写入非法类型，验证读取侧的容错。

## 三、RDB仓储与SQL验证

关系型数据库的测试重点有三个。第一是语句正确性：拼接条件、排序、分页、聚合的SQL很容易在边界翻车，用例准备固定数据集后验证查询结果的行序与内容。第二是迁移无损：版本升级脚本要保证旧表数据完整迁入新结构，每个历史版本各留一份样例库，逐版本执行迁移并断言数据与索引不变。第三是并发与时务：同一记录的并发更新是否按预期互斥。设备侧用例示例：

```typescript
import { describe, it, expect } from '@ohos/hypium';
import { RdbHelper } from '../db/RdbHelper';

describe('下载记录表', () => {
  it('分页查询按时间倒序', 0, async () => {
    const db = await RdbHelper.open(':memory:');
    await db.batchInsert('download', [
      { id: 1, name: 'a', ts: 100 },
      { id: 2, name: 'b', ts: 300 },
      { id: 3, name: 'c', ts: 200 },
    ]);
    const page = await db.query('download', { orderBy: 'ts desc', limit: 2, offset: 0 });
    expect(page.rows.map(r => r.name)).assertDeepEquals(['b', 'c']);
  });
  it('升级迁移保留历史数据', 0, async () => {
    const db = await RdbHelper.openWithVersion(1, sampleV1Data);
    await db.migrateTo(2);
    const cnt = await db.count('download');
    expect(cnt).assertEqual(sampleV1Data.length);
    expect(await db.hasColumn('download', 'extra')).assertTrue();
  });
});
```

## 四、脏数据与损坏场景设计

持久化最危险的不是读写失败，而是读到"格式合法但语义错误"的旧数据。必须覆盖的场景包括：字段类型变化（旧版本存字符串、新版本期望数字）、枚举值退役（旧数据含已下线的状态码）、超大单条记录（历史遗留的巨幅草稿）、半写状态（进程在写入中途被杀）。防御策略是在反序列化入口做白名单校验与裁剪，测试对每种脏形态注入并断言"降级为默认值且不崩溃、可被新写入覆盖修复"。同时，全量导出导入功能也要纳入测试：导入一份结构合法但业务非法的文件时的拒绝行为。

## 五、检查清单与规范沉淀

- 业务代码禁止直接操作存储API，一律经仓储接口；
- 每个仓储接口提供内存假实现，与生产实现同步维护；
- 默认值、越界、空值三条分支是每个读写方法的最低用例集；
- 每个数据库版本留样例库，迁移用例纳入版本回归必跑集；
- 反序列化入口集中做白名单校验，脏数据用例覆盖类型变化与枚举退役；
- 大记录与半写状态有专项用例，断言降级而非崩溃；
- 设备侧真实性用例集中在独立集合，标注执行前置（模拟器/真机）。

## 六、测试数据库的制备与速度优化

持久层设备侧用例最大的痛点是执行慢与数据制备繁琐，值得专门建设制备工具。方案有三件套：其一，SQL种子文件按业务域分目录管理，每个用例套件在beforeAll里加载所需种子，afterAll清理，保证用例间互不污染；其二，对高频用例使用内存库或临时库（每次测试新建独立命名的库文件，结束即删），避免清库操作拖慢节奏；其三，把耗时的批量插入做成一次性公共夹具，多套件共享只读数据集，写操作则定向使用独立库。速度优化的判断标准是：持久层全套用例在模拟器上的执行时长不超过三分钟，超过即说明夹具设计需要重构。制备脚本本身要纳入版本管理并随表结构演进同步更新，迁移用例更新时同步更新种子，防止种子与结构脱节导致的批量红灯。

持久层是应用状态的最后防线，这一层测试做得严密，"升级后数据丢失""重装后设置错乱"这类用户最敏感的事故就有了系统性防线。

## 七、隐私数据与多用户场景

持久层测试还应覆盖隐私合规视角：用户行使删除权时，相关数据在所有存储位置（数据库表、偏好键、缓存文件）被完整清除，清除后重进应用不再出现残留痕迹，这类"删除干净"用例在监管趋严的环境下日益重要。多用户与多设备场景则验证数据隔离：切换账号后本地缓存、浏览历史、登录态正确替换而非串显。把存储位置登记成清单（哪类数据落在哪个库哪张表），删除用例按清单逐项断言，新增存储位置时清单同步更新，可防止"新存储忘了清"的漏网。
