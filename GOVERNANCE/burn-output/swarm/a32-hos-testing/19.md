# 长列表、懒加载与滚动场景的UI自动化测试

> 摘要：本文聚焦HarmonyOS应用中最普遍也最容易测试失稳的长列表场景，讲解滚动操作控制、懒加载与占位验证、滚动定位策略、分页触发断言，以及列表测试的稳定性守则与示例代码。

## 一、列表场景为何是稳定性重灾区

资讯流、商品列表、聊天记录——长列表几乎是所有应用的主体界面，也是UI自动化失败率最高的场景。原因来自三方面：其一，列表内容动态变化，条目数量与文本随数据刷新而变，基于序号的定位随时漂移；其二，懒加载使屏幕外条目根本不在控件树中，查找逻辑必须与滚动配合；其三，滚动本身是异步惯性过程，断言时机不当就会在"内容还在飞"的状态下抓取。测试设计必须逐一回应这三个不确定性：用内容锚点代替序号定位、显式管理滚动与加载的等待节奏、在断言前确认滚动稳定。

## 二、滚动操作与目标定位

UiTest的屏幕级滑动与控件级滚动配合使用。定位特定条目的推荐策略是"滚动直到出现"：循环执行滑动并在每次滑动后检查目标是否在屏，出现即停止，达到滑动次数上限则判定不存在。把这个循环封装为工具方法后，用例正文保持业务化：

```typescript
import { Driver, ON } from '@ohos/uitest';

async function scrollUntilVisible(driver: Driver, cond: ON.__ON__,
                                  maxTimes = 12): Promise<boolean> {
  for (let i = 0; i < maxTimes; i++) {
    if (await driver.hasComponent(cond)) { return true; }
    await driver.swipe({ direction: 'down', speed: 2000 });  // 向下滑动一屏
    await driver.delayMs(300);                                // 等惯性停止
  }
  return await driver.hasComponent(cond);
}

// 用例：验证第30条商品可进入详情
it('深列表条目可达详情', 0, async () => {
  const found = await scrollUntilVisible(driver, ON.textContains('限量商品#30'));
  expect(found).assertTrue();
  await driver.findComponent(ON.textContains('限量商品#30')).click();
  expect(await driver.hasComponent(ON.text('商品详情'))).assertTrue();
});
```

滑动参数（距离、速度）要调成"恰好一屏多一点"，过短导致循环次数膨胀，过长容易跳过目标。

## 三、懒加载与分页的断言

懒加载的验证点有四个：首屏快速呈现（占位骨架及时被真实内容替换）、滚动中追加流畅（新条目批量出现无长时间空白）、结束符正确（到底后出现"没有更多了"且不再重复请求）、失败可恢复（加载失败出现重试入口且点击后成功补齐）。分页触发次数的精确断言在UI层难以稳定实现，建议下沉：把分页请求计数放在仓库层的假实现里单元验证阈值与去重逻辑，UI层只断言可见行为。这样既覆盖了重复请求的浪费问题，又不把脆弱的计数断言暴露在滑动时序中。

## 四、列表项的操作与状态保持

列表项上的操作（点击、长按、勾选、左滑删除）带来额外的状态问题：操作后列表可能局部刷新或整体重建，之前获取的控件引用失效。守则是每次操作后重新查找控件，禁止跨刷新缓存引用。批量选择类交互还要验证滚动加载后的选择保持：勾选第三条，滚动十屏再回来，勾选状态仍在且计数正确，这是"状态丢失"缺陷的典型藏身处。下拉刷新则要验证刷新指示器的出现与消失，以及刷新后新内容到顶。

## 五、列表测试稳定性守则

- 定位用内容锚点（文本、key）而非条目序号；
- 滚动定位用循环滑动加出现检测，滑动距离略超一屏；
- 断言前等待惯性停止与图片占位替换；
- 操作后重新查找控件，禁止复用滚动前的引用；
- 分页精确计数下沉到单元层，UI层只断言可见行为；
- 深列表用例标注数据前置（需要至少N条测试数据）；
- 到达列表末尾的用例单独分组，避免与普通用例互相污染数据量。

列表测试做稳之后，它反而会成为最可靠的资产之一：内容锚点不随界面改版变化，数据可完全由测试环境控制。团队值得在滚动工具与数据制备上做一次性投入，换取主体界面的长期自动化覆盖能力。

## 六、列表性能与稳定性的交叉观察

列表场景是性能缺陷与稳定性缺陷的交汇处，UI测试执行过程中可以顺带采集两类信号。其一是滚动流畅性：在滑动用例中记录帧率与丢帧统计，滚动期间的帧率跌破阈值即报警，能在功能回归的同时看住流畅性退化，这类退化通常由新加入的列表项组件过度重绘引起，越早发现修复成本越低。其二是内存趋势：长列表反复滚动十分钟后的内存增量若不收敛，提示图片缓存或组件复用存在问题，把该信号接入每日冒烟，可在用户投诉卡顿之前发现苗头。交叉观察的接入成本只是几行统计代码，却让UI功能测试同时承担起性能哨兵的角色，投入产出比极高。

补充说明数据制备的规模化做法：长列表用例需要几十到上百条结构各异的数据，手写明显不现实，标准做法是数据工厂按模板批量生成——奇数行带图、偶数行纯文本、每十条插入一条广告位、末尾三条使用超长标题，用一个种子函数即可生成整套带边界特征的列表。数据模板与产品形态同步演进，新增列表项样式时模板补一档，测试数据的多样度始终略超真实数据，这样懒加载与高度测量的边界分支才能被持续触发。
