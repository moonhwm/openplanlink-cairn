# UiTest框架入门：Driver、控件树与自动化执行模型

> 摘要：本文介绍HarmonyOS官方UI自动化测试框架@ohos/uitest的核心对象模型：Driver的获取与能力边界、控件树的加载与等待、用例在ohosTest中的组织方式，以及从零搭建第一条UI自动化用例的完整流程。

## 一、UiTest在测试体系中的位置

UI自动化测试位于测试金字塔的第三层，它启动真实应用、驱动真实渲染管线，从用户视角验证界面呈现与交互流程，是所有层级中保真度最高、成本也最高的一层。@ohos/uitest框架提供了跨越这一层的基础设施：Driver对象代表与设备UI的会话，负责查找控件、注入输入、截屏与断言；UiComponent对象代表控件树中的具体节点，可读取属性与执行操作；ON辅助类构造各类定位条件。UiTest用例运行在ohosTest环境中，与被测应用部署在同一设备上，通过辅助能力接口访问界面信息。选择UiTest的标准很简单：需要验证"用户看到什么、点了会怎样"的问题用它，纯数据与逻辑问题应下沉到单元层。

## 二、Driver的获取与第一条用例

Driver是单例会话对象，通过静态方法创建。第一条用例以登录页为例，覆盖输入、点击、结果断言的完整闭环：

```typescript
import { describe, it, beforeAll } from '@ohos/hypium';
import { Driver, ON } from '@ohos/uitest';

describe('登录流程UI测试', () => {
  let driver: Driver = null as unknown as Driver;

  beforeAll(async () => {
    driver = await Driver.create();
    await driver.delayMs(1000);        // 等待首帧稳定
  });

  it('输入合法凭据可进入首页', 0, async () => {
    await driver.findComponent(ON.id('phone_input')).inputText('1380000000');
    await driver.findComponent(ON.id('code_input')).inputText('123456');
    await driver.findComponent(ON.id('login_btn')).click();
    const home = await driver.findComponent(ON.text('首页'));
    expect(home).assertNotNull();
  });
});
```

用例的骨架与单元测试一致：describe组织套件、it定义用例、expect断言，区别仅在于被操作的对象从内存对象变成了控件。这也意味着团队在单元层建立的组织习惯可以直接平移到UI层。

## 三、控件树的加载与等待模型

UI自动化的成败一半取决于等待策略。控件从"发起查找到真实存在"之间存在天然延迟：页面路由动画、数据加载、懒渲染。UiTest的查找在找不到时会按内部超时机制等待，但用例设计者仍要显式管理两类等待：其一，动作前等待目标可交互，例如列表滚动停止后再点击；其二，断言前等待状态到达，例如提交后等待结果文案出现。推荐的等待方式是条件轮询而非固定延时：循环查找目标控件直到出现或达到上限，固定sleep则作为最后兜底且时长克制。粗暴的大延时会让套件时长失控，而过短的延时又会造成时好时坏的幽灵失败。

## 四、用例组织与Page Object的引入

UI用例超过二十条后，逐条堆driver.findComponent会让维护噩梦迅速到来：界面改一个控件id，几十条用例逐一修改。标准解法是Page Object模式——每个页面封装为一个类，控件查找与操作收敛为方法，用例只调用页面方法表达业务意图：

```typescript
class LoginPage {
  async inputPhone(p: string): Promise<void> {
    await (await Driver.create()).findComponent(ON.id('phone_input')).inputText(p);
  }
  async tapLogin(): Promise<void> {
    await (await Driver.create()).findComponent(ON.id('login_btn')).click();
  }
  async isErrorVisible(msg: string): Promise<boolean> {
    return (await Driver.create().hasComponent(ON.text(msg)));
  }
}
```

页面类与页面一一对应，界面变更时只改一处；用例读起来是业务步骤清单，非技术人员也能评审覆盖面。

## 五、上手期的检查清单

- 每条用例自带前置准备与数据清理，不依赖其他用例留下的状态；
- 等待优先用条件轮询，固定延时总量不超过用例时长的一成；
- 控件定位优先使用稳定的id或文本，避免依赖控件在树中的序号；
- 用例断言用户可见的结果（文本、页面元素），不断言内部实现细节；
- Page Object与页面文件同步维护，新增页面必须同步建类；
- 每条用例有失败诊断附件：关键步骤截屏与页面描述留档；
- 套件按业务旅程分组，冒烟子集控制在十分钟左右。

## 六、执行环境与套件规模治理

UiTest用例必须运行在设备上，环境管理与规模治理决定了这套资产的可持续性。环境方面要在用例元数据里显式标注前置：需要真机还是模拟器即可、需要预登录账号还是自注册、需要特定权限预授还是用例内申请，流水线据此匹配目标设备池，避免"到机器上才发现缺前置"的空转。规模方面坚持冒烟与全量分层：冒烟集控制在十到十五条核心旅程、执行十分钟以内，每天多轮运行；全量集在夜间跑一次，覆盖分支细节。设备复用要有并发与隔离策略：单设备串行执行避免用例互相抢焦点，多设备并行分片按套件哈希切分，保证分片稳定可复现。失败重跑只对环境类失败（设备离线、安装失败）自动执行，功能失败必须人工分析后重跑，防止自动化把真实缺陷重跑成"通过"而悄然放过。

从第一条用例开始就坚持Page Object与显式等待两条纪律，UI自动化才能在界面频繁演进的项目里保持可用，而不是三个月后沦为无人敢碰的红色废墟。

## 七、UiTest与单元层的职责再确认

引入UiTest后团队常犯的方向性错误是"哪里都往UI层堆"：数据校验、规则计算、协议解析都写成界面走查，套件越来越慢而拦截能力并没有提升。方向应当反过来：每条新UI用例合入前回答"这件事能不能在更低的层验证"，能则下沉，UI层只保留必须经过真实渲染的验证。实践中可以给UI用例打上"必要性标签"（渲染、交互、旅程三类），评审时非必要标签的用例退回下沉。这条纪律执行几个月后，UI套件会收敛到精干的旅程集，执行时间与维护成本同时下降，整个测试体系的健康度随之上升。
