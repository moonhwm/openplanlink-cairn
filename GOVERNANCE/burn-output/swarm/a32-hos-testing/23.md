# UI测试稳定性工程：等待策略、防抖与失败诊断体系

> 摘要：本文系统讲解UI自动化"幽灵失败"的治理方法，包括三类等待（存在等待、稳定等待、超时控制）的设计、操作防抖与重试的边界、失败现场自动留存（截屏与日志），以及稳定性指标的度量闭环。

## 一、幽灵失败的根源剖析

UI自动化最消磨团队信任的不是"测出缺陷"，而是"时红时绿"：同一条用例昨天通过今天失败，重跑一遍又绿了。幽灵失败的根源几乎都可以归为三类：时序问题，断言发生在界面到达目标状态之前；环境问题，设备性能波动、动画掉帧、后台通知抢占焦点；用例问题，自身依赖执行顺序或残留状态。治理思路不是盲目加重试掩盖，而是把每类根源对应到确定性手段：时序问题用显式等待消灭、环境问题用隔离与防护消除、用例问题用独立性规范根除。重试只保留给确证的瞬时环境抖动，且重试必须记录与告警，不能静默。

## 二、三层等待体系的设计

第一层是存在等待：查找目标控件时自动重试直到出现或达到上限，这是定位器的基本职责。第二层是稳定等待：在执行滑动、输入等操作前，确认界面处于静止状态——列表停止滚动、键盘已弹出、动画已结束，通过特征元素属性的连续一致（如连续两次采样内容相同）来判定。第三层是超时控制：每个等待都有上限且分级设置，普通元素三秒、页面切换八秒、网络依赖十五秒，超时失败必须携带"等的是什么、等了多久、当前屏上有什么"的诊断信息。三层等待封装为统一的工具函数库，用例正文禁止出现裸sleep：

```typescript
async function waitStable(driver: Driver, cond: ON.__ON__,
                          timeoutMs = 5000): Promise<void> {
  const deadline = Date.now() + timeoutMs;
  let lastText = '';
  while (Date.now() < deadline) {
    const c = await driver.findComponent(cond).catch(() => null);
    if (c) {
      const t = await c.getText();
      if (t === lastText && t !== '') { return; }   // 连续一致视为稳定
      lastText = t;
    }
    await driver.delayMs(250);
  }
  throw new Error(`等待超时: 目标未稳定出现, 已等${timeoutMs}ms`);
}
```

## 三、失败现场的自动留存

诊断幽灵失败的关键是现场重现，用例框架必须在失败瞬间自动留存三类证据：全屏截屏（标注时间戳与用例名）、当时控件树的文本导出、关键时间窗口的hilog日志片段。证据按流水线运行编号归档，并保留最近若干次运行供对比——同一用例多次失败的时间线对照，往往能直接看出是"环境整体变慢"还是"特定元素永不出现"。留存动作要在afterEach钩子里根据用例状态触发，成功用例只保留摘要，控制存储成本。

## 四、稳定性度量与治理闭环

把"稳定性"变成可管理的指标：波动率定义为近期运行中"非缺陷性失败次数除以总运行次数"，健康线设在百分之二以下。治理闭环的运转方式是每周固定一次红灯复盘会，每条非缺陷性失败必须归因到三类根源之一并派发对应整改：时序类整改等待方式、环境类整改隔离手段、用例类整改独立性。连续两周无归因处置的红灯自动升级为负责人督办。同时统计重试后通过的比例，比例上升说明环境在劣化，需要停下来修基础设施而不是继续跑。

## 五、稳定性守则清单

- 用例内禁止裸延时，所有等待经三层等待工具；
- 每条用例独立：自带数据准备与清理，任意顺序可执行；
- 单步操作失败允许一次显式重试并记录，用例级静默重跑禁止；
- 失败自动留存截屏、控件树与日志，按运行编号归档；
- 每周复盘非缺陷性失败并归因整改，波动率低于百分之二；
- 性能孱弱的执行设备不进入正式流水线；
- 新用例合入前连续三轮运行全绿方可纳入门禁。

稳定性工程没有戏剧性的单点技术，全是纪律性的累积。但它决定了UI自动化能否从"演示项目"进化为"生产资产"——团队对绿灯的每一次信任，都来自背后这套治理体系的默默运转。

## 六、环境指纹与环境漂移拦截

不少幽灵失败的真凶是环境漂移：某次模拟器镜像升级后动画时长变化、某次SDK更新后控件树结构微调。治理手段是给每次运行打环境指纹：记录系统版本、SDK版本、镜像标识、设备型号与性能档位，失败分析时先比对指纹再查用例，指纹变化的运行优先怀疑环境。当环境必须升级时，先跑稳定性基线集对比新旧环境下的用例时长分布与失败模式，确认无系统性偏移再切换。环境指纹成本近乎为零，却能把"查了一晚上用例最后发现是环境变了"的尴尬降到最低。

与指纹配套的是环境基线库：把"已知良好"的环境配置（镜像、系统版本、性能档位组合）固化成命名基线，流水线只在基线环境上出正式结论，非基线环境的结果一律标记为"参考"，不阻塞也不放行。需要验证新环境时，先以候选身份跑稳定性基线集，达标后经评审晋升为正式基线。这套机制把环境变更从"悄悄发生的事故源"变成"有评审有记录的受控流程"，是稳定性治理从被动救火走向主动管理的最后一块拼图。
