# 基于Hypium的稳定性测试套件设计：场景驱动与数据构造

> 摘要：本文讲解如何用Hypium编写确定性的稳定性用例套件，包括压力场景设计（高频切换、并发操作、数据极限）、循环与持续时间控制、断言降级策略，以及与随机注入工具的配合分工。

## 一、确定性稳定性用例的定位

随机注入（monkey、wukong）擅长广度探索，但有三个先天短板：无法断言业务正确性（点完不知道对错）、难以深入需要前置条件的场景（登录后才能到的页面）、失败归因成本高。确定性稳定性套件正好互补：用Hypium编写带业务断言的循环用例，明确知道每轮循环"做了什么、应该发生什么"。两类手段的分工原则是：探索交给随机，验证交给用例。凡是被随机流发现过的缺陷路径，都应沉淀为确定性用例加入套件，让同类问题获得永久防线。

## 二、压力场景的设计模式

确定性稳定性用例的核心是场景设计，常用模式有六种。高频切换：前后台快速交替、页面间往返跳转，暴露生命周期与缓存问题；并发操作：多请求同时发起、下载与播放并行，暴露竞态与资源争抢；数据极限：最长文本、最大列表、最深嵌套的输入，暴露边界处理；资源压力：存储写满、网络切换，暴露异常路径的健壮性；重复执行：同一操作连续千次，暴露状态累积类泄漏；组合串联：把上述模式按业务旅程串联，模拟重度用户行为。用例骨架示例：

```typescript
import { describe, it, beforeAll } from '@ohos/hypium';
import { Driver, ON } from '@ohos/uitest';

describe('播放器压力循环', () => {
  let driver: Driver = null as unknown as Driver;
  beforeAll(async () => { driver = await Driver.create(); });

  it('快速切换一千次不崩溃不泄漏', 0, async () => {
    for (let i = 0; i < 1000; i++) {
      await driver.findComponent(ON.id('btn_play')).click();
      await driver.delayMs(20);              // 极短间隔模拟快速操作
      await driver.findComponent(ON.id('btn_pause')).click();
      if (i % 200 === 0) {
        // 周期性健康自检：关键控件仍可用
        expect(await driver.hasComponent(ON.id('player_page'))).assertTrue();
      }
    }
    expect(await driver.hasComponent(ON.id('player_page'))).assertTrue();
  });
});
```

## 三、断言策略与执行控制

稳定性用例的断言要分级降级：阻断断言只保留"进程存活、关键页面可达、核心功能可用"三件事，细节断言（文案、样式）全部让位，否则循环中任何微小波动都会中断长跑。执行控制上，每轮循环之间加入可配置的间隔，用于调节压力强度；用例总时长受全局超时保护，防止挂死占用机时；健康自检按周期执行而非每轮执行，平衡覆盖与时长。数据准备要在套件启动前一次性完成，循环内只做操作不做准备，这既是速度考虑，也避免准备逻辑的波动污染压力测量。

## 四、资源监控的并行采集

确定性好比体检问卷，还需配合仪器读数。套件执行期间应并行采集资源曲线：内存占用按固定间隔采样记录、帧率在滑动循环中统计、文件句柄与线程数在长跑前后对比。采集脚本与用例解耦，通过hdc在宿主机侧轮询执行，结果输出为时间序列文件。判定标准示例：千次循环后内存增长不超过初始值的百分之五、线程数回到初始水平加减二、无持续增长趋势。资源曲线与用例执行日志按同一时间轴归档，异常波动可以直接对齐到具体循环步骤。

## 五、套件组织与持续运行规范

- 稳定性套件独立目录组织，与功能用例分开，标注执行时长与前置；
- 每个历史稳定性缺陷对应一条回归用例，缺陷修复时同步补入；
- 长跑用例分级：十分钟快速集每日多轮、一小时标准集每夜执行、四小时以上专项按需；
- 资源曲线纳入版本对比，关注趋势而不仅是单点值；
- 用例失败输出操作序列与轮次编号，配合日志可精确定位；
- 套件时长纳入预算管理，总执行时长超过两小时需评估拆分并行。

确定性稳定性套件的建设是一个"复利账户"：每沉淀一条用例，防线就厚一分。它不能替代随机探索，但把团队对已知风险区域的掌控从"每次靠人盯"变成"机器常驻验证"，这是稳定性保障从偶然走向必然的关键一步。
