# Ability生命周期与后台任务逻辑的单元测试

> 摘要：本文讲解UIAbility生命周期回调、ServiceExtensionAbility后台逻辑、后台任务与提醒发布等系统能力封装层的单元测试方法，核心是生命周期钩子的抽取与窄接口隔离。

## 一、生命周期逻辑的测试困境与解法

Stage模型把应用的舞台交给UIAbility管理，onCreate、onWindowStageCreate、onForeground、onBackground、onDestroy等回调是业务衔接系统事件的关键节点。典型问题在于生命周期方法同时做三件事：初始化资源、触发业务动作、注册系统监听，三者纠缠导致无法脱离设备验证。解法依然是抽取：把生命周期回调里的每段业务逻辑提取为独立方法或委托给控制器类，Ability本体只保留一行转发。这样测生命周期逻辑就转化为测控制器方法，而转发关系留给少量设备侧集成测试确认。同时把回调时序本身建模为可断言的状态序列：控制器记录收到的事件流，测试模拟onForeground与onBackground交替，验证资源加载与释放严格配对、无泄漏无重复。

## 二、生命周期控制器的测试示例

```typescript
// ctrl/PlayerAbilityCtrl.ets
export type LifecycleEvent = 'create' | 'foreground' | 'background' | 'destroy';

export class PlayerAbilityCtrl {
  private events: LifecycleEvent[] = [];
  private resLoaded = false;

  onEvent(e: LifecycleEvent): void {
    this.events.push(e);
    if (e === 'foreground' && !this.resLoaded) {
      this.resLoaded = true;             // 首次前台才加载
    }
    if (e === 'destroy') {
      this.resLoaded = false;            // 销毁释放
    }
  }
  get isResident(): boolean {            // 后台是否驻留的派生判断
    const last = this.events[this.events.length - 1];
    return last === 'background';
  }
}

// test/PlayerAbilityCtrl.test.ets
import { describe, it, expect } from '@ohos/hypium';
import { PlayerAbilityCtrl } from '../ctrl/PlayerAbilityCtrl';

describe('生命周期逻辑', () => {
  it('前后台交替保持资源', 0, () => {
    const c = new PlayerAbilityCtrl();
    for (const e of ['create', 'foreground', 'background', 'foreground'] as const) {
      c.onEvent(e);
    }
    expect(c.isResident).assertFalse();
  });
  it('最后事件为后台判定驻留', 0, () => {
    const c = new PlayerAbilityCtrl();
    c.onEvent('create'); c.onEvent('foreground'); c.onEvent('background');
    expect(c.isResident).assertTrue();
  });
});
```

同样的模式适用于onNewWant的意图分发：把want中的参数解析与路由决策提取为纯函数，单测覆盖各种uri与参数组合，Ability里只调用决策函数并执行跳转。

## 三、后台任务与系统能力封装层的测试

长时任务、延迟提醒、代理提醒等后台能力属于设备侧专属，测试策略是"接口窄化加假实现"。定义业务需要的最小接口（如申请续期、取消任务），生产环境用系统API实现，测试环境用内存假实现记录调用序列。断言聚焦三点：申请与取消是否成对出现（防止后台任务泄漏导致耗电）；参数是否合法（时长上限、内容非空）；失败是否可重试且不崩溃。对reminderAgentManager这类提醒发布能力，假实现记录发布的提醒内容与触发时间，用例验证时间计算的边界（跨天、跨月、立即触发）而无需等待真实提醒弹出。

```typescript
export interface BgTaskPort {
  start(kind: string, want?: object): Promise<void>;
  stop(kind: string): Promise<void>;
}

export class FakeBgTask implements BgTaskPort {
  calls: string[] = [];
  async start(kind: string): Promise<void> { this.calls.push(`start:${kind}`); }
  async stop(kind: string): Promise<void> { this.calls.push(`stop:${kind}`); }
}

it('播放时申请长时任务且停止时成对释放', 0, async () => {
  const bg = new FakeBgTask();
  const p = new PlaySession(bg);
  await p.begin();
  await p.end();
  expect(bg.calls).assertDeepEquals(['start:audio', 'stop:audio']);
});
```

## 四、设备侧集成补充与检查清单

单测覆盖逻辑之后，仍需少量设备侧集成用例确认真实接线：Ability生命周期与控制器转发是否正确、后台任务在真实系统上能否获得、前后台切换时资源状态是否符合预期。这些用例数量控制在十几个以内，进入每版本回归集。日常评审检查清单如下：

- 生命周期回调体不超过三行转发，业务逻辑全部在控制器或纯函数中；
- 资源申请与释放路径成对，异常路径（onDestroy时未初始化）不崩溃；
- want参数解析独立成纯函数，非法参数有默认路由；
- 后台能力经窄接口访问，测试用假实现断言调用序列；
- 长时任务泄漏有专项用例：反复进出后台后任务计数归零；
- 设备侧集成用例标注运行前置（模拟器或真机、权限预授）。

## 五、多实例与异常生命周期的补充场景

真实设备上的生命周期远比理想路径复杂，测试设计必须覆盖三类易漏场景。其一是多实例：应用配置为多实例模式时，同一Ability可能并存多个实例，控制器若使用静态成员保存状态就会互相串改，单测通过并行构造两个控制器实例并交替触发事件来暴露这类共享状态缺陷。其二是异常销毁：系统在低内存下可能直接回收后台实例，onDestroy不被调用，需要在onBackground时就完成关键持久化，用例应验证"仅有background事件时数据已落盘"。其三是重启恢复：冷启动时从持久化数据恢复到销毁前页面，恢复逻辑要按纯函数实现并覆盖数据缺失、版本不匹配、字段非法三种脏数据输入，保证恢复失败时优雅降级到首页而非崩溃。这三类场景的用例写好后应标记为回归必跑集，因为它们守护的是用户感知最强的"丢状态、回首页、闪退"体验。

生命周期与后台逻辑是稳定性缺陷的高发区，把它们从"只能上真机碰运气"改造成"本地秒级验证"，是单层测试投入对整体质量拉动最明显的领域之一。

## 六、后台任务的耗电与配额视角

后台任务测试除了功能正确，还承担耗电合规的验证责任。系统对后台行为有严格的可见性与持续性约束：任务类型必须与实际业务匹配（音频播放任务不能被用于保活无关逻辑）、通知栏提示必须如实呈现、退到后台后无任务支撑的活动应尽快静默。测试手段是把"任务存活状态"与"通知发布状态"纳入假实现的记账记录，版本回归时对账：进入后台的任务申请清单与可见提示一一对应、无孤儿任务残留。再配合设备侧的耗电统计做抽样复核（后台静置一小时耗电不超过阈值），功能测试就升级为合规测试，避免上架审核阶段才暴露后台行为违规的风险。
