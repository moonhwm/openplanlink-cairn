# 状态管理装饰器的单元测试策略：@State/@Prop/@Link与可测架构

> 摘要：本文分析V1状态装饰器体系（@State、@Prop、@Link、@Provide/@Consume）与V2观察体系对单元测试的影响，给出"状态逻辑下沉到可测Store、组件只做绑定"的架构模式及配套测试代码。

## 一、装饰器为何难以直接单测

状态装饰器的本质是框架在编译期织入的观测代理：@State让组件在变量被赋值时触发重渲染，@Link把父子组件绑到同一数据源，@Provide/@Consume建立跨层级注入。这些能力依附于组件实例与渲染管线存在，脱离UI直接new一个组件类去改@State变量，既不合法也测不出框架织入的行为。因此对状态逻辑的测试策略不是硬啃装饰器，而是改变代码的形状：把"状态值+变更规则+派生计算"整体下沉到无装饰器的Store类，组件层只保留绑定与事件转发。这样改写后，绝大多数原本藏在组件里的业务分支都变成Store的普通方法调用，可测性与同步代码完全一致。

## 二、Store模式与配套单测

以一个典型的表单Store为例，包含字段校验、提交状态与错误提示三类逻辑：

```typescript
// store/LoginStore.ets —— 无装饰器，纯ArkTS类
export class LoginStore {
  phone: string = '';
  code: string = '';
  submitting: boolean = false;
  errors: string[] = [];

  validate(): boolean {
    this.errors = [];
    if (!/^1\d{9}$/.test(this.phone)) { this.errors.push('手机号格式不正确'); }
    if (!/^\d{6}$/.test(this.code)) { this.errors.push('验证码须为6位数字'); }
    return this.errors.length === 0;
  }

  async submit(send: (p: string, c: string) => Promise<boolean>): Promise<string> {
    if (!this.validate()) { return '校验失败'; }
    this.submitting = true;
    try {
      const ok = await send(this.phone, this.code);   // 发送动作注入
      return ok ? '成功' : '服务端拒绝';
    } finally {
      this.submitting = false;
    }
  }
}

// test/LoginStore.test.ets
import { describe, it, expect } from '@ohos/hypium';
import { LoginStore } from '../store/LoginStore';

describe('登录状态逻辑', () => {
  it('非法手机号收集错误', 0, () => {
    const s = new LoginStore();
    s.phone = '123'; s.code = '000000';
    expect(s.validate()).assertFalse();
    expect(s.errors).assertDeepEquals(['手机号格式不正确']);
  });
  it('提交流程恢复submitting', 0, async () => {
    const s = new LoginStore(); s.phone = '1380000000'; s.code = '123456';
    const r = await s.submit(async () => { expect(s.submitting).assertTrue(); return true; });
    expect(r).assertEqual('成功');
    expect(s.submitting).assertFalse();
  });
});
```

注意submit内部对注入函数的断言：在动作执行瞬间校验中间状态，这是验证异步流程状态翻转的关键技巧。

## 三、组件绑定层与V2观察体系的测试边界

组件绑定层（@Entry组件把Store实例挂到@State或用@ObservedV2/@Trace标注的属性上）承担的工作只剩三件事：声明式渲染、事件转发、生命周期衔接。这一层不适合纯单测，原因是渲染正确性依赖真实管线，留给UiTest做少量关键路径验证即可。V2装饰器体系（@ObservedV2、@Trace、@ComponentV2）提供了更细粒度的属性级观测，架构原则不变：观测的仍是Store的属性，业务规则依然收敛在类方法里。对@Watch回调这类"状态变更触发副作用"的逻辑，把副作用提取为可调用方法后同样纳入Store测试，@Watch仅做一行转发。

## 四、派生状态与跨组件通信的测试

派生状态（由基础状态计算出的展示值）是最常被写错的一层：内联在build里导致无法复验，散落多处导致口径不一。规范做法是全部实现为Store的getter或纯函数，用单测锁定口径。跨组件通信优先评估是否真的需要@Provide/@Consume，多数场景下事件总线或单一Store实例更清晰也更好测。确需使用注入链路时，测试策略是验证"提供方修改后消费方读到的值"，在Store层以同源数据验证代替组件层验证。以下清单约束状态层测试的完整度：

- 每个变更方法验证：合法输入生效、非法输入拒绝且错误信息准确；
- 每个派生getter用表驱动锁定边界（空、零、极大、负值）；
- 异步变更验证状态翻转的进入与退出（submitting、loading成对出现）；
- 错误路径验证可恢复性（失败后再次提交成功）；
- @Watch副作用提取为方法后单测，组件内只留转发；
- 组件文件中不出现业务条件表达式，评审逐行检查。

## 五、状态测试与回归防线的价值兑现

状态层测试的长期价值体现在两类高频事故的拦截上。第一类是口径漂移：同一个"可用余额"在页面甲与页面乙计算方式不一致，把派生计算统一到Store的getter并用表驱动锁定后，任何一侧私改口径都会立刻红灯。第二类是异步状态残留：加载失败后loading永远为真、提交后按钮永久禁用，这类缺陷在手工测试中极易漏检，而Store单测把"状态必须成对翻转"写成断言后成为不可能事件。为了让价值持续兑现，团队需要把状态测试纳入回归防线的关键路径：合入门禁跑Store单测全量，版本回归时对状态类缺陷做专项复盘，确认每个缺陷都能对应到一条缺失的用例并当场补齐。另一个实践要点是保持Store的粒度克制：一个Store对应一个内聚的业务域，过大的Store会让用例定位变慢，过小则产生大量样板转发，以"一次产品需求通常只改动一到两个Store"为粒度基准。

这套策略的收益是结构性的：状态逻辑全部具备毫秒级可验证性，UI层薄到可以用肉眼与少量UiTest兜底，状态相关缺陷的定位范围从"整个页面"收敛到"单个Store方法"。

## 六、从装饰器版本演进看测试资产的保护

状态管理机制本身在持续演进，从V1装饰器到V2观察体系，团队迁移时最担心的是测试资产作废。Store模式的另一个长期价值在这里显现：由于测试锚定的是无装饰器的普通类，框架层的装饰器替换、绑定方式调整都不会触碰测试代码，迁移成本被压缩到组件绑定层的少量改写。反过来，如果把逻辑直接写在组件里再用UI自动化覆盖，每次框架语法演进都会导致大面积脚本失效。因此即使不考虑短期效率，仅从框架演进的风险对冲角度，状态逻辑下沉也是稳赚的架构投资。评审迁移方案时，把"测试代码零修改或少量修改"作为验收条件之一，能倒逼架构保持干净的分层。
