# 弹窗、菜单、半模态与自定义弹层的UI测试

> 摘要：本文讲解系统与自定义弹层类交互的自动化测试方法，包括模态与半模态容器的定位模型、弹出与关闭的时序验证、遮罩层交互规则断言，以及弹层测试的焦点管理要点与代码示例。

## 一、弹层交互的特殊性

弹层（Dialog、Sheet半模态、Menu菜单、Toast提示、自定义Popup）是界面的"第二层空间"：它们浮于页面之上、有时带遮罩、生命周期短暂、焦点行为特殊。这给自动化带来三个具体困难：查找范围变化——弹层出现后控件树新增分支，同名控件可能同时存在于页面与弹层中；焦点劫持——模态弹层存在时页面主体不可交互，操作会失效或落到遮罩上；瞬时性——Toast几秒自动消失，断言窗口极窄。测试设计必须把弹层当作一等公民建模，而不是当作普通页面元素的变体。

## 二、弹出与关闭的时序验证

弹层用例的基本骨架是"触发-验证弹出-操作-验证关闭"。验证弹出用弹层内特征元素的存在性，验证关闭用特征元素的消失加上页面主体可交互性的恢复：

```typescript
import { describe, it, expect, beforeAll } from '@ohos/hypium';
import { Driver, ON } from '@ohos/uitest';

describe('删除确认弹窗', () => {
  let driver: Driver = null as unknown as Driver;
  beforeAll(async () => { driver = await Driver.create(); });

  it('确认删除后弹窗关闭且条目消失', 0, async () => {
    await driver.findComponent(ON.id('item_delete_entry')).click();

    const dialog = await driver.findComponent(ON.id('confirm_dialog'));
    expect(dialog.isVisible()).assertTrue();
    expect(await driver.findComponent(ON.id('list_page')).isClickable())
      .assertFalse();                       // 模态期间主体不可点

    await driver.findComponent(ON.id('confirm_yes')).click();
    expect(await driver.hasComponent(ON.id('confirm_dialog'))).assertFalse();
    expect(await driver.hasComponent(ON.text('待删除条目'))).assertFalse();
  });

  it('点击遮罩关闭且数据不变', 0, async () => {
    await driver.findComponent(ON.id('item_delete_entry')).click();
    await driver.click({ x: 50, y: 50 });    // 遮罩区域按比例换算
    expect(await driver.hasComponent(ON.id('confirm_dialog'))).assertFalse();
    expect(await driver.hasComponent(ON.text('待删除条目'))).assertTrue();
  });
});
```

## 三、遮罩规则与焦点管理

每个弹层都必须回答三个问题：点遮罩关不关、按返回键关不关、关闭后焦点回到哪里。这三条规则是产品交互一致性的基石，也是回归的重灾区。自动化应把规则做成参数化矩阵：对每个弹层逐一验证遮罩点击、系统返回、弹层内取消三种关闭路径的行为是否符合产品定义的矩阵（有的弹层允许误触关闭，有的强制显式选择）。焦点验证则关注关闭后键盘是否收起、输入焦点是否回到触发明细的控件，遗漏焦点恢复会造成"关闭弹窗后按键无效"的诡异缺陷。

## 四、Toast与瞬时提示的捕捉

Toast类提示存活期短，捕捉策略有两条路线：主路线是出现检测的快速轮询——触发动作后立即以两百毫秒间隔轮询特征文本，捕获后读取内容即刻断言，不做任何延时；辅助路线是把Toast文案的触发逻辑下沉到业务层单元测试验证（什么条件下发什么提示），UI层只保留两条代表性用例验证展示管线畅通。半模态Sheet还需要验证拖拽手柄的交互：下拉关闭、上滑展开更多内容，断言用容器高度或内部特征元素的变化表达，避免依赖像素。

## 五、弹层测试规范清单

- 弹层内控件定位一律使用弹层容器为锚的组合条件，防止与页面同名控件混淆；
- 弹出与关闭配对断言，另加主体可交互性恢复的验证；
- 遮罩点击、系统返回、显式取消三种关闭路径逐一覆盖并记录规则矩阵；
- Toast用快速轮询捕捉，文案逻辑下沉单元层；
- 连续弹层场景（弹层中再开弹层）验证层级与关闭顺序；
- 自定义弹层开发时同步提供稳定的id锚点，作为可测性约定；
- 弹层用例独立成套件，避免弹层残留影响后续用例的页面主体操作。

弹层交互的规律性很强，把规则矩阵与工具方法沉淀好之后，新增弹层的测试成本接近于填一张表，而收益是交互一致性问题在提测前就被系统性地拦截。

## 六、连续弹层与层级栈场景

真实使用中弹层往往不是孤立出现：表单未保存就点返回弹出确认框、分享面板上再弹登录提示、半模态里长按唤出菜单。层级栈场景的测试要点有三个：一是层级正确性，后弹的层覆盖先弹的层，关闭顺序符合栈逻辑，不会出现"关掉一层把两层都关了"或"关不干净露出残影"；二是数据保持，下层表单已填内容在上层弹层开关一轮后不丢失；三是焦点正确，逐层关闭后焦点回到最初的触发控件。团队应把产品内所有弹层整理成层级关系图，图中出现的每条边（A上弹B）至少一条用例覆盖，新弹层接入时更新关系图即可推导出需要补充的组合，避免层级测试的遗漏随弹层数量增长而放大。

弹层测试还有一个容易忽视的视角：与系统全局弹层的竞争。应用弹层展示期间系统来电、低电量提醒、权限申请等系统级弹窗可能叠加出现，此时应用弹层应保持状态而非被意外关闭，系统弹层消失后交互恢复正常。这类场景在真机上可用两条用例代表（来电中断后恢复、权限弹窗叠加后正常关闭），纳入每版本专项而非日常冒烟。同时约定弹层展示期间对返回键的响应必须显式定义——是关闭弹层还是整页退出，未定义的行为正是线上"按返回直接闪退"类缺陷的主要来源，评审交互稿时即要求设计师标注每个弹层的返回语义。
