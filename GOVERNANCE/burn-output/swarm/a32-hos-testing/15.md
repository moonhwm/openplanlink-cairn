# 系统能力Mock体系：通知、剪贴板、弹窗授权等平台API的测试隔离

> 摘要：本文给出通知发布、剪贴板、系统弹窗与权限授权、设备信息等平台能力的一站式Mock方案，讲解平台端口层的设计原则、假实现的记账式断言方法与设备侧补充验证的边界划分。

## 一、平台端口层：系统能力的统一隔离带

除网络与存储外，应用还会调用大量平台能力：发布通知、读写剪贴板、获取设备信息、申请权限、拉起系统选择器。这些能力的共同特征是：调用结果依赖系统状态、可能在测试沙箱不可用、副作用对用户可见。直接调用会让单测无法离线运行，也让"是否真的调用了、调用了几次、参数对不对"无法断言。解决方式是建立平台端口层：按能力域定义窄接口，UI与业务逻辑只面向接口编程，生产环境绑定真实实现，测试环境绑定假实现。端口层的接口粒度以"业务用到的操作"为单位，不做大而全的API镜像——镜像整个系统接口既昂贵又难维护，业务用不到的路径不需要测试。

## 二、记账式假实现与断言

假实现的核心价值不只是返回可控数据，更在于记录调用现场供事后断言。这种风格称为记账式Mock：

```typescript
export interface NotifyPort {
  publish(title: string, text: string, channelId: string): Promise<void>;
  cancel(id: number): Promise<void>;
}

export class FakeNotify implements NotifyPort {
  published: Array<{ title: string; text: string; channelId: string }> = [];
  cancelled: number[] = [];
  shouldThrow = false;

  async publish(title: string, text: string, channelId: string): Promise<void> {
    if (this.shouldThrow) { throw new Error('通知被系统拒绝'); }
    this.published.push({ title, text, channelId });
  }
  async cancel(id: number): Promise<void> { this.cancelled.push(id); }
}

// 用例：下载完成后发布通知且参数正确、失败不崩溃
import { describe, it, expect } from '@ohos/hypium';

describe('下载完成通知', () => {
  it('成功时发布到下载渠道', 0, async () => {
    const n = new FakeNotify();
    const job = new DownloadJob(new FakeHttp(), n);
    await job.run();
    expect(n.published.length).assertEqual(1);
    expect(n.published[0].channelId).assertEqual('download');
    expect(n.published[0].title).assertInclude('下载完成');
  });
  it('通知失败不影响任务结果', 0, async () => {
    const n = new FakeNotify(); n.shouldThrow = true;
    const job = new DownloadJob(new FakeHttp(), n);
    const r = await job.run();
    expect(r.ok).assertTrue();          // 核心结果不受通知失败影响
  });
});
```

同样的模式套用到剪贴板（记录写入内容与读取返回值）、设备信息（注入机型、屏幕参数）、权限（按场景返回已授权或拒绝）。权限Mock尤其重要：授权、拒绝、永久拒绝三种形态驱动完全不同的UI分支，真机上难以瞬间切换，假实现一键切换。

## 三、系统弹窗与授权流程的分支覆盖

系统级弹窗（权限申请、安全键盘、位置选择）的测试重点不是弹窗本身的渲染，而是"每个选择分支之后的业务走向"。把弹窗交互抽象为返回枚举的端口方法后，分支测试就是普通的表驱动：同意进入功能页、拒绝显示引导文案、永久拒绝跳设置页。要注意拒绝路径的用户体验验证：拒绝后功能是否仍可部分使用、再次进入是否重复骚扰申请，这类产品规则的回归完全可以在端口层完成。设备侧补充用例只验证真实弹窗弹出与点击的接线正确性，每条权限一例，总量控制在个位数。

## 四、端口层的工程化管理

端口接口与假实现应当沉淀为独立的测试工具包，按能力域分文件维护，配套README说明每个假实现的旋钮。演进纪律有三条：新增能力调用必须先加端口，评审检查import清单里不出现绕过端口的系统模块；假实现的行为要与真实API语义对齐，发现真实行为与假实现不符时先修假实现再补差异用例；每个假实现的默认状态要"宽松"（不抛错、返回正常数据），逼真故障由用例显式设置，避免新用例莫名失败。以下清单用于例行审计：

- 平台能力调用全部经端口，业务代码无直接系统API import；
- 每个端口有配套假实现，具备可控旋钮与调用记录；
- 授权三分支、通知成功失败、剪贴板读写异常均有用例；
- 假实现默认宽松，故障显式注入；
- 设备侧接线用例集中在冒烟集，标注权限前置；
- 测试工具包有版本与变更记录，假实现偏差定期校准。

## 五点五、端口层与依赖注入容器的简化实现

端口数量增多后，手工在每处构造函数里传递依赖会变得啰嗦，可以引入极简的服务定位器：一个静态注册表在应用启动时绑定生产实现，测试的beforeAll里替换为假实现并注册恢复逻辑。保持两点克制：注册表只按接口类型存取，不提供按字符串键的模糊获取，避免运行期拼写错误；不做动态代理与自动生成等重装备，百行以内的手写代码即可满足绝大多数工程规模。这样业务代码零感知注入细节，测试切换实现只需一行，同时保留了"依赖必须显式声明"的可读性。若团队后续引入更完整的依赖注入框架，迁移路径也是平滑的：注册表退化为框架的组装模块，业务代码不动。

建立端口层后，平台相关逻辑的测试覆盖率与执行速度与其他业务代码拉平，系统能力的真实行为差异被压缩到十几个设备侧用例的窄缝里，质量保障的确定性显著提升。

## 六、端口层的防腐蚀监控

端口层最大的长期风险是被慢慢腐蚀：赶工的提交直接import系统API绕过端口，日积月累隔离带千疮百孔。防腐蚀不能靠自觉，要靠机制：其一，在代码评审清单中固化"新增系统能力调用必须走端口"条目；其二，用静态检查脚本扫描业务目录下的import语句，出现未登记的系统模块名即报告，扫描纳入流水线门禁；其三，每季度做一次端口盘点，合并语义重复的接口、删除无人使用的端口，保持隔离带精简。三招成本极低，却能保证这项基础设施在人员更替与需求洪峰中始终完好。
