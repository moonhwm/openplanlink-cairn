# 网络层单元测试：@ohos.net.http的隔离与Mock策略

> 摘要：本文讲解HarmonyOS网络层的可测试架构设计，包括窄接口封装@ohos.net.http、假实现与本地Mock服务的两种隔离手段、网络异常族的用例设计，以及请求重试与超时逻辑的确定性验证方法。

## 一、网络层为什么必须隔离测试

直接依赖@ohos.net.http的代码无法在本地单测中运行，强行放到设备侧测试则要面对真实网络的不确定：响应时间抖动、服务端数据变化、弱网环境难构造。更关键的是，网络层缺陷的重灾区不在"请求成功路径"而在"失败路径与边界"：超时后的重试节奏、断网时的错误映射、响应体被截断、字段类型与服务端约定不符。这些场景在真实网络上几乎无法按需复现，只有把网络依赖隔离成可注入的桩，才能精确制造每一种故障形态并断言业务侧的反应。隔离的第一步是定义窄接口：业务层需要的不是http模块本身，而是"给定请求参数，返回成功数据或失败原因"这样一个契约。

## 二、窄接口与假实现

```typescript
// net/HttpPort.ets —— 业务视角的最小契约
export interface HttpPort {
  get<T>(url: string, params?: Record<string, string>): Promise<T>;
  post<T>(url: string, body: object): Promise<T>;
}

// 生产实现内部使用@ohos.net.http（略），测试使用假实现：
export class FakeHttp implements HttpPort {
  private routes = new Map<string, (p?: Record<string, string>) => object>();
  failWith: Error | null = null;
  delayMs = 0;

  on(pattern: string, handler: (p?: Record<string, string>) => object): void {
    this.routes.set(pattern, handler);
  }
  async get<T>(url: string, params?: Record<string, string>): Promise<T> {
    if (this.failWith) { throw this.failWith; }
    if (this.delayMs > 0) { await sleep(this.delayMs); }
    const h = this.routes.get(url.split('?')[0]);
    if (!h) { throw new Error('未注册路由:' + url); }
    return h(params) as T;
  }
  async post<T>(url: string, body: object): Promise<T> {
    const h = this.routes.get(url);
    return h ? h(undefined) as T : Promise.reject(new Error('未注册路由'));
  }
}
```

假实现提供三个可控旋钮：按路由返回不同数据、统一抛出指定异常、注入延迟。这三个旋钮足以构造绝大多数测试场景，而且全部同步可预测。

## 三、网络异常族的用例设计

用例设计按异常族展开，每一族对应业务侧的一种应对策略：其一，立即失败族（无网络、域名解析失败），业务应提示用户且不触发重试；其二，可重试族（超时、网关错误），业务应按退避策略重试并最终给出可理解的错误文案；其三，数据异常族（状态码成功但结构不符、字段类型错误），业务应拒绝使用脏数据并上报，绝不崩溃。示例验证重试与错误映射：

```typescript
import { describe, it, expect } from '@ohos/hypium';
import { NewsRepo } from '../repo/NewsRepo';
import { FakeHttp } from './FakeHttp';

describe('新闻仓库异常处理', () => {
  it('超时触发两次重试后放弃', 0, async () => {
    const net = new FakeHttp();
    net.failWith = new Error('timeout');
    let attempts = 0;
    const repo = new NewsRepo(net, { retries: 2, interval: 0 });
    attempts = 0;
    const r = await repo.load();
    expect(r.ok).assertFalse();
    expect(r.message).assertInclude('网络超时');
  });
  it('脏数据不进入缓存', 0, async () => {
    const net = new FakeHttp();
    net.on('/news/list', () => ({ total: '十篇' }));   // total应为数字
    const repo = new NewsRepo(net, { retries: 0, interval: 0 });
    const r = await repo.load();
    expect(r.ok).assertFalse();
    expect(repo.cacheSize()).assertEqual(0);
  });
});
```

注意用例中重试间隔被注入为零，测试瞬间完成，这正是可测试性设计的又一次兑现。

## 四、本地Mock服务与契约测试的补充

假实现覆盖单元层，当需要验证真实序列化与并发时，可以在设备侧测试中使用本地回环Mock服务：测试内启动轻量TCP监听，返回预置报文，把请求指向回环地址。这种方式保留了真实HTTP栈的编解码路径，能暴露请求头拼装、编码与分块解析的问题。更进一步，团队可以沉淀"契约用例集"：关键接口各留一条设备侧用例，真实访问测试环境并只断言结构不断言具体数据，用于捕捉服务端契约变更，结构断言失败即提示与服务端同步契约。

## 五、评审清单与常见反模式

- 业务代码禁止直接import @ohos.net.http，一律经HttpPort访问；
- 错误必须映射为业务语义（可重试、不可重试、需登录），禁止把原始异常文案直接抛给UI；
- 每个仓库类至少覆盖：成功、立即失败、可重试耗尽、脏数据四条路径；
- 重试参数（次数、间隔、总量上限）可注入，测试中置零加速；
- 响应体字段校验集中在解析层，禁止在使用处散落空值判断；
- 取消语义有测试覆盖：页面退出后迟到响应不覆盖新状态；
- 契约用例标注运行环境（需测试网络），与离线用例分集合管理。

## 六、从单元到集成的分层接线

网络隔离做完单元层后，还需要一条清晰的上升通道把验证逐步逼近真实。第一级是本地假实现（前文FakeHttp），验证业务规则；第二级是设备侧回环Mock，验证真实序列化、请求头与拦截器链；第三级是测试环境联调，验证契约与鉴权流程；第四级是发布前的生产预检，只做只读接口的连通性与结构断言。每一级都保留固定的用例集合并标注级别，故障排查时从下往上逐级复现，能在最便宜的层级定位问题。这种分级还能服务于契约管理：当服务端变更接口时，第二级的回环用例不受影响而第三级立刻红灯，团队可以快速区分"我方回归"与"契约变更"，避免把服务端问题误判为客户端缺陷，减少跨团队扯皮成本。

网络层隔离完成后，绝大多数与服务端交互的缺陷都可以离线复现与验证，联调阶段节省的时间会以小时计，而这层投入通常只需一次性完成即可长期复用。

## 七、安全相关断言的顺带覆盖

网络层测试还有一个常被遗忘的维度：安全基线的自动化确认。请求统一走HTTPS、敏感字段不入URL查询串、日志打印对令牌与手机号脱敏、错误响应不回显内部堆栈，这四条基线都可以写进端口层的公共用例：拦截所有发出的请求做规则断言，拦截日志输出做脱敏断言。用例数量不过五六条，却能把最常见的低级安全问题变成合入即检的硬约束，安全评审时的人力得以聚焦在业务逻辑层面的风险上。
