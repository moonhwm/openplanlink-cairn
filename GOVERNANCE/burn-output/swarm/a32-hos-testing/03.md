# ArkTS语言特性对可测试性的影响与面向测试的代码设计

> 摘要：本文分析ArkTS的状态装饰器、单向数据流、模块加载与异步模型等语言特性对单元测试可测试性的影响，并给出依赖注入、纯函数抽取、适配器隔离等可测试性设计模式与示例代码。

## 一、可测试性是设计属性而非工具属性

ArkTS在TypeScript基础上扩展了声明式UI与状态管理，这让"逻辑与界面纠缠"变得非常容易：业务规则写在build函数的内联表达式里，网络请求散落在组件的生命周期回调中。这类代码在UI层尚能通过肉眼验证，一旦进入自动化测试就会暴露三个障碍：组件无法脱离渲染管线实例化、系统能力无法在测试沙箱中获得、状态变更的触发路径与界面耦合。因此可测试性必须在编码阶段就作为设计约束，而不是事后靠工具补救。判断标准很朴素：一段业务逻辑，能否在不启动任何Ability、不渲染任何页面的前提下，用普通函数调用来验证其输入输出。

## 二、状态装饰器对单测的影响与应对

@State、@Prop、@Link等装饰器只有挂在自定义组件上才生效，这意味着直接对含状态的组件类做纯单测往往不可行。工程上的做法是把状态承载的"值"与操作值的"逻辑"分离：逻辑收敛到无装饰器的普通类（通常命名为XxxViewModel或XxxStore），组件只负责订阅与渲染。这样ViewModel可以完整地做单元测试，而组件层交给UiTest做少量关键路径验证。

```typescript
// store/CartStore.ets —— 无任何UI依赖，可独立单测
export class CartStore {
  private items: Map<string, number> = new Map();

  addItem(id: string, n: number): string {
    if (n <= 0) { return '数量非法'; }
    const cur = this.items.get(id) ?? 0;
    const next = Math.min(cur + n, 99);   // 业务上限99
    this.items.set(id, next);
    return 'ok';
  }

  totalPrice(priceOf: (id: string) => number): number {
    let sum = 0;
    this.items.forEach((n, id) => { sum += priceOf(id) * n; });
    return sum;
  }
}

// test/CartStore.test.ets
import { describe, it, expect } from '@ohos/hypium';
import { CartStore } from '../store/CartStore';

describe('购物车逻辑', () => {
  it('数量上限99', 0, () => {
    const c = new CartStore();
    c.addItem('sku1', 50);
    c.addItem('sku1', 60);
    expect(c.totalPrice(() => 10)).assertEqual(990);
  });
});
```

注意totalPrice把价格查询抽象为函数参数，这就是最轻量的依赖注入：测试中无需访问任何真实商品服务即可注入桩函数。同样的思路适用于@ohos.net.http、Preferences等系统能力——定义窄接口，由组件侧实现真实适配器，测试侧传入假实现。

## 三、异步模型与模块边界

ArkTS大量使用async/await与Promise，单测需要保证断言发生在异步完成之后。Hypium对返回Promise的用例函数会自动等待，因此推荐用例统一声明为async并在内部await业务调用，避免回调嵌套导致的时序脆弱。另一个影响可测试性的特性是模块顶层副作用：如果模块在被import时就发起网络请求或读文件，任何引用它的测试都会连带触发这些副作用，导致用例之间互相污染。规范是模块顶层只做常量与类型定义，副作用收敛到显式的init函数，由宿主决定何时调用。

单向数据流同样是可测试性的朋友。数据从Store流向组件、事件从组件流回Store，中间不出现组件私有的派生状态，可以大幅减少"状态在多处被改写"这类难以复现的缺陷，也让每个状态迁移都能写成确定性的用例。

## 四、面向测试的分层设计清单

在代码评审中可使用如下检查清单来守护可测试性：

- 业务规则不得出现在build函数的内联表达式中，必须抽取为可独立调用的函数或类；
- 系统能力访问必须经过窄接口封装，禁止在逻辑层直接import @ohos.net.http等模块；
- 模块顶层禁止副作用，初始化逻辑集中到显式入口函数；
- 随机数、当前时间等非确定输入必须经由参数或注入源获取；
- 异步接口统一返回Promise，禁止混合回调风格；
- 每个ViewModel类配套同名单测文件，构造函数不依赖全局单例；
- 复杂分支逻辑优先表达为纯函数与数据表，便于参数化用例覆盖。

## 五、把不可测代码改造为可测代码的实操步骤

面对存量工程中纠缠严重的代码，可以按固定的四步重构节奏改造，每一步都保持可编译可运行。第一步是提取：把build内联表达式中的业务条件、生命周期里的数据处理逻辑，原样搬移到独立的普通类或纯函数中，组件改为调用它，此步不改任何行为。第二步是接口化：识别函数体内直接调用的系统能力，定义仅包含所需方法的窄接口，原调用改为通过接口发起，组件侧提供真实实现。第三步是注桩：在单测中编写假实现，覆盖成功、失败、超时三种返回形态，验证调用方的分支处理。第四步是参数化：把时间、随机数、配置值等环境依赖改为入参，使相同输入必得相同输出。完成四步后，原有凭肉眼验证的逻辑全部落入毫秒级单测，UiTest只保留渲染与交互断言。改造顺序应从缺陷高发模块开始，每改完一个模块即补充该模块的回归用例并纳入门禁，防止回退。这种渐进式改造不需要专项立项，将其融入日常需求开发的顺手工作量，一年之内即可显著改善整个工程的可测试性基线。

## 六、小结：可测试性约束的长期回报

把可测试性作为ArkTS编码的硬约束，短期看会增加少量设计成本，长期回报则体现在三个方面：缺陷定位速度显著加快，因为逻辑都在可独立运行的单元内；重构安全感大幅提升，任何行为改变都有测试网络即时报警；新人上手周期缩短，窄接口与单向数据流本身就是最好的架构文档。让这条约束真正落地的机制，是在代码评审清单中固化可测试性条目，并让单元测试与业务代码同仓库同评审，评审者看到没有配套测试的提交有权要求补充后再合入。
