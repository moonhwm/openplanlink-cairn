# 声明式组件断言：属性、文本、可见性与状态校验

> 摘要：本文讲解UiTest对控件属性的读取与断言方法，包括文本与id校验、可见性与可点击性判断、组件属性对比、屏内坐标验证，以及"断言用户可感知结果而非实现细节"的原则与代码示例。

## 一、UI断言的对象与原则

UI层断言回答的问题应当是"用户此刻看到了什么、能做什么"，而不是"内部状态变量等于几"。前者例如：提交按钮显示为禁用置灰、错误提示文案出现且位于表单下方、列表条目数量增长到二十条；后者例如：某个布尔标志为真、某个路由栈长度为二。断言实现细节的用例会在重构时大面积失效，因为重构恰恰改变实现而保留行为。判断一条断言是否合格的标准很朴素：把实现完全重写但用户看到的完全一样，这条用例是否仍然通过——通过则合格。UiTest为这一原则提供了配套能力：从UiComponent读取文本、id、类型等属性，判断可见性与可用性，Driver层面的hasComponent与assertComponent提供存在性断言，配合截屏可以留存视觉证据。

## 二、核心断言方法与用例

```typescript
import { describe, it, expect, beforeAll } from '@ohos/hypium';
import { Driver, ON } from '@ohos/uitest';

describe('表单提交界面断言', () => {
  let driver: Driver = null as unknown as Driver;
  beforeAll(async () => { driver = await Driver.create(); });

  it('非法输入时按钮禁用且提示可见', 0, async () => {
    await driver.findComponent(ON.id('phone_input')).inputText('123');
    const btn = await driver.findComponent(ON.id('submit_btn'));
    expect(btn.isClickable()).assertFalse();        // 可点击性
    const tip = await driver.findComponent(ON.id('phone_tip'));
    expect(tip.isVisible()).assertTrue();           // 可见性
    expect(tip.getText()).assertInclude('手机号格式');  // 文本内容
  });

  it('提交成功后进入结果页', 0, async () => {
    await driver.findComponent(ON.id('phone_input')).inputText('1380000000');
    await driver.findComponent(ON.id('submit_btn')).click();
    const ok = await driver.findComponent(ON.text('提交成功'));
    expect(ok).assertNotNull();
    expect(await driver.hasComponent(ON.id('submit_btn'))).assertFalse(); // 旧按钮消失
  });
});
```

这段用例体现了配对断言的节奏：不仅验证新状态出现（成功文案），也验证旧状态消失（提交按钮不在屏上）。只断言出现的用例会漏掉"新旧界面叠加"这类渲染缺陷。

## 三、动态内容与属性的稳健断言

真实界面的文本大量包含动态片段：时间戳、金额、昵称、计数。对这类内容坚持完整等于断言必然脆弱，应按语义分层断言：结构层用正则或前缀匹配验证格式（如"支付成功 ¥"开头的金额格式），数值层把数字抽出后做区间断言（余额在99到101之间），语义层只在文案确定不变时才做完整匹配。对于加载中的占位态，断言占位控件的出现与消失时机，而不是对最终内容设置过短的超时。国际化场景下文案匹配要以资源键为准或维护多语言字典，禁止把中文文案硬编码进所有用例然后期待海外版本不出问题。

## 四、视觉细节的断言边界

纯文本与属性断言无法覆盖"视觉回归"：间距错乱、图片错位、颜色错误。处理方式分三档：影响可读性的问题（元素重叠导致不可点）转化为可交互性断言；明确的视觉规范（主按钮颜色、字号）在评审层面用规范约束，自动化不做像素级比对；确需视觉比对的区域（品牌页、支付面板）采用基线截屏对比，把图片差异比例阈值调到只捕捉显著变化，且基线更新必须走评审。截屏对比的维护成本高，只用于少数高价值区域，避免全套件像素比对带来的海量误报。

## 五、断言体系检查清单

- 每条用例断言用户可感知的结果，不引用内部状态变量；
- 状态迁移用配对断言：新元素出现与旧元素消失同时验证；
- 动态文本用结构匹配加数值区间，完整匹配仅限静态文案；
- 可见性与存在性区分使用，被遮挡场景断言前者；
- 占位态与空态有专属用例，验证其出现与被替换的时机；
- 国际化文案经资源键或多语言字典管理；
- 像素级比对限定在高价值区域并设置合理的差异阈值。

把断言口径统一到"用户视角"，UI用例的失效频率会显著下降，因为绝大多数代码变更并不改变用户可见行为，这些变更引发的用例红灯本质上是断言设计不当造成的噪音。噪音少了，团队才会真正信任并维护这套资产。

## 六、断言失败信息的语义化改造

断言的可维护性还取决于失败时的表达质量。默认的失败输出往往只有"期望A实际B"，排查者需要打开用例、对照界面才能理解含义。改造方向是给关键断言附上业务语境：Page Object的校验方法在断言前组装"页面名-步骤-检查点"的描述串，失败信息完整呈现"购物车页-点击结算后-底部总价应为199但实际19.9"。再配合失败瞬间的截屏归档，排查者无需复现就能定位到具体环节。语义化改造是纯投入型工作，没有技术难度，却能把团队的平均排障时间压缩一半以上，属于回报确定的基建。

## 七、空态与异常态的断言补全

界面断言最容易遗漏的是非正常态：空列表时的引导插画与文案、网络错误时的重试入口、无权限时的申请引导、加载中的骨架屏。这些状态要么"长得不像正式界面"被开发者遗忘，要么依赖特定条件难以手工触发。自动化恰好擅长制造条件（注入假网络故障、清空数据、撤销权限），应当为每个核心页面补全"空、错、载"三态用例。产品评审时同步评审三态设计，测试侧把三态纳入页面验收清单，形成设计与验证的闭环。
