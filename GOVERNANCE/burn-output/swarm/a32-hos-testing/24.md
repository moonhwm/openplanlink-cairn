# 无障碍（Accessibility）测试与可访问性检查清单

> 摘要：本文讲解HarmonyOS应用无障碍能力的测试方法，包括控件的无障碍属性（文本描述、角色、可用性）校验、读屏焦点顺序验证、触控目标尺寸检查，以及团队级的可访问性评审清单。

## 一、无障碍是质量的一部分

读屏软件用户依赖控件的无障碍树获取界面信息：控件的角色（按钮、图片、文本）、名称（朗读出的内容）、状态（选中、禁用）、可操作性。开发者的常见疏漏包括：图标按钮没有文本描述，读屏只会念出"按钮"两个字；纯装饰图片未标记为不可朗读，造成信息噪音；焦点顺序与视觉顺序脱节，读屏用户在页面间"瞬移"；触控目标过小，运动障碍用户无法准确点击。无障碍测试的目标就是让这些"对多数用户不可见"的问题进入显式的验证清单。它不仅是合规要求，也反向提升应用的整体可测性——无障碍属性天然是稳定的自动化定位锚点。

## 二、无障碍属性的自动化校验

控件的无障碍属性可以通过自动化读取并断言。测试策略分两步：先做静态扫描式校验，遍历核心页面的控件树，检查所有可点击控件具备非空描述、图片控件有内容描述或显式标记装饰、文本控件内容非空；再做行为校验，验证禁用控件的不可用状态被正确暴露。示例：

```typescript
import { describe, it, expect, beforeAll } from '@ohos/hypium';
import { Driver, ON } from '@ohos/uitest';

describe('首页无障碍属性', () => {
  let driver: Driver = null as unknown as Driver;
  beforeAll(async () => { driver = await Driver.create(); });

  it('图标按钮具备朗读文本', 0, async () => {
    const btn = await driver.findComponent(ON.id('search_icon_btn'));
    const desc = await btn.getAccessibilityText?.() ?? btn.getText();
    expect(desc).assertInclude('搜索');      // 不是空的"按钮"
  });
  it('禁用状态对读屏可见', 0, async () => {
    const btn = await driver.findComponent(ON.id('submit_btn'));
    expect(btn.isClickable()).assertFalse();
    expect(btn.isEnabled?.() ?? true).assertFalse();
  });
});
```

静态扫描不必等到页面写完，可以在每版本回归时对核心页面批量执行，输出"缺描述控件清单"作为整改工单。

## 三、焦点顺序与触控目标的验证

读屏用户按手势逐个遍历焦点，焦点顺序应当与视觉上的逻辑阅读顺序一致。验证方式是沿焦点链遍历并记录朗读文本序列，与预期的页面阅读脚本比对，错序与遗漏立即暴露。触控目标尺寸遵循最小可点击区域的规范（通常以密度无关像素为单位的下限），自动化上可以通过控件的可点击区域坐标计算宽高并断言达标，重叠的可点击区域也要检查——两个按钮热区互相覆盖会让误触率上升，影响所有用户而不仅是无障碍用户。

## 四、人工体验与自动化结合

自动化能覆盖属性与结构，但"朗读起来是否通顺、信息是否有用"需要人工体验：开启读屏功能，蒙眼走完一条核心旅程（注册、下单、支付），记录卡点。建议每版本安排一次轮值体验，把发现的问题转化为自动化断言（例如为缺失描述的控件补属性校验），使人工发现一次、机器长期守护。深色模式与大字号作为相关的易用性维度一并检查：字号放大两档后无截断、无遮挡，这是低视力用户的直接需求，也顺带暴露布局的脆弱点。

## 五、无障碍检查清单

- 所有可交互控件具备非空且有意义的内容描述，纯图标按钮必查；
- 装饰性图片显式标记为不朗读，信息性图片提供描述；
- 焦点遍历顺序与视觉阅读顺序一致，弹层打开后焦点移入、关闭后归位；
- 禁用、选中状态在无障碍属性中正确暴露；
- 可点击区域尺寸达到规范下限，无互相重叠的热区；
- 大字号与深色模式下核心页面无截断遮挡；
- 每版本一次读屏人工走查核心旅程，问题转自动化断言沉淀。

无障碍测试的投入产出比常被低估：它服务的用户群体真实存在，它暴露的问题（描述缺失、焦点混乱、热区过小）往往同时是普通用户体验与自动化稳定性的隐患。把无障碍清单纳入界面验收标准，是低成本高回报的质量实践。

## 六、无障碍问题的量化追踪

要让无障碍改进持续发生，需要把问题变成趋势可见的指标。建议维护三个数字：核心页面的"描述缺失控件数"（静态扫描自动统计，每次回归产出）、核心旅程的"读屏走查通过率"（人工走查的通过条目占比）、历史问题的"整改关闭率"。三个数字按版本出趋势，纳入质量例会通报。经验表明，描述缺失类问题在自动化扫描上线后一到两个版本内即可清零，因为开发者在合入门禁处就会收到提醒；焦点顺序与状态暴露类问题则需要交互设计师参与定义规范，修复节奏稍慢但同样可追踪。量化让无障碍从"良心活"变成"常规工程"，这是它长期不退化的制度保障。

顺带一提无障碍与自动化的共生关系：为读屏补充的内容描述、为焦点管理做的顺序整理，同时正是UI自动化最需要的稳定锚点与交互语义。许多团队在推进自动化时抱怨控件"无法定位、语义不明"，解法往往与无障碍整改殊途同归——给控件以名字、给界面以秩序。因此可以把两项工作合并立项：一次整改，两份收益，无障碍达标的同时自动化定位质量同步提升，这是质量工程里少见的正和博弈。
