# 长时运行（Soak）测试与资源监控指标体系

> 摘要：本文讲解长时运行测试的设计方法：执行形态（时长分级与场景配比）、资源指标体系（内存、存储、连接、电量、温度）、监控采集方案与告警阈值设定，以及长跑结果的版本对比分析实践。

## 一、为什么必须有长时运行测试

多数测试验证的是"一次做对"，而真实用户的重度使用是"数千次之后还对"。许多缺陷只在累积效应下显现：句柄缓慢泄漏在百次打开后耗尽、定时器漂移导致后台任务错乱、缓存碎片使存储缓慢膨胀、日志文件无限增长、长连接的心跳异常在数小时后断链。短时测试无论用例设计多精巧都无法覆盖时间维度，Soak测试的本质就是把时间本身作为测试输入。它同时是资源问题的照妖镜：任何"只增不减"的设计在长跑曲线上都无所遁形。

## 二、执行设计：时长分级与场景配比

时长上分三级：小时级（两到四小时）用于每夜例跑，覆盖核心场景循环；天级（二十四小时以上）用于版本发布前验证，模拟重度用户单日行为；周级用于重大版本或后端配合的专项，观察更缓慢的漂移。场景配比上，长跑不是把功能用例简单重复，而是按用户行为画像构造混合负载：核心旅程占大头、异常路径定期注入、后台静置穿插其间（模拟用户锁屏离开）、弱网与网络切换按比例出现。执行脚本应支持从配置文件读取场景权重，不同产品形态（工具类、内容类、通讯类）维护各自画像，避免一套权重走天下。

## 三、资源指标体系与采集

指标体系覆盖五类。内存类：进程常驻内存、各内存分区构成、GC频率；存储类：应用数据目录大小、数据库文件大小、日志与缓存体积；连接类：长连接存活状态、心跳成功率、socket数量；系统类：CPU占用均值与峰值、温度与降频事件；电池类：单位时间耗电。采集方式以宿主机侧脚本轮询为主：

```bash
# 长跑监控脚本（节选）：每60秒采集一轮写入CSV
while true; do
  ts=$(date +%s)
  pid=$(hdc shell pidof com.example.myapp | tr -d '\r')
  rss=$(hdc shell "hidumper --mem $pid" | awk '/Total [Pp]ss/ {print $3}')
  cpu=$(hdc shell "top -n 1 -p $pid" | awk 'NR>0 && $1==$pid {print $(NF-2)}')
  du=$(hdc shell "du -sk /data/app/el2/100/base/com.example/myapp" | cut -f1)
  echo "$ts,$rss,$cpu,$du" >> soak.csv
  sleep 60
done
```

曲线数据配合场景执行日志对齐分析，任何台阶式跳变都能定位到具体场景。

## 四、阈值设定与告警分级

指标必须配阈值才有判定力。设定方法是以最近三个健康版本的长跑数据为基线，取分位数加安全余量：例如常驻内存八小时涨幅不超过百分之八、存储增长不超过百兆级、心跳成功率不低于三个九、静置时段CPU接近零。告警分三级：提示级（单项超基线百分之十）记录观察、警告级（连续两个采集点超阈值）通知责任人、阻断级（影响功能的资源异常）终止发布流程。阈值本身每季度校准一次，防止基线漂移后告警失效或误报泛滥。

## 五、结果分析与版本对比

长跑报告的形态是"曲线加事件"：各指标的时间序列图叠加场景标记与异常事件点。版本对比时关注三个模式：台阶型增长提示按次泄漏、锯齿扩大提示缓存无上限、缓慢线性漂移提示碎片或日志累积。每条异常曲线都应产出归因结论与整改项，未归因的异常不允许带病发布。长跑资产（脚本、画像、阈值、历史曲线）随版本演进持续积累，它的价值在于把"重度用户数周后遇到的问题"提前到发布前的一夜之间暴露，这是任何短时测试都无法替代的质量纵深。
