# Hypium单元测试框架入门：模块配置与用例结构

> 摘要：本文介绍华为官方测试框架Hypium的定位、工程目录结构、依赖配置、用例组织方式（describe/it/beforeEach）以及两种运行形态（Local单测与ohosTest设备侧测试）的完整上手指南。

## 一、Hypium的定位与核心概念

Hypium是OpenHarmony与HarmonyOS生态官方提供的自动化测试框架，名称由其分层结构衍生：hypium unittest提供单元测试能力，hypium unitest服务于UI与设备侧测试，配套的命令行执行器xdevice负责把测试包部署到目标设备并回收结果。它承担三个职责：用例的组织与发现、断言与校验、以及与DevEco Studio和命令行的执行集成。对开发者而言，掌握Hypium意味着可以把手里的任何ArkTS逻辑纳入自动化验证体系，而不是依赖手工点按界面来确认行为。框架的核心概念非常精简：suite（测试套件）对应一个业务模块的用例集合，用describe声明；spec（用例）对应一个可独立执行的验证点，用it声明；hook（钩子）提供套件与用例级别的前置后置逻辑，包括beforeAll、beforeEach、afterEach、afterAll四个时机。这一结构与业界主流框架保持一致，具备其他语言测试经验的开发者可以零成本迁移心智模型。

## 二、工程结构与依赖配置

在DevEco Studio创建工程时选择带测试模板的模块，会自动生成ohosTest目录。典型结构如下：

```text
entry/src/
  main/ets/            业务代码
  test/
    LocalUnitTest/     本地单测：运行在开发机，速度快，无法访问系统能力
      src/test/List.test.ets
    ohosTest/          设备侧测试：运行在模拟器/真机，可访问系统能力
      src/main/ets/test/
        List.test.ets          用例注册入口
        Ability.test.ets       具体用例文件
      src/test/Resource/       测试资源（图片、配置等）
      module.json5             测试模块清单
      oh-package.json5         测试依赖声明
```

依赖声明在oh-package.json5中写入"@ohos/hypium"依赖项，同步后即可import。List.test.ets是框架的用例注册中心，每个新建的测试文件都要在这里登记才会被执行：

```typescript
// List.test.ets —— 用例注册入口
import { describe, it, expect, beforeAll, beforeEach } from '@ohos/hypium';
import localunitTest from './LocalUnit.test';

export default function testsuite(): void {
  localunitTest();
  // 每新增一个测试文件，在这里追加一行注册
}
```

## 三、第一个测试套件的编写与运行

以验证一个格式化函数为例，完整演示用例结构。被测代码位于main/ets/utils/FormatUtil.ets，测试代码放在同级test目录，保持"源文件与测试文件同名映射"的惯例：

```typescript
import { describe, it, expect, beforeAll, afterAll } from '@ohos/hypium';
import { formatDuration } from '../../../../main/ets/utils/FormatUtil';

describe('FormatUtil格式化', () => {
  let base: number = 0;

  beforeAll(() => { base = 3600; });        // 整个套件执行一次
  afterAll(() => { base = 0; });

  it('毫秒级时长转为分秒', 0, () => {
    expect(formatDuration(95_000)).assertEqual('01:35');
  });
  it('零与负数返回占位符', 0, () => {
    expect(formatDuration(0)).assertEqual('00:00');
    expect(formatDuration(-5)).assertEqual('--:--');
  });
  it('超一小时进位', 0, () => {
    expect(formatDuration(base * 2 + 120)).assertEqual('02:02');
  });
});
```

it的第二个参数是过滤标签（0表示默认），第三个参数是同步或异步的用例体。运行方式有两种：在DevEco Studio中打开测试文件，点击用例旁的绿色箭头单跑或整套跑，结果面板展示每个用例的耗时与状态；命令行方式则由构建工具触发测试任务并输出报告，适合接入持续集成。

## 四、Local单测与设备侧测试的选择

两种形态的边界必须清晰。Local单测运行在开发机的本地运行时中，毫秒级反馈，但无法调用@ohos开头的系统能力，适合纯逻辑、数据结构、算法与不依赖平台API的ViewModel。设备侧测试（ohosTest）部署到模拟器或真机执行，可以真实调用网络、存储、通知等能力，速度慢一个数量级，适合系统能力封装层与集成验证。工程实践上建议把百分之八十以上的逻辑用例放在Local层，仅把必须触碰系统能力的部分下沉到设备侧，两层各自维护独立的用例注册入口与运行配置。判断某个用例归属哪层的简单标准：把import里所有@ohos模块去掉后逻辑是否还能跑，能跑则归Local，否则归设备侧。

## 五、常见踩坑与规范清单

- 用例文件必须同步登记到List.test.ets，否则静默不执行，这是新手最常见的"我的测试没跑"问题；
- Local单测中import系统能力会在运行时报错，遇到即应拆分或移到设备侧；
- 用例之间禁止共享可变状态，公共数据在beforeEach中重建，保证任意顺序执行结果一致；
- 测试文件命名与目录和被测模块一一对应，禁止把所有用例堆进单个巨型文件；
- 断言失败信息应包含业务语义描述，避免只留一行堆栈；
- 提交前本地全量跑一遍测试再推送，门禁红灯浪费的是全组的时间。

## 六、套件组织与执行模型的工程细节

理解Hypium的执行模型能解决团队规模化后的三类问题。第一是筛选：it的过滤标签参数可以区分冒烟集与全量集，命令行与门禁按标签挑选执行范围，避免每次全量跑造成反馈迟缓。第二是隔离：框架默认按注册顺序同步执行套件，任何依赖顺序的用例都是隐患，公共初始化放beforeAll、每用例数据重建放beforeEach，使任意单条用例都可以独立重跑，这是排查失败时的硬需求。第三是并发：设备侧测试受目标设备性能约束，不宜盲目提高并发度，否则执行时间波动会掩盖真实的性能回归信号。目录组织上建议按业务域拆分测试文件，每个文件聚焦一个被测单元，套件名使用"模块_单元"的中文命名，失败报告直接呈现业务位置而非匿名编号。团队还应约定测试文件的导入路径规范，相对路径层级过深时在配置中设置路径别名，减少重构搬移文件时的大面积修改。当这些细节成为团队默认习惯后，测试代码才能像业务代码一样被长期维护而不是定期推倒重来。

掌握Hypium的配置与组织方式后，团队就具备了"让任何逻辑可验证"的基础设施，后续的断言技巧、异步测试与Mock策略都建立在这套结构之上。
