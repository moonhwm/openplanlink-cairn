# Hypium断言库expect详解与自定义断言

> 摘要：本文系统讲解Hypium断言对象expect的完整断言方法族（相等、布尔、包含、空值、深度比较、异常），分析弱类型断言与严格断言的选择原则，并给出失败信息工程化与自定义断言封装的实践方法。

## 一、断言是用例的灵魂

一个没有断言的测试只是"执行了一段代码"，无论通过与否都不构成质量证据。断言的三个要素是：实际值从哪来、期望值是什么、失败时能否快速定位差异。Hypium的断言围绕expect函数构建，把实际值包装为断言对象，再链式调用校验方法。方法命名区分手工断言与断言链两种风格：手工风格直接返回布尔结果，适合嵌入复杂条件；断言链风格抛出带差异信息的异常，失败即终止当前用例并记录现场，是绝大多数场景的默认选择。两者混用时要注意语义：assertTrue包装的复合条件失败时只能报告真假，而assertEqual能报告两边的实际取值，诊断价值完全不同，能用精确断言的场景就不要退化为布尔断言。

## 二、核心断言方法族

```typescript
import { describe, it, expect } from '@ohos/hypium';
import { parseCoupon } from '../utils/CouponParser';

describe('断言方法族演示', () => {
  it('相等类断言', 0, () => {
    expect(1 + 1).assertEqual(2);
    expect('ok').assertEqual('ok');
    expect(0.1 + 0.2).assertClose(0.3, 0.0001);   // 浮点比较必须用容差
  });
  it('布尔与空值类断言', 0, () => {
    expect(parseCoupon('NONE').usable).assertFalse();
    expect(parseCoupon('NONE').rule).assertUndefined();
    expect([]).assertNull();          // 注意：数组非null，此断言会失败——先想清楚语义
  });
  it('包含与长度类断言', 0, () => {
    const msg = '优惠券将于今日24时过期';
    expect(msg).assertInclude('24时');
    expect([1, 2, 3]).assertContain(2);
    expect(msg.length).assertLargerOrEqual(10);
  });
  it('实例与深比较断言', 0, () => {
    const r = parseCoupon('FULL100');
    expect(r).assertInstanceOf(Object);
    expect(r.tags).assertDeepEquals(['满减', '可叠加']);
  });
  it('异常断言', 0, () => {
    expect(() => parseCoupon('')).assertThrowError('空券码');
  });
  it('Promise结果断言', 0, async () => {
    await expect(parseCouponAsync('X1')).assertPromiseResolveIs('done');
  });
});
```

上述示例刻意保留了一个语义陷阱：assertNull检查的是null而非空集合，用错断言方法会让用例"看起来在验证"实则验证了错误的不变量。评审断言时应逐条追问"这个断言失败时会输出什么信息"，输出不了有效差异信息的断言都值得改造。

## 三、异步断言与超时控制

异步是被断言对象的高频形态。Hypium对async用例函数会等待其返回的Promise落定后再判定结果，因此正确姿势是await到底再断言，禁止把未await的Promise直接交给断言——那只会得到"断言一个Promise对象本身"的错误语义。涉及定时器或轮询的场景要显式控制超时：用Promise包装一个带超时上界的等待循环，超时即用assertTrue(false, '描述')制造带语义的失败，而不是让用例无限挂起占用执行器。对预期会reject的调用，要么捕获错误后断言错误码，要么使用框架提供的Promise方向断言，确保"正确地失败了"与"意外地失败了"可区分。

## 四、失败信息工程化

断言的价值密度在失败瞬间兑现。三条工程化规则：第一，期望值写具体字面量而非变量引用，失败信息里能直接看到差异；第二，复合对象断言聚焦关键字段而非整体序列化比较，整体比较失败时输出一长串难以阅读的差异；第三，利用消息参数附加业务上下文。当框架自带输出不足时，可以在断言前主动校验并构造失败：

```typescript
function assertDiscount(actual: number, want: number, scene: string): void {
  if (Math.abs(actual - want) > 0.001) {
    expect(`场景[${scene}] 折扣不符`).assertEqual(
      `期望${want.toFixed(2)} 实际${actual.toFixed(2)}`);
  }
}
```

这种自定义断言把领域语义编码进失败信息，排查者无需打开用例代码即可理解失败含义。团队可以沉淀一套业务断言库（金额相等、时间窗内、列表含关键项），统一精度与文案格式，让整个测试套件的失败报告像日志一样可读。

## 五、断言质量检查清单

- 每个用例至少一个精确断言（相等、包含、实例），禁止只有console输出的"观察型用例"；
- 浮点比较一律使用容差断言，禁止直接assertEqual；
- 异常路径必须断言错误类型或消息，禁止空catch；
- 异步值必须await后断言，禁止对Promise对象本身断言；
- 深比较用于结构校验，关键字段另加独立断言保证失败可读；
- 自定义断言集中维护，命名表达业务语义而非技术操作；
- 定期清理恒真断言（如assertTrue(true)）与被注释掉的断言。

## 六、断言数量与粒度的平衡艺术

一条用例该放多少断言并没有绝对数字，但有清晰的权衡逻辑。单一职责的极端是每条用例只断言一件事，失败时定位最快，但前置准备重复执行，套件总时长膨胀；聚合的极端是一趟流程断言十几个值，时长经济但失败后后续断言全部不执行，一次只能暴露一个问题。工程上的折中规则是：同一业务动作的直接后果可以聚合断言（提交后同时验证返回值、状态、副作用次数），不同业务动作必须拆分用例；前置成本高昂的集成场景可以适度聚合，但聚合用例的断言顺序应从"最可能失败的粗检"排到"细粒度校验"，让最常见的失败最早暴露。另一个易被忽视的维度是断言的独立性：任何断言不应以其他断言的通过为前提，例如先断言列表长度再断言元素内容是安全的，但"若上一断言失败则本断言必失败"的链式依赖要拆开。定期统计失败用例的平均首次诊断时长，是检验断言粒度设计是否合理的最直接指标，超过十分钟的用例值得回头重构其断言结构。

断言方法的选择看似细节，实则决定了测试套件的诊断效率。把"失败时我能知道什么"作为断言设计的第一问题，测试报告从"红绿灯"升级为"排障指南"，这是自动化测试成熟度最直观的分水岭。
