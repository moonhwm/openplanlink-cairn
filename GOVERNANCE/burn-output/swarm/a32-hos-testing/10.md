# 异步代码单元测试：Promise、async/await与回调的验证方法

> 摘要：本文讲解Hypium框架下异步代码的完整测试方法，包括async用例的等待语义、回调转Promise封装、定时器与轮询的可控化、并发与竞态场景的确定性构造，以及异步测试常见假通过陷阱的识别。

## 一、异步测试的基本范式

ArkTS的运行时是单线程事件循环，异步无处不在：网络请求、文件读写、动画回调、定时任务。异步测试的第一原则是用例本身声明为async并await被测逻辑，让断言发生在结果落定之后。Hypium会等待用例函数返回的Promise落定再判定通过与否，因此"await后断言"是最可靠的范式；反过来，忘记await是异步测试第一大假通过来源——用例在Promise落定前就返回，断言根本没执行，绿灯毫无意义。评审异步用例时只需机械检查一件事：每个断言之前，所有产出被断言值的调用是否都被await或以同步方式完成。

```typescript
import { describe, it, expect } from '@ohos/hypium';
import { loadConfig, mergeUser } from '../service/ConfigLoader';

describe('异步逻辑验证', () => {
  it('加载默认配置并合并用户覆盖', 0, async () => {
    const cfg = await loadConfig();          // 必须await
    expect(cfg.theme).assertEqual('light');
    const merged = await mergeUser(cfg, { theme: 'dark' });
    expect(merged.theme).assertEqual('dark');
    expect(cfg.theme).assertEqual('light');  // 原对象不被污染
  });
});
```

## 二、回调风格的可测化封装

存量代码里大量回调风格接口（成功回调查结果、失败回调查错误），直接测试需要手工桥接。标准做法是编写promisify工具，把回调转换为Promise，测试即回到await范式：

```typescript
function waitEvent(off: (cb: () => void) => void,
                   on: (cb: () => void) => void,
                   ms = 2000): Promise<void> {
  return new Promise((resolve, reject) => {
    const t = setTimeout(() => reject(new Error('等待事件超时')), ms);
    on(() => { clearTimeout(t); off(() => {}); resolve(); });
  });
}

it('缓存刷新完成后发出通知', 0, async () => {
  const bus = new EventBus();
  const p = waitEvent(bus.off.bind(bus), bus.on.bind(bus));
  bus.emitRefresh('user');      // 触发动作
  await p;                      // 等待事件
  expect(bus.lastEvent).assertEqual('user');
});
```

超时上限是必选项：没有超时的等待会让挂死的用例永久占用执行器，把整套测试拖成超时灾难。超时时长要明显大于正常路径耗时又远小于人工忍耐阈值，通常一到两秒。

## 三、定时、轮询与节流的确定性测试

依赖真实时间的逻辑（重试退避、轮询间隔、防抖节流）必须做时钟注入才能确定性测试：把"当前时间"与"延时调度"抽象为可替换的注入点，测试中使用虚拟时钟手动推进。验证节流的经典断言是：连续触发N次后回调仅执行符合窗口约定的次数。没有虚拟时钟时，退而求其次的方案是缩短真实间隔并容忍毫秒级误差，但这类用例天然脆弱，只应作为兜底而非常态。轮询场景还要验证终止条件：达到目标停止、达到最大次数停止、错误可终止，三条缺一不可，否则线上会出现永不停止的轮询耗电缺陷。

## 四、并发与竞态的确定性构造

竞态缺陷在真机上几乎无法复现，却是单测可以精确构造的场景。典型手法有三：其一，用受控的假异步源（立即resolve的桩与延迟resolve的桩组合）强制特定完成顺序，验证"快请求后发先至"时旧结果是否被丢弃；其二，验证幂等性，同一操作并发触发两次，副作用只发生一次（如重复下单拦截）；其三，验证取消语义，请求被取消后其回调不再影响状态。以下示例验证过期响应丢弃：

```typescript
it('过期响应不覆盖新数据', 0, async () => {
  const slow = new Promise(r => setTimeout(() => r('old'), 30));
  const fast = Promise.resolve('new');
  const box = new RespGuard();
  box.accept(slow);                 // 先发
  box.accept(fast);                 // 后发先至
  await new Promise(r => setTimeout(r, 60));
  expect(box.current).assertEqual('new');
});
```

## 五、异步用例卫生清单

- 所有产出断言值的调用都被await，禁止裸调用后断言；
- 等待外部事件必有超时，超时失败带场景描述；
- 定时逻辑经时钟注入验证，真实等待仅作兜底；
- 竞态用例显式标注强制的事件顺序假设；
- 并发副作用断言次数而非只断言最终值；
- 用例禁止依赖其他用例的异步残留，afterAll里清理全局监听。

## 六、虚拟时钟的设计细节与团队复用

虚拟时钟要真正好用，需要处理好四个细节。第一是统一时间源：工程内禁止直接调用系统时间与延时接口，一律经由ClockPort获取，生产环境提供真实实现，测试环境提供FakeClock，这一约定一旦有例外就会重新引入不确定性。第二是手动推进语义：FakeClock的advance方法除了移动当前时间，还要按到期顺序触发已注册的定时回调，保证"推进两千毫秒"与"真实流逝两秒"在业务视角等价。第三是回调队列的可观测性：FakeClock应暴露待触发任务队列的查询接口，测试可以断言防抖场景下队列中只有一个挂起任务，直接验证"合并多次触发"的实现正确性，这比等待后数回调次数更精确。第四是边界注入：advance支持跨过多个到期点时逐个触发并在每个触发点提供检查钩子，用于验证重试退避序列的间隔递增。把FakeClock与配套断言沉淀为团队公共测试库后，时间相关的业务逻辑测试从最脆弱的一类变成最确定的一类，深夜跑批的重试逻辑也能在白天被完整验证。

## 七、异步测试的执行时长治理

异步用例天然比同步用例慢，若不治理，套件时长会悄悄失控。治理手段按优先级排列：第一优先消除真实等待，把轮询与重试间隔参数化并在测试中置零，多数"必须等"其实只是实现偷懒；第二收紧行为等待上限，单条用例的超时上限默认两秒，确需更长的场景显式标注理由；第三拆分长链路用例，串联五个异步阶段的端到端用例应拆成阶段级用例，只在集成层保留一条完整链路作为串联验证；第四为套件设置总时长预算，超预算的流水线环节报警并要求优化。每月统计异步用例的平均与尾部时长，尾部长度往往由个别病态用例贡献，定点消除即可显著提速。
