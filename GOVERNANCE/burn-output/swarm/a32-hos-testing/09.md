# ArkTS纯函数与业务类的单元测试实践

> 摘要：本文以真实业务形态为样本，讲解纯函数、带状态业务类与参数化表驱动三类典型被测对象的单元测试写法，覆盖用例组织、依赖隔离与失败诊断的完整实践细节。

## 一、纯函数测试：最高性价比的测试投资

纯函数指输出只依赖输入、不产生副作用的函数，例如金额格式化、日期计算、规则校验、数据归一化。它们是单测回报率最高的对象：无需任何桩与环境，一个输入输出表即可穷尽验证。写好纯函数测试的关键是表驱动组织——把所有输入输出对集中成一张数据表，用例体只做"取一行、调函数、比结果"的循环，新增等价类只需加一行数据，不需要复制整个用例骨架。

```typescript
import { describe, it, expect } from '@ohos/hypium';
import { roundMoney } from '../utils/Money';

describe('金额取整规则', () => {
  const table: Array<[number, number, string]> = [
    [10.555, 2, 10.56],   // 常规四舍五入
    [10.554, 2, 10.55],   // 舍去侧边界
    [-10.555, 2, -10.56], // 负数对称性
    [0.001, 2, 0.00],     // 归零边界
    [99.999, 1, 100.0],   // 进位跨整数
    [1234.5, 0, 1235],    // 零位小数
  ];
  for (const [input, digits, want] of table) {
    it(`roundMoney(${input},${digits})=${want}`, 0, () => {
      expect(roundMoney(input, digits)).assertClose(want, 1e-9);
    });
  }
});
```

用例名由数据行自动生成，失败报告直接暴露是哪一行数据不匹配，诊断成本趋近于零。凡是能写成纯函数的业务规则，都应当主动抽取成独立导出函数，这是"为可测试性而设计"最廉价的实践。

## 二、带状态业务类测试：状态机的穷举验证

业务对象往往持有内部状态并按事件迁移，例如播放器控制器、订单状态机、倒计时器。测试这类对象的核心方法是状态迁移穷举：列出全部状态与全部事件构成的矩阵，逐格验证合法迁移的结果与新状态，非法迁移则验证被拒绝且状态不变。以倒计时为例，初始为空闲态，start事件进入运行态，pause在运行态合法、在空闲态应被忽略，reset任意态回到空闲：

```typescript
import { describe, it, expect, beforeEach } from '@ohos/hypium';
import { CountDown } from '../model/CountDown';

describe('倒计时状态机', () => {
  let cd: CountDown = new CountDown(60);
  beforeEach(() => { cd = new CountDown(60); });   // 每用例全新实例

  it('start后处于运行态', 0, () => {
    cd.start();
    expect(cd.isRunning()).assertTrue();
  });
  it('空闲态pause被忽略', 0, () => {
    cd.pause();
    expect(cd.isRunning()).assertFalse();
    expect(cd.remain()).assertEqual(60);
  });
  it('运行态pause冻结剩余值', 0, () => {
    cd.start();
    cd.tick(10);
    cd.pause();
    const frozen = cd.remain();
    cd.tick(5);                       // 暂停后tick不应减少
    expect(cd.remain()).assertEqual(frozen);
    expect(cd.remain()).assertEqual(50);
  });
  it('归零触发结束回调一次', 0, () => {
    let fired = 0;
    cd.onFinish(() => { fired++; });
    cd.start(); cd.tick(60); cd.tick(1);
    expect(fired).assertEqual(1);     // 只触发一次
  });
});
```

注意tick被设计为注入时间推进量而非依赖真实时钟，这正是可测试性设计的体现：测试可以用任意节奏快进慢放，不受真实定时器精度干扰。回调验证使用局部计数器而非全局标志，避免用例间污染。

## 三、参数化与随机化补充

表驱动覆盖的是已知危险点，随机化测试则用于发现未知边界：对数值函数生成大量随机输入，验证不变量（如roundMoney的结果与输入差值不超过半个最小精度单位、序列化再反序列化必还原原值）。随机测试的种子要打印进失败信息，保证失败可精确复现。两类技术互为补充：表驱动守已知边界，随机不变量守未知领域，每发现一个随机失败就提炼一行新表项，让确定性集合持续生长。

## 四、失败诊断与用例卫生

业务类测试最容易腐化的方式是断言弱化与状态泄漏。评审时执行以下清单：

- 每个状态断言同时验证"新状态正确"与"副作用次数正确"（回调触发次数、通知次数）；
- beforeEach重建被测对象，禁止用例依赖执行顺序或共享实例；
- 随机源与时间源全部经注入获取，失败信息携带种子；
- 表驱动数据行带语义注释，评审者能看懂每行代表的业务场景；
- 删除"探针式"中间输出，只保留断言；
- 状态机用例覆盖矩阵的每个格子，标注不适用格的原因。

## 五、业务类测试的价值排序与推进节奏

存量工程不可能一夜之间补齐所有业务类测试，需要一套价值排序规则指导投入方向。第一优先级是资损与规则类：价格计算、优惠叠加、库存扣减、积分增减，这类逻辑出错直接造成经济损失，且缺陷单一旦线上化很难追溯。第二优先级是多状态流转类：订单、审批、播放等状态机，分支组合多、人工回归易漏。第三优先级是协议解析类：对服务端下发数据的解析与容错，脏数据引发崩溃的防线全在这里。排在最后的才是展示辅助类逻辑，它们出错的代价最小且肉眼可见。确定顺序后，推进节奏建议与需求迭代合流：每个迭代从存量清单里按优先级领取两三个类补齐测试，同时新需求的业务类必须带测试合入，一年左右存量高风险区即可清零。补充存量测试时要克制"顺手重构"的冲动：先按现状锁定行为（哪怕行为是错的），再单独提缺陷与修复，避免测试与重构混在一个变更里导致回归无法归因。

## 六、测试数据的构造与复用

表驱动与状态机用例都依赖高质量的数据构造。推荐建立独立的测试数据工厂文件，集中提供典型业务对象的构造函数：合法用户、过期会员、空购物车、满减临界订单等，每个构造函数的名字直接表达业务含义。数据工厂带来的好处有三层：用例正文只保留业务叙事，读起来像需求描述；构造逻辑修改变更时全量用例自动受益；新人补充用例时不需要重新摸索字段含义。对深层嵌套的对象提供覆盖式参数（只传关心的字段，其余取默认），可以避免用例里出现大段与断言无关的填充噪音。数据工厂本身也应保持精简，膨胀到难以维护时说明被测模型本身字段过肥，这往往是可测试性预警信号。
