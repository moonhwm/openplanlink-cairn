# 17 MCP工具重入问题：同一工具的并发与递归调用竞态

> 摘要：本文剖析同一MCP工具被并发调用或递归调用时的竞态形态：共享状态撕裂、检查与行动间隙竞态、自递归栈膨胀，给出串行化、状态隔离与递归防护的实现。

## 一、重入的三种形态

重入指同一执行体在尚未完成前被再次进入。MCP服务器上它以三种形态出现。形态一是并发重入：多个客户端会话（或同一会话的多路请求）同时调用同一工具，工具内部共享的内存状态被交叉读写，出现丢更新、脏读、迭代中修改。形态二是自递归重入：工具A的实现内部经间接路径再次调用自身，典型如文件整理工具在处理目录时对子目录调用自己，缺乏深度控制时深目录或符号链接环导致栈溢出或无限执行。形态三是事件重入：工具执行中触发的回调（定时器、通知处理）再次进入同一工具的代码路径，回调里读到的共享状态正处于中间态。三种形态的共性是执行体假设了独占状态，而这个假设在并发环境中不成立。

## 二、竞态的具体机理

以"检查再行动"模式为例：工具先检查任务表中是否存在同名草稿，不存在则创建。两个并发调用同时通过检查，各自创建，产生重复草稿——检查与行动之间存在时间间隙，间隙中对方的写入不可见。内存数据结构上的竞态更隐蔽：工具在迭代一个列表时另一个调用删除元素，轻则跳项重项，重则底层结构损坏抛异常。自递归的机理则是状态依赖环：工具把"处理嵌套结构"实现为"对子结构调用自己"，而子结构经配置或符号链接指回祖先，调用图成环，深度无界。这些竞态的共同特征是复现概率低、Damage与时机相关，测试环境难以稳定触发，必须在设计期消除而不是靠测试兜底。

## 三、防护实现参考

```python
class ReentrancyGuard:
    def __init__(self):
        self.locks = KeyedLocks()          # 按资源键的细粒度串行化
        self.depth = ContextVar("depth", default=0)
        self.max_depth = 16

    def tool(self, name, resource_key_fn):
        def deco(fn):
            async def wrapped(args, ctx):
                key = resource_key_fn(args)
                async with self.locks.acquire(f"{name}:{key}"):
                    if self.depth.get() >= self.max_depth:
                        raise ToolError("recursion depth exceeded",
                                        code=-32020)
                    token = self.depth.set(self.depth.get() + 1)
                    try:
                        return await fn(args, ctx)
                    finally:
                        self.depth.reset(token)
            return wrapped
        return deco
```

三层防护各司其职：键控锁把同一资源的并发调用串行化，不同资源保持并行，避免全局锁的性能塌陷；上下文深度计数拦截自递归，深度上限按最深的合法嵌套结构加余量设定；finally中的深度复位保证异常路径也正确退栈。对确实需要并发读的场景，用读写锁或不可变快照替代互斥，把"写串行、读并行"的语义显式化。

## 四、重入安全改造清单

- 盘点工具内部的共享可变状态，逐项标注并发访问策略：串行、快照、原子原语。
- 资源键设计到业务实体粒度，锁粒度过粗伤吞吐、过细漏竞态。
- 唯一性约束下沉到存储层，作为检查行动竞态的最后防线。
- 自递归路径显式传深度参数或走上下文计数，环状引用在入口检测。
- 迭代共享集合一律用快照副本，禁止边迭代边让其他路径修改。
- 并发压测以同一工具同键高并发调用为必测项，断言无重复副作用。
- 死锁排查预案：锁获取顺序全局排序，超时获取失败即告警。

## 五、边界情形

锁与取消的交互是易错边界：等待键锁的请求被客户端取消，等待必须立即中断并释放登记，否则一个取消的请求会永久占坑。嵌套锁顺序必须全局一致，两个工具分别以相反顺序获取两把锁必然偶发死锁，静态检查锁序应纳入代码评审。重入防护的另一个极端是过度串行化：全局互斥把服务器退化成单线程，吞吐崩塌；键控粒度的持续调优是运行期任务，依据锁等待时间的分布数据调整。重入安全的本质是把工具从"独占世界的脚本"改造成"并发环境中的服务"，这一步没走完的MCP服务器，规模一上去就会被自己的竞态淹没。
