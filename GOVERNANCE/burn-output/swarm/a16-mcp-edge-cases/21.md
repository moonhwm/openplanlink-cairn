# 21 长事务工具的取消后再入：清理路径与半途状态收容

> 摘要：本文聚焦被取消的长事务工具在再次调用时的衔接问题：半途状态的识别与收容、续做与重做的决策、清理路径的幂等化与防死锁。

## 一、取消留下的半途状态

长事务工具（数据迁移、批量重建、媒体转码流水线）被取消后，世界停在中间态：一部分记录已迁移一部分没有、部分中间产物已生成、外部系统的部分调用已完成。客户端此时再次调用同一工具，服务器面对的问题不是从零执行，而是收容前次半途状态：哪些已完成、哪些做了一半、哪些未开始。无意识的重跑轻则浪费（重做已完成部分），重则出错（在半成品中间产物上叠加执行、对外部系统重复触发不可幂等的动作）。取消后再入的工程目标，是让第二次调用能够精确衔接或安全重做，而不是赌前次取消的现场恰好无害。

## 二、续做与重做的决策依据

再入策略分两类。续做（resume）：基于前次断点继续，适合步骤昂贵、状态可标识的场景，要求工具落盘执行进度（断点日志、已完成集合的游标）。重做（redo from scratch）：先清理前次现场再完整重来，适合步骤幂等且廉价、或状态太碎无法续做的场景，要求清理动作完备且幂等。决策依据三条：前次状态的碎片化程度（越碎越倾向重做）；单步成本（越贵越倾向续做）；清理的风险（清理本身可能破坏已完成部分时倾向续做）。无论哪种，工具描述必须声明再入语义，调用方需要知道再次调用是续是重，特别是外部副作用是否会被再次触发。

## 三、断点与清理的实现

```python
class LongTxnTool:
    async def run(self, plan_id, items):
        state = await self.store.load_checkpoint(plan_id)
        if state and state.phase == "cancelled_midway":
            policy = self.reentry_policy(plan_id)
            if policy == "resume":
                items = [i for i in items
                         if i.id not in state.completed_ids]
            else:                                   # redo
                await self.cleanup(state, mode="idempotent")
                state = Checkpoint.fresh(plan_id)
        for item in items:
            await self.process_one(item)            # 每项幂等
            await self.store.mark_done(plan_id, item.id)   # 先做事后记点
            if self.cancelled():
                await self.store.set_phase(plan_id, "cancelled_midway")
                raise Cancelled(completed=len(state.completed_ids))
        await self.store.set_phase(plan_id, "finished")
```

两个顺序纪律：先做事后记点——崩溃发生在事与点之间时，重入会把该事再做一次，因此process_one自身必须幂等（按项幂等键）；取消退出前显式落盘cancelled_midway相位与已完成集合，让下次再入有据可查。清理函数的幂等化手段：按清单清理而非按目录通配、每项清理记录回执、重复清理无副作用（删除不存在项视为成功）。

## 四、再入安全清单

- 长事务工具强制携带计划标识（plan_id或幂等键），作为断点的挂载点。
- 断点记录原子化：相位、已完成集合、游标一次写入，避免断点自身撕裂。
- 每个工作项的执行幂等：项级幂等键下沉到后端唯一约束。
- 清理动作清单化执行，回执留档，支持中断后继续清理。
- 再入语义（续做或重做）写入工具描述，外部副作用的重触发情况显式标注。
- 取消到再入的时间窗口内，后台不得有遗留任务仍在写同一状态。
- 演练用例：取消在每一阶段边界发生后再入，断言最终结果与一次性执行一致。

## 五、边界情形

取消后的孤儿任务是隐蔽边界：取消通知只是请求停止，实际任务线程可能还在收尾，再入瞬间新旧两个执行并发写同一断点，必须由断点存储的乐观锁（版本号递增）裁决，旧执行对断点的写入被拒绝并强制其自 cleanup 退出。另一个边界是外部系统的不可回滚动作：前次已触发的对外下单无法清理，再入策略只能续做并在结果中披露前次已触发的动作清单。长事务的取消后再入能力，本质上是把"取消"从丢失现场的事故变成可恢复的暂停，这个转变完全依赖断点与幂等两块基础设施的扎实程度。
