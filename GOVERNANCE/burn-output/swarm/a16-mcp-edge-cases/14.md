# 14 通知与请求通道分离时的部分失败：请求成功但通知丢失

> 摘要：本文讨论MCP中通知（progress、cancelled、listChanged、日志）与请求响应走不同路径时的丢失形态，分析通知丢失造成的隐性后果与可靠通知的补偿设计。

## 一、通知的可靠性地位

MCP的消息分两类：请求响应对与通知。通知没有回执、没有重试、没有确认，协议把它设计为尽力而为。在单通道传输（stdio）上，通知与响应共享同一条有序流，响应到达则此前的通知大概率也已到达；但在多通道部署（Streamable HTTP的独立事件流、经消息代理转发的通知）中，通知与请求响应分道扬镳，部分失败获得独立形态：请求成功、通知丢失。丢失的通知不会产生任何错误，它的影响全部以"该发生的事没发生"的形式延迟显形——进度通知丢了只是观测缺失，取消通知丢了意味着服务器把一个该停的任务执行到底，变更通知丢了意味着客户端拿着永远陈旧的缓存继续决策。

## 二、各类通知丢失的后果分级

按后果严重度排序：取消通知丢失最重，直接造成资源浪费与副作用放大，取消意图必须送达；资源与工具清单变更通知丢失次重，客户端缓存与服务器实际状态分叉，后续调用引用不存在的条目或错过新能力；进度通知丢失较轻，影响观测与超时豁免判定，可能引发误判超时；日志与遥测通知丢失最轻，损失可观测性但不影响正确性。分级决定投入：重级别的通知需要可靠性机制，轻级别保持尽力而为即可，一刀切地全量可靠化会付出不必要的时延与复杂度代价。

## 三、可靠通知的补偿设计

```python
class ReliableNotify:
    def __init__(self, channel, store):
        self.channel = channel
        self.store = store            # 持久化最近通知的环形日志
        self.seq = 0

    def emit(self, method, params, critical=False):
        self.seq += 1
        record = {"seq": self.seq, "method": method, "params": params}
        if critical:                  # 关键通知先持久化再发送
            self.store.append(record)
        self.channel.send(record)

    def on_client_resync(self, last_seen_seq):
        # 客户端重连后带最后见到的序号，补发缺口
        for record in self.store.since(last_seen_seq):
            self.channel.send(record)
```

配套的客户端逻辑：对关键通知类（取消、变更）维护连续序号，检测到跳号即发起resync；重连后总是发送last_seen_seq请求补发，而不是从零重建。对于无法改造为可靠通道的场景，用状态对账替代通知投递——变更通知丢了，但客户端定期全量拉取清单校验，最终一致收敛；取消通知丢了，但服务器侧超时兜底终会停止任务。状态对账的周期就是通知丢失的最大影响窗口，必须与业务容忍度匹配。

## 四、通知可靠性建设清单

- 为关键类通知引入单调序号，客户端检测跳号并触发补发。
- 通知载荷保持幂等与可重放，补发重复通知不得引发重复副作用。
- 重连流程内建resync步骤，携带最后序号而非依赖客户端记忆。
- 为无法可靠化的通知配置周期性状态对账兜底，周期与业务容忍度挂钩。
- 取消意图同时走通知与请求参数标记（幂等键标注已取消），双保险。
- 监控通知投递率与跳号率，作为通道健康的独立指标。

## 五、边界情形

通知顺序是敏感边界：序号保证了检测跳号的能力，但跨通道的通知乱序仍可能让客户端先见到变更后的全量拉取结果、后见到过期的变更通知，处理逻辑必须以序号大小裁决新旧而不是以到达顺序。另一个边界是通知风暴与可靠化的叠加：清单高频变更时补发日志膨胀，需要合并语义——同一资源的多次变更通知可以折叠为最新状态，序号推进但历史可丢弃，只保证最终状态可达。通知部分失败的教训是：尽力而为的通道上承载确定性意图时，必须用序号、补发、对账三件套把"大概送达"升级为"最终送达"。
