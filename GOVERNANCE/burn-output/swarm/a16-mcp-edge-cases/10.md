# 10 批量资源读取的部分失败：单项出错的处理模型

> 摘要：本文讨论一次MCP调用内聚合多个子项（多资源读取、多键查询、多文件解析）时部分子项失败的三种响应模型，给出部分结果包装结构与客户端消费规范。

## 一、聚合调用的部分失败困境

客户端常在一个请求里请求多个逻辑子项：读取三个资源URI、查询五个键、解析一批文件。JSON-RPC的响应结构对这种场景天然不友好——整个请求只有一个结果或一个错误，单项失败要么吞掉其余成功项（整体报错，浪费已完成工作），要么隐藏失败（全部成功，数据静默缺失），要么中断执行（后面的项不再处理）。三种处理都不符合调用方预期：调用方通常希望拿到成功的部分、知道失败的部分与失败原因，再自行决定是否重试失败项。部分失败的工程目标就是把这三份信息完整、结构化地交出去，同时保持协议兼容——外层仍是正常的JSON-RPC响应，不把单项错误升格为协议错误。

## 二、三种响应模型

第一种是快速失败模型：遇错即停，未处理的项标记为skipped。语义最简单，适合有严格顺序依赖的批量（后项依赖前项输出），缺点是失败一项拖累全部。第二种是尽力而为模型：全部子项独立执行，失败项携带错误信息返回，成功项正常返回。语义最实用，适合子项彼此独立的绝大多数批量场景，也是推荐默认。第三种是分级降级模型：子项按重要性分层，核心层失败则整体失败，次要层失败仅记录。适合混合了必需数据与可选数据的调用。三种模型的选择必须写进工具描述，客户端依据描述决定如何消费结果，而不是靠猜。

## 三、部分结果包装结构

```json
{
  "content": [
    { "type": "text", "text": "..." }
  ],
  "structuredContent": {
    "results": [
      { "key": "res-a", "status": "ok",   "value": { "body": "..." } },
      { "key": "res-b", "status": "error", "code": -32010,
        "message": "resource not found" },
      { "key": "res-c", "status": "skipped",
        "message": "aborted after threshold" }
    ],
    "summary": { "ok": 1, "error": 1, "skipped": 1 }
  },
  "isError": false
}
```

设计要点：外层isError为false表示调用本身完成，单项失败在结果内部表达；每个子项携带稳定key（通常是请求中的URI或索引），让客户端能把成败映射回请求项；status枚举严格三值，skipped与error必须区分，前者代表未尝试，后者代表尝试后失败；summary供快速判断，避免客户端遍历大数组。单项错误码使用服务器自定义区间，禁止占用协议保留错误码。

## 四、服务器实现与客户端消费清单

- 每子项独立超时与独立错误捕获，单项超时不得拖垮整批。
- 并发子项数设上限，防止批量请求瞬时打满后端连接池。
- 失败子项重试只针对error项，skipped项需整批重新调度。
- 错误信息不得泄漏内部路径、堆栈与凭据类字段。
- 批大小设上限并在超出时要求分页，防止部分失败场景下的巨型响应。
- 客户端对summary中error占比设阈值，超阈值视同整体失败走降级路径。
- 记录每子项耗时，定位拖慢整批的慢子项并为其单独设配额。

## 五、边界情形

边界之一是顺序副作用：若子项处理顺序影响结果（例如先读后写同一资源），尽力而为模型的并行执行会引入竞态，需要退化为串行或按资源分片串行。边界之二是部分失败与重试的放大效应：客户端只重试失败项时，服务器必须支持按子集调用，否则整批重试会重新执行成功项，对非幂等子项造成重复副作用，工具设计时应提供子集参数。边界之三是缓存交互：成功项被缓存后，失败重试批次中成功项来自缓存，错误项来自实时执行，两者的时间一致性不同，必要时在结果中标注数据时间戳。部分失败模型的价值在于诚实——不夸大失败也不掩盖失败，把裁决权交还调用方。
