# 15 后端存储部分写入对MCP返回语义的影响

> 摘要：本文讨论服务器后端（数据库、文件系统、搜索引擎）发生部分写入时，MCP层应如何选择返回语义：明确失败、明确成功、还是携带一致性元数据的成功，并给出写读一致性保障。

## 一、部分写入的形态

服务器工具的执行终点是后端存储，而存储的部分写入形态多样：数据库多语句事务中连接中断，前面的语句已自动提交（ autocommit模式或事务外语句），形成半成品状态；主从复制异步，写入主库成功但从库尚未追上，紧接着的读请求打到从库读到旧值；文件系统写一半进程崩溃，留下截断文件；搜索引擎与数据库双写，一侧成功一侧失败，索引与数据分叉；批量插入中部分行违反约束，整批语义取决于驱动配置。这些形态的共同点是存储内部状态与"成功或失败"的二值结论不匹配，而MCP协议要求服务器返回一个明确的结果。返回语义的选择错误会把存储层的含糊放大为业务层的灾难：明明半成品却报成功，调用方基于假数据继续；明明已落大部分却报失败，调用方重试造成大面积重复。

## 二、返回语义的决策规则

规则一：不确定即失败原则。当服务器无法确认写入完整生效时，返回isError为true并在元数据中标注uncertain，宁可让调用方走对账也不要伪造确定性。规则二：成功必须可验证。返回成功的前提是提交确认已到达（数据库的commit ack、文件fsync返回、双写的两侧确认或补偿登记完成），异步复制的场景下成功语义只能指主库视角，从库可见性另行说明。规则三：一致性元数据透明化。允许返回成功的场景中，附带写入水位（时间戳、日志位置、版本号），让后续读请求可以校验或等待水位到达，把"写后立读"的一致性选择权交给调用方。

## 三、双写与写读一致性参考

```python
async def dual_write(db, index, doc):
    db_tx = await db.begin()
    try:
        await db_tx.insert(doc)
        await db_tx.commit()               # 先提交数据库（真相源）
    except DbError:
        return Error("write failed", uncertain=False)
    try:
        await index.upsert(doc.id, doc)    # 再同步索引（可补偿）
    except IndexError:
        await enqueue_compensation("index_upsert", doc.id)
        # 仍返回成功：索引经补偿最终一致，元数据标注索引延迟
        return Ok(metadata={"index_consistent": False, "version": doc.ver})

async def read_with_watermark(query, min_version):
    row = await db.query(query)
    if row and row.ver >= min_version:
        return row
    await db.await_wal_position(min_version)   # 等待复制水位
    return await db.query(query)
```

该实现的取舍：数据库是真相源，索引失败不否定写入成功，但必须补偿并在元数据中暴露不一致；读路径支持按版本水位等待，写后立读不再依赖运气。若反过来先写索引后写数据库，索引成功而数据库失败时删除索引的补偿同样成立，但真相源选择要与业务查询的主路径一致。

## 四、存储边界一致性清单

- 明确每个工具的真相源存储，其他存储一律视为可补偿的视图。
- 事务边界覆盖全部关键语句，禁止事务外裸写后再"补一个事务"。
- 提交确认到达才可返回成功，异步复制场景在元数据中标注一致性水位。
- 双写一侧失败走补偿队列，补偿失败升级人工并暴露不一致指标。
- 文件写入显式fsync，截断文件在读取路径上有校验与自愈逻辑。
- 部分行失败的批量写入返回逐行成败明细，不掩盖为整体成败。
- 用故障注入验证：提交瞬间断连、fsync前掉电、复制延迟窗口，逐一核对返回语义。

## 五、边界情形

一个微妙边界是只读缓存的失效时序：写入成功但缓存未失效，紧随的读命中旧缓存，调用方误以为写入失败而重试；缓存失效应在提交事务内登记，读路径对刚写入的键有旁路机制。另一个边界是跨多个工具调用的复合写入：调用方在两个工具间自行组合事务，服务器无法提供跨调用事务，只能在文档中明确每个调用的一致性边界，避免调用方对原子性产生幻觉。存储部分写入的应对核心是把二值的返回语义扩展为带元数据的三态：确定成功、确定失败、成功但带一致性注记，让上层始终知道自己在和什么状态打交道。
