# 05 长任务进度上报与超时豁免机制

> 摘要：本文围绕MCP的progressToken进度通知机制，讲解长任务如何在总时长预算内争取宽限、豁免与硬上限的边界划分，以及进度造假与进度停摆的识别。

## 一、进度上报要解决的问题

MCP允许客户端在请求参数的元数据中携带progressToken，服务器在执行长任务期间以notifications/progress通知回传进度，字段包含progress当前值、total可选总量、progressToken回显标识。这一机制直接改变超时判定的语义：没有进度时，客户端只能对着一段沉默计时，长任务几乎必然撞上总时长上限；有了进度，客户端观察到的是一条持续向前推进的执行曲线，可以把"沉默超时"升级为"停滞超时"——只要进度在推进就继续等待，进度停摆超过阈值才判定死亡。这等价于把死循环与慢任务区分开的能力，是长任务工具从不可用到可用的分水岭。

## 二、豁免的边界：宽限不是无限

超时豁免容易被误解为只要进度在走就永远等下去，这是危险的。正确的模型是三层结构：基线预算按工具配置授予；进度推进可以在预算耗尽前申请有限次的宽限延长，每次延长幅度与最近一次进度推进的间隔挂钩；绝对硬上限始终存在，任何豁免不得越过。硬上限的存在理由是进度可以造假——服务器每五秒发一个递增数字并不代表真实工作在发生，有缺陷的实现甚至会在死循环里照常上报进度。因此豁免机制必须同时监控两个信号：进度的绝对推进量（防止原地踏步式上报）与推进速率的下限（防止龟速推进掩盖的假活）。

## 三、客户端豁免逻辑参考

```python
async def wait_with_progress(stream, token, budget):
    deadline = monotonic() + budget.hard_limit
    stall_limit = budget.stall_limit          # 停滞阈值，如90秒
    last_progress, last_advance = None, monotonic()
    while True:
        frame = await stream.next(deadline=deadline)
        if frame.is_final_result():
            return frame
        if frame.is_progress(token):
            if frame.progress != last_progress:      # 有真实推进
                last_progress, last_advance = frame.progress, monotonic()
            continue
        if monotonic() - last_advance > stall_limit: # 进度停摆
            raise StallTimeout(tool, last_progress)
```

这段代码体现了三个关键决策：最终结果与进度通知共用一个截止时钟，硬上限不被进度重置；进度值未变化的通知不刷新活性时间戳；停滞超时作为独立于硬上限的第二把刀，先于硬上限砍向假活任务。服务器侧的对应责任是诚实上报——total已知时提供总量、进度值单调、任务完成后停止发送进度，且进度通知必须携带正确的token以便客户端路由。

## 四、进度机制健康度清单

- 校验progressToken在请求与通知间严格一致，类型不得漂移。
- 监控进度推进速率分布，识别龟速任务并调整其预算或实现。
- 记录"进度到达百分之九十九后停滞"的案例，此类多为收尾阶段的锁等待或输出序列化问题。
- 验证服务器在任务失败与取消后停止进度通知，防止幽灵通知污染下个任务的判定。
- 对无total的进度流，客户端按推进计数而非百分比做停滞判定。
- 压测进度通知的量级，防止高频进度本身成为带宽与解析负担。

## 五、边界情形

一个反复出现的边界是进度粒度选择：粒度过粗会让合法任务在两个进度点之间被误判停滞，粒度过细则通知风暴抬高链路负担，工程上以停滞阈值的四分之一到二分之一为参考间隔。另一个边界是进度与取消的交互：客户端因停滞判定放弃并发送取消通知后，进度通知可能仍在途中，客户端应按token丢弃孤儿通知而不是抛路由错误。进度豁免机制的总原则可以概括为一句话：进度是延长信任的依据，不是取消监督的借口，硬上限与停滞阈值构成豁免机制不可谈判的地板。
