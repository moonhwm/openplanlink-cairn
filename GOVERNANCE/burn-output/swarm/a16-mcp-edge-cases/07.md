# 07 多跳MCP链路中的超时预算分配

> 摘要：本文讨论客户端、MCP网关与后端服务器组成的多跳调用链上超时预算如何逐层分配、截止时间如何传播，以及网关超时倒挂导致的连环失败问题。

## 一、链路超时的倒挂问题

生产环境中MCP调用经常不是两跳而是多跳：客户端到聚合网关，网关到工具服务器，工具服务器再到数据库或外部接口。每一段都有自己的超时配置，问题出在这些配置往往是各团队独立设置的。最典型的故障形态是倒挂：网关到客户端的总超时为十秒，而网关到后端服务器的超时为三十秒。后端在第十二秒成功返回，网关却在第十秒已经向客户端报超时，随后网关自己又收到了后端结果并将其丢弃——资源被消耗、结果被抛弃、客户端拿到失败，三方全输。倒挂的根因是各跳超时没有共同的上游视角，每一段都按自己的最坏情况设置，叠加后必然超过前端预算。

## 二、截止时间传播机制

解决倒挂的标准做法是传播截止时间而非各自计时。链路入口处确定一个绝对截止时刻，随请求逐跳传递；每一跳在开始工作前检查剩余时间，把剩余时间作为自己下游调用的超时上限；剩余时间不足时立即快速失败，不再启动注定无法按时完成的工作。

```python
async def gateway_handle(request):
    deadline = request.deadline          # 入口计算的绝对时刻
    remaining = deadline - monotonic()
    if remaining < MIN_USEFUL:           # 剩余太少，快速失败
        return error(code=-32001, msg="budget exhausted at gateway")
    upstream = pick_backend(request)
    # 下游超时 = 剩余预算 - 本跳保留的收尾时间
    result = await with_timeout(
        upstream.call(request.body, deadline=deadline),
        timeout=remaining - RESERVE_SERIALIZE)
    return serialize(result)             # 序列化消耗保留时间
```

这段实现包含三个不可省略的细节：序列化与传输回程要保留时间余量，否则干完活却来不及把结果送回去；剩余预算低于最小可用阈值时快速失败，错误信息里带budget exhausted字样与剩余毫秒数，让上游能区分"预算耗尽"与"下游故障"；截止时刻必须用同一时钟语义（单调时钟或经校正的墙钟），跨机器传播墙钟时要吸收时钟偏差，通常做法是传播相对剩余量而非绝对时刻。

## 三、各级角色的预算责任

客户端负责设定总预算并尊重结果：预算耗尽类错误不应重试，重试只会再次耗尽预算，除非整体放宽预算。网关负责再分配：它知道后端的延迟分布，可以把剩余预算按各段的历史分位数切分，而不是平均主义；网关还负责熔断已经持续超时的下游，把预算留给其他路径。后端服务器负责诚实：执行前检查剩余时间，长任务在剩余不足时主动拒绝而不是开跑后超时；已经注定超时的任务提前终止，把节省的资源转化为整条链路的可用性。三个角色共同的纪律是：任何一跳的本地超时不得大于入口分给它的剩余预算，这条规则静态检查配置即可校验。

## 四、链路预算治理清单

- 建立链路登记表：记录每条调用路径上各跳的超时配置，自动检测倒挂并告警。
- 请求元数据中统一携带截止时间或剩余预算字段，跨团队标准化格式。
- 错误信息区分超时类型：预算耗尽、下游超时、下游快速失败，便于归因。
- 网关按后端分位延迟动态调整分配，避免静态配置随负载漂移失真。
- 对预算耗尽率设定告警阈值，持续耗尽说明预算与真实耗时结构不匹配。
- 定期用链路追踪核对每跳实际耗时与分配预算的偏差。

## 五、边界情形

一个隐蔽边界是重试与预算的交互：客户端重试时新的总预算应当重新授予，但网关必须识别这是重试（通过幂等键或重试头），避免旧任务的在途结果与新任务交叉。另一个边界是网关聚合多个后端的扇出调用：并行扇出应取最大后端预算，串行扇出应把预算分段授予，混淆两者会造成某些分叉总是被掐断。链路预算分配的本质是把"快"变成链路的集体契约，任何一跳的私心配置都会在边界处以倒挂的形式暴露。
