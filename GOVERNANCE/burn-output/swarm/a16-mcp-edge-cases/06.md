# 06 超时重试策略：幂等性判定、退避与抖动、重试预算

> 摘要：本文给出超时后重试的完整决策框架：先判定幂等性决定能否重试，再用指数退避加抖动控制节奏，最后用重试预算约束总量，防止重试放大故障。

## 一、重试的第一道闸门：幂等性判定

超时之后能否重试，不取决于耐心而取决于幂等性。调用分为三类：天然幂等的纯读操作，超时后可无条件重试；设计幂等的写操作，服务器通过幂等键去重，重试安全；非幂等的写操作，例如不带唯一约束的创建类动作，盲目重试会导致重复副作用，必须先对账确认前次未生效。判定依据应当来自工具的元数据与本地策略表，而不是调用处临时拍脑袋。工程实践要求把幂等等级写进工具注册信息，让客户端的重试器可以自动化决策；同时警惕"看似幂等实则不然"的陷阱，例如自增计数、追加写日志、外部支付接口，这些操作重试一次就多一份效果，属于典型的伪幂等。

## 二、退避与抖动：控制重试的节奏

确定可重试之后，节奏决定成败。固定间隔立即重试会把超时瞬间积累的失败调用在同一时刻砸向刚恢复的服务器，形成重试风暴，其流量可能数倍于正常水平，把一次短暂抖动放大成一次真实宕机。指数退避让间隔随失败次数翻倍增长，给下游喘息窗口；抖动则在退避值上叠加随机扰动，把大量客户端的重试时刻打散在时间轴上。两者组合的常用公式为间隔等于基数乘以二的重试次幂，再乘以零点五到一点五之间的随机系数，并设置间隔上限。

```python
def backoff_with_jitter(attempt, base=0.5, cap=30.0):
    raw = min(base * (2 ** attempt), cap)
    return raw * uniform(0.5, 1.5)

async def retry_call(call, policy):
    for attempt in range(policy.max_attempts):
        try:
            return await call()
        except TimeoutElapsed if policy.idempotent else NoRetry:
            if attempt == policy.max_attempts - 1:
                raise
            await sleep(backoff_with_jitter(attempt))
```

注意异常分流：非幂等调用抛出的超时直接穿透不重试，幂等调用才进入退避循环。退避只对超时与瞬时错误生效，对协议层的确定性错误（方法不存在、参数非法、权限拒绝）重试毫无意义，只会浪费预算并污染日志。

## 三、重试预算：约束总量

单次调用的重试上限只约束了纵向深度，横向总量同样需要约束。重试预算的思路是把重试视为一种共享稀缺资源：单位时间内全部请求中允许重试的比例设上限，例如百分之二十，预算耗尽时即使单请求的尝试次数未满也不再重试，让失败快速浮出。没有预算约束的系统在最坏时刻表现最差——下游过载导致超时，超时触发重试，重试加重过载，形成正反馈崩溃，这正是重试风暴的经典形态。预算的实现可以简单到每秒重置的计数器，也可以基于成功率的自适应令牌桶，关键在于存在一个全局视角敢于说"不"。

## 四、重试策略落地清单

- 为每个工具标注幂等等级：只读、幂等写、非幂等写，重试器按等级分流。
- 非幂等写超时后强制走对账流程，裁决前禁止重试。
- 退避参数（基数、倍率、上限、抖动系数）集中配置并可热更新。
- 区分可重试与不可重试错误码，后者直接失败不上预算。
- 部署重试预算或等效的全局阀门，监控重试流量占比。
- 观测指标至少包含：每请求尝试次数分布、重试触发原因分布、重试成功率（区分真正恢复与碰运气）。

## 五、边界情形

重试与请求体大小存在交互：携带大参数的调用重试成本高，重试次数应更保守甚至只重试一次。重试还会与服务器侧的慢任务叠加——前一次请求可能仍在服务器执行，重试造成同一任务并发两份，幂等键在这里同时承担去重与防并发的职责。另一个边界是用户取消与自动重试的冲突：用户主动放弃后，重试循环必须立即终止，不能出现用户已看到失败提示、后台还在静默重试并最终成功的时序错乱。重试策略的成熟度标志不是重试了多少次，而是每一次重试都经过了幂等判定、节奏控制与预算约束三道闸门。
