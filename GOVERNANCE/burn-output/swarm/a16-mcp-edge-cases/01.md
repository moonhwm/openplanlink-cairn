# 01 MCP客户端请求超时的分类与超时梯度设计

> 摘要：本文将MCP客户端超时拆解为连接超时、首字节超时与总时长超时三个梯度，给出参数基线、参考实现与调优清单，解决一刀切超时造成的误杀与挂死两类事故。

## 一、问题背景：一刀切超时的两类事故

MCP客户端向服务器发起JSON-RPC请求后，等待期内的每一次延迟都由不同环节贡献：TCP握手、TLS协商、initialize握手、服务器内部排队、工具实际执行、结果序列化与网络回传。若客户端只配置一个总的请求超时，例如统一十秒，会同时触发两类边界事故。第一类是误杀：某些合法的重型工具（代码库全量索引、大规模表格分析）本身就需要数十秒，统一超时会在任务即将完成时将其掐断，用户看到的是报错，而服务器侧的副作用已经发生，形成状态不一致。第二类是挂死：连接建立失败或服务器进程僵死时，请求根本不会产生任何字节流，总超时在此之前形同虚设，客户端连接池被长期占用，最终演变为资源耗尽。因此，成熟的MCP客户端必须把"超时"从一个数字拆解为一组梯度，每个梯度只对它所覆盖的故障模式负责，互相之间不越界兜底。

## 二、三层超时模型与参数基线

第一层是连接超时，覆盖TCP与TLS建立阶段，责任是快速识别不可达的对端，基线建议两到五秒，局域网内可下调到一秒。第二层是首字节超时，从请求写出到收到第一个响应字节或任何协议帧（包括进度通知）为止，责任是识别"连得上但不干活"的僵死服务器，基线建议十到三十秒。第三层是总时长超时，覆盖完整响应到达的过程，责任是限制单个请求的最坏等待，取值应当按工具粒度配置而非全局统一，轻量工具五秒、中量六十秒、重量级配合进度上报放宽到分钟级。三层之间必须满足偏序关系：连接超时小于首字节超时，首字节超时小于或等于总时长超时，否则低层梯度永远不会先于高层触发，梯度设计失去意义。

## 三、参考实现

以下伪代码展示三梯度的组织方式，重点在于三个定时器彼此独立、任一触发即取消整体等待：

```python
async def call_with_tiers(transport, request, cfg):
    conn = await wait_for(transport.connect(), timeout=cfg.connect_timeout)
    writer = conn.send_request(request)
    first = await wait_for(writer.first_frame(), timeout=cfg.first_byte_timeout)
    # 收到首帧后，剩余等待挂到总时长预算上
    deadline = cfg.total_budget - cfg.first_byte_timeout
    result = await wait_for(writer.final_result(), timeout=deadline)
    return result
```

工程上有两个细节容易遗漏。其一，首字节判定应把进度通知也算作活性信号，否则开启进度上报的长任务会在第二层被误杀。其二，超时触发后的清理动作必须显式发出取消通知（notifications/cancelled），并向传输层请求断开或复位的指令，不能只抛异常了事，否则服务器仍会执行完整个任务，客户端却已经不再监听结果。

## 四、调优与观测清单

- 按工具名称维护差异化的总时长配置，禁止全局唯一超时。
- 为每层超时单独打点，输出触发次数与分位数延迟，验证梯度配置是否匹配真实负载。
- 连接超时触发率异常升高时优先排查网络与DNS，而不是放大超时值。
- 首字节超时触发率高说明服务器内部排队严重，应转向服务器容量问题而非客户端参数问题。
- 每次梯度调整后运行断链、慢响应、快失败三类注入用例，确认各层各司其职。
- 记录"超时后服务器实际完成"的比例，作为状态一致性风险的核心指标。

## 五、边界情形与常见误区

实践中最常见的误区是用总时长梯度去兜底连接故障，结果连接不可达时客户端要等满整个预算才报错，用户体感极差。另一个误区是把进度上报通道与响应通道混为一谈，在流式传输中只要字节在流动就无限续期总时长，导致真正的死循环任务永远不被切断；正确做法是总时长为硬上限，进度上报只用于调大预算的初始设定，不做无限豁免。还有一类隐蔽错误是梯度数值之间出现等于或倒挂，例如首字节超时大于总预算，此时总预算先爆，首字节层永远沉默，排查时应先校验偏序关系再分析业务原因。梯度超时的本质是用小成本换确定性：每一层触发都指向一个明确的故障域，使超时从模糊的"等不及"变成可定位的信号。
