# 11 采样部分失败：模型拒绝、权限拒绝与降级路径

> 摘要：本文分析MCP服务器反向请求客户端采样（sampling/createMessage）时可能遭遇的四类拒绝与超时，给出服务器侧的降级链设计与协议层注意事项。

## 一、反向采样的失败面

MCP的独特之处在于服务器可以反向请求客户端：通过sampling/createMessage让宿主的大模型代为生成内容。这个反向通道的失败面与正向调用不同，控制权在客户端手里。服务器发起采样后至少面临五种不利结局：客户端能力协商中未声明sampling能力，请求在协议层就不成立；用户在客户端的授权界面上拒绝采样（consent denied）；客户端模型策略性拒绝，例如内容触发安全过滤；模型执行出错或返回空内容；客户端长时间不响应，服务器挂在等待中。每一种都需要服务器有明确的处理路径，否则轻则请求悬挂、重则服务器死锁在自己的状态机里。

## 二、协议层的两类拒绝

第一类是能力缺失。initialize握手时客户端在capabilities中声明是否支持sampling；未声明时服务器根本不应发起采样请求，发出去的请求将得到method not found错误。服务器必须在握手后缓存能力表，运行期每次发起反向请求前检查，缺失时直接走无采样路径而不是试探。第二类是用户拒绝。客户端对采样请求弹出授权框，用户拒绝后客户端返回错误，错误信息应包含被拒语义。服务器必须把用户拒绝与系统错误区分开：用户拒绝不可重试——重试等于反复骚扰用户弹窗；系统错误可以有限重试。混淆两者的服务器会出现"重试三次弹三次窗"的糟糕体验，或者反过来把可恢复错误当成终局。

## 三、服务器侧降级链设计

```python
async def generate_with_fallback(task):
    # 降级链：客户端采样 -> 本地小模型 -> 模板生成
    if self.client_caps.get("sampling"):
        try:
            ans = await with_timeout(
                self.client.create_message(task.sampling_spec()),
                timeout=30.0)
            if ans.stop_reason == "end_turn" and ans.text:
                return ans.text
        except UserDenied:
            task.mark("sampling_denied_by_user")   # 终局，不再打扰
        except (TimeoutElapsed, ModelRefused):
            task.mark("sampling_degraded")
    if self.local_model:
        return await self.local_model.run(task.prompt())
    return task.render_template()                  # 确定性兜底
```

降级链的设计原则：采样是增强而非依赖，任务的主流程不因采样失败而中断；每级降级打上标记并进入结果元数据，让上层知道内容来自哪一级；模板兜底保证最终一定有输出，代价是质量而非可用性；本地模型如果作为降级级存在，其推理耗时必须有自己的预算，不能把等待从一个失败面转移到另一个。

## 四、采样失败处理清单

- 握手后缓存客户端能力，发起前检查sampling声明，杜绝明知不可为而为之。
- 错误分类至少四分：用户拒绝、模型拒绝、超时、协议错误，各自独立计数。
- 用户拒绝路径禁止自动重试，同一会话内限制采样频率防止弹窗轰炸。
- 采样请求带明确超时，等待期间不阻塞服务器其他请求的处理。
- 降级标记写入结果元数据，供质量归因与审计。
- 对stop_reason异常（长度截断、内容过滤）按不完整输出处理，不静默采信。

## 五、边界情形

一个协议边界是采样嵌套：客户端处理采样请求的过程中又触发了对服务器的工具调用，形成请求交叉。规范上允许但实现上必须保证请求id空间隔离与可重入处理，否则响应错位。另一个边界是双向流控：服务器并发发起大量采样请求会同时占用客户端的模型配额与用户的授权注意力，服务器应对在途采样数设上限。安全边界同样重要：采样规范要求客户端把服务器发起的采样展示给用户确认，服务器不得在提示词中夹带诱导用户批准的措辞，也不得通过采样通道变相外传用户未授权的数据。采样部分失败的处理水平，决定了服务器在宿主环境受限时的生存能力。
