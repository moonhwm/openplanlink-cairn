# 16 部分失败的错误聚合与返回格式设计

> 摘要：本文给出服务器把多个子错误的聚合、压缩与结构化返回的完整方案：错误分级、消息模板、稳定错误码区间、脱敏规则与面向LLM消费方的可读性优化。

## 一、错误聚合的三个矛盾

一次MCP调用内部产生多个子错误时，返回格式设计面临三个矛盾。矛盾一是完整与膨胀：逐条返回全部错误最有信息量，但批量操作千条全错的响应体积失控，LLM消费方的上下文窗口也会被淹没。矛盾二是机器与人类可读：JSON-RPC的error对象以code与message为核心，结构化细节靠data字段，纯文本消息对LLM友好但对程序处理不友好，纯结构化反之。矛盾三是内部与外部视角：开发者需要堆栈、SQL、内部路径定位问题，而外部消费方拿到这些信息构成安全泄漏。聚合格式的目标是在三个矛盾中找到工程折中：分级压缩、双层表达、严格脱敏。

## 二、分级压缩与双层表达

分级：错误按类聚合并计数，同类保留首例与代表性样例，附带总数。例如千条记录中九百条违反同一约束，聚合为一个错误项加count字段与一条样例detail。首错优先：若存在系统性根因（连接失败、鉴权失败），后续错误多为级联，返回根因并标注级联范围比罗列全部更有诊断价值。双层表达：外层error.code与message保持简短稳定，供程序分支；data里放结构化明细数组，每项含scope（定位到子项或步骤）、category（错误类别）、retryable（是否可重试）、hint（修复建议）。

```json
{
  "jsonrpc": "2.0", "id": 42,
  "error": {
    "code": -32010,
    "message": "batch partially failed: 12 of 100 items errored",
    "data": {
      "ok": 88, "failed": 12,
      "categories": [
        { "category": "constraint_violation", "count": 11,
          "sample": { "scope": "items[37].email", "retryable": false,
                      "hint": "duplicate value, use upsert mode" } },
        { "category": "upstream_timeout", "count": 1,
          "sample": { "scope": "items[64]", "retryable": true,
                      "hint": "transient, retry this subset only" } }
      ]
    }
  }
}
```

## 三、错误码与脱敏规则

错误码使用服务器自定义区间（规范预留负三百二零零零以下的自定义空间），并建立码表治理：每个码有唯一含义、稳定不复用、文档公开。禁止把子错误塞进message长文本里让调用方解析自然语言。脱敏规则必须机械化执行：message与hint中不允许出现内部IP、文件路径、SQL语句、堆栈、账号标识；样例中的业务值按字段敏感级掩码；根因翻译表把内部异常类映射为外部类别名。审核上，任何新增错误路径都要过一遍脱敏检查清单，防止调试信息随版本迭代渗入对外消息。

## 四、错误聚合落地清单

- 建立错误码表：码、类别、可重试性、对外消息模板四列，纳入版本管理。
- 聚合器实现同类别计数、首例保留、级联折叠三个原语。
- data明细条目强制包含scope、category、retryable、hint四字段。
- 响应体积上限：聚合后明细超限时截断并附total与continuation指引。
- message长度约束在一百二十字符内，长解释移入hint。
- 脱敏过滤器作为输出管线最后一道强制环节，白名单字段制。
- 为高频错误类别建立消费方文档：含义、常见触发、建议动作。

## 五、面向LLM消费方的特殊考量

MCP的错误最终常由大模型消费并转述给用户或决定下一步动作，格式要照顾模型的理解方式：hint给出可执行建议（重试哪个子集、改哪个参数），比抽象错误名更能引导正确恢复；类别名使用自解释词汇；可重试标记明确，避免模型对不可重试错误发起无意义重试。同时要防住反向风险：错误消息进入模型上下文后可能被复述给用户，脱敏因此更加重要；错误文本中不嵌入指令式内容，防止提示注入经由错误通道传播。错误聚合格式是服务器与调用方之间的错误契约，契约清晰，部分失败才可能被系统性消化而不是逐案救火。
