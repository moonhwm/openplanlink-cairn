# 20 重入与幂等键：请求ID去重与重复响应检测

> 摘要：本文讲解JSON-RPC请求ID与业务幂等键在去重中的不同角色：请求ID判定协议层重复、幂等键判定执行层重复，给出双键协同的去重缓存实现与过期治理。

## 一、两个键，两种去重

重入与重试环境下，同一逻辑操作可能以多个请求到达服务器，去重需要两个层面的键。第一个是JSON-RPC的请求id：它是协议层的消息标识，用于把响应配回请求；规范要求客户端对同一id的请求等待响应后才发下一个同id请求，但重发场景（超时重试、断连重放）会让服务器看到同一id两次。第二个是业务幂等键：随工具参数携带的执行标识，服务器用它识别"这是否是同一逻辑操作的又一次投递"。两者职责不同：id重复解决"响应怎么配对与是否重复回送"，幂等键重复解决"是否重复执行"。只依赖id去重的服务器，在客户端换id重试（很多客户端重试会生成新id）时失效；只依赖幂等键而不处理id，响应配对会错乱。健壮的服务器两者都管。

## 二、去重的状态与生命周期

去重需要缓存"已见键到执行结果"的映射，生命周期治理是核心问题。窗口太短，客户端在网络慢路径上的迟到重发穿透缓存造成双执行；窗口太长，缓存膨胀消耗内存。工程基线是窗口覆盖客户端最大重试跨度再加余量，例如二十四小时，并以执行结果的持久性决定存储介质：结果可从业务系统反查的，缓存只存"键已提交"的标记；结果不可反查的，缓存需存完整响应供回放。键的语义必须与调用方契约化：幂等键相同代表调用方声明这是同一操作，参数不一致时服务器应拒绝（键冲突检测）而不是默认后到覆盖，否则键会被误用为更新通道。

## 三、双键协同实现参考

```python
class DedupGate:
    def __init__(self, store, ttl=86400):
        self.store = store                  # 支持原子占位的KV存储
        self.ttl = ttl

    async def admit(self, request):
        rid = request.id                    # JSON-RPC id
        idem = request.params.get("_idem_key")
        if rid is not None:
            cached = await self.store.get(f"rid:{rid}")
            if cached:
                return Replay(cached.response)      # 协议层重复：回放响应
        if idem:
            slot = await self.store.reserve(f"idem:{idem}", ttl=self.ttl)
            if slot.state == "occupied":
                if slot.finished:
                    return Replay(slot.response)    # 执行层重复：回放结果
                return Conflict("execution in flight, retry later")
            # occupied但未完成：同键并发，拒绝而非排队执行
        return Proceed(record={"rid": rid, "idem": idem})

    async def settle(self, admission, response):
        if admission.record["rid"] is not None:
            await self.store.put(f"rid:{admission.record['rid']}",
                                 response, ttl=600)   # id缓存窗口可较短
        if admission.record["idem"]:
            await self.store.finish(f"idem:{admission.record['idem']}",
                                    response)
```

细节：id缓存与幂等键缓存分离，前者窗口短（覆盖响应乱序重放），后者窗口长（覆盖执行重复）；同键在途时的并发请求返回冲突而不是排队，排队会让重试风暴演变为执行风暴；回放的响应保持与原响应字节级一致或语义一致，客户端无法区分首送与回放。

## 四、去重治理清单

- 全部写操作工具强制接收幂等键，无键调用直接拒绝或降级为不可重试。
- 幂等键冲突检测：同键不同参数返回冲突错误，防键被挪用。
- 去重存储的容量与过期策略纳入容量规划，防止内存型缓存无界增长。
- 回放命中率、冲突率、在途并发拒绝率三个指标独立观测。
- 客户端重试时保持幂等键不变、允许id变化的行为写入接口契约文档。
- 去重存储故障时的降级顺序：只读工具跳过去重、写工具快速失败。

## 五、边界情形

一个边界是回放与新执行的裁决竞态：缓存过期边缘，一个请求触发回放、另一个同时触发新执行，原子占位（reserve的原子性）是唯一防线，实现上必须依赖存储的原子原语而不是先查后写的两步动作。另一个边界是跨节点去重：集群中两个节点同时收到同键请求，本地缓存各自为政，去重必须落在共享存储或按键路由的节点上，这也是幂等体系通常外置存储的根本原因。id与幂等键的双键体系看似冗余，实际是分别封住协议层与执行层两条重复通路，缺一不可。
