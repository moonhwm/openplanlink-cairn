# 18 有状态服务器的状态机重入安全：请求交叉与状态撕裂

> 摘要：本文讨论MCP服务器在会话状态机层面遭遇请求交叉时的状态撕裂问题：非法状态转换、半完成状态、响应错位，给出显式状态机建模与交叉防护方案。

## 一、状态机视角下的服务器

许多MCP服务器不是无状态函数，而是有生命周期的状态机：initialize前的握手态、就绪态、订阅管理态、长任务执行态、关闭中状态。会话状态决定了哪些请求合法：握手未完成时只允许initialize相关消息；关闭流程启动后应拒绝新业务请求。请求交叉打破这个秩序：客户端因超时重发initialize，而服务器已进入就绪态；订阅刷新请求与取消订阅并发到达，前者的回调写入已被后者删除的登记项；长任务执行中收到新的互斥操作（如重置工作区）。状态撕裂的表现包括：会话卡在中间态不再接受任何请求、内部登记表与实际通道状态分叉、对同一请求回送两次响应或零次响应。

## 二、三类撕裂的机理

第一类是非法转换撕裂：状态机实现为散落在各处理函数里的标志位修改，某个路径遗漏了转换或转换条件判断不完整，并发消息让标志位组合出不该存在的状态。第二类是半完成撕裂：状态迁移涉及多个结构（登记表、订阅通道、缓存），迁移过程被并发请求打断，一半更新一半旧值，后续请求基于撕裂视图决策。第三类是响应错位：请求处理中状态被其他请求改变，处理器在收尾时引用了已失效的会话对象，把响应发往已关闭的通道，或把新请求的响应误配给旧请求id。三类撕裂的根源一致：状态变迁没有被建模为原子转换，而是散装的副作用序列。

## 三、显式状态机与防护参考

```python
class SessionMachine:
    TRANSITIONS = {
        "handshaking": {"initialize": "ready", "disconnect": "closed"},
        "ready":       {"begin_task": "running", "close": "closing",
                         "disconnect": "closed"},
        "running":     {"finish_task": "ready", "abort_task": "ready",
                         "close": "closing", "disconnect": "closed"},
        "closing":     {"cleanup_done": "closed"},
        "closed":      {},
    }

    async def accept(self, event, payload):
        async with self.lock:                    # 转换原子化
            nxt = self.TRANSITIONS.get(self.state, {}).get(event)
            if nxt is None:
                if self.state == "closed":
                    return Drop("session closed")   # 静默丢弃或按需报错
                return Error(code=-32002,
                             msg=f"illegal event {event} in {self.state}")
            self.state = nxt                      # 先迁状态再执行副作用
            try:
                await self.effects[nxt](payload)  # 副作用集中于迁移函数
            except Exception:
                await self.rollback(self.state, nxt)
                raise
```

要点：转换表集中声明，非法事件得到结构化拒绝而不是未定义行为；状态迁移与副作用在锁内原子完成，效果函数要么可回滚要么幂等可重放；closed状态对后续事件的策略显式声明（丢弃或报错），不留默认路径。请求级别的交叉防护交给会话层之上的每请求队列：同一会话的请求按序处理或按冲突键分组并行，从调度上消除大部分交叉。

## 四、状态机安全清单

- 把会话生命周期画成状态图并代码化为转换表，禁止散装标志位。
- 每个状态对每个事件的响应（转换、拒绝、丢弃）在表内穷举。
- 迁移副作用集中且可回滚，回滚路径纳入测试。
- 同会话请求按序或按键分组调度，跨会话共享资源另行加锁。
- 双发initialize、关闭中发请求、任务中重置等交叉场景进入用例库。
- 每会话维护已响应请求id的短期记忆，重复id回放缓存响应防双执行。
- 状态分布直方图接入监控，异常态滞留时间告警。

## 五、边界情形

一个现实边界是协议允许initialize被重发（客户端重试握手），状态机需把就绪态收到initialize定义为幂等重放而不是非法事件，这提示转换表的"非法"判定要区分协议明确行为与实现未定义行为。另一个边界是关闭的竞态：cleanup执行中新请求到达，策略应为入队等待cleanup完成后统一拒绝，而不是在cleanup中间插入处理。状态机重入安全的回报是把"偶发诡异行为"变成"可枚举的拒绝与告警"，问题空间从无穷偶发收敛到有限转换。
