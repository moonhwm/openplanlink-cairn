# 01 · A2A协议的定位与核心概念

> 所属主题：A2A×MCP双栈互操作——工具连接与智能体互操作的分工和组合模式（子题目 01/48）

## 一、问题域：智能体之间的互操作

A2A（Agent-to-Agent）协议要解决的不是"模型如何调用工具"，而是"一个智能体如何与另一个由不同厂商、不同框架、不同模型驱动的智能体协作"。当智能体从单体走向多体，跨组织边界的能力复用就出现了协议层面的空缺：发送方不知道对方能做什么、如何认证、任务进行到哪一步、结果以什么形态返回。A2A把这些约定标准化，使智能体之间可以像微服务之间一样通过公开契约对话，而不需要共享内存、共享代码或共享运行时。

它的三个前提假设值得强调：第一，参与方是对等的主体，彼此不暴露内部思维链与提示词，只交换任务级消息；第二，任务可能是长时异步的，协议必须内建状态机而不是假设一次请求一次响应；第三，内容形态多样，文本、结构化数据、文件都要有一等公民的表达。这三点决定了A2A的所有后续设计。

## 二、核心概念清单

A2A的抽象层由以下对象构成，理解它们是理解双栈分工的基础：

- **AgentCard**：智能体的自描述文档，托管在 `/.well-known/agent-card.json`，包含名称、描述、能力（skills）、端点、认证要求、偏好传输方式。
- **Task**：协作的基本单位，具有唯一标识与完整状态机（submitted、working、input-required、completed、failed、canceled）。
- **Message**：任务内的一轮对话轮次，区分 user 与 agent 角色，承载 ContentPart 列表。
- **Artifact**：任务产出的持久结果，一个任务可产生多个Artifact，供下游消费。
- **ContentPart**：内容的分型单元，text、file、data 三类，可组合出现。
- **Push Notification**：长时任务完成时的回调机制，使客户端不必轮询。

## 三、最小可读的AgentCard示例

下面是一份裁剪后的AgentCard，展示了能力声明与传输偏好如何落地：

```json
{
  "name": "行程规划智能体",
  "description": "根据预算与时间约束生成多城市行程草案",
  "url": "https://planner.example.internal/a2a",
  "version": "1.2.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": true,
    "stateTransitionHistory": false
  },
  "defaultInputModes": ["text/plain", "application/json"],
  "defaultOutputModes": ["application/json", "text/plain"],
  "skills": [
    {
      "id": "itinerary.draft",
      "name": "行程草案生成",
      "description": "输入约束条件，输出逐日行程的JSON草案",
      "tags": ["travel", "planning"]
    }
  ],
  "security": ["bearerAuth"],
  "preferredTransport": "JSONRPC"
}
```

注意 skills 只有标识与人类可读描述，没有参数级JSON Schema——这是与MCP工具定义最显性的粒度差，后续章节会展开。

## 四、小结

A2A把"智能体当黑箱对等方"作为第一原则，用AgentCard解决发现、用Task状态机解决异步、用ContentPart解决多模态。它与MCP处于不同的问题层：前者连接主体，后者连接能力。掌握这两个协议的边界，是设计双栈系统的第一步。
