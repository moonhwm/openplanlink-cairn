# 08 · 生命周期对照：MCP会话与A2A任务状态机

> 所属主题：A2A×MCP双栈互操作——工具连接与智能体互操作的分工和组合模式（子题目 08/48）

## 一、MCP会话：连接级生命周期

MCP的生命周期绑定在连接上：`initialize` 握手（交换版本与能力）→ 正常工作（请求/通知往来）→ `shutdown` 或连接断开。会话内没有业务状态机——一次 `tools/call` 从发起到返回即是全部历史。需要跨调用保持状态的场景（如打开的游标），要么靠服务器侧按会话ID自持，要么把状态显式编码进后续调用参数。

这种轻量模型换来的是极高的可组合性：任何崩溃都可容忍，客户端重建连接即可续命；但也意味着"进行中的工作"无法被第三方观察，外层只能靠进度通知感知体温。

## 二、A2A任务：业务级状态机

A2A把任务定义为一等实体，状态机如下：

```text
submitted --> working --> completed
                |  ^       |
                v  |       +--> failed
         input-required|
                |       +--> canceled
                +--(补充输入)--> working
```

- **submitted**：任务已受理，尚未开始执行。
- **working**：执行中，可伴随status-update流事件。
- **input-required**：需要委托方补充信息，任务挂起等待。
- **completed / failed / canceled**：三个终态，completed附带Artifact产出。

任务对象持久存在，客户端可以随时以 `tasks/get` 幂等地查询快照，或以 `tasks/get` 加历史参数取回状态变迁序列。这使长时协作具备了崩溃恢复与旁观审计的基础。

## 三、桥接时的状态映射规则

当编排器用MCP工具模拟长任务、或用A2A任务承载工具化需求时，需要一张显式映射表：

1. `tools/call` 发出 → 创建A2A任务，进入submitted。
2. 首个进度通知 → 状态跃迁为working（只能前进，不能倒退）。
3. 工具返回isError=true → 任务终态failed，错误细节写入任务描述。
4. 工具正常返回 → completed，返回值包装为Artifact（data类型）。
5. 客户端发 `notifications/cancelled` → 映射为 `tasks/cancel`，等待远端确认终态。
6. input-required在MCP侧无对等物，除非宿主实现elicitation面向最终用户——桥接层应把它降级为failed并附"需人工输入"原因，而不是静默挂死。

```python
def tool_result_to_task_state(result: dict) -> str:
    if result.get("isError"):
        return "failed"
    if result.get("structuredContent", {}).get("pendingInput"):
        return "input-required"   # 仅当宿主支持elicitation时保留
    return "completed"
```

## 四、超时与恢复策略清单

- MCP侧：为每次调用设置与工具性质匹配的截止时间，超时后必须假定操作可能已生效，重试前先查询副作用。
- A2A侧：为任务设置业务级SLA，超时先用 `tasks/get` 对账再决定取消或续等。
- 桥接层：任何把"工具超时"直接翻译成"任务failed"的实现都要复查——真实状态可能仍是working。
- 恢复：编排器重启后应按任务ID重放查询，而不是重新提交造成重复副作用。

## 五、小结

会话与任务是两种时间尺度的生命周期：前者关心连接的健康，后者关心业务的进展。双栈系统的稳健性很大程度上取决于桥接层对状态映射的诚实程度——宁可保守地多查询一次，也不要凭空编造状态。
