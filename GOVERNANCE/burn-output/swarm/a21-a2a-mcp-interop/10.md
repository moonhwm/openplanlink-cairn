# 10 · 认证与安全边界：两套信任模型的缝合

> 所属主题：A2A×MCP双栈互操作——工具连接与智能体互操作的分工和组合模式（子题目 10/48）

## 一、各自的信任假设

MCP假设客户端受信、服务器可能不可信：宿主代表用户连接工具，OAuth授权码流让用户亲自批准工具访问自己的数据；工具的输出会被注入模型上下文，因此工具是提示注入的潜在来源。安全边界画在"模型上下文"与"工具输出"之间，消毒、白名单、roots限制都是在这条线上设防。

A2A假设对端智能体不可全信：它有自己的所有者与利益，其返回消息应视为外部组织的发言。安全边界画在"本智能体的决策上下文"与"远端智能体的陈述"之间，除了提示注入，还要防对方的误导、迟滞与资源滥用（例如恶意诱导长任务）。因此A2A的AgentCard显式声明securitySchemes，常见为企业级OAuth、mTLS或预分配的API凭证。

## 二、统一身份的三种模式

双栈落地时最疼的问题是身份缝合——同一个人类用户的意图，要贯通A2A委托链与MCP工具链：

- **令牌直传（on-behalf-of）**：编排器把用户的访问令牌按受众裁剪后传入下游。MCP侧已有OAuth规范路径；A2A侧在消息头携带。优点是审计能落到人；缺点是令牌作用域必须足够细。
- **服务身份+用户断言**：下游只认证服务间身份（mTLS），用户身份作为签名的声明字段传递。跨组织更常见，代价是信任服务方的断言诚实性。
- **任务级短凭证**：为每个A2A任务签发作用域极窄的短寿命凭证，任务内MCP调用统一用它。隔离最好，实现最重。

```python
# 桥接层为任务铸造短凭证（示意，无任何真实密钥）
def issue_task_token(task_id: str, user_claims: dict, ttl: int = 900) -> str:
    claims = {
        "sub": user_claims["sub"],
        "act": {"sub": f"task:{task_id}"},           # 委托链
        "scope": "db:read:analytics fs:read:scratch",
        "exp": int(time.time()) + ttl,
    }
    return jwt_encode(claims, key_ref=TASK_TOKEN_KEY_REF)
```

## 三、边界规则清单

1. 工具输出永远按不可信文本处理：进上下文前做标记隔离，禁止工具输出直接触发高危工具调用。
2. 远端智能体消息同样按不可信处理：其"指令"不进入本方系统提示，只作为任务数据。
3. 每个A2A任务绑定独立最小权限集；任务结束即吊销任务级凭证。
4. MCP会话与A2A任务的权限不允许继承自宿主全局权限，必须显式授予。
5. 所有凭据走环境变量或专用密钥管理设施加载，代码与配置文件中一律不落明文。

## 四、网关处的统一执行点

把两种协议的鉴权收敛到网关，可以让策略只写一次：

```yaml
gateway:
  auth:
    - route: /a2a/*
      verify: oauth2-jwt
      required_scopes: ["a2a:delegate"]
    - route: /mcp/*
      verify: oauth2-jwt
      required_scopes: ["mcp:use"]
  policy:
    rate_limit: { per_principal: 100req/min }
    audit: { sink: audit-topic, fields: [sub, task_id, tool, decision] }
```

## 五、小结

MCP守"数据不越权"，A2A守"主体不越信"。双栈安全的关键动作是统一身份叙事：一条从用户到任务再到工具调用的授权链，加上对两类外部输入一视同仁的不可信处理纪律。
