# 11 · 多智能体编排中MCP网关的位置

> 所属主题：A2A×MCP双栈互操作——工具连接与智能体互操作的分工和组合模式（子题目 11/48）

## 一、为什么工具层需要网关

当智能体数量增长，若每个智能体都直连每个MCP服务器，工具层会重演一次点对点混乱：认证策略重复实现、审计碎片化、工具版本漂移无人察觉。MCP网关把工具连接收敛为一点：上游对智能体暴露统一的MCP端点与聚合工具清单，下游管理到各工具服务器的连接、鉴权与路由。智能体只需认识网关，不必知道工具物理上在哪里、由谁运维。

## 二、网关的六项职能

- **聚合**：合并多个下游服务器的tools/list，统一命名空间防止重名冲突（如 `db.query` 与 `fs.read_file`）。
- **鉴权**：对智能体侧验证服务身份，对工具侧按调用主体的作用域裁剪令牌。
- **审计**：记录每次工具调用的主体、任务、参数摘要与结果状态，与A2A任务ID关联。
- **限流与配额**：按主体设置调用速率与令牌预算，防失控循环打爆下游。
- **版本治理**：工具接口变更先在网关灰度，旧schema保留窗口期。
- **选择性暴露**：把内部工具的子集按租户或角色投影，同一物理服务器呈现不同逻辑清单。

## 三、在多智能体拓扑中的落位

```text
 [智能体A] --A2A--> [智能体B]
    |                   |
    +---MCP---> [MCP网关] <---MCP--- +
                 |
     +-----------+-----------+
     |           |           |
 [db工具]    [检索工具]   [执行工具]
```

要点是：智能体之间的A2A流量绕过网关直达对端端点；工具流量一律经网关。网关不是A2A的反向代理——把智能体对话也塞进工具网关会造成层级倒挂，也是常见反模式。

## 四、路由与命名空间配置示例

```yaml
gateway:
  upstream_namespace: "gw"
  downstreams:
    - name: db
      url: https://db-tools.internal/mcp
      prefix_tools_with: "db"
      allowed_scopes: ["db:read:*"]
    - name: search
      url: https://search-tools.internal/mcp
      prefix_tools_with: "search"
      allowed_scopes: ["search:query"]
  exposure_rules:
    - principals: ["role:analyst-agent"]
      allow: ["db.*", "search.query"]
    - principals: ["role:csr-agent"]
      allow: ["search.query"]
```

## 五、落地清单

1. 网关自身无状态化，会话状态外置，便于水平扩容。
2. 工具清单在网关缓存并打版本戳，智能体侧重连时用版本比对避免全量刷新。
3. 网关到下游的连接数要有上限与熔断，防单工具拖垮全局。
4. 审计日志写入不可变主题流，禁止在日志中记录凭据或完整敏感参数。
5. 为每个智能体主体签发独立凭据，杜绝共享账号式接入。

## 六、小结

MCP网关是工具层的秩序点：让"智能体×工具"的扇形连接被归一收束。它与A2A层互不越界——网关管手，A2A管同事，两者在审计流上以任务ID交汇，构成完整的治理闭环。
