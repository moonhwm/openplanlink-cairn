# 05 · 传输层对比：JSON-RPC之上的两条路

> 所属主题：A2A×MCP双栈互操作——工具连接与智能体互操作的分工和组合模式（子题目 05/48）

## 一、共同的信封

两个协议都选择了JSON-RPC 2.0作为消息信封：请求带 method 与 params，响应带 result 或 error，通知无 id。这个共同点极为宝贵——它意味着网关、代理、日志中间件可以用同一套解析框架处理两种流量，只按方法名前缀或路由区分。实践中常见的做法是在反向代理层按路径切分：`/mcp` 进入工具总线，`/a2a` 进入智能体总线，共享连接池与TLS配置。

## 二、各自的传输选项

- **MCP**：本地场景使用 stdio（子进程管道，零网络开销，天然隔离）；远程场景使用 Streamable HTTP——单一端点同时承接普通请求与可选的SSE升级流，取代了旧版"HTTP POST + 独立SSE GET"的双端点结构。会话通过 `Mcp-Session-Id` 头维持。
- **A2A**：从设计之初就面向开放网络，基于HTTP POST的JSON-RPC为主体，响可选择升级为SSE流以承载增量事件；另含独立的推送回调通道（webhook），用于任务在无活跃连接时的完成通知。

## 三、语义差异与桥接要点

| 维度 | MCP | A2A |
| --- | --- | --- |
| 本地进程传输 | 支持（stdio） | 不适用 |
| 流式承载 | 进度通知、日志 | 消息流、状态流、Artifact增量 |
| 服务端推送 | 无独立机制 | push notification webhook |
| 会话标识 | 会话头字段 | 任务ID + 可选会话ID |
| 典型时延要求 | 毫秒到秒 | 秒到小时 |

桥接两种传输时要注意三点：其一，MCP的进度通知没有业务状态语义，桥到A2A时只能映射为 `status-update` 事件而不能伪造任务状态跃迁；其二，SSE的自动重连在两个协议里确认语义不同，A2A要求客户端按任务ID幂等重取；其三，stdio桥接HTTP时必须处理子进程崩溃的重建，不能让工具崩溃传染智能体任务。

## 四、反向代理配置骨架

```nginx
upstream agent_core { server 127.0.0.1:8081; }

server {
  listen 443 ssl;

  # MCP工具总线：短超时、大并发
  location /mcp {
    proxy_pass http://tool_gateway;
    proxy_read_timeout 60s;
  }

  # A2A任务总线：长连接、流式
  location /a2a {
    proxy_pass http://agent_core;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;          # SSE必须关缓冲
    proxy_read_timeout 3600s;     # 长时任务
  }
}
```

## 五、小结

传输层是双栈共享度最高的层：信封同构、底座同源。工程上应尽量让两股流量穿过同一套基础设施，把差异压缩到路径、超时与流式策略三处，运维复杂度即可控。
