# 15 · 组合模式三：MCP服务器内部调用A2A智能体

> 所属主题：A2A×MCP双栈互操作——工具连接与智能体互操作的分工和组合模式（子题目 15/48）

## 一、模式描述

与模式二相反，这里让一个MCP服务器在执行工具时，内部去委托一个远程智能体完成其中的自主性子步骤。典型场景：工具"简历初筛"本身是参数化的（输入候选人档案，输出评分表），但评分逻辑需要复杂判断，于是工具服务器把"读档、评估、写评语"的部分委托给一个评审智能体，自己只做格式转换与落库。

这个模式的本质是"工具外壳、智能体内芯"：对宿主保持工具契约的稳定性，对内部把判断力外包。它适合接口必须稳定（宿主不愿跟随智能体迭代）、而实现需要智能弹性的场合。

## 二、执行路径分解

```text
宿主 --tools/call(vet_resume, {doc:...})--> MCP服务器
  MCP服务器:
    1. 校验参数、规范化文档格式
    2. A2A: 向评审智能体发送任务（附评分细则作为消息）
    3. 等待任务终态；期间向宿主发 progress notification（进度百分比）
    4. 收到Artifact: 评语+分项分数
    5. 组装 structuredContent: 符合工具outputSchema的评分表
    6. tools/call 返回
```

第3步是体验关键：虽然A2A任务是黑箱等待，但服务器可以基于预估时长发送模拟进度或真实阶段事件，避免宿主侧超时误判。

## 三、实现要点清单

1. **契约冻结**：工具的input/outputSchema是对外承诺，内部换智能体、换模型都不许改变schema语义。
2. **超时预算分层**：给内部A2A任务的等待上限必须小于宿主对本工具的调用超时，留出组装与网络余量。
3. **失败翻译**：内部任务failed要翻译成工具的isError结果，并把远端失败原因脱敏后放入content，禁止把远端原始堆栈透给宿主。
4. **取消传播**：宿主的cancel通知应触发tasks/cancel；若远端不响应，本地按超时终局并标记。
5. **并发控制**：一个工具服务器对同一智能体的在途任务数设上限，防把对方打挂。
6. **凭据方向**：服务器持自己的服务身份调用智能体，禁止把宿主或用户的宽权限凭据透传给内部委托。

```python
def vet_resume(doc: dict) -> dict:
    task = a2a_send(REVIEWER_URL, build_brief(doc))
    final = await_terminal(task.id, timeout=240)
    if final.state != "completed":
        raise ToolSoftError("评审未完成，请稍后重试")
    art = final.artifacts[0].data
    return {
        "structuredContent": {
            "score": art["total"],
            "breakdown": art["dimensions"],
        }
    }
```

## 四、风险面

- **层级倒挂风险**：工具层开始"指挥"智能体层，若评审智能体又反过来调用本工具所在的服务器，会形成环路。必须在委托消息里携带深度标记并设上限。
- **审计盲区**：宿主只见工具调用成功，看不到内部经过智能体。补救：在工具结果的元数据（如 `_meta`）里附内部任务ID，供审计穿透。
- **责任归属模糊**：评分错误是工具的错还是智能体的错？组织上要预先约定：对外责任始终归工具提供方。

## 五、小结

模式三用工具的稳定外壳包裹智能体的活性内芯，是"契约稳、实现活"矛盾的优雅解。代价是引入了层级倒挂与审计穿透两个新问题，靠深度上限与元数据回链可以压住。适合作为特定高价值工具的深化手段，不宜大面积铺开。
