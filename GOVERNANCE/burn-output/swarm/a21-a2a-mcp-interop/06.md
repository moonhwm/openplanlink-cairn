# 06 · 发现机制对比：工具清单与AgentCard

> 所属主题：A2A×MCP双栈互操作——工具连接与智能体互操作的分工和组合模式（子题目 06/48）

## 一、MCP的发现：握手内协商

MCP的发现是会话内的、协议化的：客户端建立连接后发送 `initialize`，服务器在能力声明里告知是否提供tools/resources/prompts；客户端随后调用 `tools/list`，得到带JSON Schema的完整工具清单；服务器还可在运行期通过 `tools/list_changed` 通知触发客户端重新拉取。整个机制假设双方已经"认识"——端点是配置来的，发现只解决"有什么、长什么样"。

这种设计的优点是契约精确、机器可直接校验参数；代价是清单会膨胀，动辄上百个工具的schema会挤占上下文窗口，于是社区出现了工具分组、按需加载等实践。

## 二、A2A的发现：档案式发现

A2A借鉴了 robots.txt 与 OIDC 的 well-known 惯例：任何智能体在 `https://host/.well-known/agent-card.json` 发布自述档案，内容包括身份、能力skills、端点、认证方案与内容模式偏好。发现过程是先取档案、再决策、后建连：

```python
import httpx, json

def discover(base_url: str) -> dict:
    resp = httpx.get(
        f"{base_url.rstrip('/')}/.well-known/agent-card.json",
        timeout=10,
    )
    resp.raise_for_status()
    card = resp.json()
    # 校验必要字段，防止半截档案进入路由表
    for field in ("name", "url", "skills"):
        assert field in card, f"AgentCard缺少字段: {field}"
    return card
```

档案是静态文档而非会话产物，因此天然适合缓存、索引与目录化，也让第三方注册表可以只靠抓取well-known就能建库。

## 三、差异与互补清单

- **发现对象**：MCP发现操作（动词），A2A发现主体（名词）。
- **时机**：MCP在会话建立后；A2A在会话建立前。
- **精度**：MCP参数级；A2A意图级。
- **缓存策略**：AgentCard可长缓存（按版本号失效）；工具清单建议短TTL并响应list_changed。
- **组合方式**：先经目录找到智能体，再在其会话内发现工具——两级发现串联而非互斥。

## 四、统一目录的元数据桥

双栈系统常需要一个内部目录同时收录两类实体，桥接方案是为MCP服务器生成合成档案：

```json
{
  "kind": "mcp-server",
  "endpoint": "https://tools.internal/calendar/mcp",
  "transport": "streamable-http",
  "summary": "日历读写工具集",
  "toolCount": 7,
  "auth": "oauth",
  "indexedAt": "2026-09-20T08:00:00Z"
}
```

目录消费方按 `kind` 字段决定后续走MCP握手还是A2A委托，发现层由此归一。

## 五、小结

发现机制的分野再次印证分工：工具要"查得准"，智能体要"找得到"。工程上把AgentCard做成长缓存的公开契约、把工具清单做成会话内的动态视图，并在目录层做统一索引，是兼顾性能与治理的常规解。
