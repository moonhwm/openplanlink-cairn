# 09 · 能力表达：参数级Schema与意图级Skills

> 所属主题：A2A×MCP双栈互操作——工具连接与智能体互操作的分工和组合模式（子题目 09/48）

## 一、两种表达精度

MCP工具的能力表达是参数级的：名称、描述、inputSchema（JSON Schema）、可选outputSchema。模型据此可以直接构造合法调用，网关据此可以做参数校验与权限匹配。精度高，但表达成本也高——schema会进上下文，工具多了就贵。

A2A的skills是意图级的：一个标识符加人类可读的名称与描述，可选标签。它不承诺参数结构，因为对话本身就是参数协商过程——委托方在消息里逐步给出约束，受托方在需要时反问。表达便宜，但无法被机器直接校验，只能被模型理解。

## 二、并排示例：同一件事的两种写法

把"生成行程草案"分别写成MCP工具与A2A skill：

```json
{
  "name": "draft_itinerary",
  "description": "根据预算与日期生成多城市行程草案",
  "inputSchema": {
    "type": "object",
    "properties": {
      "cities":   { "type": "array", "items": { "type": "string" } },
      "budget":   { "type": "number", "exclusiveMinimum": 0 },
      "start":    { "type": "string", "format": "date" },
      "end":      { "type": "string", "format": "date" }
    },
    "required": ["cities", "start", "end"]
  }
}
```

```json
{
  "id": "itinerary.draft",
  "name": "行程草案生成",
  "description": "给定旅行约束，产出逐日行程JSON草案；预算、偏好等细节可在对话中补充",
  "tags": ["travel", "planning"]
}
```

前者可以被任何模型一次调用成功；后者需要一轮对话才能对齐参数，但也能接受"帮我安排个不太贵的西南之旅"这类模糊输入。

## 三、能力翻译层

双栈系统常需要把一种表达翻译成另一种，方向不同难度天差地别：

- **MCP工具 → A2A skill**：容易。把schema的description与人读名称合并进skill描述，声明defaultInputModes为application/json，受托智能体内部再调用工具。语义有损但方向安全。
- **A2A skill → MCP工具**：危险。被迫发明一个收敛的inputSchema，而真实的参数空间是对话协商出来的。除非确知该skill接口稳定，否则会造成"schema说谎"——校验通过却语义失败。

```python
def mcp_tool_to_skill(tool: dict) -> dict:
    schema = tool.get("inputSchema", {})
    props  = ", ".join(schema.get("properties", {}).keys())
    return {
        "id":   f"mcp.{tool['name']}",
        "name": tool["description"][:40] or tool["name"],
        "description": (
            f"{tool['description']} 参数经由JSON正文传递，"
            f"常见字段：{props or '无'}。"
        ),
        "tags": ["mcp", "tool-backed"],
    }
```

## 四、选型要点清单

1. 接口稳定、参数可枚举 → 用MCP工具表达，享受校验与静态分析。
2. 接口开放、需澄清 → 用A2A skill表达，让对话完成收敛。
3. 同一能力两种暴露 → 在skill描述里注明"亦提供结构化端点"，给高级调用方留快路径。
4. 目录检索 → skill的tags与工具的description都应埋入可检索关键词，两边检索行为要保持一致。

## 五、小结

能力表达的分野是精度的分野：schema服务机器，skill服务模型。翻译要顺着"高精度→低精度"的方向做，逆向翻译只有在接口冻结的前提下才值得尝试。
