# Python SDK的streamable_http传输与FastMCP的差异

**一句话摘要**：本文厘清Python官方SDK中低层streamable_http传输模块与高层FastMCP框架的关系——前者提供StreamableHTTPSessionManager与传输原语，后者在uvicorn/Starlette上把它封装成一挂即用的应用——并分析两者的定制点与选择标准。

## 一、两个层次各自的交付物

Python SDK的HTTP栈由两部分组成。低层部分在mcp.server.streamable_http命名空间，交付三样东西：StreamableHTTPServerTransport（单会话的传输实现，持有内存消息对、可选SSE流、会话id生成器、是否resumable等配置）、StreamableHTTPSessionManager（面向ASGI应用的多会话管理者，负责initialize时签发会话、按Mcp-Session-Id路由请求、空闲超时清扫、挂载到Starlette路由）、以及JSONResponse/SSE辅助类型。高层FastMCP（mcp.server.fastmcp.FastMCP）则是把Server实例、工具/资源/提示词装饰器注册、stdio与HTTP运行器打包成一体的框架：mcp.run(transport="stdio")起本地进程，streamable_http_app()返回一个可被uvicorn托管的Starlette ASGI应用，mcp.run(transport="http", host/port参数)则直接拉起uvicorn监听。一句话概括关系：FastMCP是"配置即用"的成品，低层streamable_http是"自行组装"的零件包；前者内部正是用后者实现的。

选择标准因此清晰：需求只是"把我的工具函数暴露成HTTP端点"，用FastMCP十分钟收工，认证、自定义路由、多应用挂载再逐级下沉定制；需要精细控制会话策略（外部存储、自定义超时、粘性路由集成）、需要把MCP端点嵌进已有大型Starlette/FastAPI应用、或需要在同一进程里区分多个Server实例，则直接使用低层SessionManager。

## 二、FastMCP的HTTP运行路径剖析

FastMCP.streamable_http_app()的组装逻辑值得剖析：它创建一个StreamableHTTPSessionManager，事件流设置为可恢复（resumable）时启用事件存储；用Starlette的路由把POST/GET/DELETE /mcp（路径可配）都路由到session_manager.handle_request；再挂上可配置的中间件位。run(transport="http")则在此基础上建uvicorn服务器，host默认127.0.0.1（安全默认：不暴露公网）、可传port与log_level。会话管理器对请求的处理流程：POST先查会话头，initialize则创建transport与会话id并在响应头回发；命中会话则把ASGI请求交给该会话的transport，transport按第06、07篇的语义决定回JSON还是SSE流；GET尝试开推送流（无则405）；DELETE终结会话。FastMCP还默认开启了json_response模式与否、host绑定、状态码等一批评改项，升级SDK版本时建议对照变更日志复核行为。

定制点分布：认证——FastMCP允许在app上包你自己的中间件校验Bearer令牌（令牌验证逻辑自备，注意不要在日志回显）；路径与多应用——可以把两个FastMCP实例的app分别挂在主应用的/mcp/a与/mcp/b子路径下；超时与会话TTL——低层SessionManager构造参数；工具级限流——装饰器外再包一层自己的限流包装函数。

## 三、两种用法的对照代码

```python
# —— 用法A：FastMCP成品式（适合绝大多数场景）——
from mcp.server.fastmcp import FastMCP
import anyio

mcp = FastMCP("demo")

@mcp.tool()
def add(a: int, b: int) -> int:
    """两数相加"""
    return a + b

# 本地：mcp.run()  # stdio
# HTTP：自定义宿主时取ASGI应用
app = mcp.streamable_http_app()   # 交给 uvicorn/gunicorn 托管
if __name__ == "__main__":
    mcp.run(transport="http", host="127.0.0.1", port=8000)

# —— 用法B：低层组装式（嵌已有Starlette应用+自管会话）——
import starlette.applications as sa
from starlette.routing import Mount
from mcp.server.lowlevel import Server
from mcp.server.streamable_http import StreamableHTTPSessionManager
from mcp import types

low = Server("lowlevel")

@low.list_tools()
async def list_tools() -> list[types.Tool]:
    return [types.Tool(name="ping", description="探活",
                       inputSchema={"type": "object", "properties": {}})]

manager = StreamableHTTPSessionManager(
    app=low,          # 低层Server实例
    event_store=None, # None=不可恢复；提供EventStore实现则启用Last-Event-ID重放
    json_response=False,  # False允许SSE流；True强制纯JSON（无状态友好）
    stateless_http=False, # True=无会话形态（Serverless）
)

main_app = sa.Starlette(routes=[
    Mount("/mcp", app=manager.handle_request),  # 嵌入既有大应用
], lifespan=lambda scm: manager.run())  # 生命周期内启动/清扫会话任务
```

## 四、选择与验收清单

两条路线共同的验收清单：initialize返回会话头且后续请求校验；404/410触发客户端重握手路径可用；DELETE终结会话；GET流在允许SSE时工作、禁用时回405；host默认回环、公网部署必配TLS与认证；json_response=True与False两种模式各自的行为正确；同一进程双实例（挂不同子路径）互不串会话；压测下每会话内存有界（事件存储要有上限）。选型判断只需回答三个问题：是否要嵌入既有ASGI应用（是→低层）、是否需要自管会话存储（是→低层）、是否只求最快上线（是→FastMCP）。理解了这层"成品与零件"的关系，Python侧HTTP传输的定制再无迷雾。
