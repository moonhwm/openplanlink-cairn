# 自定义绑定（Custom Transports）：从内存传输到私有协议适配

**一句话摘要**：本文讲解MCP规范预留的自定义传输通道——什么信道可以承载MCP、官方SDK的Transport扩展点长什么样、四类典型自定义绑定（内存、消息队列、gRPC、进程桥）的设计要点与完整代码示例。

## 一、自定义绑定的合法性与边界

MCP规范把传输层定义为可插拔层，官方标准化了stdio与HTTP族两种绑定，但明确允许任何满足下列契约的信道承载MCP：第一，能不重不漏地传递完整JSON-RPC消息（传输负责分帧或选择具备消息边界的载体）；第二，双向可达——客户端到服务器与服务器到客户端都能传消息，因为服务器也会发起请求；第三，提供启动、关闭与故障通知的机制；第四，对无界二进制数据没有强制要求（MCP消息都是JSON文本）。这段边界描述直接划定了候选信道名单：进程内队列、Unix域套接字、消息队列主题、gRPC双向流、邮槽、蓝牙RFCOMM、甚至电子邮件式的存储转发，理论上都能成为MCP传输。

选择自定义绑定通常是出于四类动机：测试便利（内存传输让客户端与服务器同进程直连，毫秒级往返且可精确控制故障注入）；基础设施亲和（企业已有Kafka/NATS/gRPC网格，不想为MCP单开HTTP面）；宿主嵌入（把MCP服务器嵌进另一个应用进程内，如IDE与语言服务器同进程通信）；特殊拓扑（离线批量、窄带物联网）。风险同样要认清：自定义绑定失去生态互操作性——官方客户端默认只认stdio与HTTP，凡是选择私有信道的系统，必须同时分发对应的适配器实现，并把版本协商、认证、恢复这些官方绑定"免费赠送"的能力自己补齐。

## 二、官方SDK的扩展点形状

各语言SDK都把传输抽象成小接口。TypeScript的Transport契约是：start()建立连接、send(msg)发送一条JSON-RPC消息、close()优雅关闭、onmessage/onclose/onerror三个回调；服务器端与客户端端各有一套对称实现。Python SDK低层提供MemoryTransport（asyncio队列对）与 transports 里的session对象抽象；Java/Kotlin/C#的SDK同样以接口形式暴露（如Java的McpTransport与McpAsyncProcessor）。实现自定义传输的全部工作就是填充这几个成员，把信道读写桥接到回调。下面给出最有代表性的内存传输实现（TypeScript），它同时是测试工具与接口教学样本：

```typescript
import { Transport } from "@modelcontextprotocol/sdk/shared/transport.js";

export class InMemoryTransport implements Transport {
  onmessage?: (m: unknown) => void;
  onclose?: () => void;
  onerror?: (e: Error) => void;
  private peer?: InMemoryTransport;
  private closed = false;

  static createLinkedPair(): [InMemoryTransport, InMemoryTransport] {
    const a = new InMemoryTransport(), b = new InMemoryTransport();
    a.peer = b; b.peer = a;                 // 双向直连
    return [a, b];
  }

  async start(): Promise<void> {
    if (!this.peer) throw new Error("not linked");
  }

  async send(msg: unknown): Promise<void> {
    if (this.closed) throw new Error("transport closed");
    // 直接投递到对端回调：同进程零拷贝语义
    queueMicrotask(() => this.peer!.onmessage?.(msg));
  }

  async close(): Promise<void> {
    if (this.closed) return;
    this.closed = true;
    this.onclose?.();
    queueMicrotask(() => this.peer!.onclose?.()); // 通知对端
  }
}

// 用法：客户端与服务器同进程连接，毫秒级往返
```

## 三、四类典型自定义绑定的设计要点

内存绑定：用createLinkedPair模式，注意投递走微任务队列避免同步重入（服务器在处理消息中同步回调客户端会造成栈溢出）；支持故障注入开关（随机丢弃、延迟）以测试上层重试。消息队列绑定：上行与下行各用一个主题（或一对队列），offset确认语义与JSON-RPC id配对解耦；必须限制单消息大小并处理投递重复（幂等靠id去重）；会话用消息头携带。gRPC双向流绑定：一条BiDi流天然承载全双工，每条gRPC消息体放一条JSON；流断即传输断，重连恢复复用流重建；错误码映射（UNAVAILABLE触发重连、DEADLINE_EXCEEDED映射请求超时）。进程桥绑定（跨语言嵌入）：宿主语言与插件语言之间用stdin/stdout或套接字，本质是复刻stdio规范，重点是双侧分帧器与生命周期回调对齐。

## 四、落地核对清单

交付任何自定义绑定时按此清单验收：实现了start/send/close与onmessage/onclose/onerror全集合；消息不重不丢（或明确声明at-least-once并做幂等）；双向都能传请求与通知（测一个服务器发起的elicitation请求就能验证）；关闭语义三路径完备（主动close、对端close、信道异常）；认证与版本协商有等价物（私有信道至少要有自己的握手校验）；分帧上限与UTF-8正确性有测试；提供同版本SDK的两侧适配器并锁定协议版本。达成这些，自定义绑定就从"玩具"升级为可运维的生产传输。
