# 版本协商与兼容：MCP-Protocol-Version与旧客户端握手降级

**一句话摘要**：本文系统梳理MCP协议版本协商与向后兼容工程——版本字符串的精确匹配语义、initialize参数与请求头的双重协商、服务器对旧版客户端的降级策略、多版本共存服务的实现模式，以及兼容性回归的验收清单。

## 一、版本协商的双重机制

MCP的版本管理有两个正交机制。机制一，握手参数协商：initialize请求的params.protocolVersion携带客户端期望版本（日期格式字符串，如"2025-03-26"、"2025-06-18"），服务器在result.protocolVersion回定——支持则原样返回，不支持则返回自己支持的版本，客户端据此决定继续或断开；这是逻辑层协商，决定双方按哪版语义解释消息。机制二，请求头复核（Streamable HTTP）：握手后的每个HTTP请求携带MCP-Protocol-Version头，服务器校验与握手结果一致，不一致回400/410——这是防漂移机制，抓"握手用A版本、后续请求按B版本语义"的错位客户端。两者的正确关系是"参数定版本、头部守版本"：头部值必须取自握手结果（客户端保存initialize响应里的version），而不是客户端自己的期望值——取错源是常见bug。

匹配语义的纪律：精确字符串相等，不是语义化版本比较。不存在"2025-06-18大于2025-03-26所以兼容"的推论——每个日期版本都可能包含破坏性变更（例如2025-06-18将旧的HTTP+SSE标记为deprecated、调整了结构化工具输出与资源语义），兼容判断唯一依据是官方变更日志与服务器实际支持列表。实现里把支持版本写成显式数组，不要写"大于等于"。

## 二、服务器侧降级策略矩阵

服务器面对旧版客户端的策略分四档：档一，完全支持——客户端请求2025-03-26且服务器仍实现旧语义（含旧版HTTP+SSE端点），原样回定，一切按旧版走；档二，降级支持——服务器主实现新版本，但对旧版本日期参数回定旧版本号并在内部做语义垫片（例如旧版的elicitation行为差异在适配层抹平）；档三，能力收缩——回定旧版本号但明确不支持旧版特有传输（例如只提供单端点，旧版HTTP+SSE客户端无法工作，只能服务stdio旧客户端）；档四，拒绝——不支持则回定自己最高版本，客户端自行判断，或Streamable HTTP下按规范返回410并可在响应中给出可重试指引。选择取决于维护成本：语义垫片（档二）长期是负债，官方对旧版的态度是尽快迁移，因此主流SDK的服务器实现收敛在"支持最近两三个日期版本+旧传输端点保留一个窗口期"。客户端侧的降级则是20篇的传输探测（先Streamable HTTP后旧版SSE）加上本文的版本参数回退：把支持版本列表从新到旧逐个尝试initialize，取第一个握手成功的组合。

## 三、多版本共存服务器的实现模式

```typescript
import { randomUUID } from "node:crypto";

// 版本注册表：每个版本一组语义开关与消息兼容钩子
const VERSIONS = {
  "2025-06-18": { latest: true,  structuredToolOutput: true,
                  legacyHttpSse: false },
  "2025-03-26": { latest: false, structuredToolOutput: "adapt",
                  legacyHttpSse: false },
  "2024-11-05": { latest: false, structuredToolOutput: "adapt",
                  legacyHttpSse: true },   // 此版本客户端可能走双端点
} as const;
type Ver = keyof typeof VERSIONS;
const DEFAULT: Ver = "2025-06-18";

export function negotiateVersion(requested?: string): Ver {
  if (requested && requested in VERSIONS) return requested as Ver; // 精确匹配
  return DEFAULT;  // 不认识/不支持：回定自家默认，由客户端决断去留
}

// initialize处理器
async function handleInitialize(msg: any, res: express.Response) {
  const ver = negotiateVersion(msg.params?.protocolVersion);
  // 会话上钉死版本：后续所有消息按ver语义解释（含输出结构的适配开关）
  const session = createSession(ver);
  res.header("mcp-session-id", session.id);
  return {
    protocolVersion: ver,                       // 回定：协商结果
    capabilities: capabilitiesFor(ver),
    serverInfo: { name: "versioned-server", version: "1.0" },
  };
}

// 请求头守卫（6篇规则的多版本化）
function versionGuard(req: express.Request, res: express.Response, next: () => void) {
  if (req.body?.method === "initialize") return next();
  const session = lookup(req.header("mcp-session-id"));
  const header = req.header("mcp-protocol-version");
  if (!session) return res.status(404).end();
  if (header !== undefined && header !== session.version)
    return res.status(400).json({ error: "version drift: re-initialize" });
  next();
}

// 输出适配示例：旧客户端没有结构化输出语义 -> 降级为纯文本内容
function renderToolResult(ver: Ver, structured: object): object[] {
  const cfg = VERSIONS[ver];
  if (cfg.structuredToolOutput === true)
    return [{ type: "structured_content", content: structured } as never];
  return [{ type: "text", text: JSON.stringify(structured, null, 2) }];
}
```

## 四、兼容性回归与治理清单

兼容性工程验收清单：支持版本矩阵（客户端版本×服务器版本）全组合的initialize冒烟，结果（回定值、能力集）与文档一致；版本漂移用例——握手A后续头部B收到400并提示重握手；旧版客户端走旧传输端点（若保留）全功能通过且指标可区分占比；新客户端对新服务器端到端（含structure输出、GET流、DELETE）通过；头部取值源自握手结果的单元断言（防"期望值bug"）；410路径的客户端行为验证（自动降级或明确报错，不悬挂）；版本支持列表的变更进入发布说明与弃用时间线（提前一版公告）。治理上建议维护一张"版本×特性×传输"的支持表作为单一事实源，文档、代码注册表、测试矩阵三处由它生成——版本兼容从口头承诺变成可回归的资产。
