# 传输层背压与流量控制

**一句话摘要**：本文讨论MCP传输层的背压工程——生产快于消费时的挂起、丢弃与分级策略，覆盖stdio管道缓冲、SSE流写出的反压、有界队列的选取、以及端到端背压级联的设计与验收。

## 一、背压从哪里来

背压问题的通用形态：生产者（服务器生成事件/响应）快于消费者（客户端读取与处理），未受控的差额要么爆内存（无界缓冲）要么丢消息（无界丢弃）。MCP传输里背压具体出现在四个环节。环节一，stdio管道：操作系统的管道缓冲有限（Linux默认64KB），子进程写满stdout后write阻塞——这是内核免费送的背压，客户端读得慢服务器就写得慢，看似安全，但若服务器是单线程事件循环，一个阻塞的协议write会卡死它的全部处理，包括stderr日志，表象为整机假死。环节二，SSE/HTTP流写出：服务器向慢客户端写响应流，框架若提供写缓冲（Node的res.write返回false、Go的Flusher阻塞、Python的await drain）就是显式背压信号，忽略它而无限写就是无界缓冲。环节三，会话内推送队列：服务器主动通知排队等待下发，队列无界则慢客户端拖垮内存。环节四，客户端侧：通知处理器若慢（比如UI渲染），接收泵被卡住会反压到网络层，进而波及同连接上的响应接收——需要把"接收"与"处理"解耦成有界队列。

策略空间有三档：挂起（await背压信号，保序保完整，代价是生产端变慢）、丢弃（仅通知类，保内存，代价是信息损失要有补偿路径）、断开（超限客户端判为异常，保护服务器其它会话）。选档原则：响应与请求类消息永挂起或断开、绝不静默丢弃；通知类在配额内挂起、超配额丢最旧并计数；心跳与保活永不排队（直接写或跳过本次）。

## 二、各栈的背压原语与正确用法

- Node.js：stream.write()返回false时必须等drain事件再继续写；`for await`语义或pipeline()自动处理；WS的ws.send不回压，要监听bufferedAmount并自挂起。
- Python asyncio：await writer.drain()在写缓冲高水位时挂起；anyio内存流send()在缓冲满时挂起（有界设置）。
- Go：net/http的ResponseWriter写在内核缓冲满时阻塞（隐式背压）；channel天然有界，select+default实现丢最旧或非阻塞尝试。
- Rust：tokio有界mpsc的send().await满时挂起——编译器强制你选容量，是最不易出错的原语。
- Kotlin/Flow：buffer(capacity, onBufferOverflow=SUSPEND|DROP_OLDEST)正是两档策略的声明式表达。

## 三、端到端背压级联的实现

以下TypeScript展示"接收-处理解耦+分级推送+写反压"的组合：

```typescript
export class BackpressuredSession {
  private reliableQ: object[] = [];         // 响应/请求：永不丢弃
  private bestEffortQ: object[] = [];       // 通知：有界丢最旧
  private processing = new Promise<void>(r => r());
  private dropped = 0;

  constructor(private sink: { write(s: string): boolean; onceDrain(cb: () => void): void },
              private limits = { bestEffort: 256, warnBytes: 1 << 20 }) {}

  enqueue(msg: object, kind: "reliable" | "bestEffort"): void {
    if (kind === "reliable") this.reliableQ.push(msg);          // 挂起策略的队列形态
    else {
      this.bestEffortQ.push(msg);
      if (this.bestEffortQ.length > this.limits.bestEffort) {
        this.bestEffortQ.shift();                                // 丢最旧+计数
        this.dropped++;
      }
    }
    void this.pump();
  }

  private async pump(): Promise<void> {
    this.processing = this.processing.then(async () => {
      for (;;) {
        const next = this.reliableQ[0] ?? this.bestEffortQ[0];
        if (!next) return;
        const frame = JSON.stringify(next) + "\n";
        if (!this.sink.write(frame)) {                           // 写反压信号
          await new Promise<void>(r => this.sink.onceDrain(() => r())); // 挂起等drain
        }
        this.reliableQ[0] === next ? this.reliableQ.shift()
                                   : this.bestEffortQ.shift();
      }
    });
    await this.processing;
  }

  stats(): { droppedNotifications: number } { return { droppedNotifications: this.dropped }; }
}

// stdio服务器侧的自保护（防单write卡死整个循环）：
// 把协议stdout的写出放到独立的"写者task"，业务循环只enqueue；
// 写者task内部处理write/drain，并在持续不可写超过阈值时判死连接。
```

级联设计的最后一步是跨进程传播：服务器内部有界后，压力自然经网络TCP窗口传导到客户端接收缓冲，再到客户端处理循环——只要每一跳都有界，整条链路内存可控；任何一跳偷懒放无界数组，整条链路的保护就被击穿。

## 四、验收清单

背压验收清单：灌入十万条通知而客户端每百条读一次，服务器内存曲线平稳且dropped计数吻合预期；慢消费者场景下其它会话P99不受影响（联动29篇隔离测试）；reliable队列在慢消费者下增长有界并最终触发断开或显式排队上限错误，绝不OOM；写反压挂起期间心跳独立通路仍活（否则会被误判死）；drain事件监听无泄漏；客户端侧处理解耦验证——通知处理器人为阻塞5秒，期间响应接收不受影响；stdio子进程在客户端停读时自身日志（stderr）仍持续输出（证明协议write的阻塞未卡死日志任务）。这份清单模拟的都是真实弱网与慢客户端场景，通过即证明传输层在压力下是"变慢"而不是"变炸"。
