# 断线重连与消息恢复：Last-Event-ID与resumability能力

**一句话摘要**：本文深入MCP Streamable HTTP的消息恢复机制——事件id分配、Last-Event-ID请求头、EventStore重放窗口、客户端恢复流程与降级路径——并给出一个带界重放缓冲的可运行实现。

## 一、恢复问题的本质与协议方案

服务器主动推送的事件流（GET长流与POST响应流）面临一个根本问题：断线期间服务器发出的消息会丢失。对通知类消息，丢失或许可容忍（客户端可轮询补偿）；但Streamable HTTP的POST响应流上可能承载着JSON-RPC响应，丢一条响应等于请求永远悬挂。协议给出的方案是SSE原生的恢复三元组：服务器在每个（或关键）事件上携带id字段；客户端记住最后收到的事件id；断线重连时（GET流）在请求头带Last-Event-ID；服务器在支持的情况下重放该id之后缓存的事件，从而把流"续"上。MCP规范把这套机制定名为resumability（可恢复性），并允许服务器声明是否支持——不支持的服务器可以忽略Last-Event-ID，直接从当前时刻开始新流；客户端必须把"无重放"视为正常路径并走补偿逻辑（重新initialize或重发查询类请求；有副作用的请求走人工确认）。

恢复语义的边界要理解清楚：恢复的是"流上事件的连续性"，不是"会话的原子性"。重放窗口有限的EventStore只承诺窗口内的续传——窗口外的旧事件，客户端要靠协议层补偿（重拉列表、重新订阅）；会话本身过期（404/410）时，事件恢复无从谈起，必须整体重新握手。因此健壮客户端的断线流程是两级：先尝试带Last-Event-ID重连（轻量，毫秒级）；失败再走重握手（重量，重协商+补偿）。两级之间的选择由服务器响应自动驱动：重连成功且事件连续即恢复；404/410即升级。

## 二、EventStore：服务器侧的重放引擎

服务器侧需要一个有界的事件存储：环形缓冲按事件id（单调递增整数或可比较字符串）索引，每事件存（id, streamId, event对象序列化）。关键设计点：缓冲按流隔离（GET流与各POST响应流各自成序，恢复时只重放同流事件）；每会话的总缓冲上限（如4MB或2000条）防内存失控；POST响应流通常短命（响应事件即末尾），真正需要恢复窗口的主要是GET长流；写入与读取并发安全。以下实现可嵌入09篇的会话管理器：

```typescript
interface StoredEvent { id: number; streamId: string; payload: string }

export class RingEventStore {
  private buf: StoredEvent[] = [];
  private nextId = 1;

  append(streamId: string, payload: string): number {
    const id = this.nextId++;
    this.buf.push({ id, streamId, payload });
    if (this.buf.length > 2000) this.buf.splice(0, this.buf.length - 2000); // 有界
    return id;
  }

  /** 重放：同流、id严格大于afterId的事件，按序返回 */
  replayAfter(afterId: number, streamId: string): StoredEvent[] {
    return this.buf.filter(e => e.streamId === streamId && e.id > afterId);
  }

  hasContinuity(afterId: number, streamId: string): boolean {
    const same = this.buf.filter(e => e.streamId === streamId);
    return same.length === 0 || same[0].id <= afterId + 1; // 窗口未越过该id
  }
}

// GET流处理器的恢复分支：
function handleGetStream(req, res, session, store: RingEventStore) {
  const lastId = Number(req.header("last-event-id") ?? 0);
  const streamId = "push";                    // 会话级推送流的固定流标识
  res.set({ "content-type": "text/event-stream", "cache-control": "no-cache" });

  if (!Number.isFinite(lastId) || lastId <= 0 || !store.hasContinuity(lastId, streamId)) {
    // 无恢复点或窗口已滚过：从当前时刻开始（客户端自行补偿）
    session.attachPush(res);
    return;
  }
  for (const ev of store.replayAfter(lastId, streamId)) {   // 1) 先重放
    res.write(`id: ${ev.id}\nevent: message\ndata: ${ev.payload}\n\n`);
  }
  session.attachPush(res);                    // 2) 再挂实时泵（注意原子衔接）
}

// 实时发送路径：写出前先append，id随事件下发
function push(session, store, msg: object) {
  const id = store.append("push", JSON.stringify(msg));
  session.pushRaw(`id: ${id}\nevent: message\ndata: ${store.lastPayload}\n\n`);
}
```

原子衔接是重放的难点：重放完毕到实时泵接管之间存在竞态窗口，实现上要在持锁状态下完成"重放+注册写入者"两步，或用单一写者队列承接两段。

## 三、客户端恢复流程

客户端配合逻辑：消费事件时记录流级最后id（SSEParser已暴露，见08篇）；GET流断开后立即（小退避）带Last-Event-ID与Mcp-Session-Id重连；对重连得到的事件流，重放段照常处理（通知上抛、响应对应等待器）；若重连被404/410拒绝或服务器行为显示无恢复（例如返回全新流且无重放），走重initialize加补偿；补偿清单包括重拉tools/resources列表、重发订阅请求、对断线时在途的有副作用请求向用户或应用层确认状态。客户端还要处理重复：恢复语义是at-least-once，跨断点边界可能出现一条事件被收两次（写入与断线的竞态），通知类幂等无碍，响应类按id配对天然幂等（同一id的第二次到达被等待器忽略）。

## 四、验收清单

恢复机制验收清单：断流后带Last-Event-ID重连，窗口内事件按原序完整重达（用序号校验器验证无缺无重）；窗口滚过后行为降级为"新流+客户端补偿"而非报错；POST响应流中断时，客户端对该请求的等待器在恢复后正确resolve（响应事件经重放到达）；同一事件被收两次时业务侧幂等（用计数器验证）；会话过期与流断开两类故障分别触发重握手与重连两条路径；EventStore内存上限在广播风暴下有界；重放段与实时段衔接处无事件丢失（高压断连模糊测试）；不支持恢复的服务器组合下客户端全功能可用。这份清单对应的是"弱网可用的推送"这一硬指标，逐项通过即达生产级恢复能力。
