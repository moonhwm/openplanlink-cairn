# stdio传输的消息分帧规范：换行分隔JSON（NDJSON）的细节与边界

**一句话摘要**：本文逐条拆解MCP stdio绑定的NDJSON分帧规范——每行一条UTF-8编码的JSON-RPC消息——并覆盖空行、超长行、非法行、编码错误等边界情况的处理约定。

## 一、分帧规则的本体

stdio传输的分帧规范可以用一句话说完：每条JSON-RPC消息被序列化为单行UTF-8 JSON文本，以换行符（\n）结尾写入stdin/stdout；接收方以行为单位切分字节流，每行独立做一次JSON解析，解析结果即一条完整协议消息。这个选择背后有清晰的权衡：JSON对象本身没有长度前缀，而stdin/stdout是无消息边界的字节流，必须有分帧机制；备选方案里，按长度前缀分帧需要传输层预先序列化并维护二进制头部，复杂且跨语言易错；按定界符分帧则要求数据永不出现定界符——JSON序列化默认把所有控制字符（包括换行）转义为\\u000a形式，因此一行合法JSON内部不可能出现裸换行，\\n是天然安全的定界符。这就是NDJSON（Newline-Delimited JSON）风格，与JSON Lines格式同宗。

规范同时明确了宽松侧的要求：接收方应当同时接受\\n与\\r\\n两种行结束符，即解析前应剥掉行尾的\\r；发送方可以任选其一，但生态惯例是统一输出\\n。接收方还应容忍空行（strip后为空的行直接跳过，不报错），因为某些环境或包装脚本可能向管道插入空行。规范对消息大小的态度是"建议实现设置合理上限"，由实现方自行决定，典型取值从1MB到数十MB不等，超限时应当记录错误并终止连接，而不是默默丢弃。

## 二、发送侧的实现纪律

发送侧有三条纪律。第一，原子写出：一条消息的整行（含结尾换行）应当一次性写入并确保flush，避免上半行与下半行之间插入其他消息的输出——多任务并发发送时必须有全局写锁或单一写出协程。第二，紧凑或标准序列化均可，但不得开启pretty-print（多行缩进会直接破坏分帧），也不得以任何理由在JSON前后附加日志、横幅、提示文本。第三，编码必须是UTF-8且不丢失字符完整性：宽字符环境下（如Windows某些区域设置）若运行时默认用本地代码页编码，中文与emoji会变成乱码字节，接收方解析失败。发送侧还应注意Unicode转义策略的一致性：ensure_ascii=True会全量转义（安全但可读性差），False保留原字符（要求通道两端都按UTF-8处理）；两者对分帧安全性等价，因为转义与否都不影响换行的处理。

## 三、接收侧的边界处理矩阵

接收侧的状态机很简单——累积字节、找\\n、切行、strip \\r、空行跳过、JSON解析、上抛——但边界情况要逐一决断。下表给出推荐且被主流SDK遵循的处理矩阵：

- 合法JSON行：解析后立即作为消息上抛，不做跨行缓冲。
- 空行或纯空白行：静默跳过，不报错、不断连。
- 非法JSON行（语法错误）：无法构造合法的JSON-RPC错误响应（拿不到id），正确做法是写错误日志到stderr；可选择继续（容错）或关闭连接（严格）。多数实现选择继续运行并计数，超过阈值再断开。
- 行超过max_message_size：视为协议违规，返回/记录错误后关闭连接，防止内存被无界帧耗尽。
- EOF（管道关闭）：正常结束读取循环，触发连接关闭回调，不视为错误。
- 部分行残留于缓冲区且EOF到来：丢弃残留（对端写到一半死掉），按关闭处理。

## 四、参考实现与压力测试

下面是一段防御性较强的按行分帧器（TypeScript），可直接嵌入stdio传输的读写泵：

```typescript
export class LineFramer {
  private buf = "";
  constructor(
    private readonly onMessage: (obj: unknown) => void,
    private readonly maxLineBytes = 4 * 1024 * 1024,
  ) {}

  feed(chunk: string): void {
    this.buf += chunk;
    if (this.buf.length > this.maxLineBytes) {
      throw new Error("frame exceeds size limit"); // 上层据此断开
    }
    let nl: number;
    while ((nl = this.buf.indexOf("\n")) >= 0) {
      const raw = this.buf.slice(0, nl).replace(/\r$/, "");
      this.buf = this.buf.slice(nl + 1);
      const line = raw.trim();
      if (!line) continue;                 // 空行：跳过
      try {
        this.onMessage(JSON.parse(line));  // 一行一条消息
      } catch {
        // 非法行：记日志（stderr），不断流
        process.stderr.write(`bad frame dropped: ${line.slice(0, 200)}\n`);
      }
    }
  }

  end(): void { /* EOF：丢弃残包，通知关闭 */ }
}
```

验收分帧实现时建议做四组压测：其一，把一条大消息（数MB含中文与emoji）切块投喂，验证累积与切帧正确；其二，连续投喂两条消息粘在同一chunk、以及一条消息被拆进多个chunk，两种情形都要正确；其三，混入空行与含BOM的首行（BOM应被strip或至少不致崩溃）；其四，注入一行二进制垃圾字节，验证走的是日志+继续或断开路径而非抛未捕获异常。这四组用例能覆盖真实集成中九成以上的分帧类故障，是每个自研stdio传输交付前的必做项。
