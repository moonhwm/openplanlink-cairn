# Rust SDK的传输实现与tokio异步模型

**一句话摘要**：本文分析Rust生态官方rmcp SDK（modelcontextprotocol/rust-sdk）的传输设计——基于tokio的异步特质、StdioTransport与StreamableHttp/HTTP+SSE实现、axum挂载服务端端点——并讨论Rust特有的一切权、取消与背压处理。

## 一、rmcp的传输抽象与tokio底座

Rust官方SDK（crate名rmcp，由官方rust-sdk仓库维护）把传输抽象为一组与运行时绑定的trait：传输对象在建立时产出"一对通道"——发送端实现sink式接口（发送JSON-RPC消息并返回Future）、接收端是Stream<Item=JsonRpcMessage>；服务器的serve*族函数与客户端的serve_client族函数消费任意实现该形状的对象，这正是15篇自定义绑定的Rust版扩展点。官方实现族：StdioTransport以tokio::process::Command拉起子进程，stdin/stdout映射为tokio的AsyncWrite/AsyncRead，配合按行编解码器（tokio_util::codec::LinesCodec思想的JSON升级版）；HTTP侧基于reqwest（客户端）与axum（服务端），提供新版Streamable HTTP（含会话头、SSE流、DELETE）与旧版HTTP+SSE兼容。tokio的选取决定了全部工程语义：取消靠CancellationToken与drop Future（Rust的取消即丢弃，天然结构化）；并发靠JoinSet管理每连接任务；背压靠有界channel（bounded mpsc）——发送端await send在满时挂起，这正是16篇send()背压契约的地道实现。

Rust特有且值得写进设计文档的三点：其一，所有权即生命周期——transport被move进serve循环，会话句柄（Peer）以Arc克隆分发，编译器保证不存在悬挂引用，"恰好一次onclose"被类型系统近似强制；其二，Send+Sync边界——工具处理器若持有非Send状态（如某些FFI句柄），要在spawn_blocking里隔离；其三，优雅关闭——tokio的CancellationToken孩子节点构成取消树，drop根即级联，配合process的kill_on_drop(true)防孤儿子进程。

## 二、服务端挂载与客户端使用样板

```rust
// 依赖：rmcp = { features = ["server", "transport-io", "transport-streamable-http"] }
//       tokio = { features = ["full"] }  axum（HTTP形态）
use rmcp::{ServerHandler, ServiceExt, handler::server::tool::Tool, model::*,
           transport::{stdio, streamable_http::StreamableHttpServerConfig}};
use tokio::io::{stdin, stdout};

#[derive(Clone)]
struct Echo;

#[tool(tool_box)]
impl ServerHandler for Echo {
    async fn call_tool(&self, req: CallToolRequestParam,
                       _ctx: axum::extract::State<()>) -> Result<CallToolResult, McpError> {
        if req.name == "echo" {
            let text = req.arguments.as_ref()
                .and_then(|a| a.get("text"))
                .and_then(|v| v.as_str())
                .unwrap_or("").to_string();
            return Ok(CallToolResult::success(vec![Content::text(text)]));
        }
        Err(McpError::invalid_params("unknown tool", None))
    }
    async fn list_tools(&self, _req: Option<PaginatedRequestParam>,
                        _ctx: axum::extract::State<()>)
                        -> Result<ListToolsResult, McpError> {
        Ok(ListToolsResult { next_cursor: None,
            tools: vec![Tool::new("echo", "回显文本",
                serde_json::json!({"type":"object",
                    "properties":{"text":{"type":"string"}}}))] })
    }
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let service = Echo.serve(())?;      // 构建服务，工具宏自动注册
    // 形态一：stdio（被宿主拉起）
    let stdin = stdin();
    let stdout = stdout();
    let _running = service.serve(stdio(stdin, stdout))?;
    // 形态二：Streamable HTTP —— 用StreamableHttpServerConfig装到axum路由
    //   （同一二进制按参数二选一，见47篇多传输共存）
    tokio::signal::ctrl_c().await?;
    Ok(())
}
```

## 三、工程要点与陷阱

Rust侧要点清单：编解码统一走serde_json，消息类型是强模型枚举（ClientResult/ServerResult等），不要手搓Value绕开类型；子进程管理的kill_on_drop与三段式关闭（EOF→TERM→KILL）要自己补全（tokio::process默认不发送TERM梯度）；有界channel的容量即并发在途消息上限，设过小会在高并发下伪卡顿，设过大失去背压，建议按下游处理速率定；每个连接独立task加JoinSet，配合cancellation_token子节点，避免一个慢连接拖住accept循环；HTTP形态的SSE流写出要用axum的Body::from_stream，保证分块flush；日志走tracing的subscriber，stdio形态必须确认subscriber写到stderr。常见陷阱：在异步上下文调用阻塞IO（用spawn_blocking）；忘记给工具结果设is_error标志导致客户端误判成功；测试时用tokio::time::pause导致真实进程超时行为异常。

## 四、验收清单

Rust侧交付验收：stdio与HTTP双形态冒烟；kill子进程与断开TCP两类故障下服务端任务全部回收（tokio-console核对无悬挂任务）；背压压测（灌入万条消息）内存曲线平稳、通道满时发送端挂起而非丢帧；取消语义（客户端断开触发CancellationToken级联到工具Future drop）；中文emoji往返无损；Clippy与Miri（如适用）无警告；与TypeScript/Python客户端互操作冒烟通过。这份清单加tokio语义的理解，构成Rust侧MCP传输的完整交付标准。
