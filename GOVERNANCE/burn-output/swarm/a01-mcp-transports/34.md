# 大消息分块与分页：传输层对工具结果分页的配合

**一句话摘要**：本文分析MCP在传输层消息上限约束下如何搬运大结果——协议内建的分页游标（tools/list、resources/list）、blob分片读取（resources/read）、工具结果的截断与续读模式——并给出传输上限、分页参数与客户端聚合的协同实现。

## 一、传输上限是分页的第一动因

协议对单条JSON-RPC消息的体积没有规定硬性数字，但传输现实给出了多级上限：HTTP网关与Serverless平台常见1到6MB的请求体限制；SSE事件经代理缓冲时过大会被截断或拆坏；客户端UI层对单条工具结果的可渲染量也有实际边界（几十万字符的文本会让多数宿主卡顿）；内存约束下，无界消息还会被恶意或意外的调用当攻击面（见45篇限流）。因此MCP在协议层内建了两套"大结果切小"的机制，传输层与工具设计要主动配合而非硬扛。

机制一是列表分页：tools/list、resources/list、prompts/list的响应都支持nextCursor字段——服务器返回一页与"下一页游标"，客户端带cursor参数再次请求直到nextCursor为空。游标是不透明字符串，典型实现是offset的Base64、或"上次最后一条的稳定排序键"，要求列表排序在分页会话期间稳定（按名称排序比按注册序更抗抖动）。机制二是资源内容分片：resources/read返回blob，协议对超大blob没有自动分片，惯例做法是工具/资源自己提供"打开句柄+按区间读取"的成对操作（如read_file返回前N行与hasMore，continue_read带行号游标），把大对象访问变成多次小消息。工具结果（call_tool返回的content数组）同样适用该模式：截断到预算、附上truncated:true标志与续读参数。

## 二、分页实现：服务器与客户端两侧

服务器侧分页器与客户端聚合循环的实现：

```typescript
// —— 服务器侧：稳定排序 + Base64游标 ——
import { Buffer } from "node:crypto";

interface Page<T> { items: T[]; nextCursor?: string }

export function paginate<T>(all: T[], pageSize: number,
                            cursorOf: (t: T) => string,
                            reqCursor?: string): Page<T> {
  const sorted = [...all].sort((a, b) => cursorOf(a).localeCompare(cursorOf(b)));
  let start = 0;
  if (reqCursor) {
    start = sorted.findIndex(t => cursorOf(t) > reqCursor);   // 严格大于游标
    if (start < 0) start = sorted.length;                     // 游标已越过尾部
  }
  const items = sorted.slice(start, start + pageSize);
  const last = items[items.length - 1];
  const hasMore = start + pageSize < sorted.length;
  return { items,
           nextCursor: hasMore && last ? encode(cursorOf(last)) : undefined };
}
const encode = (s: string) => Buffer.from(s, "utf8").toString("base64");

// tools/list处理器：pageSize按传输上限反推（网关4MB则每页工具元数据远小之，
// 保守取50-100个/页；分页本身防的是"工具数极多的服务器"把单响应撑爆）
server.setRequestHandler("tools/list", async (req) => {
  const page = paginate(allTools(), 100, t => t.name, req.params?.cursor);
  return { tools: page.items, nextCursor: page.nextCursor };
});

// —— 客户端侧：聚合循环（带页数上限防游标死循环）——
async function listAllTools(client: { listTools: (p?: object) => Promise<any> }) {
  const acc = [];
  let cursor: string | undefined;
  for (let i = 0; i < 100; i++) {                 // 页数熔断
    const res = await client.listTools(cursor ? { cursor } : undefined);
    acc.push(...res.tools);
    if (!res.nextCursor) return acc;
    cursor = res.nextCursor;
  }
  throw new Error("pagination did not converge"); // 游标循环异常保护
}
```

## 三、工具级截断与续读模式

对call_tool的大结果，推荐"预算+句柄"双件套模式。预算侧：工具声明maxOutputTokens或maxChars（如64KB），超限时返回前缀+truncated:true标志+totalSize元数据，让调用方（LLM或用户）决定是否续读。句柄侧：提供成对的"首读/续读"参数——例如search工具返回前20条与nextPageToken，fetch_page工具用token继续；或read_resource返回首块与transferId，续读端点按transferId取后续块并在读完后失效句柄。传输层配合点有三：单帧上限统一在一个配置点（传输max_message_size），工具层从这里取预算；分片消息各自独立完整（每片都是合法JSON-RPC响应，不跨帧拼半条消息）；续读请求是普通新请求，享受正常的超时、重试与取消语义（续读是幂等读，可安全重试，与28篇分型一致）。

## 四、验收清单

分页与大消息验收清单：万级工具的服务器分页遍历完整且总消息数=页数（无隐藏的全量响应）；游标在分页期间列表发生增删时的行为可解释（跳过或重复有限，不崩溃不死循环）；客户端聚合的页数熔断被测例覆盖；工具结果超预算时truncated标志与续读参数正确往返；续读链路在任意一环断开后可重入（幂等）；网关4MB限制下的端到端压测（构造8MB级原始结果，经截断分片后全部合规通过）；每片传输含中文emoji往返无损；监控指标含分页深度分布与截断发生率。这份清单确保"大"不再成为传输层的故障源，而成为可治理的普通工作负载。
