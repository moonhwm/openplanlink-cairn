# MCP传输层总览：stdio、HTTP、SSE、WebSocket与自定义绑定的定位与分层

**一句话摘要**：本文系统梳理MCP（Model Context Protocol）传输层的整体版图，厘清四种官方及社区传输方式在进程边界、网络拓扑、消息流向与适用场景上的分工，并给出选型决策框架。

## 一、传输层在MCP协议栈中的位置

MCP是一个基于JSON-RPC 2.0的开放协议，其架构可以分为三层来看：最上层是协议语义层，定义工具（Tools）、资源（Resources）、提示词（Prompts）、采样（Sampling）等能力对象；中间是消息层，即JSON-RPC 2.0的请求、响应与通知封装；最底层则是传输层（Transport），负责把这些JSON消息在客户端与服务器之间可靠地搬运会过进程或网络边界。传输层不理解消息内容，它只关心三件事：如何建立连接、如何分帧拆帧、如何在断开后收尾或恢复。这种分层设计意味着同一个MCP服务器实现理论上可以插上不同的传输外壳而不改动业务逻辑，各语言官方SDK也正是通过抽象Transport接口来兑现这一承诺的。

需要特别强调的是，传输层的选择会反向影响协议语义的可用范围。例如流式输出（如工具执行进度的notification）依赖一个支持服务器主动推送的通道，stdio与SSE流天然具备这种双向性，而纯请求-响应式的无流式HTTP模式下，服务器只能把进度通知捎带在最终响应之前、塞进同一个SSE流或干脆放弃推送。再如会话概念，HTTP类传输需要显式的会话标识头来串联多次请求，stdio则天然以进程生命周期为会话边界。因此理解传输层不是可选的附加知识，而是正确实现与运维MCP系统的前提。

## 二、四种传输方式的定位与分工

stdio传输是最早标准化、也最简单的绑定方式：客户端把服务器作为本地子进程启动，通过其stdin写入JSON-RPC消息、从stdout读出响应，stderr留给日志与诊断。它零网络依赖、零配置、权限模型简单（继承本地用户权限），是桌面IDE、本地CLI工具和开发期集成的默认选择。其代价是每台机器都要安装运行时、无法集中托管、不适合多租户。

HTTP类传输（Streamable HTTP，2025-03-26版规范引入）面向远程服务场景：客户端向服务器单一端点（如/mcp）发POST携带JSON-RPC消息，服务器可选择立即以JSON响应，或升级为text/event-stream流式返回；客户端还可以对同一端点发GET打开一条服务器可主动推送的SSE长流。它取代了旧版HTTP+SSE双端点设计（GET /sse建立下行流、POST /message发送上行消息），并新增Mcp-Session-Id会话头、MCP-Protocol-Version版本头与Origin校验要求。SSE在这里是HTTP流式实现的具体载体，而非独立传输。WebSocket传输未被核心规范强制，但因具备全双工、低延迟、跨浏览器兼容好的特性，被大量社区运行时与自定义绑定采用，适合长生命周期高频交互场景。自定义绑定（Custom Transports）则是协议预留的逃生舱：任何满足"可靠传递完整JSON-RPC消息、能区分请求与通知"的信道都可以承载MCP，典型例子有进程内内存传输（测试用）、基于gRPC的私有绑定、跨语言桥接的传输适配器等。

## 三、选型决策框架与对比

选型时建议按以下维度逐项打分：部署拓扑（本地子进程还是跨网络）、是否需要服务器主动推送、会话时长与频率、认证要求（本地信任还是OAuth 2.1）、基础设施限制（能否维持长连接、是否经过会剥离流式的代理）。下面的清单给出速查式对比：

- stdio：适合本地开发工具、IDE插件、个人自动化；无需认证，靠文件系统权限隔离；缺点是分发运维重、无法集中升级。
- Streamable HTTP：适合云端托管、SaaS化MCP服务器、企业内多客户端共享；配合TLS与OAuth 2.1可实现完整安全链路；缺点是实现复杂度最高，需要处理会话、重连、限流。
- HTTP+SSE（旧版）：存量系统兼容用途，新实现应迁移到Streamable HTTP并保留对旧客户端握手的降级支持。
- WebSocket：适合高频双向交互、低延迟要求高的私有部署；需自行处理子协议协商与心跳，规范背书较弱。
- 自定义绑定：适合测试（内存传输）、嵌入宿主应用、与非HTTP基础设施（消息队列、gRPC网格）集成的场景。

## 四、最小代码骨架：传输与业务解耦

无论选择哪种传输，服务器核心逻辑应当保持传输无关。以TypeScript SDK为例，同一个Server对象可以搭配不同Transport启动：

```typescript
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
// import { StreamableHTTPServerTransport } from ".../server/streamableHttp.js";

const server = new Server({ name: "demo", version: "1.0.0" }, { capabilities: {} });
// ...注册tools/resources处理器，全部与传输无关...

// 本地模式：stdio绑定
const transport = new StdioServerTransport();
await server.connect(transport);

// 远程模式：换成Streamable HTTP绑定即可，业务零改动
// const httpTransport = new StreamableHTTPServerTransport({ sessionIdGenerator: () => randomUUID() });
// await server.connect(httpTransport);
```

Python侧同理：`mcp.server.lowlevel.Server`上的处理器写好后，既可以用`async with stdio_server() as (read, write)`接入标准输入输出，也可以交给`streamable_http`相关的session manager接入HTTP。这种"语义层不动、传输层可插拔"的结构，是MCP生态能同时覆盖桌面工具与云服务的关键工程决策，也是审查一个MCP实现质量时的第一检查点：凡是把业务逻辑写死在某个传输的回调里、导致无法换绑定的实现，都应视为架构缺陷。
