# 服务器端并发处理：多客户端连接下的传输隔离

**一句话摘要**：本文研究MCP服务器同时服务多个客户端时的传输隔离工程——每连接独立状态与缓冲、共享资源的并发治理、慢客户端防御、广播通知的一致性，以及并发压测与验收清单。

## 一、隔离单元：会话即沙箱

多客户端并发的第一原则：每条连接（stdio进程实例、HTTP会话、WS连接）是一个隔离单元，协议态与缓冲都必须按连接私有。具体包括：每会话独立的读写泵任务（一个连接的读取阻塞不影响其它）、独立的消息缓冲与分帧状态（缓冲绝不可共享，否则帧串台）、独立的在途请求表（id配对按会话命名空间）、独立的取消令牌树（断开只级联本会话任务）、独立的限流计数器。可共享的是无状态的单例资源：工具注册表、配置、连接池——但访问要按只读对待，运行期变更（动态注册工具）要考虑读写锁或不可变替换（copy-on-write快照）。隔离失效的典型症状是"客户端A偶尔收到B的响应"——几乎必然是某处共享了发送缓冲或事件分发队列，定位思路是审计一切跨会话可达的可变结构。

隔离的第二层含义是资源配额：每会话设置最大在途并发请求（如16）、最大单消息大小、最大SSE流背压缓冲（如256KB）；服务器全局设置最大并发连接、最大总在途请求。配额不是可选优化而是生存必需——没有配额的单慢客户端（读了10字节就停）能把无界的推送缓冲撑爆整个进程。

## 二、共享资源与广播的并发治理

服务器主动广播（如工具列表变更通知）是并发最微妙的场景。要点：广播要做"每会话复制"，绝不能把同一个队列对象挂到多个会话（回到串台问题）；对满配额的会话，广播的丢弃策略要明确——通知类可安全丢弃（客户端可轮询补偿），响应类绝不能丢（等价于请求永远悬挂），因此推送管道要区分"可靠通道"（响应）与"尽力通道"（通知）并分级处理；广播顺序在同一会话内必须一致（列表变更通知与列表快照响应不能颠倒），实现上每会话一个单写者队列即可保证。共享的下游资源（数据库连接池、文件句柄）用池化+每会话公平配额（如每会话最多占2连接）防独占；工具处理器的并发度用信号量限制，超限排队并设置排队超时返回繁忙错误而不是无限等。

## 三、每会话隔离的服务器骨架

以下TypeScript骨架展示会话对象、私有队列与配额的组装方式：

```typescript
import { randomUUID } from "node:crypto";

interface Session {
  id: string;
  sendQueue: Promise<void>;              // 单写者链：顺序写出
  inflight: Map<number | string, unknown>; // 本会话在途请求表
  notifyBuf: unknown[];                  // 尽力通道缓冲（有界）
  permits: number;                       // 本会话并发许可
  cancelled: AbortController;            // 断开级联取消
}

const MAX_SESSIONS = 500;
const PER_SESSION_INFLIGHT = 16;
const PER_SESSION_PERMITS = 8;
const sessions = new Map<string, Session>();

export function admitSession(): Session | null {
  if (sessions.size >= MAX_SESSIONS) return null;      // 全局配额：拒绝接入
  const s: Session = { id: randomUUID(), sendQueue: Promise.resolve(),
    inflight: new Map(), notifyBuf: [], permits: PER_SESSION_PERMITS,
    cancelled: new AbortController() };
  sessions.set(s.id, s);
  return s;
}

// 会话内发送：串行化写链 + 有界通知缓冲
export function enqueue(s: Session, msg: unknown, reliable: boolean): void {
  if (!reliable) {
    if (s.notifyBuf.length >= 256) {
      s.notifyBuf.shift();               // 通知可丢：丢最旧并计数告警
    }
    s.notifyBuf.push(msg);
    return;                              // 由泵异步搬运
  }
  s.sendQueue = s.sendQueue.then(() => writeFrame(s, msg)); // 可靠：入写链
}

// 广播：逐会话复制，永不共享队列
export function broadcast(msg: unknown): void {
  for (const s of sessions.values()) enqueue(s, { ...msg }, false);
}

// 会话终结：级联取消 + 在途请求统一回填传输错误
export function releaseSession(s: Session): void {
  sessions.delete(s.id);
  s.cancelled.abort();                   // 触发本会话任务树取消
  for (const [id] of s.inflight)
    failPending(s, id, new Error("session closed")); // 对齐16篇onclose语义
}

async function withPermit<T>(s: Session, fn: () => Promise<T>): Promise<T> {
  if (s.inflight.size >= PER_SESSION_INFLIGHT)
    throw new Error("too many concurrent requests");
  return fn(); // 简化示意；生产用信号量+排队超时
}
```

## 四、并发验收清单

压测与验收清单：千连接压测下内存有界（每会话对象图固定大小）；一连接故意慢读，其它连接的P99延迟不受影响（隔离验证）；广播风暴（每秒千条通知）下响应类消息零丢失、通知按策略丢弃有计数；并发同id请求（异常客户端）不破坏配对表；会话断开瞬间其在途请求全部收到失败回调且任务回收（无泄漏句柄/定时器）；全局与每会话两级配额触发时返回明确错误（429或-32029类资源不足语义）；动态工具注册时并发list_tools读到一致快照；两客户端同时调用共享资源的工具时池配额公平。通过这份清单的服务器，才算真正具备多租户并发素质，单机支撑数千并发会话是这类设计正常发挥的结果。
