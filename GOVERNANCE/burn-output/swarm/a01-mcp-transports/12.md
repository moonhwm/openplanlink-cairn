# SSE传输的GET流建立、endpoint事件与断线重连

**一句话摘要**：本文以旧版HTTP+SSE绑定与Streamable HTTP的GET流为对象，讲透下行流的建立时序、endpoint事件（旧版）与message事件的约定、心跳保活，以及带退避与恢复的断线重连实现。

## 一、GET流的建立时序与首事件契约

旧版HTTP+SSE绑定的连接时序是有严格次序的协议契约：客户端发起GET /sse请求（携带Accept: text/event-stream），服务器返回200与事件流响应头后，必须在发送任何其他事件之前先发送endpoint事件——data为一个相对或绝对URI，指示本会话的上行消息端点。客户端必须以收到的第一个endpoint事件为准，在它到来之前不得POST任何消息（包括initialize）。这一契约的深层原因是上行端点与下行流是配对资源：服务器为这条SSE连接分配了会话态，endpoint URI就是把这些态"命名"并交给客户端的凭据。若客户端在endpoint之前抢先POST，消息会因找不到关联流而被拒或丢弃。Streamable HTTP的GET流则宽松得多：端点已知（与POST同址），首事件没有特殊类型，流上直接跑message事件；GET只是可选的推送通道，客户端不等它也能完成initialize，服务器甚至可以405拒绝GET。

两种形态下的通用纪律包括：事件流响应头一旦发出（200+text/event-stream）就不可反悔为普通JSON响应；流中每个message事件的data是恰好一条JSON-RPC消息；服务器应周期发送注释行（:ping）作为应用层心跳，因为TCP的keepalive不足以让中间层（云LB、nginx缺proxy_read_timeout配置时）保持转发路径，30秒级的心跳是通行做法。

## 二、断线的类型学：该重连还是该重建

处理断线前先分型。型一，物理闪断：网络抖动、代理重启，服务器会话仍在。型二，服务器回收：会话超时或服务器重启，会话已不存在。型三，协议性断开：服务器主动关闭（如发送了致命错误）。对型一，正确动作是重连：旧版重新GET /sse并重新等待endpoint事件（旧端点URI通常含会话参数，多数实现允许直接续会）；新版Streamable HTTP的GET流重连时携带Mcp-Session-Id与Last-Event-ID请求恢复事件重放。对型二，重连必然失败（404或新会话），应升级为重新initialize并重放订阅。对型三，不应盲目重连，先读取关闭前的错误事件再决定。重连的退避策略遵循指数加抖动：初始间隔数百毫秒，按1.5到2倍递增，封顶如30到60秒，叠加随机抖动避免大量客户端同步重连形成风暴（thundering herd）。

## 三、带退避与恢复的重连实现

以下TypeScript代码实现一个可复用的SSE重连管理器，覆盖分型与退避：

```typescript
export class SSEConnector {
  private attempt = 0;
  private stopped = false;
  private lastEventId = "";

  constructor(private opts: {
    url: string;
    headers: () => Record<string, string>;  // 会话头/版本头动态取
    onEvent: (e: { event: string; data: string; id?: string }) => void;
    onSessionLost: () => void;              // 升级为重新initialize
  }) {}

  start() { this.stopped = false; this.connect(); }

  stop() { this.stopped = true; this.ctrl?.abort(); }

  private backoff(): number {
    const base = Math.min(30000, 500 * 2 ** this.attempt++); // 指数
    return base / 2 + Math.random() * base / 2;              // 抖动
  }

  private async connect() {
    while (!this.stopped) {
      this.ctrl = new AbortController();
      try {
        const res = await fetch(this.opts.url, {
          headers: { accept: "text/event-stream",
                     ...(this.lastEventId ? { "last-event-id": this.lastEventId } : {}),
                     ...this.opts.headers() },
          signal: this.ctrl.signal,
        });
        if (res.status === 404 || res.status === 410) {
          this.opts.onSessionLost();   // 型二：会话没了，交给上层重初始化
          return;
        }
        if (!res.ok || !res.body) throw new Error(`sse ${res.status}`);
        this.attempt = 0;             // 成功建立即重置退避
        await this.pump(res);
        // 正常return（服务器关流）也落入catch路径之外：视为型一/三，重连
      } catch (e) {
        if (this.stopped) return;
      }
      await new Promise(r => setTimeout(r, this.backoff())); // 型一：退避重连
    }
  }

  private async pump(res: Response) {
    const parser = new SSEParser(ev => {
      if (ev.id) this.lastEventId = ev.id;      // 记住恢复点
      this.opts.onEvent(ev);                     // endpoint/message/自定义
    });
    const reader = res.body!.getReader();
    const dec = new TextDecoder();
    for (;;) {
      const { done, value } = await reader.read();
      if (done) return;
      parser.feed(dec.decode(value, { stream: true }));
    }
  }

  private ctrl?: AbortController;
}
```

## 四、重连语义核对清单

交付重连逻辑时按清单验证：endpoint事件只在旧版流程中作为首事件被等待，新版GET流不依赖它；重连成功后退避计数归零；连续失败达到上限（如10次）后有熔断或上报，而非无限重试；404/410正确触发重初始化而不是死循环重连；Last-Event-ID被服务器忽略（不支持重放）时客户端仍能继续工作；重连期间发出的上行POST按传输规则处理（旧版会在无流时失败排队，新版无此耦合）；并发重连被抑制（同一时刻只有一条在途重连）；停止语义干净——用户主动断开后不再有残留定时器。这份清单配合分型决策，覆盖了SSE载体在MCP远程连接中几乎全部的可用性工程。
