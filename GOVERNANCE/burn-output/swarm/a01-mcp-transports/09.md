# Streamable HTTP的会话管理：Mcp-Session-Id的生成、续用与失效

**一句话摘要**：本文完整梳理Streamable HTTP的会话机制——服务器在initialize后签发Mcp-Session-Id、客户端在后续所有请求中携带、超时或DELETE后失效、410触发重新初始化——并讨论无状态与有状态两种服务器形态的实现取舍。

## 一、会话头的设计动机与签发规则

HTTP本身是无状态协议，而MCP会话是有状态的：initialize协商出的版本与能力、订阅关系、通知上下文、可能还有业务态都要跨请求延续。Streamable HTTP为此设计了Mcp-Session-Id头：服务器在成功处理initialize请求后，在其响应中返回该头（对JSON响应放在HTTP响应头，对SSE流响应同样放在流的HTTP响应头上），值为一个不透明字符串，推荐使用密码学随机数（如UUIDv4），长度建议不超过128字符且仅含可见ASCII以避免头注入问题。从此刻起，该客户端发出的每个后续请求（POST、GET、DELETE）都必须原样携带这个头，服务器据此定位会话上下文。规范特别强调会话id是不透明标识：客户端不得解析其内部结构、不得推断语义，只能保存与回传。

签发侧有几条容易踩错的细则：其一，只有initialize会触发签发，其余请求带不带旧id都不签发新的；其二，无状态服务器可以选择完全不实现会话（不返回该头），客户端必须容忍这一点——没收到会话头就不必在后续请求中携带，这也正是Serverless形态的用法；其三，会话id必须难以预测，防止攻击者猜测他人会话id进行劫持，同时服务器应校验会话与来源（结合Origin校验与认证主体绑定）的对应关系，仅"知道id"不应自动等于"获得全部权限"，若绑定认证则不同主体携带同一id应被拒绝。

## 二、续用与失效：超时、404/410与DELETE

会话的生命周期规则形成一个小状态机。活跃期：客户端正常携带id请求，服务器命中会话并服务。过期边界：服务器可对空闲会话设置超时（时长由实现自定，从几分钟到数天皆可），超时后清理会话；客户端随后携带失效id请求时，服务器应返回404（会话不存在/已终止）。规范同时允许返回410 Gone表达"会话已终结"语义，主流SDK按404处理缺失会话；客户端收到404/410时，正确动作是自动重新走initialize握手（获取新会话id、重新协商能力、重放必要的订阅请求），而不是向用户直接报错——这一自动恢复路径是长跑客户端健壮性的关键。主动终止：客户端结束使用时应对端点发DELETE并携带会话id，服务器清理资源并以204/200确认；服务器也可以在检测到滥用时主动作废会话（例如在响应中不再保证后续可用，直接让下一请求404）。

客户端还要处理"半个会话"的边界：initialize已发出但响应还没回来时连接断开——此时没有会话id，只能整体重试initialize；携带会话id的GET长流断开重连时，必须继续带同一id（必要时加Last-Event-ID恢复事件流），绝不能重新initialize导致旧会话泄漏。服务器侧则要防止会话表无限膨胀：对每个会话记录最后活跃时间，后台定期清扫过期项；对同一会话的并发请求加适当的锁或采用无锁的按key路由，保证上下文修改不竞态。

## 三、服务器侧会话管理的参考实现

下面是一段带超时清扫的有状态会话管理器骨架（TypeScript）：

```typescript
import { randomUUID } from "node:crypto";

interface Session {
  id: string;
  protocolVersion: string;
  lastSeen: number;
  ctx: Map<string, unknown>;      // 业务上下文（订阅、缓存等）
}

const IDLE_TIMEOUT_MS = 30 * 60 * 1000; // 30分钟空闲即过期
const sessions = new Map<string, Session>();

export function createSession(version: string): Session {
  const s: Session = { id: randomUUID(), protocolVersion: version,
                       lastSeen: Date.now(), ctx: new Map() };
  sessions.set(s.id, s);
  return s;
}

export function touchSession(id: string | undefined): Session | null {
  if (!id) return null;
  const s = sessions.get(id);
  if (!s) return null;
  s.lastSeen = Date.now();
  return s;
}

// 每分钟清扫一次空闲会话，防止表膨胀与资源泄漏
setInterval(() => {
  const now = Date.now();
  for (const [id, s] of sessions) {
    if (now - s.lastSeen > IDLE_TIMEOUT_MS) sessions.delete(id);
  }
}, 60_000).unref();

// 请求中间件：未命中即404，提示客户端重新initialize
export function sessionMiddleware(req, res, next) {
  if (req.body?.method === "initialize") return next(); // 握手无需会话
  const s = touchSession(req.header("mcp-session-id"));
  if (!s) return res.status(404).json({ error: "session not found" });
  (req as any).session = s;
  next();
}

// DELETE /mcp：客户端主动终结
export function handleDelete(req, res) {
  const id = req.header("mcp-session-id");
  sessions.delete(id ?? "");
  res.status(204).end();
}
```

## 四、验收清单与互操作注意点

会话功能验收按清单执行：initialize响应确实返回Mcp-Session-Id且为高熵随机值；后续无id请求被404拒绝（有状态形态）；携带错误id得到404/410而非500；DELETE后会话立即失效；空闲超时后会话被清理且下一请求得到404；无状态形态不返回会话头且客户端照常工作；客户端在404后能自动重新初始化并恢复功能；同一id来自不同认证主体时被拒绝（若部署了认证）。互操作层面还要注意：某些早期客户端把会话头误当可选导致会话被频繁重建——服务器侧应记录会话创建速率指标以便发现；反向地，服务器若把会话头放在SSE事件流内部而非HTTP响应头，标准客户端将读不到，属于实现错误。把这些规则固化为回归用例，会话层就能长期稳定运行。
