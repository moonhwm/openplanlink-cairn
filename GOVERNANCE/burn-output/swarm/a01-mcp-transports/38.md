# 负载均衡与粘性会话：多实例MCP服务器的传输要求

**一句话摘要**：本文分析多实例部署下MCP传输对负载均衡的要求——有状态会话的三种拓扑（粘性路由、会话外置、无状态化）、LB健康检查与分配策略、扩缩容与滚动更新时的会话迁移，并给出决策矩阵与配置要点。

## 一、会话语义决定LB拓扑

多实例MCP集群的负载均衡设计由会话语义一票决定（延续18篇的三形态）。形态甲，无状态Streamable HTTP：任何实例可应答任何请求，LB可做最简单的轮询/最少连接，无需粘性——代价是无推送与反向请求能力。形态乙，有状态+粘性路由：会话仍在实例内存，LB保证同一会话的请求落到同一实例（源IP哈希、cookie哈希或一致性哈希）；实现简单、延迟最优，代价是负载可能倾斜（长会话堆积在某实例）、实例下线即会话蒸发。形态丙，有状态+会话外置：会话上下文存Redis类共享存储，实例无差别读写，LB任意分配；彻底解耦扩缩容与可用性，代价是每请求一次存储往返与序列化成本，且SSE长流仍需"谁持有流谁负责"的归属规则（事件经pub/sub广播或由会话主实例写流）。选择矩阵：需要服务器主动通知/elicitation → 乙或丙；实例数频繁伸缩 → 丙（或甲）；团队运维简单优先 → 乙起步、预留丙的演进；Serverless/FaaS → 只能甲。旧版HTTP+SSE与WS绑定天然落在乙（连接与实例绑定），扩容时要按连接数而非CPU分配，必要时前置一层连接网关做连接归集。

## 二、LB层配置要点

粘性的实现细节决定可靠性。源IP哈希在经过代理/NAT的流量下会把大量客户端折叠为少数key（同一出口IP），负载严重倾斜，仅适合纯内网无代理场景；cookie哈希最稳——LB在首个响应种cookie、后续按cookie路由，但要注意Streamable HTTP的initialize响应是POST，确认LB支持对该路径种cookie（部分LB只对GET种）；更可控的方案是应用层粘性：服务器在initialize响应头回Mcp-Session-Id的同时额外回一个路由提示（如实例编号cookie），LB按它路由，会话头本身保持协议语义不被污染。健康检查要用独立于协议端点的/healthz（36篇），并区分就绪与存活；摘除策略要给在途流宽限期（connection draining），否则长SSE流被硬切。分配策略上，最少连接优于轮询（MCP会话的请求密度差异大）；对WS/长流实例设连接数上限，超限直接503让LB绕开。grpc场景（自定义绑定）需LB支持gRPC健康协议与L7哈希，另按42篇认证链考虑。

```nginx
# Nginx粘性路由（cookie哈希）示意
upstream mcp_pods {
    hash $cookie_mcp_affinity consistent;      # 一致性哈希：摘节点只迁移小部分会话
    server pod1:8080 max_conns=2000;           # 每实例连接上限
    server pod2:8080 max_conns=2000;
    server pod3:8080 max_conns=2000;
    keepalive 64;
}
server {
    location /mcp {
        proxy_pass http://mcp_pods;
        proxy_http_version 1.1;
        proxy_buffering off;
        proxy_read_timeout 300s;
        # 应用在initialize时种下mcp_affinity；LB只认cookie，不碰会话头
        add_header Set-Cookie $upstream_cookie_mcp_affinity always; # 透传应用种的亲和值
    }
}
```

## 三、扩缩容与滚动更新的会话迁移

缩容与滚动更新是多实例会话事故高发区，正确剧本分四步：第一步，预摘除——实例进入terminating前先从LB的Endpoint摘除（K8s的preStop睡眠就是买这段窗口）；第二步，宽限在途——对长流给固定宽限期（如30秒），期间已建立流继续服务、新连接不再到来；第三步，会话处置按形态：乙形态直接终结（客户端404后重握手到新实例，短抖动可接受）、丙形态把会话所有权交还共享存储（最后写回+发布离开消息）、甲形态无感；第四步，验证收敛——确认该实例连接数归零再退出。扩容则相对安全（新实例只接新会话），但一致性哈希环变更仍会重分布一部分cookie哈希会话——用consistent参数把迁移比例压到最小，或干脆用"会话id到实例"的注册表路由（实例启动时注册、下线时注销）彻底避免重分布。另一个必测项是"实例崩溃"路径：持有千条会话的实例断电，LB应秒级摘除、客户端重连与重握手形成二次洪峰——重连要有28篇的退避抖动，否则重启实例立刻被洪峰再打死。

## 四、验收清单

多实例交付验收：粘性正确性——千次请求带同会话头，落点实例唯一（甲形态除外）；哈希倾斜压测——长会话堆积场景下实例间连接偏差在阈值内；实例缩容时在途SSE流按宽限期自然收尾、新请求零落点错误；实例崩溃注入后客户端恢复时间符合SLA且无重连风暴（退避生效）；扩容后新会话分布均匀；健康检查摘除早于进程退出（无"摘除前的请求黑洞"窗口）；会话外置形态下流归属明确（同一会话的事件不会从两个实例交错写出）；全部链路的事件级到达（35篇）在LB后复核。这份清单是多实例MCP服务上生产前的总演习，配合形态决策矩阵，负载均衡层就不再是黑箱。
