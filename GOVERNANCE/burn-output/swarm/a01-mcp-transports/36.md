# 容器化部署MCP服务器的传输选择：Docker与Kubernetes网络

**一句话摘要**：本文讨论MCP服务器容器化后的传输层适配——stdio进程与容器边界的关系、HTTP端点在Docker网络与K8s Service/Ingress下的暴露方式、健康检查与优雅下线、以及Pod生命周期对会话的影响与配置清单。

## 一、stdio与容器的错配：三种正确姿势

stdio绑定的前提是"客户端能拉起服务器进程"，这在容器世界产生错配：容器是隔离进程空间，宿主客户端无法直接spawn容器内进程。三种正确姿势化解。姿势一，客户端进容器：把宿主与MCP客户端（IDE等）一起容器化，或MCP客户端本身跑在容器里，stdio照旧在容器内成立——CI环境与云端开发容器（DevContainer）的标准做法。姿势二，stdio转HTTP适配器：在容器里同时跑一个极小的桥接进程，对外暴露HTTP、对内用stdio连接服务器进程，等于在容器内自带11篇的双栈形态；社区有现成工具承担该角色，自建则复用SDK双传输即可。姿势三，直接HTTP形态：容器化部署的最自然选择，服务器原生监听HTTP，传输选择回到第06篇语义。错误姿势也要点名：用docker exec或nsenter从宿主把stdin接进容器——脆弱且不可移植，仅限调试。

容器内stdio还有两个细节：环境变量注入用容器env而非宿主环境（敏感变量经编排层Secret挂载，容器内进程按最小集读取，呼应43篇纪律）；进程退出的容器语义——stdio服务器进程退出即容器退出，宿主客户端要能读到非零退出码与stderr尾部（19篇诊断缓冲在DevContainer场景依然生效，日志走docker logs）。

## 二、HTTP形态的容器网络暴露

Docker单机形态要点：容器内服务器必须监听0.0.0.0（不是127.0.0.1——容器内的回环不是宿主的回环），宿主经-p 8080:8080端口映射访问；Origin校验按10篇基线但要注意"可信来源"现在包括宿主与映射链路上的调用方，不要因为容器化就关掉校验。K8s形态的分层：Pod内服务器监听容器端口（如containerPort 8080）；Service做四层负载（ClusterIP内网用、NodePort/LB对外）；Ingress做七层——此时第35篇的全部流式兼容配置（缓冲、超时、粘性）作用在Ingress controller上，且必须逐项落实。多副本Deployment与有状态会话的矛盾是K8s场景的核心议题：Streamable HTTP的会话默认在Pod内存里，副本扩缩与滚动更新都会让会话漂移到不持有它的Pod。解法三选一：会话外置（18篇Redis方案，任意Pod可续）；粘性路由（Ingress按cookie哈希把同一会话固定到Pod，nginx-ingress的session-cookie注解）；无状态形态（放弃推送类能力）。选型写进部署文档并联动38篇负载均衡篇。

## 三、清单与探针

```yaml
# K8s Deployment清单要点（示意）
apiVersion: apps/v1
kind: Deployment
metadata: { name: mcp-server }
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: mcp
        image: registry.internal/mcp-server:1.4.2
        args: ["serve", "--http", "--addr=0.0.0.0:8080"]  # 监听全接口
        ports: [{ containerPort: 8080, name: http }]
        env:
        - name: MCP_SESSION_BACKEND
          value: redis://session-svc:6379      # 会话外置（18篇方案）
        readinessProbe:                        # 就绪探针：握手级健康
          httpGet: { path: /healthz, port: 8080 }
          periodSeconds: 5
        lifecycle:
          preStop:                             # 优雅下线：先摘流再退出
            exec: { command: ["/bin/sh", "-c", "sleep 10"] }
        resources:
          requests: { cpu: 100m, memory: 128Mi }
          limits:   { cpu: "1",  memory: 512Mi }
      terminationGracePeriodSeconds: 30
---
apiVersion: v1
kind: Service
metadata: { name: mcp-svc }
spec:
  selector: { app: mcp-server }
  ports: [{ port: 80, targetPort: 8080 }]
```

探针设计要点：readiness探针用独立的/healthz路径而非/mcp（避免探针POST制造协议层会话垃圾，GET /mcp会命中405造成误报）；启动慢的服务器配startupProbe给冷启动窗口；preStop睡眠配合terminationGracePeriod让在途流与长连接在Endpoint摘除后自然收尾，配合客户端重连形成无损滚动更新。

## 四、验收清单

容器化交付验收清单：容器内监听0.0.0.0且Origin校验仍生效（伪造Origin经映射访问被403）；stdio姿势一（全容器）与姿势三（HTTP）各自冒烟通过；经Service+Ingress的SSE事件级到达正常（35篇清单在Ingress层复核）；滚动更新期间旧会话按选定方案存活或被显式终结（404触发客户端重握手，绝不悬挂）；Pod OOMKill后重启与客户端恢复路径符合预期；日志与stderr统一采集（k8s下stdout不再是协议通道，风险解除但stdio姿势仍要守纪）；镜像内不含任何凭据文件，Secret经env挂载且不落入日志；NetworkPolicy按最小暴露面收紧（仅Ingress与所需后端可达）。通过后，MCP服务器就获得了云原生部署的全部通行证。
