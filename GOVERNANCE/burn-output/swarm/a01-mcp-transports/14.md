# WebSocket的保活：ping/pong心跳与超时策略

**一句话摘要**：本文专门研究MCP-over-WebSocket绑定的保活工程——为什么TCP keepalive不够、ping/pong控制帧的节奏设计、无响应判死的超时矩阵、代理环境下的双层心跳，以及可直接复用的心跳器实现。

## 一、为什么必须做应用层心跳

WebSocket长连接面对三类"静默死亡"：其一，中间设备（NAT网关、云负载均衡、企业防火墙）普遍对空闲TCP连接设置回收定时器（常见60到350秒不等），到期直接丢表项，连接在两端看来仍"开着"，但数据再也到不了对端——这就是著名的半开连接问题；其二，网络切换（WiFi到蜂窝、VPN重连）会静默改变路径，旧连接成为黑洞；其三，对端进程假死（死锁、GC风暴）时TCP层完好但应用不再响应。TCP自带的keepalive理论上可探测，但默认探测间隔以小时计、且常被运维策略禁用，更关键的是它探测不到中间设备回收的路径（对端TCP栈仍会代答）。因此RFC 6455提供了协议层的ping（opcode 0x9）/pong（0xA）控制帧：ping可携带至多125字节载荷，接收方必须在合理时间内回pong且载荷原样返回；这一机制穿透NAT刷新转发表、触发假死检测，是WS绑定的保活标准答案。SSE与HTTP流没有等价控制帧，所以那边用注释行做心跳——机制不同，目的相同：让"连接还活着"成为可观测、可判定的事实。

## 二、心跳节奏与超时矩阵设计

心跳参数要在三组矛盾间取平衡：频率高则探测快、但耗电耗流量并加剧服务器负担；频率低则省资源、但半开连接滞留久。工程上通行的起点参数是：客户端每20秒发一次ping；对端pong应在5秒内到达；连续3次miss（即约60秒无pong）判定死亡并触发重连。服务端策略可以稍宽松（30秒间隔、3到5次容忍），因为服务端通常要服务海量连接，心跳开销乘以连接数不可小觑。此外要设计完整超时矩阵，把"等待pong""读空闲""写空闲""握手存活"分列治理。建议的矩阵如下：

- ping间隔：客户端20s、服务端30s（双向都发时错开相位，避免同步抖动）。
- pong超时：5s未回记一次miss；miss阈值3次判死。
- 读空闲上限：60s内无任何入帧（数据帧或控制帧）即可判死，不必等满miss计数。
- 判死后动作：terminate（发RST立即断）而非close（可能卡在关闭握手），随后按分型重连。
- 重连成功后：立即重发一条应用层ping或业务消息，验证新路径双向可用。
- 移动/弱网场景：间隔放大到45到60s，miss阈值提高到5次，减少误杀。
- 服务器保护：对单连接ping速率限频（如每秒不超过1个），畸形控制帧直接close(1002)。

## 三、心跳器的参考实现

以下TypeScript心跳器封装了上述矩阵，可挂到任何ws连接上：

```typescript
export class WsHeartbeat {
  private misses = 0;
  private timer?: NodeJS.Timeout;
  private lastInbound = Date.now();

  constructor(
    private readonly ws: { ping: (d?: Buffer) => void; terminate: () => void },
    private readonly opts = { intervalMs: 20_000, pongTimeoutMs: 5_000,
                              maxMisses: 3, idleKillMs: 60_000 },
    private readonly onDead?: (reason: string) => void,
  ) {}

  /** 收到任何帧（pong/数据/close都要调用） */
  inbound(): void { this.misses = 0; this.lastInbound = Date.now(); }

  start(): void {
    this.timer = setInterval(() => {
      // 1) 读空闲兜底：即使miss未满，长期无入帧也判死
      if (Date.now() - this.lastInbound > this.opts.idleKillMs) {
        return this.kill("read idle");
      }
      // 2) miss计数：超阈值判死
      if (this.misses >= this.opts.maxMisses) {
        return this.kill("pong missed x" + this.misses);
      }
      // 3) 发探测并等pong窗口
      this.misses++;
      this.ws.ping();
    }, this.opts.intervalMs);
    this.timer.unref?.();
  }

  stop(): void { if (this.timer) clearInterval(this.timer); }

  private kill(reason: string): void {
    this.stop();
    this.ws.terminate();          // 判死用terminate：不走可能卡住的关闭握手
    this.onDead?.(reason);
  }
}

```

## 四、部署验证与排障清单

上线前按清单验证保活链路：把客户端置于严格NAT环境（或用tc/netem模拟丢包）观察60秒内能否可靠判死与恢复；在nginx（proxy_read_timeout默认60s会砍空闲WS）配置proxy_read_timeout 300s或确保心跳小于该值；云LB（如ALB的idle_timeout）同样对齐心跳间隔；确认心跳不承载业务语义——ping载荷可以放时间戳用于RTT观测，但不得用它传JSON-RPC内容；服务器对未按协议回pong的客户端要有宽容（有的库自动回pong，有的封装吞掉），以读空闲兜底而不是仅靠miss计数。排障速查：连接每60秒规律断开=中间设备空闲回收，降心跳间隔；连接假死不被发现=只有ping没有pong监测，补pong钩子；服务器CPU周期性尖峰=海量连接心跳同步，给间隔加随机抖动。心跳看似琐碎，却是WS绑定从"能通"到"可靠"的分水岭。
