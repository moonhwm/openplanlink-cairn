# 传输层与能力协商：initialize握手中的传输相关能力

**一句话摘要**：本文解析MCP initialize握手中与传输行为相关的能力字段——logging、roots、sampling、elicitation、completion等能力如何受传输特性影响、客户端与服务器如何声明与降级，以及握手时序对传输实现的约束。

## 一、initialize握手时序与传输的关系

MCP连接的建立遵循固定的三步握手：客户端发送initialize请求，参数携带protocolVersion、capabilities（客户端能力对象）、clientInfo（名称与版本）；服务器返回result，同样携带capabilities（服务器能力）与serverInfo，并回定最终协议版本；客户端随后发送notifications/initialized通知，宣告初始化完成，此后双方进入正常消息交互阶段。传输层与这个时序有多处耦合：其一，Streamable HTTP在initialize的响应头签发会话id，因此客户端实现里"会话id的保存"必须挂在initialize响应处理完成这个时点，而不是连接建立时；其二，initialize之前服务器原则上应拒绝其它方法（返回-32002错误码表示"服务器等待initialize"），传输层的首个POST特殊放行；其三，initialized通知之后客户端才能发起tools/list、resources/read等调用，服务器也才能发起依赖客户端能力的请求——能力协商的结果决定了谁可以发什么，传输两侧的分发器都要据此守门。

能力对象的结构是"能力名到配置的映射"，例如客户端声明{ "roots": { "listChanged": true }, "sampling": {}, "elicitation": {} }表示支持文件根目录列表（且自身列表可变）、支持采样、支持引导式问答；服务器声明{ "tools": { "listChanged": true }, "logging": {} }表示提供工具（列表可推送变更）与日志。字段缺省即"不支持"，绝不代表"支持默认值"——这是协商语义的关键，收发双方都必须按显式声明行事。

## 二、传输特性如何影响能力可用性

能力与传输之间存在实在的制约关系，实现者要按传输形态预判哪些能力可用。roots与elicitation、sampling都要求"服务器能向客户端发请求"，在stdio与WS这类全双工绑定上天然可行；在Streamable HTTP上则依赖POST响应流或GET长流捎带服务器请求——若服务器不支持任何流（纯无状态形态），它就绝不能声明sampling与elicition能力，否则运行期发起的请求将无处投递。logging能力同理：服务器日志通知要经下行通道推送，无下行能力的传输下声明logging是自相矛盾。listChanged系列（工具列表变更通知）也依赖服务器主动通知通道。归纳成矩阵：能力声明必须与传输可提供的下行/上行通道匹配；反过来，客户端在选择降级传输（如关闭GET流）时，要理解它会连带失去部分服务器侧能力或使服务器行为退化（例如工具列表只能轮询）。

另一个实际影响协商的是批量与分页参数：tools/list与resources/list支持分页游标（cursor），这是消息层能力，但传输层的消息大小上限会影响服务器选择每页大小——严格限制单帧的传输（网关4MB限制）应主动缩小页面，能力协商虽不管页面，实现却要联动。

## 三、握手与能力检查的实现示例

以下TypeScript片段展示客户端侧的握手序列与协商后的能力检查：

```typescript
interface Caps { [k: string]: Record<string, unknown> | undefined }

async function initialize(t: { send: (m: unknown) => Promise<void> },
                          request: (m: string, p: object) => Promise<any>) {
  // 1) 客户端声明自己的真实能力：不多报、不虚报
  const clientCaps: Caps = {
    roots: { listChanged: true },   // 愿意提供根目录且列表可变
    sampling: {},                   // 愿意处理sampling/createMessage
    elicitation: {},                // 愿意处理elicitation/create
  };

  const res = await request("initialize", {
    protocolVersion: "2025-06-18",
    capabilities: clientCaps,
    clientInfo: { name: "demo-client", version: "0.1.0" },
  });

  // 2) 记录服务器能力：后续调用前先检查对应能力是否存在
  const serverCaps: Caps = res.capabilities ?? {};

  // 3) 完成握手第三步：initialized通知（无id，无响应）
  await t.send({ jsonrpc: "2.0", method: "notifications/initialized" });

  return {
    version: res.protocolVersion,      // 服务器最终选定版本（可能不同于请求值）
    canCallTools: !!serverCaps.tools,
    toolsMayChange: !!serverCaps.tools?.listChanged, // 决定是否订阅变更通知/轮询
    serverMaySample: !!serverCaps.sampling || undefined,
  };
}

// 使用：调用前守门，避免-32601式运行期失败

// if (!meta.toolsMayChange) schedulePolling("tools/list"); // 无变更通知则轮询
```

## 四、协商纪律与验收清单

握手实现要遵守的纪律清单：客户端不得在initialize之前发送其它请求或通知；服务器在握手完成前收到业务请求应返回明确错误（规范错误码-32002）而非崩溃；capabilities字段不认识时必须整体忽略未知键（向前兼容），绝不能因为出现新能力而拒绝连接；版本回定后，后续消息都按该版本语义解释，Streamable HTTP还须每请求用头复核；重连后（新会话）必须重新握手与重新协商，旧能力缓存全部作废；serverInfo/clientInfo仅作展示与诊断，不得用于功能开关判断。验收用例至少覆盖：双方能力全空时基本工具流仍可用；服务器声明listChanged后确实推送通知且客户端刷新列表；客户端未声明sampling时服务器调用采样被客户端以能力错误拒绝；协议版本不一致时按降级路径继续或明确断开。这份纪律是互操作性的地基，值得固化为每次发版前的回归集。
