# 传输层安全：TLS终止、mTLS与证书管理

**一句话摘要**：本文构建MCP远程传输的通道安全体系——TLS终止的位置选择、mTLS双向认证在零信任内网的落地、证书的签发轮换与校验配置、以及从stdio信任模型到HTTP强信任模型的对照与验收清单。

## 一、信任模型先行：本地与远程的安全基线不同

MCP官方安全指引把传输按暴露面分两类。本地传输（stdio、回环HTTP）：信任边界是操作系统用户——子进程继承用户权限，协议层无需认证，防护重点是10篇的DNS重绑定与最小环境注入。远程传输（任何监听非回环的HTTP/WS）：网络即敌境，基线是TLS加密+OAuth 2.1认证（42篇）+Origin校验。通道安全（本篇）回答"字节在链路上是否机密完整、端点身份是否可信"，它排在认证之前：明文HTTP上做token认证等于把凭据广播给链路监听者。因此远程部署的第一决策是TLS拓扑：在哪里终止TLS。

三种拓扑各有位置。拓扑一，应用直挂证书：服务器自己监听https，证书管理全在应用内——简单直接，适合单实例；代价是证书轮换要重启或热加载逻辑，且私钥落应用进程（暴露面大）。拓扑二，边缘终止：LB/Nginx/Ingress终结TLS，回源用内网明文或再加密——运维最顺（证书集中管理、ACME自动续期），是K8s标准形态；回源段若跨信任域必须二次加密。拓扑三，服务网格mTLS：Sidecar间自动双向TLS与身份（SPIFFE类），应用零改动获得零信任内网——治理成本最高但内网链路默认加密。选择矩阵：公网服务→拓扑二起步；跨可用区/跨企业内网回源→拓扑二+回源加密或拓扑三；高合规要求（金融、医疗数据工具）→拓扑三。

## 二、mTLS与证书工程

mTLS把"服务器证明自己"升级为"双方互证"，适合服务器对服务器（代理到上游、网关到工具集群）与设备客户端场景。落地三件事：签发（内部CA或云PCA给每个工作负载发短周期证书，SAN里放身份标识如URI spiffe://tenant/mcp-gateway）、校验配置（要求客户端证书、指定CA链、深度校验SAN而非仅CN）、轮换（短周期证书如24小时自动换发，避免长期吊销清单负担）。Nginx侧的双向配置与应用侧Node的示例：

```nginx
# 边缘mTLS：客户端证书强制
server {
    listen 443 ssl http2;
    server_name mcp.internal;
    ssl_certificate     /etc/certs/server.pem;        # 由内部CA签发，运维体系轮换
    ssl_certificate_key /etc/certs/server.key;
    ssl_client_certificate /etc/certs/internal-ca.pem;
    ssl_verify_client on;                              # 强制客户端证书
    ssl_verify_depth 2;
    location /mcp {
        proxy_pass http://127.0.0.1:8080;              # 本机回环回源可明文
        proxy_buffering off;
        proxy_read_timeout 300s;
        proxy_set_header X-Client-Cert-Dn $ssl_client_s_dn; # 身份透传给应用做授权
    }
}
```

```typescript
// Node服务器侧自挂TLS（拓扑一）——注意：证书路径来自部署配置，代码不落任何材料
import https from "node:https";
import fs from "node:fs";

const server = https.createServer({
  cert: fs.readFileSync(process.env.TLS_CERT_PATH!),   // 路径由编排层注入
  key: fs.readFileSync(process.env.TLS_KEY_PATH!),
  // 双向校验（自建mTLS时）：
  ca: fs.readFileSync(process.env.TLS_CA_PATH!),
  requestCert: true, rejectUnauthorized: true,
  minVersion: "TLSv1.2",                               // 现代基线，禁老协议
}, app);
server.listen(8443);
```

证书工程清单：私钥权限最小化（0600、独立服务账户）；自动轮换（ACME或内部CA流水线，到期前双证书重叠部署）；校验侧固定信任锚（内部CA证书随配置分发，不做运行时下载）；吊销路径演练（CRL/OCSP或短周期自然过期策略）；TLS配置基线（TLS1.2+、现代cipher套件、HSTS于公网、会话票据轮换）；WS场景用wss且升级请求同样落在TLS上。

## 三、stdio→HTTP的信任迁移陷阱

把一个stdio服务器改成远程HTTP时有一批系统性陷阱要主动排雷：原代码假设"调用者=本机用户=全权限"，远程化后必须引入认证与按主体授权（42篇）；原来经环境变量注入的凭据，改造成按会话的主体动态取凭据（避免所有远程用户共享同一个高权限身份）；原来对参数的隐式信任（用户手工敲的）不成立，远程输入要按不可信处理（45篇限流与输入上限）；文件系统路径类的工具暴露到公网前要做路径白名单。对照检查表：每工具一行"远程化风险+缓解措施"，作为迁移评审的必过项。

## 四、验收清单

通道安全验收清单：nmap/tlsmap扫描仅见预期协议与套件，无明文端口残留；证书链完整（中间证书齐全，避免部分客户端信任失败）；到期监控与自动轮换演练通过（换证不中断服务，长连接在旧证书上继续到自然关闭）；mTLS场景无证书客户端被拒、伪造CA签发被拒、过期证书被拒三类负向用例；回环场景的Origin防护仍然开启（TLS不替代10篇）；代理链每跳的加密状态写入文档并经抓包抽验（关键链路tcpdump确认无明文JSON-RPC）；WS升级同样在TLS内。这份清单配合42篇的认证层，构成远程MCP传输的完整安全闭环。
