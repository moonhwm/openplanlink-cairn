# WebSocket传输：RFC 6455帧、子协议协商与MCP-over-WS实践

**一句话摘要**：本文讲解以WebSocket承载MCP的完整实践——HTTP升级握手、Sec-WebSocket-Protocol子协议协商、帧类型与文本帧承载JSON-RPC、与官方传输的适配层设计，以及在何种场景下WS优于HTTP流。

## 一、WebSocket承载MCP的定位与握手

WebSocket（RFC 6455）并未被MCP核心规范列为标准传输，但它是社区与私有部署中最常见的自定义绑定之一：连接一经建立即成为全双工、低开销（无逐请求HTTP头）、消息边界天然保留（每帧一条消息）的双向通道，非常契合MCP的JSON-RPC全双工语义——客户端与服务器都能随时发请求与通知，不需要像HTTP那样为服务器推送单开流。建立连接走HTTP升级：客户端发起GET请求，携带Upgrade: websocket、Connection: Upgrade、Sec-WebSocket-Key等头；服务器返回101 Switching Protocols并给出Sec-WebSocket-Accept完成握手，此后该TCP连接改说WebSocket帧协议。MCP-over-WS的通行约定是：全部JSON-RPC消息使用文本帧（opcode 0x1）传输，一帧一条完整消息，不做跨帧拼接；二进制帧保留不用于协议；initialize握手照常作为第一条应用层消息发送。

子协议协商是WS独有的规范化能力：客户端在握手头Sec-WebSocket-Protocol中列出支持的子协议，服务器择一回显（不回则视为无子协议）。MCP社区实践里可以用它做两件事：一是声明mcp类子协议与版本（例如mcp/v2、或带日期版本的标识），让同一端口同时服务不同协议族；二是网关据子协议路由。注意协商规则：服务器只能回显客户端列出的值之一，不得发明新值；客户端若强制要求子协议而服务器未回显，应当断开。握手之外，HTTP层还能携带认证头或cookie，使得WS绑定可以复用现有网关的认证体系，这也是企业内网常选WS的原因之一。

## 二、帧层要点与连接管理

帧层需要实现者留意的要点：其一，控制帧——close（0x8）是优雅关闭信号，收到后应回close再断TCP；ping（0x9）/pong（0xA）承担保活与活性探测，约定每20到30秒ping、对端必须尽快pong，连续若干次无pong判死并触发重连。其二，分片——大消息可被发送方拆成continuation帧序列（首帧opcode非0、后续opcode为0），接收方必须支持重组；每帧重组后整体做JSON解析，MCP消息上限仍由应用层设置。其三，掩码——客户端到服务器的帧必须掩码，服务器到客户端不得掩码，这是协议安全设计，库已处理但自研帧层时不可弄错。其四，关闭码——1000正常关闭、1001端点下线、1002协议错误、1006异常断开（无close帧），重连逻辑可按关闭码分型处理（对应上篇的分型学）。

## 三、MCP-over-WS的适配层实现

把WS管道适配到官方SDK的Transport接口只需要实现start/send/close/onclose四个成员。以下以TypeScript的ws库为例：

```typescript
import WebSocket from "ws";
import { Transport } from "@modelcontextprotocol/sdk/shared/transport.js";
import { randomUUID } from "node:crypto";

export class WsClientTransport implements Transport {
  private ws?: WebSocket;
  onclose?: () => void;
  onerror?: (e: Error) => void;
  onmessage?: (msg: unknown) => void;

  constructor(private url: string, private subprotocol = "mcp") {}

  async start(): Promise<void> {
    return new Promise((resolve, reject) => {
      this.ws = new WebSocket(this.url, [this.subprotocol], {
        headers: { "x-client-id": randomUUID() }, // 可携带网关认证头
      });
      this.ws.on("open", () => resolve());
      this.ws.on("error", reject);
      this.ws.on("message", (data, isBinary) => {
        if (isBinary) return;                 // 二进制帧不属于MCP协议
        try { this.onmessage?.(JSON.parse(data.toString("utf-8"))); }
        catch { /* 非法帧：记日志并跳过 */ }
      });
      this.ws.on("close", () => this.onclose?.());
      // 心跳：20s ping，3次未pong判死
      let misses = 0;
      this.ws.on("pong", () => (misses = 0));
      const t = setInterval(() => {
        if (++misses > 3) { clearInterval(t); this.ws?.terminate(); }
        else this.ws?.ping();
      }, 20_000);
      this.ws.on("close", () => clearInterval(t));
    });
  }

  async send(msg: unknown): Promise<void> {
    if (this.ws?.readyState !== WebSocket.OPEN)
      throw new Error("transport not connected");
    this.ws.send(JSON.stringify(msg));        // 一帧一条JSON-RPC消息
  }

  async close(): Promise<void> {
    this.ws?.close(1000, "client shutdown"); // 优雅关闭：先close帧
    await new Promise(r => this.ws?.on("close", r));
  }
}
```

## 四、选型核对与场景建议

采用WS绑定前按清单核对：是否真的需要全双工低延迟（高频双向交互、实时协作类工具收益最大；一问一答为主的工具用Streamable HTTP更省心）；基础设施链路（LB空闲超时、代理 Upgrade头透传、wss TLS终止）是否就绪；认证方案（握手头、cookie或首条auth消息）与网关兼容；子协议命名是否避免与其它业务冲突并纳入版本策略；心跳与重连是否覆盖（ping/pong加指数退避重连，会话态由应用层恢复）；文本帧+单帧单消息的约定写入双方文档。场景建议归纳：公网开放服务优先Streamable HTTP（规范背书、防火墙友好）；企业内网高频交互与已有WS网关的体系，WS绑定开发与运维成本最低；浏览器直连场景两者皆可，WS的浏览器API成熟度略占优。按此决策，WS成为MCP传输版图中可控且好用的一块拼图。
