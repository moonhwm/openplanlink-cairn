# JSON-RPC 2.0消息模型与MCP传输层的职责边界

**一句话摘要**：本文剖析JSON-RPC 2.0的三类消息（请求、响应、通知）如何在MCP中被序列化与搬运，划清消息层与传输层各自的职责边界，并说明传输实现必须遵守的不变量。

## 一、JSON-RPC 2.0消息模型回顾

MCP的所有协议交互都编码为JSON-RPC 2.0消息。该模型只有三种报文：请求（Request）携带jsonrpc、id、method、params四要素，id可以是字符串或数字但不能为null，用于将来的响应配对；响应（Response）要么带id+result，要么带id+error，error对象包含code、message与可选data；通知（Notification）与请求结构相同但省略id，语义上是"发后不管"，绝不引发任何回复。MCP在此之上定义了自己的方法命名空间，如initialize、tools/call、notifications/initialized、progress等，并用保留的error code区间（如-32600无效请求、-32601方法不存在、-32602参数无效、-32603内部错误，以及MCP自定义的负数区间）表达协议层错误。

传输层对这套模型的正确性负有底层责任。第一个不变量是保序：JSON-RPC依赖id配对而非顺序，但MCP的许多通知（如初始化完成通知、取消通知）在语义上与先前请求存在因果关系，传输不应无理由重排同一连接内的消息。第二个不变量是完整性：一条JSON-RPC消息必须作为不可分割的单元递交上层，任何分帧错误都会产生无法解析的半截报文。第三个不变量是双向性：客户端与服务器都能在各自方向上发送全部三类消息（服务器也可以向客户端发请求，例如sampling/createMessage、roots/list），因此传输必须是全双工逻辑通道，哪怕物理上是HTTP这种半双工协议。

## 二、传输层的职责清单与反职责

一个合格的MCP传输实现应当只做以下事情：建立物理或逻辑连接；把上层递交的JSON对象序列化并按传输自身的分帧规则写出；从对端读取字节流、按分帧规则切分、反序列化为JSON对象并上抛；在连接关闭时通知上层并清理资源；可选地提供会话标识、重连恢复等增值能力。传输层不应当做：解析method字段并据此路由（那是Server/Client分发器的职责）、合并或拆分JSON-RPC消息、缓存业务状态、静默吞掉无法解析的消息（应当报协议错误或关闭连接）、对id做去重之外的语义解释。

实践中最常见的边界越界发生在"批量消息"上。JSON-RPC 2.0规范允许把多条消息放进数组作为批处理发送，但MCP规范明确不支持批量（batching），传输与上层都不应发送数组形式的报文；收到批量的实现可以返回-32600错误。另一个常见误区是把HTTP状态码与JSON-RPC错误混为一谈：在HTTP传输中，传输层自身的失败（如404端点不存在、405方法不允许、会话失效410）用HTTP状态码表达，而业务与协议层面的失败必须用HTTP 200携带JSON-RPC error对象表达，两层错误机制不可互相替代。

## 三、分帧与序列化的工程细节

stdio绑定的分帧规则是"每条消息一行"：以换行符分隔的UTF-8 JSON文本，读写双方都要容忍\r\n与\n两种行结束符，且消息内部不得包含裸换行（JSON序列化器默认转义控制字符，天然满足）。HTTP绑定的分帧由HTTP本身承担：请求体即一条完整JSON，或Content-Type为text/event-stream时按SSE事件分帧。下面是一段符合规范的stdio分帧读写核心逻辑：

```python
import sys, json, asyncio

async def read_messages(reader: asyncio.StreamReader):
    # 每行一条JSON-RPC消息；严格逐行分帧，不猜测、不拼接
    while True:
        line = await reader.readline()
        if not line:
            return  # EOF：对端关闭，结束读取循环
        text = line.decode("utf-8").strip()
        if not text:
            continue  # 容忍空行，跳过即可
        try:
            yield json.loads(text)
        except json.JSONDecodeError:
            # 半截报文或非法JSON：写错误日志，但不向对端回包
            # （无法得知id，无法构造合法JSON-RPC错误），可选择断开
            print("unparseable frame", file=sys.stderr)

async def write_message(writer: asyncio.StreamWriter, msg: dict):
    # ensure_ascii=False保留可读性；单行写出且必须以\n结尾
    data = json.dumps(msg, ensure_ascii=False, separators=(",", ":")) + "\n"
    writer.write(data.encode("utf-8"))
    await writer.drain()
```

这段代码体现了三个细节：readline天然按\n切分但需strip处理\r；解析失败的帧不能回JSON-RPC错误（因为拿不到合法id），只能记日志；写出时必须原子地写完整行并flush，避免半行被对端读到。

## 四、验证传输实现的检查清单

交付或评审一个传输实现时，建议按此清单逐项验收：其一，三类消息是否都能双向收发，尤其服务器发起的请求是否能经该传输抵达客户端并被应答；其二，是否拒绝JSON数组批量消息；其三，超长消息是否有上限保护（防止恶意对端发送无界大帧耗尽内存，建议设一个明确的max_message_size并返回错误后关闭）；其四，id配对是否完全交给上层，传输不缓存id；其五，关闭语义是否完备——主动close、对端关闭、底层异常三种路径都会触发onclose回调且只触发一次；其六，UTF-8与转义处理是否正确，含中文与emoji的参数能否往返无损；其七，并发写入是否有互斥保护，两条并发消息不得交错成一行。通过这份清单的传输，才能安全地承载上层MCP语义。
