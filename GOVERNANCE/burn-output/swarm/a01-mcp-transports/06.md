# Streamable HTTP传输：单端点模型与MCP-Protocol-Version头

**一句话摘要**：本文解析2025-03-26版MCP规范引入的Streamable HTTP传输——客户端向服务器单一端点POST JSON-RPC消息、响应可为纯JSON或SSE流——并重点说明MCP-Protocol-Version头的协商语义与实现要点。

## 一、从双端点到单端点：传输模型的重构

Streamable HTTP对旧的HTTP+SSE绑定做了一次根本性简化：全部交互收敛到服务器暴露的单一MCP端点（例如https://host/mcp，路径由服务器自定，客户端从配置或发现机制获知）。客户端的每个JSON-RPC消息都作为HTTP POST发出，Content-Type为application/json，请求体即一条完整消息。服务器的响应有两种形态：其一，直接以application/json返回一条JSON-RPC响应（适合无需流式的同步调用）；其二，以Content-Type: text/event-stream返回一条SSE流，流中先捎带若干通知（如进度、日志），最后以一个包含对应响应的事件收尾，随后即可关闭流。此外，客户端可以对端点发GET且Accept: text/event-stream，请求打开一条长生命周期的服务器推送流，服务器用它主动下发请求与通知（比如elicitation、资源变更通知）；服务器也可以对无流可推的GET直接返回405，表示该服务器不支持主动推送，客户端不得视为致命错误。DELETE方法则用于显式终止会话。

这个模型的优雅之处在于"端点合一、语义分层"：上行永远走POST，下行既可以搭POST响应的便车（响应流），也可以走GET长流，从而把旧绑定"GET建流+POST发消息"的两条腿合并成一条可裁剪的路径。无状态服务器甚至可以完全不支持GET流与session，退化成最朴素的"POST一问一答"，这让把MCP服务器接到Serverless函数、CDN边缘Worker这类难维持长连接的基础设施上成为可能。

## 二、MCP-Protocol-Version头：版本携带与协商规则

Streamable HTTP引入了专属的协议版本头MCP-Protocol-Version，其规则简洁而严格：客户端在初始化握手完成之后发出的所有HTTP请求，都必须携带该头，值是initialize握手时协商出的协议版本字符串（形如2025-03-26、2025-06-18）。服务器用它防止版本漂移——握手时说好用某版本，后续请求却按另一个版本的语义发来（例如中途改用新版本的字段），服务器检测到不匹配应返回410 Gone或400，提示客户端重新初始化。服务器自己也可以在SSE事件流或响应头中回带该字段，向客户端声明实际使用的版本。握手之前的第一个initialize请求自然无法携带已协商版本，规范允许客户端带上自己期望的版本，服务器若不支持可以返回410并可通过响应指示支持的版本，由客户端降级重试。

版本协商的完整链条是：客户端POST initialize（params.protocolVersion写客户端期望版本）；服务器在result.protocolVersion中返回自己最终选择的版本——若支持客户端版本则原样返回，否则返回自己支持的版本，客户端收到不同版本后要么接受并按该版本继续，要么判定不兼容断开。此协商结果被缓存为会话级事实，后续每个请求的MCP-Protocol-Version头都必须与之一致。实现侧要特别注意：版本字符串比较必须是精确匹配而非语义化版本排序，"2025-03-26"与"2025-06-18"之间没有大小关系，只有等与不等。

## 三、请求-响应形态的最小实现

下面给出一个无状态Streamable HTTP服务器的骨架（TypeScript，仅展示POST路径），体现JSON响应与SSE响应的双形态：

```typescript
import express from "express";
const app = express();
app.use(express.json({ limit: "4mb" }));

const PROTOCOL_VERSION = "2025-06-18";

app.post("/mcp", async (req, res) => {
  // 1) 校验版本头（首个initialize请求除外）
  const clientVer = req.header("mcp-protocol-version");
  const isInitialize = req.body?.method === "initialize";
  if (!isInitialize && clientVer !== PROTOCOL_VERSION) {
    return res.status(400).json({ error: "protocol version mismatch" });
  }

  // 2) 同步可完成 -> 纯JSON响应
  const result = await dispatch(req.body);
  if (!result.streaming) {
    return res.status(200).json(result.response); // 一条JSON-RPC响应
  }

  // 3) 需要流式 -> 升级为SSE：先推通知，最后推响应事件
  res.status(200).set({
    "content-type": "text/event-stream",
    "cache-control": "no-cache",
    connection: "keep-alive",
  });
  for (const note of result.notifications) {
    res.write(`event: message\ndata: ${JSON.stringify(note)}\n\n`);
  }
  res.write(`event: message\ndata: ${JSON.stringify(result.response)}\n\n`);
  res.end();
});

app.get("/mcp", (req, res) => res.status(405).end()); // 无状态服务器可拒绝长流
```

## 四、实现核对清单

交付Streamable HTTP端点时按此清单核对：POST只接受application/json单条消息（收到数组批量应拒绝）；响应形态二选一且Content-Type准确；SSE流中每个事件的data都是完整JSON-RPC消息；GET流不支持时返回405而非404（避免客户端误判端点错误）；所有非initialize请求强制校验MCP-Protocol-Version并精确匹配；会话服务器需校验Mcp-Session-Id（见后文专篇）；错误分清层次——传输层问题用HTTP状态码（400/404/405/406/410/429/500），业务层问题用HTTP 200包JSON-RPC error；正确处理客户端AbortSignal带来的请求取消（中断SSE流并触发上层取消通知）。这份清单与官方SDK行为对齐，是跨实现互操作的验收基线。
