# 有状态与无状态MCP服务器：传输选择对会话语义的影响

**一句话摘要**：本文对比有状态（会话式）与无状态（请求式）两种MCP服务器形态在会话语义、能力范围、基础设施适配上的差异，说明Streamable HTTP如何让同一协议覆盖从Serverless到长连接全谱系，并给出两种形态的实现要点与决策清单。

## 一、两种形态的语义分野

有状态服务器把"一次MCP连接"视为一段有生命周期的会话：initialize协商出的版本与能力、工具订阅关系、通知上下文、采样对话挂起项，乃至业务层的工作区状态都锚定在会话上；后续每个请求都必须能映射回这段上下文，Streamable HTTP用Mcp-Session-Id头承载这个映射，stdio则直接以进程为会话。无状态服务器则不维护任何跨请求记忆：每个POST自包含一切所需信息，处理完即忘，理论上可以由集群中任意实例应答；它在Streamable HTTP里的表现是initialize不签发会话id（或客户端不携带），每个请求都独立处理。两种形态的能力边界由此分岔：有状态才能支持服务器主动通知（列表变更、日志推送）、elicitation与sampling（需要在既有连接上反向请求）、以及资源订阅；无状态形态下这些能力全部退化——服务器没有通道也没有语境向客户端发起任何主动交互，只能老老实实做"请求-应答"。

会话语义还决定了错误恢复路径：有状态会话丢失（超时、重启、负载均衡漂移）时客户端必须重新initialize并重建语境（重新订阅、重新拉列表），这是协议里404/410触发重新握手规则的来源；无状态连接根本没有"丢失"概念，每个请求自生自灭，唯一的失败模式是单请求失败重试。

## 二、基础设施适配谱系

传输与会话形态的组合覆盖了整条部署谱系。stdio=天然有状态（进程即会话），适合本地。Streamable HTTP+会话=云端有状态服务，需要粘性路由或共享会话存储来支撑多实例。Streamable HTTP+无会话=Serverless/边缘友好，函数实例处理单个POST即返回，冷启动与水平伸缩都无关会话约束，代价是没有推送与反向请求。WebSocket/长SSE=强有状态，连接本身就是会话载体，实例与连接绑定，扩缩容按连接数。旧版HTTP+SSE=强有状态且连接依赖重，是被Streamable HTTP取代的主要对象。值得强调的是"有状态但可恢复"的中间态：服务器把会话上下文外置到Redis等共享存储，多实例+粘性路由失效后任意实例可凭会话id恢复服务——这是大集群下的主流折中，工程要点是会话数据的序列化边界要清晰（能存协议态，不要试图序列化业务线程）。

## 三、两种形态的服务器骨架对比

以下代码并排展示两种形态的最小实现差异（TypeScript伪码）：

```typescript
// —— 形态A：无状态（Serverless友好）——
app.post("/mcp", express.json(), async (req, res) => {
  const msg = req.body;                       // 每请求自包含
  if (msg.method === "initialize") {
    // 无会话：不返回mcp-session-id；能力声明里不写listChanged等推送项
    return res.json({ jsonrpc: "2.0", id: msg.id, result: {
      protocolVersion: PROTO, capabilities: { tools: {} }, // 无listChanged
      serverInfo: { name: "stateless", version: "1" } } });
  }
  const result = await handleIsolated(msg);   // 不读任何跨请求缓存
  res.json(result);                           // 始终JSON应答，无流
});

// —— 形态B：有状态（外置会话存储+粘性路由兜底）——
app.post("/mcp", express.json(), async (req, res) => {
  if (req.body.method === "initialize") {
    const sid = randomUUID();
    await redis.set(`mcp:sess:${sid}`, JSON.stringify(
      { v: PROTO, caps: req.body.params.capabilities, subs: [] }),
      { EX: 1800 });                          // 30分钟TTL=会话空闲超时
    res.header("mcp-session-id", sid);
    return res.json(buildInitResult());
  }
  const sid = req.header("mcp-session-id") ?? "";
  const raw = await redis.get(`mcp:sess:${sid}`);
  if (!raw) return res.status(404).json({ error: "session expired" }); // 触发客户端重握手
  const sess = JSON.parse(raw);
  const out = await handleWithContext(sess, req.body);  // 读改写上下文
  await redis.set(`mcp:sess:${sid}`, JSON.stringify(out.sess), { EX: 1800 });
  maybeStream(res, out);                      // 可选择SSE流携带通知/响应
});
```

两段代码的关键差异点：A不签发会话头、能力集收缩、应答永远纯JSON；B签发会话、外置存储、404语义驱动重连、可选流式。同一套工具处理逻辑（handleIsolated与handleWithContext调用的业务函数）完全共享，会话只是包在外面的壳。

## 四、选型决策清单

按以下清单决断形态：是否需要服务器主动推送（列表变更、日志、进度）——需要则有状态或每次请求走流；是否有elicitation/sampling需求——有则有状态；客户端是浏览器短会话还是长驻进程；部署目标是VM、K8s还是FaaS；多实例扩缩容时能否接受粘性路由或外置会话的复杂度；单请求体积与延迟预算（无状态倾向每请求重拉配置，要评估重复开销）。实现验收则按：无状态形态在随机轮换实例的LB下全功能通过；有状态形态会话过期后客户端404自动重握手；会话TTL、空闲清扫、DEL显式终结三者行为一致；能力声明与会话形态匹配（无状态不声明推送类能力）；监控指标区分"会话数"与"在途请求数"。把形态选择当作架构决策记录下来，后续演进（例如从无状态升级为有状态以获得通知能力）就有了清晰的改造路线图。
