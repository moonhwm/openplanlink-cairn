# 传输层防滥用：限流、并发上限与DoS缓解

**一句话摘要**：本文给出MCP传输层的防滥用工程——令牌桶与并发闸的实现选点（边缘vs应用）、分级限流维度（IP/会话/主体/方法）、无界资源攻击面（慢连接、大消息、连接洪水）的针对性缓解，以及压测验证清单。

## 一、滥用面盘点：MCP服务器会被怎么打

公网（甚至内网）MCP端点的滥用面分四类。类一，请求洪水：高频tools/call耗尽CPU或下游配额——经典DoS，靠限流治理。类二，无界资源占用：超大单消息（数百MB的JSON撑爆解析内存）、超长SSE/WS连接堆积（每连接对象图+缓冲）、慢速读取客户端（背压堆积，33篇）、高频initialize制造会话垃圾——靠上限治理。类三，昂贵工具滥用：个别工具单次调用代价高（全文检索、大模型推理），频率不高也能打爆预算——靠按工具配额与排队治理。类四，协议混淆攻击：畸形帧、非法JSON-RPC结构、批处理数组、伪造会话id扫描——靠严格解析与快速失败治理。缓解要在两层布防：边缘层（LB/网关：IP级连接与速率限制、消息体大小上限）挡住最粗暴的流量；应用层（会话/主体/方法粒度）做精细与公平的配额。只做一层都会被另一维度绕过。

## 二、分级限流的维度与算法

维度选择按"惩罚精确度"排序：认证主体（sub）最公平——42篇拿到的principal是最佳限流键；会话id次之（未认证时）；客户端IP再次（经代理要取X-Forwarded-For且可伪造，仅作粗筛）；方法粒度叠加（initialize与list类便宜、call_tool按工具权重计费）。算法上，令牌桶适合速率控制（突发容忍可调），并发闸（信号量）适合在途控制，固定窗口简单但边界突刺，滑动窗口日志精确但耗内存——实用组合是：边缘IP用固定窗口粗筛、主体用令牌桶、昂贵工具用"信号量+队列超时"。超限响应规范：429带Retry-After头（39篇），负载样式返回而非裸断连接（给客户端28篇的重试逻辑正确信号）。

```typescript
import express from "express";

class TokenBucket {
  private tokens: number; private last = Date.now();
  constructor(private cap: number, private refillPerSec: number) {
    this.tokens = cap;
  }
  take(n = 1): boolean {
    const now = Date.now();
    this.tokens = Math.min(this.cap,
      this.tokens + ((now - this.last) / 1000) * this.refillPerSec);
    this.last = now;
    if (this.tokens >= n) { this.tokens -= n; return true; }
    return false;
  }
}

const buckets = new Map<string, TokenBucket>();          // 按主体/会话
const bucketOf = (k: string) => {
  if (!buckets.has(k)) buckets.set(k, new TokenBucket(30, 5)); // 突发30，每秒补5
  return buckets.get(k)!;
};

const inflight = { count: 0, limit: 64 };                 // 全局在途闸
const toolCost: Record<string, number> = { "search_all": 8, "generate": 5 };

export function rateLimit(req: express.Request, res: express.Response,
                           next: express.NextFunction) {
  const key = (req as any).principal?.sub
           ?? req.header("mcp-session-id") ?? req.ip ?? "anon";
  const method = req.body?.method ?? "";
  const cost = method === "tools/call"
    ? (toolCost[String(req.body?.params?.name)] ?? 1) : 1;

  if (inflight.count >= inflight.limit) {                 // 在途闸：保护并发
    res.status(429).header("Retry-After", "2").json({ error: "server busy" });
    return;
  }
  if (!bucketOf(key).take(cost)) {                        // 令牌桶：保护速率
    res.status(429).header("Retry-After", "1").json({ error: "rate limited" });
    return;
  }
  inflight.count++;
  res.on("finish", () => inflight.count--);               // 含异常路径的归还
  next();
}

// 应用挂载顺序：body大小上限 -> 认证 -> 限流 -> 会话 -> 分发
// app.use(express.json({ limit: "4mb" }));  // 无界消息的硬上限（第4类防线）
```

## 三、无界资源与协议混淆的缓解

慢连接治理：每会话写缓冲上限+超限断开（33篇分级策略的"断开"档）、SSE/GET流空闲超时、单客户端最大并发流数、全局连接数闸（29篇MAX_SESSIONS）。会话垃圾治理：initialize失败率与新建会话速率单独限流（正常客户端每分钟 initialize 次数应接近零，突然升高即攻击或客户端bug信号）、未完成握手的"半会话"短超时清理（10秒没完成握手即回收）。大消息治理：body大小上限（如4MB）在网关与应用双层设、分帧传输的max_line保护（04篇）、超大分页请求的页深限制（34篇）。协议混淆治理：非法JSON直接400、批量数组拒绝（02篇）、非法方法名与方法不存在快速返回、畸形头（会话id超长、含控制字符）直接拒绝。所有快速失败路径要保证不抛未捕获异常——防御代码自己成为崩溃点是常见的讽刺性事故。

## 四、压测与治理清单

防滥用验收清单：限流用例——正常客户端不受影响、超限方收到429加Retry-After、令牌按权重扣减（贵工具一次扣多点）；洪水压测——十倍峰值QPS下P99劣化可控、无内存爬升、正常会话可用性达标（差异化生存）；慢速攻击模拟——慢读客户端被超限断开而非拖垮缓冲；半会话洪水——未握手连接在短超时内清理；大消息——超限请求413/400而非OOM；畸形协议样本回归集（非法JSON、批量、错结构、超长头）全部快速失败；限流键的公平性——一个坏客户端不能吃光全局限额饿死他人（主体级桶验证）；所有429路径的日志含键摘要与计数（不含敏感参数）。治理上把限额表做成配置并按观测（37篇指标）定期校准，防滥用即从静态补丁进化为闭环运营。
