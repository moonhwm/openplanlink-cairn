# Go生态的MCP传输实现与net/http集成

**一句话摘要**：本文梳理Go生态的MCP实现版图——官方modelcontextprotocol/go-sdk的传输设计与community/mark3labs等库的取舍——聚焦net/http标准库做Streamable HTTP端点、os/exec做stdio、http.Flusher做SSE流的惯用法，并给出可运行的挂载示例与验收清单。

## 一、Go生态的传输实现版图

Go侧目前是官方SDK（github.com/modelcontextprotocol/go-sdk）与多个社区库并存的格局。官方go-sdk的传输形状与其它语言一致：Transport接口（Start/Send/Close加回调）配StdioTransport（os/exec拉子进程、scanner按行切帧）、Streamable HTTP与旧版SSE的实现（客户端基于net/http.Client，服务端以http.Handler形态提供，可直接挂进任意mux）；jsonrpc2子包承担消息编解码。社区库如mark3labs/mcp-go走"高层框架"路线（server.MCPServer加工具注册API），传输同样覆盖stdio与SSE/Streamable HTTP，封装更厚、定制点略少。选型上：追求与规范同步与最小依赖选官方SDK；要快速搭带提示词模板、会话钩子的高层API可用社区库，两者在传输语义上都应满足第06-09篇的矩阵，验收清单因此通用。

Go做传输层的天然优势是标准库完备：SSE流只需http.ResponseWriter加Flusher接口（每次写事件后Flush()即推给客户端），子进程管道就是os/exec的StdinPipe/StdoutPipe，无需第三方依赖即可拼出全部绑定；goroutine模型让"每连接一个读泵+一个写泵"直白无魔法，背压用带缓冲channel配合select实现。

## 二、net/http挂载Streamable HTTP端点

以下用官方go-sdk风格展示端点挂载与手工SSE流写出的惯用法：

```go
package main

import (
    "context"
    "encoding/json"
    "fmt"
    "net/http"

    "github.com/modelcontextprotocol/go-sdk/mcp"
)

func main() {
    server := mcp.NewServer(&mcp.Implementation{Name: "go-demo", Version: "1.0"}, nil)
    mcp.AddTool(server, &mcp.Tool{Name: "echo", Description: "回显文本"}, echoHandler)

    // Streamable HTTP端点：SDK提供Handler，可直接挂任意mux
    mux := http.NewServeMux()
    mux.Handle("POST /mcp", server.StreamableHTTPHandler(nil))
    mux.Handle("GET /mcp", server.StreamableHTTPHandler(nil))
    mux.Handle("DELETE /mcp", server.StreamableHTTPHandler(nil))

    // 手工SSE流的惯用法（自定义传输/诊断页可用）：
    mux.HandleFunc("GET /events", func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Content-Type", "text/event-stream")
        w.Header().Set("Cache-Control", "no-cache")
        flusher, ok := w.(http.Flusher)
        if !ok { http.Error(w, "stream unsupported", 500); return }
        for i := 0; ; i++ {
            select {
            case <-r.Context().Done(): // 客户端断开：靠ctx取消收尾
                return
            case <-time.After(20 * time.Second):
                fmt.Fprintf(w, ": keepalive\n\n") // 注释行心跳
                flusher.Flush()
            case ev := <-someEventChan:
                b, _ := json.Marshal(ev)
                fmt.Fprintf(w, "event: message\ndata: %s\n\n", b)
                flusher.Flush()
            }
        }
    })

    http.ListenAndServe("127.0.0.1:8080", mux) // 回环默认，公网需TLS与认证
}

func echoHandler(ctx context.Context, req *mcp.CallToolRequest,
                 args struct{ Text string `json:"text"` }) (*mcp.CallToolResult, any, error) {
    return &mcp.CallToolResult{Content: []mcp.Content{
        &mcp.TextContent{Text: args.Text}}}, nil, nil
}
```

## 三、惯用法与陷阱清单

Go侧传输工程要点：其一，客户端断开的正确信号是r.Context().Done()——net/http在连接断开时自动取消请求上下文，把它传给工具处理的ctx，长任务即获得取消能力（对齐07篇的abort语义）；其二，每次Flush()是一次系统调用级别的推送，事件粒度别细到每字节，也别攒到KB级；其三，stdio子进程要处理windows build下的命令差异与进程树回收（exec.CommandContext配cancel即杀，但注意它只杀直接子进程，孙进程要taskkill /T或进程组）；其四，goroutine纪律——每连接两泵加业务handler都要挂在与连接生命周期一致的context上，防泄漏用goleak测试；其五，SSE与ResponseWriter的缓冲中间件冲突——确认链路上没有包一层的gzip handler对event-stream生效；其六，jsonrpc消息大小上限用http.MaxBytesReader显式设置。社区库特有的陷阱：会话对象存的map要加锁或用sync.Map；通知channel满了会阻塞 pumps，选择带缓冲+丢弃策略时要打日志。

## 四、验收清单

Go侧交付验收：单端点三方法对齐09篇矩阵；r.Context()取消贯通到工具执行（curl断开后服务端日志可见任务取消）；SSE流经nginx验证事件级到达（proxy_buffering off）；stdio形态三平台冒烟；压测下goroutine数量随连接关闭回落（runtime.NumGoroutine曲线）；MaxBytesReader超限返回4xx而非OOM；与TypeScript/Python客户端互操作冒烟；goleak测试纳入CI。这份清单是Go实现从demo到生产的分水岭，全部通过即可对外提供服务。
