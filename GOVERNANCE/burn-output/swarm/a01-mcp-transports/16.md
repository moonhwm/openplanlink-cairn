# 实现自定义传输的扩展点：Transport接口的send/start/close/onclose契约

**一句话摘要**：本文逐成员剖析官方SDK的Transport接口契约——start的幂等与配对、send的串行化与背压、close的三路径语义、onmessage/onclose/onerror回调的线程纪律——并给出把任意信道适配成合规传输的模板与陷阱清单。

## 一、接口成员的精确语义

以TypeScript SDK的Transport接口为基准（其他语言SDK语义一致、命名略异），它只有三个方法与三个回调，但每个都有精确契约。start()：建立底层连接并进入可收发状态；只能被调用一次，重复start是编程错误（抛异常而非静默）；start resolve之前，实现必须已挂好读取泵，否则存在丢消息窗口；start不得阻塞上层初始化流程之外的无限期等待，连接失败要reject。send(msg)：把一条JSON-RPC消息完整送达；语义是串行化写出——上层可能并发调用send，实现必须内部排队或加锁，保证消息不交错；返回Promise用于表达背压（底层缓冲满时挂起）与失败；close后调用send必须抛错。close()：主动优雅关闭；必须触发自身的onclose回调且仅触发一次；若底层有握手式关闭（如WS的close帧），close应尽量完成握手但设超时兜底强制断；close对已关闭状态幂等。回调侧：onmessage每条入站消息回调一次，参数是已解析的JSON对象；onclose在连接终结（无论主动被动）时调用恰好一次；onerror用于可恢复错误上报（致命错误走onclose+错误日志，两者不混用）。

最容易写错的三个点值得点名：其一，onclose的"恰好一次"——半开连接、对端崩溃、自身close三条路径都要收敛到同一收尾函数，用状态标志防重入；其二，send的背压不可吞——把消息塞进无界数组假装成功，会在慢消费者场景下OOM，正确做法是把底层write返回的Promise链化；其三，回调异常要捕获——上层处理消息抛出的异常不应杀死读取泵，传输的责任是转交，不是替上层扛崩。

## 二、通用适配模板

以下模板把"任意双工字节流/消息流"适配成合规Transport，只需填三个抽象函数：

```typescript
import { Transport } from "@modelcontextprotocol/sdk/shared/transport.js";

export abstract class StreamTransport implements Transport {
  onmessage?: (m: unknown) => void;
  onclose?: () => void;
  onerror?: (e: Error) => void;

  private state: "idle" | "starting" | "open" | "closed" = "idle";
  private writeChain: Promise<void> = Promise.resolve();

  protected abstract doConnect(): Promise<void>;
  protected abstract doReadLoop(onData: (chunk: unknown) => void): Promise<void>;
  protected abstract doWrite(msg: string): Promise<void>;   // 返回背压Promise
  protected abstract doShutdown(): Promise<void>;

  async start(): Promise<void> {
    if (this.state !== "idle") throw new Error(`start in ${this.state}`);
    this.state = "starting";
    await this.doConnect();
    this.state = "open";
    this.doReadLoop(m => {
      try { this.onmessage?.(m); }              // 转交，不扛崩
      catch (err) { this.onerror?.(err as Error); }
    }).catch(() => this.finalize()).finally(() => { if (this.state === "open") this.finalize(); });
  }

  async send(msg: unknown): Promise<void> {
    if (this.state !== "open") throw new Error("transport closed");
    const payload = JSON.stringify(msg);
    // 写链串行化：并发send按顺序落盘，且继承背压
    this.writeChain = this.writeChain.then(() => this.doWrite(payload));
    return this.writeChain;
  }

  async close(): Promise<void> {
    if (this.state === "closed" || this.state === "idle") return;
    this.state = "closed";
    try { await Promise.race([this.doShutdown(), timeout(5000)]); }
    finally { this.finalize(); }
  }

  private finalize(): void {
    if (this.state === "closed") { /* 已收尾，防重入 */ }
    this.state = "closed";
    this.onclose?.();     // 恰好一次由state保证
  }
}

const timeout = (ms: number) => new Promise(r => setTimeout(r, ms));
```

## 三、语言间的接口对照

各官方SDK的等价扩展点对照如下：Python低层SDK在connect时接收一对(reader, writer)式的anyio流，stdio_server上下文就是把标准输入输出包装成这对流，自定义传输只需提供同构流或继承Session；Java SDK定义McpTransport接口（getInbound/observe/dispatch、closeGracefully等），WebFlux/Servlet栈各有基类；C#的ITransport与DotNetTY/ASP.NET Core管道集成；Kotlin与Rust同理。跨语言移植自定义绑定时，契约不变的部分是"一次start、串行send、幂等close、恰好一次onclose"，变化的部分只是异步原语（Promise/协程/CompletableFuture/Channel）。因此把本文模板的语义核对清单当作跨语言移植的验收单最合适。

## 四、陷阱与验收清单

交付前逐项自查：并发send压力测试（1000条并发）后对端收到的帧严格有序且无交错；start途中连接失败时上层能收到reject而非悬挂；对端断电式断开（不发关闭帧）在合理时间内触发onclose；close与对端关闭竞态时不双调onclose；read loop中的异常不会静默吞掉（要么onerror要么onclose）；send在close后调用得到明确异常；消息含中文emoji往返无损；单帧上限保护生效。这份清单是从各家SDK的issue tracker里高频故障提炼而来，逐项过关的自定义传输即可安全承载生产流量。
