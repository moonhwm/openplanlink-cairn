# 传输层错误分类与错误码传播：JSON-RPC error与HTTP status的分层

**一句话摘要**：本文建立MCP传输层的错误分类学——JSON-RPC error对象与HTTP状态码两层机制的分工、标准与保留错误码表、错误在代理链上的转译规则、以及面向客户端的错误呈现与重试映射实现。

## 一、两层错误机制的分界线

HTTP类绑定里存在两套错误通道，分界线是"谁造成了失败"。传输层失败——端点不存在、方法不允许、会话失效、限流、网关超时——用HTTP状态码表达：400畸形请求、404端点或会话不存在、405方法不允许（如对不支持GET流的服务器发GET）、406内容协商失败、410会话已终结、413消息过大、429限流、500内部错误、503暂不可用。协议与业务层失败——工具执行出错、参数不合法、方法未实现、能力不支持——用HTTP 200携带JSON-RPC响应，其中的error对象（code/message/data三元组）表达细节。核心纪律：两层不可互相替代——绝不能把工具失败翻成HTTP 500（客户端的重试与展示逻辑会错位），也绝不能把会话失效翻成JSON-RPC error（客户端无法区分"要重新握手"与"这个调用没成"）。客户端的解析因此是两段式：先看HTTP层非2xx→传输错误（走连接级恢复逻辑）；再看body里的error字段→业务错误（走请求级处理）。

JSON-RPC侧的码表分三段：协议保留段-32700（解析错误）、-32600（无效请求）、-32601（方法不存在）、-32602（无效参数）、-32603（内部错误）；MCP约定段——错误码在-32000到-32767区间由应用自定义，生态常见如-32002（服务器等待initialize）、-32600族的具体化；应用自选段——工具业务错误建议用-32000起的自定义码并在data里放结构化细节（如{tool:"x", reason:"not_found"}）。message字段面向开发者调试（英文短语），面向用户的信息应放在工具结果的is_error形态或data里，由客户端UI层转译。

## 二、错误在多跳链上的转译

代理链（客户端→网关→服务器、30篇的双跳代理）中错误要保真传播。规则一，HTTP层错误透传状态码但可精简body（网关别吞成统一500——503与429对客户端的后续行为完全不同）。规则二，JSON-RPC error整体透传，代理不解读不复写（网关若把上游的-32602改成自己的-32000，客户端的参数纠错提示就没了）。规则三，网关自身失败（上游连不上）要翻成明确的503/504而非伪造JSON-RPC错误——那是传输层事实。规则四，超时语义区分：网关读上游超时回504（请求命运未知，客户端不得自动重发有副作用调用，联动28篇型二）；网关自身过载回503并可带Retry-After。规则五，取消不是错误：客户端abort导致的上游中断，网关只做日志不回错误响应（连接已断，无人接收）。

## 三、客户端的错误处理骨架

```typescript
export class McpError extends Error {
  constructor(public kind: "transport" | "protocol" | "business",
              public httpStatus: number | undefined,
              public rpcCode: number | undefined,
              public rpcData: unknown,
              message: string) { super(message); }
  get shouldReconnect(): boolean {
    return this.kind === "transport" &&
      (this.httpStatus === 404 || this.httpStatus === 410);   // 触发重握手
  }
  get shouldRetryRequest(): boolean {
    if (this.kind === "transport" && this.httpStatus !== undefined)
      return [429, 503].includes(this.httpStatus);            // 可安全重试
    return false;                                              // 业务错误不重试
  }
}

export async function post(url: string, body: unknown, headers: Record<string, string>) {
  const res = await fetch(url, { method: "POST", headers,
    body: JSON.stringify(body) });

  if (!res.ok)   // —— 第一层：传输错误 ——
    throw new McpError("transport", res.status, undefined, undefined,
      `transport failure http ${res.status}`);

  const msg = await res.json();
  if (msg.error) // —— 第二层：协议/业务错误 ——
    throw new McpError(
      (msg.error.code >= -32603 && msg.error.code <= -32700) ? "protocol" : "business",
      undefined, msg.error.code, msg.error.data, msg.error.message);
  return msg;
}

// 使用侧：三类错误三套动作
try { const r = await post(ep, callReq, hdrs); }
catch (e) {
  if (e instanceof McpError) {
    if (e.shouldReconnect) { await reconnectAndReinitialize(); await retryManually(); }
    else if (e.shouldRetryRequest) { await retryWithBackoff(); }
    else if (e.kind === "business") { showToUser(humanize(e.rpcData)); }
    else { surfaceAsBug(e); }             // 协议错误=实现缺陷信号
  } else throw e;
}
```

## 四、错误呈现与服务端纪律清单

服务端纪律清单：工具业务失败优先用call_tool结果的is_error=true（内容可读、面向LLM自纠错），仅在参数不合法等协议性场景才抛-32602；错误message不回显用户原文全量（防注入与隐私），data结构化；每个自定义码写入文档表；日志记码不记敏感data原文。呈现层纪律：对用户隐藏码、给动作（重试/重连/修改参数）；对开发者显示码与message；LLM侧给is_error内容让其自行调整参数。验收清单：两层错误各自通路有测试（400/404/410/429与-32601/-32602/自定义码）；代理链错误保真（503不被吞成500，JSON-RPC码不被复写）；超时（504）不自动重发副作用调用的断言用例；重握手仅由404/410触发；错误响应体不泄漏堆栈与内部路径。这张分类表让排障时间从"猜"降到"查表"，是传输层工程成熟度的直观标志。
