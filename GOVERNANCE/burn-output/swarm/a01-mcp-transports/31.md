# 传输层超时矩阵：连接、请求、空闲与整体会话超时

**一句话摘要**：本文构建MCP传输层的完整超时矩阵——拨号、握手、单请求、流式首字节、读空闲、心跳间隔、会话TTL七类计时器的取值依据、相互作用与调校方法，并附统一超时管理器的实现。

## 一、七类计时器的语义与取值

传输层的超时不是单一数字而是七类计时器的矩阵，各自语义与起点不同。拨号超时（connect timeout）：从发起连接到TCP/TLS建立完成，跨城公网建议3到10秒，内网1到3秒。握手超时（initialize timeout）：从连接建立到initialize响应返回，要容忍服务器冷启动（拉起子进程、加载配置），本地stdio 10到30秒，远程按服务器P99加余量，建议15到60秒。单请求超时（request timeout）：一条JSON-RPC请求从发出到对应响应到达，取决于工具画像——查询类10到30秒、批处理类可到数分钟，应由客户端按工具配置而不是全局一刀切。流式首字节超时（first-byte timeout）：Streamable HTTP的POST若走SSE流，从发请求到收到第一个事件字节，应短于单请求超时（如5到10秒），防止"服务器收了请求但迟迟不开流"的半死状态。读空闲超时（read idle）：链路上无任何入帧的最长容忍时间，须大于心跳间隔的两倍（心跳20秒则读空闲45到60秒）。会话TTL（session TTL）：服务器侧空闲会话的存活期，须显著大于客户端的重连退避上限（09篇），典型30分钟到24小时。整体操作预算（overall budget）：多跳场景（代理链）从用户动作到最终结果的端到端预算，用于给内层计时器动态分配余额。

矩阵里的耦合关系必须显式管理：读空闲大于两倍心跳、会话TTL大于重试退避上限、首字节超时小于单请求超时、子请求超时之和小于端到端预算。任何一条不满足都会出现"内层先于外层放弃"或"外层已放弃而内层还在跑"的资源泄漏。

## 二、按传输形态的推荐配置表

- stdio客户端：拨号无（进程即起）、握手15秒、单请求按工具、无读空闲概念（进程活着就在）、子进程退出即会话终结，整体最简。
- Streamable HTTP客户端：拨道5秒、握手30秒、单请求30秒（可按工具覆写）、首字节8秒、GET流读空闲45秒（心跳20秒时）、会话跟随服务器（404即重握手）。
- 旧版SSE客户端：拨道5秒、endpoint事件等待10秒（握手的一部分）、SSE重连退避上限60秒、读空闲45秒。
- WebSocket：拨道5秒、握手（协议层initialize）30秒、ping间隔20秒、pong窗口5秒、miss阈值3次、读空闲60秒兜底。
- 服务器侧：accept背压满即快速拒绝（秒级）、initialize处理10秒、每会话空闲清扫30分钟、单请求执行上限由工具声明并强制、流写出 stalled（客户端不读）60秒断。

## 三、统一超时管理器实现

```typescript
export type TimerKind = "dial" | "handshake" | "request" | "firstByte"
                      | "readIdle" | "sessionTtl" | "budget";

export interface TimeoutProfile {
  dial: number; handshake: number; request: number; firstByte: number;
  readIdle: number; sessionTtl: number; budget: number;
}

export const PROFILES: Record<"local" | "remote" | "mobile", TimeoutProfile> = {
  local:  { dial: 3_000,  handshake: 15_000, request: 30_000,
            firstByte: 10_000, readIdle: 0, sessionTtl: Infinity, budget: 60_000 },
  remote: { dial: 5_000,  handshake: 30_000, request: 30_000,
            firstByte: 8_000,  readIdle: 45_000, sessionTtl: 1_800_000,
            budget: 120_000 },
  mobile: { dial: 10_000, handshake: 60_000, request: 60_000,
            firstByte: 12_000, readIdle: 90_000, sessionTtl: 1_800_000,
            budget: 180_000 },
};

export class TimeoutMatrix {
  private timers = new Map<TimerKind, NodeJS.Timeout>();

  constructor(private p: TimeoutProfile) {}

  /** 给任意Promise套一层计时器：到点抛带kind的错误，便于分型处理 */
  async with<T>(kind: TimerKind, ms: number | undefined, op: Promise<T>): Promise<T> {
    const limit = ms ?? this.p[kind as keyof TimeoutProfile] as number;
    let t: NodeJS.Timeout;
    const guard = new Promise<never>((_, rej) => {
      t = setTimeout(() => rej(Object.assign(
        new Error(`timeout:${kind}`), { kind })), limit);
      this.timers.set(kind, t!);
    });
    try { return await Promise.race([op, guard]); }
    finally { clearTimeout(t!); this.timers.delete(kind); }
  }

  /** 读空闲看门狗：每次inbound()喂狗，超时回调判死 */
  readIdleWatch(onIdle: () => void): { feed: () => void; stop: () => void } {
    let t: NodeJS.Timeout = setTimeout(onIdle, this.p.readIdle);
    return {
      feed: () => { clearTimeout(t); t = setTimeout(onIdle, this.p.readIdle); },
      stop: () => clearTimeout(t),
    };
  }

  clearAll(): void { for (const t of this.timers.values()) clearTimeout(t); }
}
```

## 四、调校与验收清单

超时调校方法论：先用直方图观测每类操作的真实P50/P99，再把超时设在P99的1.5到3倍；拒绝"拍一个很大的数"——过大超时比没有超时更糟（用户干等加资源占用）；每个超时触发都要有区分于其它失败的错误标记（如上文的timeout:kind），日志聚合后形成超时分布看板。验收清单：七类计时器各自可独立触发并被测试覆盖（用故障注入逐一验证）；读空闲严格大于两倍心跳的断言写成单元测试；会话TTL到期后首个请求收到404而非悬挂；端到端预算耗尽时内层计时器全部收尾（无残留任务）；移动与桌面两套Profile行为差异符合预期；超时错误与28篇重试分型联动正确（dial超时可重试、request超时禁盲目重发）。把超时当配置产品管理而不是散落的魔数，传输层的可预期性会立刻上一个台阶。
