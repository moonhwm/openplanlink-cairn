# 旧版HTTP+SSE传输（2024-11-05协议）：双端点设计与迁移

**一句话摘要**：本文回顾MCP 2024-11-05版规范的HTTP+SSE传输——GET /sse建立下行事件流并发送endpoint事件、POST到消息端点上行——分析其局限，并给出向Streamable HTTP迁移的完整路线与兼容策略。

## 一、双端点传输的原始设计

在2025-03-26引入Streamable HTTP之前，远程MCP连接的标准形态是HTTP+SSE传输，它用两个端点分工：客户端首先向服务器的SSE端点（通常是GET /sse，Accept: text/event-stream）发起长连接；连接建立后，服务器发送的第一个事件必须是endpoint事件，data字段携带本会话消息端点的URI（例如/messages?sessionId=abc123），客户端解析该URI；此后一切客户端到服务器的JSON-RPC消息都通过POST发往这个消息端点，而服务器到客户端的一切消息（响应、通知、服务器请求）都经SSE流下行。POST的HTTP响应本身不携带协议内容，只回202 Accepted表示已接收；真正的响应永远在SSE流上以JSON-RPC响应事件抵达，靠id与POST出去的请求配对。

这个设计能工作，但带着一批结构性缺陷。第一，SSE长连接是硬依赖：连接一断，服务器下发的消息全部丢失，客户端必须重建SSE并重新POST才能续命，且旧版对恢复语义定义得很弱。第二，两端点带来状态同步问题：endpoint URI里往往嵌入会话标识，代理改写、路径重定位都容易弄错。第三，全双工能力被捆死在一条长流上，无状态部署、Serverless、请求级扩缩容都难以支持——每来一个客户端都要挂一条常驻连接。第四，POST永远202导致错误语义贫乏，传输层问题（会话失效、方法错误）难以用HTTP状态码清晰表达。这些痛点正是规范重构成单端点Streamable HTTP的直接动因。

## 二、新旧机制对照表

迁移前先建立精确的对照关系，下表把两个版本的核心机制并排：

- 端点拓扑：旧版=GET /sse（下行）+ POST /messages（上行）双端点；新版=单端点POST/GET/DELETE /mcp。
- 握手方式：旧版=先建SSE、收endpoint事件、再POST initialize；新版=直接POST initialize，响应头带Mcp-Session-Id。
- 下行路径：旧版=全部走SSE长流；新版=POST响应自带（JSON或SSE流）+ 可选GET长流。
- 上行路径：旧版=POST固定202，无响应体；新版=POST可回JSON响应或SSE流。
- 会话标识：旧版=endpoint URI中的参数（实现自定义）；新版=标准化Mcp-Session-Id头。
- 版本协商：旧版=仅initialize参数；新版=initialize参数+MCP-Protocol-Version头每请求确认。
- 来源防护：旧版=建议校验；新版=明确要求Host/Origin校验与本地绑定基线。
- 流恢复：旧版=依赖实现；新版=Last-Event-ID+resumability能力标准化。

## 三、迁移路线与双栈兼容

迁移建议按四步走。第一步，服务端实现Streamable HTTP为权威路径：单端点、会话头、版本头、405降级、DELETE终结全部就位。第二步，保留旧版端点作为兼容层：继续暴露GET /sse与POST /messages，内部映射到同一会话管理与消息分发器——注意旧端的endpoint事件URI要指向旧消息端点，且旧会话与新会话头体系互不混用。第三步，客户端能力探测：客户端先按新协议POST initialize，若得到404/405等"不支持"信号（或配置显式指明旧版），则回退走旧流程（GET /sse等endpoint再POST）；各官方SDK的传输类已内置这类降级尝试。第四步，观察与下线：当指标显示旧端点流量归零或低于阈值后，发布弃用公告并移除旧端点。

兼容层实现的核心是把两套外皮接到同一个内核，参考骨架：

```typescript
// 权威路径：Streamable HTTP
app.post("/mcp", streamableHandler);      // 见09篇会话管理
app.get("/mcp", maybeStreamHandler);
app.delete("/mcp", terminateSession);

// 兼容路径：旧版HTTP+SSE，映射到同一dispatcher与sessionStore
app.get("/sse", (req, res) => {
  res.set({ "content-type": "text/event-stream", "cache-control": "no-cache" });
  const session = createSessionLegacy();           // 同一内核的会话存储
  const messageUri = `/messages?sessionId=${session.id}`;
  res.write(`event: endpoint\ndata: ${messageUri}\n\n`); // 首事件必须是endpoint
  session.attachDownstream(res);                   // 后续消息经此流下发
  keepAliveLoop(res);
});

app.post("/messages", express.json(), async (req, res) => {
  const session = sessionStore.get(String(req.query.sessionId));
  if (!session) return res.status(404).end();
  await dispatcher.enqueue(session, req.body);     // 复用与新版相同的分发内核
  res.status(202).end();                           // 旧版约定：响应走SSE
});
```

## 四、迁移核对清单与常见故障

迁移验收清单：新客户端走单端点全功能通过（含GET流、DELETE、410/404重初始化）；旧客户端走双端点通过且互不串会话；同一服务器上新旧客户端并存时指标可区分；旧端点的SSE流有心跳且代理配置了不缓冲；切换探测逻辑有明确开关与日志，避免每次连接都双试造成延迟；文档与发现配置（如.well-known位置或客户端配置文件）已更新为新端点。常见故障速查：客户端卡在等响应——多半是客户端走旧版期待SSE下行，服务器却按新版把响应放在POST响应体里；endpoint事件丢失——旧端首个事件不是endpoint属于违规实现；会话串号——旧版sessionId与新版Mcp-Session-Id混用同一命名空间导致覆盖，需隔离前缀。完成迁移后，新能力（请求级无状态、事件恢复、清晰错误语义）即可逐步启用。
