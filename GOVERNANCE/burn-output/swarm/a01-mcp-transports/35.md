# 代理服务器兼容性：Nginx/Caddy/CDN对SSE与流式响应的配置

**一句话摘要**：本文汇总MCP HTTP传输在反向代理、网关与CDN后的兼容性工程——Nginx的缓冲与超时族、Caddy的反代默认值、云CDN对event-stream的策略、以及逐层验证的探测方法与配置清单。

## 一、流式传输在代理层的三大杀手

把MCP的Streamable HTTP端点放到反向代理后面，会遭遇三个系统性问题。杀手一，响应缓冲：Nginx默认对上游响应做缓冲（proxy_buffering on），攒够一批再发给客户端——对SSE是灾难，事件被攒住变成"卡30秒后一次性全到"，客户端超时、恢复机制全部误判。杀手二，空闲超时：代理对上游连接设读超时（Nginx默认proxy_read_timeout 60s），心跳间隔若大于它，连接每60秒被掐一次；云LB（AWS ALB默认idle timeout 60s、部分网关30s）同理。杀手三，HTTP/1.0与分块语义：老配置的代理以HTTP/1.1之前的语义回源，丢失chunked transfer与keepalive，SSE的分块推送被破坏；另有压缩层（gzip/brotli）对event-stream聚合输出，效果等同缓冲。WS绑定还多一个升级头透传问题（Upgrade/Connection头被剥离导致握手404）。这些问题在本地直连测试中全部不可见，是"一到生产就怪"的头号来源。

## 二、Nginx与Caddy的参考配置

```nginx
# Nginx：MCP Streamable HTTP端点
upstream mcp_backend { server 127.0.0.1:8080; keepalive 32; }

server {
  listen 443 ssl http2;
  server_name mcp.example.internal;

  # TLS与头部（证书由运维体系签发，此处不涉及任何密钥材料）
  ssl_protocols TLSv1.2 TLSv1.3;

  location /mcp {
    proxy_pass http://mcp_backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";            # keepalive上游复用
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

    # —— SSE/流式三大关键项 ——
    proxy_buffering off;                       # 关闭响应缓冲：事件即到即转
    proxy_cache off;                           # 不缓存API响应
    gzip off;                                  # 对本端点禁压缩，防事件聚合

    # —— 超时族：全部大于心跳间隔(20s) ——
    proxy_read_timeout    300s;                # 上游空闲容忍
    proxy_send_timeout    60s;
    # chunked_transfer_encoding 默认开启，无需显式

    # —— 会话粘性（多实例时有状态会话需要）——
    # ip_hash;  或配合 cookie 粘性：
    # hash $cookie_mcp_route consistent;
  }
}
```

```caddy
# Caddy：默认无缓冲、超时较宽，配置极简
mcp.example.internal {
    reverse_proxy 127.0.0.1:8080 {
        # Caddy对流式响应默认flush_interval -1（即关闭），一般无需额外设置；
        # 显式声明以自文档化并防全局改写：
        flush_interval -1
        transport http {
            read_timeout 5m
        }
    }
}
```

## 三、CDN与云网关策略

公网MCP服务经CDN时要认识到event-stream是CDN的边缘场景：多数CDN默认不缓存但会缓冲或对长连接设上限（如Cloudflare的100秒无数据断连——所以经CF的SSE心跳必须小于100秒，20到30秒是安全值）；要显式给/mcp路径配置"绕过缓存、禁用响应优化（Minify/ Rocket Loader类功能会改写响应体，对事件流是毒药）"；部分CDN对POST流式响应支持不佳，退路是让服务器对POST一律回纯JSON（放弃POST流，推送走GET流）或干脆只回JSON形态。API网关类（Kong/APISIX）：关闭response buffer插件、超时调大、WS路由开启websocket插件透传Upgrade头。K8s Ingress（nginx-ingress）：注解nginx.ingress.kubernetes.io/proxy-buffering:"off"与proxy-read-timeout调大，或用Global配置；Service层无需特殊处理，但注意ingress controller的重试策略对POST默认不重试（正确），不要手滑打开对POST的重试——那会重复执行工具调用。

## 四、分层验证清单

上线前逐层验证清单：直连服务器（无代理）事件级到达正常——基线；加Nginx后事件首字节延迟与直连差异在毫秒级（差异大=缓冲未关净）；空闲90秒连接不断（超时族大于心跳）；HTTP/2与HTTP/1.1两种客户端协议都验证（部分栈h2下chunked行为不同）；经CDN的公网路径用curl --no-buffer加时间戳观测每事件到达；WS握手（若部署）经代理Upgrade透传成功；断开传播验证——客户端abort后代理把断开传给上游（否则服务器白算，联动29篇取消）；配置变更（超时、缓冲项）纳入代码评审与版本化，防止运维侧"优化"悄悄回退。每层通过后记录探测命令与时延基线入运行手册，后续任何代理链改动都有回归基准。
