# 客户端传输重试与退避策略设计

**一句话摘要**：本文给出MCP客户端传输层的重试设计——哪些失败可重试、指数退避加抖动的参数学、请求级与连接级重试的分层、幂等性约束与熔断，并附可直接复用的退避器实现。

## 一、可重试性分类：先分型再谈重试

传输层失败按可重试性分四型。型一，连接建立失败：TCP拒绝、DNS暂时失败、TLS握手失败——可重试，服务器可能正在重启。型二，请求已发出但结果未知：超时、连接中途断开、SSE流半途而亡——严禁盲目重试，因为请求可能已被服务器执行（工具调用常有副作用：写文件、下单、发消息），盲目重发等于重复执行。型三，明确失败且可安全重试：收到503/504/429（服务器明确说没处理或限流）、410后的重新initialize流程——可重试。型四，永久失败：400/404（端点错）、401/403（认证问题）、协议错误——不重试，上抛处理。这个分型是重试设计的第一原则：传输层重试只覆盖型一与型三；型二必须交给上层以"补偿询问"或幂等键的方式处理，型二的处理正确性是MCP客户端与普通REST客户端最大的差异点，因为工具调用几乎从不在协议层声明幂等性。

第二原则是分层：连接级重试（断线后重建传输、重新握手、恢复订阅）与请求级重试（单次发送失败后有限次重发）是两套独立机制，参数不同、触发条件不同，实现里必须分开管理，防止放大效应（连接抖动导致每个在途请求各自重试三连）。

## 二、退避参数学：指数、抖动与上限

标准退避公式是指数递增加全抖动：delay = random(min, base * 2^attempt * jitter)，典型参数：base=500ms、factor=2、cap=30s、jitter=0.5（即均匀取[min(cap*0.5, base*2^n*0.5), cap或计算值]）。设计约束依次是：上限必须小于服务器的会话TTL一半以上，否则重试成功时会话早已过期，白等；429响应若带Retry-After头，优先遵循它而不用本地公式；连续失败N次（如8到10次）后进入熔断冷却（如2分钟）并通知上层"连接不可用"，避免移动设备在无网状态下耗电空转；成功一次即重置退避与计数；同进程多个客户端共享退避种子要不同（随机源天然满足），避免雷鸣群效应。请求级重试则更紧：最多2到3次、base 200ms、cap 2s，且仅限型一型三。

## 三、退避器与分型重试的实现

```typescript
export class Backoff {
  attempt = 0;
  constructor(private base = 500, private cap = 30_000, private jitter = 0.5) {}
  next(): number {
    const exp = Math.min(this.cap, this.base * 2 ** this.attempt++);
    const lo = exp * (1 - this.jitter), hi = exp;
    return lo + Math.random() * (hi - lo);   // 全抖动
  }
  reset() { this.attempt = 0; }
}

export class RetryPolicy {
  private circuitOpen = false;
  private circuitUntil = 0;

  static retryable(err: { stage: "connect" | "send"; status?: number;
                           abortedAfterSend?: boolean }): boolean {
    if (err.abortedAfterSend) return false;          // 型二：结果未知，禁重试
    if (err.stage === "connect") return true;         // 型一
    if ([429, 503, 504].includes(err.status ?? 0)) return true; // 型三
    return false;                                     // 其余：永久失败
  }

  async execute<T>(op: () => Promise<T>,
                   classify: (e: unknown) => Parameters<typeof RetryPolicy.retryable>[0],
                   hooks: { onRetry?: (n: number, d: number) => void } = {}): Promise<T> {
    const bo = new Backoff();
    for (let n = 0; ; n++) {
      if (this.circuitOpen) {
        if (Date.now() < this.circuitUntil)
          throw new Error("circuit open");
        this.circuitOpen = false;
      }
      try { const r = await op(); bo.reset?.call(bo); return r; }
      catch (e) {
        const info = classify(e);
        if (!RetryPolicy.retryable(info) || n >= 3)
          throw e;                                   // 不可重试或次数用尽
        if (n === 0 && info.status === 429) {
          // 限流：尊重服务器节奏（此处示意固定1s，生产读Retry-After）
          await new Promise(r => setTimeout(r, 1000));
        }
        const d = bo.next();
        hooks.onRetry?.(n + 1, d);
        await new Promise(r => setTimeout(r, d));
        if (bo.attempt >= 8) {                       // 连续失败过多：熔断冷却
          this.circuitOpen = true;
          this.circuitUntil = Date.now() + 120_000;
          throw new Error("circuit opened after retries");
        }
      }
    }
  }
}
```

## 四、落地核对清单

重试机制验收清单：型二失败（发送后超时）绝不自动重发，单元测试用"计数服务器"验证调用次数恰为一；429遵守Retry-After；退避序列在日志中可观测（次数与延迟）；熔断触发后有明确的上层通知与恢复探测；连接级重连成功后自动重新initialize并重放订阅（联动12篇）；重试期间新请求被排队或直接快速失败（不无限堆积）；移动端在后台状态暂停重试（省电纪律）；所有重试日志不含敏感参数全文。这份清单把"重试"从拍脑袋参数升级为可验证的工程合约，是客户端传输健壮性的核心保障。
