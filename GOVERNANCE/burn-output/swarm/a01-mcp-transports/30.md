# 代理与会话边界：MCP-Proxy模式下的传输转发

**一句话摘要**：本文研究MCP代理（一个进程同时是上游服务器的客户端与下游客户端的服务器）的传输转发工程——双传输生命周期配对、消息透传规则、会话映射、故障传播与背压级联，并给出聚合代理的实现骨架。

## 一、代理的形态与价值

MCP代理在两条传输之间居中：对下以服务器身份接受客户端连接，对上以客户端身份连接真实服务器。常见形态有三种。透传代理：纯粹转发，价值在拓扑改造——让本地客户端经代理访问远程服务器（本地stdio协议转远程HTTP），或反向把远程流量终结在企业边界内。聚合网关：对上连N个服务器，对下呈现为一个虚拟服务器，工具列表是各上游的并集（带前缀消歧），请求按注册表路由到对应上游——这是"一个入口聚合多家工具"的主流架构。策略代理：在转发路径上插入治理——审计日志、参数过滤、权限裁决、限流配额、工具白名单，让企业对AI调用外部工具拥有统一的控制面。

代理的传输工程核心是"双传输的生命周期配对"：下游会话与上游连接的建立、断开、重连必须映射清楚。设计决策有二：一对一映射（每个下游会话独立连一个上游连接，隔离最好、上游连接数随下游线性增长）与共享上游（多个下游会话复用少量上游连接，省资源但要在代理内做请求多路复用与响应分发，且上游主动通知难以精确路由）。聚合网关通常对每个上游用共享连接加每服务器一路；透传代理用一对一最简单可靠。

## 二、转发规则：什么能透传、什么必须改写

透传不是逐字节复制，要按消息类型分派。通知与服务器请求（roots/list、sampling）：透传代理一般不能透传服务器→客户端的反向请求（下游客户端能力与上游服务器能力是分别协商的），正确做法是代理自己应答或按自身协商的能力截停；聚合网关必须自己实现roots、sampling的裁决，因为多个上游的此类请求语义无法简单合并。initialize：代理用自己的身份应答下游（聚合serverInfo），对上游各自发起initialize，双方能力对象都由代理重新合成——绝不能把上游的能力声明原样给下游，否则下游会调用上游才有的能力却在代理处被拒。工具列表：聚合时改名加前缀并维护路由表。call_tool：按路由表转发，参数原样、结果原样（除超大结果的裁剪策略）。错误与取消：下游取消（HTTP abort或notifications/cancelled）要转译为对上游的取消信号；上游连接死亡要把在途请求统一回填传输错误给下游，并按策略触发上游重连或下游重握手（410语义）。

## 三、聚合代理的实现骨架

```typescript
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StreamableHTTPClientTransport } from "@modelcontextprotocol/sdk/client/streamableHttp.js";
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";

interface Upstream {
  name: string;                  // 前缀，如 "db"
  client: Client;
  toolMap: Map<string, string>;  // "db_query" -> 上游真名 "query"
}

const upstreams: Upstream[] = [];

async function attachUpstream(name: string, url: string) {
  const client = new Client({ name: `gateway-${name}`, version: "1.0" });
  await client.connect(new StreamableHTTPClientTransport(new URL(url)));
  const res = await client.listTools();
  const u: Upstream = { name, client, toolMap: new Map() };
  for (const t of res.tools) u.toolMap.set(`${name}_${t.name}`, t.name);
  upstreams.push(u);
}

const gateway = new Server(
  { name: "mcp-gateway", version: "1.0" },
  { capabilities: { tools: { listChanged: false } } }, // 聚合层不转发放大列表抖动
);

gateway.setRequestHandler("tools/list", async () => ({
  tools: upstreams.flatMap(u =>
    [...u.toolMap.entries()].map(([alias, real]) => ({
      name: alias,
      description: `[${u.name}] ` + (lookupDesc(u, real) ?? ""),
      inputSchema: lookupSchema(u, real) ?? { type: "object" },
    }))),
}));

gateway.setRequestHandler("tools/call", async (req) => {
  const alias = String(req.params.name);
  const u = upstreams.find(x => x.toolMap.has(alias))
    ?? throwNotFound(alias);
  // 转发：参数透传；上游错误按原语义回给下游（代理不吞错）
  return u.client.callTool({ name: u.toolMap.get(alias)!,
                             arguments: req.params.arguments });
});

// 生命周期配对：代理对下以stdio起，对上各自维护HTTP连接与重连
await attachUpstream("db", "https://db.internal/mcp");
await attachUpstream("search", "https://search.internal/mcp");
await gateway.connect(new StdioServerTransport());
```

## 四、代理特有故障与验收清单

代理引入的特有故障要专门验收：上游一死，仅涉及其前缀的工具失败，其它上游不受影响（故障域隔离）；下游会话重握手时上游连接策略明确（复用或重建，二选一并写入文档）；在途请求跨两侧的取消链路打通（下游abort→上游cancelled）；上游列表变更通知要么聚合重推（listChanged=true时），要么声明false走轮询，不可出现"声明了却不推"；代理自身不缓存带敏感数据的结果；审计日志记录调用三元组（下游身份、别名工具、上游）但参数按脱敏策略；限流按下游会话与按上游双重计数。压测验收：两跳延迟增加应在单毫秒到十毫秒量级（非流式转发）；背压级联测试——上游慢时代理缓冲有界并反压下游。这份清单是MCP代理从demo到企业网关的过关单。
