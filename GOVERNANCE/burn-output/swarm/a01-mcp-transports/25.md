# C# SDK的传输抽象与ASP.NET Core集成

**一句话摘要**：本文解析C#官方SDK（ModelContextProtocol）的ITransport抽象、StdioClientTransport与SseClientTransport/StreamableHttpTransport实现，以及用ASP.NET Core最小API挂载MCP端点（MapMcp）的完整流程，附中间件定制与验收清单。

## 一、ITransport抽象与实现族谱

C#官方SDK以Microsoft.Extensions的Options与依赖注入风格组织，传输层核心接口ITransport定义四个成员：Task StartAsync()、Task SendAsync(JsonRpcMessage, CancellationToken)、Task CloseAsync()、以及两个回调性质成员OnMessageReceived与OnClosed（事件或委托形态随版本微调）。实现族谱：StdioClientTransport负责拉起子进程并按行分帧（语义同19篇，环境变量同样走最小集+显式注入策略）；SseClientTransport实现旧版双端点（GET事件流+endpoint事件+POST消息）；StreamableHttpTransport实现新版单端点（POST双形态、GET流、DELETE、Mcp-Session-Id与MCP-Protocol-Version头全套）；服务端提供StdioServerTransport以及与ASP.NET Core集成的中间件式实现。所有HTTP栈建立在System.Net.Http.HttpClient之上，因此连接池、代理、超时等全部可用HttpClient的标准手段配置，这是.NET生态的天然优势。

SDK同时提供高层的McpClient（WithTransport扩展方法链式配置）与服务器侧的McpServer，工具用[McpServerTool]特性标注方法即可注册，业务代码与传输完全解耦——与TypeScript的Client/Server分层一一对应。

## 二、ASP.NET Core端点挂载

服务端HTTP集成的现代做法是一行MapMcp：SDK提供扩展方法把MCP端点挂进最小API路由，内部完成POST/GET/DELETE三方法的协议处理、会话管理、SSE流写出。样板：

```csharp
// 包：ModelContextProtocol、ModelContextProtocol.AspNetCore
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddMcpServer()            // 注册服务器与工具
    .WithToolsFromAssembly()              // 扫描[McpServerTool]标注
    .WithStdioServerTransport()           // 本地形态：也可同一程序双形态
    ;

var app = builder.Build();

app.MapMcp("/mcp");                        // 远程形态：单端点三方法挂载

// 中间件链：Origin校验（10篇基线）放最前
app.Use(async (ctx, next) =>
{
    var origin = ctx.Request.Headers.Origin.ToString();
    var isLocal = string.IsNullOrEmpty(origin)
        || origin.StartsWith("http://localhost")
        || origin.StartsWith("http://127.0.0.1");
    if (!isLocal) { ctx.Response.StatusCode = 403; return; }
    await next();
});

await app.RunAsync();

// 工具定义示例（同程序集任意类）：
public static class EchoTools
{
    [McpServerTool(Name = "echo", Description = "回显文本")]
    public static string Echo(string text) => text;
}
```

双形态部署是C# SDK的一个顺手能力：同一个程序既可作为stdio子进程被本地宿主拉起（args里带--stdio之类开关时走WithStdioServerTransport），又可作为Web服务暴露/mcp——这正好服务47篇将讨论的多传输共存模式。

## 三、定制点与陷阱

定制与陷阱清单：其一，会话与DI作用域——McpServer默认单例，但每会话的HttpClientHandler、用户上下文要用Scope隔离，认证信息从HttpContext.User提取后传入工具上下文；其二，流式写出的响应缓冲——Kestrel默认行为对text/event-stream友好，但若前面挂了响应压缩中间件，必须排除event-stream（否则事件被攒住），UseResponseCompression的配置加MimeTypes排除项；其三，CancellationToken贯通——工具方法的ct参数要真实接到HttpContext.RequestAborted，客户端断开即取消长任务，这是Streamable HTTP取消语义的落地；其四，大对象序列化——SDK用System.Text.Json，中文默认转义不影响正确性，但要注意HttpClient对请求体的MaxRequestBufferSize配置与4MB级消息的分块；其五，旧版SseClientTransport在链式代理下的路径重写问题（endpoint事件里的URI与外部访问路径不一致时需手工修正基址）。

## 四、验收清单

C#侧交付验收：MapMcp端点三方法行为对齐09篇矩阵（initialize签发、无会话404、DELETE终结）；工具调用在中途断开（RequestAborted）时服务端任务真正取消；响应压缩对SSE的排除已验证；Origin校验用例覆盖伪造来源403；stdio与HTTP双形态同一程序可切换；McpClient配StreamableHttpTransport对非.NET服务器的互操作冒烟通过；每会话内存随关闭回落（dotnet-counters观察）；日志经ILogger不打到协议通道。逐项过关，C#侧传输即达生产水位。
