# Streamable HTTP的POST多语义：请求、响应与流式返回的编排

**一句话摘要**：本文深入Streamable HTTP中一个POST可能触发的全部语义分支——同步JSON响应、SSE流式响应、通知无响应、服务器借流反向请求——并给出服务器与客户端两侧的编排实现要点。

## 一、一个POST，四种结局

Streamable HTTP把"发一条JSON-RPC消息"编码为一个POST，但这个POST的命运有四种截然不同的结局，实现双方都必须处理全部分支。结局一：请求体是JSON-RPC请求（带id），服务器同步完成处理，以HTTP 200 + application/json返回一条对应id的响应——最简路径，适合查询类工具的快速往返。结局二：同样带id的请求，但处理耗时或需要边算边报进度，服务器返回HTTP 200 + text/event-stream，在SSE流里先推若干通知（progress、日志、资源变更），最终推一条带响应的事件，然后关流；客户端在此期间还可以通过HTTP断连（abort）表达取消。结局三：请求体是通知（无id），服务器处理完直接返回202 Accepted（或204），无消息体——客户端不得期待任何JSON-RPC回复。结局四：服务器在响应流或GET流中向客户端发起请求（sampling/createMessage、roots/list、elicitation），形成"服务器问、客户端答"的逆向流，客户端必须具备应答能力，否则应在initialize能力里声明不支持，让服务器避免发起。

四种结局对HTTP基础设施也有不同要求：结局一与三和普通REST无异；结局二要求整条链路（代理、负载均衡、网关）支持流式响应不缓冲；结局四在HTTP上的实现是"请求搭流捎带"——服务器的请求作为SSE事件下发，客户端的响应再作为新的POST上行，两段靠JSON-RPC id配对衔接。理解这个"一POST多结局"模型是调试Streamable HTTP互操作问题的钥匙：很多"客户端卡住"的现象，本质是客户端只实现了结局一，遇到服务器选择结局二时在等一个永远不会单独到来的JSON响应体。

## 二、服务器侧的编排决策

服务器在收到POST后需要做三个决策：第一，验消息——解析JSON、确认是单条JSON-RPC（拒绝数组）、识别请求或通知；第二，选形态——判断该method适合同步返回还是流式返回，这不是协议强制而是服务器自由裁量，常见策略是短平快工具走JSON、长任务工具固定走SSE（便于推进度并支持中途取消）、通知一律202；第三，管流——若选SSE，要在写头之前完成（一旦发送200+event-stream头部就不可再改口），并处理客户端abort事件：监听请求的close信号，向业务层转发取消，停止产生更多事件。服务器还应给每条流设置空闲与总时长上限，防止慢客户端把连接与内存拖死。多并发POST下，服务器要保证对同一会话的响应顺序不产生语义破坏：JSON-RPC本身按id配对允许乱序完成，但同一SSE流内事件必须按写出顺序送达。

## 三、客户端侧的等待与配对逻辑

客户端的核心是"响应等待器"：POST发出后，依据响应Content-Type分派——application/json则直接解析出响应并resolve对应id的等待者；text/event-stream则进入SSE解析循环，每收到一个message事件就反序列化，若带id且是等待中的id则resolve，否则作为通知上抛。等待器需要与HTTP层解耦，因为响应可能来自POST流，也可能（理论上）经GET长流到达。以下是一段客户端等待器的骨架代码：

```typescript
type Pending = { resolve: (v: any) => void; reject: (e: Error) => void };

class PostDispatcher {
  private pending = new Map<string | number, Pending>();
  private nextId = 1;

  async request(method: string, params: object) {
    const id = this.nextId++;
    const msg = { jsonrpc: "2.0", id, method, params };
    const p = new Promise<any>((resolve, reject) =>
      this.pending.set(id, { resolve, reject }));
    const res = await fetch(this.endpoint, {
      method: "POST",
      headers: {
        "content-type": "application/json",
        "mcp-protocol-version": this.version,
        ...(this.sessionId ? { "mcp-session-id": this.sessionId } : {}),
      },
      body: JSON.stringify(msg),
    });
    if (res.status === 202) return;              // 通知：无回复
    if (!res.ok) throw new Error(`transport ${res.status}`);
    const ct = res.headers.get("content-type") ?? "";
    if (ct.includes("application/json")) {
      const body = await res.json();             // 结局一：同步响应
      this.pending.get(body.id)?.resolve(body); this.pending.delete(body.id);
    } else if (ct.includes("text/event-stream")) {
      await this.consumeSSE(res);                // 结局二：流式
    }
    return p;
  }

  private async consumeSSE(res: Response) {
    const reader = res.body!.getReader();
    const dec = new TextDecoder();
    let buf = "";
    for (;;) {
      const { done, value } = await reader.read();
      if (done) break;
      buf += dec.decode(value, { stream: true });
      let i: number;
      while ((i = buf.indexOf("\n\n")) >= 0) {   // SSE事件以空行分隔
        const block = buf.slice(0, i); buf = buf.slice(i + 2);
        const data = block.split("\n")
          .filter(l => l.startsWith("data:"))
          .map(l => l.slice(5).trim()).join("\n");
        if (!data) continue;
        const msg = JSON.parse(data);
        if (msg.id !== undefined && msg.result !== undefined || msg.error) {
          this.pending.get(msg.id)?.resolve(msg); // 响应事件：配对
          this.pending.delete(msg.id);
        } else {
          this.onNotification(msg);               // 通知：上抛
        }
      }
    }
  }
}
```

## 四、边界与故障排查清单

落地时按下表核对边界行为：POST返回202/204时绝不挂等待器；SSE流在响应事件后服务器可关闭，客户端读到流尾要能正确收尾等待器；客户端abort后必须丢弃对该POST响应的期待，若服务器已发出响应事件需容忍孤儿事件；HTTP 4xx/5xx属于传输层错误，不得翻译成JSON-RPC响应喂给业务层；重试逻辑只适用于传输层失败（连接被拒、超时未建连），已送达的请求绝不能因客户端超时自动重发——工具可能有副作用，重复POST等于重复执行。掌握这张分支表，Streamable HTTP的POST语义就再无黑箱。
