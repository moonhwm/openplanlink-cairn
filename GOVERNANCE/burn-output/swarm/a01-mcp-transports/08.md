# Streamable HTTP中的SSE流：text/event-stream解析与事件类型

**一句话摘要**：本文聚焦Streamable HTTP里text/event-stream载体的细节——SSE帧格式、event/data字段规范、MCP所用的message事件约定、Last-Event-ID恢复机制，以及一套健壮的SSE解析器实现。

## 一、SSE帧格式与MCP的事件约定

服务器推送事件（Server-Sent Events）是HTML标准定义的服务器到客户端单向文本流格式，HTTP响应头为Content-Type: text/event-stream，实体由若干"事件块"组成，块间以空行分隔。每个块由若干行组成，行首字段名后跟冒号：data行携带数据（一个块可有多行data，拼接时以\n相连）；event行指定事件类型（缺省为message）；id行给出事件标识，浏览器原生EventSource会自动把最后一个id作为Last-Event-ID请求头在重连时回传；retry行建议重连间隔毫秒数。以冒号开头的行是注释，常被服务器用作保活心跳（每15到30秒发一行注释，防止中间代理判定空闲并掐断连接）。

MCP在SSE之上只定义了极少的约定：协议消息统一使用event: message（或省略event字段走默认类型），每个message事件的data字段是恰好一条完整JSON-RPC消息的JSON文本；服务器可以在流上附加自定义事件类型（如ping），客户端必须忽略不认识的事件类型而不是报错；事件块内不得把一条JSON-RPC消息拆到多个data行——虽然SSE语法允许，但MCP生态的实现按"一个事件一条消息"对齐。恢复机制方面，Streamable HTTP规定服务器可以在事件上携带id，客户端断线重连（对GET流）时带上Last-Event-ID请求头，服务器据此重放该id之后的事件，实现流级恢复；具体重放窗口多大由服务器决定，不支持的返回最新流即可。

## 二、解析SSE的状态机要点

写一个健壮的SSE解析器需要注意六点。第一，事件分隔符是空行（\n\n），但要兼容\r\n\r\n与\r\r——跨平台服务器与代理可能改写行结束符，稳妥做法是先统一把\r\n与\r归一为\n再切分。第二，一行超长或data无界增长要有上限，防止恶意流打爆内存。第三，多行data按出现顺序以\n连接后再解析JSON，解析失败按"忽略该事件"处理并记日志。第四，UTF-8多字节字符可能被TCP分块切成两半，解码必须用流式TextDecoder（或等价的增量解码）而非逐块独立decode。第五，BOM只可能出现在流头，应当剥掉。第六，连接断开（read返回EOF）在无恢复信息时应触发上层重连流程，而不是静默结束——对GET长流而言，流结束通常意味着异常掉线。

## 三、流式SSE解析器的参考实现

下面是一个处理了上述全部要点的解析器（TypeScript），可直接用于MCP客户端的SSE消费：

```typescript
export class SSEParser {
  private buf = "";
  private data: string[] = [];
  private eventType = "";
  private lastId = "";

  constructor(private readonly emit: (e: { event: string; data: string; id?: string }) => void) {}

  feed(text: string): void {
    this.buf += text.replace(/\r\n?/g, "\n");    // 行结束归一
    let nl: number;
    while ((nl = this.buf.indexOf("\n")) >= 0) {
      const line = this.buf.slice(0, nl);
      this.buf = this.buf.slice(nl + 1);
      if (line === "") {                          // 空行=事件块结束
        if (this.data.length > 0) {
          this.emit({ event: this.eventType || "message",
                      data: this.data.join("\n"), id: this.lastId || undefined });
        }
        this.data = []; this.eventType = "";      // 状态复位
      } else if (line.startsWith(":")) {
        // 注释：常为心跳，忽略即可
      } else if (line.startsWith("data:")) {
        this.data.push(line.slice(5).replace(/^ /, ""));
      } else if (line.startsWith("event:")) {
        this.eventType = line.slice(6).replace(/^ /, "");
      } else if (line.startsWith("id:")) {
        this.lastId = line.slice(3).replace(/^ /, "");
      }
      // retry: 字段对自研客户端无强制意义，可忽略
    }
  }
}
```

## 四、部署与排障核对清单

SSE流在生产环境的第一杀手是中间层缓冲，上线前按清单逐项验证：Nginx需proxy_buffering off（或响应头X-Accel-Buffering: no）；网关/CDN需确认支持text/event-stream透传且不聚合响应；压缩层（gzip/brotli）对事件流要么关闭要么确认flush粒度；空闲心跳注释行是否按间隔发出（很多云负载均衡默认60秒空闲断连）；客户端读取超时要长于心跳间隔、远短于无心跳时的绝对上限。排障时先看三层：响应头是否真是text/event-stream且立即到达（被缓冲的表现是事件成批迟到）；事件块是否以空行正确分隔（缺空行会导致两个事件粘连）；data是否为合法单条JSON（服务器把多条塞一个事件是最常见违规）。这份清单配合上面的解析器，可覆盖SSE载体在MCP场景下的全部工程要点。
