# 传输层可观测性：日志、指标与tracing注入

**一句话摘要**：本文给出MCP传输层的可观测性建设方案——三类日志事件（连接、帧、错误）的裁剪原则、核心指标集（连接数、帧率、延迟分位、背压水位）、trace上下文经自定义头注入的端到端追踪，以及验证清单。

## 一、日志：记什么、不记什么

传输层日志的价值在于回答"连接为什么断、消息为什么没到"，设计原则是"记录事件与元数据，不记录内容"。应记的三类事件：连接生命周期（dial开始/结果、握手完成含协商版本、关闭原因含分类码）；帧级摘要（方向、消息类型request/notification/response、method名、id、字节数——不记params/result内容，防止工具参数里的敏感信息落盘）；错误与降级（解析失败帧计数、超时按31篇kind分类、重连按28篇分型、限流触发）。不记的内容红线：完整请求参数与结果（含用户数据）、认证头与令牌、会话id之外的身份信息（会话id本身可记，用于串联回溯）。裁剪原则：每连接每事件一行、级别可调（INFO级默认只记生命周期，DEBUG级加帧摘要）、超长字段截断、高频路径（心跳）默认不打。

## 二、指标：传输健康的核心仪表盘

指标集按四个问题组织。问题一"现在有多少在跑"：当前连接数（按传输类型分标签）、活跃会话数、在途请求数。问题二"快不快"：握手延迟、请求RTT分位（P50/P95/P99，按method分标签）、SSE首字节延迟。问题三"丢没丢"：帧解析失败计数、通知丢弃计数（33篇背压丢弃）、重连次数（按原因分标签）、会话过期触发数。问题四"满不满"：写缓冲水位、事件重放缓冲占用、限流拒绝数、背压挂起时长。Prometheus风格的指标命名示例：mcp_transport_connections{transport="streamable_http",state="open"}、mcp_transport_request_duration_seconds{method="tools/call",quantile="0.99"}、mcp_transport_notifications_dropped_total。仪表盘最低配置三张图：连接与错误率总览、RTT分位趋势、资源水位（缓冲与限流）。告警建议：错误率环比突增、P99超SLA、丢弃计数非零持续五分钟、连接数骤降（可能上游故障）。

## 三、端到端tracing注入

MCP的JSON-RPC消息本身没有trace字段，跨客户端-服务器-代理链的追踪要靠传输层自定义头注入：客户端在每次POST/WS帧的附带头里放traceparent（W3C Trace Context格式）；代理与服务器提取后延续trace上下文，服务器侧的下游调用（数据库、HTTP）自动纳入同一trace；HTTP绑定的天然优势是头随请求走，stdio与自定义绑定则要在进程启动时经环境变量注入初始上下文（链路起点）。实现示例：

```typescript
import { trace, context, propagation } from "@opentelemetry/api";
import express from "express";

const app = express();
const tracer = trace.getTracer("mcp-transport");

app.post("/mcp", express.json(), (req, res) => {
  // 1) 提取上游trace上下文（traceparent等头）
  const parent = propagation.extract(context.active(), {
    traceparent: req.header("traceparent"),
    tracestate: req.header("tracestate"),
  });

  // 2) 开启本段span：method与消息元数据入attribute，内容不进
  context.with(parent, () => {
    const span = tracer.startSpan(`mcp ${req.body?.method ?? "?"}`);
    span.setAttributes({
      "mcp.message.type": req.body?.id !== undefined ? "request" : "notification",
      "mcp.method": req.body?.method ?? "",
      "mcp.message.id": String(req.body?.id ?? ""),
      "mcp.session.present": !!req.header("mcp-session-id"),
      "http.request.body_bytes": Number(req.header("content-length") ?? 0),
    });
    context.with(trace.setSpan(context.active(), span), async () => {
      try {
        await handle(req, res);            // 内部下游调用自动挂到同一trace
        span.setStatus({ code: 1 });       // OK
      } catch (e) {
        span.setStatus({ code: 2, message: String(e) });
        throw e;
      } finally { span.end(); }
    });
  });
});
```

反向注入（服务器到客户端方向）在SSE事件上不可加HTTP头，可以退而在事件流的首个自定义事件里携带trace标识，或仅做服务器侧单段追踪——按团队需要裁剪。

## 四、验证与治理清单

可观测性验收清单：日志能完整重演一次"连接建立→握手→三笔请求→断线→重连→重握手"的事件序列（用会话id过滤）；红线扫描——日志抽样检查无参数正文、无令牌（自动化用例：发送含标记字符串的参数，grep日志不得命中）；指标在压测下与真实连接数/吞吐对得上（对账用例）；trace能从客户端一路串到服务器的下游HTTP调用；DEBUG级别开关生效且生产默认INFO；跨实例（多Pod）的日志与trace按会话id/traceid可聚合；仪表盘与告警接入了35/38篇的代理与负载均衡层信号（而不只看应用层）。治理上，把"新传输类型必须带齐这三件套"写进代码评审清单，可观测性就从补丁变成内建属性。
