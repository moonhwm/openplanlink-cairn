# OAuth 2.1与传输层的结合：MCP作为OAuth资源服务器

**一句话摘要**：本文按2025-06-18版MCP授权规范讲解HTTP传输的认证架构——MCP服务器是OAuth 2.1资源服务器、令牌校验与WWW-Authenticate质询、元数据发现端点、动态客户端注册，以及Authorization Code+PKCE客户端流程的落地实现。

## 一、架构定位：MCP服务器=资源服务器

MCP的HTTP授权规范采用OAuth 2.1的资源模型分工：MCP服务器本身不管理用户登录，它是受保护的资源（Resource Server），只认访问令牌（Bearer Token）；用户认证、授权同意、令牌签发全部交给外部授权服务器（Authorization Server，AS）。这样MCP客户端拿到的是标准OAuth能力：跳转浏览器让用户在AS登录授权，拿授权码换访问令牌，之后每个HTTP请求带Authorization: Bearer <token>访问MCP端点。规范同时标准化了发现机制，让客户端无需手工配置AS地址：客户端请求MCP端点但无有效令牌时，服务器返回401加WWW-Authenticate头，其中resource_metadata参数指向RFC 9728的受保护资源元数据（/.well-known/oauth-protected-resource），元数据里再给出授权服务器URL；从授权服务器的/.well-known/oauth-authorization-server（RFC 8414）拿齐端点与能力。授权服务器按其注册策略工作；对无注册通道的场景，规范还允许AS实现RFC 7591动态客户端注册（registration_endpoint），公共客户端（桌面、移动MCP应用）经此自助登记。

令牌形态与校验：推荐持有者令牌为JWT，服务器本地校验签名（JWKS从AS的jwks_uri拉取并缓存轮换）或走内省端点（introspection，适合不透明令牌）。资源指示器（RFC 8707）要求授权请求带resource参数标识目标MCP服务器，AS据此签发受众受限（audience-bound）的令牌，防止"A工具集群的令牌被拿去B集群"的令牌混用——这是规范明确强调的防线。

## 二、服务器侧：校验中间件与质询

```typescript
import express from "express";
import { createRemoteJWKSet, jwtVerify } from "jose";

const ISSUER = "https://auth.internal";                    // 部署配置注入
const AUD = "https://mcp.internal";                        // 本服务器=资源标识
const RESOURCE_METADATA = `${AUD}/.well-known/oauth-protected-resource`;
const jwks = createRemoteJWKSet(new URL(ISSUER + "/.well-known/jwks.json"));

const app = express();
app.use(express.json({ limit: "4mb" }));

app.get("/.well-known/oauth-protected-resource", (_q, res) => {
  res.json({ resource: AUD,
             authorization_servers: [ISSUER] });           // 指路AS
});

function challenge(res: express.Response) {
  res.status(401).header("WWW-Authenticate",
    `Bearer resource_metadata="${RESOURCE_METADATA}"`).end();
}

app.use("/mcp", async (req, res, next) => {
  const auth = req.header("authorization") ?? "";
  const token = auth.startsWith("Bearer ") ? auth.slice(7) : undefined;
  if (!token) return challenge(res);
  try {
    const { payload } = await jwtVerify(token, jwks, {
      issuer: ISSUER,
      audience: AUD,                    // 受众绑定：防令牌混用
      clockTolerance: 5,
    });
    (req as any).principal = { sub: payload.sub as string,
                               scope: String(payload.scope ?? "") };
    next();
  } catch {
    return challenge(res);             // 无效/过期同样质询，细节不外泄
  }
});

// 工具层按scope授权（示例）：scope声明在AS侧配置
// requireScope("tools:read") / requireScope("db:write")
```

## 三、客户端侧：Authorization Code+PKCE流程

MCP客户端（尤其桌面与Web应用）的标准流程是授权码加PKCE：生成code_verifier与code_challenge（S256）；打开浏览器访问AS的authorize端点，带client_id、redirect_uri、code_challenge、resource（资源指示器）、state；本地起回环或自定义scheme回调接授权码；用码加verifier换token；把token注入传输的请求头。实现骨架：

```typescript
import { randomBytes, createHash } from "node:crypto";

export async function authorize(interactive: (url: string) => Promise<string>) {
  const verifier = randomBytes(32).toString("base64url");
  const challenge = createHash("sha256").update(verifier).digest("base64url");
  const state = randomBytes(16).toString("hex");

  // authorize URL（从AS元数据发现获得，此处示意拼装）
  const url = new URL(ISSUER + "/authorize");
  url.search = new URLSearchParams({
    response_type: "code",
    client_id: CLIENT_ID,                     // 经动态注册获得
    redirect_uri: "http://127.0.0.1:8915/callback",
    scope: "mcp tools",
    state,
    code_challenge: challenge,
    code_challenge_method: "S256",
    resource: "https://mcp.internal",         // RFC 8707：受众绑定
  }).toString();

  const code = await interactive(url);        // 宿主开浏览器+本地回调服务器
  const tokenRes = await fetch(ISSUER + "/token", {
    method: "POST",
    headers: { "content-type": "application/x-www-form-urlencoded" },
    body: new URLSearchParams({
      grant_type: "authorization_code",
      code, code_verifier: verifier,
      client_id: CLIENT_ID,
      redirect_uri: "http://127.0.0.1:8915/callback",
    }),
  });
  const { access_token, refresh_token, expires_in } = await tokenRes.json();
  return { access_token, refresh_token, expires_in };
}

// 传输注入：所有POST/GET/DELETE带 Authorization: Bearer <access_token>
// 401时：若有refresh_token走刷新；否则重走authorize（用户重新同意）。
```

令牌生命周期要点：访问令牌短寿命（分钟到小时级）；刷新在传输层透明处理（401触发一次刷新重放，失败才打断用户）；令牌存系统凭据库（OS keychain），绝不明文落盘或入日志；浏览器嵌入场景注意不要把令牌暴露给页面JS。

## 四、验收清单

认证链验收清单：无令牌401且WWW-Authenticate带resource_metadata；元数据发现两级（protected-resource→authorization-server）可达且内容与文档一致；伪造签名、过期、错受众三类令牌均401且日志计数；scope不足的调用被拒（403或insufficient_scope错误）；刷新流程在令牌过期后自动完成、会话不中断；动态注册开关按AS策略启用且注册响应不含秘密回显；stdio服务器不受此机制影响（本地信任模型，41篇）；审计日志记录sub、scope、端点、结果，不记令牌本体。通过后，MCP远程端点即获得与主流API同级的认证水位，并能接入企业既有身份体系。
