# 02 MCP协议核心机制回顾：JSON-RPC 2.0、传输层与网关的协议接口

网关的一切设计都建立在MCP协议的既有约定之上。理解协议的消息模型、生命周期与传输形态，才能明白网关在哪些点上可以介入、哪些点必须透明转发、哪些点需要小心兼容。本篇以网关实现者的视角回顾MCP的核心机制：JSON-RPC 2.0消息骨架、initialize握手、能力协商、三类服务端原语（工具、资源、提示词）以及客户端原语（采样、根目录、通知），并说明各版本传输层的关键差异对网关的影响。

## 一、JSON-RPC 2.0消息骨架与网关的解析义务

MCP的每一条消息都是一个JSON-RPC 2.0对象，分为请求、响应与通知三类。请求携带id、method与可选params；响应要么是带result的成功应答，要么是带code、message与data的error对象；通知没有id，用于单向事件传递。网关作为中间人，至少要解析method与id两个字段才能完成路由：method决定转发目标，id决定应答配对。对params与result，网关原则上可以不解析而直接透传，但要做策略过滤或参数校验时就必须深入语义，这是"透明代理"与"理解型代理"的分水岭。

```json
// 客户端请求：调用工具
{"jsonrpc":"2.0","id":41,"method":"tools/call",
 "params":{"name":"read_file","arguments":{"path":"notes/todo.txt"}}}
// 服务器成功响应
{"jsonrpc":"2.0","id":41,"result":{
 "content":[{"type":"text","text":"...文件内容..."}],
 "isError":false}}
// 服务器通知：工具清单发生变化
{"jsonrpc":"0","method":"notifications/tools/list_changed"}
```

注意上例第三条里jsonrpc版本号应为"2.0"，笔误成"0"恰好提醒网关实现者：真实世界总有不合规对端，网关解析必须宽容而输出必须严格。JSON-RPC的错误码区间也有讲究：-32700解析错误、-32600无效请求、-32601方法不存在、-32602参数无效、-32603内部错误，自定义错误应落在-32000到-32099的服务器区间。网关在向客户端报告上游故障时，应保留原始code并附加网关侧的追踪标识，便于排障时对号入座。

## 二、生命周期：initialize握手与版本协商

MCP连接的第一件事永远是initialize请求。客户端在params中声明protocolVersion（如"2025-06-18"）、自身能力（capabilities）与客户端信息；服务器响应自己支持的版本与能力。双方以通知initialized收尾，握手完成前不允许发送其他请求。版本协商规则是：若服务器支持客户端请求的版本，必须原样响应该版本；否则响应自己支持的最新版本，由客户端决定是否断开。

对网关而言，initialize是最繁忙的关口，因为它要对上扮演服务器、对下扮演客户端：先接受客户端的握手，再逐一与上游服务器握手，把多份能力清单"与"合并后呈给客户端。能力协商里有三个网关必须处理的字段：tools.listChanged表示服务器会主动通知工具变更；tools.call的结果可能包含structuredContent结构化输出；sampling意味着服务器希望反向请求客户端做模型采样——网关必须决定是否、以及如何把这种反向请求转发给客户端，这往往是聚合实现中最容易被遗漏的分支。

## 三、服务端原语与传输层差异

三类服务端原语决定了网关聚合的主要对象。工具是模型可调用的函数，以name、description与JSON Schema格式的inputSchema描述；资源是客户端可读取的数据，通过URI定位，支持templates模板化；提示词是预置的提示模板，带可选参数列表。网关聚合时要分别处理三者的命名空间与去重，工具靠名称、资源靠URI、提示词靠名称加参数签名。

传输层经历了一次重要演进。早期规范定义stdio（标准输入输出上的换行分隔JSON）与HTTP+SSE（一个GET建立事件流，一个POST发送请求）。2025年规范以Streamable HTTP取代SSE：单一HTTP端点，POST承载请求与响应，服务器可按需升级为SSE流以支持长连接与流式进度。对网关的直接影响有三点：一是stdio上游需要网关维护子进程生命周期；二是Streamable HTTP上游是请求-响应语义，网关可以做连接复用与池化；三是会话标识从隐式连接变为显式的Mcp-Session-Id头，网关必须把它与客户端会话建立映射，否则多后端会话在重连后会错乱。

- stdio上游：网关负责子进程拉起、stdin/stdout管道读写与僵尸进程回收；
- Streamable HTTP上游：网关复用HTTP连接池，维护会话头映射；
- 客户侧：网关按客户端宣告的传输能力选择对外形态，常见做法是对外仍提供stdio端点以兼容老客户端。

## 四、分帧细节与网关的容错纪律

除消息结构外，分帧是容易被低估的实现细节。stdio传输使用换行分隔消息，且明确不允许在JSON内部出现裸换行，这意味着网关读写子进程管道时必须按行缓冲而不能按固定字节块切分；一旦上游服务器在输出中混入了日志行或调试信息，网关需要识别"不是合法JSON的行"并把它归类为stderr级别的噪音，而不是让整条连接崩溃。Streamable HTTP则以HTTP报文天然分帧，但批量请求（JSON-RPC batch）在部分版本中被允许，网关要么完整支持数组消息的拆分与重组，要么在能力声明中明确不支持并在握手阶段协商排除。

容错纪律上还有两条经验值得固化。其一，超时责任必须由网关兜底：协议并未规定各类请求的标准时限，一个挂起的tools/call若无人设限，客户端会永久等待；网关应按方法类型设置分级超时，并在超时后向上游发送取消通知（若版本支持）再向客户端返回明确错误。其二，通知是易失的：JSON-RPC通知没有应答，网关无法确认上游是否收到，因此任何依赖通知的机制（如能力变更后的清单刷新）都必须有主动轮询兜底，不能把正确性建立在通知必达的假设上。

## 五、小结与要点回顾

协议回顾的落点是网关的三条实现纪律：解析层面，method与id是路由必需，其余按需深入；生命周期层面，initialize的双向扮演与能力合并是聚合的核心难点；传输层面，stdio与Streamable HTTP的会话语义差异决定了网关连接管理的两套代码路径。后续讨论路由表生成、能力漂移同步时，都会反复回到这些协议原语。

- JSON-RPC三消息类型与错误码区间是网关日志与排障的基础词汇；
- initialize能力合并与sampling反向转发是聚合实现的两处暗礁；
- Mcp-Session-Id映射是Streamable HTTP多后端会话管理的钥匙。
