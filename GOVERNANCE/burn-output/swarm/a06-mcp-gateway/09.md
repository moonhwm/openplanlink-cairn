# 09 本地网关配置文件设计与热加载

配置是网关与运维者之间的主要接口，配置文件的质量直接决定网关的使用体验与安全性。一份好的网关配置要回答五个问题：上游有哪些、怎么连、叫什么名字、允许做什么、何时生效。本篇讨论配置文件的分层结构、校验策略、热加载机制与迁移兼容，并以一份带注解的完整配置样例贯穿说明。文中所有地址、命令与令牌均为演示占位，不含任何真实环境信息。

## 一、分层结构与关键段落

推荐把配置拆成五个逻辑段：listeners（对外通道）、upstreams（上游清单）、namespacing（命名规则）、policies（策略）、telemetry（观测）。分层的好处是变更频率分离——上游清单几乎天天加，策略偶尔调，通道配置基本不动，热加载与校验可以按段区别对待。每段的设计要点如下：listeners声明对外暴露的stdio桥接、域套接字与回环HTTP及其访问控制参数；upstreams是核心，每个条目含唯一name、transport类型、连接细节、工具前缀与凭据引用（引用而非明文，凭据本体放独立保管区）；namespacing定义冲突消解规则；policies声明默认动作与覆盖规则；telemetry控制日志级别、指标暴露与审计开关。

```yaml
# 网关配置示例（全部为演示占位值）
listeners:
  - type: socket
    path: "/run/mcp-gateway.sock"
    mode: "0660"
  - type: loopback_http
    port: 8642
    token_file: "var/access-token"   # 本地访问令牌文件路径

upstreams:
  - name: fs
    transport: stdio
    command: ["mcp-fs-server", "--root", "/data/projects"]
    namespace: { prefix: "fs_" }
    credentials: none
  - name: knowledge
    transport: http
    url: "https://kb.internal.example/mcp"
    credentials: { ref: "vault:kb-reader" }  # 凭据引用，非明文
    namespace: { prefix: "kb_" }

policies:
  default: ask                      # 未知工具要求确认
  rules:
    - match: { tool: "fs_*" }
      action: allow
      audit: full
    - match: { tool: "kb_admin_*" }
      action: deny

telemetry:
  log_level: info
  audit: { enabled: true, redact: [ "token", "password" ] }
```

## 二、校验优先：配置错误的失败方式

配置加载必须先过校验再生效，失败方式有两种选择：全量拒绝（任何一处错误都不加载新配置，保持旧配置运行）与部分接受（跳过错误段落）。网关应当选择全量拒绝，因为部分接受会造成"我以为改了"的错觉，比配置报错更危险。校验分三层：语法层（YAML/JSON可解析）、结构层（schema校验，字段类型与必填项）、语义层（跨字段一致性，例如前缀冲突、引用的凭据不存在、规则匹配不到任何工具）。语义层的价值最高也最常被省略，例如两个上游声明了相同前缀，语法完全正确但运行时必然路由混乱，必须在加载前拦截。

校验失败的错误消息要面向修复而非面向机器：指出文件、行号、字段路径与期望格式，并给出最接近的合法示例。配置漂移的防线同样重要：网关可以在每次加载时记录配置的摘要哈希到审计日志，让"配置在何时被谁改成了什么样"成为可追溯事实。

## 三、热加载机制

热加载的目标是"改配置不重启、不断会话"。实现要点有四。第一，触发方式支持文件监听与显式信号两种，文件监听要做防抖（编辑器的保存会触发多次事件），显式信号（如向网关发送SIGHUP或管理命令）作为兜底。第二，计算差异集：新旧配置对比后得到新增、删除、变更三类上游，只对受影响的上游执行操作，未受影响的会话原样保留。第三，删除与变更的上游要处理存量会话：通知客户端能力变更（发送tools/list_changed通知），等待在途调用结束或超时收割后再断开上游连接。第四，回滚保护：新配置生效后若上游健康探测在宽限期内全部失败，自动回滚旧配置并告警，防止一次手滑让全网关瘫痪。

## 四、配置规模化的管理技巧

当上游数量增长到几十个、策略规则上百条时，单文件配置会遇到可读性与合并冲突的双重问题。此时应支持配置分段包含：主配置通过include指令引入upstreams与policies目录下的分片文件，每个上游或每组规则独立成文件，既便于代码评审时的差异阅读，也避免多人协作时的合并冲突。分片的命名建议与上游name一致，删除一个上游等于删除一个文件，操作直觉且可回滚。策略规则增多后还应支持规则的显式排序与优先级字段，避免依赖声明顺序这种隐性语义——顺序依赖是配置bug的温床。

另一个规模化技巧是配置生成：上游清单若已存在于CMDB、服务目录或注册表，不必手工同步维护两份，用生成器从权威源拉取并渲染配置分片，人工只维护策略与命名等判断性内容。生成器要幂等且输出稳定（同输入必同输出、字段顺序固定），这样生成物可以安全入库评审。经验上，配置管理的终态是"权威源加生成器加仓库评审"三件套，网关只消费最终产物，人只在判断性环节出现。

## 五、版本迁移与配置即代码

配置格式会随网关功能演进而变化，一开始就要内置版本字段与迁移器：每个版本升级附带一段把旧格式转换为新格式的函数链，加载旧配置时逐级迁移。团队场景下应把配置纳入版本管理（配置即代码）：仓库存配置模板，部署时由安装器合并本地差异（如本机路径、端口），凭据永不入库。这样配置的评审、回滚与多机分发都复用代码管理的成熟工具链。

- 五段结构：listeners、upstreams、namespacing、policies、telemetry；
- 校验三层，全量拒绝优先，错误消息面向修复；
- 热加载四要点：防抖触发、差异计算、存量会话处理、失败回滚；
- 版本字段加迁移器，配置模板进仓库，凭据只留引用。
