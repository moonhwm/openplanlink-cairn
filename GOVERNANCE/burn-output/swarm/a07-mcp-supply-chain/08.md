# 08 制品签名与验证实践：从哈希到透明日志

## 引言

哈希校验能发现"内容变了"，签名则能证明"是谁发布的"，并支持非对称、可规模化分发的验证。对MCP服务器这类频繁更新的制品，签名加自动验证是把来源验证从人工比对升级为机器执行的关键。本文讲解签名体系的核心概念、主流实践与落地步骤，并覆盖验证失败时的处置。

## 一、签名体系核心概念

制品签名指发布者用私钥对制品摘要做密码学签名，使用者以对应公钥验证。它同时提供完整性与身份证明：摘要不匹配说明内容被改，签名不通过说明并非持有私钥者发布。现代实践进一步解决"公钥从哪来"的问题：一是基于注册表账户的密钥关联，签名与包发布身份绑定；二是基于证书透明机制的公开审计日志，每次签名记录进可公开验证的追加式日志，攻击者即便短期窃取密钥也无法无声地在日志外发布"合法"制品；三是基于短周期受控颁发的证书，私钥只在受信颁发瞬间可用，之后验证依赖日志证据。这三种机制共同削弱了"单一私钥终身依赖"的脆弱性，使签名体系具备可追责与防抵赖能力。

## 二、验证实践与自动化

对使用者侧，验证应当全自动化并嵌入获取流程。以容器镜像为例，标准动作是以摘要锁定拉取，再校验其签名：

```bash
# 以不可变摘要拉取镜像(摘要占位)
docker pull registry.internal/mcp/search-server@sha256:摘要值占位

# 使用验签工具校验镜像签名与身份(以通用签名工具为例)
cosign verify \
  --certificate-identity "发布者身份标识占位" \
  --certificate-oidc-issuer "颁发方标识占位" \
  registry.internal/mcp/search-server@sha256:摘要值占位
```

对语言包生态，则应在安装与构建流水线中启用"安装前验签"选项，使未签名或验签失败的包直接中断流程。自动化验证要点有四：其一，验证必须发生在安装或运行之前，任何"先跑起来再说"都不被允许；其二，身份校验值（发布者标识、颁发方标识）纳入配置管理，防止攻击者诱导放松参数；其三，验证结果写入日志，失败即告警；其四，对自研服务器，签名应内置于发布流水线，签名动作使用托管密钥服务，私钥不落开发者本机。

## 三、落地步骤与失败处置

分阶段落地建议：第一步，为自研MCP服务器发布流程接入签名，产出带签名与透明日志证据的制品；第二步，在镜像与包的获取入口部署自动验证策略，先告警模式运行一个月观察误报；第三步，切换为强制模式，未通过验证的制品无法进入内部镜像源与制品库；第四步，把签名状态纳入准入登记与季度复检。验证失败处置清单：

- 立即停止安装与运行，隔离已下载制品；
- 核对失败原因：身份不匹配、证书过期、摘要不符分别对应不同事件级别；
- 身份不匹配或摘要不符：按疑似供应链事件上报，保留制品与日志证据；
- 证书过期或工具配置问题：修复后重新验证，不改放行规则；
- 任何情形下禁止以"临时跳过验证"参数放行生产制品。

## 结语

签名把"信任发布者"从口头判断变成密码学事实，透明日志又让发布行为本身可审计。MCP生态的成熟标志之一，就是签名验证成为安装的默认前提而非可选加固。组织应先从自研制品签名做起，再逐步对外部制品提出验签要求，最终实现无签名不部署。结合前述哈希登记与后续物料清单，三层证据互相补位，构成来源验证的完整技术底座。
