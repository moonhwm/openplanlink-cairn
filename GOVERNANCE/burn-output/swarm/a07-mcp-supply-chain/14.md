# 14 语义化版本的风险：SemVer不能替代验证

## 引言

语义化版本（SemVer）用主版本、次版本、修订号三段数字表达变更性质：不兼容变更升主版本，新增功能升次版本，缺陷修复升修订号。它极大改善了依赖沟通，但也催生了一种危险惯性——"修订号升级无需审查"。本文分析语义化版本在供应链场景的风险构成，说明为何它只能作为参考信号而非信任依据，并给出基于变更事实而非版本号段位的升级决策方法。

## 一、语义承诺的三个缺口

第一，承诺靠自觉。语义化版本是发布者的自我声明，没有任何机制保证"修订号只改了小问题"。恶意更新伪装成补丁版本、以及无意但破坏性巨大的补丁（依赖行为漂移、隐式接口变化）在通用生态中屡见不鲜。第二，语义边界模糊。是否不兼容、是否纯修复，判断权在发布者；对调用方而言的破坏性变更，发布者可能视为内部重构。第三，供应链视角下"最小变更"仍可携带最大危害：投毒代码只需要十几行，完全可以藏在一个修订号里。因此"只升修订号所以安全"的推理在供应链安全上不成立，版本号段位是信息，不是证据。

## 二、变更事实优先的升级决策

正确的决策输入是变更事实：这次更新实际改了什么。三类差异构成最低审查集。代码差异：两次版本之间的提交与文件变更，关注新增的网络请求、进程执行、编码解码与动态加载逻辑。依赖差异：依赖锁文件的前后比对，新增或升级的传递依赖同样进入审查。行为差异：工具列表、工具描述、能力声明的比对——描述文本的改动在MCP场景尤其敏感，因为它直接作用于模型行为。据此形成升级决策流程：

```text
升级审查(当前版本V1 -> 候选版本V2):
  1. 获取V1到V2的提交清单与变更说明
  2. 生成三类差异: 代码差异/依赖差异/行为差异
  3. 风险判定:
     代码差异含网络/执行/混淆特征 -> 人工深审
     依赖差异含新增来源不明的依赖 -> 拒绝或深审
     行为差异含工具描述实质变化 -> 评估对模型影响
  4. 通过后: 预发验证 -> 灰度 -> 更新锁定
  5. 无论版本号段位如何, 流程一致
```

## 三、把版本号放回正确位置

版本号段位的合理用途：排定审查优先级（主版本升级通常涉及更大面，安排更多时间）；识别上游态度（频繁的修订号轰炸可能是质量信号）；作为资产账本的索引键。不合理用途：替代代码审查、作为跳过哈希校验的理由、作为"兼容因此直接合并"的依据。实践清单：

- 升级审查表单不设"小版本快速通道"，只有"加急通道"且事后补审；
- 自动化机器人例行提交语义化版本，但差异审查不可省略；
- 对上游违反语义承诺的历史做记录，作为信任评分输入；
- 锁文件升级的合并请求必须附带三类差异报告链接；
- 教育团队：段位表达意图，差异表达事实，安全决策依据事实。

## 结语

语义化版本解决了沟通问题，没有解决信任问题。在供应链安全语境里，"改了什么"永远优先于"号称是什么级别的改动"。以三类差异为最低审查集、以流程一致性为纪律、把版本号降级为索引与优先级信号，组织就能既享受语义化版本的沟通红利，又不把安全决策外包给上游的自觉性。这是版本治理从形式走向实质的关键一课。
