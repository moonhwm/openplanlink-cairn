# 03 MCP服务器分发生态与注册表现状

## 引言

供应链安全的许多问题根源在分发环节：代码从开发者机器到达用户环境的路径决定了攻击者有多少插入机会。MCP生态目前没有统一的官方注册中心，分发渠道呈现多样化与碎片化特征。本文梳理当前主要的分发形态，分析各自的信任假设与风险点，并给出针对不同渠道的差异化验证策略。

## 一、主要分发形态

第一种是源码直装：用户从代码仓库克隆源码，本地安装依赖并启动。这种形态下信任锚是仓库账号与提交历史，风险在于仓库被接管、分支被篡改以及构建过程在用户本地执行时拉取的依赖不可控。第二种是语言包管理器分发：服务器以包形式发布到各类包注册表，用户通过包名加版本安装。信任锚是注册表账号与发布记录，风险在于名称抢注、账号钓鱼与版本投毒。第三种是容器镜像分发：服务器打包为镜像，从镜像仓库拉取。信任锚是镜像仓库命名空间与摘要，风险在于标签可变性与镜像层夹带。第四种是托管服务形态：服务器由第三方云端运行，客户端仅持远程连接配置。信任锚是服务域名与租户隔离，风险在于服务端代码不可审计、数据经手第三方以及连接凭据的管理。

## 二、信任假设与典型风险点

四种形态的信任模型差异显著。源码直装把构建责任交给用户，好处是理论上可完全审计，坏处是绝大多数用户不会真正逐行审读，且本地依赖解析引入了注册表层面的间接风险。包管理器分发最便捷，也最容易被名称混淆攻击利用：攻击者注册与热门项目仅差一个字符的包名，配合生成的说明文档诱导安装。容器分发具有环境一致性优势，但可变标签使"每次拉取同一镜像"并不成立，必须以摘要定位制品。托管服务形态将审计责任完全转移到服务提供方，用户只能依赖合同、认证与黑盒测试，是四类中信任要求最高的形态。此外，还有一种常见的聚合形态：第三方整理的"服务器合集"仓库或一键安装脚本，它把多个上游来源打包，实际引入了合集维护者这一额外信任节点，而用户往往意识不到。

## 三、差异化验证策略

针对各分发形态，验证重点应当区别对待，形成如下策略清单：

- 源码直装：核对仓库归属组织、提交者身份与发布标签签名；在隔离环境执行构建；锁定依赖清单并离线安装。
- 包管理器分发：逐字符核对包名与发布者；优先选择有维护历史与下载规模佐证的包；安装时锁定精确版本并校验完整性哈希。
- 容器镜像分发：始终以不可变摘要引用镜像，不使用可变标签；启用镜像签名验证；扫描镜像层中的可疑入口与外联地址。
- 托管服务形态：核查服务提供方身份与合规认证；签署数据处理协议；仅授予最小数据范围并启用审计日志导出。
- 合集与一键脚本：先展开审查合集引用的每个上游来源；脚本必须在沙箱中通读后再执行；禁止直接在生产配置中粘贴来路不明的安装命令。

一个以摘要锁定容器镜像的示例：

```yaml
services:
  search-server:
    image: registry.internal/mcp/search-server@sha256:替换为实际摘要值
    read_only: true
    cap_drop: [ALL]
    networks: [mcp-egress]
```

## 结语

分发形态决定信任锚的位置，信任锚决定验证动作的内容。碎片化生态中没有放之四海皆准的验证方法，只有针对"源码、包、镜像、托管、合集"五类形态分别设计的差异化策略。实践中最常见的错误，是用对待官方渠道的默认信任去对待合集脚本或来路不明的包名。建立"渠道分类、锚点明确、动作对应"的思维习惯，是供应链防护从口号走向操作的第一步，后续版本锁定与来源验证专题将在此基础上展开具体工程细节。
