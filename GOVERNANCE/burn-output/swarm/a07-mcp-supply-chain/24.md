# 24 传递依赖审计与依赖树治理

## 引言

直接依赖是你选择的，传递依赖是选择带来的。供应链投毒的高发区恰恰在传递依赖：层级深、无人逐一审视、名称冷门更容易被抢注。本文讨论MCP服务器场景的依赖树治理：树的构成与风险来源、审计方法、治理策略与持续运营。

## 一、依赖树的风险来源

传递依赖的风险来自四个方面。数量放大：一个现代服务器动辄引入上百个传递依赖，审查精力被摊薄，攻击者专挑"无人看守的叶子"。冷门劫持：低维护频率的底层包（多年未更新、维护者稀少）一旦被接管或抢注，影响所有引用链。重复实现：同一功能存在多个实现包，攻击者投毒其中较冷门者，等待粗心的引用者。幽灵依赖：构建脚本或运行时动态引入不在清单中的包，审计对象本身不完整。此外还有依赖混淆：内部私有包名被注册到公共源，构建系统在公共源解析到同名恶意包。MCP服务器多为轻量项目，作者安全意识参差，这些风险被进一步放大。

## 二、审计方法

第一步，拿到完整树。以锁文件为准确输入（第15篇），生成全量依赖树（含层级、版本、来源），不依赖声明文件的粗略范围。第二步，逐层风险标注。对每个节点标注：维护状态（更新频率、维护者数量、归档与否）、流行度参考、已知漏洞、来源可验证性。第三步，聚焦高风险节点。审计优先级排序：新增节点（升级审查时）、底层基础节点（被广泛复用的工具类包）、低维护节点、来源不明节点。第四步，专项检查。查找构建脚本中的动态引入、检查私有命名与公共源的隔离配置、识别树中的重复实现包并评估替换统一。第五步，输出依赖审计报告：树统计（深度、宽度、总数）、高危节点清单、整改建议（升级、替换、隔离或接受并监控）。

依赖树审查的伪流程：

```text
依赖审计(服务器S, 锁文件L):
  tree = 解析(L)
  for node in tree:
    标注(维护状态, 漏洞, 来源)
  聚焦 = 新增 ∪ 低维护 ∪ 来源不明 ∪ 基础设施类
  for node in 聚焦:
    if 维护者近期变更且无公告: 标记高危, 建议冻结版本+盯防
    if 存在同功能更活跃替代: 建议替换评估
  输出报告并更新资产库依赖索引
```

## 三、治理策略与运营

治理四策略。升级：通过版本升级消除漏洞节点，走第14篇的变更审查。替换：以维护更活跃、来源更可信的等价包替换高风险包，需功能验证。隔离：无法立即处置的，以运行隔离（限制网络与文件）压缩其可利用性。接受并监控：低风险节点登记监控，纳入漏洞情报命中范围。运营清单：

- 每台服务器登记依赖树快照，随版本更新；
- 漏洞情报以依赖坐标检索全部资产，工单化响应；
- 私有包名启用公共源占位或前缀隔离，防依赖混淆；
- 构建禁止动态解析，消除幽灵依赖；
- 季度统计：依赖总数趋势、高危节点存量、整改完成率；
- 新投毒案例复盘后，检查组织内是否有同款命中。

## 结语

依赖树治理承认一个现实：不可能人工读完全部传递依赖，但完全可以知道树里有什么、哪些节点最危险、出事时影响谁。以锁文件为准、以高危节点为焦点、以四种策略闭环，传递依赖就从无人区变成有账可查的治理对象。依赖树也是SBOM（第9篇）与漏洞响应（第44篇）的共同底层数据，值得作为基础设施长期维护。
