# 11 包完整性与哈希校验实践

## 引言

哈希校验是供应链工具箱中最朴素也最可靠的技术：用摘要函数为制品生成指纹，任何一位内容改动都会导致指纹剧变。它不依赖发布者配合、不需要密钥基础设施，是任何组织都能立即启用的控制。本文讲清哈希校验的正确姿势：基准如何取得、校验嵌入哪些环节、锁文件如何维护，以及常见的失效模式。

## 一、基准的取得与保管

哈希校验的第一原则是基准必须来自经过身份验证的渠道（详见第10篇），绝不可与制品取自同一镜像页面。取得基准的优先顺序：官方发布页公布的摘要；签名体系中随签名携带的摘要；独立第三方镜像的多源比对（多源一致可提高置信度，但不能替代官方基准）。基准应集中保管在受控的锁文件中，与版本号绑定。锁文件是"版本到摘要"的登记账本，进入版本控制，修改需评审。保管要点：锁文件按环境分份（生产与试验隔离）；摘要字段记录算法与值（不同算法摘要不可互换比对）；每条记录附来源渠道与获取日期。

## 二、校验环节的嵌入

校验应当嵌入四个环节，构成全链路防护。环节一：下载后、安装前。本地重算摘要与基准比对，一致才允许安装。环节二：入镜像源前。外部制品同步进内部源时强制校验，未登记基准的制品默认拒绝，防止内部源成为二手污染源。环节三：部署时。容器编排以摘要引用镜像，拉取动作本身即校验。环节四：运行期巡检。定期对已部署制品重算摘要，比对登记值，发现运行环境中的偷换。

多环节校验的脚本骨架：

```bash
#!/usr/bin/env bash
# 制品完整性巡检脚本骨架
set -euo pipefail
LOCKFILE="artifacts.lock"   # 格式: 名称 版本 摘要
while read -r name ver digest; do
  file="store/${name}-${ver}.tar.gz"
  actual=$(sha256sum "$file" | awk '{print $1}')
  if [ "$actual" != "$digest" ]; then
    echo "不匹配: ${name} ${ver}" >> incident.log
    # 触发告警并冻结该制品
  fi
done < "$LOCKFILE"
```

## 三、锁文件维护与失效模式

锁文件维护规则：新版本准入时新增条目并双人复核；版本退役时条目归档而非删除，供追溯；上游公布新摘要时，须先经身份验证渠道确认再更新锁文件，防止攻击者伪造"官方更正"。常见失效模式与对策清单：

- 校验放行参数被滥用：脚本设跳过开关即失去意义，跳过需高级权限并留痕；
- 基准渠道被替换：定期多源比对官方页面，域名变更走对照表复核；
- 只校验主制品不校验依赖：锁文件须覆盖关键传递依赖，配合锁文件机制固化整个依赖闭包；
- 算法弱化：优先使用现行安全强度摘要算法，避免已淘汰算法；
- 校验结果不留痕：每次校验输出日志，失败即事件，不允许静默重试。

## 结语

哈希校验的价值在于简单到无法绕过、可靠到无法伪造（在基准可信前提下）。它是签名体系的降级备份：即便生态签名尚未普及，哈希锁文件也能立即提供"内容未被替换"的保证。配合锁文件的集中登记与四环节嵌入，组织可以在不等待任何外部条件的情况下，把制品完整性管控提升到可审计水平。这正是供应链防御从零到一最稳妥的一步。
