# A2A网络额度资产六维穷举清单——时间/模型/平台/席位/用途/约束全覆盖

> 知识资产编号：G1 ｜ 专题：额度治理（账本层） ｜ 适用工程：harmony-app（铃语）
> 本篇自包含、可独立持久化。工程事实引自批次任务书共享上下文；文中具体数值均为示例占位，以实际台账为准。

## 一、文档定位与要解决的问题

harmony-app（代号铃语）是面向老年用户的鸿蒙股票异动播报应用，采用纯ArkTS加云函数架构：`EntryAbility`负责Push初始化并以onNewWant携带alertId拉起定位，`Index.ets`以List卡片流呈现并靠5秒前台轮询的`AlertPoller`兜底，`AudioPlayer`基于AVPlayer播放云端TTS音频流。围绕这样一个工程，知识生产由机主的A2A（Agent-to-Agent）智能体网络分席位完成——本篇即该网络中写手席位产出的治理文档。

A2A网络里流转的模型额度，本质上是一类特殊资产：它会被时间腐蚀（窗口关闭即清零）、被平台割裂（各平台独立记账）、被约束限制（模型锁、限速、合规红线）。没有统一登记制度时，实践中反复出现三类损失：

第一，过期作废。限时体验类额度在截止前无人认领任务，窗口一关全部归零，属于最可惜的浪费形态。第二，错配挪用。一次性高价值额度被拿去做低价值的闲聊验证或重复检索，用掉之后再遇不可重试的深度任务时已无券可用。第三，违规误用。忽略模型锁定令——例如本席位已按机主常设令锁定GLM-5.3-Flash、不得申请切换GLM-5.3（额度原因），一旦误切即造成超额计费并违反常设令。

六维穷举清单的目的，就是把"额度"从一笔模糊的余额还原为一组坐标明确的资产单元，让每个单元都能回答六个问题：何时失效、能调哪些模型、在哪个平台记账、归谁调度、适合干什么、有什么禁令。账先立清楚，后续的效率优化、排期、降级、监控才有落脚点。

## 二、为什么必须是六维，而不是一张余额表

余额表只回答"还剩多少"，资产管理还必须回答"什么条件下能用"。用三组对照说明缺维的后果：

同量不同期：同样一百万token，挂在"72小时窗口"下与挂在"每月1日重置"下是两种资产——前者是易腐品，必须按截止时间倒排燃烧（方法见G3）；后者是现金流，应当均匀消耗并保留峰值余量。若清单缺时间维，两者混记在一列里，排期必然错配，窗口额度在犹豫中过期。

同名不同账：GLM-5.3-Flash在开放平台API的余量与在席位宿主内置的调用配额，分属两个独立账本，互不抵扣、互不影响。缺平台维时，看总量似乎充裕，实际当前要用的那个账本可能已经见底，任务中途断供。

同额不同权：归属席位自治的额度可由写手在约束内自行排期；归属机主总池的额度必须按批次任务书指令消耗。缺席位维时，写手擅自调度总池额度，即构成越权，且总池被悄悄掏空后机主浑然不觉。

结论：时间、模型、平台、席位、用途、约束六个维度构成额度资产的最小完备坐标集，缺任何一维都会留下"暗账"——能被无意挥霍却无人察觉的额度。所谓"穷举"，不是把维度列得越多越好，而是每个维度都不可再合并、不可再省略。

## 三、六维定义与取值域

### 3.1 时间维：额度的时间属性

时间维回答"这份额度何时可用、何时失效"，是排期（G3）与过期预警（G5）的输入源。取值域四类：

| 类型 | 定义 | 价值衰减形态 | 登记要点 |
|---|---|---|---|
| 限时窗口型 | 起止时间戳内可用，窗口关闭清零 | 随截止逼近线性衰减至零 | 起止精确到分钟，含时区 |
| 持续配额型 | 按日/周/月周期重置 | 锯齿形，周期末未用部分作废或结转 | 重置周期、重置时刻、当期已用 |
| 一次性券型 | 总量固定，用完即止，无时间衰减 | 阶梯递减，无截止压力 | 初始总量、剩余量、消耗明细索引 |
| 可结转型 | 周期末剩余按比例滚入下期 | 衰减被结转率缓解 | 结转比例、结转上限 |

登记示例：某窗口型资产记为"2026-08-27 22:20 至 2026-08-30 22:20，可用GLM-5.3-Flash调用400次"——起点即本批次任务目录时间戳，终点与剩余次数都落在纸面上，G5的TTL预警才有依据。模糊记法（"三天内有效"）会让预警无从算起，是登记大忌。

### 3.2 模型维：额度可抵扣的模型范围

模型维登记额度可抵扣的模型清单，粒度必须到具体模型标识，禁止只写厂商名。至少区分两档：GLM-5.3为深度推理档，适合架构审计、合规复核、疑难排障类重任务；GLM-5.3-Flash为高速产出档，适合批量文档写作、清单枚举、格式整理类高体量任务。

模型维必须与约束维的"模型锁"联动登记。本席位实况即一例：G组-1号按机主常设令锁定GLM-5.3-Flash，禁止申请切换GLM-5.3，锁因记录为"额度原因"。于是该席位名下所有资产单元的模型维取值域收窄为一元集，这是硬边界——深度推理类任务在Flash上只能尽力产出并如实自评，不得以"任务太难"为由申请越锁换模型。清单里把这条锁写成显式字段，新席位接手时第一眼就能看到，越锁误用的概率大幅下降。

### 3.3 平台维：记账主体

平台维登记额度的记账主体。同一模型在不同平台各立账本，至少区分四类：

其一，开放平台API：按token计费，通常有明确的余量接口或账单页，对账最容易。其二，席位宿主：写手运行环境内置的调用配额，常按调用次数或点数计，往往没有实时余量接口，只能靠本地台账扣减，对账靠周期盘点。其三，终端应用内：如聊天应用会员权益附带的模型调用权，按会员周期刷新，常有限速但无总量。其四，本地或私有部署：按算力时间记账，计费逻辑自定义。

平台维的登记关键字段是"计费单元"——token、调用次、点数还是时长。跨平台看总账之前，必须先约定换算口径，否则把"次"和"token"直接相加得到的总账数字毫无意义。

### 3.4 席位维：归属与调度权

席位维登记额度归属与调度权，取值域三类：席位自治（额度划归某写手席位，席位在约束内自行排期）、机主总池（归机主统一调度，按批次任务书指令消耗）、共享池（多席位竞争使用，需要并发协调，防止抢占与重复消耗）。

席位维还应登记席位身份与能力画像。例如"G组-1号"是知识资产写手席位，擅长长文档产出；检索型、审计型席位各有所长。画像供G2的模型特长匹配与任务分派参考——把检索密集任务派给写作型席位，即使额度不浪费，时延与返工也是隐性浪费。

### 3.5 用途维：额度的消费去向

用途维穷举额度的消费去向，每笔消耗必须归入其一，不允许"其他"桶：

1. 产出正文：交付物主体文字，如本篇文档；
2. 检索取数：工具调用、数据查询、资料回溯；
3. 验证复核：对产出做正确性与合规检查；
4. 复盘自评：文末三维度自评与字数统计；
5. 协调通信：席位间任务传递、结果提交、问询应答；
6. 无效消耗：失败重试、超时作废、越线废弃。

其中第六类必须单列且醒目。无效消耗是效率治理（G2）的直接靶点，混入前五类会让"隐性浪费"永远不可见。登记时若一笔消耗跨越多类（先检索后写作），按主要去向归类，其余记入备注字段，保证去向往可追溯。

### 3.6 约束维：可用边界

约束维登记资产的可用边界，至少五项：限速（QPS或并发上限）；周期上限（日封顶、月封顶）；模型锁（允许与禁止的模型清单，含锁因）；合规红线——不得承诺收益或保本、不得输出催促性指令、不得涉对外公开与收费、不泄露任何Token与密钥；架构约束延伸——不得推翻harmony-app架构基调（适老化28-34fp大字白话卡片流、Stage模型compatibleSdkVersion 20 targetSdk 26、纯ArkTS零三方依赖等）。

合规红线来自批次任务书，应写入每个资产单元。要强调的是：红线约束的是产出内容与信息边界，与用哪个模型、哪个平台无关——降级、换源、换席位，任何路径都不能让红线松动半分。

## 四、登记模板

额度台账建议持久化为JSON文件（存放于治理目录，与本文同级），每单元一条：

```json
{
  "asset_id": "QUOTA-2026-0001",
  "time": {"type": "window", "start": "2026-08-27T22:20:45", "end": "2026-08-30T22:20:45", "carryover": 0},
  "model": {"allowed": ["GLM-5.3-Flash"], "locked": true, "lock_reason": "机主常设令：额度原因"},
  "platform": {"name": "席位宿主", "unit": "call", "initial": 400, "remaining": 400},
  "seat": {"owner": "G组-1号", "scope": "seat-self"},
  "usage": {"planned": ["产出正文", "复盘自评"], "actual": [], "wasted": 0},
  "constraints": {"qps": 2, "daily_cap": 100, "compliance": ["禁承诺收益/保本", "禁催促性指令", "禁对外公开收费", "禁泄露Token密钥"]}
}
```

若需在工程侧建模（例如云函数对`generate-tts`这类按需调用做额度控制），六字段结构同样适用：

```typescript
interface QuotaAsset {
  assetId: string
  timeType: 'window' | 'periodic' | 'onetime'
  window?: [string, string]      // 限时窗口起止，精确到分钟
  allowedModels: string[]        // 模型维：可抵扣清单
  platformUnit: 'token' | 'call' | 'point'
  seatScope: 'self' | 'pool'     // 席位维：自治或总池
  compliance: string[]           // 约束维：红线随资产走
}
```

## 五、登记规范六条

一单元一编号：每笔独立额度一个asset_id，跨期不复用编号，作废后封存不删除。时间必到分钟：禁止"三天内""本月里"这类模糊表述，起止时刻完整记录并含时区。模型精确到标识：厂商名只能作备注，不能作主键。消耗即记账：每笔消耗登记时间戳、用途归类与关联任务id，不做事后补录——补录必有遗漏。失效先核销：窗口关闭先核销该单元再进盘点，防止总账虚增。约束随资产走：调度任何额度前先读其约束维，模型锁优先级最高，其次合规红线，最后才是效率考量——顺序不能颠倒。

## 六、盘点与过期预警流程

日盘：每个自然日结束时核对各单元剩余量与当日消耗明细，差异当日溯源。窗口预警：限时窗口型资产在剩余时长不足百分之二十时升级提醒，并联动G3排期把该窗口额度提到燃烧队列首位；不足百分之十进入红区，非该窗口任务一律让路。月盘：对账平台账单与本地台账，差异超过百分之五必须逐笔核对，找出是漏记、错记还是平台侧计量口径不同。审计：定期抽查用途维归类质量，无效消耗占比超过百分之十触发G2效率复盘，超过百分之二十应当暂停该席位新任务并查因。

## 七、与harmony-app工程实体的对应关系

本批次五篇治理文档（G1至G5）本身即额度燃烧的产物，落盘于`GOVERNANCE/burn-output/`目录；文档正文汉字数与文末自评，即用途维"产出正文"与"复盘自评"两类的量化记录。云函数`generate-tts`按需生成TTS音频（alerts.json中audioUrl为undefined时端侧按需调用），消耗的是云端模型的额度，应登记在平台维的云端账本，并标注"按需触发"特性——它的消耗模式是离散事件型，与写手席位的连续作业型不同，监控阈值也应分设。`PushService.ets`在AGC未配置前降级轮询、Tushare失效（40101）后降级东财API——这类既有降级路径意味着不同数据源的调用额度存在替代关系，清单中应互相标注"替代关系"字段，供G4降级链直接引用，避免降级时临场找源。

## 八、常见登记错误对照表

| 错误写法 | 问题所在 | 正确写法 |
|---|---|---|
| "Flash余额充足" | 缺平台、缺单元、缺时间属性 | "席位宿主Flash调用配额余320次，月重置" |
| "体验额度快过期了" | 无截止时刻，预警无从算起 | "窗口至2026-08-30 22:20截止" |
| "随便用点额度验证下" | 用途未归类，浪费不可见 | "归类：验证复核，关联任务G4" |
| "切个大模型跑这个" | 越过模型锁 | "锁定Flash；深任务拆解为可验证浅步骤" |
| "还剩不少，先不管" | 席位维缺失，总池被悄悄占用 | "scope=pool，消耗须留调度指令号" |

## 九、小结

六维穷举清单是额度治理的地基：时间维定衰减节奏，模型维定抵扣范围，平台维定记账主体，席位维定调度权限，用途维定消费去向，约束维定使用边界。后续四篇——G2效率优化、G3窗口排期、G4降级链、G5监控仪表盘——全部建立在这份账本之上；账本不实，后面四篇皆是空中楼阁。清单本身不求一次登记完美，但求维度不缺、字段不糊，让每一次盘点都比上一次更接近真相。
